# Spec 63.5 — Floor Topic-Diversity via Embeddings

_Theme 63 Sub-Spec — Floor-Selector und Overage-Selector picken thematisch diverse Briefs via Cosine-Similarity-basiertem Score-Modifier auf Brief/Cluster-Embeddings._
_Status: Draft._
_Voraussetzung: clusters.embedding existiert (54.x). 63.7a+b+c gemerged._

---

## 1. Problem

KW21-Plan-Beobachtung 2026-05-21 nach allen Quality-Updates (63.1+63.2+63.3+63.6) zeigt:

**Cluster-Bucket (7 Floor + 1 Overage):**
- 2× OpenAI Codex Cluster-Items
- 2× RAG-bezogene Items
- 2× KI-Video-Tools Items
- 2× use_case "code-..." Items
- 2× Musik-KI Items

**Social-Bucket (~16-22 items):**
- 3× OpenAI Codex Social
- 2× RAG-related Social
- Mehrere Tool-Duplikate

**Root Cause:** Floor-Selector (`packages/pipelines/src/planning/steps/select-floor-items.ts`) und Overage-Selector picken **rein nach Score** ohne Diversity-Constraint. Wenn Pool 4 Briefs zum gleichen Tool/Thema enthält mit ähnlichen Scores, kommen alle 4 in den Plan.

**Konsequenz:** Plan wirkt thematisch redundant. SEO-Wert sinkt (interne Konkurrenz). Marcel reviewt manuell um Duplikate zu canceln.

## 2. Ziel

Soft-Diversity via Score-Modifier in Floor-Selector und Overage-Selector. Briefs mit hoher Cosine-Similarity zu **bereits gepickten** Briefs im selben Plan-Lauf bekommen einen Score-Malus.

**In Scope:**
- Floor-Selector erweitern: nach jedem pick die remaining-Briefs mit Diversity-Modifier rescoren
- Overage-Selector erweitern: gleiches Pattern
- Embedding-Source: brief.primaryKeyword → on-the-fly Voyage embedding ODER existing brief.embedding column (Phase 0 prüft was vorhanden ist)
- Score-Modifier: linearer Malus proportional zur max-Cosine-Similarity gegen bereits gepickte Briefs
- Nur für `cluster` und `social_post` content_types
- Diversity-Threshold + Malus-Factor konfigurierbar via project_planner_config

**Out of Scope:**
- Hard-Diversity (max 1 pro topic) — würde Goals unterfüllen
- Tag-Verteilung-Diversity (DistributeSlotDates ist separater Step, kein Floor)
- Comparisons Diversity (pair-uniqueness reicht)
- ki_wissen Diversity (Pool zu klein, nicht-Problem)
- LLM-basiertes Diversity-Reasoning (zu teuer)
- Re-evaluation existing Plan-Items (nur neue Picks)

**Aufwand:** 0.5-1 Tag.

## 3. Architektur-Entscheidungen

### 3.1 Diversity-Score-Formel

```
adjustedScore(brief, alreadyPicked) =
  baseScore(brief) - DIVERSITY_MALUS_WEIGHT * maxCosineSimilarity(brief, alreadyPicked)

maxCosineSimilarity(brief, picked) =
  max over picked_brief in picked: cosineSimilarity(brief.embedding, picked_brief.embedding)
```

**Beispiel:**
- baseScore = 0.85
- maxCosine = 0.92 (sehr ähnlich zu bereits gepicktem Brief)
- DIVERSITY_MALUS_WEIGHT = 0.5
- adjustedScore = 0.85 - 0.5 * 0.92 = 0.39

Brief mit weniger Ähnlichkeit (maxCosine = 0.3) hätte:
- adjustedScore = 0.85 - 0.5 * 0.3 = 0.70 → wird gepickt

**Threshold:** ab welcher Similarity beginnt der Malus? Optionen:
- A: linearer Malus ab 0 (jeder Brief bekommt Malus, Höhe proportional)
- B: Threshold + linear ab Threshold (z.B. unter 0.5 Similarity kein Malus, ab 0.5 linear)
- C: Sigmoid (smooth transition um Threshold)

**Empfehlung: Option B.** Begründung: thematisch verwandt aber nicht duplikat (similarity 0.3-0.5) ist OK, ab 0.5+ wird's Duplikat-Risiko. Konfiguration:
- `DIVERSITY_THRESHOLD = 0.5` (project_planner_config)
- `DIVERSITY_MALUS_WEIGHT = 0.5` (project_planner_config)

### 3.2 Embedding-Source pro Brief

Phase 0 prüft drei Optionen:

**Option A: brief.embedding column existiert**
- Direkt nutzen, kein zusätzlicher Cost
- Wenn nicht vorhanden, Migration nötig

**Option B: brief.cluster_id → clusters.embedding**
- Brief erbt Cluster-Embedding
- Nachteil: alle Briefs in einem Cluster hätten gleiches Embedding → no-op Diversity innerhalb Cluster
- Aber: Cross-Cluster Diversity wäre OK (verschiedene Cluster = verschiedene Embeddings)
- Cluster-loose Briefs (cluster_id=NULL) hätten kein Embedding → fallback nötig

**Option C: On-the-fly Voyage embedding von brief.primaryKeyword**
- Voyage embedding-3-light ~€0.0001 pro Embedding
- 1 Floor-Run mit 50 Briefs ≈ 50 embeddings = €0.005
- Trade-off: Cost vs Latenz vs Migration-Aufwand

**Empfehlung: Option C primary + Option B fallback.**
- Bei Floor-Run: embedding aus brief.primaryKeyword on-the-fly (Voyage)
- Cache via Map<briefId, embedding> für Lifetime des Runs
- Fallback: wenn primaryKeyword leer (sollte 63.1+63.2 nach nicht passieren), nutze clusters.embedding via cluster_id
- Wenn beides leer: skip diversity-modifier für diesen Brief (kein crash)

**Phase 0 verifiziert:** existiert brief.embedding schon? Wenn ja, Option A wäre noch besser (kostenlos, batch-precomputed).

### 3.3 Floor-Selector Integration

Aktueller Pseudo-Code in `select-floor-items.ts`:

```ts
for each contentType in [cluster, comparison, ki_wissen, social_post]:
  pool = buckets[contentType]
  target = targetWeeklyCount(goal)  // = minCount
  picked = pool.slice(0, target)    // FIFO over score
```

**Neu:**

```ts
for each contentType in [cluster, comparison, ki_wissen, social_post]:
  pool = buckets[contentType]
  target = targetWeeklyCount(goal)
  
  if (contentType IN ['cluster', 'social_post']):
    picked = pickWithDiversity(pool, target, embeddingProvider)
  else:
    picked = pool.slice(0, target)  // existing behavior
```

```ts
function pickWithDiversity(pool, target, embeddingProvider): Brief[] {
  const picked: Brief[] = [];
  const remaining = [...pool];
  
  while (picked.length < target && remaining.length > 0) {
    const scored = remaining.map(brief => ({
      brief,
      adjustedScore: adjustWithDiversity(brief, picked, embeddingProvider),
    }));
    scored.sort((a, b) => b.adjustedScore - a.adjustedScore);
    const top = scored[0];
    picked.push(top.brief);
    remaining.splice(remaining.indexOf(top.brief), 1);
  }
  
  return picked;
}
```

**Wichtig:** der Algorithmus ist O(target × pool.length × embedding-dim). Bei pool=100, target=10, dim=1024: 1M Operations pro Floor-Run. Akzeptabel (< 1 sec).

## 5. Backend — Implementation

### 5.1 Embedding-Provider

`packages/pipelines/src/planning/lib/diversity-embedding.ts` (new):

```ts
import { embedText } from '@marketing-auto/adapters-voyage';

export type EmbeddingProvider = {
  getForBrief(brief: TopicBrief): Promise<number[] | null>;
};

export function createPlanRunEmbeddingProvider(): EmbeddingProvider {
  const cache = new Map<string, number[]>();
  
  return {
    async getForBrief(brief) {
      if (cache.has(brief.id)) return cache.get(brief.id)!;
      
      const text = brief.primaryKeyword?.trim();
      if (!text) {
        // Fallback: clusters.embedding via cluster_id
        if (brief.clusterId) {
          const clusterEmbedding = await loadClusterEmbedding(brief.clusterId);
          if (clusterEmbedding) {
            cache.set(brief.id, clusterEmbedding);
            return clusterEmbedding;
          }
        }
        return null; // skip diversity for this brief
      }
      
      const embedding = await embedText(text, { model: 'voyage-3-light' });
      cache.set(brief.id, embedding);
      return embedding;
    },
  };
}
```

### 5.2 Diversity-Score-Calculator

`packages/pipelines/src/planning/lib/diversity-score.ts` (new):

```ts
export function cosineSimilarity(a: number[], b: number[]): number {
  let dot = 0, normA = 0, normB = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}

export function adjustScoreWithDiversity(
  baseScore: number,
  briefEmbedding: number[] | null,
  pickedEmbeddings: (number[] | null)[],
  config: { threshold: number; malusWeight: number },
): { adjustedScore: number; malus: number; maxSimilarity: number } {
  if (!briefEmbedding || pickedEmbeddings.length === 0) {
    return { adjustedScore: baseScore, malus: 0, maxSimilarity: 0 };
  }
  
  let maxSim = 0;
  for (const picked of pickedEmbeddings) {
    if (!picked) continue;
    const sim = cosineSimilarity(briefEmbedding, picked);
    if (sim > maxSim) maxSim = sim;
  }
  
  if (maxSim < config.threshold) {
    return { adjustedScore: baseScore, malus: 0, maxSimilarity: maxSim };
  }
  
  // Linear malus above threshold
  const malusRatio = (maxSim - config.threshold) / (1 - config.threshold);
  const malus = config.malusWeight * malusRatio;
  
  return {
    adjustedScore: baseScore - malus,
    malus,
    maxSimilarity: maxSim,
  };
}
```

### 5.3 pickWithDiversity Helper

`packages/pipelines/src/planning/lib/pick-with-diversity.ts` (new):

```ts
export async function pickWithDiversity<T extends TopicBrief>(
  pool: T[],
  target: number,
  embeddingProvider: EmbeddingProvider,
  config: { threshold: number; malusWeight: number },
  getBaseScore: (brief: T) => number,
): Promise<{ picked: T[]; reasons: Array<{ briefId: string; reason: string }> }> {
  const picked: T[] = [];
  const pickedEmbeddings: (number[] | null)[] = [];
  const remaining = [...pool];
  const reasons: Array<{ briefId: string; reason: string }> = [];
  
  while (picked.length < target && remaining.length > 0) {
    // Re-score remaining briefs with current picked set
    const scored = await Promise.all(remaining.map(async brief => {
      const briefEmb = await embeddingProvider.getForBrief(brief);
      const baseScore = getBaseScore(brief);
      const { adjustedScore, malus, maxSimilarity } =
        adjustScoreWithDiversity(baseScore, briefEmb, pickedEmbeddings, config);
      return { brief, adjustedScore, baseScore, malus, maxSimilarity };
    }));
    
    scored.sort((a, b) => b.adjustedScore - a.adjustedScore);
    const top = scored[0];
    
    picked.push(top.brief);
    pickedEmbeddings.push(await embeddingProvider.getForBrief(top.brief));
    remaining.splice(remaining.indexOf(top.brief), 1);
    
    const reasonText = top.malus > 0
      ? `picked #${picked.length} (base=${top.baseScore.toFixed(2)}, malus=${top.malus.toFixed(2)} from ${pickedEmbeddings.length - 1} picked, final=${top.adjustedScore.toFixed(2)})`
      : `picked #${picked.length} (score=${top.baseScore.toFixed(2)}, no diversity malus)`;
    
    reasons.push({ briefId: top.brief.id, reason: reasonText });
  }
  
  return { picked, reasons };
}
```

### 5.4 Floor-Selector Integration

`packages/pipelines/src/planning/steps/select-floor-items.ts`:

```ts
const DIVERSITY_CONTENT_TYPES: ContentType[] = ['cluster', 'social_post'];

export async function execute(ctx: StepContext) {
  // ... existing code: load buckets, goals, config ...
  
  const embeddingProvider = createPlanRunEmbeddingProvider();
  const diversityConfig = {
    threshold: parseFloat(plannerConfig.diversityThreshold),
    malusWeight: parseFloat(plannerConfig.diversityMalusWeight),
  };
  
  for (const goal of activeGoals) {
    const pool = buckets[goal.contentType] ?? [];
    const target = targetWeeklyCount(goal);
    
    if (DIVERSITY_CONTENT_TYPES.includes(goal.contentType) && diversityConfig.malusWeight > 0) {
      const { picked, reasons } = await pickWithDiversity(
        pool,
        target,
        embeddingProvider,
        diversityConfig,
        (brief) => brief.score ?? 0,
      );
      pickedItems.push(...picked.map((brief, idx) => ({
        brief,
        selectionReason: `Floor ${goal.contentType} #${idx + 1}/${target} — ${reasons[idx].reason}`,
      })));
    } else {
      // existing FIFO path
      const picked = pool.slice(0, target);
      pickedItems.push(...picked.map((brief, idx) => ({
        brief,
        selectionReason: `Floor ${goal.contentType} #${idx + 1}/${target}`,
      })));
    }
  }
}
```

## 8. Risiken

| Risiko | Mitigation |
|---|---|
| Voyage embedding cost zu hoch | Plan-Run mit 100 Briefs ≈ €0.01. Cache in-memory pro Run. Bei Cost-Sorge: Option A (precomputed brief.embedding) als Phase-E. |
| Algorithmus zu langsam (O(n*m*dim)) | Bei dim=1024, pool=100, target=10: 1M Ops ≈ 100ms. Akzeptabel. Bei Scale-up: cosine-table cache. |
| Diversity-Filter underfüllt Goals | Soft-Modifier ändert nur Reihenfolge, nicht Count. Target wird trotzdem erreicht (worst case: 7 ähnliche Briefs, alle gepickt mit graduiertem Malus). |
| Embedding-Provider failt für alle Briefs | Fallback in createPlanRunEmbeddingProvider: cluster_id → clusters.embedding. Wenn beide leer: return null → kein malus für diesen Brief → existing FIFO behavior. |
| primary_keyword ist nicht ausreichend für Embedding | Plus topic_title als zusätzlicher Context? Phase 0 prüft was Briefs typisch haben. Falls primary_keyword too sparse: embed `${primaryKeyword} ${topicTitle}` |
| Marcel will Diversity zwischen verschiedenen Plan-Wochen (KW21 hatte RAG, KW22 sollte nicht wieder RAG) | Out of Scope für 63.5. Phase-E: longitudinal-diversity via embedding-similarity zu vorherigen Plan-Items. |
| selection_reason wird zu lang für UI | Truncate auf 200 chars. Detail-View kann Full-Text zeigen. |
| Score-Modifier macht Plan unvorhersehbar | Logging-Transparenz via selection_reason. Plus malusWeight=0 als Off-Switch in Settings. |

**Migration:** `0085_project_planner_config_diversity` (idx 85, when 1786300000000).
Adds `diversity_threshold numeric(4,3) NOT NULL DEFAULT 0.5 CHECK (0..1)` and
`diversity_malus_weight numeric(4,3) NOT NULL DEFAULT 0.5 CHECK (0..2)` to

**Backend — Diversity-Lib (Spec 63.5 §5):**
- [packages/pipelines/src/planning/lib/diversity-score.ts](packages/pipelines/src/planning/lib/diversity-score.ts) — pure `cosineSimilarity` + `adjustScoreWithDiversity` with linear-above-threshold malus. Null-safe (zero vectors / mismatched lengths return 0 instead of NaN). `threshold>=1` OR `malusWeight==0` short-circuit to "diversity off".
- [packages/pipelines/src/planning/lib/diversity-embedding.ts](packages/pipelines/src/planning/lib/diversity-embedding.ts) — generic `EmbeddingProvider<T>` with three concrete factories:
  - `createPlanRunEmbeddingProvider` for `TopicBrief` (embeds `${primaryKeyword} ${topicTitle}`, falls back to `clusters.embedding` via `brief.clusterId`, returns `null` last)
  - `createSignalEmbeddingProvider` for `SignalTopNEntry` (embeds `signal.title`, no cluster fallback)
  - `createArticleEmbeddingProvider` for the `ArticleLike` shape used by the Social-post selector
  - Embedding text builder + cluster fallback shared via `embedWithCache` internal helper
  - Per-instance Map-based cache; Voyage errors logged as `warn` and degraded to fallback / null

## 12. Discovered & Deviations

| # | Discovery | Decision |
|---|---|---|
| 1 | `topic_briefs.embedding` does NOT exist (Phase 0 grep) — only `articles.embedding` and `clusters.embedding` are vector columns. | Option C + B fallback per spec recommendation: embed `${primaryKeyword} ${topicTitle}` on-the-fly via Voyage, fall back to `clusters.embedding` via `brief.clusterId`, return null last. No migration adding a brief-level embedding column. Phase E could revisit if Voyage cost becomes meaningful. |
| 2 | Cosine-similarity helper already lives in `packages/pipelines/src/article/author-picker/embedding.ts` but is private to that file and only used by AuthorPick. | Reimplemented in `diversity-score.ts` (~15 LoC) rather than refactoring author-picker's private helper into a shared export. Decision documented in code — duplication is small and the two callers might diverge (author-picker uses 0.55 threshold; diversity uses runtime-configurable 0.5 with malus). |
| 3 | Brief score sources are heterogeneous: trend `trendMetadata.trendScore` ∈ ~[0, 100], comparison `comparisonMetadata.score` ∈ [0, 1], gap/manual have no numeric score. | Per Marcel's clarification (variant C): `normalizeBriefBaseScore` lives in `pick-with-diversity.ts` and maps each source to [0, 1]: trend / 100, comparison as-is, others use FIFO surrogate `1 - index/poolLen`. Tested in `pick-with-diversity.test.ts`. |
| 4 | Spec wrote `embedText` from `@marketing-auto/adapters-voyage` (plural, hypothetical name). The actual export is `voyage.embed(text, ctx)` from `@marketing-auto/adapter-voyage` (singular) as called by 9 existing planner sites. | Used the real API. `EmbedContext = { projectId, operation, pipelineRunId? }`. Logged as `COST_OPS.VOYAGE_EMBED_TEXT` per the existing trend-discovery pattern. |
| 5 | The Floor selector + Overage selector both want shared embedding caches across steps (Voyage isn't free, even if cheap). | Two-tier: each step instantiates its own provider (one Voyage call per brief per step). Overage selector pays Voyage twice for Floor-picked briefs (~€0.001 per plan-run). Shared-state across step instances would require mutating step-context, which the engine forbids. Accepted as a trade-off; documented in the Overage selector header. |
| 6 | `pickWithDiversity` was initially typed `T extends TopicBrief`. The Overage and Social-post selectors needed it for signals + articles respectively — different shapes. | Refactored to generic `T` with `getItemId` + `getBaseScore` callbacks, and split the embedding provider into three source-specific factories sharing an internal `embedWithCache` helper. Cleaner abstraction, no perf cost. |
| 7 | The Social-post `fromTodayPlans` source is parent-bound to Floor cluster items — its diversity is already enforced by the Floor pick. Applying diversity-rescoring there would either no-op (parents already diverse) or wrongly re-order the parent→child link. | Diversity in `SelectSocialPostItemsStep` is applied only to the `fromRefresh` + `fromPool` sub-paths (article-sourced). The article picker is seeded with Floor cluster + social_post brief embeddings so refresh/pool picks avoid covering Floor topics. |
| 8 | The Floor / Overage / Social-post step tests previously instantiated the steps with no constructor args — adding diversity made them fire live Voyage calls against fake-project UUIDs, producing 429s and `cost_logs` FK violations in CI logs. | Added optional `Select*Deps.create*EmbeddingProvider` factories so tests can inject `createNullBriefProvider` / `createNullSignalProvider` / `createNullArticleProvider`. Tests stay offline; production runs use the Voyage-backed defaults. New `null-providers.ts` test helper. |
| 9 | `loadArticleTitles` was a title-only helper in `SelectSocialPostItemsStep`. Diversity needs title + meta_description + clusterId for each article candidate. | Replaced with `loadArticleMeta` returning `ArticleSocialMeta { id, title, embeddingText, clusterId }`. Backwards-incompatible test-dep rename — migrated all 5 inline test deps + the canonical `emptyDeps()` helper. Plant a memory rule if other selectors gain similar shape extensions. |
| 10 | `SnapshotInputsStep.config` was already established by Spec 62.5.1 as the reproducibility SSoT for `llmMode`. The diversity knobs need the same treatment so a replay reproduces the same picks. | Added `diversityThreshold` + `diversityMalusWeight` to `plannerConfigSnapshotSchema` with `.default(0.5)`. Pre-63.5 plans replay through the default. Selectors read from the snapshot, not from `validate-goals.config`, so the contract is single-source-of-truth even if Marcel moves the sliders between plan generation and approval. |
| 11 | The German typography rule (`„…"` in double-quoted TS string literals breaks the parser) caught me on the `diversitySection.description` key in DE. | Switched the outer quotes to single quotes for that one string — same fix the spec memory rule documents. Also applied curly-closing `“` instead of straight `"` for visual correctness. |
| 12 | The `BriefEmbeddingProvider` interface needs both `getForItem(brief)` (generic) AND `getForBrief(brief)` (back-compat) because some callers use the named verb. | Both methods point at the same underlying function (`getForItem` is the canonical; `getForBrief` is the alias). No behavioural difference; the alias makes Floor selector code read naturally. |
