# Spec 62.2 — Project Goals + Cadence-DSL

_Theme 62 Sub-Spec — defines what content the Planner should generate per project per week._
_Status: Draft._
_Voraussetzung: 62.0a + 62.0a-followup + 62.0b sind gemerged. (62.1 existiert nicht — siehe 62.0b Header.)_

---

## 1. Ziel

62.2 definiert **was der Planner generieren soll**, ohne den Planner selber zu bauen (das ist 62.4). Konkret:

- DB-Schema für `project_goals` und (optional) `goal_overage_policies`
- CRUD-API für Goals
- UI zum Pflegen der Goals
- Validator-Modul `validateGoals(projectId)` als Library-Export, von 62.4 konsumierbar

**Out of Scope:**
- Planner-Engine selber (62.4)
- Signal-Score-Berechnung für Übererfüllung (62.3 + 62.4)
- Cost-Aggregation (62.0a Cost-Estimator existiert schon, 62.2 nutzt nur die Defaults)

**Geschätzter Aufwand:** 1-1.5 Tage.

## 2. Architektur-Entscheidungen

Aus Marcel-Antworten:

- **Mix-Cadence:** Jedes Goal hat `unit: "per_week" | "per_day"`. Cluster = per_day (1/Tag), Comparison = per_week (1/Woche), Social = per_day (3/Tag im Schnitt), KI-Wissen = per_week (3/Woche). Wochenweise-Goals sagen "über die Woche", tagweise-Goals sagen "im Schnitt pro Tag".
- **Top-N Signal-driven Übererfüllung:** Pro Projekt eine Config `topNSignalsAllowedOverage: number` (default 3). 62.2 speichert nur die Config, 62.4 wertet sie aus.
- **Sub-Budgets pro Content-Type:** Globales Budget bleibt hart (`weeklyBudgetEur`). Optional `perTypeMaxEur` JSONB-Map für Sanity-Checks. Beide werden vom 62.0a Cost-Estimator konsumiert.
- **Floor-Cadence, nicht Strict:** `min` ist Pflicht (immer mindestens N), `max` ist optional (Cap für Übererfüllung — wenn NULL, kein Cap außer globales Budget).
- **UI-Placement:** Spec lässt offen, gibt Empfehlung. Claude Code entscheidet basierend auf Codebase-Realität.
- **Single Goals-Set pro Projekt (kein Historie-Tracking in 62.2).** Goals werden überschrieben, nicht versioniert. Audit kommt später wenn nötig.

## 3. Datenbank-Migration

### 3.1 Migration `0071_project_goals.sql`

```sql
-- 1) project_goals: per-project, per-content-type cadence definitions
CREATE TABLE project_goals (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id      uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  
  -- What content type this goal applies to
  content_type    text NOT NULL,                    -- 'cluster' | 'comparison' | 'social_post' | 'ki_wissen' | (extensible)
  
  -- Cadence definition
  cadence_unit    text NOT NULL,                    -- 'per_day' | 'per_week'
  min_count       integer NOT NULL,                 -- floor (mandatory minimum)
  max_count       integer NULL,                     -- ceiling for overage (NULL = no per-type cap)
  
  -- Lifecycle
  is_active       boolean NOT NULL DEFAULT true,    -- soft-disable without deleting
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now(),
  
  -- Notes (optional, free text)
  note            text NULL,
  
  -- One active goal per (project, content_type) — soft enforcement; multiple inactive ok
  CONSTRAINT project_goals_unique_active EXCLUDE USING btree (project_id WITH =, content_type WITH =) WHERE (is_active = true)
);

CREATE INDEX project_goals_project_id_idx ON project_goals (project_id) WHERE is_active = true;

-- 2) project_planner_config: per-project planner-wide settings (budget, overage policy)
-- Singleton-per-project pattern. Could've been a JSON blob on projects table, but separate
-- table is clearer for adding fields later (e.g. cron config in 62.7).
CREATE TABLE project_planner_config (
  project_id                       uuid PRIMARY KEY REFERENCES projects(id) ON DELETE CASCADE,
  
  -- Budget
  weekly_budget_eur                numeric(10,2) NOT NULL,                   -- hard global cap (e.g. 50.00)
  per_type_max_eur                 jsonb NULL,                               -- optional: { cluster: 35, social: 5, comparison: 5, ki_wissen: 5 }
  
  -- Overage policy
  top_n_signals_allowed_overage    integer NOT NULL DEFAULT 3,               -- Top-N signals can each unlock +1 item over floor
  max_overage_per_signal           integer NOT NULL DEFAULT 1,               -- how many extra items per qualifying signal (usually 1)
  
  -- Lifecycle
  created_at                       timestamptz NOT NULL DEFAULT now(),
  updated_at                       timestamptz NOT NULL DEFAULT now()
);

-- 3) Content-type enum is NOT a PostgreSQL enum (purposefully).
-- Rationale: pgEnum ADD VALUE is awkward in migrations (62.0a Lesson D12).
-- Validation is enforced via Zod schema at the API/service layer instead.
```

**Note on EXCLUDE constraint:** ensures only one active goal per `(project, content_type)`. Allows multiple inactive rows (for soft history). If a btree EXCLUDE doesn't sit right with the codebase's pattern, fall back to partial unique index:

```sql
CREATE UNIQUE INDEX project_goals_one_active_per_type
  ON project_goals (project_id, content_type)
  WHERE is_active = true;
```

Claude Code entscheidet welche Variante zur Codebase passt — beide haben gleiche Semantik.

## 4. Validator-Modul (Library-Export für 62.4)

Diese Funktion wird vom 62.4 Planner-Engine als erstes aufgerufen, um zu prüfen ob ein Projekt überhaupt planbar ist.

`packages/cost-tracker/src/goal-validator.ts` (oder in einem neuen `packages/planner/` Modul falls Claude Code das sauberer findet):

```ts
export interface GoalValidationResult {
  valid: boolean;
  errors: Array<{ code: string; message: string }>;
  warnings: Array<{ code: string; message: string }>;
  resolvedGoals: ProjectGoal[];  // active goals only, sorted by content_type
  config: ProjectPlannerConfig;
}

export async function validateProjectGoals(
  projectId: string,
  options: { resolvePipelineSteps: PipelineStepResolver } // for cost-estimate sanity check
): Promise<GoalValidationResult> {
  // 1. Load active goals + config
  // 2. Required: at least 1 goal per project (else "no goals defined")
  // 3. Required: planner_config row exists (else "no budget configured")
  // 4. Warning: if all goals are "per_week, min: 0" → effectively planner does nothing
  // 5. Sanity: weekly cost-estimate from min_count * historical_avg per type
  //    via estimateWeeklyPlanCost (62.0a Cost-Estimator)
  //    If estimate > weeklyBudgetEur → ERROR ("floor exceeds budget")
  //    If estimate > weeklyBudgetEur * 0.85 → WARNING ("floor near budget, no overage room")
  // 6. Sub-budget consistency: per-type-max-eur sum should not exceed global budget
  //    (else WARNING — not error, sub-budgets can be aspirational caps)
  //
  // Returns valid=false only on errors; warnings are advisory.
}
```

**Error-Codes:**
- `NO_GOALS_DEFINED` — Projekt hat keine aktiven Goals
- `NO_PLANNER_CONFIG` — Projekt hat keinen `project_planner_config` Row
- `FLOOR_EXCEEDS_BUDGET` — `sum(min_count * avg_cost) > weekly_budget_eur`
- `INVALID_CADENCE_UNIT` — sollte nie passieren wegen Zod, defensive
- `INVALID_MIN_MAX` — sollte nie passieren wegen Zod-Refinement

**Warning-Codes:**
- `FLOOR_NEAR_BUDGET` — Floor verbraucht ≥85% des Budgets, kein Übererfüllungs-Raum
- `SUB_BUDGETS_OVER_GLOBAL` — `sum(per_type_max_eur) > weekly_budget_eur` (Sub-Budgets sind Caps, nicht Quotas, aber inkonsistent)
- `ALL_GOALS_INACTIVE_OR_ZERO` — Planner wird effektiv nichts produzieren

Diese Validierung lebt im `packages/cost-tracker` (oder neuem `packages/planner`) damit 62.4 ohne `apps/api`-Abhängigkeit darauf zugreifen kann (Lesson D15 aus 62.0a: cost-tracker bleibt leaf).

## 5. API-Endpoints

In neuem File `apps/api/src/routes/project-goals.ts` (analog zu `prompt-versions.ts` aus 62.0b):

```ts
// Goals CRUD
GET    /api/projects/:slug/goals                  // list active goals
PUT    /api/projects/:slug/goals                  // upsert full goal-set (replace all active)
PATCH  /api/projects/:slug/goals/:goalId          // toggle is_active, update min/max
DELETE /api/projects/:slug/goals/:goalId          // soft-delete (is_active=false)

// Planner config (singleton)
GET    /api/projects/:slug/planner-config         // get or null
PUT    /api/projects/:slug/planner-config         // upsert (full replace)

// Validation endpoint
GET    /api/projects/:slug/goals/validate         // returns GoalValidationResult
```

**PUT semantics for goals:** Body ist ein Array von Goals. Server diff'd gegen DB-State:
- Goals im Body, nicht in DB → Insert
- Goals in DB, nicht in Body → `is_active=false` (soft delete)
- Goals in beiden → Update

Das vereinfacht das UI (Editor speichert immer den gesamten State), erlaubt Marcel z.B. ein Goal komplett zu entfernen ohne separate DELETE-Calls.

**Authorization:** gleiche Konvention wie `articleRoutes` (62.0a-followup Pattern: keine per-route Tightening jetzt, kommt mit Multi-Tenant-SaaS-Posture).

## 9. Risiken

| Risiko | Mitigation |
|--------|-----------|
| EXCLUDE-Constraint inkompatibel mit Drizzle-Migrator | Fallback auf partial unique index dokumentiert in §3.1 |
| `content_type` als text statt enum → Tippfehler werden persisted | Zod-Validierung an API-Layer, Drizzle `$type` Hint, Tests asserieren |
| Validator-Library Cyclic-Dep zu packages/pipelines | Pattern aus 62.0a-D15: callback-injection für `resolvePipelineSteps`. cost-tracker bleibt leaf. |
| Cost-Estimate-Defaults zu niedrig → "Floor near budget" false-positive | Defaults aus 62.0a Cost-Estimator nutzen (€0.30 article:blog, €4.20 cluster, etc.). 30-day-Historie fallback. |
| Marcel ändert Goals während Planner-Run läuft (62.4) | 62.4 wird Goals zu Run-Start snapshotten. 62.2 muss sich nicht drum kümmern. |
| UI-Placement-Decision falsch → User findet Feature nicht | Cmd+K-Action garantiert Erreichbarkeit unabhängig vom Placement |

## 12. Deviations from Spec (post-implementation)

- **Partial unique index, not EXCLUDE** — §3.1 listed both as valid. Chose `CREATE UNIQUE INDEX … WHERE is_active = true` for parity with the rest of the codebase (`prompt_versions_one_golden_per_step`, `refresh_suggestions`). Same semantic guarantee.
- **Validator stayed in `packages/cost-tracker`** — §4 allowed either `cost-tracker` or a new `packages/planner`. Kept it in cost-tracker since `estimateWeeklyPlanCost` already lives there; no new workspace package created.
- **`CONTENT_TYPE_TO_PIPELINE` map added in [goal-validator.ts](../packages/cost-tracker/src/goal-validator.ts)** — not specified in §4. Needed to expand each `(contentType, cadenceUnit, minCount)` triple into N synthetic `PlannedItem` rows for `estimateWeeklyPlanCost`. Must be extended in lockstep with any new entry in the `CONTENT_TYPES` enum in `packages/shared/src/types/project-goals.ts`.
- **PATCH `/goals/:goalId` does NOT have an in-route collision check** — §5 PUT semantics handle the diff-replace path; the standalone PATCH route just trusts the partial unique index. An initial draft included a post-UPDATE collision-detection guard; /review-task flagged it as dead logic (the index has already accepted or rejected the operation by the time the check runs). Removed; race-condition violations now surface as 500. Documented as a Common Mistake in `apps/api/CLAUDE.md`.
- **`numeric` columns typed as `$type<string>()`** — §3.2 schema example omitted this. Added to match the codebase's universal Drizzle `numeric` convention (`linkRebuildRuns.totalCostEur`, `idempotencyOutputs.costEur`). Helpers coerce at the boundary (`toFixed(2)` on write, `parseFloat()` on read).
- **Singleton-per-project config table written via `onConflictDoUpdate` on PK** — §3 specified "singleton-per-project pattern" but not the helper shape. `upsertProjectPlannerConfig` uses `db.insert(...).onConflictDoUpdate({ target: projectPlannerConfig.projectId, set: {...} })` to keep the upsert atomic.
- **`note` field is `text NULL` + Zod `.nullable().optional()`** — §3.1 used `note text NULL` but §3.3 had `z.string().optional()`. Aligned to `.nullable().optional()` so empty input clears the column to NULL, consistent with how the UI's `noteInput.trim() === ""` collapses to "no note".

## 13. Discovered During Implementation

- **Cmd+K action keys live in `i18n/{de,en}/search.ts`** — not in `settings.ts`. Added `actionPlannerGoals` + `actionPlannerGoalsSubtitle` as siblings of the existing `actionPausedRuns*` pair (Spec 62.0a Section 7). The action's `href` deep-links to `/projects/${slug}/settings/planner`.
- **`apiPut` already exists in `apps/web/src/lib/api.ts`** — added in Spec 57.3. No new helper needed for the PUT-replace pattern.
- **`SettingsPage.vue` adds sections to `sections` array AND the route children** — both must be updated together so the sidebar nav renders the new entry and the route resolves. The `i18n` entry under `settings.sections.<key>` is what the sidebar reads via `$t(\`settings.sections.${section.key}\`)`.
- **Bun's PATCH-collision-on-partial-unique surfaces as 500 by default** — Hono has no default error handler for postgres unique-violation errors. If you want a clean 409 for the rare race-condition case, catch in the helper and translate. Current Spec 62.2 implementation accepts the 500 (single-tenant Toolwiki, no expected concurrent PATCH from two clients).
