# Spec 62.8 — Production-Run Execution

_Theme 62 Sub-Spec (final) — approved Plans triggern echte Item-Generation. Jedes planned_item wird zur Pipeline-Run und produziert echten Content. Batch-API-Integration. Skip+Retry-Failure-Handling. Budget-Gate._
_Status: Draft._
_Voraussetzung: 62.0a + 62.0b + 62.2 + 62.3 + 62.4 + 62.5 + 62.5.1 + 62.6 + 62.7 sind gemerged._

---

## 1. Ziel

Approved Plans laufen tatsächlich aus. Marcel klickt "Approve" auf einen Wochenplan, und das System generiert alle Content-Items innerhalb von Minuten/Stunden. Items landen als "ready" Assets in der DB und warten dort auf Distribution (Phase E).

**Mental-Model:**

```
Approve (jetzt) → Generation (sofort) → Items ready → Distribution (Phase E, separate Spec)
```

**62.8 verantwortet die mittleren zwei Schritte.** Distribution = wann/wo published wird ist Phase E.

**In Scope:**
- Item-Status-Lifecycle: `planned → enqueued → generating → ready → published`
- BullMQ-Job pro planned_item, routet zur passenden Content-Pipeline (Cluster, Blog, Comparison, KI-Wissen, Social)
- Batch-API standardmäßig bei `llmMode='batch'`
- Auto-Retry 1x mit 5-min Backoff, dann skip+log
- Hard Budget-Gate: wenn aktueller Spend > 90% Weekly-Budget → keine neuen Items enqueuen
- UI: PlannerCalendar zeigt per-Item Status-Icons + Progress-Indikator
- Approve-Action erweitern: triggert Enqueue-Loop
- Item-Detail-View (oder Inline-Expand) zeigt pipeline_run-Link für Debugging

**Out of Scope (Phase E):**
- Distribution-Layer (wann/wo published)
- Channel-Schedules (LinkedIn Mo 9:00 etc.)
- Engagement-Tracking
- slot_datetime statt slot_date (bleibt erstmal Tag-Auflösung)
- Article-Refresh-Workflow (62.8 erzeugt nur new content, refresh ist eigener Workflow)
- Plan-Pausieren/Resumen (kein Pause-Toggle, nur Cancel)
- Per-Item-Override "manuell editieren statt Pipeline" (Marcel triggert Pipeline immer)

**Geschätzter Aufwand:** 1.5-2 Tage. Größte Spec im Theme nach 62.6 — viele bewegliche Teile aber gut abgegrenzt.

## 2. Architektur-Entscheidungen

### 2.1 Item-Status-Lifecycle

```
┌─────────┐  approve   ┌──────────┐  worker picks up   ┌────────────┐  pipeline done   ┌───────┐
│ planned │ ─────────> │ enqueued │ ─────────────────> │ generating │ ──────────────> │ ready │
└─────────┘            └──────────┘                    └────────────┘                  └───────┘
                                                              │
                                                              ↓ pipeline fails (after retry)
                                                       ┌────────┐
                                                       │ failed │
                                                       └────────┘
                                                       
ready ─ (Phase E Distribution-Layer) ─> published
```

**Per-Item-Pipeline-Lookup:** `planned_items.pipeline_run_id` (neu) referenziert den konkreten Pipeline-Run der dieses Item generiert. Bei Retry wird neue pipeline_run_id geschrieben (alte bleibt in History via pipeline_runs.parent_run_id).

**Failed-Items werden NICHT in der Quarantäne (62.7) angezeigt** — die zeigt nur failed Plan-Generation-Runs, nicht Item-Execution-Runs. Falls Quarantäne erweitert werden soll: eigene Spec.

### 2.2 Approve-Trigger-Mechanik

Bei Plan-Approve im UI:

1. Frontend ruft `POST /api/projects/:slug/plans/:planId/approve` (existing aus 62.5 — Body wird erweitert)
2. Backend transitioniert plan-status `draft → approved` (existing 62.5)
3. **NEU:** Backend enqueued in BullMQ Queue `plan-execution` einen einzigen Job `{ planId }`
4. Worker `plan-execution-worker` läuft:
  - Iteriert alle planned_items mit status='planned'
  - Pro Item: Budget-Check (§2.5), wenn OK → status='enqueued' + Job in passende Pipeline-Queue
  - Wenn Budget knapp: status bleibt 'planned' mit Reason-Field, Loop terminiert
5. Response an Frontend: `{ enqueued: N, blocked_by_budget: M }`

**Wichtig:** Approve ist atomar — Marcel klickt einmal und die ganze Logic-Cascade läuft. Keine zweite Action nötig.

### 2.3 Pipeline-Routing pro Item-Type

Jedes planned_item.content_type → eine spezifische Pipeline:

| content_type | source_kind | Pipeline | Input |
|---|---|---|---|
| `cluster` | `topic_brief` | ClusterGenerationPipeline | `{ briefId, projectId, llmMode }` |
| `comparison` | `topic_brief` | BlogPipeline | `{ briefId, projectId, collectionType: 'comparisons', llmMode }` |
| `ki_wissen` | `topic_brief` | BlogPipeline | `{ briefId, projectId, collectionType: 'ki-wissen', llmMode }` |
| `social_post` | parent-cluster oder refresh oder pool | SocialImagePipeline | `{ articleId / parentArticleId, llmMode }` |

**Implementation:** `getPipelineForItem(item)` Helper in `packages/planner/src/execution/pipeline-router.ts`. Pure function `(item) → { pipelineName, jobData }`.

### 2.4 Batch-API standardmäßig wenn llmMode='batch'

Item-Execution-Worker holt `projects.llmMode` und passt es in alle Pipeline-Inputs durch (siehe Routing-Tabelle).

Pipelines selbst sind die Stelle wo Batch vs Sync entschieden wird (bereits aus 62.0a/62.5.1 Mechanik). 62.8 reicht den Mode-String durch, mehr nicht.

**Default-Modus für Toolwiki (sync):** Toolwiki bleibt sync bis Marcel auf batch flippt. Per-Project-Setting, keine Item-Level-Override.

### 2.5 Hard Budget-Gate (90%)

Vor jedem Item-Enqueue:

```ts
const currentSpend = await getWeeklySpend(projectId, isoWeek);
const weeklyBudget = await getWeeklyBudget(projectId);
const itemEstimate = item.estimatedCostEur;

if (currentSpend + itemEstimate > weeklyBudget * 0.9) {
  await markItemBlocked(item.id, { reason: 'budget_gate' });
  break; // stop enqueuing further items
}
```

**Reasoning:**
- Schwellwert 0.9 nicht 1.0 — Buffer für Schätzungs-Fehler (LLM-Calls können 20% teurer werden)
- Plan-Approve hat schon `BudgetGateStep` (62.4) — diese Layer ist die zweite Sicherheit gegen mid-week Drift
- "blocked" Items bleiben in status='planned' mit explanation, NICHT gefailed — Marcel kann später entweder Budget erhöhen + retrigger oder Items canceln

**Frontend-Behaviour:** PlannerCalendar zeigt "blocked" Items grau mit Warnung-Icon und Tooltip "Skipped due to budget gate (95% of weekly budget reached)".

### 2.6 Auto-Retry mit Backoff

BullMQ-Job-Config pro Item:

```ts
{
  attempts: 2,         // initial + 1 retry
  backoff: {
    type: 'fixed',
    delay: 5 * 60 * 1000, // 5 minutes
  },
  removeOnComplete: { count: 1000 },
  removeOnFail: { count: 1000 },
}
```

**Wichtig:** Retry passiert auf BullMQ-Job-Level, nicht auf Item-Level. Heißt:
- Item-status flippt zu 'generating' beim ersten Versuch
- Wenn Versuch 1 failed → BullMQ wartet 5 Min → Versuch 2
- Wenn Versuch 2 failed → BullMQ markiert Job failed → Item-status flippt zu 'failed'
- Plan-Execution-Worker pickt nicht das gleiche Item nochmal auf (sonst Endlos-Loop)

**Audit-Trail:** `pipeline_runs` für beide Attempts werden persistiert via `parent_run_id` Mechanik (existing aus 62.0a). Marcel kann in 62.6 Debug-UI beide Attempts inspizieren.

### 2.7 Manual Item-Retry (post-failure)

Nach Item-Failure kann Marcel im PlannerCalendar pro Item ein "Retry"-Button anklicken:
- Item-Status flippt 'failed' → 'enqueued'
- Neuer BullMQ-Job mit gleicher pipeline-config
- Budget-Check läuft erneut
- Neue pipeline_run_id

Granular per-item, NICHT plan-weit.

## 4. Backend — Plan-Execution-Worker

### 4.1 Queue + Worker

`packages/pipelines/src/execution/plan-execution-queue.ts`:

```ts
export const planExecutionQueue = new Queue<{ planId: string }>("plan-execution", {
  connection: getRedisConnection(),
});

export const planExecutionWorker = new Worker<{ planId: string }>(
  "plan-execution",
  async (job) => {
    const { planId } = job.data;
    return await executePlan(planId);
  },
  {
    connection: getRedisConnection(),
    concurrency: 1, // one plan-execution at a time per project
  },

```

### 4.2 `executePlan()` Logic

`packages/pipelines/src/execution/execute-plan.ts`:

```ts
async function executePlan(planId: string) {
  const plan = await db.query.weeklyPlans.findFirst({ where: eq(weeklyPlans.id, planId) });
  if (!plan || plan.status !== 'approved') {
    throw new Error(`Plan ${planId} not approved`);
  }

  const project = await db.query.projects.findFirst({ where: eq(projects.id, plan.projectId) });
  const llmMode = project.llmMode;

  const items = await db.query.plannedItems.findMany({
    where: and(
      eq(plannedItems.weeklyPlanId, planId),
      eq(plannedItems.executionStatus, 'planned'),
    ),
    orderBy: [asc(plannedItems.slotDate), asc(plannedItems.position)],
  });

  const stats = { enqueued: 0, blocked: 0 };

  for (const item of items) {
    // Budget pre-check
    const currentSpend = await getWeeklySpend(plan.projectId, plan.targetIsoWeek);
    const budget = await getWeeklyBudget(plan.projectId);
    
    if (currentSpend + (Number(item.estimatedCostEur) || 0) > budget * 0.9) {
      await markItemBlocked(item.id, 'budget_gate');
      stats.blocked++;
      break; // stop enqueuing
    }

    // Route to pipeline + enqueue
    const { pipelineName, jobData } = getPipelineForItem(item, llmMode);
    const job = await enqueueItemPipeline(pipelineName, jobData);
    
    await markItemEnqueued(item.id, job.id);
    stats.enqueued++;
  }

  return stats;
}
```

### 4.3 Pipeline-Router

`packages/planner/src/execution/pipeline-router.ts`:

```ts
type RoutedJob = {
  pipelineName: string;
  jobData: Record<string, unknown>;
};

export function getPipelineForItem(
  item: PlannedItem,
  llmMode: 'sync' | 'batch',
): RoutedJob {
  const pipelineInput = item.pipelineInput as Record<string, unknown>;
  
  switch (item.contentType) {
    case 'cluster':
      return {
        pipelineName: 'cluster:full-plan',
        jobData: { ...pipelineInput, llmMode, plannedItemId: item.id },
      };
    
    case 'comparison':
      return {
        pipelineName: 'article:blog',
        jobData: { ...pipelineInput, collectionType: 'comparisons', llmMode, plannedItemId: item.id },
      };
    
    case 'ki_wissen':
      return {
        pipelineName: 'article:blog',
        jobData: { ...pipelineInput, collectionType: 'ki-wissen', llmMode, plannedItemId: item.id },
      };
    
    case 'social_post':
      return {
        pipelineName: 'social:image',
        jobData: { ...pipelineInput, llmMode, plannedItemId: item.id },
      };
    
    default:
      throw new Error(`Unknown contentType: ${item.contentType}`);
  }
}
```

### 4.4 Pipeline-Run-Hook für Status-Updates

Jede Content-Pipeline muss `plannedItemId` aus jobData lesen und am Anfang + Ende den Item-Status updaten:

**Beim Start:** `plannedItems.executionStatus = 'generating'`, `generationStartedAt = NOW()`, `pipelineRunId = ctx.runId`

**Bei Erfolg:** `plannedItems.executionStatus = 'ready'`, `generationCompletedAt = NOW()`

**Bei Failure (nach Retry-Versuch):** `plannedItems.executionStatus = 'failed'`, `generationCompletedAt = NOW()`

**Mechanismus:** Zentrales `updatePlannedItemStatus()` Helper in `packages/db/src/helpers/planned-items-write.ts`. Pipelines callen es via `ctx.afterComplete()` und `ctx.onError()` Hooks (62.0a Pattern).

### 4.5 Plan-Status-Aggregation

`weekly_plans.status` flippt automatisch wenn alle Items finalisiert sind:
- Wenn alle Items in (`ready`, `failed`) → plan-status flippt zu `completed` (mit Sub-Status `partial_failure` falls failed > 0)
- Trigger: nach jedem Item-Status-Update prüfen ob noch pending Items existieren

**Implementation:** in `updatePlannedItemStatus()` als afterUpdate-Hook.

### 4.6 Approve-Endpoint erweitern

`apps/api/src/routes/projects/plans.ts` POST /approve:

Existing 62.5 macht nur status-flip. 62.8 erweitert:

```ts
async function approvePlan(planId: string) {
  const plan = await db.update(weeklyPlans)
    .set({ status: 'approved', approvedAt: new Date() })
    .where(eq(weeklyPlans.id, planId))
    .returning();
  
  // NEU: enqueue plan-execution
  await planExecutionQueue.add('execute', { planId }, { 
    jobId: `plan-exec-${planId}`, // idempotent
  });
  
  return { plan, executionEnqueued: true };
}
```

`jobId` deterministic → Approve mehrmals klicken triggert nur einen Execute-Lauf.

## 9. Risiken

| Risiko | Mitigation |
|---|---|
| Pipeline-Router falsche Pipeline pro Item-Type | Tests in 7.1 covern alle 4 Types. Phase 0 Discovery verifiziert exakte Pipeline-Inputs. |
| Item-Status-Update racet mit Pipeline-Run-Completion | `updatePlannedItemStatus` ist atomic single-statement UPDATE mit WHERE-Clause auf erwarteten alten Status. Lost-update wird durch DB-CHECK abgefangen. |
| Budget-Gate falsche Berechnung → Items unnötig blocked | `getWeeklySpend` aus 62.4 ist battle-tested. Threshold 90% gibt Buffer. |
| Wenn `cluster:full-plan` LLM-Call free-function bleibt (Memory D127), kann llmMode nicht durchgereicht werden | Bekannte Limitation. Cluster-Items laufen erstmal Sync auch im Batch-Mode. Akzeptierte Sub-Optimalität, eigener Spec für Free-Function-Refactor. |
| BullMQ-Retry race-condition mit DB-Status | BullMQ-Job-Status ist die source of truth während Job läuft. DB-Item-Status wird via Hooks aktualisiert. Konsistenz garantiert weil Job-Hook synchron in DB schreibt. |
| Worker-Crash mid-Plan-Execution | `executePlan()` ist idempotent — Items mit status != 'planned' werden geskipped. Worker-Restart pickt verbleibende Items wieder auf. |
| Marcel klickt Approve mehrmals | Job-ID `plan-exec-${planId}` deterministic → BullMQ dedup verhindert Doppel-Execution |
| Pipeline-Update-Hook fehlt bei einer Pipeline | Phase 3 macht alle 3 Pipelines bewusst. Tests in 7.1 verifizieren alle 4 Content-Types. |
| Frontend zeigt veraltete Status weil SSE failed | Polling-Fallback alle 30s. Plus Manual Refresh-Button. |
| Cancel-Pending wird ausgelöst während Plan-Execution-Worker iteriert | Cancel-Endpoint setzt Items auf 'cancelled', Worker prüft pre-enqueue ob noch 'planned'. Race-window klein und nicht-destruktiv (worst case: 1 item zu viel enqueued, läuft, ist trotzdem 'ready' am Ende). |
| Distribution-Layer (Phase E) erwartet anderen Status-Lifecycle als 62.8 etabliert | Lifecycle wurde mit Distribution mitgedacht ('published' als Endstate). Distribution-Spec wird darauf aufsetzen. |
