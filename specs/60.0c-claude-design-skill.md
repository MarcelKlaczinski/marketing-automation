## Goal

Integrate the Claude Design handoff bundle into the repo so:

1. The bundle becomes a **Claude Code skill** at `.claude/skills/toolwiki-design/` — every Claude Code session in this repo automatically discovers it via `<available_skills>` and follows its design rules
2. The `REMOTION.md` prop-schemas (which document min/max character budgets per field for all 5 templates) become the **authoritative bounds source**, overriding the empirically-derived `*Bounds` objects from 59.3.5 Section E
3. The full handoff bundle (HTML files, CSS, README, assets) is committed to `packages/social/design-reference/` as on-disk reference material for both humans and Claude Code

After 60.0c lands, every subsequent Spec 60.x can assume:
- Claude Code sessions in this repo have the toolwiki-design skill in their working context
- `<template>Bounds` constants match REMOTION.md exactly (no drift between design intent and renderer)
- HTML reference files are at predictable paths for visual comparison during implementation

## What this is NOT

- Not a visual change — no compositions are modified
- Not a new template — the bundle covers the 5 existing templates only
- Not a fix for 59.3.5 patterns (bucket table, validateAndReprompt etc.) — those stay; only the Bounds *values* change
- Not the Inter font migration — that happens in 60.1 with the first composition that needs the new font load
- Not the DS components — that's 60.0b v2

## Why this spec exists (motivation)

Three things landed simultaneously and need reconciliation:

1. **Spec 59.3.5 completed** with Retro-Patches that derived `*Bounds` objects from production data: "query last 50 renders per template, round up max observed length to nearest 10". This was the best available method at the time.

2. **Claude Design produced `REMOTION.md`** with field-by-field min/max budgets per template, derived from **design-side measurement** (what fits the layout at the tested font sizes). This is a more reliable source than production data because:
  - It accounts for character-width variance across content types (German runs ~15% longer than English; the budgets account for that)
  - It's tied to the actual layout grid the new visual refresh targets
  - Production data reflects what the OLD layout could handle, not what the NEW layout requires

3. **A handoff `SKILL.md` shipped with the bundle** designed for Claude Code skills integration. Skipping it means every Spec 60.x session has to re-read the 1.2MB bundle from `packages/social/design-reference/` and re-derive design rules. Installing it as a skill means Claude Code loads the rules automatically.

The convergence is fortunate: the design system documentation, the prop-schemas, and a skill packaging arrived together. Spec 60.0c integrates all three in one shot.

## Section C — Bounds Override

### C.1 Principle

The `*Bounds` objects in `packages/social/src/templates/definitions/*.ts` (added in 59.3.5 Section E retro-patches) are updated to match REMOTION.md prop-schemas exactly. The REMOTION.md schemas are the **single source of truth**.

If a field exists in REMOTION.md but not in the current `*Bounds`, add it.
If a field exists in `*Bounds` but not in REMOTION.md, KEEP it with a note (the renderer may need it for an internal slot REMOTION.md doesn't describe) — flag in implementation as open question.
If a field's min/max in REMOTION.md differs from the current `*Bounds` numbers, REMOTION.md wins.

### C.2 The mapping (template-by-template)

#### C.2.1 `cover` template

The `cover` template **doesn't yet exist** as a `TemplateKey`. The Audit (Section 10 of pre-spec audit) recommended treating the cover HTML files as a redesign of `CoverSlideStunning.tsx` (the existing top-of-carousel slide used by list-carousel-based templates). Decision: do NOT introduce a new `cover` template; instead, when 60.1 redesigns `single-tool-spotlight`, the cover-slide variant of that template adopts the `CoverProps` from REMOTION.md as its content contract.

For 60.0c specifically: **no Bounds change for cover**. The cover-related fields will land in 60.1+ as part of the per-template visual refresh.

#### C.2.6 `pro-con-verdict`

REMOTION.md does **not** include `pro-con-verdict` (Open Question 6 from the audit confirmed this). The template stays with its existing 59.3 / 59.3.5 Bounds for 60.0c. The visual refresh in 60.5 will derive new Bounds by extrapolating from the other 4 templates + DS tokens.

### C.3 Field-name normalization

REMOTION.md uses camelCase consistently (`heroTitle`, `headerNum`, `ctaLine`). Existing `*Bounds` objects may have different naming conventions. The implementer should:

1. Rename existing fields to match REMOTION.md
2. Update all consuming code: composition files, slot maps (from 59.3.5 Section A.2), test fixtures, override schemas

This is touchy work; commit per template (5 commits, not 1 batch).

### C.4 Discovered During Implementation

- `ContentBounds = Record<string, FieldBound | ListBound>` was too narrow for REMOTION.md's nested slot groups (`tools.name`, `footer.ctaLine`, `bullets.pros.each`). Extended to a recursive interface: `interface ContentBounds { [key: string]: FieldBound | ListBound | ContentBounds | number }`. This allows `count: 4` (numeric constraint) and nested objects while `satisfies ContentBounds` still compiles cleanly.
- `listCarouselInputSchema.tools.min(2)` was wrong vs the test that expected `min(3)` — a pre-existing drift bug. Fixed in the same session (tools.min raised to 3).
- Section C.3 (field-name normalization in consuming code) was partially deferred: render internals (`pros`, `cons`, `tagline`) kept as-is. The `*Bounds` objects use REMOTION.md naming (`strengths`, `weaknesses`, `verdict`) for documentation, while composition props retain the older names. Renaming composition internals requires a visual-change session (60.1+).

**Open question resolution (Section C.2.5):** `strengths.countMin: 3` → Option A applied. `SINGLE_TOOL_SPOTLIGHT_CONSTRAINTS.fieldBounds.pros.minItems` raised from 2 → 3. Articles with fewer than 3 pros are now ineligible for `single-tool-spotlight`.

## Section D — Bounds-to-Prompt Sync

### D.1 Why this section exists

Spec 59.3.5 introduced `buildConstraintBlock(bounds, locale)` (Section F of 59.3.5; also recommended by the audit's Section 9). The constraint block formats the bounds into an LLM-prompt section listing every field with its min/max.

When `*Bounds` change in Section C, the prompts generated by `buildConstraintBlock` automatically change too — as long as the helper reads from the same `*Bounds` source. Verify this is true:

- Each template's `generateContent()` MUST call `buildConstraintBlock(<template>Bounds, locale)` and inline the result into the LLM prompt
- No template should hardcode "max 80 chars" in a prompt string when the bound is in the object

If any template uses hardcoded numbers, they're now stale. Fix in Section D.2.

### D.2 Audit + fix per template

For each of the 4 in-scope templates (skip pro-con-verdict; skip cover):

1. Open the template's `generateContent()` function in `packages/social/src/templates/definitions/<template>.ts`
2. Grep the prompt string for: `max`, `min`, character counts, e.g. `"≤"`, `"chars"`, `"Zeichen"`
3. Replace any hardcoded number with `${bounds.field.max}` or via `buildConstraintBlock`
4. Run the template's existing fixtures through `generateContent()` (mock LLM) to confirm the rendered prompt looks reasonable
5. Commit per template

### D.3 Discovered During Implementation

- All 4 in-scope templates use `generateContentWithGate()` which has no template-specific prompt strings. No hardcoded character counts exist in any `generateContent()` body — Section D was effectively a no-op for these templates. The `buildConstraintBlock` helper mentioned in Section D.1 does not yet exist; it was listed as a future utility in Spec 59.3.5 Section F but was never implemented. This is not a problem for the current templates since their prompts are generic.

## Section E — Visual Baseline Regeneration

### E.1 What changes might trigger re-baseline

Section C should NOT change visual output. The Bounds are **constraints on input**, not on output rendering. The composition reads its content and renders it; tightening the input bounds doesn't change how content within bounds renders.

BUT: if a fixture (characteristic / edge-min / edge-max from 59.3.5 Section D) had content that **exceeded** the new tighter bounds, that fixture now FAILS Zod validation. The visual test for it would error out before rendering.

### E.2 Fixture validation pass

For each template, run:

```bash
bun test --filter "fixtures within declared bounds"
```

(That's the test from 59.3.5 Section G.3.) Any failure means the fixture has content over the new max. Fix by:

1. Shortening the fixture content to fit the new bound
2. Re-rendering the visual baseline (since content changed)
3. Committing the new baseline PNG

### E.3 Edge-max fixtures may need real updates

If 59.3.5 derived an `edgeMax` fixture using last-50-renders max-observed length (e.g. 120 chars), and REMOTION.md says max is 80 chars, the edgeMax fixture must now be at 80 chars. Re-render the baseline.

This is expected and normal — REMOTION.md tightens the contract; baselines reflect the new contract.

### F.2 Bounds-source consistency test

```typescript
// packages/social/test/bounds-match-remotion-md.test.ts

import { describe, it, expect } from "vitest";
import { readFileSync } from "node:fs";
import { comparisonGrid4Bounds } from "../src/templates/definitions/comparisonGrid4";

describe("Bounds match REMOTION.md", () => {
  const remotionMd = readFileSync(
    ".claude/skills/toolwiki-design/REMOTION.md",
    "utf-8",
  );

  it("comparisonGrid4Bounds.heroTitle.max matches REMOTION.md", () => {
    // Parse the doc for the specific budget line
    const match = remotionMd.match(/heroTitle:\s*string;\s*\/\/\s*min\s*(\d+),\s*max\s*(\d+)/);
    expect(match).toBeTruthy();
    const [, min, max] = match!;
    expect(comparisonGrid4Bounds.heroTitle.min).toBe(Number(min));
    expect(comparisonGrid4Bounds.heroTitle.max).toBe(Number(max));
  });

  // ... similar tests per field per template
});
```

This is a **drift detector**. If REMOTION.md updates (Claude Design re-exports the bundle), the test fails, prompting the implementer to update `*Bounds`. Single source of truth, mechanically enforced.

Alternative simpler approach: generate a small `BOUNDS_FROM_REMOTION.md.json` file as part of the build, parse REMOTION.md once into that JSON, then have `*Bounds` import from it. Decision: defer to implementer — test-based drift detection is sufficient for now.

## Deviations from Spec

**Section C.3 (field-name normalization) — partially deferred:**
The spec said to rename existing fields to match REMOTION.md and update all consuming code (composition files, slot maps, fixtures, override schemas). In practice this was split:
- `*Bounds` objects use REMOTION.md naming (`strengths`, `weaknesses`, `verdict`, `winnerName`, etc.)
- Render internals and Remotion composition props retain pre-existing names (`pros`, `cons`, `tagline`) to avoid triggering visual changes

Renaming composition internals requires updating the Remotion composition schema + slide components, which is a visual-change operation out of scope for this spec. The CLAUDE.md in `packages/social/src/templates/` now documents this separation explicitly.

**Section F.3 (constraint-block snapshot tests) — not implemented:**
`buildConstraintBlock` does not exist — it was specified in Spec 59.3.5 Section F as a future utility but was never implemented. The snapshot tests were skipped. These become relevant only once the helper is built (likely during a future composition visual refresh that adds LLM-generated slot content).

**`ContentBounds` type change (not in spec):**
The spec showed `as const` (without `satisfies ContentBounds`) on the new bounds objects. Instead, `ContentBounds` was extended to a recursive interface that accommodates nested slot groups and `number` count fields. This keeps `satisfies ContentBounds` working everywhere and makes the type accurate. The change is backwards-compatible — existing flat bounds objects still compile.
