# Spec 54.6: Trend Discovery UI

**Phase:** 54 / B — Trend Discovery (3 of 3) — completes Phase B
**Estimated Effort:** 2.5–3 days (~18-20 focused hours over 5 sessions)
**Dependencies:** Spec 54.5 (synthesis producing briefs), Spec 54.5b (cleanup + score rebalancing)
**Status:** Ready for implementation
**Recommended Model:** Sonnet 4.6 (Quasar UI work + small backend additions, no architectural novelty)

---

## Goal

Build the first end-to-end UI for Trend Discovery: Marcel can browse pending trend briefs at `/projects/<slug>/trends`, inspect their score breakdowns and source signals, approve or dismiss them, lightly edit SEO fields, browse rejected candidates, inspect the raw signal pool, and trigger synthesis manually. This completes Phase B.

The UI is a **hybrid throwaway**: layouts and styling will be replaced by Spec 54.9's full UI redesign, but the underlying components (`TrendBriefList`, `TrendBriefDetail`, `RejectedTopicsBrowser`, `SignalPoolInspector`, `SynthesisTriggerCard`) are designed for reuse. 54.9 re-styles, doesn't rewrite.

Also: this spec adds **Voyage AI credential vault integration**, mirroring the Product Hunt installer/settings pattern from 54.4. Until 54.6 ships, the only way to set `VOYAGE_API_KEY` is the env file.

Spec 54.6 delivers:

1. New Quasar route `/projects/<slug>/trends` with three tabs: Pending Briefs / Rejected / Signal Pool
2. `TrendBriefList` component — paginated list of pending trend_discovery briefs with score, freshness, source-mix indicator
3. `TrendBriefDetail` component — full score breakdown, source signals, suggested title/meta/slug (light editable), approve/dismiss/edit actions
4. `RejectedTopicsBrowser` component — filtered list of rejected candidates with reason, similarity, expires_at countdown
5. `SignalPoolInspector` component — raw `external_signals` browser with source/date/processed-status filters
6. `SynthesisTriggerCard` component — manual "Run Synthesis Now" button, status polling
7. Backend additions: GET endpoints for pending trend briefs, rejected topics, signal pool; POST endpoints for approve/dismiss/light-edit; POST trigger-synthesis endpoint
8. Voyage Vault wiring: extend `system-service.ts`, add `StepVoyage.vue` installer step, settings entry, hint text in German

After deploy:
- Marcel can review every synthesis run's output without psql
- Approving a brief with `cluster_action='append_to_existing'` triggers existing `/automate` route (Phase A pipeline)
- Approving a brief with `cluster_action='create_new'` is **disabled with hint "Cluster Creator coming in Spec 54.7"** — visible but not actionable
- Voyage API key is settable via UI (not only env)

## What this is NOT

- Not a full UI redesign — that's 54.9. Layouts use standard Quasar components, no custom design tokens, no polish beyond functional clarity
- Not the Cluster Creator (54.7) — `create_new` briefs surface but their approve button is disabled
- Not a generic gap-briefs view — only `source='trend_discovery'` briefs visible in this route. The existing GapsPanel (from 54.1) handles gap-sourced briefs.
- Not a settings page for score weights / thresholds — that's POST-54-BACKLOG. Threshold value is read-only in the UI for now (shown as "Current threshold: 25")
- Not an audit/history view of past synthesis runs — just current pending state
- Not a multi-user permission system — single-user assumption holds
- Not new authentication / authorization — uses existing session
- Not Cordova / mobile-specific layouts — desktop primary, Quasar handles responsive defaults

## Architecture

### Component composition strategy

The TrendsPage is a thin container. Heavy logic lives in three child components with clear boundaries:

```
TrendsPage.vue
├── q-tabs ("Pending" / "Rejected" / "Signals")
├── SynthesisTriggerCard      (always visible in header)
├── q-tab-panels
│   ├── (Pending tab)
│   │   ├── TrendBriefList    (master)
│   │   └── TrendBriefDetail  (detail, right pane or modal)
│   ├── (Rejected tab)
│   │   └── RejectedTopicsBrowser
│   └── (Signals tab)
│       └── SignalPoolInspector
```

Each child component:
- Owns its own data-fetching via the SDK
- Emits domain events (e.g. `brief:approved`, `brief:dismissed`, `signals:refresh-requested`)
- Stays Options API with `data: () => ({...})` pattern (per CLAUDE.md convention)
- No global Pinia store added — components query their own slices

This is fine for a throwaway UI; 54.9 may introduce a `useTrendsStore` if cross-component state grows.

### Backend endpoint surface

Five new endpoints under `/projects/:slug/trends/*`:

```
GET    /projects/:slug/trends/pending-briefs     → list pending trend_discovery briefs
GET    /projects/:slug/trends/rejected-topics    → list non-expired rejected candidates
GET    /projects/:slug/trends/signal-pool        → paginated external_signals view
POST   /projects/:slug/trends/briefs/:id/approve → call existing routing policy
POST   /projects/:slug/trends/briefs/:id/dismiss → manually reject brief (write to rejected_topic_candidates, mark signals)
POST   /projects/:slug/trends/briefs/:id/edit    → light edit (title, meta, slug only)
POST   /projects/:slug/trends/synthesize         → enqueue manual synthesis-project job
```

Each endpoint validates the project ownership via existing auth middleware. Each returns Zod-validated responses for `@hey-api/openapi-ts` SDK generation.

### Approve flow (the hairy bit)

When Marcel clicks "Approve" on a brief, the backend route does:

```
1. Load the brief (status = 'pending')
2. Run TopicRoutingPolicy.decideRoute(brief) — same path as 54.3 /generate
3. Switch by RoutingDecision.kind:
   - 'create_article' → call existing /automate path (chain pipeline)
                        OR /generate path (immediate generation)
                        based on UI choice (radio in detail view)
   - 'create_cornerstone_spec' → reject in 54.6 (specs need their own flow)
   - 'create_translation' → not produced by trend_discovery source (skip)
   - 'refresh_article'   → not produced by trend_discovery source (skip)
   - 'create_cluster'    → 400 with message "Cluster Creator (Spec 54.7) required"
                          UI's Approve button should be disabled for these — backend
                          enforces as safety net
4. Update brief.approval_status = 'approved'
5. Set brief.routed_article_id or routed_cornerstone_spec_id
6. Return success with target route URL (so UI can navigate)
```

UI presents two action variants for `cluster_action='append_to_existing'` briefs:
- "Approve & Generate Now" → `/generate` flow (immediate, blocks until article exists)
- "Approve & Queue" → `/automate` flow (chain enqueued)

Default: "Approve & Queue". Marcel can switch in detail view.

### Dismiss flow

When Marcel clicks "Dismiss" on a brief, the backend route does:

```
1. Load brief
2. Insert into rejected_topic_candidates with:
   - reason = 'manual_dismissal'
   - source_signal_ids = brief.trend_metadata.signals[].id
   - candidate_title_normalized = normalize(brief.topic_title)
   - expires_at = NOW() + 30 days
3. Update brief.approval_status = 'rejected'
4. Stamp source signals: processed_at = NOW() (preserve processed_into from brief, for audit)
```

This requires a new reason in the `rejected_topic_candidates.reason` CHECK constraint. Schema migration:

```sql
ALTER TABLE rejected_topic_candidates
  DROP CONSTRAINT rejected_topic_candidates_reason_check;

ALTER TABLE rejected_topic_candidates
  ADD CONSTRAINT rejected_topic_candidates_reason_check
  CHECK (reason IN (
    'existing_coverage', 'low_score',
    'excluded_by_scope', 'low_signal_volume',
    'manual_dismissal'
  ));
```

### Edit flow (light edit, decision Q from prep)

Only three fields editable: `suggested_title`, `suggested_meta`, `suggested_slug`.

Backend validation:
- `suggested_title`: 10-200 chars
- `suggested_meta`: 50-160 chars (hard limit, no `.transform(slice)` — Marcel writes it manually, so it's deterministic)
- `suggested_slug`: regex `/^[a-z0-9-]+$/`, max 100 chars

If validation fails → 400 with field-level errors. UI shows errors inline.

After edit, brief stays `pending` — no auto-approve. Edit is "tune before approve".

### Synthesis trigger flow

`SynthesisTriggerCard` shows:
- Last synthesis run timestamp (from `cost_logs` or BullMQ history)
- Signal pool size (count of unprocessed signals in 14-day window)
- "Run Synthesis Now" button (disabled when a synthesis-project job is already in-flight for this project)
- Status pill: idle / running / completed-X-briefs / failed

Polling: when "Run" is clicked, button locks, UI polls `GET /projects/:slug/trends/synthesis-status` every 3 seconds. When status flips to `completed` or `failed`, button re-enables and the pending briefs list auto-refreshes.

Backend:
- POST `/synthesize` enqueues a `synthesize-project` job, returns `{ jobId }`
- GET `/synthesis-status` checks BullMQ for active/completed jobs of this project for the current day

### Backend route: pending-briefs

`apps/api/src/routes/projects/trends.ts`:

```typescript
import { Hono } from "hono";
import { z } from "zod";
import { and, desc, eq, isNull, sql } from "@marketing-auto/db";
import { db, topicBriefs, externalSignals, rejectedTopicCandidates } from "@marketing-auto/db";

const trends = new Hono();

// GET pending briefs
trends.get("/pending-briefs", async (c) => {
  const projectId = c.get("projectId");

  const briefs = await db
    .select()
    .from(topicBriefs)
    .where(and(
      eq(topicBriefs.projectId, projectId),
      eq(topicBriefs.source, "trend_discovery"),
      eq(topicBriefs.approvalStatus, "pending"),
    ))
    .orderBy(desc(sql`(trend_metadata->'score_breakdown'->>'total')::int`));

  return c.json({ briefs });
});
```

Each subsequent endpoint follows the same Hono + Drizzle pattern. Approve and dismiss are the more involved ones — they call into the existing `TopicRoutingPolicy.decideRoute` and `executeDecision` from 54.3.

### `usePolling.ts` composable

Small helper for poll-with-stop. Used by `SynthesisTriggerCard`.

```typescript
import { onUnmounted, ref } from "vue";

export function usePolling<T>(args: {
  poll: () => Promise<T>;
  shouldStop: (result: T) => boolean;
  intervalMs?: number;
  onStop?: (lastResult: T) => void;
}) {
  const isPolling = ref(false);
  let timer: ReturnType<typeof setInterval> | null = null;

  function start(): void {
    if (isPolling.value) return;
    isPolling.value = true;
    timer = setInterval(async () => {
      const result = await args.poll();
      if (args.shouldStop(result)) {
        stop();
        args.onStop?.(result);
      }
    }, args.intervalMs ?? 3000);
  }

  function stop(): void {
    if (timer) clearInterval(timer);
    timer = null;
    isPolling.value = false;
  }

  onUnmounted(stop);

  return { isPolling, start, stop };
}
```

Per convention: composable uses Composition API (`ref`, `onUnmounted`). Consuming components use Options API and pull it in via `setup()`.

## Open Questions / Decisions Made

**Decision 1: Three-tab layout, not a dashboard.**
Tabs are simpler to build, simpler to learn, sufficient for the throwaway scope. A dashboard with multiple panels visible at once is 54.9 territory.

**Decision 2: Master/Detail pane within the Pending tab.**
Standard Quasar pattern. Brief list on left, detail on right (responsive: stacks on mobile). Modal would feel heavy for the read-then-decide flow.

**Decision 3: Light edit only (title/meta/slug).**
Per user direction (b). Full edit risks `cluster_action` mutations that break routing — Marcel could mark a brief `append_to_existing` and forget to pick a cluster. Stay safe.

**Decision 4: Dismiss writes manual_dismissal to rejected_topic_candidates.**
Consistent with auto-rejection lifecycle. 30-day expiry means same topic can resurface later. Avoids needing a separate "manually dismissed" tracker.

**Decision 5: Approve has two modes: Queue vs Generate.**
"Queue" (default) uses /automate's chain pipeline — articles get full outline → draft → schema → localize processing. "Generate" uses /generate's immediate path — single article, blocks until done. User picks per-brief in detail view via radio.

**Decision 6: Create_new briefs visible but disabled.**
Per user direction (a). Transparency about pipeline capability matters more than hiding incomplete features. Users see the queue building up for 54.7.

**Decision 7: No global Pinia store for trends.**
Components own their data. State is naturally local. If 54.9 introduces cross-component reactivity needs, extract then.

**Decision 8: Voyage Vault gets installer step + settings entry.**
Per user direction (c). Standard adapter pattern. Env fallback preserves dev workflow.

**Decision 9: SynthesisTriggerCard polls every 3s.**
Empirical: synthesis takes 30-90 seconds. 3s polling means ~10-30 polls per run, trivial load. Could swap for WebSocket later (54.9).

**Decision 10: Signal pool inspector has no edit actions.**
54.6 is inspection-only. Marking a signal as "ignore this" is a future feature (POST-54-BACKLOG candidate).

**Decision 11: Components use Options API + arrow-function data().**
Per CLAUDE.md convention. Composables use Composition API. usePolling is the only Composition API code added.

**Decision 12: All component files include English JSDoc.**
Per convention. New props get a `@prop` annotation.

**Decision 13: Score-Threshold display is read-only.**
"Current threshold: X" shown as info text. Configurability is POST-54-BACKLOG.

**Decision 14: Synthesis trigger lives in page header, not per-tab.**
Visible regardless of which tab is active — Marcel can trigger at any time.

**Decision 15: Hybrid throwaway philosophy.**
Components are reusable. 54.9 will re-style with custom design tokens and may reorganize layout, but won't rewrite component logic. Test coverage protects the rewrite.
