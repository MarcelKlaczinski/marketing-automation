# Spec 63.7b — Cluster-Routing Fix für append_to_existing Briefs

_Theme 63 Sub-Spec — Pipeline-Router routet append_to_existing Briefs zur article:blog Pipeline statt cluster:full-plan. Verhindert Phantom-Cluster._
_Status: Draft._
_Voraussetzung: 63.6 gemerged + Diagnose 2026-05-21 (Cluster-Routing-Investigation)._
_Paired: 63.7a (DB-Cleanup), läuft separat._

---

## 1. Problem

Aus Diagnose 2026-05-21:

> "Plan router does NOT look at cluster_action — every content_type='cluster' goes to cluster:full-plan, regardless of whether brief means 'new cluster' or 'append to existing'."

**Konsequenz bei Plan-Approve:**
- append_to_existing Briefs erzeugen Phantom-Cluster mit überlappenden Themen zu existing Cluster
- Existing Cluster (z.B. video-ki-2026, music-generation-2026) bleiben unbefüllt
- Gap-Detection-Mechanik wird unterminiert
- Soft duplicates mit verwirrenden Namen entstehen

**Root Cause:**
1. `matchBriefToContentType` → routet append_to_existing zu content_type='cluster'
2. `getPipelineForItem` → routet content_type='cluster' immer zu cluster:full-plan
3. `runClusterFullPlanFromBrief` → ignoriert brief.clusterAction, baut immer neuen Cluster

**Aktueller historischer Pfad der funktioniert hat:**
- 4 ältere routed gap_analysis Briefs liefen über legacy `executeDecision` Pfad
- Diese erzeugten Spoke-Artikel direkt im existing Cluster (routed_article_id gesetzt)
- semantisch korrekt — aber bypasst Plan-Workflow

## 2. Ziel

Plan-Router routet **append_to_existing Briefs zu article:blog** (Spoke-Generation im existing Cluster), NICHT zu cluster:full-plan.

**Architektur-Wahl (Option 1 der Diagnose):** Router-level dispatch.
- Planner-Step stempelt cluster_action + clusterId + intent_type in pipelineInput
- Router liest und routet entsprechend
- Memory D140 (Pipeline-Router Discriminated Union) wird erweitert um cluster_action-Branch

**In Scope:**
- Planner-Step Erweiterung: pipelineInput für cluster-Items enthält cluster_action + parent_cluster_id + intent_type
- Pipeline-Router: append_to_existing → article:blog mit parent_cluster_id als spoke-Anbindung
- article:blog Pipeline: liest parent_cluster_id und schreibt Article als Spoke unter Cluster
- Brief-Status-Update beim Approve: korrekte routed_article_id statt routed_cluster_id

**Out of Scope:**
- cluster:full-plan Pipeline ändern (bleibt für create_new identisch)
- Cluster-Matching-Algorithmus erweitern
- Neue content_types in Migration
- gap_analysis Briefs die NICHT missing_hub sind (use_case, alternatives etc.) — die haben andere Anforderungen
- "push cluster build link error" — separates Problem

**Aufwand:** 0.5-1 Tag.

### 3.4 Plan-Goals und content_type

Wichtige Frage: wenn append_to_existing zu article:blog routed wird, ist content_type immer noch 'cluster' für Plan-Goal-Erfüllung?

**Optionen:**

**Option A: content_type bleibt 'cluster'.** Plan-Goal für 'cluster' min=7 erfüllt auch wenn Items als Spokes gerouted werden.
- Pro: keine Plan-Goal-Migration nötig
- Con: semantisch fragwürdig — cluster:full-plan generation und blog-spoke-generation sind verschiedene Cost-Profile

**Option B: content_type wechselt zu 'blog' oder 'spoke'.** Plan-Goal für 'cluster' min=7 muss reduziert werden weil append_to_existing nicht mehr cluster-content_type sind.
- Pro: semantisch korrekt
- Con: Plan-Goals manuell anpassen, Migration für neuen content_type

**Mein Vorschlag: Option A für 63.7b**, mit Notiz in Spec dass langfristig vielleicht Option B sauberer ist. Begründung:
- Plan-Goal-Migration ist Scope-Creep für diese Spec
- Marcel sieht im UI immer noch "cluster" Badge — UX-konsistent mit aktueller Mental-Model
- Cost-Schätzung muss in Spec erweitert werden: append_to_existing items sind günstiger (~€1.06 statt €4.20) → estimateCostForItem muss source-aware werden

## 12. Discovered During Implementation

Phase-0 discovery überrollte mehrere Annahmen der ursprünglichen Spec:

- **`articles.parent_cluster_id` Column existiert nicht — wird auch nicht gebraucht.** `articles.cluster_id` (uuid FK zu `clusters.id`, nullable) ist bereits die Spoke-Membership. `packages/pipelines/src/article/blog/persist.ts:40` schreibt seit jeher `clusterId: brief.clusterId ?? null`. Sobald der Brief mit gesetzter `clusterId` durch `createBlogArticleFromBrief` läuft, wird der Article automatisch zum Spoke unter dem existing Cluster. Keine Migration nötig.
- **`BlogPipelineInputSchema` braucht KEIN neues `parentClusterId` Feld.** Der existing `briefId`-Pfad reicht: persist.ts lädt den Brief und liest `brief.clusterId` direkt. Die Spec §3.3 / §5.4 Annahme war redundant.
- **Pre-existing Bug entdeckt:** der Planner-Router setzte `collectionType: "comparisons"` (plural, Astro-Folder-Name) statt `"comparison"` (singular, `ArticleCollectionType` enum). Spec-pre war Dead Code — der Executor (execute-plan.ts) hat `collectionType` aus `jobData` einfach gedroppt vor dem `enqueueBlogGeneration`-Call. Konsequenz: Comparison- + ki_wissen-Plans landeten ALLE mit `articles.collection='blog'` in der DB, nicht in der korrekten Astro-Collection. 63.7b's Thread-Through-Fix (Phase 4) hat das gleichzeitig mitkorrigiert — `"comparisons"` wurde zu `"comparison"` in [pipeline-router.ts:122](packages/planner/src/execution/pipeline-router.ts:122), und der Executor leitet es jetzt durch.
- **Cost-Estimation source-aware ohne neue Funktion möglich:** Spec §3.5 / §5.5 schlugen eine separate `estimateCostForBriefItem` Funktion vor. Stattdessen reicht es, `planned_items.pipeline_name` auf `article:blog` zu setzen (statt `cluster:full-plan`) wenn append_to_existing — der tier-1 step-sum estimator pickt dann automatisch die billigeren `article:blog`-Steps. `pipelineNameForItem()` in [select-floor-items.ts:148](packages/pipelines/src/planning/steps/select-floor-items.ts:148) macht das. Tier-3-Fallback bleibt zwar €4.20 (itemType='cluster' wins über pipelineName), aber in Production ist tier-1 immer gewired (apps/api `resolvePipelineSteps`), also dominiert die korrekte Estimate.

## 13. Deviations from Original Spec

- **§3.3 `parent_cluster_id` field in pipelineInput:** Renamed to `clusterId` to match the existing `topic_briefs.cluster_id` column name (we wanted no new column). The router still uses `clusterId` for the same purpose.
- **§4 Migration:** None needed — see Discovery #1 above.
- **§5.4 `BlogPipelineInputSchema` parentClusterId field:** Skipped — see Discovery #2 above.
- **§5.5 source-aware cost-estimation function:** Replaced by `pipelineNameForItem()` override at plan time — see Discovery #4 above.
- **§3.3 `parent_cluster_id` separate field:** the actual implementation also stamps `intentType` and (correctly named) `clusterAction` so the router can make the routing decision purely from `pipelineInput` without a brief re-query.
- **`createBlogArticleFromBrief` change:** Spec §5.3 implied only the Pipeline needed parent_cluster handling; in reality `createBlogArticleFromBrief` ALSO needed an optional `collection` param so the initial article INSERT picks the right Astro collection (`"ki-wissen"`, `"usecases"`, etc.) instead of always hardcoding `"blog"`. `PersistArticleStep` (step 13) later UPDATEs it correctly via `collectionType` in pipelineInput, but the initial INSERT being wrong would mean any intermediate query-by-collection in steps 1-12 would see the wrong value.
- **Type-hardening added beyond spec:** `deriveCollectionFromIntent` returns `ArticleCollectionType` (not `string`), and the comparison/ki_wissen cases assign through a typed `const collectionType: ArticleCollectionType` so the original `"comparisons"` typo cannot reoccur — TypeScript catches it at compile time now.
