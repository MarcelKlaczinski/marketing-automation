# Spec 57.1 — Brand-Token Completion + Locale-Multi-Render + Editorial Cleanup

**Theme:** 57 (Social Media + Remotion Refinement)
**Status:** Draft (revised after 57.4 landed first)
**Estimated effort:** 6-8 days

**Sequencing note:** Spec 57.4 (Hashtag Generation Refactor) was implemented before this spec. Because both touch `GenerateCaptionStep` and the social-image pipeline schemas, this spec has been revised to build on the post-57.4 state. Key changes:
- `GenerateCaptionStep` already returns `{caption, hashtags}` — locale-multi-render now produces N caption-and-hashtag pairs (one per locale), not separate caption-and-hashtag steps
- `LoadArticleStep` already exposes `intentType` — no schema additions needed
- `jsonMode: true` is NOT to be used with `claude-sonnet-4-6` (per 57.4 Discovered #4 — Sonnet rejects prefill); JSON output is prompt-only

---

## Goal

Complete the brand-token integration for all 4 production social templates by tokenizing the remaining hardcoded values, add multi-locale rendering capability to the social-image pipeline + UI, and remove the deprecated Editorial variant. After this spec, projects can fully customize their social templates via brand tokens (no hardcoded colors/fonts/sizing leak through), and users can generate social posts in 1 or N locales per trigger.

## Non-Goals

- Auto-publishing to Instagram/TikTok/LinkedIn (out of scope, manual download stays)
- BullMQ migration (Spec 57.2)
- Project-scoped template overrides for copy/layout (Spec 57.3)
- Hashtag research completion (Spec 57.4 — **already done**, this spec builds on top)
- New template types (`news-slide`, `concept-explainer-deck`, `pro-con-verdict` stubs remain in `TemplateKey` union for future sub-specs)
- Video / MP4 output

## Three-Part Scope

This spec combines three logically separate but technically coupled changes that all touch the template input schema. Splitting them would require touching `BrandTokens` Zod schema + migrations 3×; bundling is more efficient.

**Part A: Brand-Token Completion** — Tokenize remaining hardcoded values
**Part B: Locale-Multi-Render** — Render N locales per trigger
**Part C: Editorial Variant Cleanup** — Deprecate + remove the legacy variant

### A.4 WCAG Contrast Validation

Brand tokens that affect text readability must be validated. Add a validator function:

**Location:** `packages/social/src/lib/contrast-validator.ts` (new file)

```typescript
import { wcagContrast, parse } from "culori";  // already a dependency? check
import type { BrandTokens } from "./theme";

export type ContrastViolation = {
  field: string;        // e.g. "colors.eyebrowColor"
  background: string;   // e.g. "surfaceDark"
  ratio: number;
  required: number;     // 4.5 for AA normal, 3.0 for AA large
  message: string;
};

export function validateBrandTokenContrast(tokens: BrandTokens): ContrastViolation[] {
  const violations: ContrastViolation[] = [];
  const c = tokens.colors;

  // Critical pairs:
  const pairs = [
    { fg: c.eyebrowColor,     bg: c.surfaceDark,      field: "eyebrowColor",     bgName: "surfaceDark",      required: 3.0 },
    { fg: c.ink,              bg: c.surfaceDark,      field: "ink",              bgName: "surfaceDark",      required: 4.5 },
    { fg: c.inkMuted,         bg: c.surfaceDark,      field: "inkMuted",         bgName: "surfaceDark",      required: 4.5 },
    { fg: c.primary,          bg: c.surfaceDark,      field: "primary",          bgName: "surfaceDark",      required: 3.0 },
    { fg: c.accent,           bg: c.surfaceDark,      field: "accent",           bgName: "surfaceDark",      required: 3.0 },
    { fg: c.ink,              bg: c.surfaceSecondary, field: "ink",              bgName: "surfaceSecondary", required: 4.5 },
    { fg: c.pricingFree,      bg: c.surfaceDark,      field: "pricingFree",      bgName: "surfaceDark",      required: 3.0 },
    { fg: c.pricingFreemium,  bg: c.surfaceDark,      field: "pricingFreemium",  bgName: "surfaceDark",      required: 3.0 },
    { fg: c.pricingPaid,      bg: c.surfaceDark,      field: "pricingPaid",      bgName: "surfaceDark",      required: 3.0 },
  ];

  for (const pair of pairs) {
    const ratio = wcagContrast(parse(pair.fg), parse(pair.bg));
    if (ratio < pair.required) {
      violations.push({
        field: `colors.${pair.field}`,
        background: pair.bgName,
        ratio: Math.round(ratio * 100) / 100,
        required: pair.required,
        message: `Contrast ${pair.field} vs ${pair.bgName} is ${ratio.toFixed(2)}, needs >= ${pair.required}`,
      });
    }
  }

  return violations;
}
```

**Integration**: Called by the projects PATCH endpoint when brand_tokens is updated. Returns violations as a 400 response if any. **Warning, not blocker** — Marcel may want to allow violations with `?force=true` query param for design experimentation, TBD per acceptance criteria.

### B.2 Step Behavior

**Post-57.4 reality**: The pipeline is now 7 steps (down from 8). `ResearchHashtagsStep` was removed. `GenerateCaptionStep` produces both caption AND hashtags in a single Sonnet 4.6 call via the shared `buildHashtagInstructions()` utility (from `@marketing-auto/core`).

`RenderSlidesStep` becomes locale-aware (loops over `locales`):

```typescript
for (const locale of input.locales) {
  const localizedContext = { ...context, locale };
  const result = await renderFn(localizedContext);
  results.push({ locale, slides: result.slides, sequenceCount: result.sequenceCount });
}
```

`GenerateCaptionStep` runs **per locale** — captions AND hashtags are language-specific:

```typescript
const perLocaleOutputs: Array<{ locale: string; caption: string; hashtags: string[] }> = [];

for (const locale of input.locales) {
  const hashtagSection = buildHashtagInstructions({
    locale,                                    // NEW: locale per iteration, not from input
    contentType: deriveContentType(input.intentType),
    toolNames: input.resolvedTools.map(t => t.name),
    toolCategory: input.cluster?.category,
  });

  const captionLocale = locale.startsWith("de") ? "GERMAN" : "ENGLISH";
  const prompt = buildCaptionPrompt({ ...input, locale, captionLocale, hashtagSection });

  // NOTE: no jsonMode:true — Sonnet 4.6 rejects it per 57.4 Discovered #4
  const response = await anthropic.messages({
    operation: COST_OPS.SOCIAL_IMAGE_CAPTION,
    model: "claude-sonnet-4-6",
    systemSuffix: "Return only valid JSON matching the requested shape.",
    userMessage: prompt,
    maxTokens: 600,
  });

  const parsed = parseJsonResponse(response.raw);  // raw.indexOf("{") pattern
  const validated = generateCaptionOutputSchema.parse(parsed);
  perLocaleOutputs.push({ locale, caption: validated.caption, hashtags: validated.hashtags });
}

return { ...input, perLocaleOutputs };
```

Two design choices worth flagging:

**B.2.a Per-locale hashtag generation (not translation)**

Each locale renders its own hashtag set rather than translating from a canonical. Reasons:
- Hashtags are anchor-tag-based (`#KITools` for DE, `#AITools` for EN), not free translations
- `buildHashtagInstructions(locale=de-DE)` produces a different bilingual mix than `(locale=en-US)` — both bilingual, but anchor positioning differs
- Coherence: each locale's caption mentions tools the way that locale would; hashtags reinforce that locale's caption

**Cost implication**: N locale renders = N Sonnet 4.6 caption calls. Cost scales linearly: `0.028 * locales.length`. Already accounted for in API cost estimate.

**B.2.b LLM call count**

Pre-57.4: 1 caption + 1 hashtag call per locale = 2 LLM calls per locale
Post-57.4: 1 merged call per locale = 1 LLM call per locale
Multi-locale (2 locales): 2 merged calls total

The merge in 57.4 makes locale-multi-render cheaper than originally specced.

`PersistSocialPostStep` inserts **N rows** in `social_posts` (one per locale). Each row tagged with `locale` column. Each row gets its own (caption, hashtags) pair from `perLocaleOutputs[i]`.

## Risks & Mitigations

**Risk 1: Visual regression for toolwiki**
- *Mitigation*: Migration script sets toolwiki defaults = current hardcoded values. Side-by-side visual comparison of pre/post render of same article.

**Risk 2: Contrast validator too strict, blocks valid designs**
- *Mitigation*: Validator returns warnings (HTTP 200 + violations array), not blockers. Optional `?force=true` for override.

**Risk 3: Locale-multi-render explodes costs / time**
- *Mitigation*: UI shows cost estimate scaling per locale. Max 5 locales enforced. Default to 1 locale selected. Pipeline still synchronous per locale (BullMQ migration is Spec 57.2 — if rendering 5 locales × 30s = 150s blocks one BullMQ worker for 2.5 minutes, that's acceptable until 57.2).

**Risk 4: Editorial removal breaks old social_posts rows**
- *Mitigation*: Backfill migration before code removal. Old rows still queryable by `articleId`; their renders are immutable URLs in S3 unaffected.

**Risk 5: Schema migration breaks dev/prod parity**
- *Mitigation*: Migration adds nullable column with default, then backfills, then enforces NOT NULL. Standard pattern.

## Discovered During Implementation

**Sessions 5+6 (Locale-Multi-Render Pipeline + UI)**

1. **Hook JSON defensive parsing required**: `GenerateCaptionStep`'s hook parser (`generateHookWithGate`) must validate that `leadPhrase`, `highlightWord`, and `trailPhrase` are all strings before passing the parsed object to `validateHook`. Without this guard, when a test's `mockImplementationOnce` is exhausted the base mock's tools-extraction JSON reaches `validateHook`, crashing on `hook.highlightWord.trim()`. The guard is the correct defensive pattern for any step that makes N LLM calls — only 1 of which is mocked by a one-shot test helper.

2. **Social tab component lives in `pages/articles/tabs/`, not `components/article/`**: The spec says `SocialPostsTab.vue` in `src/components/article/`. The project's established pattern for article detail tabs (ArticleRunsTab, ArticleCostTab, etc.) uses `pages/articles/tabs/ArticleXxxTab.vue`. The implementation follows the actual project pattern: `ArticleSocialTab.vue` in `pages/articles/tabs/`.

3. **`RenderHistoryList.vue` is embedded, not a separate component**: Spec specced a separate `RenderHistoryList.vue`. History grouped by locale was embedded directly in `ArticleSocialTab.vue` since it has no reuse need outside this tab.

4. **i18n flat-string→object collision**: The existing `social.ts` had `history: "Render-Verlauf"` as a flat string. Adding `history: { localeGroupHeader: "..." }` caused TS1117 duplicate key. Fix: convert to `history: { label: "Render-Verlauf", localeGroupHeader: "..." }` and remove the old flat key. Any spec that adds nested i18n keys must first check whether the parent key already exists as a flat string.

5. **`common.error` i18n key does not exist**: The spec's error handling referred to `$t("common.error")` as a fallback. The key does not exist in `common.ts`. Use `$t("social.renderCard.statusFailed")` instead for social-specific error notifications.

**Session 7 (Polish + QA)**

6. **`social_posts.status` is a content lifecycle enum, not a render status** — The spec assumed a "ready" status would gate download/preview. The actual `social_status` PostgreSQL enum is: `draft`, `in_review`, `approved`, `scheduled`, `published`, `failed`, `replaced`. `"ready"` never exists. Slides are written to `content.slides[]` JSONB on pipeline completion regardless of status. The correct gate for download/preview availability is `post.content?.slides?.length > 0`.

7. **STATUS_LABEL_KEYS needed a full rewrite** — The Vue component's status label map referenced render-engine statuses (`ready/rendering/pending/superseded`) not present in `social_status`. Replaced with a `social.postStatus.*` i18n namespace mapping the actual lifecycle enum values.

8. **`social_posts` has no `variant` column** — Spec C.4 said "backfill `social_posts.variant = 'stunning'`". The table has no `variant` column — it was never added. The step was a no-op.

9. **Inline contrast warnings deferred** — The spec called for client-side real-time contrast preview when changing a brand color. Not implemented: the PATCH route already returns `violations[]` server-side with `?force=true`, and the save flow works without inline preview. Inline contrast warnings remain a future enhancement.

## Deviations

| Spec says | Reality | Reason |
|-----------|---------|--------|
| `SocialPostsTab.vue` in `src/components/article/` | `ArticleSocialTab.vue` in `src/pages/articles/tabs/` | Follows established tab pattern in this project |
| `RenderHistoryList.vue` separate component | Embedded in `ArticleSocialTab.vue` | No reuse need; added complexity without benefit |
| Cost estimate `€0.03 * locales.length` | `€0.028 * locales.length` | Post-57.4 merged caption+hashtag call is slightly cheaper |
| `history.localeGroupHeader: "{locale} ({slides} Slides)"` | `"{locale} · {slides} slides"` (EN) / `"{locale} · {slides} Slides"` (DE) | Mid-dot separator is more readable; lowercase "slides" for EN consistency |
| `?force=true` for contrast validation unconfirmed | Implemented: `force=true` skips block, violations still returned with 200 | Marcel confirmed "warning not blocker" during session |
| Inline client-side contrast warnings on color change | Not implemented — server-side `violations[]` on save only | Scope creep; `?force=true` makes API advisory; inline preview deferred |
| Backfill `social_posts.variant = 'stunning'` | No-op — column does not exist | `social_posts` table has no `variant` column |
