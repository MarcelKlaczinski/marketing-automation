# Spec E.2 — Social Re-Render UI

**Theme:** Phase E (post-Theme-57 backlog)
**Status:** Draft
**Estimated effort:** 2 days
**Prerequisite:** Spec 57.2 (BullMQ render queue) implemented

---

## Goal

Allow Marcel to re-render existing social posts via UI. After editing brand tokens, template overrides, or noticing a rendering issue, clicking "Re-Render" on a social_post enqueues a new render job using the existing 57.2 BullMQ infrastructure. Per-locale separate re-render (in multi-locale posts) is supported.

## Non-Goals

- Re-render with different template (that's "generate new", not re-render)
- Re-render with manually-edited prompt overrides (separate spec if ever needed)
- Bulk re-render across multiple articles (use existing batch trigger; out of scope here)
- Re-render history / versioning (each re-render replaces previous slides; old URLs may stay in S3 but DB references current)

---

## Background

Per Spec 57.2 Open Question #3: "Re-render flow for existing posts" was deferred — "v1 has no UI; Marcel manually edits DB if needed". Marcel will iterate on brand tokens (per 57.1) and template overrides (per 57.3). Without a re-render UI, brand-token edits require DB intervention or generating a fresh new social_post (which leaves the old one as orphan).

This is the natural Phase-E follow-up to 57.2.

## Architecture

### Re-Render Flow

```
User clicks Re-Render on social_post row
  ↓
API: POST /api/social-posts/:id/re-render
  ↓
1. Reset render state on social_posts row:
   - renderStatus: 'pending'
   - renderJobId: null
   - renderStartedAt: null
   - renderCompletedAt: null
   - renderError: null
   - content.slides: []  (preserve other content fields like caption/hashtags)
2. Resolve current overrides (template overrides may have changed since original render)
3. Resolve current brand_tokens (may have changed)
4. Enqueue new render job with current snapshots
5. Return renderJobId
  ↓
Worker (existing from 57.2) picks up job → renders → updates DB
  ↓
SSE event social.render.completed → UI refetches
```

**Key principle**: re-render uses **current** brand tokens + template overrides at trigger time. NOT the original snapshot. Marcel's intent: "the article didn't change, but my brand tokens did — re-render with new tokens."

**Caption + hashtags**: NOT regenerated. They stay as-is from original render. Re-render only re-renders slides. (If caption/hashtags should be regenerated, that's a fresh "Generate" trigger, not re-render.)

## Schema Changes

None. Existing fields from 57.2 are sufficient:
- `renderStatus` enum already supports pending → rendering → rendered cycle
- `renderJobId` already nullable, gets new UUID on re-render
- `renderError` resets on retry

## API Endpoint

```typescript
// apps/api/src/routes/social-posts/re-render.routes.ts

// POST /api/social-posts/:id/re-render
// No body needed — uses current brand_tokens + overrides
router.post("/social-posts/:id/re-render", async (req, res) => {
  // 1. Fetch existing social_post
  const [post] = await db
    .select()
    .from(socialPosts)
    .innerJoin(articles, eq(socialPosts.articleId, articles.id))
    .where(eq(socialPosts.id, req.params.id))
    .limit(1);

  if (!post) return res.status(404).json({ error: "Social post not found" });

  // 2. Guard: cannot re-render while currently rendering
  if (post.social_posts.renderStatus === "rendering") {
    return res.status(409).json({
      error: "Render already in progress",
      renderJobId: post.social_posts.renderJobId,
    });
  }

  // 3. Resolve current overrides + brand tokens (live data, NOT snapshot)
  const [project] = await db
    .select()
    .from(projects)
    .where(eq(projects.id, post.social_posts.projectId))
    .limit(1);

  const overrideRow = await fetchTemplateOverrides(
    post.social_posts.projectId,
    post.social_posts.templateKey
  );
  const schema = getOverrideSchema(post.social_posts.templateKey);
  const resolvedOverrides = mergeOverrides(schema, overrideRow?.values);

  // 4. Re-resolve article tools (in case tool data changed since original)
  const resolvedTools = await resolveArticleTools(post.social_posts.articleId);
  const hook = await loadOrRegenerateHook(post.social_posts.articleId, post.social_posts.locale);
  // ^ uses existing hook from original render; only regenerates if missing

  // 5. Reset render state
  await db
    .update(socialPosts)
    .set({
      renderStatus: "pending",
      renderJobId: null,
      renderStartedAt: null,
      renderCompletedAt: null,
      renderError: null,
      content: sql`jsonb_set(content, '{slides}', '[]'::jsonb)`,
      totalSlides: 0,
    })
    .where(eq(socialPosts.id, req.params.id));

  // 6. Enqueue render with current state
  const renderJobId = await enqueueSocialRenderJob({
    socialPostId: req.params.id,
    projectId: post.social_posts.projectId,
    articleId: post.social_posts.articleId,
    templateKey: post.social_posts.templateKey,
    locale: post.social_posts.locale,
    brandTokens: project.brandTokens,
    overrides: resolvedOverrides,
    resolvedTools,
    articleTitle: post.articles.title,
    articleUrl: buildArticleUrl(post.articles),
    cluster: post.articles.cluster,
    hook,
  });

  return res.json({ renderJobId, socialPostId: req.params.id });
});
```

## Frontend UI

### Add Re-Render Button to Render History List

In `ArticleSocialTab.vue` (per 57.2):

```vue
<template>
  <div class="render-history">
    <div v-for="post in posts" :key="post.id" class="post-row">
      <span class="locale-badge">{{ post.locale }}</span>
      <span class="slide-count">{{ post.content?.slides?.length ?? 0 }} slides</span>

      <q-chip v-if="post.renderStatus === 'pending'" color="grey">
        {{ $t('socialPosts.render.pending') }}
      </q-chip>
      <!-- ... existing status chips per 57.2 ... -->

      <q-btn-group flat>
        <q-btn v-if="post.renderStatus === 'rendered'" :label="$t('socialPosts.downloadZip')" @click="downloadZip(post)" />

        <q-btn
          v-if="canReRender(post)"
          :label="$t('socialPosts.reRender')"
          icon="refresh"
          :loading="reRenderingIds.has(post.id)"
          @click="confirmReRender(post)"
        >
          <q-tooltip>{{ $t('socialPosts.reRenderHint') }}</q-tooltip>
        </q-btn>
      </q-btn-group>
    </div>
  </div>
</template>

<script lang="ts">
export default defineComponent({
  setup() {
    const reRenderingIds = ref(new Set<string>());

    function canReRender(post: SocialPost): boolean {
      // Cannot re-render while rendering; OK to re-render rendered or failed
      return post.renderStatus === "rendered" || post.renderStatus === "failed";
    }

    async function confirmReRender(post: SocialPost) {
      $q.dialog({
        title: $t("socialPosts.reRenderConfirm.title"),
        message: $t("socialPosts.reRenderConfirm.message"),
        ok: { label: $t("socialPosts.reRenderConfirm.ok"), color: "primary" },
        cancel: $t("common.cancel"),
      }).onOk(async () => {
        reRenderingIds.value.add(post.id);
        try {
          await apiPost(`/api/social-posts/${post.id}/re-render`);
          // SSE will update UI when worker picks up + completes
        } catch (err) {
          $q.notify({ type: "negative", message: $t("socialPosts.reRenderFailed") });
        } finally {
          reRenderingIds.value.delete(post.id);
        }
      });
    }

    // ... rest
  },
});
</script>
```

**UX flow**:
1. User clicks Re-Render → confirmation dialog
2. User confirms → button shows spinner; row shows `pending` chip
3. Worker picks up → row updates to `rendering` (via SSE)
4. Render completes → row updates to `rendered` with new slides (via SSE)

**Confirmation dialog rationale**: re-render takes ~10-30s and consumes worker capacity. Brief confirmation prevents accidental triggers. Not "are you sure" (paternalistic) but "will use current brand tokens — proceed?" (informative).

### CC.3 Hook Persistence Decision

Session 1 task: determine if hooks are persisted or always-regenerated. Two paths:

**If persisted** (e.g. in `social_posts.content.hook`):
- Re-render loads existing hook, reuses
- No additional LLM cost

**If regenerated**:
- Re-render also regenerates hook (small LLM cost)
- Document in spec output

**Recommendation**: ideally persisted. If not today, this spec adds persistence as side-effect (small change in original GenerateCaptionStep to write hook to `social_posts.content.hook`).

## Risks & Mitigations

**Risk 1: User re-renders rapidly (clicks button many times)**
- *Mitigation*: Backend 409 conflict if rendering. Frontend disables button while pending/rendering. Confirmation dialog adds friction.

**Risk 2: Brand tokens were valid at original render but contrast-violated now (force=true was used)**
- *Mitigation*: Re-render endpoint doesn't validate contrast (Marcel can use force-edited tokens at his discretion). Documented as acceptable behavior.

**Risk 3: Article tool data changed between original render and re-render**
- *Mitigation*: Re-resolved tools at re-render time. If a tool was removed from the article, re-render uses current article state. This may produce different output than original — intended behavior.

**Risk 4: Hook regeneration produces different hook on re-render**
- *Mitigation*: Hook persistence (recommended). If hook is regenerated, slides may have different opening text — caption now mismatches the slides. Persistence avoids this.

**Risk 5: Override snapshot vs current overrides confusion**
- *Mitigation*: Documentation. Spec is explicit: re-render uses CURRENT state, not snapshot. Marcel knows the semantic.
