## Background

Spec 57.1 completed brand-token migration for visual properties (colors, fonts, sizing). Spec 57.3 extends override capability to three non-visual surfaces:

1. **Copy strings** — slide text (CTA, eyebrow labels, transitions)
2. **Layout knobs** — boolean toggles (showPricingChip, showRankBadge, includeEndSlide)
3. **Eligibility parameters** — numeric bounds + flags that decide which articles a template can render

Without precise inventory, Spec 57.3 risks the same schema-verification gaps that affected Spec 56.6 (`articles.lastRefreshedAt` didn't exist) and Spec 57.1 (`social_posts.variant` didn't exist).

## Area A: Copy String Inventory

For each of the 4 production templates, identify EVERY user-visible text string and classify its source.

### A.1 Classification Categories

- **HARDCODED**: String literal directly in `.tsx` file (e.g. `"Mehr Tools auf"`)
- **DATA-DRIVEN**: Comes from article/tool data via props (e.g. `tool.name`, `article.title`)
- **LLM-GENERATED**: Produced by Sonnet/Haiku call upstream (e.g. caption text, hook phrases)
- **BRAND-TOKEN**: Already configurable via `brand_tokens.social` (e.g. `instagramHandle`, `websiteUrl`)

### A.2 Per-Template Inventory

For each of:
- `list-carousel/CoverSlideStunning.tsx`
- `list-carousel/ToolSlideStunning.tsx`
- `list-carousel/EndSlideStunning.tsx`
- `single-tool-spotlight/SpotlightSlide.tsx` (or equivalent)
- `use-case-verdict/VerdictSlide.tsx` (or equivalent)
- `shared/BrandLogo.tsx` and `shared/BrandFooter.tsx` (if shared across all templates)

For each template file, produce:

```markdown
### Template: CoverSlideStunning

| Element | Source Category | Current Value/Source | Override-Candidate? |
|---------|----------------|---------------------|---------------------|
| Eyebrow text | HARDCODED | `"TOP 5 TOOLS"` | YES — language + count vary |
| Title | LLM-GENERATED | `<hook.leadPhrase> <hook.highlightWord> <hook.trailPhrase>` | NO — LLM produces |
| Tool count badge | DATA-DRIVEN | `tools.length` | NO — comes from data |
| CTA bottom | HARDCODED | `"→ Weitersliden"` | YES — copy override |
| Website URL | BRAND-TOKEN | `brandTokens.social.websiteUrl` | ALREADY (no new override) |
| Instagram handle | BRAND-TOKEN | `brandTokens.social.instagramHandle` | ALREADY |
```

**Critical**: For each HARDCODED string, also classify by **purpose** to help group overrides logically:
- *Brand voice*: signature phrases, slogans
- *Navigation*: "Swipe →", "Mehr unten", "Weitersliden"
- *Section labels*: "Pros", "Cons", "Verdict", "Pricing"
- *Eyebrow text*: small uppercase header above slide title
- *CTA*: end-slide call to action, link prompts
- *Locale-dependent*: any string that has DE/EN variants and switches on `locale.startsWith("de")`

### A.3 LLM-Generated Surface (NOT for override)

For completeness, list which slides have LLM-generated text:

- The EN string (or `.startsWith("en")` equivalent)

## Area B: Layout Knob Surface

### B.1 Existing Optional Elements

Look for conditional rendering in templates:
- `{showPricing && <PricingChip />}` — `showPricing` is an existing layout knob
- `{tool.rank && <RankBadge />}` — `tool.rank` presence-based, not a knob
- `{footer.enabled !== false && <BrandFooter />}` — boolean knob

For each template, enumerate:
1. **What's optional today** (already gated by some boolean or data presence)
2. **What's conditional but not knob-able** (gated by data presence — `{tool.icon && <Icon />}`)
3. **What's always rendered** (no conditional — but could become a knob)

### B.2 Always-Rendered Elements as Knob Candidates

Some always-rendered elements might reasonably be hide-able:
- End-slide (some projects might want to end on last tool slide)
- Cover slide (some content types might want to jump straight to first tool)
- Rank badges (some projects might want unranked listicles)
- Pricing chips (some projects might not care about pricing)

For each always-rendered element, investigator's judgment: **would a project plausibly want this hidden?**

### B.3 Numeric / Enum Knob Candidates

Beyond booleans, are there other configurable values?
- `maxToolsShown: number` (template might support 3-10 tools, project picks)
- `slideOrder: "rank-asc" | "rank-desc" | "alphabetical"`
- `pricingDisplay: "chip" | "inline" | "hidden"` (three-way enum vs simple boolean)

List all such candidates currently hardcoded.

### C.1 Current Eligibility Predicates

`packages/social/src/registry.ts` (or wherever eligibility lives):

eligibility: (article, discovery) => {
  if (!discovery.tools || discovery.tools.length < 3) return false;

### C.2 Common Parameter Schema Across Templates

Across all 4 templates, what parameter types appear?
- Tool count bounds (min/max)
- Intent type allow-list or block-list
- Required data fields (e.g. `requiresPricing: boolean`)
- Article cluster constraints?
- Article length constraints?

Goal: identify a **shared parameter schema** that covers most predicates, vs template-specific parameters.

### C.3 Predicates That Don't Cleanly Parameterize

Some predicates may have complex logic that resists parameter extraction:
- `if (article.cluster?.tools?.some(t => t.pricing !== "free")) return false`
- Boolean combinations: `(A && B) || (C && !D)`

For each such case, investigator's judgment: **can this become a simple parameter, or does it need to stay in code?**

If a predicate stays in code, it cannot be project-overridable — note these.

## Area E: Cross-cutting Considerations

### E.1 Per-Render vs Per-Project Overrides

Currently planned: overrides are **per-project** (apply to all renders for that project).

Question: are there cases where a project would want **per-article overrides**? E.g. one specific article wants `showPricing: false` even though project default is true.

Investigator's recommendation: include per-article override layer now (3-tier: project → article-specific → template-default), or keep simple (2-tier: project → template-default)?

### E.2 `last_used_at` Update Strategy

Tracking `last_used_at` on `project_template_overrides` requires updates on each render. Options:
- **Synchronous in pipeline**: blocks pipeline by ~5ms per write, but simple
- **Background job**: fire-and-forget UPDATE after pipeline completes
- **Approximated**: only UPDATE if existing `last_used_at` is older than 1h

What's the codebase's existing pattern for hot-path timestamp updates? Search for `last_used_at`, `last_run_at`, `updated_at` patterns in other tables.

### E.3 Migration Strategy

After 57.3 lands, existing projects have NO `project_template_overrides` rows. Pipeline must handle this gracefully — fall through to template defaults.

Question: should there be a one-time migration that creates empty (no-override) rows for each (project, template) pair? Or lazy-create only when user actually overrides something?

Investigator's recommendation: lazy is simpler.
