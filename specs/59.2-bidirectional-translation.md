# Spec 59.2 — Bidirectional Translation EN → DE

**Theme:** 59 (Tier 3 Pre-Launch Foundation)
**Status:** Implemented (all 5 sessions complete)
**Estimated effort:** 3-4 days (~22 focused hours across 5 sessions)
**Prerequisite:** Spec 54.10 (Translation Pipeline DE → EN, production-ready)
**Successor:** 59.3 news-slide Social Template

---

## Goal

Generalize the existing DE → EN translation pipeline from Spec 54.10 to work **bidirectionally** — when an EN article is generated (via gap/trend discovery sources that surface English content, or manual article-tools standalone generation with `locale=en`), the system auto-triggers a DE-translation, mirroring the existing DE → EN auto-trigger pattern.

The pipeline functions are locale-parameterized: `findSibling(article)` resolves to the opposite-locale article via `translationKey`, `buildTranslationContext(source, targetLocale)` works in both directions, `decideTranslationStrategy` adapts its prompt based on source locale.

After 59.2 lands, toolwiki's content lifecycle is fully symmetric:
- DE-Article generated → EN sibling auto-translated (existing 54.10)
- EN-Article generated → DE sibling auto-translated (NEW)
- Either direction: refresh propagates to sibling automatically
- Source-of-truth conflicts: last-write-wins + UI warning offers manual re-sync

## What this is NOT

- Not a separate parallel pipeline — refactor existing 54.10 functions to be bidirectional
- Not changing voice-reference loading mechanism — locale-parameterized already (54.10 D.1)
- Not adding `cluster_action` enum values — `'translation'` already exists, semantics unchanged
- Not bidirectional cluster generation — clusters remain DE-first via Cluster Creator (Phase D 54.12 backlog)
- Not adding versioning for divergent siblings — last-write-wins, no per-locale forks
- Not changing the `translationAutoTrigger` semantics — extends to both directions

```typescript
export async function findSibling(article: Article): Promise<Article | null> {
  if (!article.translationKey) return null;

  // Determine target locale (opposite of source)
  const targetLocale: "de" | "en" = article.locale === "de" ? "en" : "de";
```

```typescript
// packages/pipelines/src/article/translation/decision.ts

export async function decideTranslationStrategy(input: {
  sourceArticle: Article;
  sourceLocale: "de" | "en";
  targetLocale: "de" | "en";
  brief: TopicBrief | null;
}): Promise<{ decision: "literal" | "adaptive"; reasoning: string }> {

  const prompt = buildDecisionPrompt(input);

  const response = await anthropic.messages.create({
    model: "claude-haiku-4-5-20251001",
    max_tokens: 200,
    messages: [{ role: "user", content: prompt }],
  });

  await logCost({
    projectId: input.sourceArticle.projectId,
    service: "anthropic",
    operation: COST_OPS.TRANSLATION_DECISION,
    costEur: 0.005,
    articleId: input.sourceArticle.id,
  });

  return parseJsonResponse(response);
}

function buildDecisionPrompt(input: {
  sourceArticle: Article;
  sourceLocale: "de" | "en";
  targetLocale: "de" | "en";
  brief: TopicBrief | null;
}): string {

  // Locale-specific adaptation markers
  const adaptiveMarkers = input.sourceLocale === "de"
    ? deToEnAdaptiveMarkers
    : enToDeAdaptiveMarkers;

  const sourceLocaleName = input.sourceLocale === "de" ? "German" : "English";
  const targetLocaleName = input.targetLocale === "de" ? "German" : "English";

  return `
You are evaluating whether a ${sourceLocaleName} blog article needs a ${targetLocaleName}-audience-specific outline adaptation, or can be translated literally.

Source article title: ${input.sourceArticle.title}
Source article body (first 2000 chars):
${input.sourceArticle.bodyMd?.substring(0, 2000)}

Brief context:
- Primary keyword: ${input.brief?.primaryKeyword ?? "n/a"}
- Intent: ${input.brief?.intentType ?? "n/a"}
- Source: ${input.brief?.source ?? "n/a"}

Evaluate whether the article should be:
- "literal": ${targetLocaleName} version preserves source outline; only language changes. Content is universally relevant; no source-specific context needs reframing.
- "adaptive": ${targetLocaleName} audience needs different angles.

Examples that justify "adaptive" for ${sourceLocaleName} → ${targetLocaleName}:
${adaptiveMarkers}

Respond in JSON:
{
  "decision": "literal" | "adaptive",
  "reasoning": "brief explanation (max 100 words)"
}
`;
}

const deToEnAdaptiveMarkers = `
- German-specific pricing (EUR only, no USD reference)
- DSGVO/BaFin/Mittelstand emphasis
- "Made in Germany" framing
- DACH-only market data (Statista DE, Bitkom)
- German legal context (UWG, BDSG)
- German B2B sales norms (very formal, Sie-form heavy)
`;

const enToDeAdaptiveMarkers = `
- US-centric pricing (USD only, no EUR equivalent)
- US-specific regulatory framing (HIPAA, SOC 2 emphasis without GDPR mention)
- "Silicon Valley" or US-startup-culture framing
- US market data (Gartner US, Forrester US-only)
- English idioms that don't translate (e.g. "move fast and break things")
- US legal context (CCPA, but not GDPR/DSGVO)
- US-only tool examples (e.g. assumes user has SSN, US ZIP code)
`;
```

```typescript
// packages/pipelines/src/article/translation/pipeline.ts

export interface TranslationPipelineInput {
  sourceArticleId: string;
  targetArticleId?: string;  // present for refresh_propagation mode (update existing)
  mode: "fresh_translation" | "refresh_propagation" | "manual_resync";
  pipelineRunId: string;
}

export async function runTranslationPipeline(input: TranslationPipelineInput): Promise<TranslationResult> {
  const sourceArticle = await loadArticle(input.sourceArticleId);

  if (!sourceArticle.locale) {
    throw new TranslationPipelineError(`Source article ${input.sourceArticleId} has no locale`);
  }

  // Determine target locale (opposite of source)
  const sourceLocale = sourceArticle.locale as "de" | "en";
  const targetLocale: "de" | "en" = sourceLocale === "de" ? "en" : "de";

  const brief = sourceArticle.briefId ? await loadBrief(sourceArticle.briefId) : null;

  // 1. Decision call (locale-aware)
  const decision = await decideTranslationStrategy({
    sourceArticle,
    sourceLocale,
    targetLocale,
    brief,
  });

  // 2. Load voice references in TARGET locale (existing 54.10 D.1, already parameterized)
  const voiceRefs = await loadVoiceReferences({
    projectId: sourceArticle.projectId,
    clusterId: sourceArticle.clusterId,
    locale: targetLocale,
    excludeArticleId: input.targetArticleId ?? null,
    limit: 3,
  });

  // 3. Find or create target article
  let targetArticle: Article;

  if (input.mode === "refresh_propagation" || input.mode === "manual_resync") {
    // Update existing sibling
    if (!input.targetArticleId) {
      throw new TranslationPipelineError(`${input.mode} requires targetArticleId`);
    }
    targetArticle = await loadArticle(input.targetArticleId);

    // Persist old version BEFORE regeneration (54.10 B.4 pattern)
    await persistVersion(targetArticle, input.mode);
  } else {
    // fresh_translation: create new article row
    targetArticle = await createTargetArticleRow({
      sourceArticle,
      targetLocale,
      decision,
    });

    // Back-apply translationKey to source if it doesn't have one
    if (!sourceArticle.translationKey) {
      await db.update(articles)
        .set({ translationKey: targetArticle.translationKey })
        .where(eq(articles.id, sourceArticle.id));
    }
  }

  // 4. Pipeline branch (literal vs adaptive)
  let bodyMd: string;
  let outline: OutlineResult | null = null;

  if (decision.decision === "adaptive") {
    const enBrief = await buildBriefForTranslation({
      sourceArticle,
      targetLocale,
      decision,
      sourceBrief: brief,
    });

    outline = await runOutlineStep({
      brief: enBrief,
      sourceContext: buildTranslationContextFragment({
        sourceArticle,
        sourceLocale,
        targetLocale,
        decision,
      }),
      toolsContext: await buildToolsContext(enBrief, targetLocale),
      voiceReferences: voiceRefs,
      pipelineRunId: input.pipelineRunId,
      articleId: targetArticle.id,
    });

    const draft = await runDraftStep({
      brief: enBrief,
      outline,
      sourceContext: buildTranslationContextFragment({
        sourceArticle,
        sourceLocale,
        targetLocale,
        decision,
      }),
      toolsContext: await buildToolsContext(enBrief, targetLocale),
      voiceReferences: voiceRefs,
      pipelineRunId: input.pipelineRunId,
      articleId: targetArticle.id,
    });

    bodyMd = draft.bodyMd;
  } else {
    // literal: locale-aware translate-draft
    const translateResult = await runTranslateDraftStep({
      sourceBody: sourceArticle.bodyMd!,
      sourceOutline: sourceArticle.outline,
      sourceLocale,
      targetLocale,
      voiceReferences: voiceRefs,
      pipelineRunId: input.pipelineRunId,
      articleId: targetArticle.id,
      projectId: sourceArticle.projectId,
    });

    bodyMd = translateResult.bodyMd;
  }

  // 5. Linkify with target locale (existing 54.10 step, already locale-parameterized)
  const linkified = await linkifyMarkdown(bodyMd, sourceArticle.projectId, targetLocale);

  // 6. Update target article
  await db.update(articles)
    .set({
      title: extractTitle(linkified.bodyMd),
      bodyMd: linkified.bodyMd,
      wordCount: countWords(linkified.bodyMd),
      outline: decision.decision === "adaptive" ? outline?.value : translateOutline(sourceArticle.outline, sourceLocale, targetLocale),
      status: input.mode === "fresh_translation" ? "draft_done" : targetArticle.status,
      updatedAt: new Date(),
      lastSyncedFromSiblingAt: new Date(),  // NEW column, see Section C
    })
    .where(eq(articles.id, targetArticle.id));

  // 7. SelfReview + Schema for target (existing steps)
  await runSelfReviewStep({ articleId: targetArticle.id, pipelineRunId: input.pipelineRunId });
  await runSchemaExtensionStep({ articleId: targetArticle.id });

  return {
    sourceArticleId: sourceArticle.id,
    targetArticleId: targetArticle.id,
    sourceLocale,
    targetLocale,
    decision: decision.decision,
    decisionReasoning: decision.reasoning,
    mode: input.mode,
    toolsLinked: linkified.linkedTools,
  };
}
```

```typescript
You are translating a ${sourceLocaleName} blog article into idiomatic ${targetLocaleName} for ${targetAudience}.

Voice references (existing ${targetLocaleName} articles in the same content space):
${formatVoiceReferences(input.voiceReferences)}

The ${sourceLocaleName} article body to translate:
${input.sourceBody}

Requirements:
- Preserve the article's narrative structure (don't reorder sections)

- Match the voice tone of the reference articles (anti-hype, concrete, pragmatic)
- Tool names stay in their canonical form (e.g. "ChatGPT" stays "ChatGPT")
- Adapt audience-specific context naturally where it doesn't fit

${styleNotes}

Output: the translated article body in markdown, no preamble or commentary.
`;
```

```typescript
async function finalizeBlogPipeline(article: Article, project: Project): Promise<void> {
  // ... existing logic ...

  // Bidirectional auto-trigger
  if (project.translationAutoTrigger === false) return;

  const sourceLocale = article.locale as "de" | "en";
  const targetLocale: "de" | "en" = sourceLocale === "de" ? "en" : "de";

  // Map short codes to BCP-47 for targetLocales check

    return;

    sourceArticleId: article.id,
    mode: "fresh_translation",
    pipelineRunId: generatePipelineRunId(),
```

```typescript
async function handleManualTranslate(c: Context) {
  const { slug, id } = c.req.param();
  const { force = false } = await c.req.json().catch(() => ({}));

  const project = await loadProjectBySlug(slug);
  if (!project) return c.json({ ok: false, error: "project_not_found" }, 404);

  const article = await loadArticle(id);
  if (!article || article.projectId !== project.id) {
    return c.json({ ok: false, error: "article_not_found" }, 404);
  }

  if (!article.bodyMd) {
    return c.json({ ok: false, error: "article_not_ready", message: "Article has no body content yet" }, 422);
  }

  const existingSibling = await findSibling(article);

  if (existingSibling && !force) {
    return c.json({
      ok: false,
      error: "sibling_exists",
      message: "Sibling translation already exists. Use force=true to re-translate as manual_resync.",
      data: { siblingId: existingSibling.id },
    }, 409);
  }

  const mode: "fresh_translation" | "manual_resync" = existingSibling ? "manual_resync" : "fresh_translation";

  const pipelineRunId = generatePipelineRunId();
  await enqueueTranslationPipeline({
    sourceArticleId: article.id,
    targetArticleId: existingSibling?.id,
    mode,
    pipelineRunId,
  });

  return c.json({
    ok: true,
    data: { pipelineRunId, mode, targetArticleId: existingSibling?.id ?? null },
  }, 202);
}
```

### C.1 Divergence detection

A sibling pair is "diverged" when one side has been edited or refreshed since the last translation sync. Track this with new column:

```sql
-- migration 0xxx_translation_sync_tracking.sql
ALTER TABLE articles
  ADD COLUMN last_synced_from_sibling_at TIMESTAMP,
  ADD COLUMN last_edited_at TIMESTAMP;
```

**Semantics**:
- `last_synced_from_sibling_at`: set when this article was produced or updated by Translation Pipeline (with sibling as source). NULL means article was never produced as a translation (original/source side).
- `last_edited_at`: set on every user-driven edit (article-detail save, manual rewrite). Set by article-update endpoint, not by pipelines.

**Divergence formula**: a sibling pair is divergent if `EITHER side's last_edited_at > BOTH sides' last_synced_from_sibling_at`.

In practice: simpler heuristic that works for the UI:

```typescript
async function detectDivergence(article: Article): Promise<DivergenceState> {
  const sibling = await findSibling(article);
  if (!sibling) return { state: "no_sibling" };

  // Both sides know about the same translation event (the most recent sync)
  const lastSyncOfThis = article.lastSyncedFromSiblingAt ?? new Date(0);
  const lastSyncOfSibling = sibling.lastSyncedFromSiblingAt ?? new Date(0);
  const lastSyncAt = new Date(Math.max(lastSyncOfThis.getTime(), lastSyncOfSibling.getTime()));

  const thisEditedAfter = (article.lastEditedAt ?? new Date(0)) > lastSyncAt;
  const siblingEditedAfter = (sibling.lastEditedAt ?? new Date(0)) > lastSyncAt;

  if (thisEditedAfter && siblingEditedAfter) {
    return {
      state: "both_diverged",
      sibling: { id: sibling.id, locale: sibling.locale, lastEditedAt: sibling.lastEditedAt },
    };
  }
  if (thisEditedAfter) {
    return {
      state: "this_newer",
      sibling: { id: sibling.id, locale: sibling.locale, lastEditedAt: sibling.lastEditedAt },
    };
  }
  if (siblingEditedAfter) {
    return {
      state: "sibling_newer",
      sibling: { id: sibling.id, locale: sibling.locale, lastEditedAt: sibling.lastEditedAt },
    };
  }
  return { state: "in_sync", sibling: { id: sibling.id, locale: sibling.locale } };
}
```

```vue
    showDivergenceBanner(): boolean {
      if (this.dismissedDivergenceBanner) return false;
      const state = this.article?.sibling?.divergence?.state;
      return state === "this_newer" || state === "sibling_newer" || state === "both_diverged";
    },
  },
  methods: {
    // ... existing methods ...
    async onResyncSibling() {
      // Calls POST /articles/:id/translate with force=true
      // Source is whichever article is "newer" — for "this_newer" it's the current article,
      // for "sibling_newer" it's the sibling (we should open the sibling and re-trigger there)
      const state = this.article.sibling.divergence.state;

      if (state === "this_newer" || state === "both_diverged") {
        // Re-sync sibling from THIS article (current article is source)
        const result = await apiClient.articles.translate({
          slug: this.projectSlug,
          articleId: this.article.id,
          force: true,
        });
        this.$q.notify({
          type: "positive",
          message: this.$t("articleDetail.divergence.resyncStarted", { jobId: result.data.pipelineRunId }),
        });
      } else if (state === "sibling_newer") {
        // Sibling is newer — open it and trigger re-sync from there
        this.onOpenSibling();
      }
    },
    onOpenSibling() {
      const siblingId = this.article.sibling.divergence.sibling.id;
      this.$router.push(`/projects/${this.projectSlug}/articles/${siblingId}`);
    },
    onDismissBanner() {
      this.dismissedDivergenceBanner = true;
    },

});
```

## Section D: Adaptive Decision Prompt Variations

The decision call (A.3) uses different "adaptive markers" per source locale. This section documents them in more detail.

### D.1 DE → EN adaptive markers (existing, restated for clarity)

Existing 54.10 implementation — refactor doesn't change logic, just moves into `deToEnAdaptiveMarkers` constant.

Triggers "adaptive" path when DE article emphasizes:
- DSGVO over GDPR
- BaFin / Mittelstand specifics
- EUR-only pricing (no USD parallel)
- "Made in Germany" or DACH-only framing
- German legal contexts (UWG, BDSG)
- German formal address conventions (Sie-Form, very formal)

### D.2 EN → DE adaptive markers (NEW)

Triggers "adaptive" path when EN article emphasizes:
- US-only regulations (HIPAA, SOC 2 without GDPR parallel)
- US-only pricing (USD without EUR parallel for SaaS)
- "Silicon Valley" / "Bay Area" framings that don't translate
- US-specific market data (Gartner US, Forrester US-only)
- English idioms that need rewording for German B2B (e.g. "move fast and break things")
- US-only consumer contexts (assumes SSN, US ZIP, US tax IDs)
- US-cultural references that distract DE readers
- Imperial units without metric equivalents

### D.3 When literal is correct

For both directions: if content is about universal tech topics (LLM technology, vector databases, embeddings, math concepts, programming patterns), literal translation is appropriate. The decision call returns `literal` and Translate-Draft step handles the language conversion without restructuring.

### D.4 Expected adaptive frequency

Based on toolwiki content patterns:
- DE → EN: ~25-35% adaptive (most AI-tool reviews are universal)
- EN → DE: ~20-30% adaptive (similar pattern, English source articles need DACH-localization when they're US-specific)

Adaptive cost ~€0.30 vs literal ~€0.18. Decision call €0.005. Expected avg per translation: ~€0.21 (validated 54.10).

### D.5 Future: Voice-of-translator marker

Not in 59.2 scope, but planned for Phase E: track which adaptive markers were detected per article in `articles.translationMetadata` JSONB. Allows future analytics on what kinds of content need adaptation.

## Decisions Made

**Decision 1: Bidirectional via locale-parameterization, not parallel pipelines (Q4 = A).**
Existing 54.10 pipeline becomes locale-aware. `findEnSibling` aliased for backward compatibility. Future locales (FR, ES) can be added by extending the locale type union.

**Decision 2: Auto-trigger after EN-Article completion (Q2 = B).**
Mirror of 54.10 DE→EN auto-trigger. Same Blog Pipeline finalize hook, just doesn't hardcode source locale.

**Decision 3: Last-write-wins with UI warning + re-sync offer (Q3 = B).**
No version forking, no primary-flag complexity. Two new timestamps track sync state and edit state. UI banner shows divergence + offers re-sync. Marcel decides per case.

**Decision 4: EN articles emerge from same pipeline as DE (Q1).**
Trend discovery, gap analysis, or manual article-tools generation — all already produce articles with explicit locale. No special "EN import" path. Existing 54.5.1 locale handling already supports this.

**Decision 5: Same auto-trigger flag controls both directions.**
`translationAutoTrigger` semantics extend without new column. Per-direction toggles unnecessary at toolwiki scale.

**Decision 6: Manual re-sync endpoint shared with auto-trigger pipeline.**
`POST /articles/:id/translate` handles all manual cases. Mode parameter distinguishes fresh_translation vs manual_resync.

**Decision 7: Refresh propagation symmetric in both directions.**
54.10 B.3 step 9 drops `locale === "de"` guard. Refresh from any locale propagates to sibling.

**Decision 8: Decision prompt has two adaptive marker variants.**
DE-source uses German-specific markers, EN-source uses US-specific markers. Decision call cost unchanged (~€0.005).

**Decision 9: Divergence detection uses two timestamps, no edit history.**
`last_edited_at` (user-edits) + `last_synced_from_sibling_at` (pipeline-syncs). Simple comparison shows divergence. No need for diff/merge tooling.

**Decision 10: Refresh does NOT set last_edited_at.**
Refresh is a sync operation, not user-divergence. Only manual article edits set `lastEditedAt`.

**Decision 11: Divergence banner dismissible per session.**
Once Marcel dismisses, banner stays hidden for that session. Persists across page navigation but resets on page reload. Simple, no DB tracking of dismissals.

**Decision 12: Backfill assumes existing translated pairs are in-sync.**
Sets `last_synced_from_sibling_at = updated_at` for existing translations. No false divergence warnings post-deploy.

**Decision 13: Sibling re-sync from "sibling_newer" state requires opening sibling.**
When sibling is the newer version, the re-sync button on current page just navigates to sibling. Marcel hits re-sync there with sibling as source. Avoids cross-article state mutation from a passive viewing context.

**Decision 14: No `cluster_action` enum change.**
Existing `'translation'` value covers EN→DE just as it covers DE→EN.

## Risks & Mitigations

**R1: Existing translation flows break during refactor.**
- *Mitigation*: Session 1 keeps `findEnSibling` alias + verifies all 54.10 tests pass before moving on.

**R2: Divergence detection has edge cases (clock skew, daylight savings).**
- *Mitigation*: Use UTC timestamps throughout. PostgreSQL's `TIMESTAMP` is timezone-naive UTC by convention. Compare via `getTime()` which returns ms since epoch.

**R3: Auto-trigger creates infinite loop (EN→DE→EN→...).**
- *Mitigation*: Auto-trigger checks for existing sibling before enqueuing. After first translation, sibling exists, so future Blog Pipeline finalize on either side hits the duplicate-guard and exits. Refresh Pipeline uses `refresh_propagation` mode which updates (not creates), no loop possible.

**R4: Existing imported articles trigger false divergence on first load.**
- *Mitigation*: Backfill `last_edited_at = created_at` AND `last_synced_from_sibling_at = updated_at`. Both timestamps equal, so divergence formula returns "in_sync".

**R5: Manual re-sync replaces unsaved user changes in sibling.**
- *Mitigation*: Re-sync triggers Translation Pipeline with `manual_resync` mode, which persists current sibling body to `article_versions` BEFORE overwriting (per 54.10 B.4 pattern). User can recover from version history.

**R6: `findSibling` returns wrong sibling when multiple translations exist.**
- *Mitigation*: Per existing schema, `translation_key` + `locale` are unique together within a project. No way to have 2 EN siblings for one DE article. Query is single-row safe.

**R7: User edits source while translation is queued, creating immediate divergence.**
- *Mitigation*: Expected behavior. Translation pipeline runs against article state at queue-time. After completion, divergence banner appears if user kept editing. UI guides user through re-sync.

**R8: Cost surprise from unintended translations.**
- *Mitigation*: Auto-trigger respects `translationAutoTrigger=false`. Marcel can disable globally per project. Manual translate endpoint always requires user action (no auto-fire).

## Deviations from Spec (Sessions 1–2)

### Dev 1: Kept class-based step architecture (Section A.4)

Spec Section A.4 showed `runTranslationPipeline` rewritten as a standalone function. Implementation kept the existing class-based `Pipeline` + `BaseStep` architecture and refactored the steps in-place. This preserves the cost-tracking, idempotency, and Zod-validation contracts provided by `BaseStep`. The function-based pseudocode in the spec was illustrative, not prescriptive.

### Dev 2: Locale-neutral step I/O field names (Section A.2–A.5)

Spec examples used DE-named fields (`deBodyMd`, `enArticleId`, `enTitle`). Implementation uses locale-neutral names (`sourceBodyMd`, `targetArticleId`, `targetTitle`) throughout `TranslationSetupOutput` and `TranslationBodyStep` output. This prevents confusion when EN is the source and eliminates the need for aliasing. All bridge references in `pipeline.ts` updated accordingly.

### Dev 3: Sibling-existence guard added to BlogPipeline auto-trigger (Section B.1)

Spec Section B.1 did not include an explicit DB query to check for an existing sibling before enqueuing. Implementation adds `findSibling()` check inside `BlogPipeline.afterComplete` to prevent accidental duplicate creation when the blog pipeline is re-run on an article that already has a sibling. The spec's intent (avoid duplicate creation) is preserved; the mechanism is made explicit.

### Dev 5: `detectDivergence()` is synchronous and pure (Section C.1)

Spec C.1 showed `detectDivergence(article)` as an async function that fetches the sibling internally. Implementation makes it a pure synchronous function that receives pre-fetched timestamp values from the GET handler (sibling is already loaded). This is cleaner — no redundant DB call — and the divergence computation itself is four comparisons with no I/O.

### Dev 6: `lastEditedAt` only set on content-field PATCH, not status changes (Section C.5)

Spec C.5 said "set `last_edited_at` on every user-driven edit via `PATCH /articles/:id`". Implementation restricts this to content-field changes (title, metaDescription, cornerstoneKeyword, slug). Status-only PATCHes (approve workflow) do NOT set `lastEditedAt` because status is a workflow action, not a content edit. Setting it on status changes creates false divergence warnings when Marcel approves a freshly-translated article.

### Dev 7: DivergenceBanner description strings require `{locale}` interpolation (Section C.4)

The spec's pseudocode did not show interpolation params for description text. All three i18n description strings were written with `{locale}` placeholder, requiring `{ locale: siblingLocaleLabel }` to be passed to every `$t()` call including `descriptionText`. Omitting the param renders the literal `{locale}` text in the UI.

### Dev 4: `enqueueTranslationPipeline` gained `preRunId` field (Section B.4)

Spec Section B.4 defined the manual endpoint but didn't specify how it wires to `triggerWithPreRunId`. Implementation added optional `preRunId` to `EnqueueTranslationInput` so the enqueue wrapper is compatible with the CLAUDE.md-mandated `triggerWithPreRunId` pattern.
