# Spec 62.5 — Planner Kalender-UI + Approval-Flow

_Theme 62 Sub-Spec — visualisiert weekly_plans + planned_items, gibt Marcel Approval-Workflow._
_Status: Draft._
_Voraussetzung: 62.0a, 62.0b, 62.2, 62.3.5, 62.3, 62.4 sind gemerged._

---

## 1. Ziel

62.4 produziert `weekly_plans` + `planned_items` in der DB. 62.5 macht das sichtbar und bearbeitbar:

1. **Top-Level Planner-Page** unter `/projects/:slug/planner` mit Cmd+K-Action
2. **Wochen-Kalender** mit Grid- und List-View-Toggle
3. **"Generate Plan"-Button** für KW+1 (und custom KW-Auswahl)
4. **Item-Detail-Page** mit allen Plan-Item-Metadaten + State-Transitions
5. **Drei-Stufen-Approval:**
  - Approve / Cancel pro Item
  - Drag&Drop-Reschedule des slot_date
  - Approve-All vs. Partial-Approve

**In Scope:**
- Page + Routes + Sidebar-Integration
- Wochen-Grid + List-View
- KW-Navigation (vor/zurück)
- Generate-Trigger via UI
- Budget-Display mit Color-Status
- Item-Detail-Page
- Approval/Cancel per Item
- Approve-All / Approve-Selected
- Drag&Drop slot_date (Desktop)

**Out of Scope:**
- Item-Execution (62.8 — Approve setzt nur status='approved')
- Cron-UI (62.7)
- Mobile Drag&Drop (Desktop only — Mobile bekommt Date-Picker als Fallback)
- Step-Pause-UI für Planner-Pipeline-Debug (62.6)
- Quarantäne-View (62.7)
- Real-time Updates während Plan-Generation (SSE oder Poll — kommt mit 62.6)

**Geschätzter Aufwand:** 2-3 Tage.

---

## 2. Architektur-Entscheidungen

Aus Marcel-Antworten + UI-Konventionen:

- **Eigene Top-Level-Page:** Route `/projects/:slug/planner`, eigene `PlannerPage.vue`. Settings-Plan-Page (62.2) bleibt für Goals-Config — kriegt einen Link-Button "Open Planner".
- **View-Toggle persistent:** localStorage-Key `planner.viewMode` = `"grid" | "list"`. Default `"grid"` auf Desktop, `"list"` auf Mobile.
- **Item-Detail als Route, nicht Modal:** `/projects/:slug/planner/items/:itemId`. Vermeidet Modal-Hell, deep-linkable, Browser-Back funktioniert natürlich.
- **Drag&Drop nur auf Desktop-Grid:** Mobile zeigt stattdessen einen Date-Picker im Item-Detail (`slot_date`-Field editierbar).
- **API-Endpoints aus 62.4 unverändert:** GET/PATCH/POST sind alle da. 62.5 ist ausschließlich Frontend (plus ein zusätzlicher PATCH-Endpoint für `slot_date`-Reschedule — siehe §5).
- **Optimistic Updates für Snappiness:** Approve/Cancel/Reschedule updaten State sofort, Re-Sync bei Server-Response. Bei Fehler Rollback + Toast.
- **Quasar als UI-Framework wie üblich.** Custom Glassmorphism-Components wo Quasar nicht reicht.
- **Generate-Button-Flow:** loading-state während Pipeline läuft, dann Auto-Refresh des Kalenders auf neue Plan-ID.

### 4.6 Generate-Flow

Wenn User auf "Generate Plan for KW X" klickt:

1. Confirm-Dialog: "Plan für KW X / Year Y generieren? Geschätzte Kosten: pre-flight unbekannt"
2. Approve → POST `/api/projects/:slug/plans/generate` mit `{ targetYear, targetIsoWeek, force: false }`
3. UI zeigt Spinner mit "Generating plan..." (Pipeline dauert typischerweise 1-3s)
4. Response → Auto-Navigate zur generierten KW
5. Bei `PlanAlreadyExistsError` → Confirm-Dialog "Plan existiert. Überschreiben?" → 2. Call mit `force: true`
6. Bei `BudgetExceededError` → klare Error-Message mit Aufschlüsselung, kein Plan persisted

## 5. API-Erweiterung

62.4 hat fast alles. Nur **ein zusätzliches Endpoint** für Reschedule:

```ts
// PATCH /api/projects/:slug/plans/:planId/items/:itemId
// Body: { 
//   status?: 'cancelled',           // existing from 62.4
//   slotDate?: string (ISO date)    // NEW in 62.5
// }
// 
// Constraints:
// - Plan-status muss 'draft' oder 'approved' sein (nicht 'running' / höher)
// - Item-status muss 'pending' sein für slot_date-Change
// - slotDate muss innerhalb week_start_date - week_end_date des Plans liegen
// - Bei sibling_locale items: slot_date wird relativ zum parent neu berechnet? 
//   ENTSCHEIDUNG: nein, sibling kann unabhängig reschedule werden (Marcel entscheidet)
```

Server-Side Validation:

```ts
if (newSlotDate < plan.week_start_date || newSlotDate > plan.week_end_date) {
  throw new ValidationError("slot_date outside plan week boundaries");
}
if (item.status !== "pending") {
  throw new ValidationError(`Cannot reschedule item in status '${item.status}'`);
}
if (!["draft", "approved"].includes(plan.status)) {
  throw new ValidationError(`Cannot reschedule items in plan status '${plan.status}'`);
}
```

### 7.3 Drag&Drop-Implementation

Vermutlich `vuedraggable` (basiert auf SortableJS, gut getestet). Falls schon im Workspace: nutzen. Falls neu: Add-Dep.

**Wichtig:** vuedraggable braucht ein reactive Array. Pro Tag eine Liste der Items, Drag zwischen Listen ändert `slot_date`. Bei drop:

```ts
function onItemDropped(item, newDate) {
  const oldDate = item.slot_date;
  // Optimistic
  item.slot_date = newDate;
  
  try {
    await patchItem(item.id, { slotDate: newDate });
  } catch (e) {
    // Rollback
    item.slot_date = oldDate;
    showErrorToast(e);
  }
}
```

## 10. Risiken

| Risiko | Mitigation |
|---|---|
| vuedraggable bringt bugs auf macOS Safari | Falls Mobile-Test passes auf iOS: vermutlich ok. Sonst HTML5-native-fallback |
| Drag&Drop friert UI ein bei vielen Items (50+) | Realistic plan = 30 items. Falls je problem: virtualisieren |
| Optimistic Update + Server-Error → State-Drift | Rollback-Pattern in `usePlanItemActions`, Toast-Error |
| Date-Picker erlaubt slot_date außerhalb Plan-Woche | Server-Validation als Backstop, UI-Date-Picker `min`/`max` props |
| KW-Year-Boundary bugs (KW 53 / KW 1 cross-year) | Nutze existierende ISO-Week-Helper aus 62.4 Discovery (`packages/planner/src/iso-week.ts`) |
| Mobile-Layout bricht | Default-List auf Mobile, Grid wird ausgeblendet. Detail-Page is mobile-friendly schon |
| Sidebar-Eintrag kollidiert mit anderen Sections | Phase 0 prüft, ggf. Order anpassen |
| Item-Card-Truncation entfernt wichtige Info | Tooltip auf Title-Hover zeigt vollen Title |
| Generate-Pipeline ist langsam (>5s) → UI-Spinner-Fatigue | 62.4 schätzte 1-3s. Falls länger: Progress-Indicator mit Step-Names (out of scope, 62.6) |
| Bulk-Approve via Checkbox + Approve-All-Button verwirrt | UI-Pattern: wenn 0 Checkboxes selected → Button heißt "Approve All". Wenn ≥1 selected → "Approve Selected (N)" |

## 12. Anschluss

Nach 62.5:
- **62.6 (Debug-UI):** PlannerPage hat einen "View Pipeline Runs" Button auf Plan-Detail, der zu Step-Pause-UI führt. Step-Pause-Mechanik aus 62.0a wird für Marcel ergonomisch nutzbar
- **62.7 (Cron + Quarantäne):** Cron-Toggle in SettingsPlannerPage, Quarantäne-Items werden in Plan-View mit Badge angezeigt
- **62.8 (Batch-Execution):** Approved-Plans triggern automatisch Item-Execution. PlannerPage zeigt Live-Status der Runs

**Bewusst NICHT in 62.5:**
- Live-Status-Updates während Pipeline läuft (SSE/Poll — Komplexität nicht nötig für draft → approved)
- Multi-Project-View (alle Plans über alle Projekte) — Single-Project erstmal
- History-View (vergangene Wochen mit Performance-Metrics) — kommt mit Daten
- Plan-Templates oder Defaults — Goals + Algorithm liefern das

**Was 62.5 nebenbei mitlöst:**
- Marcel's API-Trigger-Problem von vorhin: über "Generate"-Button im UI kein Auth-Theater mehr nötig
- First Real Plan: nach 62.5 mergen + Generate klicken siehst du den ersten echten Wochenplan

## 14. Discovered During Implementation

- **`common.loading` and `common.notFound` i18n keys were missing.** The detail page needs both for its loading/not-found state-blocks. Added to `apps/web/src/i18n/de/common.ts` + `apps/web/src/i18n/en/common.ts`. Caught during /review-task by noticing `$t("common.notFound", "Not found")` — and uncovered a separate gotcha: vue-i18n v10 with `legacy: false` interprets the second `$t()` argument as named params, NOT a fallback message. The literal "Not found" string was being silently ignored. Added to [apps/web/CLAUDE.md](../apps/web/CLAUDE.md) Common Mistakes.

- **Web app does not import from `@marketing-auto/*` workspace packages.** `apps/web/tsconfig.json` has no path aliases for them, and Quasar/Vite doesn't resolve them at runtime. The ISO-week helpers from `packages/planner/src/iso-week.ts` had to be **copied** into `apps/web/src/lib/iso-week.ts` with a header comment noting the source. The duplication is small (~5 functions) and intentional. Documented in [apps/web/CLAUDE.md](../apps/web/CLAUDE.md) Common Mistakes.

- **Vue 3 reactivity doesn't track Set/Map mutations.** `this.selectedIds.add(id)` does NOT trigger re-render. The `onToggleSelect` handler in `PlannerPage.vue` builds a fresh `Set` (`new Set(this.selectedIds)`) and assigns it in one step. Documented in [apps/web/CLAUDE.md](../apps/web/CLAUDE.md).

- **Sidebar gained a 5th top-level section.** Originally 4 sections (Orchestration / Content / Discovery / Platform). Added "Planner" as its own section between Orchestration and Content (matches Marcel's Punkt 6 in the planning conversation). New `nav.plannerSection` i18n key.

- **TanStack Query optimistic cache patching pattern.** For snappy cancel/approve/reschedule actions, `usePlanItemActions` patches the cached `["planner", "plan-detail", slug, planId]` entry directly via `qc.setQueryData<T>(...)` instead of invalidating-and-refetching on success. Invalidation only fires in the `catch` branch (server error → resync). Documented in [apps/web/CLAUDE.md](../apps/web/CLAUDE.md) as a reusable pattern for future action-heavy UIs.

- **Spec filename naming convention.** The spec was initially staged as `specs/62-5-planner-calendar-ui.md` (hyphen). All other Theme 62 specs use `.` (`62.0a-…`, `62.4-…`). Renamed via `git mv` to `specs/62.5-planner-calendar-ui.md` during /review-task to keep the directory consistent.

- **`reschedulePlannedItem` returns a discriminated union, not a thrown error.** Used `{ ok: true, item } | { ok: false, reason: 'not_found' | 'wrong_item_status' | 'wrong_plan_status' | 'out_of_range' }` so the route handler can map each reason to its own HTTP status (404 vs 409 vs 422) without parsing exception messages. Same pattern as `transitionWeeklyPlanStatus` from 62.4.
