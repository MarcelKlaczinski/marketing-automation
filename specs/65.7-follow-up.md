### 3.2 Worker-Dispatch Pattern Evaluation (Marcel: Discovery evaluiert)

**Option α — 3-6 separate worker-branches (one per template):**

```typescript
if (templateKey === 'comparison-grid-3') {
  return await renderComparisonGrid3({ ...compositionInput, brandTokens, ...overrides });
}
if (templateKey === 'comparison-grid-5') {
  return await renderComparisonGrid5({ ...compositionInput, brandTokens, ...overrides });
}
if (templateKey === 'head-to-head-vs') {
  return await renderHeadToHeadVs({ ...compositionInput, brandTokens, ...overrides });
}
// ... etc
```

Pros:
- Explicit, easy to follow
- Each template's renderInput-shape can vary independently
- Mirrors existing comparison-grid-3 branch pattern

Cons:
- Verbose (3-6× repeated structure)
- Drift-risk: future template-add can forget worker-branch (D30 silent-break)

**Option β — Generic dispatch map:**

```typescript
const FAMILY_A_DISPATCH = {
  'comparison-grid-3': renderComparisonGrid3,
  'comparison-grid-4': renderComparisonGrid4,
  'comparison-grid-5': renderComparisonGrid5,
  'head-to-head-vs': renderHeadToHeadVs,
  'head-to-head-deep-dive': renderHeadToHeadDeepDive,
  'verdict-per-use-case': renderVerdictPerUseCase,
  'single-tool-spotlight': renderSingleToolSpotlight,
  'pro-con-verdict': renderProConVerdict,
} as const;

const renderFn = FAMILY_A_DISPATCH[templateKey];
if (renderFn) {
  return await renderFn({ ...compositionInput, brandTokens, ...overrides });
}
```

Pros:
- DRY, single point of dispatch
- Template-add only requires adding to map (compile-time TypeScript can catch missing key if map keyed-type matches `TemplateKey` enum)
- Drift-risk lower (single source of truth)

Cons:
- Assumes all Family-A templates have IDENTICAL renderInput-shape (single `compositionInput` object)
- If one template needs different input-handling, map breaks down

**Option γ — Hybrid: Set-based gate + switch dispatch:**

```typescript
const FAMILY_A_TEMPLATE_KEYS = new Set([
  'comparison-grid-3', 'comparison-grid-4', 'comparison-grid-5',
  'head-to-head-vs', 'head-to-head-deep-dive',
  'verdict-per-use-case', 'single-tool-spotlight', 'pro-con-verdict',
]);

if (FAMILY_A_TEMPLATE_KEYS.has(templateKey)) {
  // Use shared snapshot-reading + brandTokens-spread pattern
  const input = { ...compositionInput, brandTokens, ...overrides };
  
  switch (templateKey) {
    case 'comparison-grid-3': return await renderComparisonGrid3(input);
    case 'comparison-grid-5': return await renderComparisonGrid5(input);
    case 'head-to-head-vs': return await renderHeadToHeadVs(input);
    // ... etc
    default:
      assertNever(templateKey);
  }
}
```

Pros:
- Set-membership-check mirrors FAMILY_B_TEMPLATE_KEYS pattern (Memory D30 consistency)
- Switch makes dispatch explicit per-template
- TypeScript-exhaustive via `assertNever` catches missing-case at compile-time
- Each template can have slight input-variations if needed (within the switch case)

Cons:
- More code than Option β
- Set + switch is mildly redundant (membership check + switch)

### Discovery-Recommendation: **Option γ (Hybrid: Set-based gate + switch dispatch)**

Reasoning:

1. **Mirrors FAMILY_B_TEMPLATE_KEYS pattern** — Memory D30 just established this convention; Family-A should follow same pattern for consistency
2. **Exhaustive TypeScript-check catches future register-only adds** — `assertNever` in default branch prevents D30 silent-break recurrence
3. **Per-template input flexibility** — switch-case can handle template-specific input-massaging if needed (vs Option β rigid map)
4. **Clear separation Family-A vs Family-B** in worker (each family has own Set + switch block)
5. **Consistent with existing comparison-grid-3 branch** — easy to extend, not refactor

**Implementation sketch:**

```typescript
// apps/api/src/workers/social-render.worker.ts

const FAMILY_A_TEMPLATE_KEYS = new Set<TemplateKey>([
  'comparison-grid-3',
  'comparison-grid-5',
  'head-to-head-vs',
  'head-to-head-deep-dive',
  // + others from audit if confirmed registered
]);

const FAMILY_B_TEMPLATE_KEYS = new Set<TemplateKey>([
  'story-arc-clickbait',
  'lifestyle-listicle',
  'opinion-recommendation',
]);

// Dispatch logic:
if (FAMILY_A_TEMPLATE_KEYS.has(templateKey)) {
  const input = { ...compositionInput, brandTokens, ...overrides };
  
  switch (templateKey) {
    case 'comparison-grid-3': return await renderComparisonGrid3(input);
    case 'comparison-grid-5': return await renderComparisonGrid5(input);
    case 'head-to-head-vs': return await renderHeadToHeadVs(input);
    case 'head-to-head-deep-dive': return await renderHeadToHeadDeepDive(input);
    // ... add audit-confirmed templates
    default:
      const _exhaustive: never = templateKey;
      throw new Error(`Unhandled Family-A templateKey: ${templateKey}`);
  }
}

if (FAMILY_B_TEMPLATE_KEYS.has(templateKey)) {
  // ... existing Family-B branch
}

throw new Error(`Unknown templateKey: ${templateKey}`);
```

**Phase 0 audit result:** all 8 candidate pre-65.7 templates (comparison-grid-3/4, verdict-per-use-case, single-tool-spotlight, pro-con-verdict) were already wired. The only gap was the 3 Spec 65.7 multi-slide carousels (`comparison-grid-5`, `head-to-head-vs`, `head-to-head-deep-dive`) — exactly matching the 65.8 Day-5-followup §16 flag. Outcome B/C (renderFn-missing / ghost-reference) did NOT occur. Spec §3.3 pre-65.7 classification table was a no-op.

**Final dispatch shape (per Marcel-Decision, Option γ):**

`apps/api/src/workers/social-render.worker.ts` now exposes:

```typescript
const FAMILY_A_TEMPLATE_KEYS = [...] as const satisfies readonly TemplateKey[];
const FAMILY_B_TEMPLATE_KEYS = [...] as const satisfies readonly TemplateKey[];
type UnsupportedTemplateKey = "news-slide" | "concept-explainer-deck" | "price-comparison";

// Compile-time guard — TS2344 if any TemplateKey isn't in one of the 3 sets.
type _AssertNever<T extends never> = T;
const _exhaustivityCheck = null as unknown as _AssertNever<
  Exclude<TemplateKey, FamilyATemplateKey | FamilyBTemplateKey | UnsupportedTemplateKey>
>;
void _exhaustivityCheck;

export function isFamilyA(key: string): key is FamilyATemplateKey { ... }
export function isFamilyB(key: string): key is FamilyBTemplateKey { ... }

// Pure dispatcher — extracted for offline testability.
export async function dispatchByTemplateKey(
  templateKey: string,
  fullInput: Record<string, unknown>,
  renderServer: RenderServerLike,
): Promise<{ slides: Buffer[]; sequenceCount: number }> {
  if (isFamilyB(templateKey)) { switch (...) { ... assertNever default } }
  if (isFamilyA(templateKey)) { switch (...) { ... assertNever default } }
  throw new Error(`Unknown templateKey: ${templateKey}`);
}
```

`renderSlidesViaRemotion(data)` now does ONLY snapshot-read + family-specific `fullInput` build (Family-B nested under `compositionInput`, Family-A flat), then delegates to `dispatchByTemplateKey(...)`. ~150 lines of duplicated `if/else if + DB select` collapsed into ~40 lines.

**Test coverage** ([apps/api/test/workers/social-render-dispatch.test.ts](../apps/api/test/workers/social-render-dispatch.test.ts), 14/14 green, ~230ms offline):

1. **Registry-gap guard** (2 cases) — walks `templateRegistry.list()` after `bootstrapTemplates()`, asserts every registered key lives in FAMILY_A ∪ FAMILY_B + asserts the two sets are disjoint. **This locks down the gap-class the spec fixes.**
2. **Per-template dispatch** (11 cases via `it.each(allKeys)`) — for each registered templateKey, calls `dispatchByTemplateKey(key, probeInput, mockServer)` and asserts the matching `render*` mock was called exactly once + no other render fn was called.
3. **Unknown templateKey throw** (1 case) — `dispatchByTemplateKey("not-real", {}, server)` rejects with `/Unknown templateKey/`.

**Exhaustivity guard verified live** by temporarily commenting out `head-to-head-deep-dive` from `FAMILY_A_TEMPLATE_KEYS` → TS2344 ("Type 'head-to-head-deep-dive' does not satisfy the constraint 'never'.") + TS2678 at the switch case. Both surface immediately at `tsc`.

**Test budget:** ~0.2d (unit-only per Marcel-Decision). Integration tests with mocked render-fns deferred — registry-gap guard + per-template unit dispatch test give the same coverage at a fraction of the wiring cost.

**Spec deviations §13 (5 entries):**

1. **Pre-65.7 audit was a no-op.** Spec §3.3 Outcome A/B/C classification produced 0 entries — all 4 candidate templates were already wired. Scope shrunk to exactly the 3 Spec 65.7 templates the gap flag pointed at.
2. **Exhaustivity check uses `null as unknown as _AssertNever<...>` + `void`**, NOT the spec §3.2 sketch's `type _ExhaustivityCheck = _AssertNever<_UnhandledTemplateKey>` named alias. Reason: TS2344 catches the same constraint violation, but the named alias triggers TS6196 "declared but never used" under `noUnusedLocals`. The const+void form satisfies both rules with one declaration.
3. **`UnsupportedTemplateKey` explicit listing.** Spec §3.2 didn't anticipate that 3 keys (`news-slide`/`concept-explainer-deck`/`price-comparison`) sit in the `TemplateKey` union but aren't registered in `bootstrap.ts`. The exhaustivity guard would false-positive on them without an explicit "unsupported" bucket. Listed inline with `// never shipped` comments so future templates that ARE meant to ship don't accidentally land here.
4. **Pure `dispatchByTemplateKey` extracted** instead of inlining into `renderSlidesViaRemotion`. Snapshot-read + family-specific `fullInput` build stays in `renderSlidesViaRemotion` (needs DB); dispatch stays pure (testable offline). Splits the "loads from DB" concern from the "routes by key" concern.
5. **Test pattern uses DI seam (`RenderServerLike`) instead of `mock.module`.** Avoids the process-global `mock.module` leak (Memory: bun's `mock.module` is process-wide, leaks across files). Tests pass a custom `RenderServerLike` object with `mock(...)` per-fn stubs.
