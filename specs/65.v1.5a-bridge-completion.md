## 3. Architecture Decisions

### 3.1 Bridge #1 — Engine reads brand-assets from DB (Marcel-Decision: DB + chain fallback)

**Implementation:**

```typescript
// packages/social/src/resolve-tool-brand-asset.ts (extend existing)

interface BrandAssetResolution {
  logoUrl: string;             // R2 URL or inline SVG
  primaryColor?: string;
  secondaryColor?: string;
  tertiaryColor?: string;
  brandNameCanonical?: string;
  source: 'db' | 'chain';
}

// In-memory cache with TTL
interface CacheEntry {
  asset: BrandAssetResolution;
  cachedAt: number;
}

const cache = new Map<string, CacheEntry>();
const CACHE_TTL_MS = 60_000; // 60s per Marcel-Decision

export async function resolveToolBrandAsset(
  toolId: string,
  slug: string,
): Promise<BrandAssetResolution> {
  // 1. Check cache
  const cached = cache.get(toolId);
  if (cached && Date.now() - cached.cachedAt < CACHE_TTL_MS) {
    return cached.asset;
  }
  
  // 2. Read from DB
  const dbRow = await getBrandAssetsForTool(toolId);
  
  if (dbRow && dbRow.logoUrl) {
    const asset: BrandAssetResolution = {
      logoUrl: dbRow.logoUrl,
      primaryColor: dbRow.primaryColor ?? undefined,
      secondaryColor: dbRow.secondaryColor ?? undefined,
      tertiaryColor: dbRow.tertiaryColor ?? undefined,
      brandNameCanonical: dbRow.brandNameCanonical ?? undefined,
      source: 'db',
    };
    cache.set(toolId, { asset, cachedAt: Date.now() });
    return asset;
  }
  
  // 3. Fallback to chain (graceful)
  const chainResolved = await resolveToolIconViaChain(slug); // existing fn
  const asset: BrandAssetResolution = {
    logoUrl: chainResolved, // either URL or inline SVG
    source: 'chain',
  };
  cache.set(toolId, { asset, cachedAt: Date.now() });
  return asset;
}

// Existing `resolveToolIcon` wraps this:
export async function resolveToolIcon(projectId: string, slug: string): Promise<string> {
  const toolId = await getToolIdBySlug(projectId, slug);
  if (!toolId) return await resolveToolIconViaChain(slug);
  
  const asset = await resolveToolBrandAsset(toolId, slug);
  return asset.logoUrl;
}
```

**Cache-TTL pattern (Marcel-Decision: 60s):**

- Marcel-edit via Settings-UI Brand-Assets page → DB-row updated
- Next render fetches from cache (might be stale up to 60s)
- After 60s, next cache-miss re-reads DB → updated values

**Acceptable staleness:** Marcel-edits happen <1×/day typically. 60s window invisible.

**Cache-key strategy:**

- Keyed by `toolId` (UUID, project-scoped uniqueness implicit via FK)
- Cache lives per-API-process (not shared across workers) — fine because render-workers re-fetch independently
- Map.size bounded by total-tools-in-system (~100s, no eviction needed V1)

**No Redis pub/sub** per Marcel-Decision — simpler.

**Edge cases:**

- DB-row exists but `logoUrl IS NULL` → falls through to chain (treat like missing row)
- DB-row has `needs_review=true` and partial data → uses what's there + chain fills logo if missing
- Cache survives DB-row deletion until TTL expires — acceptable

### 3.2 Bridge #2 — Cross-locale Brand-Assets Backfill (Marcel-Decision: backfill 108)

**Strategy:**

Migrate existing 54-row state to 108 rows. For each Toolwiki tool that has DE-row but no EN-row, INSERT EN-row sharing same logo + colors.

**Migration approach:**

```sql
-- packages/db/drizzle/0124_brand_assets_en_locale_backfill.sql

-- For every Toolwiki DE-locale tool article that has brand_assets,
-- create a parallel EN-locale row if the EN-sibling exists in articles.

INSERT INTO tool_brand_assets (
  tool_id, logo_url, logo_wordmark_url, primary_color, secondary_color, tertiary_color,
  brand_name_canonical, source, needs_review, fetched_at
)
SELECT
  en_article.id AS tool_id,
  ba.logo_url, ba.logo_wordmark_url, ba.primary_color, ba.secondary_color, ba.tertiary_color,
  ba.brand_name_canonical, ba.source, ba.needs_review, ba.fetched_at
FROM tool_brand_assets ba
JOIN articles de_article ON de_article.id = ba.tool_id
JOIN articles en_article ON en_article.translation_key = de_article.translation_key
WHERE de_article.locale = 'de'
  AND en_article.locale = 'en'
  AND en_article.collection = 'tools'
  AND NOT EXISTS (
    SELECT 1 FROM tool_brand_assets ba2 WHERE ba2.tool_id = en_article.id
  );
```

**Verify-Critical Assumption:**

- `articles.translation_key` exists and links DE+EN sibling articles
- Per Memory D8 + bilingual schema from 59.2 — should exist

**Migration safety:**

- Idempotent via `NOT EXISTS` clause
- Re-runnable
- Doesn't modify existing DE-rows
- Adds maximum 54 new rows (one EN per existing DE)

**Post-migration verification:**

```sql
-- Expected: 108 total rows (54 DE + 54 EN)
SELECT 
  a.locale,
  COUNT(*) AS row_count
FROM tool_brand_assets ba
JOIN articles a ON a.id = ba.tool_id
GROUP BY a.locale;
```

### 3.3 Bridge #3 — Multi-locale Fan-out Schema (Marcel: Discovery evaluiert)

**Option α — `targetLocales: string[]` field on definition:**

```typescript
recurring_content_definitions {
  // ... existing fields
  targetLocales: string[];  // ['de', 'en']
}

// In brief-generator dispatch:
async function generateBriefsForDefinition(definition) {
  const briefs = [];
  for (const locale of definition.targetLocales) {
    const brief = await generateLocaleScopedBrief(definition, locale);
    briefs.push(brief);
  }
  return briefs;
}
```

Pros:
- Marcel creates 1 definition for both locales, no duplication
- Hook-pick uses per-locale hooks (65.4 `language` param)
- Tool-selection same across locales (Claude is Claude in DE+EN)

Cons:
- 2× LLM-cost per fire (separate cover-headlines, verdicts per locale)
- Sibling-relationship between DE+EN briefs NOT preserved

**Option β — Separate definitions per locale:**

Marcel creates 2 definitions: one with `language='de'`, one with `language='en'`. Same format-config otherwise.

Pros:
- Simplest implementation (no fan-out logic)
- Independent schedules possible (DE Mondays, EN Wednesdays)

Cons:
- Marcel-effort: 2× clicks per recurring topic
- Drift-risk: Marcel updates DE-definition but forgets EN
- No semantic-relationship between sibling-briefs

**Option γ — `targetLocales` + sibling-linking via shared `runGroupId`:**

```typescript
// Each fire generates N briefs linked by shared runGroupId UUID
brief.recurring_metadata = {
  // ... existing
  targetLocale: 'en',
  runGroupId: '<shared-uuid>',  // links DE+EN siblings from same fire
}
```

Pros:
- Same as α plus sibling-relationship preserved
- Enables future cross-locale features (e.g. coordinated posting times)
- Article output can link `articles.translationKey` automatically post-render

Cons:
- More fields in recurring_metadata
- Migration to add runGroupId tracking

### Discovery-Recommendation: **Option γ (targetLocales + runGroupId)**

Reasoning:

1. **Marcel-Decision was "alle 4 bridges nötig" + cross-locale-aware** — γ captures relationship-data without much extra cost
2. **runGroupId is cheap addition** — single UUID field in recurring_metadata, no migration needed (jsonb is flexible)
3. **Article-translation linking is automatic** — when article-output creates article-rows for both, can set `articles.translationKey = runGroupId` for sibling-linking
4. **V2-friendly** — distribution-layer can read runGroupId to coordinate posting times across locales
5. **Marcel-UX clean** — 1 definition, multi-locale toggle in Settings-UI

**Schema-Update:**

```typescript
// packages/db/src/schema/recurring-content-definitions.ts (extend)
targetLocales: jsonb('target_locales').notNull().default(['de']),
  // Array of locale codes, e.g. ['de'], ['de', 'en']
```

Migration 0125 just sets default for existing rows.

### 3.4 Bridge #4 — Planner-Executor Wiring (Marcel: Discovery evaluiert)

**Per 65.10 §16.6:** Pipeline-router in `packages/planner/src/execution/pipeline-router.ts` `case 'recurring_content'` enqueues `article:social-image` with `briefId`, but pipeline needs `articleId`.

**Option α — Pipeline-router preprocesses (creates article BEFORE enqueue):**

```typescript
// packages/planner/src/execution/pipeline-router.ts
case 'recurring_content': {
  // 1. Resolve brief
  const brief = await getTopicBriefById(briefId);
  if (!brief) return { error: 'brief-not-found' };
  
  // 2. Create article-stub (idempotent)
  const article = await createRecurringContentArticle({ brief });
  
  // 3. Enqueue article:social-image with articleId
  return await enqueuePipeline({
    pipelineName: 'article:social-image',
    input: { articleId: article.id },
  });
}
```

Pros:
- Single-step in router, mirrors immediate-dispatch path
- Reuses existing `createRecurringContentArticle` helper (idempotent per 65.10)

Cons:
- Router gets broader concern (article-creation, not just routing)
- Article-creation side-effect happens at router-layer, not pipeline-layer

**Option β — Planner-executor calls helper as preprocessing step:**

```typescript
// packages/planner/src/execution/executor.ts (extend)
async function executePlannedBrief(plannedItem) {
  if (plannedItem.brief.source === 'recurring') {
    // Mirror immediate-dispatch: create article first
    const article = await createRecurringContentArticle({ brief: plannedItem.brief });
    return await dispatchToPipeline({
      pipelineName: 'article:social-image',
      input: { articleId: article.id },
    });
  }
  // ... existing non-recurring path
}
```

Pros:
- Executor-level decision, router stays generic
- Cleaner separation of concerns
- Easy to add more brief-types with similar pattern (Family B same path)

Cons:
- Touches executor code that other content-types share

**Option γ — Wrapper-job that does (create-article → enqueue social-render):**

```typescript
// New BullMQ job-type 'recurring-content-wrapper'
const worker = new Worker('recurring-content-wrapper', async (job) => {
  const { briefId } = job.data;
  const brief = await getTopicBriefById(briefId);
  const article = await createRecurringContentArticle({ brief });
  await enqueuePipeline({
    pipelineName: 'article:social-image',
    input: { articleId: article.id },
  });
});

// Pipeline-router enqueues to wrapper-job
case 'recurring_content':
  await enqueueWrapperJob({ briefId });
```

Pros:
- Most isolated — wrapper-job is self-contained
- Async/independent retries
- Easy observability (own queue metrics)

Cons:
- New worker to maintain
- 2-job-hop adds latency (~5s)

### Discovery-Recommendation: **Option β (Planner-executor preprocessing)**

Reasoning:

1. **Mirror immediate-dispatch path** — `approveBrief` recurring-branch in 65.10 already does this exact sequence; planner-executor just needs same logic
2. **createRecurringContentArticle is idempotent** — calling it from 2 different code-paths (immediate + planner) is safe
3. **No new worker** — minimal infrastructure addition
4. **Pattern-consistency** — executor handles brief-type-specific preprocessing, router stays pure routing
5. **Future-friendly für Family B** — when 65.8 Family B briefs land in planner, same path

**Implementation:**

```typescript
// packages/planner/src/execution/executor.ts (extend existing)
async function executePlannedBrief(plannedItem: PlannedItem): Promise<ExecutionResult> {
  const brief = await getTopicBriefById(plannedItem.briefId);
  
  // Recurring-content pre-processing
  if (brief.source === 'recurring') {
    const article = await createRecurringContentArticle({ brief });
    return await enqueuePipelineDispatch({
      pipelineName: 'article:social-image',
      input: { articleId: article.id, briefId: brief.id },
    });
  }
  
  // ... existing non-recurring paths (cluster, comparison, etc.)
}
```

**Edge case — re-entry:**

If planner re-tries (cron picks up brief that errored), `createRecurringContentArticle` is idempotent via slug-uniqueness probe (per 65.10 implementor). No duplicate-article problem.

## 8. Risk Analysis

| Risk | Severity | Mitigation |
|---|---|---|
| Cache stale longer than 60s due to clock-drift | Low | TTL uses `Date.now()` monotonic source |
| EN-backfill duplicates existing manually-curated EN-rows | Medium | `NOT EXISTS` clause prevents duplication |
| `articles.translation_key` doesn't exist or is named differently | High | Verify-point §2.2 #5 — fail-loud migration if column missing |
| Multi-locale fan-out doubles LLM-costs (EN-content) | Low | Marcel-cap on monthly budget; locale-aware skip in cost-cap-check |
| Planner-executor + immediate-dispatch race on same brief | Medium | `createRecurringContentArticle` idempotent per slug-uniqueness; Redis-lock could be added if needed |
| Migration 0124 query timeout on large article-count | Low | Toolwiki has 54 tools = 54 max INSERTs; vernachlässigbar |
| Cache-TTL invalidates mid-render (logo URL changes during multi-slide render) | Medium | Render uses single cache-fetch at composition start; subsequent slides use same value |
| Settings-UI wizard needs new targetLocales field | Medium | Implementor adds checkbox-group; defaults to current locale |
