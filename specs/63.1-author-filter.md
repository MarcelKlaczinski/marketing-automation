# Mini-Task — Author-Profiles aus Social-Post-Source ausschließen

**Geschätzter Aufwand: 30 Min. Kein Spec nötig.**

## Symptom

Im aktuell generierten Plan KW 21/2026 erscheinen Author-Profile als Social-Post-Items (z.B. "Anna Weidner"). Das ist Stamm-Daten — keine generierbaren Content-Hooks. Author-Profile sollten **nicht** in der social-post pool/refresh selection landen.

**Wichtig:** Tools, KI-Wissen, etc. bleiben drin. Nur `authors`-Collection raus.

## Aufgabe

### Phase 0 — Discovery

```bash
# Welche Article-Collections gibt es?
grep -rn "collectionType\|collection_type" packages/db/src/schema/ | head -20

# Wo wird in SelectSocialPostItemsStep gefiltert?
grep -A 30 "loadRefresh\|loadPool\|pickRefresh\|pickPool\|selectSocialPost" \
  packages/pipelines/src/planning/steps/select-social-post-items.ts

# Welche Collections existieren in articles Tabelle?
# (Kann auch via SQL: SELECT DISTINCT collection_type FROM articles)
```

**Ergebnisse dokumentieren:**
- Liste aller Article-Collections
- Aktueller Filter-Code in der Social-Post-Selection
- Gibt es weitere "Stamm-Daten-artige" Collections die auch raus müssen? (tags, categories, glossary?)

### Phase 1 — Filter

In SelectSocialPostItemsStep (oder dem Helper der den Article-Pool aufbaut):
- WHERE-Clause erweitern um `collection_type != 'authors'`
- Falls Phase 0 weitere Stamm-Daten-Collections zeigt: auch ausschließen

**Wichtig:** Tools-Collection bleibt drin. Tools sind valide Social-Post-Source (single-tool-spotlight Template).

### Phase 2 — Test

Bestehender SelectSocialPostItemsStep-Test sollte einen Test-Case haben dass Author-Article NICHT als Social-Source genutzt wird:

```ts
// In select-social-post-items.test.ts
test('excludes authors collection from social-post pool', async () => {
  // Setup: pool article with collectionType='authors'
  // Run select
  // Assert: not in result
});
```

### Phase 3 — Verify

Nach Merge: Plan KW 21 oder neuer neu triggern. Im Kalender sollten keine Author-Cards mehr auftauchen.

## Commit-Message

```
fix(planner): exclude authors collection from social-post selection

Author profiles are reference data, not generatable content hooks.
Tools, ki-wissen and other collections remain eligible as social-post 
sources for content variety.
```

## Anti-Patterns

- Andere Collections "while we're at it" ausschließen ohne Discovery
- Tools mit ausschließen — Marcel will Tool-Variety explizit drin behalten
- Filter zentral in irgendeine Util refactoren — bleibt bei dem einen Select-Step

## Hintergrund

Aus 62.8-Implementation-Pipeline läuft parallel. Dieser Mini-Task berührt nur `select-social-post-items.ts` + Test — kein Konflikt zu 62.8-Branch.

Spec-Referenzen:
- Memory: Headlines-Implementation hat select-social-post-items.ts kürzlich angefasst (cluster-parent + refresh + pool sub-cases)

## Resolution (2026-05-21)

**Filter sitzt nicht im Step, sondern in den DB-Readern.** `SelectSocialPostItemsStep` baut den Pool nicht selbst — er bekommt Kandidaten via `SelectSocialPostDeps` injiziert (`pickFromRefreshSuggestions`, `pickFromSuggestionPool`). Echte Query lebt in `packages/planner/src/social-source-selectors.ts`. Dort drei WHERE-Klauseln erweitert.

**Discovery — DB-Realität:**
- Spec sprach von `collection_type`, gemeint war `articles.collection` (text, NOT NULL, default `'blog'`). Der Enum `article_collection_type` existiert, hat aber nur `blog|comparison|ki-wissen|tools|usecases` — kein `authors`. Das `authors`-Profil ist eine reine `collection`-Text-Sache.
- Tatsächliche `collection`-Werte im DB: `tools` (108), `blog` (94), `ki-wissen` (24), `usecases` (24), `comparisons` (22), `tool-categories` (14), `authors` (10), `special-landings` (10).
- Anti-Pattern "while we're at it" eingehalten: nur `authors` raus. `tool-categories` und `special-landings` bleiben drin bis ein konkretes Symptom auftaucht.

**Geänderte Files:**
- [`packages/planner/src/social-source-selectors.ts`](../packages/planner/src/social-source-selectors.ts) — `ne(articles.collection, "authors")` in `pickFromRefreshSuggestions`, `pickFromSuggestionPool`, `countSuggestionPool`.
- [`packages/planner/test/social-source-selectors.test.ts`](../packages/planner/test/social-source-selectors.test.ts) — 3 Regression-Tests, `afterEach` cleart `refresh_suggestions` mit (Author-Fixtures hängen FKs dran).

**Test-Standort weicht von Spec ab:** Spec schlug `select-social-post-items.test.ts` vor — der Test lebt aber als DB-roundtrip in `packages/planner/test/social-source-selectors.test.ts`, dort wo die echte Query lebt. Der pipelines-Step-Test arbeitet ausschließlich mit injizierten Fixtures und hätte den Filter nicht erfasst.

**Verify:** KW 21/2026 Plan re-trigger durch Marcel — "kein autor mehr sichtbar".
