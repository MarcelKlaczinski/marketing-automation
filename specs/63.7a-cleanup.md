# Mini-Task 63.7a — DB-Cleanup: alle plan_pending Briefs zurück auf pending + KW21 Plan canceln

**Modus: DB-Cleanup. Kein Code. ~10 Min.**

**Voraussetzung: 63.7b Spec gemerged ODER bewusst zwischen 63.7a und 63.7b warten (Marcel entscheidet Reihenfolge).**

## Kontext

Diagnose 2026-05-21 hat gezeigt: Plan-Router routet alle `content_type='cluster'` Items via `cluster:full-plan` Pipeline, ignoriert `cluster_action`. append_to_existing Briefs würden zu Phantom-Cluster führen statt Spokes für existing Cluster zu sein.

Marcel will sauberen Reset: alle plan_pending Briefs zurück in den Pool, KW21-Draft canceln, Plan-Workflow erst nach 63.7b Code-Fix wieder triggern.

## Aufgabe

### Schritt 1 — Discovery der betroffenen Briefs

```sql
-- Alle plan_pending Briefs in Toolwiki
SELECT 
  id,
  topic_title,
  source,
  cluster_action,
  parent_cluster_id,
  intent_type,
  approval_status,
  approved_at,
  routed_via_plan_item_id
FROM topic_briefs
WHERE approval_status = 'plan_pending'
  AND project_id = (SELECT id FROM projects WHERE slug = 'toolwiki')
ORDER BY approved_at DESC;
```

**Erwartung:** mindestens 11 Briefs (4 comparison_discovery + 7 gap_analysis missing_hub).

**Verifikation:** Marcel zeigt SQL-Output vor weiteren Steps. Falls Anzahl überraschend (mehr oder weniger), pausieren und fragen.

### Schritt 2 — KW21 Plan + planned_items identifizieren

```sql
-- Aktueller KW21 Draft-Plan
SELECT 
  id,
  iso_week,
  status,
  cost_estimate_eur,
  created_at
FROM weekly_plans
WHERE project_id = (SELECT id FROM projects WHERE slug = 'toolwiki')
  AND status = 'draft'
ORDER BY created_at DESC LIMIT 5;
```

```sql
-- Welche planned_items hängen am Draft-Plan?
SELECT 
  content_type,
  source_kind,
  COUNT(*) as count,
  SUM(estimated_cost_eur) as total_cost
FROM planned_items
WHERE weekly_plan_id = (
  SELECT id FROM weekly_plans 
  WHERE project_id = (SELECT id FROM projects WHERE slug = 'toolwiki')
    AND status = 'draft'
  ORDER BY created_at DESC LIMIT 1
)
GROUP BY content_type, source_kind
ORDER BY count DESC;
```

### Schritt 3 — Cleanup in Transaction

**WICHTIG: alles in einer Transaction. Bei Fehler ROLLBACK.**

```sql
BEGIN;

-- 3a) Alle plan_pending Briefs zurück auf pending
UPDATE topic_briefs
SET 
  approval_status = 'pending',
  approved_at = NULL,
  routed_via_plan_item_id = NULL
WHERE approval_status = 'plan_pending'
  AND project_id = (SELECT id FROM projects WHERE slug = 'toolwiki');

-- Erwartete Row-Count: 11+ (aus Schritt 1)
-- Falls != erwartet: ROLLBACK; und Marcel fragen!

-- 3b) KW21 Draft-Plan canceln (status zu 'cancelled' oder ähnliches Terminal-State)
UPDATE weekly_plans
SET status = 'cancelled'  -- oder 'discarded', je nach Schema-Convention
WHERE project_id = (SELECT id FROM projects WHERE slug = 'toolwiki')
  AND status = 'draft';

-- Erwartete Row-Count: 1
-- Falls = 0: kein Draft mehr (vielleicht schon gecancelt) → OK
-- Falls > 1: ROLLBACK; mehrere Drafts ist Inkonsistenz, Marcel fragen

-- 3c) planned_items vom gecancelten Plan
-- Annahme: cascade delete oder müssen wir manuell?
-- Phase 0 verifiziert: hat weekly_plans ON DELETE CASCADE für planned_items?
-- Wenn ja: nichts tun, sie verschwinden mit dem Plan
-- Wenn nein: explizit löschen

-- Optional: planned_items markieren statt löschen
UPDATE planned_items
SET execution_status = 'cancelled'  -- behalten als Audit-Trail
WHERE weekly_plan_id = (
  SELECT id FROM weekly_plans 
  WHERE project_id = (SELECT id FROM projects WHERE slug = 'toolwiki')
    AND status = 'cancelled'
  ORDER BY updated_at DESC LIMIT 1
)
  AND execution_status IN ('planned', 'enqueued');

-- Wenn alle Verifications OK:
COMMIT;
```

**Alternative wenn weekly_plans-Status-Enum 'cancelled' nicht erlaubt:**
- Phase 0 prüfen: welche terminal-States gibt es?
- Vermutete Optionen: 'cancelled', 'discarded', 'abandoned'
- Falls keine: vielleicht delete + cascade?
