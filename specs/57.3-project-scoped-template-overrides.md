# Spec 57.3 — Project-Scoped Template Overrides

**Theme:** 57 (Social Media + Remotion Refinement)
**Status:** Implemented (Phase 1 complete — all 6 sessions)
**Estimated effort:** 5-6 days (Phase 1 — HIGH/MEDIUM priority only)
**Prerequisite discovery:** `specs/_drafts/57-3-template-override-surface.md`

---

## Goal

Enable project-level overrides for the 4 production social templates across three dimensions: copy strings (brand voice + section labels), layout knobs (boolean toggles for optional slide elements), and eligibility parameters (numeric bounds). Project admins can customize how each template renders for their project without forking template code. Existing toolwiki output remains visually identical via template default values.

## Non-Goals

- Custom template designs per project (out of scope — would require composition-level forking)
- Per-article overrides (deferred — 2-tier merge: template-default → project-override; per-article layer can be added later if needed)
- Override of LLM-generated copy (hook phrases, captions — those are content, not template structure)
- LOW-priority cosmetic section labels (deferred to Phase 2 — see Deferred section)
- Override of brand-token-aware properties (those go via `brand_tokens.*`, not template overrides)
- UI for cron-status-style real-time override-effect preview (settings save → next render uses new values)

---

## Three-Part Scope

**Part A: Template Default Surface Declaration** — Each template declares its override-able surface as a Zod schema with defaults
**Part B: Persistence Layer** — `project_template_overrides` table with audit trail + override-merge in pipeline
**Part C: Admin UI** — Settings page subsection for editing overrides per template

Plus two **opportunistic fixes** uncovered during discovery (both within scope because the relevant code is touched anyway):
- **Fix X**: 8 DE-only hardcoded strings in `EndSlideStunning` + `ToolSlideStunning` (rendered as German even on EN renders)
- **Fix Y**: `single-tool-spotlight` consolidates `websiteUrl`/`instagramHandle` to use `brandTokens.social` (matching list-carousel pattern, currently flat props)

### A.3 Discriminated Union for Type Safety

```typescript
// packages/social/src/registry/overrides.ts
export type TemplateOverrides =
  | { templateKey: "comparison-stunning"; values: ComparisonStunningOverrides }
  | { templateKey: "comparison-stunning-3"; values: ComparisonStunningOverrides }  // shares schema
  | { templateKey: "single-tool-spotlight"; values: SingleToolSpotlightOverrides }
  | { templateKey: "use-case-verdict-per-tool"; values: UseCaseVerdictOverrides };

export function getOverrideSchema(templateKey: TemplateKey): z.ZodObject<any> {
  switch (templateKey) {
    case "comparison-stunning":
    case "comparison-stunning-3":
      return comparisonStunningOverridesSchema;
    case "single-tool-spotlight":
      return singleToolSpotlightOverridesSchema;
    case "use-case-verdict-per-tool":
      return useCaseVerdictOverridesSchema;
    default:
      throw new Error(`Unknown template key: ${templateKey}`);
  }
}
```

### A.4 Merge Function

```typescript
// packages/social/src/registry/mergeOverrides.ts
export function mergeOverrides<T extends z.ZodObject<any>>(
  schema: T,
  storedValues: Record<string, any> | undefined
): z.infer<T> {
  // Stored values are validated + filled with defaults via schema.parse()
  // Unknown keys stripped via .strip() (schema evolution safety)
  return schema.parse(storedValues ?? {});
}
```

Usage in pipeline:
```typescript
const schema = getOverrideSchema(input.templateKey);
const overrideRow = await fetchOverrides(input.projectId, input.templateKey);
const resolved = mergeOverrides(schema, overrideRow?.values);
```

### B.2 Repository Functions

```typescript
// packages/api/src/repos/template-overrides.repo.ts

export async function fetchOverrides(projectId: string, templateKey: TemplateKey) {
  const [row] = await db
    .select()
    .from(projectTemplateOverrides)
    .where(and(
      eq(projectTemplateOverrides.projectId, projectId),
      eq(projectTemplateOverrides.templateKey, templateKey)
    ))
    .limit(1);
  return row ?? null;
}

export async function upsertOverrides(
  projectId: string,
  templateKey: TemplateKey,
  values: Record<string, any>
) {
  // Validate via schema before persist
  const schema = getOverrideSchema(templateKey);
  const validated = schema.parse(values);  // strips unknowns

  await db
    .insert(projectTemplateOverrides)
    .values({ projectId, templateKey, values: validated })
    .onConflictDoUpdate({
      target: [projectTemplateOverrides.projectId, projectTemplateOverrides.templateKey],
      set: { values: validated, updatedAt: new Date() },
    });
}

/**
 * Approximated last-used-at update.
 * Only writes when existing lastUsedAt is older than 1 hour or null.
 * Prevents write contention from parallel pipeline runs.
 */
export async function markUsed(projectId: string, templateKey: TemplateKey) {
  const oneHourAgo = new Date(Date.now() - 60 * 60 * 1000);
  await db
    .update(projectTemplateOverrides)
    .set({ lastUsedAt: new Date() })
    .where(and(
      eq(projectTemplateOverrides.projectId, projectId),
      eq(projectTemplateOverrides.templateKey, templateKey),
      or(
        isNull(projectTemplateOverrides.lastUsedAt),
        lt(projectTemplateOverrides.lastUsedAt, oneHourAgo)
      )
    ));
  // No-op if last_used_at is fresh (within 1h) — saves write
  // No-op if no row exists yet — that's fine, override row only exists if user customized
}
```

### B.5 Eligibility Override

The template registry's `eligibility()` predicate must also consume project overrides:

```typescript
// packages/social/src/registry.ts
export function getTemplateEligibility(
  templateKey: TemplateKey,
  article: Article,
  discovery: DiscoveryContext,
  projectOverrides: Record<string, any> | null
): boolean {
  const schema = getOverrideSchema(templateKey);
  const resolved = mergeOverrides(schema, projectOverrides);
  const baseEligibility = templateRegistry[templateKey].eligibility(article, discovery);
  if (!baseEligibility) return false;

  // Apply override-specific gates:
  if (templateKey === "single-tool-spotlight") {
    const tool = discovery.tools[0];
    const prosCount = tool?.pros?.length ?? 0;
    if (prosCount < resolved.eligibility.minProsCount) return false;
    if (prosCount > resolved.eligibility.maxProsCount) return false;
  }
  if (templateKey === "use-case-verdict-per-tool") {
    const verdictsCount = discovery.useCaseVerdicts?.length ?? 0;
    if (verdictsCount < resolved.eligibility.minVerdictsCount) return false;
  }
  return true;
}
```

**Caller change**: existing callers of `eligibility()` (in `findEligibleTemplates()` etc.) must pass project overrides. Add a wrapper that fetches overrides for the project once, then applies to all template eligibility checks.

```typescript
// GET /api/projects/:slug/template-overrides
// Returns all override rows for the project, joined with template metadata
router.get("/projects/:slug/template-overrides", async (req, res) => {
  const project = await getProjectBySlug(req.params.slug);
  const rows = await db
    .select()
    .from(projectTemplateOverrides)
    .where(eq(projectTemplateOverrides.projectId, project.id));

  // For each known template key, return either the row or null + defaults
  const result = ALL_TEMPLATE_KEYS.map(key => {
    const row = rows.find(r => r.templateKey === key);
    const schema = getOverrideSchema(key);
    const defaults = schema.parse({});  // all defaults
    return {
      templateKey: key,
      hasCustomOverrides: row !== undefined,
      values: row?.values ?? defaults,
      lastUsedAt: row?.lastUsedAt ?? null,
      updatedAt: row?.updatedAt ?? null,
    };
  });
  return res.json(result);
});

// PUT /api/projects/:slug/template-overrides/:templateKey
// Upserts override row. Body must validate against template's override schema.
router.put("/projects/:slug/template-overrides/:templateKey", async (req, res) => {
  const project = await getProjectBySlug(req.params.slug);
  const templateKey = req.params.templateKey as TemplateKey;
  if (!ALL_TEMPLATE_KEYS.includes(templateKey)) {
    return res.status(404).json({ error: "Unknown template key" });
  }
  const schema = getOverrideSchema(templateKey);
  const parsed = schema.safeParse(req.body.values);
  if (!parsed.success) {
    return res.status(400).json({ error: "Validation failed", details: parsed.error.flatten() });
  }
  await upsertOverrides(project.id, templateKey, parsed.data);
  return res.json({ ok: true });
});

// DELETE /api/projects/:slug/template-overrides/:templateKey
// Removes override row → template falls through to defaults
router.delete("/projects/:slug/template-overrides/:templateKey", async (req, res) => {
  const project = await getProjectBySlug(req.params.slug);
  const templateKey = req.params.templateKey as TemplateKey;
  await db
    .delete(projectTemplateOverrides)
    .where(and(
      eq(projectTemplateOverrides.projectId, project.id),
      eq(projectTemplateOverrides.templateKey, templateKey)
    ));
  return res.json({ ok: true });
});
```

## Opportunistic Fixes

### Fix X: DE-Only Hardcoded Strings

`ToolSlideStunning.tsx` and `EndSlideStunning.tsx` contain hardcoded German strings rendered regardless of locale (`"Perfekt für"`, `"Tools im Detail"`, `"für "`). Discovery confirmed: on EN renders, these display in German.

**Fix**: Replace hardcoded strings with locale-aware reads from `overrides.copy.*` (which has both DE + EN defaults). Strings:
- `"Perfekt für"` → `overrides.copy.endSlide.perfektFürLabel[locale.startsWith("de") ? "de" : "en"]`
- `"Tools im Detail"` → `overrides.copy.endSlide.toolsRecapLabel`

This is in scope **because** the override surface introduces both DE + EN variants for these keys; the bug fix comes for free with the override implementation.

### Fix Y: `single-tool-spotlight` Brand-Token Consolidation

`single-tool-spotlight` template passes `websiteUrl` and `instagramHandle` as flat props to its compositions, while `list-carousel` (post-57.1) reads them from `brandTokens.social`. Discovery flagged this as inconsistent.

**Fix**: Update `single-tool-spotlight` compositions to read from `brandTokens.social.websiteUrl` and `brandTokens.social.instagramHandle`. Remove the flat props from the template's input schema. The single-tool-spotlight tests must be updated to pass `brandTokens.social` instead of flat props.

**Touch surface**: `CoverSlide.tsx`, `EndSlide.tsx` (single-tool-spotlight), plus the pipeline's `RenderSlidesStep` where it constructs the composition input.

## Risks & Mitigations

**Risk 1: Visual regression for toolwiki**
- *Mitigation*: All schema defaults exactly match current hardcoded values. Render same article pre/post 57.3 and visually diff. Any difference = bug in default values.

**Risk 2: Locale handling — projects with `fr-FR` or other locales**
- *Mitigation*: Phase 1 only supports DE + EN. UI shows warning. Non-DE/EN locales fall back to DE default in templates (matching current behavior).

**Risk 3: `last_used_at` write contention from parallel renders**
- *Mitigation*: Approximated update (only writes if older than 1h). Pattern proven in `cron_state` from Spec 56.6.

**Risk 4: Schema evolution breaks existing override rows**
- *Mitigation*: `.strip()` on all schemas + defaults on every leaf. Adding a new field is non-breaking — old rows just get the default. Removing a field is non-breaking — old data is stripped on read.

**Risk 5: `comparison-stunning-3` shares schema with `comparison-stunning` — confusing UI**
- *Mitigation*: Template picker shows them as separate entries. Each can have independent overrides. Shared schema is implementation detail. If user wants identical overrides for both, they must save twice (acceptable for v1).

**Risk 6: 23 override keys plus 7 layout knobs plus 4 eligibility params is a complex UI**
- *Mitigation*: Phase 1 ships everything (HIGH + MEDIUM + LOW per discovery), but Override Editor uses tabbed sub-sections to reduce visual noise. If feedback is "too much UI", Phase 2 can collapse to most-common-overrides view.

**Risk 7: Override merge bug silently produces wrong output**
- *Mitigation*: Strong typing via discriminated union + `mergeOverrides` round-trip tests + visual smoke test as final gate.

## Deviations from Spec

### Override schema file locations
**Spec said:** one file per template at `src/templates/<template-key>/overrides.ts` alongside the template definition.  
**Reality:** centralized directory `src/templates/overrides/<name>.overrides.ts` with a barrel `index.ts`. Reason: the overrides subpath export (`@marketing-auto/social/templates/overrides`) needs a single entry point; scattering files under per-template directories makes the barrel harder to maintain and the import path confusing.

### `upsertOverrides` placement
**Spec said:** `upsertOverrides` repo function in `packages/db`.  
**Reality:** upsert logic is inlined in the API route (`apps/api/src/routes/projects/template-overrides.ts`). Reason: upsert requires Zod schema validation via `@marketing-auto/social/templates/overrides`, which creates a circular dependency if pulled into `packages/db`. Only the API needs upsert; the pipeline only needs `fetchTemplateOverrides` + `markTemplateOverrideUsed`, which do live in `packages/db`.

### Helper function names
**Spec said:** `fetchOverrides`, `markUsed`.  
**Reality:** `fetchTemplateOverrides`, `markTemplateOverrideUsed`. Reason: consistent with the naming convention for other DB helpers in this package (always include the entity noun for grep-ability).

### Admin UI location
**Spec said:** sub-page within `/projects/:slug/settings/brand-tokens` area.  
**Reality:** added as Section 9 at the bottom of `SettingsProjectPage.vue` (`/settings` route for a specific project). Reason: the Settings page already has all other project configuration sections; adding a separate sub-page would require new routing just to split content that fits naturally in the existing flow.

## Discovered During Implementation

### `locale` field missing from `listCarouselInputSchema`
`listCarouselInputSchema` in `packages/social/src/compositions/list-carousel/types.ts` had no `locale` field before this spec. Fix X required locale-aware string resolution in `EndSlideStunning.tsx` and `ToolSlideStunning.tsx`, so `locale: z.enum(["de", "en"]).default("de")` was added to the schema. The pipeline step now derives locale from `input.locales[0]?.startsWith("de") ? "de" : "en"` and passes it through. Any future composition that needs locale-conditional text must check whether its input schema already declares `locale`.

### `apiPut` was absent from the web API client
`apps/web/src/lib/api.ts` had `apiGet`, `apiPost`, `apiPatch`, `apiDelete` but no `apiPut`. Added `apiPut` following the same pattern as `apiPatch`. The override route uses `PUT` (full-replace semantics on the values blob) not `PATCH` (partial-update semantics), so `apiPost` was not a substitute.

### Dynamic import not needed for overrides module in pipeline
The spec anticipated needing a dynamic import in `RenderSlidesStep` to avoid circular dependency between `packages/pipelines` and `packages/social`. In practice, `packages/social/templates/overrides` has no dependency on `packages/pipelines`, so the import is static. Dynamic import would have been needed only if override logic called pipeline-internal types.
