## 1. Ziel

62.0a baut die **Foundation-Layer** für den Content-Planner: alles, was nötig ist, damit eine Pipeline an JEDEM Step pausieren kann, der User eine von 7 Actions wählt, und die Pipeline mit dem korrekten State weiterläuft. Außerdem: ein Cost-Estimator-Aggregator über `BaseStep.estimatedCostEur()`, der einen Wochenplan gegen ein hartes Budget validiert.

**In Scope (explizit, da systemweiter Refactor):** ALLE LLM-Steps systemweit werden auf `ctx.promptOverride` umgestellt. Marcel-Entscheidung: lieber konsistent jetzt als später dafür sorgen müssen, dass jeder neue Step das mitbringt. Konkrete Liste in Section 4.4.

**Out of Scope (in 62.0b):** Prompt-Versionierung als DB-Tabelle, Golden-Set, `step_optimization_requests`-Tabelle. (Diese Spec ist die Foundation für 62.0b — alle Step-Pause-Strukturen sind so designed, dass 62.0b additive sein kann.)

**Out of Scope (spätere Sub-Specs):** Planner-Engine, Goals/Cadence, Kalender-UI, Debug-UI. Diese Spec liefert nur die Mechanik darunter.

## 2. Architektur-Entscheidungen (aus Discovery + Marcel-Antworten)

Diese sind verbindlich für 62.0a:

- **Runner-Level Mode-Handling (Wurf 3).** Steps wissen nichts von `runMode`. Der Runner wrappt jeden `BaseStep.execute()` und entscheidet basierend auf `ctx.runMode` über Suspend/Resume und Sync/Batch-Adapter-Wahl.
- **Step-Pause als Erweiterung des bestehenden `batchPending`-Patterns**, nicht als parallele Mechanik. Wir kopieren die Architektur aus `engine/runner.ts:62` + `engine/batch-resume.ts:15` und führen ein zweites Signal `stepPaused` ein.
- **`overrideLlmMode` in `PipelineRunOptions`.** Per-Run-Override statt `projects.llmMode` flippen.
- **Idempotency-Key-Caching JETZT verdrahten.** Pflicht-Implementation in 62.0a — sonst kostet `edit-input` jedes Mal alle vorhergehenden Steps.
- **Per-Article `skip_auto_translation_until` Flag.** Statt Week-Disable von `BlogPipeline.afterComplete`.
- **`paused` Enum-Wert in 62.0a-Migration einlumpen.** Keine Vorab-Migration.
- **Cost-Estimator in 62.0a, nicht in 62.3.** Wird vom Planner-Engine als Foundation gebraucht.
- **Pipeline-Blacklist hardcoded:** `article:pagespeed-validation`, `article:pagespeed-api-validation`.
- **Substep-Orphan-Cleanup via neuem Enum-Wert `superseded`.** Wenn ein Step neu ausgeführt wird (batch-resume, edit-input, edit-prompt), wird der vorherige Substep auf `superseded` gesetzt statt orphan zu bleiben. Cosmetic Issue aus Pre-flight Task 1 wird damit hier strukturell gelöst.
- **Anthropic `custom_id` Separator:** `_` (nicht `:`). Pre-flight D9 hat gezeigt dass Anthropic `^[a-zA-Z0-9_-]{1,64}$` enforced. Interne step_pauses-IDs dürfen `:` bleiben — nur Strings, die zu Anthropic gehen, brauchen `_`.
- **Article-Freshness-Definition** in `weekly-budget.ts` und allen späteren Planner-Komponenten: `coalesce(frontmatterUpdatedAt, lastRefreshedAt, publishedAt, updatedAt)`. Aus Refresh-Detector-Fix in Pre-flight Task 3 als kanonische Quelle festgeschrieben.

## 3. Datenbank-Migrationen

### 3.1 Migration `0070_step_pause_foundation.sql`

```sql
-- 1) New enum values in pipeline_run_status
ALTER TYPE pipeline_run_status ADD VALUE IF NOT EXISTS 'paused';
ALTER TYPE pipeline_run_status ADD VALUE IF NOT EXISTS 'superseded';
-- Note: requires Postgres restart-free commit. Drizzle handles this via raw SQL.
-- 'superseded' marks a substep that has been re-executed (by batch-resume, edit-input, or edit-prompt).
-- See Section 4.5 for orphan-cleanup mechanic.

-- 2) step_pauses — captures a single pause-resume cycle per step-run
CREATE TABLE step_pauses (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  pipeline_run_id uuid NOT NULL REFERENCES pipeline_runs(id) ON DELETE CASCADE,
  step_run_id     uuid NOT NULL REFERENCES pipeline_runs(id) ON DELETE CASCADE,
  step_name       text NOT NULL,
  pipeline_name   text NOT NULL,           -- denormalized for query-without-join
  project_id      uuid NOT NULL REFERENCES projects(id),
  
  -- Frozen at suspend
  step_input      jsonb NOT NULL,          -- the input that produced the paused output
  step_output     jsonb NOT NULL,          -- what the step computed
  prompt_used     text NULL,               -- the actual prompt text at time of execution (62.0b will link to prompt_versions)
  
  -- User decision
  action          text NULL,               -- 'approve' | 'edit-output' | 'edit-prompt' | 'edit-input' | 'abort' | 'promote-golden' | 'extract-for-optimization' | 'auto-dismissed'
  edited_input    jsonb NULL,              -- when action='edit-input'
  edited_output   jsonb NULL,              -- when action='edit-output'
  edited_prompt   text  NULL,              -- when action='edit-prompt' or 'promote-golden'
  user_note       text  NULL,              -- free text (especially for extract-for-optimization)
  
  -- Lifecycle
  requested_at    timestamptz NOT NULL DEFAULT now(),
  resolved_at     timestamptz NULL,
  resolved_by     text NULL,               -- 'marcel' for now, multi-user later; 'system' for auto-dismissed
  
  -- Idempotency
  UNIQUE (step_run_id)                     -- a step-run can only have one active pause cycle
);

CREATE INDEX step_pauses_pipeline_run_id_idx ON step_pauses (pipeline_run_id);
CREATE INDEX step_pauses_unresolved_idx ON step_pauses (project_id, requested_at DESC) WHERE resolved_at IS NULL;

-- 3) idempotency_outputs — cache for step-level memoization (Idempotency-Key-Caching)
-- All inserts MUST use ON CONFLICT DO NOTHING (pattern bewährt aus refresh-detector pre-flight-fix).
CREATE TABLE idempotency_outputs (
  idempotency_key  text NOT NULL,
  pipeline_name    text NOT NULL,
  step_name        text NOT NULL,
  project_id       uuid NOT NULL REFERENCES projects(id),
  step_output      jsonb NOT NULL,
  cost_eur         numeric(10,6) NOT NULL DEFAULT 0,
  created_at       timestamptz NOT NULL DEFAULT now(),
  expires_at       timestamptz NULL,         -- optional TTL, default no-expiry
  PRIMARY KEY (idempotency_key, pipeline_name, step_name, project_id)
);

CREATE INDEX idempotency_outputs_lookup_idx ON idempotency_outputs (pipeline_name, step_name, project_id, created_at DESC);

-- 4) articles: per-article auto-translation skip flag
ALTER TABLE articles ADD COLUMN IF NOT EXISTS skip_auto_translation_until timestamptz NULL;
```

**Why raw SQL + not `references()` for FKs:** Cross-spec pattern, FK constraints via raw SQL migration not Drizzle `references()`.

**Why `step_pauses.pipeline_run_id` AND `step_run_id`:** the parent pipeline run + the specific step-row. Both are `pipeline_runs.id` (self-FK pattern). Allows efficient query "all pauses in run X" without recursion.

### 4.3 Runner Logic Changes

**Pre-step (before `execute()`):**

```ts
// Pseudo-code, actual changes go in runner.ts around line 100-200
const stepCtx = buildStepContext({
  // ... existing ...
  llmMode: opts.overrideLlmMode ?? project.llmMode,
  runMode: opts.runMode ?? "production",
});

// Idempotency-Key cache check
const idemKey = step.idempotencyKey(input);
if (idemKey) {
  const cached = await getIdempotencyOutput({
    idempotencyKey: idemKey,
    pipelineName: pipeline.name,
    stepName: step.name,
    projectId: ctx.projectId,
  });
  if (cached) {
    log.info(`Step ${step.name}: idempotency cache HIT, skipping execution`);
    return step.outputSchema.parse(cached.stepOutput);
  }
}
```

**Post-step (after successful `execute()`):**

```ts
// 1) Persist idempotency cache (if key present)
if (idemKey) {
  await writeIdempotencyOutput({
    idempotencyKey: idemKey,
    pipelineName: pipeline.name,
    stepName: step.name,
    projectId: ctx.projectId,
    stepOutput: output,
    costEur: await getLatestCostForStepRun(stepRunId),  // approximation
  });
}

// 2) If debug-mode AND step is pausable: SUSPEND
if (stepCtx.runMode === "debug" && step.pausableInDebug()) {
  await persistStepPause({
    pipelineRunId: parentRunId,
    stepRunId,
    stepName: step.name,
    pipelineName: pipeline.name,
    projectId: ctx.projectId,
    stepInput: input,
    stepOutput: output,
    promptUsed: extractPromptFromCtxOrStep(step, input, ctx),  // may be null
  });
  
  await db.update(pipelineRuns)
    .set({ status: "paused" })
    .where(eq(pipelineRuns.id, parentRunId));
  
  return { ok: false, suspended: true, reason: "step-pause", stepKey: step.name };
}
```

**Resume from step-pause:**

```ts
// On enqueue with opts.stepPauseResume:
if (opts.stepPauseResume) {
  const { stepName, action, editedInput, editedOutput, editedPrompt } = opts.stepPauseResume;
  
  switch (action) {
    case "approve":
      // Use stored step_pauses.stepOutput as priorOutput[stepName], skip step, resume next
      opts.priorOutput = { ...opts.priorOutput, [stepName]: pausedOutput };
      opts.resumeFromStep = nextStepKey(pipeline, stepName);
      break;
    
    case "edit-output":
      // Use editedOutput (validated against step.outputSchema) as priorOutput[stepName]
      const parsed = step.outputSchema.parse(editedOutput);
      opts.priorOutput = { ...opts.priorOutput, [stepName]: parsed };
      opts.resumeFromStep = nextStepKey(pipeline, stepName);
      break;
    
    case "edit-input":
      // Re-execute step with editedInput, drop cached priorOutput for this step
      opts.priorOutput = { ...opts.priorOutput };  // unchanged for prior steps
      delete opts.priorOutput[stepName];           // force re-execute
      opts.resumeFromStep = stepName;
      // Pass editedInput through bridge() override — needs new mechanism
      opts.stepInputOverride = { [stepName]: editedInput };
      break;
    
    case "edit-prompt":
      // Re-execute with same input but force prompt override
      // 62.0a: prompt override flows via ctx.promptOverride (read by step's execute())
      opts.resumeFromStep = stepName;
      delete opts.priorOutput[stepName];
      opts.promptOverride = { [stepName]: editedPrompt };
      break;
    
    case "abort":
      // Mark run as cancelled, no resume
      await db.update(pipelineRuns).set({ status: "cancelled" }).where(eq(pipelineRuns.id, parentRunId));
      return { ok: false, aborted: true };
    
    case "promote-golden":
      // 62.0a: treat as 'approve' (the prompt is saved to step_pauses.editedPrompt for 62.0b to consume)
      // 62.0b will hook in here to write to prompt_versions
      opts.priorOutput = { ...opts.priorOutput, [stepName]: pausedOutput };
      opts.resumeFromStep = nextStepKey(pipeline, stepName);
      break;
    
    case "extract-for-optimization":
      // 62.0a: just log + persist user_note on step_pauses. No pipeline state change.
      // The UI freezes here, Marcel inspects elsewhere. Treat as a 'pause-still-active' state.
      // 62.0b will add the dedicated step_optimization_requests table.
      return { ok: false, suspended: true, reason: "extract-for-optimization" };
  }
}
```

**Wichtig:** `stepInputOverride` und `promptOverride` sind neue `PipelineRunOptions`-Felder; sie werden im Runner an die Step-Ausführung weitergereicht. Wie `ctx.promptOverride` von Steps konsumiert wird → siehe 4.4.

### 4.4 Step-Side: Prompt-Override-Konsumierung (systemweiter Refactor)

**Marcel-Entscheidung: alle LLM-Steps systemweit auf `ctx.promptOverride` umstellen** — lieber konsistenter Cut jetzt als pro Sub-Spec nachziehen.

Pattern:

```ts
// Inside e.g. OutlineStep.execute()
const promptToUse = ctx.promptOverride?.[this.name]
  ?? buildSystemPrompt({ /* default */ });
```

**Helper im Engine-Modul** zur Reduktion von Boilerplate:

```ts
// packages/pipelines/src/engine/prompt-resolver.ts
export function resolvePrompt(
  ctx: StepContext,
  stepName: string,
  buildDefault: () => string
): string {
  return ctx.promptOverride?.[stepName] ?? buildDefault();
}
```

So braucht jeder Step nur `resolvePrompt(ctx, this.name, () => buildSystemPrompt({...}))` statt manueller `??`-Logik.

### 4.5 Substep-Orphan-Cleanup + Auto-Dismiss

**Hintergrund:** Pre-flight Task 1 hat aufgedeckt, dass nach einem batch-resume der originale Outline-Substep orphan in `status='running'` bleibt. Mit Step-Pause-Mechanik wird dieser Effekt vervielfacht: jedes `edit-input` und `edit-prompt` erzeugt einen neuen Substep, der alte bliebe ebenfalls orphan.

**Lösung:** drei Cleanup-Pfade.

#### 4.5.1 Substep-Supersession beim Re-Execute

Im Runner, bevor ein Step erneut ausgeführt wird (egal aus welchem Grund — batch-resume, edit-input, edit-prompt):

```ts
// Pseudo-code in runner.ts around step-re-execution
async function supersedeOldSubstep(parentRunId: string, stepName: string) {
  await db.update(pipelineRuns)
    .set({ status: "superseded", completedAt: new Date() })
    .where(and(
      eq(pipelineRuns.parentRunId, parentRunId),
      eq(pipelineRuns.stepName, stepName),
      inArray(pipelineRuns.status, ["running", "batch_pending", "paused"]),
    ));
}
```

Aufruf-Pattern:
- Vor `enqueuePipeline()` mit `resumeFromStep=X` UND `priorOutput[X] deleted` → `supersedeOldSubstep(parentRunId, X)`.
- Innerhalb `engine/batch-resume.ts` direkt vor dem Resume-Trigger → same call (löst auch das pre-flight cosmetic issue).

#### 4.5.2 step_pauses Auto-Dismiss bei Parent-Cancellation

Wenn das parent `pipeline_run` auf `cancelled`, `failed`, oder `superseded` geht, alle aktiven `step_pauses` desselben Runs auto-dismissen:

```ts
// Trigger: parent-status-change-hook in runner, oder DB-trigger
async function autoDismissPauses(parentRunId: string, reason: string) {
  await db.update(stepPauses)
    .set({
      action: "auto-dismissed",
      resolvedAt: new Date(),
      resolvedBy: "system",
      userNote: `Parent run ${reason}`,
    })
    .where(and(
      eq(stepPauses.pipelineRunId, parentRunId),
      isNull(stepPauses.resolvedAt),
    ));
}
```

Vorbild ist der Auto-Dismiss-Pass aus Pre-flight Task 3 (`refresh-detector.ts`) — Pattern bewährt.

#### 4.5.3 Cleanup-Worker (defense-in-depth)

Selbst wenn 4.5.1 und 4.5.2 sauber implementiert sind, gibt es Crash-Szenarien (Process-Kill mitten im Resume) wo Substeps in `running` hängen können. Kleiner Cleanup-Worker:

- Läuft alle 6h via BullMQ-Repeat-Job (`stepPauseCleanup` in `apps/api/src/workers/`)
- Findet `pipeline_runs` mit `status='running'` AND `updated_at < now() - interval '24 hours'` AND `step_name IS NOT NULL` (also: Substeps, nicht parents)
- Setzt sie auf `superseded` mit Log-Entry
- Wenn parent dadurch alle Substeps in non-running state hat: keine Aktion, parent bleibt wie er ist (operativer Eingriff erforderlich, Notification triggern)

**Konfiguration:** Worker-Enable über `cron_state` mit `cron_job_type='step-pause-cleanup'`. Default-Pattern `0 */6 * * *`. Default-State `is_active=true` (Defense-in-Depth lohnt sich).

```ts
  // Compare against weeklyBudgetEur

```

**Strategie pro Item:**
1. Wenn `Pipeline.estimatedCostEur(input)` aussagekräftig (alle Steps haben non-zero estimates) → nutze diese.
2. Sonst → Historische avg-cost per `pipelineName` aus `cost_logs` (last 30d) als Fallback.
3. Wenn Pipeline noch nie gelaufen ist → konservativer Default pro `itemType` (in `weekly-budget.ts` als const).

**Defaults aus Discovery (cost_logs avg):**
- `article:blog` ≈ €0.30 (Outline + Draft + SelfReview + SocialImage etc.)
- `article:translation` ≈ €0.10
- `article:social-image` ≈ €0.02 pro Render
- Voller Cluster (hub+spokes) ≈ €4.20 (aus Memories bestätigt)
- `batch:claude-sonnet-4-6` einzelner Call ≈ €0.028 (aus Pre-flight Smoke gemessen)

**Hartstop-Logic:** Caller (Planner-Engine in 62.4) entscheidet was bei `withinBudget=false` passiert (heutiges UI-Verhalten in 62.5). 62.0a liefert nur das Estimate.

### 5.1 Article-Freshness als kanonische Definition

Aus Pre-flight Task 3 (Refresh-Detector-Fix) wurde der echte Edit-Marker identifiziert. Diese Definition lebt ab jetzt in `weekly-budget.ts` als shared Utility und wird von ALLEN späteren Planner-Komponenten verwendet:

```ts
// packages/cost-tracker/src/article-freshness.ts
import { sql, coalesce } from "drizzle-orm";

/**
 * Canonical effective-freshness expression for articles.
 *
 * Order of preference:
 * 1. `frontmatterUpdatedAt` — Marcel's real edit marker (Astro `updated:` frontmatter)
 * 2. `lastRefreshedAt` — set by article-refresh pipeline
 * 3. `publishedAt` — initial publish timestamp
 * 4. `updatedAt` — DB row update (Drizzle-managed, often unrelated to content)
 *
 * Established in Pre-flight Task 3 (apps/api/src/workers/refresh-detector.ts).
 * Mirror any change here in refresh-detector to keep both consistent.
 */
export const effectiveFreshnessSql = sql<Date>`COALESCE(
  ${articles.frontmatterUpdatedAt},
  ${articles.lastRefreshedAt},
  ${articles.publishedAt},
  ${articles.updatedAt}
)`;

export function effectiveFreshness(article: {
  frontmatterUpdatedAt: Date | null;
  lastRefreshedAt: Date | null;
  publishedAt: Date | null;
  updatedAt: Date;
}): Date {
  return article.frontmatterUpdatedAt
    ?? article.lastRefreshedAt
    ?? article.publishedAt
    ?? article.updatedAt;
}
```

**Verwendung in 62.0a:** `weekly-budget.ts` muss `effectiveFreshness` für jeden geplanten Refresh-Item nutzen, um zu entscheiden ob ein Refresh überhaupt nötig ist (wenn Article < 30 Tage frisch → konservativer Default-Cost = 0, Item wird im Plan markiert als "skipped, recent").

**Verwendung in späteren Specs:** 62.4 Planner-Engine nutzt `effectiveFreshness` für alle Refresh-Pool-Queries. Refresh-Detector (`apps/api/src/workers/refresh-detector.ts`) wurde in Pre-flight schon entsprechend gepatcht — beide Quellen müssen synchron bleiben (Auditiert über den Test in Section 8.4).

## 13. Deviations from Implementation

Per-session log of where the implementation diverged from the spec. Each entry: what changed, why, where to find it.

### Session 1 (Phase 0 + Phase 1, 2026-05-20)

**D1 — Migration numbered `0067` (spec says `0070`).**
- Spec was drafted assuming three migrations would land between Spec 61.4 and Spec 62.0a. They didn't — last migration on master is `0066_batch_api_worker_schema`.
- Decision: keep migrations contiguous. File is [`packages/db/drizzle/0067_step_pause_foundation.sql`](../packages/db/drizzle/0067_step_pause_foundation.sql), journal entry `idx: 67`, `when: 1784500000000`.
- No functional impact; future references to "migration 0070" in other 62-* specs should read 0067.

**D2 — `step_pauses_step_run_id_unique` is a `uniqueIndex` in Drizzle, `CONSTRAINT UNIQUE` in SQL.**
- Spec 3.1 SQL declares `CONSTRAINT "..." UNIQUE (step_run_id)`; Drizzle 3.2 declares the same column as `uniqueIndex(...).on(t.stepRunId)`.
- Both produce identical on-disk btree-unique-index (verified via `psql \d step_pauses`: `step_pauses_step_run_id_unique" UNIQUE CONSTRAINT, btree (step_run_id)`). Drizzle queries are unaffected; functional equivalence.
- Standardise during 62.0b if Marcel prefers; not blocking.

**D3 — `NormalizedStatus` in `apps/api/src/routes/pipeline-runs.ts` widened with `paused`, and `superseded → failed` mapping added.**
- Out-of-spec consequence of adding two new `pipelineRunStatusEnum` values: TypeScript narrowed `NormalizedStatus` rejected the wider DB type at two `pr.status` assignment sites.
- Fix: added `paused` to the union; mapped `superseded → "failed"` (internal cleanup state, no UI surface); wrapped both `pr.status` assignments with `normalizeStatus()`.
- Activity-feed UI now treats `paused` as its own status; `superseded` rows surface as "failed".

**D4 — Pre-existing baseline failures NOT addressed in this PR.**
- `packages/adapters/astro-sync/test/gap-detection-includes-generated.test.ts:24` — mockCtx missing `llmMode` (Spec 61.4 fallout). Spawned as side-task; tracked separately.

### Session 2 (Phase 2.1–2.5, 2026-05-20)

Marcel landed two commits in parallel (`596eb03`, `ff40dea`) that covered Phase 2.1 + 2.4 (runner type extensions, resume switch-case dispatcher, skip-logic unification). My Session 2 commit completed Phase 2.2, 2.3, 2.5 plus baseline cleanups.

**D5 — `StepAction` exported from `@marketing-auto/shared`, not `@marketing-auto/db`.**
- Spec Section 3.3 placed `stepActionSchema` in `packages/shared/src/types/step-pause.ts`. Marcel's parallel commit imported `type StepAction` from `@marketing-auto/db` where it does not exist (workspace typecheck would have caught this — see CLAUDE.md "DO NOT add a value to an existing `pgEnum` without auditing TypeScript consumers" for the audit habit).

**D6 — `pipeline_runs.batchCheckpoint` reused for step-pause checkpoints.**
- Spec Section 3.1 did not specify where the runner persists `accumulatedOutput` (= priorOutput at suspend time) so the resolve service can reconstruct `PipelineRunOptions.priorOutput`. `step_pauses` only stores `stepInput` + `stepOutput`.
- Session 2 reuses `pipeline_runs.batchCheckpoint` (jsonb, already typed `Record<string, unknown>`) with a `kind: "step_pause"` discriminator on the checkpoint object. Shape:
  ```
  { kind: "step_pause", stepKey, stepPauseId, accumulatedOutput }
  ```
- Rationale: shape is identical to the existing `BatchCheckpoint`; no migration; the resolve service reads it back at re-enqueue time. - Spec Section 4.3 lists `abort` in the resume switch-case but is ambiguous about whether the service should short-circuit. Session 2 chose to re-enqueue with `action: "abort"` so all "mark cancelled + auto-dismiss siblings" logic lives in one place (the runner). Cost: a brief `running` → `cancelled` flip on `pipeline_runs.status`. No observable race.

**D8 — `extract-for-optimization` keeps `resolved_at` NULL (does NOT re-enqueue).**
- Spec Section 8.2 #9 says "Pipeline bleibt paused, KEIN Resume getriggert". Spec Section 4.3 switch-case includes the action ambiguously.
- Session 2 resolves the ambiguity: the service tags the row (`action`, `userNote`) but keeps `resolved_at = NULL` so the pause stays in the partial unresolved index. No re-enqueue. The runner's switch-case still has a defensive branch that re-suspends if the action somehow reaches it (logged as `warn`).

**D9 — `StepPauseResume.storedOutput` is optional.**
- Marcel's commit declared it as `storedOutput: unknown` (required). The Zod-inferred type from `z.unknown()` is `storedOutput?: unknown` (optional). Under `exactOptionalPropertyTypes`, these are incompatible.
- Session 2 changed the interface to `storedOutput?: unknown` to align with the Zod inference, plus a single justified `as Parameters<typeof runPipeline>[2]` cast in [queue.ts:194](packages/pipelines/src/engine/queue.ts:194) where the worker dispatches into runner opts.

**D10 — `editedInput`/`editedOutput` API boundary uses `unknown` with documented cast.**
- The Zod payload schema declares `editedInput: z.unknown().optional()`. The DB column is jsonb. The service casts `payload.editedInput as Record<string, unknown>` to satisfy the Drizzle `$type` hint. The cast is functionally safe (jsonb accepts any JSON value; the runner's `step.inputSchema.parse()` re-validates on re-execute), but technically a lie. See [packages/pipelines/CLAUDE.md](packages/pipelines/CLAUDE.md) note on the unknown→jsonb boundary pattern.

Session 2 had to patch 9 fixtures in `packages/pipelines/test/`, 1 in `packages/adapters/astro-sync/test/`, and 1 inline literal in `apps/api/src/routes/projects.ts:622`. ### Session 3 (Phase 2.5.1–2.5.3, 2026-05-20)

**D12 — `cron_state` rows for `step_pause_cleanup` seeded in worker code, not SQL migration.**
- Spec Section 4.5.3 implied the seed would live in a migration alongside the `cron_job_type` enum value. PostgreSQL rejects this pattern: `ALTER TYPE ADD VALUE 'step_pause_cleanup'` followed by `INSERT ... cron_state (job_type) VALUES ('step_pause_cleanup', ...)` in the same migration session fails with `invalid input value for enum cron_job_type: "step_pause_cleanup"` even after split into two transactions — the new enum value is not visible in the same backend session that added it.
- Resolution: migration `0068_step_pause_cleanup_enum.sql` is enum-only. Seed lives in `apps/api/src/workers/step-pause-cleanup.worker.ts::seedStepPauseCleanupCron()`, called once at worker startup (idempotent `onConflictDoNothing`). New projects also get the row at creation time in `apps/api/src/routes/projects.ts`.
- Trade-off: a fresh DB clone must boot the worker at least once before `cron_state` is seeded. Acceptable — `bun run db:migrate` doesn't include the seed step in any case for this app.

**D13 — Post-failure auto-dismiss is wrapped in try-catch (defense-in-depth, no escalation).**
- Spec Section 4.5.2 specified that `autoDismissStepPauses` should run when the parent transitions to `cancelled`/`failed`/`superseded`. Implementation choice for Session 3: wrap each call site in try-catch so a DB hiccup during the cleanup query does NOT re-throw — the parent failure or cancel is already persisted; rethrowing would either (a) escalate a failed pipeline into a BullMQ retry (expensive — would re-run paid LLM steps), or (b) turn a successful HTTP cancel into a 500.
- Pattern mirrors the existing `afterError` / `afterComplete` hook convention. Stale unresolved pauses are caught by the 6h `step_pause_cleanup` worker as backup.

**D14 — `PATCH /api/pipeline-runs/:id/cancel` whitelist broadened.**
- Pre-62.0a allowed cancellation only for `queued` / `running` runs. Session 3 added `paused` and `batch_pending` so users can abandon a paused debug run without going through the resolve flow, or kill a stuck `batch_pending` whose batch will never complete.
