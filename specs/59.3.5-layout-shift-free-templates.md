# Spec 59.3.5 — Layout-Shift-Free Templates (Cross-Template Convention)

**Theme:** 59 (Tier 3 Pre-Launch Foundation)
**Status:** Draft
**Estimated effort:** 2.5 days (~18 focused hours across 5 sessions)
**Prerequisite:** 59.3 pro-con-verdict shipped
**Successor:** Spec 60 — Design System Visual Refresh

---

## Goal

Codify a cross-template convention for **layout-shift-free** Remotion compositions, and retroactively patch the four existing production templates to comply. This spec turns ad-hoc practices accumulated across `comparison-grid-4`, `comparison-grid-3`, `verdict-per-use-case`, `single-tool-spotlight`, and the freshly-landed `pro-con-verdict` into a documented, enforceable pattern set.

After 59.3.5 lands, every template — present and future — obeys the same five patterns. Spec 60 (Visual Refresh) can then redesign templates against the toolwiki Design System without re-deriving "what does layout-shift-safe even mean" for each one.

## What this is NOT

- Not a visual refresh — visual output stays identical until Spec 60 (only structural / type-level changes)
- Not a new template — applies to the 5 existing templates only
- Not a render-pipeline change — Remotion / BullMQ / R2 wiring untouched
- Not a brand_tokens migration — DB schema unchanged
- Not auto-template-suggestion — separate Phase E backlog item
- Not a fix for runtime PNG render bugs — those are caught by visual tests, not by these patterns. These patterns *prevent* the class of bug; they don't replace render assertions.

The convention is about **the contract between LLM-produced content and Composition-rendered layout**: bounding what the LLM can emit so the layout never has to flex to fit it, and bounding what the layout can request so the LLM never produces content that doesn't fit.

---

## Why now (motivation)

Three forcing functions:

1. **Spec 60 builds on this.** Visual Refresh against the toolwiki Design System changes typography, spacing, and color tokens for all 5 templates simultaneously. Without a layout-shift contract in place, every Design-System change risks invisible regressions where an LLM-produced field overflows its new container at a new font size. Establishing the contract first means Spec 60 patches *visual values* not *layout integrity*.

2. **Five templates is the point where conventions stop emerging and start needing to be written down.** With 4 templates, ad-hoc patterns survived. With 5, and 5 more on the Phase E roadmap (workflow-impact-stack, feature-showcase, definition-card, alternative-to-x, myth-vs-reality), the cost of "every template re-derives length bucketing" is now higher than the cost of writing this spec.

3. **The 59.3 implementation surfaced no layout-shift bugs — but only because the spec preemptively bounded `verdict_snippet`, `whenToUse`, `whenToSkip` at LLM-prompt level.** That preemptive bounding was author-discipline, not convention. This spec turns discipline into a checklist.

## Section A — Constraint-Based Content

### A.1 Principle

**Layout dictates content bounds; LLM serves the layout.**

This inverts the naive flow ("LLM generates content, layout adapts to fit") which is the root cause of every layout-shift bug in Remotion compositions: when content height is variable and the surrounding `flex` / `grid` track is `auto` or `1fr`, sibling slots get pushed, baselines drift, and the same template renders differently across fixtures.

The fix is mechanical: every text slot has a **declared maximum character length**, baked into a Zod schema. The LLM is told the bound in the prompt and the LLM output is Zod-parsed before composition rendering. If the LLM overshoots, the pipeline either reprompts (Section F) or truncates with ellipsis (last-resort).

### A.2 The contract structure

Each template defines a `ContentBounds` object next to its `TemplateDefinition`:

```ts
// packages/social/src/templates/definitions/pro-con-verdict.ts
import { z } from "zod";

/**
 * Hard bounds on LLM-produced fields for this template.
 * Numbers match the layout container sizes EXACTLY (see Section B for
 * the bucket table that derives these).
 */
export const proConVerdictBounds = {
  verdictSnippet: { min: 30, max: 80 },     // Cover slide, 1 line @ fontSize 56
  whenToUse:      { min: 40, max: 120 },    // Verdict slide, 2 lines @ fontSize 44
  whenToSkip:     { min: 40, max: 120 },    // Verdict slide, 2 lines @ fontSize 44
  hookText:       { min: 20, max: 90 },     // Cover hook, 1-2 lines @ fontSize 48
  captionBody:    { min: 200, max: 1800 },  // Instagram caption, not rendered in slide
  // Hashtags are bounded by count + per-tag length (Section A.3)
} as const;

export const proConVerdictGeneratedSchema = z.object({
  verdictSnippet: z.string()
    .min(proConVerdictBounds.verdictSnippet.min)
    .max(proConVerdictBounds.verdictSnippet.max),
  whenToUse: z.string()
    .min(proConVerdictBounds.whenToUse.min)
    .max(proConVerdictBounds.whenToUse.max),
  whenToSkip: z.string()
    .min(proConVerdictBounds.whenToSkip.min)
    .max(proConVerdictBounds.whenToSkip.max),
  // ... etc
});
```

**Why the bounds object is separate from the schema**: the bounds are *referenced by the LLM prompt* (e.g. "Schreibe maximal 80 Zeichen") and *enforced by the schema*. Keeping them in one source-of-truth prevents drift between "what the prompt says" and "what the schema accepts" — a class of bug the team has hit before (Discovery D1 from 59.3 is a related "two places to update" surface, in spirit).

### A.3 Hashtag and list-content bounds

Hashtags and list items (pros / cons / use-cases) are bounded by **count** AND **per-item length**:

```ts
export const proConVerdictBounds = {
  // ... single fields above
  hashtags: { count: 7, perTagMaxChars: 24 },   // 7 tags, each ≤ 24 chars
  prosVisible: { max: 5, perItemMaxChars: 80 }, // up to 5 pros, each ≤ 80 chars
  consVisible: { max: 5, perItemMaxChars: 80 },
} as const;
```

The composition reads `prosVisible.max` to know how many slots to render; if the article has fewer pros, empty slots collapse via the Section C grid pattern (fixed track, optional content).

### A.4 The bound numbers are not negotiable per fixture

A common temptation: "for the edge-max fixture, allow longer strings so we can test the visual limit." **No.** The edge-max fixture uses content that fits *within* the declared bounds at the maximum-allowed length. The point of the bound is that nothing exceeds it in production. The edge-max fixture proves the layout survives at the bound; testing past the bound tests behavior we never want to ship.

### A.5 What this prevents

| Bug class | Without bounds | With bounds |
|---|---|---|
| LLM emits 150-char verdict, overflows cover | Frequent | Schema rejects, reprompt |
| Pros list with 8 items pushes layout taller than canvas | Possible | Composition reads `prosVisible.max = 5`, ignores rest |
| Hashtag `#KünstlicheIntelligenzImMittelstand2026` breaks caption line-wrap | Possible | Per-tag max 24 chars rejects it |
| Font-size auto-scaling causes baseline drift across fixtures | Frequent | Bounds → fixed bucket (Section B) |

### A.6 Discovered During Implementation

- **`TemplateDefinition` needed three new fields, not one.** The spec described `slotMap` only, but the test scaffold requires `bounds` (for alignment checks) and `generatedSchema` (for fixture validation) as well. All three were added as optional fields to `TemplateDefinition` in `types.ts`.
- **`MockFixture` needed a `generatedContent` optional field.** The `fixtures-respect-bounds.test.ts` needs to access the generated verdict data from fixtures. Added `generatedContent?: unknown` to `MockFixture`.
- **Dual-schema pattern emerged.** Two schemas per template, not one: `llmResponseSchema` (validates raw LLM output in snake_case before transformation) and `generatedSchema` / `proConVerdictGeneratedSchema` (validates the camelCase-transformed verdict fields, used by fixture tests). The spec example in F.3 implied a single schema passed to `validateAndReprompt` — see F.7 for detail.
- **Bounds values deviated from spec examples.** `proConVerdictBounds.whenToUse.max` = 280 (not 120 as in A.2 example) to match existing `llmResponseSchema` and Verdict slide layout capacity. `captionBody.min` = 20 (not 200 as in A.2 example) — the 200-char floor was too high for short EN captions.

## Section B — Fluid Typography Rules

### B.1 Principle

**Discrete length buckets, never continuous scaling.**

Continuous font scaling (`fontSize: clamp(...)` or `fontSize: text.length * k`) sounds elegant but breaks layout-shift guarantees in two ways:

1. **Sub-pixel rendering**: Chromium rounds sub-pixel font sizes inconsistently across runs, causing 1-2px baseline differences between fixtures and re-renders. Visual diff tests flag false positives.
2. **Reflow ambiguity**: When fontSize and container height both vary with content, the geometric relationship is implicit, not declared. Debugging a 4px overshoot means tracing two variables instead of one.

The fix: every text slot has a **`getFontSize(textLength, slotType)` function** with discrete integer buckets. Same input → same output. Same bucket → same baseline.

### B.2 The bucket table

A shared utility lives at `packages/social/src/compositions/_shared/getFontSize.ts`:

```ts
/**
 * Discrete font-size buckets per slot type.
 * NEVER use continuous scaling — sub-pixel rendering causes baseline drift
 * across fixtures and re-renders. See Spec 59.3.5 Section B for rationale.
 */
export type SlotType =
  | "cover-headline"      // largest, 1-2 lines
  | "cover-snippet"       // medium, 1 line
  | "slot-headline"       // per-slide section title
  | "slot-body"           // per-slide content text
  | "list-item"           // pro/con/use-case item
  | "eyebrow"             // small, all-caps label
  | "caption-cta"         // end-slide CTA text
  | "footer";             // smallest, attribution

interface Bucket {
  maxChars: number;
  fontSize: number;        // px, integer only
  lineHeight: number;      // multiplier, 2 decimals max
  letterSpacing: number;   // px, integer only
}

const BUCKETS: Record<SlotType, Bucket[]> = {
  "cover-headline": [
    { maxChars: 30,  fontSize: 88, lineHeight: 1.05, letterSpacing: -2 },
    { maxChars: 60,  fontSize: 72, lineHeight: 1.10, letterSpacing: -1 },
    { maxChars: 120, fontSize: 56, lineHeight: 1.15, letterSpacing:  0 },
  ],
  "cover-snippet": [
    { maxChars: 40,  fontSize: 56, lineHeight: 1.20, letterSpacing: 0 },
    { maxChars: 80,  fontSize: 44, lineHeight: 1.25, letterSpacing: 0 },
  ],
  "slot-headline": [
    { maxChars: 25,  fontSize: 64, lineHeight: 1.10, letterSpacing: -1 },
    { maxChars: 50,  fontSize: 48, lineHeight: 1.15, letterSpacing:  0 },
  ],
  "slot-body": [
    { maxChars: 80,  fontSize: 40, lineHeight: 1.30, letterSpacing: 0 },
    { maxChars: 160, fontSize: 32, lineHeight: 1.35, letterSpacing: 0 },
  ],
  "list-item": [
    { maxChars: 40,  fontSize: 36, lineHeight: 1.30, letterSpacing: 0 },
    { maxChars: 80,  fontSize: 28, lineHeight: 1.35, letterSpacing: 0 },
  ],
  "eyebrow": [
    { maxChars: 30,  fontSize: 24, lineHeight: 1.20, letterSpacing: 4 },
  ],
  "caption-cta": [
    { maxChars: 40,  fontSize: 40, lineHeight: 1.20, letterSpacing: 0 },
  ],
  "footer": [
    { maxChars: 60,  fontSize: 18, lineHeight: 1.20, letterSpacing: 1 },
  ],
};

export function getFontSize(text: string, slotType: SlotType): Bucket {
  const buckets = BUCKETS[slotType];
  const len = text.length;
  for (const bucket of buckets) {
    if (len <= bucket.maxChars) return bucket;
  }
  // Fallback: smallest bucket. If we hit this, content overshot bounds —
  // truncation in composition will kick in. See Section C.4.
  return buckets[buckets.length - 1]!;
}
```

### B.3 Bucket counts per slot type

Three buckets per text-heavy slot, one bucket for fixed-width slots (eyebrow, footer, CTA). Three is the sweet spot: enough to absorb realistic length variance, few enough to memorize and verify visually.

### B.4 Bucket boundaries align with Zod bounds

The `maxChars` in each bucket's *last* entry must match the corresponding Section A bound. Example:

- `proConVerdictBounds.verdictSnippet.max = 80`
- Last bucket of `cover-snippet`: `maxChars: 80`

This alignment is the **layout-shift guarantee** — content that passes Section A validation is guaranteed to fit a known bucket, which is guaranteed to render at a known font-size, which is guaranteed to fit a known container (Section C).

A unit test enforces this alignment (Section G.2).

### B.5 No `clamp()`, no `vw` units, no `auto` line-heights

For composition CSS:
- ❌ `fontSize: 'clamp(32px, 4vw, 56px)'` — `vw` is undefined in Remotion's fixed-canvas context, results are unpredictable
- ❌ `fontSize: \`${Math.min(56, 4000 / text.length)}px\`` — continuous, sub-pixel
- ❌ `lineHeight: 'normal'` — font-defined, varies by font
- ✅ `fontSize: bucket.fontSize` — integer, deterministic
- ✅ `lineHeight: bucket.lineHeight` — explicit multiplier

### B.6 Discovered During Implementation

- **`slot-body` last bucket must be `maxChars: 280`, not `160`.** The spec's example table showed `maxChars: 160` as the last slot-body entry. The actual `whenToUse`/`whenToSkip` bounds (280 chars) required the last bucket to be 280. Always derive bucket boundaries from the template's actual field bounds, not from the spec table example.
- **`cover-snippet` at 44–56px is much larger than traditional "snippet" styling.** The 25px italic snippet in the pre-formalization `CoverSlide` looked like a footnote. After applying `getFontSize(text, "cover-snippet")`, the same text renders at 44px. This is an intentional visual change (formalization, not retro patch), but future template authors should know that `cover-snippet` is a prominent slot, not a small label.
- **`getFontSize()` result must be cached before destructuring.** Calling `getFontSize(text, slot).fontSize` and `getFontSize(text, slot).lineHeight` on separate lines executes the lookup twice. Always: `const b = getFontSize(text, slotType); style={{ fontSize: b.fontSize, lineHeight: b.lineHeight }}`. Caught in review-task.

## Section C — Fixed-Slot Layout

### C.1 Principle

**Composition root is a Grid with fixed `px` tracks. Content slots may be `1fr` but their *inner* slots are again `px`.**

A Remotion composition that uses `flex: 1` for the content area lets content height dictate layout. When content is variable (LLM-produced), layout becomes variable. Visual regressions become inevitable. The fix is to **declare every height up front** in `px`, and let content **clip or shrink** to fit (via Section B's bucket system), never to **push** layout.

### C.2 The standard composition skeleton

Every composition follows this skeleton:

```tsx
// packages/social/src/compositions/pro-con-verdict/CoverSlide.tsx
import { AbsoluteFill } from "remotion";

const CANVAS_W = 1080;
const CANVAS_H = 1350;

// Fixed vertical rhythm (sums to CANVAS_H):
const ROW_EYEBROW   = 100;  // top eyebrow
const ROW_HEADLINE  = 380;  // cover headline + snippet
const ROW_VISUAL    = 620;  // signature visual (split-screen, grid, hero)
const ROW_FOOTER    = 250;  // logo + URL
// 100 + 380 + 620 + 250 = 1350 ✓

export const CoverSlide: React.FC<Props> = ({ content, tokens }) => {
  return (
    <AbsoluteFill style={{ background: tokens.background }}>
      <div style={{
        display: "grid",
        gridTemplateRows: `${ROW_EYEBROW}px ${ROW_HEADLINE}px ${ROW_VISUAL}px ${ROW_FOOTER}px`,
        width: CANVAS_W,
        height: CANVAS_H,
        padding: `0 60px`,
      }}>
        <EyebrowRow content={content} tokens={tokens} />
        <HeadlineRow content={content} tokens={tokens} />
        <VisualRow content={content} tokens={tokens} />
        <FooterRow content={content} tokens={tokens} />
      </div>
    </AbsoluteFill>
  );
};
```

The rows are `px`, sum to canvas height, leave no `1fr` at the root.

### C.3 Inner slots may use `1fr`, but only when their parent is fixed

Inside a fixed-height row, content alignment with `1fr` is fine, because the parent already constrains the total:

```tsx
const HeadlineRow: React.FC = ({ content, tokens }) => {
  return (
    <div style={{
      height: ROW_HEADLINE,                       // fixed parent
      display: "grid",
      gridTemplateRows: "auto auto 1fr",          // headline, snippet, spacer
      gap: 24,
    }}>
      <Headline text={content.headline} tokens={tokens} />
      <Snippet text={content.snippet} tokens={tokens} />
      <div />  {/* 1fr spacer absorbs any leftover within the 380px row */}
    </div>
  );
};
```

The `1fr` here is bounded by `ROW_HEADLINE = 380px`. It can never push the slide taller.

### C.4 Truncation as last-resort safety net

Even with Section A bounds and Section F validation, defensive truncation in the composition catches edge cases (override-passed strings, mis-aligned bucket counts, content-extension fields):

```tsx
const Headline: React.FC<{ text: string }> = ({ text }) => {
  const bucket = getFontSize(text, "cover-headline");
  return (
    <div style={{
      fontSize: bucket.fontSize,
      lineHeight: bucket.lineHeight,
      letterSpacing: bucket.letterSpacing,
      overflow: "hidden",
      display: "-webkit-box",
      WebkitLineClamp: 2,             // hard cap
      WebkitBoxOrient: "vertical",
      textOverflow: "ellipsis",
    }}>
      {text}
    </div>
  );
};
```

`WebkitLineClamp` is the safety net. If Section A and F worked, it never engages. If a bug slips through, the slide ships with ellipsis rather than overflowing.

### C.5 No content-driven container sizes

Forbidden patterns:
- ❌ `flexGrow: 1` on a content container at the root level
- ❌ `height: 'auto'` on any slot
- ❌ `minHeight: ...` without a matching `maxHeight`
- ❌ Conditionally rendered slots that change overall layout count (e.g. `{hasFooter && <Footer />}` changing total row count)

Allowed alternatives:
- ✅ Fixed `px` rows summing to canvas height
- ✅ `1fr` inside a fixed parent
- ✅ Always-rendered slots that may be visually empty (e.g. `{hasFooter ? <Footer /> : <div />}` preserves grid track)

### C.6 List slots use fixed item counts

Pro/con lists, use-case grids, tool-comparison grids: the composition reads `bounds.prosVisible.max` (Section A.3) and renders that many slots. If the article supplies fewer items, the remaining slots render as `<div />` placeholders — same height, no content. The grid track count never changes.

```tsx
const ProsList: React.FC<{ pros: string[] }> = ({ pros }) => {
  const MAX = 5;
  const slots = Array.from({ length: MAX }, (_, i) => pros[i] ?? null);
  return (
    <div style={{
      display: "grid",
      gridTemplateRows: `repeat(${MAX}, 80px)`,    // fixed 5 rows
      gap: 16,
    }}>
      {slots.map((pro, i) =>
        pro ? <ProItem key={i} text={pro} /> : <div key={i} />
      )}
    </div>
  );
};
```

## Section D — Visual Test Matrix

### D.1 Principle

**Every template ships with exactly 3 fixtures: characteristic, edge-min, edge-max.** Visual regression tests render all three to PNG and diff against baselines. This is a **hard requirement** — bootstrap.ts registration is gated on fixture presence.

### D.2 The three fixtures explained

| Fixture | Content profile | Purpose |
|---|---|---|
| **characteristic** | Realistic average — what 80% of generated content looks like | Catches drift in the common case |
| **edge-min** | Shortest realistic content within bounds (1 pro, 1 con; min-length strings; minimum-required fields populated) | Catches layout collapse, baseline shifts when slots are sparse |
| **edge-max** | Longest realistic content within bounds (max-count items; max-length strings per item; all optional fields populated) | Catches overflow, truncation engagement at the limit |

Edge-min and edge-max sit **at the declared bounds**, not past them (per A.4).

### D.3 Fixture file structure

```
packages/social/src/templates/definitions/fixtures/
  pro-con-verdict.fixtures.ts
  comparison-grid-4.fixtures.ts
  comparison-grid-3.fixtures.ts
  verdict-per-use-case.fixtures.ts
  single-tool-spotlight.fixtures.ts
```

Each file exports:

```ts
export const proConVerdictFixtures = {
  characteristic: { /* article + brandTokens + overrides + generatedContent */ },
  edgeMin: { /* ... */ },
  edgeMax: { /* ... */ },
} as const;

export type ProConVerdictFixtureKey = keyof typeof proConVerdictFixtures;
```

### D.4 Baseline PNG storage

Baseline renders live in the test directory (not alongside fixtures):

```
packages/social/test/__baselines__/
  comparison-grid-4/
    characteristic/dark/slide-01.png … slide-04.png
    characteristic/light/slide-01.png … slide-04.png
    edge-min/dark/ …
    edge-max/dark/ …
  comparison-grid-3/ …
  verdict-per-use-case/ …
  single-tool-spotlight/ …
  pro-con-verdict/ …
```

160 slide PNGs total (5 templates × 3 fixtures × 2 themes × variable slides per template). **Gitignored** — generated on first `test:visual` run; not committed (binary files, 160 PNGs would bloat the repo). `.gitignore` entry: `/packages/social/test/__baselines__/`.

### D.5 Visual diff harness

The harness script (`packages/social/scripts/visual-render-all.ts`) has three modes:

```bash
bun run --cwd packages/social test:visual
# check mode: diffs rendered output against __baselines__/; exit 1 if any slide >0.1% diff

bun run --cwd packages/social test:visual:update
# update mode: re-renders all tuples and OVERWRITES __baselines__/

bun packages/social/scripts/visual-render-all.ts --out /tmp/x
# render-only mode: writes to custom dir, no diff
```

The harness calls `render-server.ts` functions directly (not via template `.render()`) — this avoids needing mock `Article`/`ArticleDiscovery` objects and keeps the harness self-contained. The script is not a Bun test file — it exits 0/1 and writes PNGs. The `test:visual` script wraps it in a `bun:test` file (`test/visual.test.ts`) gated on `RUN_VISUAL=1`.

Baseline updates are commit-reviewed. CI runs `test:visual` (read-only).

### D.6 Running the visual test in CI

```bash
RUN_VISUAL=1 bun test packages/social/test/visual.test.ts
```

Without `RUN_VISUAL=1`, the test is skipped (`it.skip`). This keeps `bun test` fast in normal development; visual regression only runs when explicitly requested or in CI.

### D.7 Bootstrap-time fixture presence check

`packages/social/src/templates/bootstrap.ts` checks every registered template's in-memory `mockFixtures` object for the three required keys before calling `templateRegistry.register()`:

```ts
function assertFixtures(t: TemplateDefinition<unknown>): void {
  if (!t.mockFixtures) throw new Error(`[Templates] ${t.key}: mockFixtures missing`);
  for (const key of ["characteristic", "edge-min", "edge-max"]) {
    if (!(key in t.mockFixtures)) {
      throw new Error(`[Templates] ${t.key}: mockFixtures missing required key "${key}"`);
    }
  }
}
```

This reads from the already-imported template objects (no dynamic import). Catches "I forgot to add a fixture" at boot, not at PR review.

### D.8 Discovered During Implementation (Sessions 3–4)

- **Fixture keys use `"edge-min"` and `"edge-max"` (kebab-case), not `edgeMin`/`edgeMax` (camelCase)** — The spec examples show camelCase. Actual `MockFixtureMap` is `Record<string, MockFixture>` with string keys, and the `fixtures-respect-bounds.test.ts` test iterates templates checking for `generatedContent` on each fixture, not by canonical key name. Use `"edge-min"` and `"edge-max"` to be consistent with the project's fixture naming convention.

## Section E — Retroactive Patches (4 existing templates)

### E.1 Scope

The four production templates pre-dating 59.3 (`comparison-grid-4`, `comparison-grid-3`, `verdict-per-use-case`, `single-tool-spotlight`) were built before this convention existed. They need:

1. **`*Bounds` object exported** alongside each `TemplateDefinition`, with numbers derived from current rendering behavior (audit step, see E.3)
2. **Zod schema for generated content** matching the bounds, wired into `generateContent()` return-value validation
3. **`getFontSize` adoption** — replace any inline font-size logic with bucket-table calls
4. **Composition skeleton review** — confirm or fix root-level fixed-px grid, no `flexGrow` at root
5. **3-fixture compliance** — confirm or fill missing fixtures (characteristic + edge-min + edge-max)
6. **Visual baseline PNGs committed**

`pro-con-verdict` (just landed in 59.3) is already mostly compliant by author-discipline; it only needs Section A formalization (extract `proConVerdictBounds` from in-prompt constants into the exported object) and the fixture audit.

### E.2 Per-template audit checklist

For each of the 4 existing templates, the implementer runs:

```
[ ] Find all LLM-produced fields (grep generateContent return)
[ ] Measure current "in-the-wild" max length per field across production data
[ ] Round up to nearest 10 → that's the new `max` bound
[ ] Inspect composition: list every text slot, classify by SlotType
[ ] Replace inline fontSize logic with getFontSize(text, slotType)
[ ] Inspect composition root: confirm fixed-px grid OR refactor
[ ] Run existing fixtures through visual harness, save as baselines
[ ] If fewer than 3 fixtures exist, add the missing ones (characteristic / edgeMin / edgeMax)
```

### E.3 Audit-first, refactor-second

Each template gets a **discovery session** before any code change. The implementer:

1. Greps for the template's `generateContent()` and lists every output field
2. Queries `social_posts.content` for the last 50 renders of this template, extracts each field, finds max observed length
3. Inspects the composition file structure, lists slot types
4. Produces a 1-page audit note: bounds derived, slot types found, current font-size approach, current fixture count

Then refactor. Audit prevents "I'll just guess the bounds" which leads to bounds that reject existing-content edge cases.

### E.4 Per-template sub-sections

- **E.4.1 comparison-grid-4** — likely the most complex (4 tool slots × multiple fields each). Expect 8-12 bounded fields.
- **E.4.2 comparison-grid-3** — same shape, smaller grid. Mostly mechanical translation from E.4.1 patterns.
- **E.4.3 verdict-per-use-case** — variable use-case count is the layout-shift risk. Likely needs `useCases.max` bound + Section C.6 fixed-slot list pattern.
- **E.4.4 single-tool-spotlight** — fewest fields, simplest layout. Quick audit, mostly a Zod-schema wrap.

### E.5 No visual change

The retro patches must produce **identical PNG output** to pre-patch for the current production fixtures. The visual harness running against pre-patch baselines is the regression gate.

If a patch incidentally changes a font-size or spacing, that's a *visual change* and belongs in Spec 60, not here. 59.3.5 is structural-and-types only.

**Exception**: if the audit finds that a template *was already shifting* across fixtures (a latent bug), fixing it is in scope. The new baseline replaces the inconsistent one. Document the change in E.6.

### E.6 Discovered During Implementation (Sessions 3–4)

- **`getFontSize` NOT applied to `ToolSlideStunning`** — The spec said "refactor compositions to use `getFontSize`". But `ToolSlideStunning.tsx` hardcodes `tagline=36px`, `starStrength=38px`, `regularStrengths=30px`. None of these match any existing bucket entry (slot-body: 40px/32px; list-item: 36px/28px; slot-headline: 56px/40px). Applying getFontSize would change pixel output, violating E.5 ("no visual change"). `slotMap: {}` is declared with all four templates — Session 5 or Spec 60 should add the missing bucket entries and wire getFontSize to ToolSlideStunning properly.

- **`comparison-grid-3` was sharing `comparison-grid-4`'s fixture file** — `comparisonGrid3.ts` was importing `COMPARISON_STUNNING_FIXTURES` from `comparisonGrid4.fixtures.ts`. That file had 2-tool fixtures, making the 3-tool grid completely untestable. Session 3 created `comparisonGrid3.fixtures.ts` with 3-tool data. ## Section F — LLM-Output Validation Layer

### F.1 Principle

**Every `generateContent()` return value passes through Zod-parse before reaching the composition.** On parse failure, the pipeline either reprompts the LLM with the error message, or fails the render with a 422 (for batch jobs) / surfaces to the user (for manual jobs).

### F.2 The validation wrapper

A shared helper at `packages/social/src/templates/validateGenerated.ts`:

```ts
import { z } from "zod";

export interface ValidationConfig<T> {
  schema: z.ZodType<T>;
  maxReprompts: number;       // default 1
  onValidationFailure: "reprompt" | "truncate" | "throw";  // default "reprompt"
}

export async function validateAndReprompt<T>(
  initialOutput: unknown,
  reprompt: (errorHints: string[]) => Promise<unknown>,
  config: ValidationConfig<T>,
): Promise<T> {
  let attempt = 0;
  let current = initialOutput;

  while (attempt <= config.maxReprompts) {
    const result = config.schema.safeParse(current);
    if (result.success) return result.data;

    const hints = result.error.issues.map(formatHint);

    if (attempt === config.maxReprompts) {
      if (config.onValidationFailure === "truncate") {
        return truncateToFit(current, config.schema);
      }
      throw new ContentValidationError(hints);
    }

    current = await reprompt(hints);
    attempt++;
  }

  throw new ContentValidationError(["Exhausted reprompts"]);
}
```

### F.3 Wiring per template

Each template's `generateContent()` ends with:

```ts
const rawOutput = await llmCall(prompt);
return validateAndReprompt(
  rawOutput,
  (hints) => llmCall(rebuildPromptWithHints(prompt, hints)),
  {
    schema: proConVerdictGeneratedSchema,
    maxReprompts: 1,
    onValidationFailure: "reprompt",
  },
);
```

One reprompt is the default. Two LLM calls is acceptable cost; three is wasteful — if the bounds are right, one reprompt with explicit error hints almost always succeeds.

### F.4 Error-hint formatting

The hint string fed back to the LLM is specific and actionable:

```ts
function formatHint(issue: z.ZodIssue): string {
  // e.g. "Feld 'verdictSnippet' ist zu lang (105 Zeichen). Maximum: 80. Kürze es."
  if (issue.code === "too_big" && issue.type === "string") {
    return `Feld '${issue.path.join(".")}' ist zu lang (${issue.maximum + 1}+ Zeichen). Maximum: ${issue.maximum}. Kürze es.`;
  }
  if (issue.code === "too_small" && issue.type === "string") {
    return `Feld '${issue.path.join(".")}' ist zu kurz (${issue.minimum - 1} Zeichen). Minimum: ${issue.minimum}. Erweitere es.`;
  }
  // ... per issue code
}
```

Hint locale follows the LLM prompt locale (German for DE pipelines, English for EN). Generate via a per-locale formatter rather than hardcoded strings.

### F.5 Failure modes

| Failure | Behavior |
|---|---|
| LLM returns valid JSON, but field too long | Reprompt with length hint |
| LLM returns invalid JSON | Existing JSON-extraction logic (`raw.indexOf("{") / lastIndexOf("}")`) catches this; if still invalid, treat as validation failure |
| Reprompt exhausted | `ContentValidationError` thrown; render job fails with status `failed`, error stored in `pipeline_runs.error` |
| Test fixtures fail validation | Build fails — fixtures must respect their own template's bounds |

### F.6 No silent truncation in production path

`onValidationFailure: "truncate"` exists for emergency / batch-recovery scenarios but is **not** the default. Truncation hides the underlying problem (bound too tight, prompt unclear, model regressing). Reprompt-then-fail surfaces it.

### F.7 Discovered During Implementation

- **`validateAndReprompt` is called with the raw-LLM schema, not the transformed schema.** Section F.3's code example shows `proConVerdictGeneratedSchema` (camelCase, verdict-only) passed to `validateAndReprompt`. In practice, `validateAndReprompt` is called with `llmResponseSchema` (snake_case, full LLM response shape) because validation happens *before* the JSON-to-TypeScript field renaming. The `proConVerdictGeneratedSchema` is used only by the fixture test. Rule: always validate LLM output in the *LLM's key format* (snake_case if that's what the prompt requests), then transform.
- **`onValidationFailure: "truncate"` in the config does not actually truncate — it still throws** (with a different message noting truncation was attempted). Actual in-composition truncation happens via `WebkitLineClamp`, which is the intended last-resort safety net. The "truncate" option in `ValidationConfig` exists for future batch-recovery use; it should not be used in the current production path.

### G.5 Discovered During Implementation

- **`bootstrapTemplates()` must be called explicitly in test files** — importing `bootstrap.ts` as a side-effect module does not register templates. Both test scaffolds require `import { bootstrapTemplates } from "../src/templates/bootstrap"; bootstrapTemplates();` at the top of the test file.
- **Test runner must be invoked from workspace root.** Running `bun test` from `packages/social/` with relative path filters fails ("no matching files"). All test invocations must be run from the monorepo root: `bun test packages/social/test/...`
- **Session 5 full CLAUDE.md authoring is the right moment** — detailed composition skeleton docs and cross-links were deferred to Session 5 (visual harness + CI). Sessions 1–2 only needed the TEMPLATES/CLAUDE.md gotcha section and the compositions stub. Don't front-load Session 5 docs work.
- **`fileURLToPath` is in `node:url`, not `node:path` in Bun** — importing it from `node:path` throws `SyntaxError: Export named 'fileURLToPath' not found in module 'node:path'` at runtime. Always `import { fileURLToPath } from "node:url"`.
- **Heterogeneous `TemplateDefinition<T>[]` arrays require `as unknown as TemplateDefinition<unknown>[]`** — TypeScript infers the array type as a union `TemplateDefinition<A> | TemplateDefinition<B> | ...` which makes generic calls like `register<T>(t)` fail with "not assignable". Cast the whole array once: `const templates = [...] as unknown as TemplateDefinition<unknown>[];`. Add a justification comment explaining `assertFixtures` / `register` only read non-generic fields.
- **Visual harness calls render-server functions directly, not `template.render()`** — calling `template.render()` requires a full `RenderContext` including a mock `Article` DB row, which is complex to construct. The harness bypasses this by importing render-server functions directly and building composition inputs inline. This is intentional: the harness tests composition rendering, not the `buildInput` adapter layer.
