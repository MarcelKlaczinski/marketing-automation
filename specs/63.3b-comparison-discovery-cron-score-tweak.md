# Spec 63.3b — ComparisonDiscovery Cron + Score-Formel-Tweak + Routing-Fix

_Theme 63 Sub-Spec — automatisiert wöchentliche ComparisonDiscovery, verschärft den Score-Filter gegen cross-category Pairs, fixt Routing für intent_type='comparison' Trend-Briefs._
_Status: Draft._
_Voraussetzung: 63.3a manual run hat verifiziert dass Algorithmus brauchbare Pairs liefert (4 net-new pairs, 50% strong yield)._

---

## 1. Ziel

Drei zusammenhängende Verbesserungen am ComparisonDiscovery-Pfad:

1. **Score-Formel-Tweak** — categoryOverlap-Gewicht 0.2 → 0.4 + Cross-Category-Penalty. Drückt Cross-Category-Pairs runter, hält Same-Category-Pairs oben.
2. **Pending-Default** — neue Briefs landen mit `status='pending'`, Marcel reviewt im UI vor Plan-Eintritt. Doppel-Safety unabhängig vom Score-Tweak.
3. **Weekly Cron** — automatisiert Trigger Sonntags pre-Plan-Run.
4. **A.3 Routing-Fix** — Trend-Briefs mit `intent_type='comparison'` landen jetzt im Comparison-Bucket statt Cluster-Bucket.

**In Scope:**
- Score-Formel anpassen in `packages/planner/src/comparison-discovery.ts`
- Pending-Default-Verifikation (vermutlich schon so)
- Neuer Cron-Job-Type `comparison_discovery` analog `planner_weekly_generation` (62.7 Pattern)
- Routing-Fix in `packages/pipelines/src/planning/steps/select-floor-items.ts` (matchBriefToContentType)
- Cron-Toggle in SettingsPlannerPage UI

**Out of Scope:**
- ComparisonDiscovery-Algorithmus radikal umbauen (Score-Tweak ist minimal)
- Auto-Approve-Mechanismus
- Pair-Filter erweitern (Marcel-Review via Pending übernimmt das)
- Andere Cron-Job-Types

**Aufwand:** 0.5-1 Tag.

## 2. Architektur-Entscheidungen

### 2.1 Score-Formel-Tweak

Aktuell (per 63.3a Discovery):
```
score = (coMentionCount / maxCoMention) * 0.6 
      + (categoryOverlap ? 0.2 : 0) 
      + recencyBoost * 0.2
```

Neu:
```
score = (coMentionCount / maxCoMention) * 0.4 
      + (categoryOverlap ? 0.4 : -0.1) 
      + recencyBoost * 0.2
```

Änderungen:
- coMention-Gewicht: 0.6 → 0.4 (weniger pure popularity)
- categoryOverlap: 0.2 → 0.4 (Same-Category-Bonus verdoppelt)
- Cross-Category-Penalty: -0.1 (war: 0)
- recencyBoost: unverändert 0.2

**Effekt auf 63.3a-Daten (Simulation):**
| Pair | alter Score | neuer Score | Threshold 0.3 |
|---|---|---|---|
| ChatGPT/Claude (covered) | (28/28)·0.6 + 0.2 + 0.2 = 1.0 | (28/28)·0.4 + 0.4 + 0.2 = **1.0** | über |
| ChatGPT/Perplexity | (10/28)·0.6 + 0 + 0.2 = 0.414 | (10/28)·0.4 + 0 + 0.2 -0.1 = **0.243** | **drunter** |
| Claude/Perplexity | 0.414 | 0.243 | **drunter** |
| ChatGPT/DeepL | (8/28)·0.6 + 0 + 0.2 = 0.371 | (8/28)·0.4 + 0 + 0.2 -0.1 = **0.214** | **drunter** |
| Claude/DeepL | 0.371 | 0.214 | **drunter** |

**Achtung:** Bei der Simulation fallen ALLE 4 net-new Pairs unter Threshold weil keiner categoryOverlap hat. Das ist zu hart.

**Alternative-Simulation:** Threshold senken parallel zum Tweak.
| Threshold | über Threshold |
|---|---|
| 0.3 | nur covered pairs (chatgpt/claude etc.) |
| 0.25 | + ChatGPT/Perplexity (0.243 — knapp drunter) |
| 0.2 | + ChatGPT/Perplexity, Claude/Perplexity, ChatGPT/DeepL, Claude/DeepL |
| 0.15 | wahrscheinlich auch noise weiter unten |

**Pragmatisch:** entweder Penalty schwächer (`-0.05` statt `-0.1`) oder Threshold senken auf 0.25.

**Empfehlung Implementor:** beide Knobs konfigurierbar machen, dann probiert Marcel post-merge welche Kombi am besten passt. Default: `categoryOverlap=0.4`, `crossCategoryPenalty=0.05`, `minScore=0.3`. Verändert Same-Category-Bonus deutlich, Cross-Category leicht runter, behält Perplexity-Pairs als Borderline-Kandidaten.

**Aber:** Phase 0 Discovery: Score-Formel komplett im Code anschauen, Konstanten finden, Vorschlag vor Implementation für Marcel approval präsentieren.

### 2.4 Routing-Fix (A.3)

In `packages/pipelines/src/planning/steps/select-floor-items.ts` `matchBriefToContentType`:

**Aktuell:**
```ts
if (brief.source === 'comparison_discovery' || brief.clusterAction === 'comparison') {
  return 'comparison';
}
```

**Neu:**
```ts
if (
  brief.source === 'comparison_discovery' 
  || brief.clusterAction === 'comparison'
  || brief.intentType === 'comparison'  // NEU
) {
  return 'comparison';
}
```

**Caveat von 63.3a Discovery:**
> "Trend-comparison-Briefs haben oft keine konkreten Tool-Slugs in comparisonToolSlugs"

Heißt: ein Brief mit `intent_type='comparison'` aber ohne `comparisonToolSlugs` könnte zu einem comparison-Plan-Item routen, das aber nicht zu den comparison-Templates passt (die brauchen 3-4 konkrete Tools).

**Mitigation:** im Routing-Fix zusätzlich prüfen `metadata->>'comparisonToolSlugs'` ist NOT NULL:

```ts
if (
  brief.source === 'comparison_discovery' 
  || brief.clusterAction === 'comparison'
  || (
    brief.intentType === 'comparison' 
    && brief.metadata?.comparisonToolSlugs?.length >= 2
  )
) {
  return 'comparison';
}
```

Sicher dass Trend-comparison-Briefs nur dann zu Comparison-Bucket gehen wenn sie wirklich Tool-Comparison-fähig sind.

### 4.1 Score-Formel anpassen

Discovery: aktuelle Score-Formel-Konstanten finden:
```bash
grep -A 20 "computeScore\|scoreFor\|coMentionCount.*0.6" packages/planner/src/comparison-discovery.ts
```

Anpassen mit den drei Konstanten:
```ts
const COMENTION_WEIGHT = 0.4;        // war 0.6
const CATEGORY_OVERLAP_BONUS = 0.4;  // war 0.2
const CROSS_CATEGORY_PENALTY = 0.05; // war 0
const RECENCY_WEIGHT = 0.2;          // unverändert

function computePairScore(pair: PairCandidate): number {
  return (
    (pair.coMentionCount / pair.maxCoMention) * COMENTION_WEIGHT
    + (pair.categoryOverlap ? CATEGORY_OVERLAP_BONUS : -CROSS_CATEGORY_PENALTY)
    + pair.recencyBoost * RECENCY_WEIGHT
  );
}
```

## 11. Discovered During Implementation

- **Trend briefs carry no structured tool-slug field.** Phase 0 grep showed `emit-brief.ts` produces only `trendMetadata` (no `comparisonToolSlugs`, no `metadata` JSON column at all). The TopicBrief schema has typed metadata buckets (`gapMetadata` / `trendMetadata` / `refreshMetadata` / `comparisonMetadata`) — there is no generic `metadata` field. Consequence: the routing-fix `intent_type='comparison'` rule never fires on current trend briefs, only on (future) sources that populate `comparisonMetadata`. The rule is forward-compat scaffolding rather than an immediate behaviour change.
- **Score-formula knobs benefit from explicit input fields.** Marcel explicitly wanted to retune post-merge. Exposing `coMentionWeight` / `categoryOverlapBonus` / `crossCategoryPenalty` / `recencyWeight` on `DiscoverComparisonPairsInput` lets a `POST /comparison-discovery/run` body re-tune live without a deploy.
- **Test fixtures fan-out on `ProjectPlannerConfig` widening.** Adding the 3 `comparison_cron_*` NOT NULL columns broke 2 pipeline test fixtures (`budget-gate-step.test.ts`, `select-overage-items-step.test.ts`). Workspace typecheck caught both. Same shape as the existing memory rule about widening DB-derived types — no new rule needed.

## 12. Deviations from Spec

- **§2.4 routing guard field path.** Spec assumed `brief.metadata?.comparisonToolSlugs`. The actual schema has no `metadata` field — implemented as `getComparisonToolSlugs(brief)` helper reading `brief.comparisonMetadata?.toolASlug + toolBSlug` (the only structured tool-pair fields that exist today). Helper documents the forward-compat intent.
- **§3 migration numbering.** Spec said "008X / 008Y". Actual: `0080_comparison_discovery_cron_enum.sql` + `0081_comparison_discovery_cron_config.sql`.
- **§3.2 cron_state seed location.** Spec proposed seeding via SQL migration. Followed Memory D124 (canonical pattern from 62.7's 0076/0077): `ALTER TYPE` migration commits first, the `INSERT INTO cron_state` for each project happens in `seedComparisonDiscoveryCron()` at worker startup (idempotent via `onConflictDoNothing`). Plus per-project INSERT in `routes/projects.ts` so new projects pick it up immediately.
- **§4.1 cross-category penalty default.** Spec recommended `0.05` (text) but the simulation table used `0.1`. Went with `0.05` per the "pragmatic" recommendation — yields the borderline behaviour Marcel asked for (Perplexity-pairs stay just-under-threshold, retunable via input knobs).
- **§4.5 cron toggle blocker.** Spec implied symmetric "requires valid config" gate for both crons. Comparison-discovery cron is NOT gated — it only writes pending briefs (no planned_item, no cost expansion), so it can run independently of goal-validation errors. Documented inline in `comparisonCronHintText` comment.
- **§3.3 column naming.** Went with explicit `comparison_cron_*` prefix on `project_planner_config` (spec's pragmatic option) rather than introducing a generic `project_cron_config` table.
