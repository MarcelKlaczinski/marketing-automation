# Spec 54.1: TopicBrief & Source Abstraction

**Phase:** 54 / A — Foundations (1 of 3)
**Estimated Effort:** 1.5 days (~10-12 focused hours over 2-3 sessions)
**Dependencies:** Spec 49b/49c/49d (Gap Detection), Spec 54.0 (Content Planner ADR)
**Status:** Ready for implementation
**Recommended Model:** Sonnet 4.6 (schema + refactor work, no architectural novelty after the ADR)

---

## Goal

Introduce **TopicBrief** as the universal, explicit contract between any Topic Source (Gap Analysis today; Trend Discovery, Refresh Detection, Manual later) and the downstream Topic Routing Policy + Article Generator. Spec 54.1 delivers three things:

1. A new DB table `topic_briefs` with a polymorphic schema (source discriminator + source-specific JSONB metadata) and a Zod schema in `packages/db/src/schema/content.ts` exported for use across packages.
2. A small **TopicSource interface** (`packages/pipelines/src/topic-sources/`) with one concrete implementation: `GapAnalysisTopicSource`, which wraps the existing `DetectContentGapsStep` and emits TopicBriefs as a side-effect of detection.
3. **Dual-write semantics**: the existing gap-detection flow keeps writing `content_gaps` rows exactly as before AND emits a TopicBrief per detected gap. No consumer of the new table is built in this spec — Spec 54.3 is the first reader.

After this spec, every `POST /api/projects/:slug/detect-gaps` and every Astro-import-driven gap detection produces both a `content_gaps` row and a `topic_briefs` row. Existing UI and endpoints continue to function unchanged.

## What this is NOT

- Not refactoring `/api/projects/:slug/content-gaps/:id/generate` or `/automate` — those routes still read from `content_gaps.metadata`. Refactoring to read from `topic_briefs` is Spec 54.3.
- Not building the TopicRoutingPolicy — that is Spec 54.3.
- Not building Trend Discovery, Refresh Detection, or Manual sources — they come in 54.4/54.5 (Trend) and later specs.
- Not removing or deprecating `content_gaps` — both tables coexist throughout Theme 54.
- Not exposing TopicBriefs in the UI — they are an internal contract for now. UI surface is Spec 54.6 / 54.9.
- Not implementing the `approval_status` state machine in code — the column exists, but its only writer in this spec is the dual-write path (always `pending`).
- Not modifying the Article Generator — it still reads from `articles` and `cornerstone_specs`.
- Not implementing the `mode` field beyond storing it — interpretation by Article Generator is Spec 54.8.

## Architecture

### TopicSource as a thin interface, not a Pipeline

Topic Sources are intentionally **lighter** than the Pipeline framework (Spec 05). A `TopicSource` is a class with one method: `emit(input): Promise<TopicBrief[]>`. It MAY internally call `runPipeline()` (Gap Analysis does, via the existing `DetectContentGapsStep`), but it doesn't have to. Trend adapters in 54.4 will fetch from external APIs without the Pipeline wrapper — Pipelines are for multi-step orchestration with cost tracking, and a single RSS fetch doesn't need that overhead.

This keeps the abstraction honest: a Topic Source is "anything that produces TopicBriefs". The Pipeline framework is one way to implement that; not the only way.

### Why dual-write, not migrate-and-cut-over

The ADR (Section 3.1) committed to backward compatibility through Phases A and B. Concretely:
- The UI (`GapsPanel.vue`) reads `content_gaps` directly via `GET /api/projects/:slug/content-gaps`.
- The `/suggest` and `/generate` endpoints write to `content_gaps.metadata` and read from it.
- Pipeline chains (Spec 49d) reference gap_id, not brief_id.

Cutting over to TopicBriefs in one shot would require simultaneous changes in UI, routes, chains, and tests. That's the kind of multi-file change that breaks at midnight. Dual-write means: 54.1 adds the new path silently, 54.3 builds the first consumer (TopicRoutingPolicy), and only after 54.9 (UI redesign) does `content_gaps` become a candidate for deprecation.

### Source-specific metadata as polymorphic JSONB

The TopicBrief schema has three optional JSONB columns: `gap_metadata`, `trend_metadata`, `refresh_metadata`. Exactly one is non-null per row, determined by the `source` discriminator. Zod refinement enforces this invariant.

Alternatives considered:
- **Single `metadata` JSONB** discriminated by `source`: simpler, but loses the per-source TypeScript narrowing benefits. Rejected.
- **Separate tables per source** (`gap_briefs`, `trend_briefs`): forces joins and a union view to query "all open briefs". Rejected.
- **Inheritance via `topic_briefs` + extension tables**: classic SQL polymorphism, more rigorous but adds 4 tables and FK complexity. Overkill at this scale.

Polymorphic JSONB with Zod refinement is the pragmatic middle ground — used elsewhere in the codebase (e.g., `content_gaps.metadata`, `pipeline_chains.step_runs`).

### Brief lifecycle in 54.1

```
detect-content-gaps runs
  ├── existing: upsert content_gaps row (status: open | restamped | resolved)
  └── NEW: for each gap row that's open or restamped, upsert topic_brief row
            (status: pending; approval_required: true; gap_id FK set)

resolve flow (existing code, untouched in 54.1):
  content_gaps.status → resolved | dismissed
  └── NEW (small hook): mark corresponding topic_brief as superseded
```

No new state transitions are exposed via API in 54.1. The brief's lifecycle is owned by the same code path that owns the gap's lifecycle. When 54.3 lands, the routing policy becomes a brief writer too (status: routed).

### File coordination — atomicity of dual-write

Both writes happen inside the existing `db.transaction(...)` block in `detect-content-gaps.ts`. If the gap insert fails, the brief insert is rolled back, and vice versa. This is the single most important invariant of this spec: **a gap and its brief are created or not created together**. The test suite must cover the rollback case.

```sql
CREATE TABLE topic_briefs (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id           UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,

  -- Source discriminator
  source               TEXT NOT NULL CHECK (source IN (
                         'gap_analysis', 'trend_discovery',
                         'refresh_detection', 'manual'
                       )),

  -- Back-reference to originating gap (only when source='gap_analysis')
  gap_id               UUID REFERENCES content_gaps(id) ON DELETE SET NULL,

  -- Topic identity
  topic_title          TEXT NOT NULL,
  primary_keyword      TEXT,
  secondary_keywords   JSONB NOT NULL DEFAULT '[]'::jsonb,
  locale               TEXT,                                 -- 'de' | 'en' | NULL
  intent_type          TEXT,                                 -- from project config taxonomy

  -- Cluster context
  cluster_id           UUID REFERENCES clusters(id) ON DELETE SET NULL,
  cluster_action       TEXT NOT NULL CHECK (cluster_action IN (
                         'append_to_existing', 'create_new',
                         'translation', 'refresh', 'standalone'
                       )),

  -- SEO input
  search_volume_de     INTEGER,
  search_volume_en     INTEGER,
  difficulty           INTEGER,
  serp_snapshot        JSONB,                                -- top results, featured snippets

  -- Generation hints (filled by source or by /suggest in 54.3)
  suggested_title      TEXT,
  suggested_slug       TEXT,
  suggested_meta       TEXT,
  hero_image_prompt    TEXT,
  generation_mode      TEXT CHECK (generation_mode IS NULL OR generation_mode IN (
                         'evergreen', 'timely', 'pillar',
                         'spoke', 'refresh', 'translation'
                       )),

  -- Approval & automation
  approval_required    BOOLEAN NOT NULL DEFAULT TRUE,
  approval_status      TEXT NOT NULL DEFAULT 'pending' CHECK (approval_status IN (
                         'pending', 'approved', 'rejected',
                         'auto_approved', 'superseded', 'routed'
                       )),
  approved_by          TEXT,                                 -- UUID (user) | 'rule:<id>'
  approved_at          TIMESTAMPTZ,

  -- Source-specific metadata (exactly one non-null, enforced by Zod refinement)
  gap_metadata         JSONB,
  trend_metadata       JSONB,
  refresh_metadata     JSONB,

  -- Audit
  created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX topic_briefs_unique_open_per_gap
```

```typescript
  suggestedSlug: z.string().nullable().optional(),
  suggestedMeta: z.string().nullable().optional(),
  heroImagePrompt: z.string().nullable().optional(),
  generationMode: z.enum([
    "evergreen", "timely", "pillar", "spoke", "refresh", "translation",
  ]).nullable().optional(),

  approvalRequired: z.boolean().default(true),
  approvalStatus: z.enum([
    "pending", "approved", "rejected",
    "auto_approved", "superseded", "routed",
  ]).default("pending"),
  approvedBy: z.string().nullable().optional(),
  approvedAt: z.date().nullable().optional(),

  gapMetadata: GapMetadataSchema.nullable().optional(),
  trendMetadata: TrendMetadataSchema.nullable().optional(),
  refreshMetadata: RefreshMetadataSchema.nullable().optional(),

  // Exactly one of (gap | trend | refresh) metadata must be non-null,
  // matching the source discriminator. Manual source has no metadata.
  const counts = {
    gap: data.gapMetadata != null ? 1 : 0,
    trend: data.trendMetadata != null ? 1 : 0,
    refresh: data.refreshMetadata != null ? 1 : 0,
  };
  const total = counts.gap + counts.trend + counts.refresh;
  if (data.source === "manual" && total !== 0) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: "Manual source must have no source-specific metadata",
    });
  }
  if (data.source !== "manual" && total !== 1) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: `Source '${data.source}' requires exactly one matching metadata field`,
    });
  }
  const expectedField = {
    gap_analysis: "gap",
    trend_discovery: "trend",
    refresh_detection: "refresh",
    manual: null,
  }[data.source];
  if (expectedField && counts[expectedField as keyof typeof counts] !== 1) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: `Source '${data.source}' requires '${expectedField}_metadata' to be set`,
    });
  }
  // gapId must be set iff source='gap_analysis'
  if (data.source === "gap_analysis" && !data.gapId) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: "gap_analysis briefs require gapId",
    });
  }
  if (data.source !== "gap_analysis" && data.gapId) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: "Only gap_analysis briefs may set gapId",
    });
  }
});
```

### TopicSource Interface

`packages/pipelines/src/topic-sources/types.ts`:

```typescript
import { z } from "zod";
import type { TopicBriefInsert } from "@marketing-auto/db";

/**
 * A TopicSource produces TopicBriefs.
 *
 * Implementations MAY use the Pipeline framework internally (Gap Analysis does)
 * or call external APIs directly (Trend adapters in 54.4 will). The interface
 * is intentionally minimal: one method, one return type.
 *
 * Sources are identified by their `source` discriminator, which must match
 * one of the TopicBrief source enum values.
 */
export interface TopicSource<Input = unknown> {
  readonly source: TopicBriefInsert["source"];
  readonly inputSchema: z.ZodType<Input>;

  /**
   * Produce zero or more TopicBriefs from the given input.
   *
   * Implementations:
   * - MUST NOT persist briefs themselves. The caller (wrapping route, worker,
   *   or import step) decides when to persist, allowing transactional dual-write.
   * - SHOULD be idempotent w.r.t. input: calling emit() twice with identical
   *   input should produce equivalent briefs (modulo timestamps).
   * - MAY return an empty array if nothing was found.
   */
  emit(input: Input, ctx: TopicSourceContext): Promise<TopicBriefInsert[]>;
}

export interface TopicSourceContext {
  readonly projectId: string;
  readonly pipelineRunId?: string;
}
```

```typescript
import type { ContentGap, TopicBriefInsert, GapMetadata } from "@marketing-auto/db";

/**
 * Pure mapper from a ContentGap row to a TopicBriefInsert.
 *
 * No DB calls, no LLM, no side effects. Tested in isolation.
 */
export function mapGapToBrief(gap: ContentGap): TopicBriefInsert {
  const clusterAction = inferClusterAction(gap);
  const generationMode = inferGenerationMode(gap);

  const gapMetadata: GapMetadata = {
    gapType: gap.gapType as GapMetadata["gapType"],
    priority: gap.priority,
    // Carry-over from existing metadata (may be undefined)
    clusterName: (gap.metadata as any)?.clusterName,
    clusterMemberCount: (gap.metadata as any)?.clusterMemberCount,
    existingLocale: (gap.metadata as any)?.existingLocale,
    existingArticleSlug: (gap.metadata as any)?.existingArticleSlug,
    spokesPresent: (gap.metadata as any)?.spokesPresent,
    translationKey: gap.translationKey ?? undefined,
    suggestedCornerstoneKeyword: (gap.metadata as any)?.suggestedCornerstoneKeyword,
    discoveredKeywords: (gap.metadata as any)?.discoveredKeywords,
  };

  const topicTitle = buildTopicTitle(gap);

  return {
    projectId: gap.projectId,
    source: "gap_analysis",
    gapId: gap.id,

    topicTitle,
    primaryKeyword: gapMetadata.suggestedCornerstoneKeyword ?? null,
    secondaryKeywords: gapMetadata.discoveredKeywords ?? [],
    locale: (gap.locale as "de" | "en" | null) ?? null,
    intentType: gap.intentType ?? null,

    clusterId: gap.clusterId ?? null,
    clusterAction,

    generationMode,

    approvalRequired: true,
    approvalStatus: "pending",

    gapMetadata,
  };
}

function inferClusterAction(gap: ContentGap): TopicBriefInsert["clusterAction"] {
  switch (gap.gapType) {
    case "missing_hub":           return "append_to_existing";  // hub joins existing cluster
    case "missing_spoke_type":    return "append_to_existing";
    case "cluster_too_small":     return "append_to_existing";
    case "missing_translation":   return "translation";
    default:                      return "append_to_existing";
  }
}

function inferGenerationMode(gap: ContentGap): TopicBriefInsert["generationMode"] {
  if (gap.gapType === "missing_hub") return "pillar";
  if (gap.gapType === "missing_translation") return "translation";
  return "spoke";
}

function buildTopicTitle(gap: ContentGap): string {
  const meta = gap.metadata as any;
  const cluster = meta?.clusterName ?? "unknown cluster";
  switch (gap.gapType) {
    case "missing_hub":
      return `Pillar article for cluster "${cluster}"`;
    case "missing_spoke_type":
      return `${gap.intentType ?? "spoke"} article for cluster "${cluster}"`;
    case "missing_translation":
      return `Translate "${meta?.existingArticleSlug ?? "article"}" to ${gap.locale}`;
    case "cluster_too_small":
      return `Additional spoke for cluster "${cluster}"`;
    default:
      return `Topic for cluster "${cluster}"`;
  }
}
```

```typescript
import { z } from "zod";
import type { ContentGap, TopicBriefInsert } from "@marketing-auto/db";
import type { TopicSource, TopicSourceContext } from "../types.ts";
import { mapGapToBrief } from "./map-gap-to-brief.ts";

const InputSchema = z.object({
  gaps: z.array(z.unknown()),  // typed as ContentGap[] in the implementation
});

export class GapAnalysisTopicSource
  implements TopicSource<{ gaps: ContentGap[] }>
{
  readonly source = "gap_analysis" as const;
  readonly inputSchema = InputSchema as unknown as z.ZodType<{ gaps: ContentGap[] }>;

  async emit(
    input: { gaps: ContentGap[] },
    _ctx: TopicSourceContext,
  ): Promise<TopicBriefInsert[]> {
    // Filter out resolved/dismissed gaps — only open/in_progress get briefs
    const eligible = input.gaps.filter((g) =>
      g.status === "open" || g.status === "in_progress",
    );
    return eligible.map(mapGapToBrief);
  }
}
```

```markdown
# Topic Sources

A TopicSource produces TopicBriefs. See `types.ts` for the interface contract.

## Adding a new source

1. Pick a `source` discriminator value (must match the DB enum).
2. Define a source-specific metadata Zod schema in `@marketing-auto/db`.
3. Implement the `TopicSource` interface in a new subfolder.
4. Wire it into the caller (a route, worker, or import step) that decides when
   to invoke `emit()` and persist the result.

Sources do NOT persist briefs themselves — the caller owns persistence so that
dual-write transactions (e.g., gap + brief in one tx) remain atomic.
```

### Dual-Write Hook in detect-content-gaps.ts

`packages/adapters/astro-sync/src/import/steps/detect-content-gaps.ts` — add to the existing transaction block:

```typescript
// Existing code (abridged):
const result = await db.transaction(async (tx) => {
  // ... existing fingerprint matching, upsert, restamping, resolution logic ...

  const upserted: ContentGap[] = await upsertGaps(tx, fingerprintToGap);
  const restamped: ContentGap[] = await restampGaps(tx, existingGaps);
  const resolved: ContentGap[] = await resolveGaps(tx, gapsToResolve);

  // NEW: dual-write topic briefs for open/restamped gaps
  const source = new GapAnalysisTopicSource();
  const briefs = await source.emit(
    { gaps: [...upserted, ...restamped] },
    { projectId: input.projectId },
  );

  if (briefs.length > 0) {
    await tx.insert(topicBriefs)
      .values(briefs)
      // Upsert by (gap_id) for open/routed states — see unique index
      .onConflictDoUpdate({
        target: topicBriefs.gapId,
        where: sql`${topicBriefs.approvalStatus} IN ('pending', 'approved', 'auto_approved', 'routed')`,
        set: {
          // Refresh derived fields if the gap's metadata changed
          topicTitle: sql`EXCLUDED.topic_title`,
          gapMetadata: sql`EXCLUDED.gap_metadata`,
          updatedAt: sql`NOW()`,
        },
      });
  }

  // NEW: mark briefs as superseded for resolved gaps
  if (resolved.length > 0) {
    await tx.update(topicBriefs)
      .set({ approvalStatus: "superseded", updatedAt: new Date() })
      .where(and(
        inArray(topicBriefs.gapId, resolved.map((g) => g.id)),
        inArray(topicBriefs.approvalStatus, ["pending", "approved", "auto_approved"]),
      ));
  }

  return { gapsCreated, gapsRestamped, gapsResolved, totalOpen };
});
```

The same pattern applies in `apps/api/src/routes/projects.ts` for the manual `POST /detect-gaps` route (it shares the same helper functions).

### API Resolve / Dismiss Hooks

In `apps/api/src/routes/projects.ts`, the existing `PATCH /:slug/content-gaps/:id` route updates `content_gaps.status`. Extend it to mirror the change to briefs:

```typescript
// Inside the existing PATCH handler, after the content_gaps update:
if (newStatus === "resolved" || newStatus === "dismissed") {
  await tx.update(topicBriefs)
    .set({ approvalStatus: "superseded", updatedAt: new Date() })
    .where(and(
      eq(topicBriefs.gapId, gapId),
      inArray(topicBriefs.approvalStatus, ["pending", "approved", "auto_approved"]),

}
```

No new endpoint is added. The brief mirror happens silently.

## Open Questions / Decisions Made

**Decision 1: TopicSource is an interface, not a Pipeline.**
Pipelines (Spec 05) are heavyweight — cost tracking, step orchestration, pipeline_runs rows. A TopicSource may be as simple as a 10-line RSS fetcher. Forcing it through Pipeline would add overhead for no benefit. Sources MAY internally use Pipelines (Trend Discovery in 54.5 will), but the source interface itself stays minimal.

**Decision 2: Sources do not persist briefs; the caller does.**
The caller (detect-gaps step, manual endpoint, future trend worker) owns the transaction. This is essential for dual-write atomicity: in 54.1, the gap and the brief must be inserted in the same transaction. A source that persists internally would break that invariant.

**Decision 3: Dual-write, not migrate-and-cut-over.**
Cutting over `content_gaps` to `topic_briefs` in one shot would require simultaneous changes across UI, routes, chains, and tests. ADR Section 3.1 committed to backward compatibility through Phase A and B. Dual-write is the cost of that commitment: every gap-detection produces both writes, but no consumer of the new table exists until 54.3.

**Decision 4: Polymorphic JSONB metadata, not extension tables.**
Three nullable JSONB columns (`gap_metadata`, `trend_metadata`, `refresh_metadata`) with Zod refinement enforcing exactly-one-non-null. Alternatives (single discriminated JSONB; separate extension tables) traded clarity for tooling complexity. The polymorphic-JSONB pattern is already used elsewhere in the codebase.

**Decision 5: `mapGapToBrief` is pure.**
No DB, no LLM, no I/O. This lets us unit-test all gap-type → brief-shape mappings deterministically, without DB fixtures.

**Decision 6: Resolved/dismissed gaps mark briefs as `superseded`, not delete them.**
Auditability — once 54.3 starts routing briefs, we want to track "this brief was created, then superseded before approval". Deletion would lose that history. The `superseded` status also keeps the unique-per-gap partial index clean (terminal states are excluded).

**Decision 7: `approval_status` enum includes `routed` even though no code writes it in 54.1.**
Forward declaration. 54.3 will write `routed` when the TopicRoutingPolicy hands a brief off to a pipeline. Including the value in the enum now avoids a migration in 54.3.

**Decision 8: No `topic_briefs` exposure in any API endpoint in 54.1.**
The table is internal until 54.3. The temptation to add `GET /topic-briefs` for "debugging" would create a public contract before we're sure about the shape. Use direct SQL or psql for inspection during 54.1.

**Decision 9: FK declared via raw SQL migration, not Drizzle `references()`.**
`content_gaps` and `topic_briefs` live in the same schema file; Drizzle's `references()` with forward declarations is awkward. Raw SQL FK avoids the ordering dance.

**Decision 10: No `pipeline_runs` row for source emission.**
The gap-detection step already creates a `pipeline_runs` row (existing behavior). Adding a separate run for the source emission would double-count. Cost is zero anyway (no LLM, no DataForSEO).

## Discovered During Implementation

**`ContentGap` / `NewContentGap` type aliases were not exported from `@marketing-auto/db`.**
The `contentGaps` table existed but had no `$inferSelect` / `$inferInsert` aliases. Callers in
`packages/pipelines` and `packages/adapters/astro-sync` were forced to use inline
`import("@marketing-auto/db").ContentGap` type annotations inside function bodies (non-idiomatic).
Added `ContentGap` and `NewContentGap` to `content.ts` alongside the table. Added a Conventions
rule to `packages/db/CLAUDE.md`: every new table must export both type aliases at definition time.

**`gap.metadata` is already typed as `ContentGapMetadata` — no cast needed.**
Initial implementation cast `gap.metadata` to `Record<string, unknown>` and then re-cast each
field back. Because the column is declared `.$type<ContentGapMetadata>()`, fields like
`gap.metadata?.clusterName` are already `string | undefined`. The cast was removed in the review
pass; `locale` (plain `text` column, not narrowed to `"de"|"en"`) is the only cast that remains.

**Zod `.optional()` × Drizzle `exactOptionalPropertyTypes` conflict on insert.**
`TopicBriefInsert = z.infer<typeof TopicBriefInsertSchema>` has optional fields typed
`T | undefined`. Drizzle's insert type expects `T | null` — TypeScript rejects the array
under `exactOptionalPropertyTypes`. Fix: strip undefined entries before passing to `.values()`:
```typescript
Object.fromEntries(Object.entries(b).filter(([, v]) => v !== undefined))
  as Array<typeof topicBriefs.$inferInsert>
```
Safe because `mapGapToBrief` always uses explicit `null` (never `undefined`) for absent fields.
Added as a `DO NOT` to `packages/db/CLAUDE.md`.

## Deviations

**No existing `db.transaction()` block in `detect-content-gaps.ts`.**
The spec assumed the write path was already wrapped in a transaction. It was not — each gap
insert/update was a standalone `await db.update/insert(...)`. We created the transaction from
scratch, wrapping steps 5 (insert/restamp), 6 (resolve), and the new brief writes together. The
atomicity invariant is satisfied; the implementation matches the spec's intent exactly.

**`targetWhere` instead of `where` in `onConflictDoUpdate`.**
The spec pseudocode used `where: sql\`...\`` on `onConflictDoUpdate`, which in Drizzle is the
*update* condition. To match a partial unique index, the correct Drizzle API is `targetWhere`
(the index predicate). We used `targetWhere: sql\`approval_status IN (...)\`` which generates
the correct `ON CONFLICT (gap_id) WHERE approval_status IN (...) DO UPDATE SET ...` SQL.

**Drizzle operators in `detect-content-gaps.ts` and `projects.ts` imported from `drizzle-orm` (pre-existing).**
Both files already imported `and`, `eq`, `inArray` from `drizzle-orm` (violating the
workspace-wide rule to import from `@marketing-auto/db`). The new code added in this spec reuses
those existing imports rather than introducing a second import source in the same file, which
would cause Drizzle type-incompatibility errors. Fixing the pre-existing violation is out of
scope for 54.1.
