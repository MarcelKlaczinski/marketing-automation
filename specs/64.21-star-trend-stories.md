## 1. Problem

GitHub repos in the inventory table accumulate star counts over time. A spike in stars ("X gained 10k stars this quarter") is a strong editorial signal — it indicates a tool just hit mainstream attention and is worth a "Why is X exploding?" story. Pre-64.21 we tracked the current `starsCount` but had no time-series to compare against, so the trend signal was invisible.

## 2. Ziel (Scope)

**In scope** — V1 implementation per Marcel's 4 decisions (default-recommendation across all 4):
- Time-series snapshot table written by the refresh worker
- Two-rule detection (absolute >= 5000 OR relative >= 50% gated by min 500 stars)
- New `topic_briefs.source = 'star_trend'` lane with structured metadata bucket
- Per-project pacing cap (max 3 briefs/week, configurable)
- Per-project configurable detection knobs via JSONB (mirror Spec 64.19 / Phase D pattern)

**Out of scope** — explicit deferrals:
- Multi-tenant detection across BK / Balkonkraftwerk (star-counts are GitHub-specific; flagged as "Niedrig multi-domain readiness" in [64.20 §3.4](64.20-github-tool-inventory.md#3-4-angle-d---star-trend-stories-x-gained-10k-stars-this-quarter))
- Settings-UI knob editor (the JSONB column defaults to NULL = use code defaults; future task)
- "Star decline" stories (negative-growth angle) — different editorial framing, V2

## 4. Schema

### Migration 0109 — `topic_briefs.source` widening + `star_trend_metadata` jsonb

Mirror of 0107 (release-detection):
- DROP CONSTRAINT + ADD CONSTRAINT widens the source CHECK with `'star_trend'`
- New `star_trend_metadata jsonb NULL` column

### Migration 0110 — `inventory_star_history` table

```sql
CREATE TABLE inventory_star_history (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id   uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  inventory_id uuid NOT NULL REFERENCES content_source_inventory(id) ON DELETE CASCADE,
  snapshot_at  timestamptz NOT NULL DEFAULT NOW(),
  stars_count  integer NOT NULL CHECK (stars_count >= 0),
  created_at   timestamptz NOT NULL DEFAULT NOW()
);
```

Three indexes:
1. `(inventory_id, snapshot_at DESC)` — primary read pattern for `queryStarsAgo()`
2. `(snapshot_at)` — pruning scan
3. `(project_id)` — multi-tenant cross-project queries

**Retention:** 90 days. 3× default 30-day detection window; pruned at end of every refresh tick via `pruneStarSnapshots(NOW - 90 days)`. Single DELETE per tick, idempotent.

### Migration 0111 — `project_planner_config.star_trend_config jsonb`

Same partial-override pattern as `trend_score_weights` (Spec 64.19 / Phase D):
- NULL column = use code defaults
- Partial objects merge field-by-field via `resolveStarTrendConfig`

```typescript
DEFAULT_STAR_TREND_CONFIG = {
  absoluteThreshold:      5_000,
  relativeThresholdPct:   50,
  minAbsoluteForRelative: 500,
  weeklyCap:              3,
  windowDays:             30,
};
```

### Pure detection logic

[`packages/pipelines/src/topic-sources/star-trend/detect.ts`](../packages/pipelines/src/topic-sources/star-trend/detect.ts) — pure function, no I/O:

```typescript
detectStarTrend({priorStarsCount, currentStarsCount, config}): {
  triggered: boolean;
  growthAbsolute: number;
  growthPct: number;  // rounded to 2 decimals (JSONB stability)
  trigger: "absolute" | "relative" | "none";
}
```

Rules:
- `growthAbsolute = current - prior`
- Negative growth → no trigger (Star-Trend Stories are upside-only)
- Zero prior → `growthPct = 0` (division guard); absolute trigger still works
- Absolute hits when `growthAbsolute >= absoluteThreshold`
- Relative hits when `growthPct >= relativeThresholdPct AND current >= minAbsoluteForRelative`
- Absolute wins on tie (simpler-to-explain signal first; UI still surfaces both via metadata)

### Brief emission

[`packages/pipelines/src/topic-sources/star-trend/emit.ts`](../packages/pipelines/src/topic-sources/star-trend/emit.ts) mirrors release-detection's `emit.ts`:
- Pacing check via `countWeeklyStarTrendBriefs` against `config.weeklyCap`
- Idempotency check via `existsBriefForStarTrend(projectId, inventoryRowId, windowDays)` — application-layer dedup, no partial unique index (PostgreSQL forbids non-immutable `NOW()` in partial-index `WHERE`)
- Locale: from `projects.target_locales[0]` (de-DE / en-US BCP-47)
- Title: `Star-Sprung: ${displayName} +${formatted} Stars in ${periodDays} Tagen` (DE) or `Star spike: ${displayName} gained ${formatted} stars in ${periodDays} days` (EN)
- `intentType='news'`, `clusterAction='standalone'`, `approvalRequired=true`

### Worker integration

[`apps/api/src/workers/github-inventory-refresh.worker.ts`](../apps/api/src/workers/github-inventory-refresh.worker.ts) extended with three new responsibilities:

1. **Per-row snapshot insert** before `markInventoryOk` — keeps the time-series order consistent with metadata write order (read-after-write).
2. **Per-row detect + emit** via `maybeEmitStarTrend(row, currentStarsCount, latestReleaseTag, deps)`. Reads `star_trend_config` once per project per tick (in-memory Map cache).
3. **End-of-tick prune + cache clear** so subsequent ticks pick up config changes Marcel made in the UI between fires.

All three are wrapped in a try/catch — star-history failures must NOT break the refresh tick (same posture as A3 release-detection).

**DI seam (Pattern 121):** `InventoryRefreshDeps.emitStarTrendBrief` is the test injection point. Production callers use the package default `defaultEmitStarTrendBrief`.

## 8. Deviations & Discoveries

1. **`topicBriefSnapshotEntrySchema` in `packages/shared`** had its own hardcoded `source: z.enum([...])` that also needed `'star_trend'` added — caught by the Planner snapshot-step typecheck. Two-source enum gotcha (Memory rule referenced in 62.6).
2. **`TopicBriefInsertSchema.source` Zod enum** is separate from the Drizzle `$type<>()` union on the column — both needed updating. Same two-source pattern; both edited in `content.ts`.
3. **No partial unique index for dedup** — PostgreSQL's `WHERE` predicate must be immutable, and `created_at >= NOW() - INTERVAL '30 days'` is not. Mirror to the `rejected_topic_candidates` index decision; application-layer check is the alternative.
4. **`negative growth → no trigger`** is enforced in `detect.ts`, not in `emit.ts` — keeps the negative-growth branch out of the emit pipeline entirely. Future "star decline" stories would use a separate detect function with the inverse rule.
5. **`absolute wins on tie`** is editorial-decision-as-code — when both rules fire, the absolute number (`+15000 stars`) is more concrete than the relative pct (`200% growth`). UI still has access to both via metadata.
6. **Test fixture `releaseMetadata: null` sites** (10 files across pipelines + apps/api) needed parallel `starTrendMetadata: null` additions for the discriminated-union exhaustive shape. Batch perl-sed handled this. Same pattern as Spec 64.15 Phase C extending `embedding: null`.
7. **Pre-existing `bun test … grep "fail\b"` couldn't find the failure line** — the regex `\b` doesn't match in zsh basic-grep without `-E`. Used `grep "(fail) "` instead.

## 9. Patterns Surfaced

- **Time-series-via-history-table + retention-prune-at-tick-end** — clean separation between hot-path (snapshot insert) and cold-path (housekeeping); single DELETE per tick scales linearly with active inventory.
- **Per-project config cache scoped to single tick** — Map keyed by projectId, `.clear()` at end-of-tick. Cheaper than per-row SELECT, safer than session-long cache (Marcel's UI edits visible at next tick).
- **DI seam for two-step emission** (`emitStarTrendBrief` injected, `insertStarSnapshot` + `queryStarsAgo` used as defaults from `@marketing-auto/db`) — keeps tests offline without mocking the DB.
- **Idempotency via window-scoped existence check** when partial unique indexes can't express the predicate.
