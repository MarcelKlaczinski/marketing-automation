# Spec 54.5: Trend Scoring & Topic Synthesis

**Phase:** 54 / B — Trend Discovery (2 of 3)
**Estimated Effort:** 2.5 days (~16-18 focused hours over 4-5 sessions)
**Dependencies:** Spec 54.0 (ADR), Spec 54.1 (TopicBrief), Spec 54.2 (Project Config), Spec 54.3 (Topic Routing Policy), Spec 54.4 (External Signal Adapters)
**Status:** Ready for implementation
**Recommended Model:** Opus 4.7 (LLM-prompt-heavy spec — the synthesis prompts are high-leverage)

---

## Goal

Turn the raw `external_signals` pool into actionable **TopicBrief** rows via an LLM-driven synthesis pipeline with a **composite trend score**. After this spec lands, the daily BullMQ run consumes unprocessed signals from the last 14 days, clusters them into topic candidates, computes a 0–100 trend score per candidate, checks against existing toolwiki coverage, and emits TopicBriefs with `source='trend_discovery'` for the surviving topics.

This is the spec where Trend Discovery becomes real. Marcel will see, for the first time, AI-discovered topic candidates that the system thinks are worth covering.

Spec 54.5 delivers:

1. A new `TrendDiscoveryTopicSource` (implements the `TopicSource` interface from 54.1) that consumes `external_signals` and produces TopicBriefs.
2. A new `dataforseo.trendsExplore({ keywords })` adapter function for the search-volume-growth score component.
3. A composite **Trend Score** computation (community buzz + search volume growth + official announcement boost + SERP volatility - existing coverage penalty).
4. An **existing-coverage check** using the `articles.embedding` column (vector similarity) with LLM tiebreaker for borderline cases.
5. A **rejected_topic_candidates** table for tracking topics that didn't make it (with 30-day auto-expiry, after which they may resurface).
6. A BullMQ `trend-synthesizer` worker that runs daily after `signal-collector`.
7. Per-signal lifecycle stamps: `processed_at = NOW()` when a signal contributes to a brief OR is past the 14-day window OR is filtered out by minimum thresholds.

After deploy:
- Daily cron at ~01:30 UTC (after signal-collector at 00:30): synthesis runs across all projects with enabled `trend_discovery`
- Synthesis cost per project per day: ~€0.30–€0.80 (one Opus synthesis call + 3–10 DataForSEO SERP calls)
- Output: 0–5 new TopicBriefs per project per day (depending on signal richness)
- Briefs land with `approval_status = 'pending'`, ready for the 54.6 UI

## What this is NOT

- Not building the UI to review the briefs — that's Spec 54.6
- Not auto-approving any briefs — Phase 1 stays human-in-the-loop. `approval_required: true` on every emitted brief.
- Not implementing `cluster_action = 'create_new'` end-to-end — Cluster Creator is 54.7. The synthesis MAY emit briefs with `cluster_action = 'create_new'` (when no existing cluster matches), but the routing policy throws `RoutingNotImplementedError` if executed in 54.3-only state. Briefs stay `pending` in the queue until 54.7 lands and a human approves them.
- Not implementing **Reddit or GitHub adapter** — that's 54.4b in the backlog
- Not implementing **DataForSEO Trends as a full signal source** — the `trendsExplore` function is for **per-candidate scoring**, not bulk-signal-collection. Bulk DataForSEO Trends as a signal source is a future spec.
- Not implementing **A/B testing of synthesis prompts** — single prompt version per project (config can override the master_prompts in 54.2)
- Not implementing **trend score weight tuning UI** — weights are fixed constants in 54.5, observability via logged score breakdown. Adjustable weights tracked in POST-54-BACKLOG.
- Not changing `external_signals` schema beyond what's already in 54.4
- Not adding new fields to `topic_briefs` — `trend_metadata` JSONB from 54.1 already exists for this purpose
- Not migrating old signals — the 14-day cutoff means any signal older than 14 days at synthesis time is auto-stamped `processed_at = NOW()` (without producing a brief)

## Architecture

### Signal lifecycle (the (6c) decision)

Per user direction: signals get `processed_at = NOW()` stamped under three conditions:

```
Signal enters external_signals via collector (54.4)
  └── processed_at = NULL, in active pool

  Synthesis runs daily, fetches:
    WHERE processed_at IS NULL
      AND collected_at > NOW() - INTERVAL '14 days'
      AND project_id = X

  Per signal, one of:
    (a) Signal contributes to an emitted TopicBrief
        → processed_at = NOW(), processed_into = brief.id
    (b) Signal is in a candidate cluster that gets rejected
        (existing coverage OR low score OR scope mismatch)
        → processed_at = NOW(), processed_into = NULL,
          referenced from rejected_topic_candidates.source_signal_ids
    (c) Signal is below per-source filtering thresholds (e.g., HN points <3)
        → not part of synthesis input at all; processed_at stays NULL
        BUT: a daily janitor query also stamps signals older than 14d
        WHERE collected_at < NOW() - INTERVAL '14 days' AND processed_at IS NULL
        → processed_at = NOW(), processed_into = NULL (auto-expired)
```

This ensures:
- A signal has up to 14 days to contribute to a brief
- After 14 days, it's archived (stays in DB for audit, not in synthesis pool)
- Re-running synthesis on the same day doesn't re-process already-stamped signals (idempotency)
- The daily cron is independent of when the collector ran (synthesis-first or collector-first, either order works)

### Composite Trend Score (the (4a) decision — full version)

Four positive components + one penalty, all normalized to 0–100, then weighted-summed:

```typescript
trend_score = clamp(
    w_buzz * community_buzz_normalized       // HN points + PH votes + RSS engagement proxy
  + w_growth * search_volume_growth_norm     // DataForSEO Trends YoY growth, OR 0 if no DataForSEO data
  + w_official * official_announcement_bonus // RSS from major vendor = significant boost
  + w_serp * serp_volatility_norm            // New domains in top 10 SERP for primary keyword
  - w_coverage * existing_coverage_penalty   // embedding similarity to existing toolwiki articles
, 0, 100);

// Weights for 54.5 (fixed constants; tuning in POST-54-BACKLOG):
w_buzz = 30
w_growth = 25
w_official = 15
w_serp = 20
w_coverage = 40  // penalty has larger magnitude — heavily covered topics get rejected
```

Per-component definitions:

| Component | How computed | Range | Source |
|---|---|---|---|
| `community_buzz` | log10(sum(signals.metrics.points + signals.metrics.votes + signals.metrics.comments)) normalized to 0-100 | 0-100 | signals |
| `search_volume_growth` | DataForSEO Trends `(current_month - prev_year_same_month) / prev_year_same_month`, clamped/normalized | 0-100 | dataforseo.trendsExplore |
| `official_announcement_bonus` | If candidate has a vendor_rss signal from a major lab (OpenAI/Anthropic/Google/HF/Mistral), +100; else 0 | 0 or 100 | signals |
| `serp_volatility` | DataForSEO SERP: count of domains in top 10 that weren't there 30 days ago, normalized | 0-100 | dataforseo.serp |
| `existing_coverage_penalty` | Max cosine similarity between candidate-title embedding and any toolwiki article's embedding in the same project. 0.9 sim → 100 penalty, 0.5 sim → 0 penalty (linear) | 0-100 | articles.embedding |

**Disable conditions:**
- If DataForSEO Trends call fails or returns empty: `search_volume_growth = 0`, log warning
- If DataForSEO SERP call fails: `serp_volatility = 0`, log warning
- If embeddings missing for some articles: similarity is computed across whatever's available; warning if <50% have embeddings

**Threshold for emitting a brief:** `trend_score >= 40`. Below 40 → rejected topic candidate.

### Existing-coverage check (the (5c) decision — hybrid)

The most important decision-gate. For each topic candidate produced by the LLM synthesis:

```
1. Compute embedding for candidate title (via existing embedding adapter)
2. SQL: SELECT articles.id, title, 1 - (embedding <=> $candidate_emb) AS sim
        FROM articles
        WHERE project_id = $X
          AND embedding IS NOT NULL
        ORDER BY sim DESC LIMIT 5

3. Decision:
   - If max_sim > 0.85 → DEFINITELY COVERED → reject with reason='existing_coverage'
   - If max_sim < 0.60 → DEFINITELY NEW → proceed
   - If 0.60 <= max_sim <= 0.85 → LLM tiebreaker:
       Prompt: "We have an article '<existing_title>' covering <existing_summary>.
                A new topic candidate is '<candidate_title>' with summary <candidate_summary>.
                Is the new topic substantially the same as the existing article?
                Answer: 'covered' | 'distinct' | 'partial_overlap'"
       - 'covered' → reject with reason='existing_coverage', record matched_article_id
       - 'distinct' or 'partial_overlap' → proceed
```

The LLM tiebreaker uses Haiku (cheap, ~€0.005 per check), only triggered in the 0.6–0.85 band. Probably <2 calls per synthesis run.

### Rejected topic candidates

Per user direction (6b): track rejected topics in their own table, with 30-day auto-expiry. After 30 days, the same candidate can resurface if signals re-emerge.

```sql
CREATE TABLE rejected_topic_candidates (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id           UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  topic_title          TEXT NOT NULL,
  candidate_title_normalized TEXT NOT NULL,  -- lowercased, trimmed, used for dedup

  reason               TEXT NOT NULL CHECK (reason IN (
                         'existing_coverage', 'low_score',
                         'excluded_by_scope', 'low_signal_volume'
                       )),
  trend_score          INTEGER,                    -- if rejected for low_score
  similarity_score     NUMERIC(4,3),               -- if rejected for existing_coverage
  matched_article_id   UUID REFERENCES articles(id) ON DELETE SET NULL,

  source_signal_ids    JSONB NOT NULL,             -- array of external_signal.id

  rejected_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  expires_at           TIMESTAMPTZ NOT NULL        -- rejected_at + 30 days
);

CREATE INDEX rejected_topic_candidates_project_active_idx
  ON rejected_topic_candidates(project_id, expires_at)
  WHERE expires_at > NOW();

CREATE INDEX rejected_topic_candidates_normalized_idx
  ON rejected_topic_candidates(project_id, candidate_title_normalized);
```

Synthesis checks against this table:

```
For each candidate from LLM synthesis:
  - Check rejected_topic_candidates WHERE
      project_id = X AND
      candidate_title_normalized = normalize(candidate.title) AND
      expires_at > NOW()
  - If match found: skip (don't even score it; signal stays unprocessed for now,
                          might re-cluster differently next run)
```

**Daily janitor**: a cleanup query in the synthesis job stamps expired rejections (their `expires_at` is in the past) — they're now eligible to resurface. Done implicitly by the `expires_at > NOW()` filter; no explicit DELETE needed. Optional periodic DELETE after 90 days for storage cleanup (not in 54.5; backlog).

### Synthesis pipeline (the LLM call)

The heart of the spec. One Anthropic call per project per day. Opus 4.7 because synthesis quality matters and the input fits in a single call.

**Input to Anthropic** (~5-15K tokens depending on signal pool):

```
System prompt (cacheable, project-specific via master_prompts):
  Skills: ai-seo, content-strategy, marketing-ideas
  Project context (marketing-context.md excerpt)
  Topic scope (from project_configurations.topic_scope)

User message:
  Here are <N> external signals from the last 14 days for <project name>:

  <signal_1>:
    source: producthunt
    title: "Voker (YC S24) – Analytics for AI Agents"
    summary: "Voker provides analytics dashboards for AI agent..."
    published_at: 2026-05-12
    metrics: { votes: 412, comments: 89 }
    url: ...

  <signal_2>: ...
  ...

  Task:
    1. Cluster these signals into 3-8 distinct TOPIC CANDIDATES
       (related signals about the same theme group together).
    2. For each topic, propose:
       - topic_title (concise, SEO-aware, German: how a German searcher would phrase it)
       - primary_keyword (the SEO target)
       - secondary_keywords (3-5)
       - intent_type (from project's intent taxonomy)
       - generation_mode ('timely' if breaking news; 'evergreen' otherwise)
       - suggested_title (article headline)
       - suggested_slug
       - suggested_meta (max 160 chars)
       - hero_image_prompt (concise visual brief)
       - related_signal_ids (which signals support this topic)
       - freshness_window ('breaking' | 'rising' | 'stable')
       - relevance_score (0-100, your assessment of fit to project scope)
    3. SKIP signals that don't fit any natural cluster (mention them in 'unclustered').
    4. Output strict JSON matching the schema.
```

**Output validation:** Strict Zod schema. If output is malformed, log error, throw — the worker will retry up to BullMQ's default (3 attempts).

```typescript
const SynthesisOutputSchema = z.object({
  topics: z.array(z.object({
    topic_title: z.string().min(5).max(300),
    primary_keyword: z.string().min(2).max(100),
    secondary_keywords: z.array(z.string()).min(0).max(10),
    intent_type: z.string(),
    generation_mode: z.enum([
      "evergreen", "timely", "pillar", "spoke", "refresh", "translation",
    ]).default("timely"),
    suggested_title: z.string().min(10).max(200),
    suggested_slug: z.string().regex(/^[a-z0-9-]+$/).max(100),
    suggested_meta: z.string().min(50).max(160),
    hero_image_prompt: z.string().min(80).max(800),
    related_signal_ids: z.array(z.string().uuid()).min(1).max(20),
    freshness_window: z.enum(["breaking", "rising", "stable"]),
    relevance_score: z.number().int().min(0).max(100),
  })).min(0).max(15),
  unclustered_signal_ids: z.array(z.string().uuid()).default([]),
});
```

### Per-signal cap on input

To prevent token explosion: at most **80 signals** per synthesis call. If the pool has more, take the top 80 by:
1. Most recent first (`published_at DESC`)
2. Tiebreak by `metrics->>'points' DESC NULLS LAST`

The rest get re-considered the next day (still in their 14-day window).

### After-synthesis flow

```
For each topic in SynthesisOutput.topics:

  1. Check existing-coverage (embedding + LLM tiebreaker)
     → if covered: insert rejected_topic_candidates row, mark signals processed,
       continue to next candidate

  2. Check rejected_topic_candidates for non-expired duplicate
     → if recent rejection exists: skip silently (signals stay unprocessed)

  3. Compute trend score (community_buzz + DataForSEO calls + ...)
     → if score < 40: insert rejected with reason='low_score',
       mark signals processed, continue

  4. Find matching cluster (if any) via embedding similarity:
     - For each cluster in project, get its embedding (computed from
       cluster.name + cluster.primary_keyword + sample article titles)
     - Highest similarity > 0.65: cluster_action = 'append_to_existing',
       set brief.cluster_id = matched_cluster.id
     - Else: cluster_action = 'create_new', cluster_id = null

  5. Insert topic_briefs row inside transaction:
     - source = 'trend_discovery'
     - approval_required = true
     - approval_status = 'pending'
     - trend_metadata = { trend_score, signals_used, freshness_window,
                          score_breakdown, related_event? }
     - cluster_id and cluster_action from step 4
     - generation_mode from LLM
     - suggested_* from LLM

  6. Mark contributing signals: processed_at = NOW(), processed_into = brief.id

  7. Log structured event: brief created, with score breakdown for observability

For each signal in SynthesisOutput.unclustered_signal_ids:
  - Stamp processed_at = NOW(), processed_into = NULL (skipped by LLM)
```

All inside `db.transaction(async (tx) => { ... })` per topic to maintain atomicity.

### Cluster matching uses cluster-level embeddings

This is new in 54.5. Currently `clusters` does not have an `embedding` column. Two options:

- (a) Add `clusters.embedding` column, computed when cluster is updated
- (b) Compute on-the-fly during synthesis: read cluster name + primary_keyword, embed once, cache in-memory for the run

Per the 54.4 lesson "don't fight the framework, mirror what works": **option (a) with a small ALTER TABLE**. Embeddings are a known pattern in this codebase (articles have one). Worker job that updates `clusters.embedding` when name or primary_keyword changes — for 54.5, we compute it once per cluster during synthesis if it's null (lazy backfill).

Migration:

```sql
ALTER TABLE clusters
  ADD COLUMN embedding vector(1024);

CREATE INDEX clusters_embedding_idx
  ON clusters USING hnsw (embedding vector_cosine_ops);
```

Lazy backfill in synthesis worker: for any cluster in the active project whose `embedding IS NULL`, compute and persist before the matching step. ~10 clusters × €0.0001 embedding cost = negligible.

### Scheduling: 01:30 UTC daily, after collector

The signal-collector cron is at 00:30 UTC (set in 54.4). The trend-synthesizer cron is at **01:30 UTC**, giving the collector 60 minutes for all projects' daily fetches. If a project's collector takes longer than 60 minutes (worst-case: dozens of RSS feeds with timeouts), the synthesizer simply operates on yesterday's pool — no correctness issue, just a one-day-lag for that project.

BullMQ scheduling pattern mirrors `signal-collector` (Spec 54.4):
- `schedule-daily` job → fans out to N `synthesize-project` jobs
- Each `synthesize-project` runs the full per-project synthesis pipeline

### Cost & runtime estimate

Per project per daily run:

| Step | Cost | Calls |
|---|---|---|
| Fetch unprocessed signals | €0 | DB |
| Compute candidate embeddings (for coverage check) | ~€0.001 | 1 per candidate × ~5 |
| Compute cluster embeddings (lazy, once per cluster lifetime) | ~€0.001 | 1 per uninitialized cluster |
| LLM synthesis (Opus 4.7, 80 signals input, structured JSON output) | ~€0.40 | 1 |
| LLM tiebreaker (Haiku) | ~€0.005 | 0-3 |
| DataForSEO Trends per candidate | ~€0.010 | 0-5 |
| DataForSEO SERP per candidate | ~€0.002 | 0-5 |
| **Total per project per day** | **~€0.45–€0.50** | |

For toolwiki: ~€15/month. Cheap relative to article generation (~€2.41 per article).

```typescript
import type { TopicSource, TopicSourceContext } from "../types.ts";
import type { TopicBriefInsert } from "@marketing-auto/db";
import { fetchEligibleSignals } from "./fetch-signals.ts";
import { synthesizeTopics } from "./synthesize.ts";
import { checkExistingCoverage } from "./coverage.ts";
import { computeTrendScore } from "./score.ts";
import { findMatchingCluster } from "./cluster-match.ts";
import { buildBriefFromCandidate } from "./emit-brief.ts";

const InputSchema = z.object({
  projectId: z.string().uuid(),
});

type Input = z.infer<typeof InputSchema>;

export class TrendDiscoveryTopicSource implements TopicSource<Input> {
  readonly source = "trend_discovery" as const;
  readonly inputSchema = InputSchema;

  async emit(input: Input, ctx: TopicSourceContext): Promise<TopicBriefInsert[]> {
    // 1. Load signals
    const signals = await fetchEligibleSignals(input.projectId);
    if (signals.length === 0) return [];

    // 2. Synthesize topic candidates via LLM
    const synthesis = await synthesizeTopics(input.projectId, signals);

    // 3. For each candidate, score + coverage check
    const briefsToEmit: TopicBriefInsert[] = [];
    for (const candidate of synthesis.topics) {
      // 3a. Existing coverage check
      const coverage = await checkExistingCoverage(input.projectId, candidate);
      if (coverage.covered) {
        await recordRejection(input.projectId, candidate, "existing_coverage",
                              { similarity: coverage.similarity, matchedArticleId: coverage.matchedArticleId });
        continue;
      }

      // 3b. Recently rejected?
      if (await wasRecentlyRejected(input.projectId, candidate.topic_title)) {
        continue;  // signals stay unprocessed, may re-cluster differently next run
      }

      // 3c. Compute trend score
      const scoreResult = await computeTrendScore(input.projectId, candidate, signals);
      const minScore = await loadMinTrendScore(input.projectId);  // from project config
      if (scoreResult.total < minScore) {
        await recordRejection(input.projectId, candidate, "low_score",
                              { trendScore: scoreResult.total });
        continue;
      }

      // 3d. Find matching cluster
      const clusterMatch = await findMatchingCluster(input.projectId, candidate);

      // 3e. Build brief
      const brief = buildBriefFromCandidate({
        projectId: input.projectId,
        candidate,
        score: scoreResult,
        clusterMatch,
        signals,
      });
      briefsToEmit.push(brief);
    }

    // 4. Stamp unclustered signals as processed
    await markSignalsProcessed(synthesis.unclustered_signal_ids, null);

    return briefsToEmit;
  }
}
```

### fetch-signals.ts

```typescript
import { and, isNull, gte, eq } from "@marketing-auto/db";
import { db, externalSignals } from "@marketing-auto/db";
import { loadActiveConfig } from "../../config/load-active-config.ts";

export async function fetchEligibleSignals(projectId: string) {
  const config = await loadActiveConfig(projectId);
  const cutoff = new Date(Date.now() - 14 * 86_400_000);

  const all = await db
    .select()
    .from(externalSignals)
    .where(and(
      eq(externalSignals.projectId, projectId),
      isNull(externalSignals.processedAt),
      gte(externalSignals.collectedAt, cutoff),
    ))
    .orderBy(desc(externalSignals.publishedAt))
    .limit(120);  // hard cap; filter below trims further

  // Apply per-source min thresholds
  const thresholds = config.topicScope.min_signal_thresholds ?? {};
  const filtered = all.filter((s) => {
    const t = thresholds[s.source];
    if (t === undefined) return true;
    if (s.source === "hackernews") return (s.metrics.points ?? 0) >= t;
    if (s.source === "producthunt") return (s.metrics.votes ?? 0) >= t;
    return true;
  });

  // Cap at 80 (synthesis token budget)
  return filtered.slice(0, 80);
}
```

```typescript
  const systemInstructions = await resolveMasterPrompt({
    projectId,
    promptKey: "trend.synthesis",

    skills: ["ai-seo", "content-strategy", "marketing-ideas"],

  });

    model: "claude-opus-4-7",
    systemPrefix: systemPrompt.cacheablePrefix,
    systemSuffix: systemPrompt.variableSuffix,
    userMessage,

    jsonMode: true,
    estimatedCostEur: 0.40,

function buildUserMessage(signals: ExternalSignal[]): string {
  const lines: string[] = [
    `Here are ${signals.length} external signals from the last 14 days.`,
    `Each signal has an ID (UUID) — use these IDs when referencing signals in your output.`,
    "",
  ];
  for (const s of signals) {
    lines.push(`# Signal ${s.id}`);
    lines.push(`Source: ${s.source}`);
    lines.push(`Title: ${s.title}`);

    if (Object.keys(s.metrics).length > 0) {
      lines.push(`Metrics: ${JSON.stringify(s.metrics)}`);
    }
    lines.push("");

  lines.push("Now produce the clustered topics. Output JSON only, no prose preamble.");
  return lines.join("\n");
```

### score.ts

Plain TypeScript, no LLM. Pure-ish (depends on DataForSEO calls but otherwise deterministic). Composite computation per the architecture table.

```typescript
export type ScoreBreakdown = {
  community_buzz: number;        // 0-100
  search_volume_growth: number;  // 0-100
  official_announcement: number; // 0 or 100
  serp_volatility: number;       // 0-100
  existing_coverage_penalty: number;  // 0-100 (subtracted)
  total: number;                 // 0-100, final
};

const WEIGHTS = {
  buzz: 30,
  growth: 25,
  official: 15,
  serp: 20,
  coverage: 40,
} as const;

export async function computeTrendScore(
  projectId: string,
  candidate: SynthesisTopicCandidate,
  signalPool: ExternalSignal[],
): Promise<ScoreBreakdown> {
  const candidateSignals = signalPool.filter(
    (s) => candidate.related_signal_ids.includes(s.id)
  );

  const buzz = computeCommunityBuzz(candidateSignals);
  const official = computeOfficialAnnouncementBonus(candidateSignals);

  // DataForSEO Trends (optional — may fail)
  let growth = 0;
  try {
    const trendsData = await dataforseo.trendsExplore({
      projectId,
      operation: `trends-${slugify(candidate.primary_keyword)}`,
      keywords: [candidate.primary_keyword],
      estimatedCostEur: 0.010,
    });
    growth = normalizeGrowthRatio(trendsData[0]?.growth_ratio ?? 0);
  } catch (e) {
    log.warn({ err: e, keyword: candidate.primary_keyword }, "trendsExplore failed");
  }

  // DataForSEO SERP for volatility
  let serpVol = 0;
  try {
    const serpData = await dataforseo.serp({
      projectId,
      operation: `serp-${slugify(candidate.primary_keyword)}`,
      keyword: candidate.primary_keyword,
      depth: 10,
      estimatedCostEur: 0.002,
    });
    serpVol = computeSerpVolatility(serpData);
  } catch (e) {
    log.warn({ err: e, keyword: candidate.primary_keyword }, "serp failed");
  }

  // Coverage check is done separately (in coverage.ts) but its result is needed here
  // for the final score. By the time computeTrendScore is called, the candidate has
  // already passed the hard-coverage gate (>0.85 was rejected). Coverage penalty
  // here applies to borderline-similar candidates (0.6-0.85 sim that LLM said 'distinct').
  const coveragePenalty = await getCoveragePenalty(projectId, candidate);

  const total = clamp(
    (WEIGHTS.buzz * buzz / 100) +
    (WEIGHTS.growth * growth / 100) +
    (WEIGHTS.official * official / 100) +
    (WEIGHTS.serp * serpVol / 100) -
    (WEIGHTS.coverage * coveragePenalty / 100),
    0, 100
  );

  return {
    community_buzz: buzz,
    search_volume_growth: growth,
    official_announcement: official,
    serp_volatility: serpVol,
    existing_coverage_penalty: coveragePenalty,
    total: Math.round(total),
  };
}
```

### coverage.ts

```typescript
import { sql } from "@marketing-auto/db";
import { embed } from "@marketing-auto/adapter-anthropic";  // or wherever embed lives
import { anthropic } from "@marketing-auto/adapter-anthropic";

export async function checkExistingCoverage(
  projectId: string,
  candidate: SynthesisTopicCandidate,
): Promise<{
  covered: boolean;
  similarity: number;
  matchedArticleId: string | null;
}> {
  const embedding = await embed(candidate.topic_title);

  // Find nearest articles by cosine similarity
  const rows = await db.execute<{
    id: string;
    title: string;
    metaDescription: string | null;
    sim: number;
  }>(sql`
    SELECT id, title, meta_description, 1 - (embedding <=> ${embedding}::vector) AS sim
    FROM articles
    WHERE project_id = ${projectId}
      AND embedding IS NOT NULL
    ORDER BY embedding <=> ${embedding}::vector
    LIMIT 5
  `);

  if (rows.length === 0) {
    return { covered: false, similarity: 0, matchedArticleId: null };
  }

  const topMatch = rows[0];

  if (topMatch.sim > 0.85) {
    return {
      covered: true,
      similarity: topMatch.sim,
      matchedArticleId: topMatch.id,
    };
  }

  if (topMatch.sim < 0.60) {
    return { covered: false, similarity: topMatch.sim, matchedArticleId: null };
  }

  // LLM tiebreaker for 0.60-0.85 band
  const tiebreaker = await callTiebreakerLlm({
    candidate,
    existingArticle: topMatch,
  });

  if (tiebreaker === "covered") {
    return {
      covered: true,
      similarity: topMatch.sim,
      matchedArticleId: topMatch.id,
    };
  }

  return { covered: false, similarity: topMatch.sim, matchedArticleId: topMatch.id };
}

async function callTiebreakerLlm(args: {
  candidate: SynthesisTopicCandidate;
  existingArticle: { title: string; metaDescription: string | null };
}): Promise<"covered" | "distinct" | "partial_overlap"> {
  const result = await anthropic.messages({
    projectId: "...",  // ctx.projectId
    operation: "trend-coverage-tiebreaker",
    model: "claude-haiku-4-5",
    systemPrefix: "You are a content strategist judging topic similarity.",
    userMessage: `
Existing article: "${args.existingArticle.title}"
${args.existingArticle.metaDescription ? `Existing summary: ${args.existingArticle.metaDescription}` : ""}

New topic candidate: "${args.candidate.topic_title}"
New topic summary: ${args.candidate.suggested_meta}

Is the new topic substantially the same as the existing article?
Output strict JSON: {"verdict": "covered" | "distinct" | "partial_overlap"}
    `.trim(),
    maxTokens: 200,
    jsonMode: true,
    estimatedCostEur: 0.005,
  });

  return result.json.verdict;
}
```

```typescript
async function handleSynthesizeProject(data: { projectId: string }): Promise<void> {
  // Janitor: stamp expired signals as processed
  await db.update(externalSignals)
    .set({ processedAt: new Date() })
    .where(and(
      eq(externalSignals.projectId, data.projectId),
      isNull(externalSignals.processedAt),
      lt(externalSignals.collectedAt, new Date(Date.now() - 14 * 86_400_000)),
    ));

  // Lazy-backfill cluster embeddings
  await backfillClusterEmbeddings(data.projectId);

  // Run synthesis
  const source = new TrendDiscoveryTopicSource();
  const briefs = await source.emit({ projectId: data.projectId }, { projectId: data.projectId });

  // Persist (caller owns persistence — 54.1 convention)
  if (briefs.length > 0) {
    await db.transaction(async (tx) => {
      await tx.insert(topicBriefs).values(briefs);
    });
  }

  log.info({
    projectId: data.projectId,
    briefsEmitted: briefs.length,
  }, "trend synthesis complete");
}
```

## Open Questions / Decisions Made

**Decision 1: Synthesis as a TopicSource, not a pipeline.**
Mirrors 54.4's adapter pattern. The TopicSource interface from 54.1 handles this cleanly. Internal calls to anthropic/dataforseo happen inside source.emit, but the source itself is a thin contract.

**Decision 2: Caller owns brief persistence.**
Same convention as 54.1 (GapAnalysisTopicSource). The worker owns the transaction. Allows future composition with rule-based automation that may batch decisions before persisting.

**Decision 3: 14-day rolling window, daily synthesis.**
Per user direction (c). Signals get up to 14 days to find a home. After that, auto-stamped processed (audit-preserving expiry). Daily runs are sparse but additive over the window.

**Decision 4: Composite score with DataForSEO Trends adapter.**
Per user direction (4a). New `trendsExplore` function added to existing `@marketing-auto/adapter-dataforseo` (per 54.5's pre-spec discussion). Other components (community_buzz, serp_volatility, official_announcement) work without DataForSEO Trends if it fails.

**Decision 5: Embedding-based coverage with LLM tiebreaker.**
Per user direction (5c). Two hard thresholds (0.85, 0.60) bracket a band where Haiku makes the call. Cheap (~€0.005 per tiebreaker), 0-3 calls per synthesis run.

**Decision 6: Rejected topic candidates with 30-day expiry.**
Per user direction (6b). Auto-resurfacing after 30 days lets topics that were "too soon" come back when momentum builds. No manual cleanup needed.

**Decision 7: cluster_action = create_new emits briefs that wait for 54.7.**
Briefs that don't match any existing cluster have `cluster_action = 'create_new'`. The routing policy in 54.3 throws on this kind. Briefs stay `pending` in the queue, visible in 54.6 UI but not approvable until 54.7 Cluster Creator lands. Decision: do not gate emission on having a viable cluster match — let the UI surface these as "needs new cluster" candidates.

**Decision 8: Cluster embeddings via lazy backfill.**
New column `clusters.embedding`. Synthesis worker populates it on-demand. Avoids a one-shot migration backfill (which would need to call the embedding API for every existing cluster at deploy time).

**Decision 9: Synthesis schedule at 01:30 UTC.**
60-minute lag after collector at 00:30. Hard-coded; configurable later if needed.

**Decision 10: No API endpoints in 54.5.**
Consistent with 54.1, 54.2, 54.3, 54.4. The briefs surface in the 54.6 UI which builds on the existing brief-loading endpoints (or new minimal ones).

**Decision 11: Fixed weights, not configurable.**
Per spec design. Weights live as constants in `score.ts`. Tuning is observable via `trend_metadata.score_breakdown` in each emitted brief. Adjustable weights tracked in POST-54-BACKLOG.

**Decision 12: Hard cap of 80 signals per synthesis call.**
Token budget. With current toolwiki signal volumes (~64/day after 14d), we're under the cap. If volume grows past 80, oldest signals get held over for the next day.

**Decision 13: Multi-component score makes failure modes graceful.**
If DataForSEO Trends fails: growth = 0. If SERP fails: volatility = 0. If embeddings missing: coverage penalty = 0 (system errs on side of "emit the brief" rather than blocking). All component failures logged for observability.

**Decision 14: Master prompt key 'trend.synthesis' added to MasterPromptsSchema.**
Sixth key after the article-generation five. Empty by default — falls back to code constant. Override via SQL during dev tuning, no migration needed.

## Discovered During Implementation

**`exactOptionalPropertyTypes` + optional `pipelineRunId`**: Passing `pipelineRunId: string | undefined` to functions whose parameter type is `pipelineRunId?: string` fails under `exactOptionalPropertyTypes`. Fix: build the options object with the conditional spread pattern everywhere `ctx.pipelineRunId` is optional: `...(pipelineRunId !== undefined && { pipelineRunId })`. Applied in `synthesize.ts`, `coverage.ts`, `cluster-match.ts`, and `source.ts`.

**Drizzle insert incompatibility — Zod `undefined` vs Drizzle `null`**: `TopicBriefInsert` (Zod-inferred) uses `field?: T | undefined` for optional fields. Drizzle's `$inferInsert` uses `field?: T` (no `undefined`), which TypeScript rejects under `exactOptionalPropertyTypes`. Fix: strip undefined values before insert with `Object.fromEntries(Object.entries(b).filter(([,v]) => v !== undefined)) as typeof topicBriefs.$inferInsert`. Cast to the Drizzle type, not the Zod type.

**`metrics` double-cast was unnecessary**: `ExternalSignal.metrics` is already typed as `Record<string, number>` via `.$type<Record<string, number>>()` in the schema. Removing the `as Record<string, number>` casts in `fetch-signals.ts` and `synthesize.ts` cleaned up noise.

**`TopicScopeSchema` gained required fields mid-implementation**: Sessions 1–2 extended `TopicScopeSchema` (spec 54.5) with `primary_themes`, `relevance_keywords`, `min_trend_score`, `min_signal_thresholds`. The existing project-creation path in `apps/api/src/routes/projects.ts` was constructing the scope inline `{ languages: ["de","en"], exclusions: [] }` — the added required fields caused a typecheck error. Fix: switch to `TopicScopeSchema.parse({ languages: ["de","en"] })` so Zod applies defaults for the new fields.

**Pre-existing caller errors from 54.4 adapter changes**: `HackerNewsSignalSource.fetch()` and `VendorRssSignalSource.fetch()` gained a required `maxAgeDays` field in spec 54.4, but `signal-collector.ts` was never updated. Fixed by adding `maxAgeDays: 30` (HN) and `maxAgeDays: 14` (vendor_rss).

**`ContentGapMetadata` type narrowed**: `metadata: { gapType, priority }` in `projects-suggest-idempotent.test.ts` was passing extra fields that don't belong in `ContentGapMetadata` (they are top-level DB columns). Removed to align with the type.

**Worker lives in `apps/api`, not `apps/worker`**: The spec described a separate `apps/worker` directory that doesn't exist in the codebase. The `trend-synthesizer.ts` worker lives in `apps/api/src/workers/` alongside `signal-collector.ts` and all other BullMQ workers. Cron registration follows the existing pattern in `apps/api/src/workers/index.ts`.

**`VOYAGE_API_KEY` is env-only (not vault-wired)**: The Voyage AI adapter was not wired into the credential vault (DB-encrypted creds). `VOYAGE_API_KEY` must be added to `.env` directly — there is no SQL insert or installer UI step to set it.

## Deviations

**`apps/worker/` → `apps/api/src/workers/`**: The spec listed `apps/worker/src/workers/trend-synthesizer.ts` as the output location. The actual codebase has no `apps/worker` package — all workers live in `apps/api/src/workers/`. The worker and cron registration were placed there instead.

**`backfillClusterEmbeddings` not yet implemented**: The spec described a lazy-backfill helper that computes `clusters.embedding` on first synthesis run if null. This was not included in Session 4 — the synthesis pipeline reads cluster embeddings correctly (null embeddings are handled by `findMatchingCluster` falling back to `create_new`). The backfill can be added when a project has many existing clusters that need scoring improvement.

**`SynthesisOutputSchema.parse` vs `.safeParse` + throw**: The spec recommended `.safeParse` + throw with a human-readable message. Implemented as `SynthesisOutputSchema.safeParse(result.json)` with `throw new Error(...)` on failure — functionally identical, slightly cleaner error message for BullMQ retry logs.
