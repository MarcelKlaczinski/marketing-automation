# Spec 64.17 — Bulk Brief Actions (Approve + Dismiss)

_BriefsPage gets a Gmail-style "Select all 168 matching filter" affordance, raised volume cap, and a pre-flight cluster-check summary in the approve modal._
_Status: Draft._
_Voraussetzung: Discovery [specs/_drafts/64.17-brief-bulk-actions.discovery.md](specs/_drafts/64.17-brief-bulk-actions.discovery.md)._
_Multi-Domain Refactor läuft parallel ab 2026-05-24 — conflict-map siehe §10._
_Aufwand: ~0.75–1.0 d._

---

## 1. Problem

Marcel hat in Toolwiki aktuell **168 pending Briefs** (gap_analysis = 168, trend_discovery = 22, comparison_discovery = 4, refresh_detection = 1, manual = 1+). Die existierende Bulk-Infrastruktur (Spec 63.6) ist drei wichtige Schritte vom "ich räume meine Pending-Liste auf" entfernt:

1. **Volume-Cap zu niedrig**: `bulkApproveSchema.briefIds.max(50)` und `bulkDismissSchema.briefIds.max(50)` in [apps/api/src/routes/projects/briefs.ts:190](apps/api/src/routes/projects/briefs.ts:190) blocken jeden "Wähle alle 168" Versuch. Selbst wenn das Frontend sie hätte, der Backend-Boundary lehnt ab.
2. **Selection-Modus zu schwach**: Per-Card-Checkboxen existieren via [BriefsSection.vue](apps/web/src/pages/briefs/BriefsSection.vue) + `selectedBriefIds: string[]` Set in [BriefsPage.vue:187](apps/web/src/pages/briefs/BriefsPage.vue:187), aber es gibt keinen "Select all 168 matching filter"-Affordance. Marcel müsste 168 Checkboxen einzeln klicken (und durch alle Pagination-Seiten scrollen — `limit: 50` per Page).
3. **Pre-Flight-Cluster-Check fehlt im UX**: Das Backend gibt bereits Option-β-Counts zurück (`skippedCount` mit `reason: "cluster_assignment_required"`), aber die `BulkApproveModal` zeigt dem User vor dem Submit nicht, dass z.B. "5 von 22 trend_discovery-Briefs eine Cluster-Zuweisung brauchen". Marcel klickt blind und sieht erst nach 5–30 s sequenzieller Verarbeitung das Ergebnis.

Symptom: Spec 63.6 hat den Bulk-Approve-Pfad strukturell gelöst, aber operativ ist er für realistische Volumina nicht nutzbar.

## 2. Ziel

**In Scope:**

- **Backend** — Zwei Endpoint-Varianten unter einer Route je Action:
  - `POST /api/projects/:slug/briefs/bulk-approve` mit Body `{briefIds: string[]} | {filter: BriefsFilter, excludeIds?: string[]}`
  - `POST /api/projects/:slug/briefs/bulk-dismiss` mit gleicher discriminated Body-Shape
  - Cap raised: `briefIds.max(50)` → `max(500)` (Soft-Safety-Limit, Marcel-Default per Discovery Q2).
  - Filter-shape Path re-queriert `topic_briefs` server-side mit identischer Where-Clause-Logik wie `GET /briefs` (Section + Source + Readiness), excludiert `excludeIds`, processed dann sequenziell mit demselben `approveBrief()` Service.
  - **Neues Pre-Flight Endpoint**: `POST /api/projects/:slug/briefs/bulk-preflight-cluster-check` — nimmt identische Body-Shape, läuft als reine SQL-Aggregate (kein Side-Effect), returned Counts `{ totalMatched, needsClusterAssignment, eligibleForApprove, eligibleForDismiss }` pro Dispatch-Mode (plan + immediate).

- **Frontend** — Selection-Mechanik erweitern + Modal-UX hardening:
  - `BriefsPage` bekommt `selectAllMatching: boolean` Flag im `data()`. Mode-1 = per-card IDs (heute), Mode-2 = "Select all 168 matching filter" via Filter-Shape.
  - `BulkSelectionBar` rendert "Select all N matching filter →" Banner wenn alle sichtbaren Cards der Section selected sind UND die `pendingHasMore`/Section-Total-Count > visible count.
  - `BulkApproveModal` ruft beim Open das Pre-Flight-Endpoint, zeigt Summary: `"22 Briefs ausgewählt — 17 bereit, 5 brauchen Cluster-Zuweisung (werden übersprungen)"`. Submit aktiviert sich erst wenn `eligibleForApprove > 0` für den gewählten Dispatch-Mode.
  - `BulkApproveModal` Body-Submit: erweitert um optionales `filter`/`excludeIds`-Payload statt nur `briefIds`.

**Out of Scope:**

- **Add-to-Plan als separate Action** (Marcel Q1 = drop, per Discovery Recommendation). Path A wäre semantisch identisch zu Approve (plan_pending → planner picks up), Path B/C würden Planner-Bypass + Schema-Arbeit einführen. Wenn nach Multi-Domain Sprint 3 (Categories) ein echter Use-Case erscheint → eigener Spec M4.1.
- **Auto-Cluster-Guess für trend_discovery Briefs** (Marcel Q5 = no). Briefs mit `cluster_action='append_to_existing' AND cluster_id IS NULL` werden im Pre-Flight als "needs assignment" gezählt und im Bulk-Approve als `skipped` zurückgegeben — der User muss sie einzeln zuweisen.
- **Notification beim Bulk-Complete** (Marcel Q6 = no). Bulk-Approve ist synchron-during-HTTP; das `BulkApproveModal` zeigt das Result inline. Wenn die Anzahl Briefs irgendwann tatsächlich Minuten dauert → eigener Spec (würde async Job + SSE brauchen).
- **Hard-Cap-Wechsel auf BullMQ-fanout**: Bulk-Approve macht keine Job-Enqueues (außer im legacy `immediate`-Dispatch der einzeln `triggerWithPreRunId` aufruft). Status-Updates für Plan-Dispatch laufen in einer einzigen DB-Transaktion-pro-Brief, sequenziell. 500 Briefs sind selbst worst-case noch unter 30 s.
- **`plan_pending → rejected`-Pfad in Bulk-Dismiss**: aktueller Code (`bulk-dismiss` line 408) flippt nur `approvalStatus = 'pending'`. Bleibt so — Marcel-vouched Briefs (`plan_pending`) sollen nicht durch einen "alle ablehnen"-Misclick verloren gehen. Per-Brief-Dismiss aus Detail-View bleibt der Weg dafür.

**Aufwand:** Backend ~0.4d (Schema-Widening + Filter-Shape + Pre-Flight-Endpoint + Tests), Frontend ~0.4d (Selection-Mode + Banner + Modal-UX + i18n), Marcel-Verify ~0.1d.

## 3. Backend

### 3.1 Schema-Widening — diskriminierte Body-Union

`bulkApproveSchema` und `bulkDismissSchema` in [apps/api/src/routes/projects/briefs.ts](apps/api/src/routes/projects/briefs.ts) werden zu einer discriminated union:

```typescript
const bulkBriefSelectorSchema = z.union([
  z.object({
    briefIds: z.array(z.string().uuid()).min(1).max(500),
  }),
  z.object({
    filter: z.object({
      section: z.enum(["pending", "in-flight", "done", "all"]).default("pending"),
      source: z.array(z.enum(BRIEF_SOURCES)).optional(),
      readiness: z.enum(["ready", "unready", "plan_ready", "all"]).optional(),
    }),
    excludeIds: z.array(z.string().uuid()).max(500).default([]),
  }),
]);

const bulkApproveSchema = bulkBriefSelectorSchema.and(
  z.object({
    mode: z.enum(["assist", "auto"]).default("assist"),
    dispatch: z.enum(["plan", "immediate"]).default("plan"),
  }),
);

const bulkDismissSchema = bulkBriefSelectorSchema;
```

**Resolution-Helper** in einer neuen File `src/lib/brief-bulk-selector.ts`:

```typescript
// Resolves either body shape to a concrete brief-ID array, scoped to the project.
// For filter-shape: re-queries topic_briefs with the same WHERE-clause logic as
// GET /briefs, then subtracts excludeIds. The re-query is the race-safety guard
// the discovery doc §4 calls out — selecting "all 168" at T0 might match 173 at
// T1 if cron fires between.
export async function resolveBulkBriefIds(
  project: Project,
  body: BulkBriefSelectorInput,
): Promise<{ briefIds: string[]; reQueried: boolean }> {
  if ("briefIds" in body) {
    return { briefIds: body.briefIds, reQueried: false };
  }
  const conditions = buildBriefsWhere(project.id, body.filter); // shared with GET /briefs
  const rows = await db.select({ id: topicBriefs.id }).from(topicBriefs).where(and(...conditions)).limit(500);
  const allIds = rows.map((r) => r.id);
  const excluded = new Set(body.excludeIds);
  return { briefIds: allIds.filter((id) => !excluded.has(id)), reQueried: true };
}
```

**Refactor** der existierenden `WHERE`-Klausel-Composition aus `GET /briefs` (lines 98–127) in einen extrahierten `buildBriefsWhere(projectId, filter)` Helper, damit GET und Bulk dieselbe Logik teilen (Discovery verify-point 7 + 8).

### 3.2 Bulk-Approve — minimal-invasiver Patch

Existierender Handler bleibt strukturell gleich (sequenzielles `approveBrief()` mit Result-Bucketing, Option β). Patch:

1. Replace inline `briefIds` destructure mit `const { briefIds, reQueried } = await resolveBulkBriefIds(project, body)`.
2. Log `{ slug, reQueried, requested: briefIds.length, ... }` so Marcel im Log sieht ob Filter-Replay oder ID-Liste.
3. Response erweitert um `reQueried: boolean` + `totalMatched: number` (= `briefIds.length` post-exclude) so der Frontend die "168 matched filter → 173 approved" Diskrepanz-Banner-UX vom Discovery §4 bauen kann wenn nötig.

### 3.3 Bulk-Dismiss — gleicher Patch + Konstanz

Existierender Handler (single `UPDATE ... WHERE projectId AND inArray(id, briefIds) AND approvalStatus = 'pending'`) bleibt. Patch:

1. Selektor via `resolveBulkBriefIds` (gleich wie Approve).
2. **Constraint bleibt**: nur `approvalStatus = 'pending'` wird geflippt. `plan_pending` Briefs sind Marcel-vouched (Spec 63.6) und müssen einen expliziten Per-Brief-Dismiss durchlaufen. Filter-Shape `readiness=plan_ready` matched alle plan_pending — der Server returnt 0 dismissed counts, klare `skipped: <count>`-Surface im Response.

### 3.4 Pre-Flight-Cluster-Check Endpoint (neu)

```typescript
scopedBriefRoutes.post(
  "/:slug/briefs/bulk-preflight-cluster-check",
  zValidator("json", bulkBriefSelectorSchema),
  async (c) => {
    const slug = c.req.param("slug");
    const project = await resolveProject(slug);
    if (!project) return c.json({ ok: false, error: "project_not_found" }, 404);

    const { briefIds } = await resolveBulkBriefIds(project, c.req.valid("json"));
    if (briefIds.length === 0) {
      return c.json({
        ok: true,
        data: { totalMatched: 0, plan: { eligible: 0, needsCluster: 0 }, immediate: { eligible: 0, needsCluster: 0 } },
      });
    }

    // Single SQL aggregate. Gates mirror approveBrief() in apps/api/src/lib/brief-service.ts:
    //   plan-dispatch blocks ONLY: cluster_action='append_to_existing' AND cluster_id IS NULL
    //   immediate-dispatch blocks: cluster_action='create_new' OR cluster_id IS NULL
    // Both: also drop comparison_discovery (no cluster needed — see Spec 64.9 brief-service.ts).
    const [agg] = await db
      .select({
        total: sql<number>`count(*)::int`,
        planNeedsCluster: sql<number>`count(*) FILTER (WHERE cluster_action = 'append_to_existing' AND cluster_id IS NULL)::int`,
        immediateNeedsCluster: sql<number>`count(*) FILTER (WHERE (cluster_action = 'create_new' OR cluster_id IS NULL) AND source != 'comparison_discovery')::int`,
      })
      .from(topicBriefs)
      .where(and(eq(topicBriefs.projectId, project.id), inArray(topicBriefs.id, briefIds)));

    return c.json({
      ok: true,
      data: {
        totalMatched: agg?.total ?? 0,
        plan: {
          eligible: (agg?.total ?? 0) - (agg?.planNeedsCluster ?? 0),
          needsCluster: agg?.planNeedsCluster ?? 0,
        },
        immediate: {
          eligible: (agg?.total ?? 0) - (agg?.immediateNeedsCluster ?? 0),
          needsCluster: agg?.immediateNeedsCluster ?? 0,
        },
      },
    });
  },
);
```

Reine Read-Operation. Kein Side-Effect, kein Cost-Log. Wird von `BulkApproveModal` bei Open + bei Dispatch-Mode-Switch aufgerufen.

## 5. State Machine — keine Änderung

| Action  | Status Transition          | Side-Effects                                          |
|---------|---------------------------|-------------------------------------------------------|
| Approve | `pending → plan_pending` (dispatch=plan) / `pending → approved` (dispatch=immediate, via approveBrief) | Planner cron picks up plan_pending; immediate ruft executeDecision + triggerWithPreRunId pro Brief auf (Cost-Gate + Idempotenz). |
| Dismiss | `pending → rejected`       | UPDATE-only, kein BullMQ.                              |

`approveBrief()` discriminated-union behavior bleibt unverändert (siehe `apps/api/src/lib/brief-service.ts` ab Spec 64.9). Keine Migration nötig.

## 10. Discovered & Deviations

**Phase 1 (Backend):**

1. **Preflight SQL: `comparison_discovery` carve-out dropped.** Spec §3.4 originally included `AND source != 'comparison_discovery'` in the `immediate.needsCluster` FILTER, citing brief-service.ts. Re-reading [apps/api/src/lib/brief-service.ts:78](apps/api/src/lib/brief-service.ts:78) + [:129](apps/api/src/lib/brief-service.ts:129) confirmed the immediate gate is purely `cluster_action === 'create_new' || !clusterId` — **source-agnostic**. Comparison briefs have `cluster_action='comparison'` (not `create_new`) but `clusterId === null`, so `!clusterId` blocks them under immediate dispatch by design. The preflight now matches reality (no source filter); Marcel still has to assign a cluster to a comparison brief before immediate dispatch, which is the intended UX. Plan dispatch passes comparison briefs through (`'comparison' !== 'append_to_existing'`).

2. **`z.union(...).extend()` doesn't compose; use `z.intersection(unionSchema, z.object({...}))`.** The natural shape for `bulkApproveSchema` is "selector + mode + dispatch". Tried `bulkBriefSelectorSchema.extend({mode, dispatch})` — Zod rejects because the receiver is a `ZodUnion`, not a `ZodObject`. Tried `bulkBriefSelectorSchema.and(z.object({...}))` — works but produces less-readable inferred types. Settled on `z.intersection(bulkBriefSelectorSchema, z.object({mode, dispatch}))` — explicit and Zod-idiomatic. Logged as a footgun in root CLAUDE.md.

3. **`BriefsFilter` type widens to `field?: T | undefined` (Zod-inference compat).** Under `exactOptionalPropertyTypes`, a Zod-inferred `source?: T[] | undefined` is not assignable to a hand-written `source?: T[]`. Documented inline at [apps/api/src/lib/brief-bulk-selector.ts:63](apps/api/src/lib/brief-bulk-selector.ts:63). This is one instance of the existing root rule about Zod-inferred optional vs DB-defined types — no new rule needed.

4. **Test cleanup uses `beforeEach` reset for selector-lib tests** (rather than `afterAll`-only) — the per-test inserts otherwise leak into subsequent assertions because filter-shape queries match all `section=pending` briefs in the project scope. The HTTP tests get away with `afterAll`-only because each `it` uses fresh primary-keyword titles + cross-references inserted IDs explicitly.

**Phase 2 (Frontend):**

5. **Re-using the preflight endpoint as a "section total" probe.** The spec hinted at a separate count source for the "Select all N matching filter" banner. Phase 2 noticed `bulk-preflight-cluster-check` already returns `totalMatched`, so `maybeProbePendingTotal()` in [`BriefsPage.vue`](apps/web/src/pages/briefs/BriefsPage.vue) POSTs the filter-shape payload to the preflight endpoint when all-visible-selected + `pendingHasMore` is true. Saves an extra endpoint + keeps the count in lockstep with what the modal would compute. The probe short-circuits in two places (`selectAllMatching` already true OR `selectAllMatchingTotal` already set) so the two watchers (`selectedBriefIds` + `pendingBriefs`) can't form a loop.

6. **Mode-2 toggle-on-checkbox collapses, doesn't excludeIds.** Spec §4.4 left inverse-deselect as out-of-scope for V1. `onToggleSelect` in [`BriefsPage.vue`](apps/web/src/pages/briefs/BriefsPage.vue) treats a checkbox flip while in Mode-2 as a fresh per-card selection containing only that brief (Mode-1 again). The `currentSelectorPayload` computed still always returns an `excludeIds: []` array on the filter branch so a future PR can wire inverse-deselect without changing the body shape.

7. **`BulkSelectionBar.totalInFilter` prop needs `PropType<number | null>` cast.** Vue's `type: Number, default: null` doesn't widen to `number | null` in the inferred prop type — TypeScript narrows it to `number` and rejects the parent's `:total-in-filter="selectAllMatchingTotal"` bind. Fixed with `type: Number as unknown as PropType<number | null>` plus an inline comment ([`BulkSelectionBar.vue`](apps/web/src/components/ui/BulkSelectionBar.vue) line 67). Pattern is documented elsewhere as PropType usage but the `as unknown as` two-step cast is the idiomatic resolution for nullable scalar props.

8. **Mode-2 reset on filter chip change.** Phase 2 added watchers on `activeSources` + `activeReadiness` that call `resetSelection()` whenever the user toggles a source or readiness chip. Rationale: the Mode-2 selection is implicitly defined by the active filter; changing the filter without resetting would silently change what "all matching" means under the user. Cleaner to require an explicit re-selection.

9. **Preflight soft-fail keeps Submit enabled.** The modal's `submitDisabled` computed returns `false` when the preflight POST errored (transient server issue, timeout). Rationale: the server-side bulk-approve handler re-checks cluster eligibility per-brief at dispatch time anyway, so a missed preflight just degrades the UX hint, not correctness. Inline-documented at [`BulkApproveModal.vue`](apps/web/src/components/briefs/BulkApproveModal.vue) `submitDisabled`.

10. **Race-condition diagnostic gated on `expectedSelectedCount > 0`.** Banner only fires when (a) the action used filter-shape (`result.reQueried`), (b) the user had a meaningful selection before submit (`expectedSelectedCount > 0`), AND (c) the server's re-query produced a different total. Without (b), the empty Mode-1 paths (briefIds=[]) would mis-trigger.
