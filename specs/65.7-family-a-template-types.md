### 3.2 Slide Anatomy

#### comparison-grid-N (where N = 3, 5, 10):

```
Slide 1: Cover
  - LLM-generated headline
  - Category-icon + "Top N <Category>" label
  - Theme-aware background

Slide 2: Compare-Header
  - "What we're comparing" — category + criteria
  - Static-ish: derived from brief.recurring_metadata.formatConfig
  - "5 tools, 1 question: which is best for <use-case>?"

Slides 3 to N+2: Tool-Slides (data-bound)
  - Tool #K (running ranking)
  - Brand-logo (large)
  - Tool name (wordmark if available)
  - 2-3 key stats from tools.metadata: pricing, free-tier, key-feature
  - "Bullet-points" maxbe 3 lines (data-bound, NOT LLM)

Slide N+3: Verdict (NEW slide-type)
  - LLM-generated "And the winner is..." text
  - Highlights #1 tool with brand-color background
  - Brief verdict-reasoning (1-2 sentences)

Slide N+4: End-Slide
  - Composed via 65.9 component (data passed-through)
```

**Total slides:** 5+N slides (grid-3 = 8 slides, grid-5 = 10 slides, grid-10 = 15 slides)

**comparison-grid-10 concern:** 15 slides is at Instagram-max (10 slides per carousel-post until 2024, recently expanded to 20). Should V1 cap at 10 slides anyway to avoid platform-friction? See §11 Q1.

#### head-to-head-vs:

```

Slide 3: Tool B — full-slide profile
Slide 4: Side-by-side compare-slide — 3 criteria, both tools
Slide 5: Verdict — winner + reasoning
```

6 slides total — compact, focused.

### 3.3 Bi-Theme System (CORRECTED per 65.9 D2)

**Correct implementation: `deriveDsTokens(brandTokens, theme)` — NOT CSS-vars.**

Every existing slide component in the codebase (since Spec 60.0b) consumes `DsTokens`, never CSS-vars. 65.7 MUST follow this pattern, otherwise visual consistency breaks with:

- Engine Day 5 sample-template
- Spec 65.9 End-Slide-Components (which already consume `deriveDsTokens`)
- single-tool-spotlight (canonical reference template)

**Canonical composition pattern:**

```tsx
// Each slide component (Cover, Tool, Verdict, etc.) — top-level derivation
import { useMemo } from "react";
import { AbsoluteFill } from "remotion";
import { deriveDsTokens, type DsTokens } from "../../brand-tokens/derive";
import { resolveBrandTokens } from "../../lib/brand-tokens";

export const MySlide: React.FC<Props> = ({ brandTokens, theme, content }) => {
  // Resolve loose-typed input → typed BrandTokens, then derive DsTokens once.
  const tokens = useMemo(
    () => deriveDsTokens(resolveBrandTokens(brandTokens), theme),
    [brandTokens, theme],
  );

  return (
    <AbsoluteFill style={{ background: tokens.surface.base, color: tokens.ink.base }}>
      {/* … */}
    </AbsoluteFill>
  );
};
```

**Actual `DsTokens` shape** (from `packages/social/src/brand-tokens/derive.ts`):

- `tokens.surface.{base, raised}` — primary + raised-card backgrounds (theme-aware)
- `tokens.ink.{base, muted}` — primary + secondary text colors (theme-aware)
- `tokens.brand[300]/[500]/[900]` — numbered DS brand stops (theme-aware)
- `tokens.accent[500]` — accent emphasis (theme-aware)
- `tokens.border` — theme-aware divider color
- `tokens.typography.{fontFamily, fontFamilyMono, headingWeight, eyebrowLetterSpacing}`

(Marcel's discovery sketch used conceptual names like `ds.bg.primary` / `ds.text.onBrand` / `ds.brand.tertiary` — translate those to the actual token shape above. E.g. "ds.bg.primary" → `tokens.surface.base`, "ds.text.muted" → `tokens.ink.muted`.)

**Brand-color binding per tool:** Per-tool brand colors from `tool_brand_assets` (Spec 65.2) do NOT live on `tokens.brand.*` — they propagate through the per-tool `FamilyATool` payload as `tool.primaryColor` / `secondaryColor` / `tertiaryColor`. Slides use the fallback chain `tool.primaryColor ?? tokens.brand[500]` when rendering tool-specific accents (winner-flag, score badge, verdict gradient).

**Subpath import:** `@marketing-auto/social/ds-tokens` does not exist in `package.json` exports. Canonical convention (per single-tool-spotlight) is the relative import `../../brand-tokens/derive`. The barrel `@marketing-auto/social/brand-tokens` is also valid.

**Contrast-safety:** Brand-colors from 65.2 are NOT contrast-checked against bi-theme backgrounds. V1 mitigation: `deriveTertiaryColor(primary, theme)` in `_shared/family-a/helpers.ts` returns an oklch alpha-mix with white (dark theme) or black (light theme) — automatic text-contrast for tools with only 1 brand color. See §10 Risk-Analysis.

### 3.4 Content-to-Slide Mapping (Hybrid per Marcel-Decision)

**LLM-generated slides:**

1. **Cover headline** — Sonnet/Opus call per Memory D28 (content-generation)
2. **Verdict text** — Sonnet/Opus call (1-2 sentences "winner-reasoning")
3. **End-CTA wording** — handled by 65.9, not 65.7

**Data-bound slides:**

1. **Compare-Header** — derived from brief.recurring_metadata.formatConfig (category, criteria)
2. **Tool-Slides** — direct read from tools.metadata + brand-assets (no LLM)
3. **Side-by-side compare-slide (head-to-head)** — data-bound

**LLM-call budget per render:**

- Cover-headline: ~€0.05 (Sonnet, ~500 tokens output)
- Verdict-text: ~€0.05 (Sonnet, ~300 tokens output)
- End-CTA: ~€0.02 (handled by 65.9, Haiku-classifier picks pre-written CTA)
- **Total per render: ~€0.10-0.15**

**Where do LLM-calls happen?**

Two options:

**Option α — LLM-calls in brief-generator (65.5 extension):**

Brief-text from 65.5 already includes cover-headline + verdict-text fields.

Pros: LLM-calls happen once at brief-generation, render is pure data-binding
Cons: Brief-generator gets format-specific knowledge ("top_n_comparison briefs need verdict-text"); cross-spec scope-creep

**Option β — LLM-calls in render-trigger (65.10 or template-level):**

Renderer reads brief.briefText, calls LLM for cover/verdict at render-time.

Pros: 65.5 stays format-agnostic, 65.7 owns its LLM-needs
Cons: LLM-calls at render-time add latency, harder to retry separately, brief.briefText doesn't contain all renderable text

**Option γ — LLM-call helper used by 65.5 brief-generator:**

65.5's `buildTopNComparisonBriefText` function (already exists per implementor §4.2) is extended to generate `briefText` containing structured fields:

```typescript
{
  coverHeadline: string;        // LLM-generated
  compareHeaderText: string;    // data-derived
  verdictText: string;          // LLM-generated
  toolsPayload: ToolForRender[]; // data-bound
}
```

Pros: LLM-calls at brief-time (recoverable, observable), structured-output ready for any template, brief-generator orchestrates content + template-key
Cons: Brief-generator now knows about template-slide-anatomy

### Discovery-Recommendation: **Option γ (LLM-calls in brief-generator helpers)**

Reasoning:

1. **Brief-text-build is already brief-generator's responsibility** — 65.5's `buildTopNComparisonBriefText` exists exactly for this
2. **Recoverable & observable** — LLM-fails happen at brief-generation, brief stays in error-state, retryable
3. **Render becomes deterministic** — data-only render is testable, snapshottable
4. **Brief becomes the renderable artifact** — `brief.renderPayload` is the single source-of-truth
5. **Matches existing brief-pipeline pattern** — brief contains all rendered-text already in existing flows

**Trade-off accepted:** Brief-generator has light coupling to template-slide-anatomy via shared `RenderPayload` type. Acceptable — they're parts of one feature.

**Implementation:** 65.7 extends 65.5's brief-generator helpers OR 65.5 implementor's `buildTopNComparisonBriefText` gets updated to produce structured `renderPayload` instead of free-text.

```typescript
// packages/social/src/carousel-templates/shared/render-payload.ts
export const FAMILY_A_RENDER_PAYLOAD_SCHEMA = z.object({

    name: z.string(),
    rank: z.number().int().min(1),

    winnerToolId: z.string().uuid(),
```

## 4. Verdict-Slide Implementation Detail

Verdict-Slide is **new slide-anatomy** — Cover existed in 65.0 sample-template, Verdict is fresh.

```tsx
// slides/VerdictSlide.tsx
import { useMemo } from "react";
import { AbsoluteFill } from "remotion";
import { deriveDsTokens } from "../../../brand-tokens/derive";
import { resolveBrandTokens } from "../../../lib/brand-tokens";
import { deriveTertiaryColor } from "../../_shared/family-a/helpers";

interface VerdictSlideProps {
  winnerTool: FamilyATool;     // includes primaryColor / secondaryColor / tertiaryColor from tool_brand_assets
  reasoning: string;
  theme: "dark" | "light";
  brandTokens?: unknown;
}

export const VerdictSlide: React.FC<VerdictSlideProps> = ({ winnerTool, reasoning, theme, brandTokens }) => {
  const tokens = useMemo(
    () => deriveDsTokens(resolveBrandTokens(brandTokens), theme),
    [brandTokens, theme],
  );

  // Per-tool brand colors come from FamilyATool (not from tokens.brand.*).
  // Fallback chain: tool.primaryColor → tokens.brand[500] keeps the slide
  // valid for tools whose brand-asset row is unset.
  const winnerPrimary   = winnerTool.primaryColor   ?? tokens.brand[500];
  const winnerSecondary = winnerTool.secondaryColor ?? tokens.brand[300];
  const textContrast    = winnerTool.tertiaryColor  ?? deriveTertiaryColor(winnerPrimary, theme);

  return (
    <AbsoluteFill
      style={{
        background: `linear-gradient(135deg, ${winnerPrimary} 0%, ${winnerSecondary} 100%)`,
        color: "#fff",
      }}
    >
      {/* "And the winner is" label, winner logo, name, reasoning — text colors
          use textContrast (oklch alpha-mix when tertiaryColor absent). */}
    </AbsoluteFill>
  );
};
```

**Bi-theme detail:** Verdict-slide uses **brand-gradient background** (not theme-bg). The `tokens` object still derives bi-theme-aware ink + surface for the `DsTop` + `DsFoot` overlays. Tertiary-color (or its computed fallback) handles text-contrast against the brand gradient.

## 10. Risk Analysis

| Risk | Severity | Mitigation |
|---|---|---|
| Bi-theme contrast issues (dark brand-color on dark bg) | High | Tertiary-color fallback + contrast-ratio check helper (WCAG AA min) |
| 10-tool comparison-grid-10 layout-density | Medium | Layout-validation render-time + 12-slide cap per V1 |
| Verdict-slide brand-gradient looks generic across all renders | Medium | Use brand-color-extracted from logo via 65.2's lobe-icons gradient parser |
| LLM-cover-headline drift toward AI-generic patterns | High | Style-curation in prompt (Master-Spec Risk #1: "Family A 'AI-generic' feel"); few-shot examples in prompt |
| Brand-asset missing for tool (per-locale issue from 65.2 D1) | Medium | Pre-flight gate (65.5 already implements `ensureBrandAssetsAvailable`) |
| Render-time exceeds 120s abort for grid-10 | Low | Engine Day 6 added 120s abort-controller; 15-slide render ~30s well within |
| Bi-theme CSS-var convention drifts across templates | Medium | Shared `theme/types.ts` enforces TypeScript-typed theme-keys |
| RenderPayload schema-drift between brief-generator + template | High | Single shared schema in packages/social/, both 65.5 + 65.7 import from it |
| Verdict winner is sometimes ambiguous (tie/multi-winner) | Medium | LLM-prompt explicitly asks for single-winner; tie → pick by stars-desc |
| Family A "AI-generic" feel | High | Multiple LLM-cover-style-variants pre-curated; rotate per run |

**Patterns surfaced (candidates for future CLAUDE.md additions):**
- "Family A render-server helper" — `renderMultiSlideComposition(compositionId, input, totalSlides, slug)` cuts ~25 lines per new multi-slide template by abstracting the for-loop over `slideIndex`. Reusable for any future multi-slide carousel template.
- "Per-template `_extra` payload extension" — generalising Spec 60.1's `_verdict` pattern. When LLM output needs more fields than `GeneratedContent` allows, `_<tplKey>Extra` carries the typed payload + a single-cast escape from `GeneratedContent`. Each template's `render()` does the cast once.
- "Cross-template slide component reuse" — grid-3 slide components are imported by 3 other templates. Different from `_shared/` because the components stay co-located with their canonical template, and import direction documents the visual relationship (grid-5 IS a 5-tool grid-3).
- "Bi-theme via DS-tokens, not CSS-vars" — `deriveDsTokens(brandTokens, theme)` once-per-slide is the canonical pattern. Spec's CSS-var system would be drift from convention.
