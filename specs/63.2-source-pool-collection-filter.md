# Spec 63.2 — Source-Pool Collection-Filter

_Theme 63 Sub-Spec — verhindert dass Social-Post-Selector aus Collections pickt für die keine Templates existieren._
_Status: Draft._
_Voraussetzung: 63.1 gemerged (Author-Filter)._

---

## 1. Problem

`pickFromSuggestionPool` zieht Articles aus allen Collections (außer `authors` durch 63.1), aber die Social-Templates sind nur eligible für `tools` und `comparisons`. Im KW21-Plan landeten:

| collection | items im Plan | eligible für Templates? |
|---|---|---|
| tools | 9 | ✅ |
| comparisons | 1 | ✅ |
| usecases | 2 | ❌ |
| ki-wissen | 1 | ❌ |
| (authors) | 1 | ❌ (gefiltert durch 63.1) |

**Konsequenz:** 3-4 von 17 article-derived social_posts würden zur Generation-Zeit am Eligibility-Check sterben oder still skippen. Plan-Cost wird falsch berechnet (estimate-Cost-Step rechnet sie ein), tatsächliche Item-Count nach Generation ist niedriger als geplant.

## 2. Ziel

Source-Pool-Selectors filtern nur Articles aus Collections die mindestens 1 Social-Template haben. Aktuell: `tools` und `comparisons`. Erweiterbar wenn Phase-E-Templates kommen.

**In Scope:**
- Filter in `pickFromSuggestionPool`, `pickFromRefreshSuggestions`, `countSuggestionPool` (alle drei Stellen aus `packages/planner/src/social-source-selectors.ts`)
- Allowed-Collection-Liste als shared constant in `packages/planner/src/`
- Test-Coverage

**Out of Scope:**
- Per-Article Eligibility-Check via templateRegistry (komplexer, lebt im Spec 63.x falls D.3 ausgewählt)
- Phase-E-Template-Implementation
- Counter-Adjustment für shortfall-Reporting

**Aufwand:** 30 Min.

## 3. Architektur

### 3.1 Allowed-Collections Constant

`packages/planner/src/social-eligible-collections.ts`:

```ts
/**
 * Article collections that have at least one social-post template.
 * 
 * Current templates (Stand 2026-05):
 * - comparison-grid-4/3, verdict-per-use-case → comparisons
 * - single-tool-spotlight, pro-con-verdict → tools
 * 
 * When Phase-E templates (workflow-impact-stack, definition-card, etc.) 
 * arrive, add ki-wissen, usecases, etc. here.
 */
export const SOCIAL_ELIGIBLE_COLLECTIONS = ["tools", "comparisons"] as const;
```

**Warum als constant Array statt aus templateRegistry derived:** Die Eligibility-Logik in templateRegistry ist per-Article (braucht Tool-Count, Pro-Count etc.). Pool-Filter braucht nur collection-Level-Check. Constant ist günstiger + klar dokumentiert.

### 3.2 Filter-Anwendung

Alle drei Selectors in `packages/planner/src/social-source-selectors.ts`:

```ts
import { inArray } from "drizzle-orm";
import { SOCIAL_ELIGIBLE_COLLECTIONS } from "./social-eligible-collections";

// In pickFromRefreshSuggestions:
.where(and(
  // ... existing conditions ...
  ne(articles.collection, "authors"),  // 63.1
  inArray(articles.collection, SOCIAL_ELIGIBLE_COLLECTIONS),  // 63.2 NEU
))

// Gleicher Pattern für pickFromSuggestionPool und countSuggestionPool
```

**Note:** `ne(articles.collection, "authors")` aus 63.1 wird durch `inArray()` redundant gemacht — authors ist nicht in der allow-list. Kann gleich mit raus aus den drei Stellen, oder defensive belassen. Implementor entscheidet.

## 9. Implemented (2026-05-21)

### Deviations from spec

- **Dropped the `ne(articles.collection, "authors")` line** in all three selectors. Spec §3.2 explicitly left this as implementor choice ("kann gleich mit raus oder defensive belassen"). Chose the cleaner path — `inArray(SOCIAL_ELIGIBLE_COLLECTIONS_ARR)` subsumes the authors exclusion. The 63.1 canonical-comment was replaced with `// Spec 63.2: only collections with at least one social template.`
- **Constant ships as `as const` tuple + mutable typed array.** `SOCIAL_ELIGIBLE_COLLECTIONS = ["tools", "comparisons"] as const` plus a module-level `SOCIAL_ELIGIBLE_COLLECTIONS_ARR: SocialEligibleCollection[] = [...SOCIAL_ELIGIBLE_COLLECTIONS]` because Drizzle's `inArray()` rejects `readonly` tuples (root CLAUDE.md rule). The `as const` form stays the public API; the mutable array is a private adapter for the Drizzle call sites.

### Discovered during implementation

- **Pre-existing 63.1 tests baked `collection: "blog"` as their "should be included" baseline.** After narrowing the allow-list to `tools` + `comparisons`, those fixtures silently broke — `blog` is no longer eligible. Fix: bumped four fixture rows from `"blog"` → `"tools"` in `packages/planner/test/social-source-selectors.test.ts`. The 63.1 `describe` block's assertion semantics are preserved (eligible-baseline-row IS returned, authors row is NOT) but the baseline collection changed. Documented as a new "Common Mistake" entry in `packages/planner/CLAUDE.md`.
- **The "Spec 62.8: production-run execution" export block in `packages/planner/src/index.ts` is Marcel's WIP** — appeared in my diff but was already present in the uncommitted state when 63.2 started. Not modified by 63.2; flagged here so the upcoming commit's diff doesn't surprise the reviewer.
