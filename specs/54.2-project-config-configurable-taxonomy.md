**Phase:** 54 / A — Foundations (2 of 3)
**Estimated Effort:** 2 days (~14-16 focused hours over 3-4 sessions)
**Dependencies:** Spec 54.0 (Content Planner ADR), Spec 54.1 (TopicBrief & Source Abstraction)

## Goal

Introduce **Project Configuration** as a versioned first-class entity that defines the "DNA" of a project: which intent types its pillars expect, which master prompts drive generation, which signal sources are active (for 54.4+), which automation rules apply (for Phase 2 future).

Spec 54.2 delivers:

1. A new DB table `project_configurations` (versioned per project) with Drizzle schema, Zod schemas, and type-aliases (`ProjectConfiguration`, `NewProjectConfiguration`).
2. A nullable `articles.project_config_version_id` column linking each article to the config version it was generated under.
3. A nullable `content_pillars.intent_taxonomy_override` column for per-pillar taxonomy overrides (hybrid model: project-level default + pillar-level override).
4. **Auto-seed migration**: on migrate, every existing project gets a v1 config row with hardcoded code-defaults, and all existing articles are back-stamped to that v1 (resolves Open Question Q2 from ADR option-c).
5. Refactor of the hardcoded `EXPECTED_SPOKE_INTENTS` constant in `detect-content-gaps.ts` to read from the active project config (with pillar-override fallback to project-default).
6. Refactor of `OutlineStep`, `DraftStep`, `SelfReviewStep`, `LocalizeArticleStep` to read their system prompts from `master_prompts` config field, with code-default fallback if the config field is empty.

After this spec lands:
- `EXPECTED_SPOKE_INTENTS` no longer exists as a hardcoded constant
- A project can have different intent types per pillar (e.g., toolwiki = `comparison/pricing/alternatives/use_case`, future automotive project = `model_review/spec_comparison/dealership_local`)
- Master prompts for article generation are editable in DB (no UI yet — that's 54.9 — but direct SQL works)
- Every new article records its `project_config_version_id` for audit
- A **post-spec manual task** (Claude Code session, no Anthropic API) fills the actual config values for each project from observation of their existing content

## What this is NOT

- Not building UI for editing project configurations — that's Spec 54.9
- Not changing Cold-Start phases 2b/3/4 to write a v1 config on new project creation — that's a small follow-up in this spec but the **Cold-Start integration test is deferred** to 54.7 where Cold-Start is also touched
- Not refactoring the `/suggest` and `/generate` route logic (still in 54.3)
- Not building the TopicRoutingPolicy (54.3)
- Not implementing `automation_rules` interpretation — column exists, empty in Phase 1, consumed in future Phase 2 spec
- Not implementing `topic_scope` schema beyond a minimal `{ languages: string[], exclusions: string[] }` — full scope shape lives in 54.5 where Trend Discovery is the first consumer
- Not implementing **prompt versioning UI / A/B testing** — that's a future spec on top of 54.2's versioning foundation
- Not migrating Cold-Start step prompts (those stay in code; only article-generation prompts move to config)
- Not deleting the hardcoded prompt strings from step files — they become fallback constants used when the config field is null

## Architecture

### Versioning model

Project Configuration is versioned per project. The `version` column auto-increments per project (not globally). At any time, exactly one config per project has `status = 'active'`; others are `'draft'` (not yet activated) or `'archived'` (previously active).

```
project P:
  config v1, status=archived, activated_at=2025-01-01, archived_at=2026-03-15
  config v2, status=active,   activated_at=2026-03-15
  config v3, status=draft,    activated_at=null

Article A1 created 2025-06-01 → project_config_version_id = v1.id
Article A2 created 2026-04-01 → project_config_version_id = v2.id
```

This gives us a clean audit trail: "which article was generated under which config version" without freezing config fields onto every article row.

**Rule (enforced via partial unique index):** At most one `active` config per project at any time.

### Why a separate table, not JSONB on `projects`

The ADR Section 1.5 already resolved this (Decision D2): own table, versioned. The rationale is auditability — when Marcel iteratively refines master prompts over months, we want to know which prompt version produced which article. A JSONB column on `projects` would either freeze history into every article (heavy) or lose it on each update (no audit). A versioned side-table cleanly separates "current shape" from "historical shape".

### Intent taxonomy: hybrid model

Per user direction, the model is:
- **Project default**: `project_configurations.intent_taxonomy_default` (JSONB, array of strings)
- **Per-pillar override** (optional): `content_pillars.intent_taxonomy_override` (JSONB nullable, array of strings)
- **Resolution**: when computing expected intents for a pillar, prefer the pillar's override; if null, use the project default

This avoids embedding pillar UUIDs as JSONB keys (which would be fragile to pillar renaming/deletion). Pillar overrides live on the pillar row, which is the natural ownership boundary.

Concrete example (toolwiki):
```
project_configurations.intent_taxonomy_default
  = ["comparison", "pricing", "alternatives", "use_case"]

content_pillars[pillar_id=X "AI Image Tools"].intent_taxonomy_override
  = ["comparison", "pricing", "free_alternatives", "use_case", "ethics"]
  (ethics is added for image generation tools specifically)

content_pillars[pillar_id=Y "AI Code Tools"].intent_taxonomy_override
  = null  → falls back to project default
```

The gap-detection refactor (deliverable 5) uses this resolution every time it computes "what intents does cluster C expect?". Cluster's pillar is loaded, override checked, default used as fallback.

### Master prompts: config-aware resolver with code-default fallback

The current state: every step file has a hardcoded `const SYSTEM_PROMPT = "..."` near the top of the file. These are good prompts that ship the product; they shouldn't be lost.

Target state: each step calls a tiny resolver:

```typescript
const systemPrompt = await resolveMasterPrompt({
  projectId: ctx.projectId,
  promptKey: "article.outline",
  fallback: OUTLINE_STEP_DEFAULT_PROMPT,  // existing constant, kept
});
```

If `project_configurations.master_prompts["article.outline"]` is set, use it. Otherwise fall back to the constant. This means **on day-one after deploy, behavior is identical** (config has no overrides yet, all fallbacks trigger). Marcel can iteratively override prompts via direct SQL during the manual-fill follow-up, then later via UI in 54.9.

Prompt keys (this is the canonical set 54.2 supports):

```
article.outline
article.draft
article.self_review
article.localize.fresh      (localize stub for EN sibling)
article.localize.translate  (full cultural adaptation)
```

Other prompts (Cold-Start, Research, HeroImage, SchemaExtension) stay hardcoded for this spec. They become configurable in future specs as needed.

### Auto-seed migration strategy

The migration runs in two phases:

**Migration 0XXX (project_configurations):**
1. `CREATE TABLE project_configurations` with all columns
2. `CREATE INDEX`es
3. Seed v1 row for every existing project:
   ```sql
   INSERT INTO project_configurations (project_id, version, status, ...)
   SELECT id, 1, 'active', ...defaults... FROM projects;
   ```
   Defaults are hardcoded SQL literals matching the current code values (intent taxonomy = `'["comparison","pricing","alternatives","use_case"]'::jsonb`, master_prompts = `'{}'::jsonb` → all use fallback).

**Migration 0XXY (articles back-stamp + pillar override):**
1. `ALTER TABLE articles ADD COLUMN project_config_version_id UUID REFERENCES project_configurations(id) ON DELETE SET NULL`
2. `ALTER TABLE content_pillars ADD COLUMN intent_taxonomy_override JSONB`
3. Back-stamp existing articles:
   ```sql
   UPDATE articles SET project_config_version_id = (
     SELECT id FROM project_configurations
     WHERE project_id = articles.project_id AND status = 'active'
     LIMIT 1
   );
   ```
4. Create index on `articles(project_config_version_id)` for audit queries

Splitting into two migrations follows the 54.1 lesson (FK ordering issues with Drizzle). Project configs are created first; the articles FK is set in the second migration.

### Post-spec manual fill task

Once the migration has seeded v1 configs with code-defaults, the actual project-specific values still need to be filled. For toolwiki specifically:
- Per-pillar intent taxonomies need to be inspected (what intent types actually appear in each pillar's articles?)
- Master prompts may want toolwiki-specific tweaks (e.g., affiliate-disclaimer hints in the draft prompt)
- Signal sources need to be set (`producthunt: true, hackernews: true, reddit: true, github: true, vendor_rss: true, dataforseo_trends: false`)
- Topic scope `languages: ["de", "en"]`, `exclusions: []` to start

This is a **post-spec manual task** done in a dedicated Claude Code session **without Anthropic API calls** — Claude Code reads the project's articles/pillars from DB, proposes config values, Marcel approves and runs SQL. Spec 54.2's acceptance criteria do NOT include the manual fill; that's tracked as a follow-up issue.

### Backward compatibility

Throughout 54.2:
- `EXPECTED_SPOKE_INTENTS` constant is removed; its callers read from config
- All existing articles get a `project_config_version_id` via back-stamp
- Step files keep their default prompt constants as fallbacks
- No UI change; no API change
- All existing tests must stay green

The single behavioral change is: **after deploy, a new project created via Cold-Start has v1 config defaults applied automatically**. This is desirable — it means Cold-Start can stop hardcoding the same values inline.

### DB Schema — project_configurations

`packages/db/migrations/0XXX_project_configurations.sql`:

```sql
CREATE TABLE project_configurations (
  id                       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id               UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  version                  INTEGER NOT NULL,
  status                   TEXT NOT NULL DEFAULT 'draft' CHECK (status IN (
                             'draft', 'active', 'archived'
                           )),

  -- Intent taxonomy (project-level default; pillars may override)
  intent_taxonomy_default  JSONB NOT NULL DEFAULT '["comparison","pricing","alternatives","use_case"]'::jsonb,

  -- Master prompts (keyed by prompt-key; empty → fallback to code defaults)
  master_prompts           JSONB NOT NULL DEFAULT '{}'::jsonb,

  -- Topic scope (minimal in 54.2; expanded by 54.5)
  topic_scope              JSONB NOT NULL DEFAULT '{"languages":["de","en"],"exclusions":[]}'::jsonb,

  -- Active external signal sources (consumed by 54.4)
  signal_sources           JSONB NOT NULL DEFAULT '{}'::jsonb,

  -- Automation rules (Phase 2 future)
  automation_rules         JSONB NOT NULL DEFAULT '[]'::jsonb,

  -- Audit
  created_at               TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  activated_at             TIMESTAMPTZ,
  archived_at              TIMESTAMPTZ,

  UNIQUE (project_id, version)
);

CREATE INDEX project_configurations_project_idx
  ON project_configurations(project_id);

-- At most one active config per project
CREATE UNIQUE INDEX project_configurations_one_active_per_project
  ON project_configurations(project_id)
  WHERE status = 'active';

-- Seed v1 for every existing project
INSERT INTO project_configurations (project_id, version, status, activated_at)
SELECT id, 1, 'active', NOW() FROM projects;
```

### Master Prompt Resolver

`packages/pipelines/src/config/load-active-config.ts`:

```typescript
import { and, eq } from "drizzle-orm";
import { db, projectConfigurations, type ProjectConfiguration } from "@marketing-auto/db";

// In-process cache: projectId → active config + cached-at timestamp.
// Cache TTL is short (60s) so that config edits via SQL/UI take effect quickly
// without round-tripping the DB on every Anthropic call.
const cache = new Map<string, { config: ProjectConfiguration; cachedAt: number }>();
const TTL_MS = 60_000;

/**
 * Loads the active project configuration for a project, with a 60s in-process cache.
 *
 * If no active config exists (shouldn't happen post-migration), throws.
 * Callers should not catch — missing active config is a system invariant violation.
 */
export async function loadActiveConfig(projectId: string): Promise<ProjectConfiguration> {
  const cached = cache.get(projectId);
  if (cached && Date.now() - cached.cachedAt < TTL_MS) {
    return cached.config;
  }

  const [config] = await db
    .select()
    .from(projectConfigurations)
    .where(and(
      eq(projectConfigurations.projectId, projectId),
      eq(projectConfigurations.status, "active"),
    ))
    .limit(1);

  if (!config) {
    throw new Error(
      `No active project_configuration for project ${projectId}. ` +
      `This is a system invariant violation — every project must have v1+ active.`,
    );
  }

  cache.set(projectId, { config, cachedAt: Date.now() });
  return config;
}

/**
 * Clears the cache. Use in tests, or after manual SQL edits in dev.
 */
export function clearConfigCache(projectId?: string): void {
  if (projectId) cache.delete(projectId);
  else cache.clear();
}
```

`packages/pipelines/src/config/resolve-master-prompt.ts`:

```typescript
import { loadActiveConfig } from "./load-active-config.ts";
import type { MasterPromptKey } from "@marketing-auto/db";

/**
 * Resolves a master prompt: checks active project config, falls back to code default.
 *
 * If the config has an override for `promptKey`, returns the override.
 * Otherwise returns `fallback` (the constant currently hardcoded in the step file).
 *
 * This contract is the migration path: step files keep their default constants
 * until Marcel decides to override via SQL/UI.
 */
export async function resolveMasterPrompt(args: {
  projectId: string;
  promptKey: MasterPromptKey;
  fallback: string;
}): Promise<string> {
  const config = await loadActiveConfig(args.projectId);
  const override = config.masterPrompts[args.promptKey];
  return override?.prompt ?? args.fallback;
}
```

`packages/pipelines/src/config/resolve-intent-taxonomy.ts`:

```typescript
import { eq } from "drizzle-orm";
import { db, contentPillars, type IntentTaxonomy } from "@marketing-auto/db";
import { loadActiveConfig } from "./load-active-config.ts";

/**
 * Resolves the expected intent taxonomy for a cluster's pillar.
 *
 * Resolution order:
 * 1. If the pillar has `intent_taxonomy_override`, use that
 * 2. Otherwise use the project's `intent_taxonomy_default`
 *
 * The caller passes the pillar ID directly (cluster → pillar resolution
 * happens in the caller; gap-detection already loads clusters with their
 * pillar IDs joined).
 */
export async function resolveIntentTaxonomy(args: {
  projectId: string;
  pillarId: string | null;
}): Promise<IntentTaxonomy> {
  const config = await loadActiveConfig(args.projectId);

  if (!args.pillarId) {
    return config.intentTaxonomyDefault;
  }

  const [pillar] = await db
    .select({ override: contentPillars.intentTaxonomyOverride })
    .from(contentPillars)
    .where(eq(contentPillars.id, args.pillarId))
    .limit(1);

  return pillar?.override ?? config.intentTaxonomyDefault;
}
```

### Refactor: detect-content-gaps.ts

Current state (problematic — hardcoded):
```typescript
const EXPECTED_SPOKE_INTENTS = ["comparison", "pricing", "alternatives", "use_case"] as const;
```

Target state:
```typescript
import { resolveIntentTaxonomy } from "@marketing-auto/pipelines/config";

// Inside the step's execute() method, for each cluster being analyzed:
const expectedIntents = await resolveIntentTaxonomy({
  projectId: input.projectId,
  pillarId: cluster.pillarId,  // already loaded in existing query
});

// Use `expectedIntents` wherever `EXPECTED_SPOKE_INTENTS` was used:
for (const intent of expectedIntents) {
  if (!cluster.intentsPresent.includes(intent)) {
    // emit missing_spoke_type gap as before

Cache implication: `resolveIntentTaxonomy` calls `loadActiveConfig` once per project, then queries `contentPillars` once per cluster. For a project with 50 clusters, that's 1 + 50 queries per gap-detection run. Acceptable, but if it shows up in performance tests later, we can batch-load all pillar overrides into a Map first.

### Cold-Start Integration (small follow-up only)

### Post-Spec Manual Fill Task

Once the spec is shipped and green, a dedicated Claude Code session fills in real config values for toolwiki. This session runs in `apps/api/` or a dedicated `scripts/` folder, **does not call Anthropic**, and does the following:

```
For each existing project:
  1. SELECT articles WHERE project_id = X, group by pillar_id, count intent_types
     → propose intent_taxonomy_override per pillar based on observed intents
  2. SELECT clusters WHERE project_id = X, group by pillar_id, list satellite_keywords
     → confirm pillar coverage matches taxonomy
  3. For toolwiki specifically:
     - signal_sources = { producthunt: true, hackernews: true, reddit: { enabled: true, subreddits: [...] }, ... }
     - topic_scope = { languages: ["de", "en"], exclusions: [potentially competing big-brand names] }

## Open Questions / Decisions Made

**Decision 1: Auto-seed at migration, not at runtime.**
The seed runs once, in SQL, deterministically. A runtime "ensure config exists" check would be slower and harder to audit. Per user direction: option (c) hybrid — migration seeds with hardcoded defaults; a post-spec manual Claude Code session fills real values without Anthropic API.

**Decision 2: Master prompts moved are only the article-generation prompts.**
Outline, Draft, SelfReview, Localize (×2). Cold-Start, Research, HeroImage, SchemaExtension stay hardcoded. Rationale: focus on the prompts Marcel actually wants to iterate on. Cold-Start prompts run once per project; HeroImage/Research/Schema are less voice-sensitive.

**Decision 3: Hybrid intent taxonomy — project default + pillar override.**
Per user direction. Avoids fragile pillar-ID-as-JSONB-key pattern. Pillar override lives where pillars live (`content_pillars` table). Resolution is "pillar override wins, else project default".

**Decision 4: Back-stamp existing articles to v1.**
Per user direction option (b). Migration sets `project_config_version_id` for all existing articles to their project's v1. Cleaner audit queries; no "null forever" rows.

**Decision 5: Two sequential migrations (0XXX + 0XXY).**
Per user direction. Following 54.1's lesson — FK ordering issues with Drizzle. First migration creates `project_configurations` and seeds; second migration adds `articles.project_config_version_id` FK and back-stamps.

**Decision 6: `topic_scope` minimal in 54.2 — full shape in 54.5.**
Per user direction. Column exists with `{ languages, exclusions }` schema. 54.5 (Trend Synthesis) is the first consumer and will expand the schema when it knows what it needs.

**Decision 7: In-process 60s cache for active config.**
Loading config on every Anthropic call would round-trip the DB. 60s TTL is short enough that SQL edits take effect quickly during dev, long enough to amortize across batch operations. `clearConfigCache()` exists for tests and manual dev workflows.

**Decision 8: `loadActiveConfig` throws on missing active config.**
A missing active config post-migration is a system invariant violation, not a recoverable state. Throw loudly. Callers should not catch — the operator must fix the data.

**Decision 9: Step files keep default prompts as `*_DEFAULT_PROMPT` constants.**
Renamed for clarity, not deleted. They are the migration safety net: on day-one, no config has overrides, so every step uses its default. Identical behavior to pre-migration.

**Decision 10: Cold-Start integration is minimal — just the project-creation hook.**
A bigger Cold-Start refactor (writing actual derived intent taxonomies, etc.) is out of scope. Only the "create v1 row on new project" is needed; everything else is the post-spec manual fill task.

**Decision 11: No API endpoints for project_configurations in 54.2.**
Same discipline as 54.1's Decision 8. The table is internal until 54.9's UI redesign. Inspection via SQL during dev.

## Discovered During Implementation

**Dynamic prompt interpolation means `*_DEFAULT_PROMPT` is scoped inside `execute()`, not at module level.**
`OutlineStep`, `DraftStep`, and `LocalizeArticleStep` build their system prompt strings with runtime values (`input.clusterName`, `input.authorInstruction`, locale labels). These cannot be top-level constants. The naming convention (`OUTLINE_STEP_DEFAULT_PROMPT`) is preserved for intent clarity — the const is just scoped inside `execute()` or a private method instead of at module level. Only `SelfReviewStep`, whose prompt has zero interpolation, achieved a true module-level constant.

**`detect-content-gaps.ts` was importing from `drizzle-orm` directly.**
The pre-existing file violated the workspace rule (operators must come from `@marketing-auto/db`). This was fixed as part of the refactor. If you find similar direct `drizzle-orm` imports in other adapter/pipeline files when touching them, fix them in the same PR.

## Deviations

**`*_DEFAULT_PROMPT` naming: module-level vs scoped.**
The spec's implementation example implied module-level constants for all steps. In practice, steps with dynamic interpolation keep the constant inside the function scope. This is functionally identical — it's the scope of the variable, not its name or content, that differs. No behavioral change.
