### 3.1 renderPayload Bridge (Marcel-Decision: 65.10 extends buildRenderPayload)

The bridge converts brief.recurring_metadata + tools-data + brand-assets → typed renderPayload for templates.

```typescript
// apps/api/src/lib/article-output/build-render-payload.ts

interface BuildRenderPayloadInput {
  brief: TopicBrief;          // has recurring_metadata, briefText, etc
  projectId: string;
}

interface RenderPayload {
  templateKey: string;
  theme: 'light' | 'dark';
  brandTokens: BrandTokens;   // per-project tokens
  tools: FamilyATool[];       // hydrated from articles + tool_brand_assets
  
  // LLM-generated content (this spec's responsibility):
  cover: FamilyACoverContent;     // headline, subheadline, category
  compareHeader: FamilyACompareHeaderContent;
  verdict: FamilyAVerdictContent; // winner, reasoning
  
  // End-slide (from brief.recurring_metadata):
  endSlide: EndSlideData;     // discriminated-union from 65.9
  
  // Family B (when 65.8 lands):
  hook?: { rendered: string; variables: Record<string, string> };
}

export async function buildRenderPayload(input: BuildRenderPayloadInput): Promise<RenderPayload> {
  const { brief, projectId } = input;
  const meta = brief.recurringMetadata!;
  
  // 1. Load tools data (with brand-assets per per-locale resolution from 65.2 D1)
  const tools = await loadToolsWithBrandAssets(meta.formatConfig.toolIds, projectId);
  
  // 2. Resolve theme from definition or default
  const definition = await getRecurringDefinition(meta.definitionId);
  const theme = definition.formatConfig?.theme ?? 'light';
  
  // 3. LLM-calls for Cover + Verdict (Sonnet/Opus per Memory D28)
  const [cover, verdict] = await Promise.all([
    generateCoverContent({ tools, formatType: meta.formatType, formatConfig: meta.formatConfig, briefText: brief.briefText }),
    generateVerdictContent({ tools, formatType: meta.formatType, briefText: brief.briefText }),
  ]);
  
  // 4. Compare-Header derived from formatConfig
  const compareHeader = buildCompareHeader(meta.formatType, meta.formatConfig);
  
  // 5. Brand tokens for the active project
  const brandTokens = await loadBrandTokens(projectId);
  
  // 6. End-slide from brief (already selected by 65.5 brief-generator)
  const endSlide: EndSlideData = meta.formatConfig.selectedEndSlide as EndSlideData;
  
  return {
    templateKey: meta.formatConfig.selectedTemplateKey,
    theme,
    brandTokens,
    tools,
    cover,
    compareHeader,
    verdict,
    endSlide,
  };
}
```

### 3.3 Approval-to-Render-Trigger UX Evaluation (Marcel: Discovery evaluiert)

**Option α — Approved brief immediately triggers render (5s lag):**

```typescript
// In existing brief-approval flow (Settings/Planner page):
PATCH /api/projects/:slug/topic-briefs/:id/status { status: 'approved' }
   ↓
   handler updates brief.status='approved'
   ↓

     await enqueueArticleOutputJob({ briefId, projectId })
   ↓
```

Pros:
- Best UX — Marcel approves, file ready in ~30-40s
- Standard BullMQ event-driven pattern
- No polling-overhead

Cons:
- Render-failure surfaces 30-60s after approval (Marcel might already navigated away)

**Option β — Approved brief landed in 'pending-render' queue, cron every 5min:**

Pros: Simpler, no event-driven worker
Cons: 5min lag feels slow, redundant with BullMQ Redis already there

**Option γ — Marcel manual approval includes render-trigger button (one-click approve+render):**

```vue
<q-btn @click="approveAndRender(brief)">Approve & Render</q-btn>
<q-btn @click="approve(brief)">Approve only (no render)</q-btn>
```

Pros: Explicit Marcel control
Cons: Marcel-friction (extra decision per approval); kept defaults?

### Discovery-Recommendation: **Option α (Auto-render on approval)**

Reasoning:

1. **Marcel decision was "Auto-render on brief approval + Marcel can re-trigger via UI button"** — α matches this directly
2. **BullMQ is already in-stack** — Redis-coordinator pattern (Memory D17) handles retries (but Marcel-Decision: no-retry, so just enqueue-once)
3. **Re-trigger button covers edge-cases** — if render fails, Marcel re-triggers manually
4. **Render-failure UX**: immediate admin-notification per Marcel-Decision — Marcel sees error in Notifications-Panel even if navigated away

### 3.5 Render-Worker Implementation

**File:** `apps/api/src/workers/article-output.worker.ts`

```typescript
import { Worker } from 'bullmq';
import { logger } from '@marketing-auto/shared';

const worker = new Worker('article-output', async (job) => {
  const { briefId, projectId } = job.data;
  
  // No retries per Marcel-Decision — fail-fast
  // BullMQ default would retry 3x — override to attempts=1
  
  try {
    // 1. Load brief
    const brief = await getTopicBriefById(briefId);
    if (brief.status !== 'approved') {
      return { status: 'skipped', reason: 'brief-not-approved' };
    }
    
    // 2. Build renderPayload (includes LLM cover + verdict calls)
    const renderPayload = await buildRenderPayload({ brief, projectId });
    
    // 3. Create articles row (status='draft')
    const article = await createRecurringContentArticle({
      brief,
      renderPayload,
      projectId,
    });
    
    // 4. Render carousel via 65.7 templates
    const slideBuffers = await renderCarouselTemplate({
      templateKey: renderPayload.templateKey,
      input: renderPayload,
    });
    
    // 5. Upload each slide to R2
    const uploadedSlides = await uploadSlidesToR2({
      articleId: article.id,
      projectSlug: brief.projectId,  // resolve to slug
      slides: slideBuffers,
    });
    
    // 6. Update articles row (status='ready')
    await markArticleReady(article.id, { renderedFiles: { carousel_4_5: uploadedSlides } });
    
    // 7. Mark brief rendered
    await updateBriefStatus(brief.id, 'rendered');
    
    return { status: 'rendered', articleId: article.id, slideCount: uploadedSlides.length };
  } catch (err) {
    // 8. Failure: no-retry, immediate notification
    await notifyAdminRenderFailed({
      briefId,
      error: err.message,
      stack: err.stack,
    });
    
    // Update brief.status='render-failed' for UI surfacing
    await updateBriefStatus(briefId, 'render-failed');
    
    throw err;  // mark job failed in BullMQ
  }
}, {
  concurrency: 2,  // limit concurrent renders
  // Per Marcel-Decision: no retries
  attempts: 1,
});
```

**Worker-config:** `attempts: 1` overrides BullMQ-default-3-retries per Marcel-Decision.

### 3.6 R2-Upload Pattern (per 65.2 reference)

```typescript
// apps/api/src/lib/article-output/upload-slides-to-r2.ts

interface UploadSlidesInput {
  articleId: string;
  projectSlug: string;
  slides: Array<{ slideIndex: number; pngBuffer: Buffer }>;
}

export async function uploadSlidesToR2(input: UploadSlidesInput) {
  const uploadedSlides = [];
  
  for (const slide of input.slides) {
    const r2Key = `${input.projectSlug}/articles/${input.articleId}/slide-${slide.slideIndex.toString().padStart(2, '0')}.png`;
    
    await r2Client.putObject({
      Bucket: 'toolwiki-content',
      Key: r2Key,
      Body: slide.pngBuffer,
      ContentType: 'image/png',
    });
    
    uploadedSlides.push({
      slideIndex: slide.slideIndex,
      r2Key,
      url: `https://cdn.toolwiki.ai/${r2Key}`,  // or whatever CDN-pattern
    });
  }
  
  return uploadedSlides;
}
```

**Per Memory D17 cost-tracking:** Each R2-PUT is a cost-event. Track via existing cost-tracker.

## 10. Risk Analysis

| Risk | Severity | Mitigation |
|---|---|---|
| LLM cover-headline hallucination (wrong tool-name) | Medium | Validate against `input.tools` names; throw if hallucinated |
| LLM verdict-winnerToolId hallucination | Medium | Validate `winnerToolId` against `input.tools` UUIDs; fallback to stars-desc top tool |
| Render-failure mid-pipeline leaves article.status='draft' forever | High | Worker catch-block sets status='failed' + admin-notify (Marcel-Decision: no retry) |
| R2-upload partial-failure (3/N slides uploaded) | High | Transactional: all-or-nothing; failed upload throws, article stays 'draft' |
| Re-render race: 2 BullMQ-jobs for same brief | Medium | Redis-lock per briefId (Memory D17 pattern from 65.5) |
| End-slide schema-mismatch FamilyAEndContent ↔ EndSlideData | High | Implementor verifies bridge in §2.2 #7; explicit transformation-helper |
| LLM-cost overruns at scale (Marcel re-renders 20×) | Medium | Re-render UI warning shows "kostet ~€0.10/render" before confirm |
| Articles.collection='recurring_content' rejected by existing CHECK | High | Migration 0122 widens collection-enum/CHECK |
| Render-time exceeds default BullMQ timeout (30s default) | Medium | Worker timeout: 180s (60s buffer above worst-case 120s render) |
| Brief-approval flow doesn't enqueue (existing approve-handler unaware) | High | Verify existing approve-handler location + extend with `if brief.source='recurring' enqueue` |
| End-slide-wiring breaks existing template fallback path | Medium | Backwards-compat: if brief.endSlide present use it, else fall back to inline FamilyAEndContent |

### 16.1 Phase 0 Findings — Spec-vs-Reality Discrepancies

Verification (parallel Explore agents on schema, templates, R2/approval) found four load-bearing spec hypotheses wrong:

1. **`articles.status` migration unnecessary.** `'generating'`, `'published'`, `'failed'` all already exist in `article_status` pgEnum (since pre-001). Spec hypothesized adding `'ready'` + `'failed'` — only `'ready'` was actually missing, and we skipped even that by reusing `'published'` as the terminal state for recurring carousels. No migration 0122.
2. **`articles.collection` has no enum constraint.** Plain `text` column with no CHECK. `'recurring_content'` can be inserted as-is — no migration needed.
3. **`renderMultiSlideComposition` does not exist.** Each Family-A template has its own `renderComparisonGrid3` / `renderComparisonGrid5` / `renderHeadToHeadVs` / `renderHeadToHeadDeepDive` function in `render-server.ts`. Spec's centralized-render assumption was wrong.
4. **`article:social-image` already does most of the spec's described work.** The pipeline ships carousels through Remotion + R2 via `convertImageToWebp` + the `social-render` BullMQ worker. The actual V1-gap was narrower: brief→article creation + an immediate-dispatch path that bypasses the weekly planner. `loadToolsWithBrandAssets` doesn't exist (`listToolsWithBrandAssets` does, but per-locale resolution is implicit via the article row's `locale` column).

### 16.4 Patterns Surfaced

- **Brief→article-stub for recurring content** (canonical: `createRecurringContentArticle`) — first bridge of its kind; if Family-B-only briefs land in 65.8, mirror this pattern, do NOT invent a parallel one.
- **Collection-guarded status flip in shared worker hook** — `syncRecurringArticleStatus` is the canonical pattern for "when this shared event fires, only act on rows of a specific collection". Reusable for any future per-collection lifecycle hook on the social-render worker.
- **Opt-in runtime switch via optional jsonb-schema field** — `familyACommonInputSchema.endSlideData?: z.record(z.unknown()).optional()` + shared `RenderEndSlide` dispatch is the back-compat pattern for swapping internal components without forking templates. Applied uniformly across the 4 Family-A carousels via a single schema edit.
- **Post-trigger status flip** — when an HTTP endpoint flips DB state + triggers a pipeline, do the flip AFTER the trigger's guard chain (cost / pause / idempotency) passes, never before. The new comment in [articles.ts re-render](apps/api/src/routes/articles.ts) (after-flip block) documents the contract.
