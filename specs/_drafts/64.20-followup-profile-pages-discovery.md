# Discovery — Task A Follow-up: Profile-Pages Inventory Integration (2026-05-25)

_Successor of Spec 64.20 Task A. Scoped during /review-task after `RenderMdxStep` Phase-0 revealed Toolwiki tool articles are 100% `source='imported'` and never flow through the MDX-render path. Inventory data is in the DB but no Astro template reads it._

**Status:** Discovery (pre-spec). 3 routing options evaluated; Marcel-decision driven.
**Voraussetzung:** Spec 64.20 done (data layer + cron worker + Settings-UI + Marcel-Seed via CSV import). Wait for ≥7d of cron-refresh data so `last_fetched_at` actually means something.
**Aufwand-Range:** 0.5d (A1, forward-compat only) → 1.5d (A3, write-back-to-MDX).

---

## 1. The Problem

Spec 64.20 ships `content_source_inventory` with stars/license/latest-release for every approved tool + skill. The Settings-UI shows the data, comparison-pipeline LLM reads it (Spec 64.20 Task B done), but Toolwiki's tool-profile pages at `/tools/[slug]` know nothing about it. Marcel-Decision in §11 of Spec 64.20 had this as "V1 Angle B" — but the actual implementation crosses repos:

- **marketing-automation** owns the inventory data
- **ki-wissensraum-neu** (Astro) renders the tool-profile pages from MDX
- `RenderMdxStep` only writes MDX for **generated** tool articles. Current 50-100 tool articles are `source='imported'`: they live in the Astro repo, our DB just mirrors them.

So injecting `github:` into the MDX from our side has no consumer — the existing MDX files don't get re-rendered when inventory refreshes.

## 2. Routing Options

### Option A1 — Forward-compat only (`RenderMdxStep` extension, 0.5d)

Extend `RenderMdxStep` so that when a tool article is GENERATED via `BlogPipeline` (`collectionType='tools'`), it gets `github:` frontmatter auto-injected. No effect on current imported articles.

**Pros:**
- Smallest scope
- All-marketing-automation work, no Astro-repo edits
- Future generated tool articles (when Marcel does LLM-driven tool reviews) inherit GitHub data

**Cons:**
- **Zero immediate value** — current 50-100 imported tool articles unchanged
- Still needs Astro-repo schema + template work to actually render the field

**When this makes sense:** Marcel starts generating tool articles via LLM (not just curating MDX manually).

### Option A2 — Snapshot-export script (0.75d)

`apps/api/src/scripts/export-inventory-snapshot.ts` writes the inventory as `src/data/inventory.json` to the Astro repo via GitHub-App commit. The Astro tool-profile template imports it at build-time and JOINs by slug.

**Pros:**
- Works for ALL tool articles (imported + future generated)
- One commit per snapshot export (e.g. daily) — manageable Astro commit-history
- Reuses existing GitHub-App auth from `@marketing-auto/adapter-astro-sync`
- Astro template only needs schema for a JSON-import + JOIN, no per-MDX edits

**Cons:**
- Astro repo gains a machine-committed data file
- Snapshot is stale between cron-runs (acceptable since GitHub data is stable)
- Cross-repo coordination: schema in Astro `config.ts` + template in `tools/[slug].astro`

**When this makes sense:** if Marcel wants the inventory data to surface on tool-profile pages NOW with minimal Astro-repo noise.

### Option A3 — Write-back to MDX per-tool (1.5d)

Inventory-refresh worker, after each successful fetch, commits `github:` frontmatter into the existing tool MDX via GitHub-App.

**Pros:**
- MDX file is self-contained — no JOIN at Astro build time
- Astro template just reads frontmatter normally

**Cons:**
- **Noisy Astro commit-history**: 1 commit per tool per refresh → ~50 commits/week
- Race against manual Marcel edits (a `frontmatter:` write while Marcel has the MDX checked out locally)
- More complex worker (per-tool branch-write-commit cycle)
- Same Astro-side template work as A2

**When this makes sense:** never, IMO. Too noisy for marginal gain over A2.

### Option A-defer — Skip until Theme 65.10

Inventory data stays in our DB. Theme 65.10 (Marketing-automation backlog for tool-profile-page enhancements) wraps the Astro-template + schema work alongside other tool-profile changes (brand-asset display, persona-scoring, etc.).

**Pros:**
- Zero work now
- Avoids fragmenting the Astro-template changes across multiple specs
- Lets the inventory data accumulate ~2 weeks of refresh-history before consumers depend on it

**Cons:**
- Marcel sees no user-facing payoff from Spec 64.20 until Theme 65.10 lands
- Inventory cron runs weekly with no visible consumer

**When this makes sense:** if Theme 65.10 is on the near-term roadmap (1-2 months).

## 3. Recommendation

**A-defer + A2 stub** — defer the immediate work to when Marcel either:
- (a) Starts Theme 65.10, OR
- (b) Decides to do A2 standalone because the Settings-UI evidence is enough to commit

A2 is the cleanest mechanic if/when Marcel wants immediate user-visible value. A1 is too narrow (forward-compat only). A3 is over-engineering.
