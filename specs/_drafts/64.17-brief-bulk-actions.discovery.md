## 1. State-Machine Recap (für context)

`topic_briefs.status` lifecycle (rekonstruiert aus 64.9 + 64.14 + 63.6):

```
pending → plan_pending → approved → routed
   ↓
rejected (terminal)
   ↓
superseded (terminal, planner overwrites)
```

**Action-Mapping:**

| Action | Status Transition | Side-Effects |
|---|---|---|
| Approve | `pending → plan_pending` | Planner picks up in next cron-cycle, generates planned_item |
| Dismiss | `pending → rejected` | Terminal, no further work, archive |
| Add-to-Plan | TWO PATHS — see §3 | Either deferred (= Approve) or immediate (= dispatch pipeline) |

**Key insight aus 64.9:** `plan_pending` ist explicit das brief-state-VOR-immediate-dispatch. Wenn Marcel sofort "Add-to-Plan" will → muss durch cluster_assignment_required gate (§3 Path B).

## 3. Add-to-Plan Path Evaluation

This is the most consequential decision. Two paths, evaluating both:

### Path A — Deferred (status=plan_pending, planner picks up)

**Mechanik:**
```
bulk_briefs.forEach(brief => {
  UPDATE topic_briefs SET status='plan_pending' WHERE id=brief.id;
})
// Next planner cron-tick (62.6 pattern) sees plan_pending briefs → picks them into next weekly plan
```

**Pros:**
- ✅ Re-uses existing planner cron (no new dispatch logic)
- ✅ Functionally identical to "Approve" — Add-to-Plan as semantic alias?
- ✅ Zero pipeline cost at action-time (planner picks at next cycle)
- ✅ Respects floor/cap rules (62.4 goal.minCount)
- ✅ Cross-week diversity from 64.15B applies automatically
- ✅ Bulk-safe — only DB UPDATE, no fan-out

**Cons:**
- ⚠️ User-mental-model overlap with "Approve" — what's the difference?
- ⚠️ No control over WHICH week the briefs land in
- ⚠️ Planner might reject if floor/cap already hit → briefs sit in plan_pending limbo
- ⚠️ Marcel can't see "I added 50 things to plan" — they just go into queue

**Verdict A:** Path A reduces "Add-to-Plan" to a label, not a distinct action. **If chosen → drop it, keep Approve+Dismiss only.**

### Path B — Immediate (inject into current week's draft plan)

**Mechanik:**
```
bulk_briefs.forEach(brief => {
  // Find or create current draft weekly_plan
  // INSERT INTO planned_items (brief_id, weekly_plan_id, status='planned')
  // UPDATE topic_briefs SET status='routed' WHERE id=brief.id
})
// Marcel sees items in current week's plan UI immediately
```

**Pros:**
- ✅ Distinct from Approve — clear semantic (immediate inclusion)
- ✅ Marcel has agency — "I want these in THIS week's plan"
- ✅ Immediate visual feedback in plan view

**Cons:**
- ⚠️ Bypasses planner's diversity/floor/cap logic (64.15B cross-week diversity NOT applied)
- ⚠️ Cluster-assignment gate (64.9): for trend_discovery briefs with `cluster_action='create_new'` → cluster_full-plan pipeline must run. For `append_to_existing` → clusterId required.
- ⚠️ 64.9 dispatch endpoint takes single clusterId — bulk endpoint must handle heterogeneous cluster_action per brief
- ⚠️ Volume risk — 168 briefs immediately into one week's plan would blow goal caps
- ⚠️ Requires draft weekly_plan to exist — what if no current draft?

**Verdict B:** Path B is the "real" Add-to-Plan but introduces planner-bypass + complexity.

### Path C — Hybrid (recommended)

**Mechanik:**
- "Add-to-Plan" = Path A semantically (sets plan_pending, planner picks up next cycle)
- BUT: add explicit "Target Week" picker in BulkApproveModal — `KW21 / KW22 / next available`
- Updates `topic_briefs.target_week` column (new column? or use metadata jsonb?)
- Planner respects target_week when scoping cycle

**Pros:**
- ✅ User-control without bypassing planner logic
- ✅ Re-uses cron infrastructure
- ✅ Marcel still sees items "land" in correct week (via planner respect)

**Cons:**
- ⚠️ Requires schema change (target_week column or jsonb metadata) — adds scope
- ⚠️ Planner code must learn target_week constraint (new code)
- ⚠️ NEW pattern — not strictly minimal

**Verdict C:** Best UX but **NOT 0.5d work**. Closer to 1.5d.

### 🎯 Recommendation

**Drop "Add-to-Plan" as separate action.** Reduce M4 scope to **Approve + Dismiss only**.

**Rationale:**
- Path A makes Add-to-Plan = Approve semantically — confusing, no value
- Path B introduces planner-bypass complexity that fights 64.15B + 62.4 floor mechanics
- Path C is 1.5d not 0.5d — out of scope for "UX quick-win"

**Alternative if Marcel wants Add-to-Plan:** Defer it as M4.1 follow-up after Multi-Domain Sprint 3 lands (Categories table may simplify cluster-assignment for bulk).

**Marcel-Decision required:** Confirm scope reduction OR specify Path A/B/C preference with widened effort estimate.

## 4. Selection Mechanics — "Select all matching filter" Pattern

This is the second-most consequential decision. Pattern is well-known (Gmail, Linear, GitHub) but has gotchas.

### Two-Mode Selection Pattern

**Mode 1: Per-card selection (visible items)**
- `<q-checkbox>` on each brief card
- `selectedIds: Set<string>` in component data
- Toolbar shows "5 selected"

**Mode 2: "Select all matching filter" (server-side)**
- After Mode 1 selects all visible cards (e.g. 25 of 168), banner appears:
  > "All 25 briefs on this page are selected. **Select all 168 briefs matching filter →**"
- Click switches to Mode 2: `selectAllMatching: true` + current filter-state
- Toolbar shows "168 selected (all matching filter)"
- Selection becomes virtual — no IDs stored, filter-state is the selection

### Frontend State Shape

```typescript
data: () => ({
  selectedIds: new Set<string>() as Set<string>,
  selectAllMatching: false,
  currentFilter: {} as BriefsFilter,
})
```

### Backend Endpoint Shape (bulk-approve example)

```typescript
// EITHER explicit IDs
POST /api/projects/:slug/briefs/bulk-approve
Body: { briefIds: string[] }

// OR filter-based (matches Mode 2)
POST /api/projects/:slug/briefs/bulk-approve
Body: { filter: BriefsFilter, excludeIds?: string[] }
```

**Recommendation:** Support both. Frontend sends `{ briefIds }` in Mode 1, `{ filter, excludeIds }` in Mode 2 (excludeIds for "select all except these unchecked ones").

### Race-Condition Concern

If Marcel selects "all 168 matching filter" and clicks Approve:
- **Race:** Cron-sync runs between selection and action → 5 new briefs match filter → are they approved?
- **Mitigation:** Backend re-queries filter at action-time, returns count actually approved
- **Confirmation UX:** "168 briefs matched filter → 173 approved" with discrepancy banner

**Verify points:**
7. Existing BriefsListPage filter API shape (must be serializable to backend)
8. Is brief count stable enough that race-condition surprises Marcel?

## 5. Volume-Cap Risk Analysis (per source/action)

Marcel asked Discovery to evaluate. Per source × action matrix:

| Source | Toolwiki count | Approve | Dismiss | Add-to-Plan |
|---|---|---|---|---|
| gap_analysis | 168 | ✅ safe (low fan-out) | ✅ safe | ⚠️ blow planner |
| trend_discovery | 22 | ⚠️ cluster_action gate | ✅ safe | ⚠️ blow planner |
| comparison_discovery | 4 | ✅ safe | ✅ safe | ✅ marginal |
| refresh_detection | 1 | ✅ safe | ✅ safe | ✅ safe |
| manual | 1+ | ✅ safe | ✅ safe | ✅ safe |

**Approve action analysis:**
- For `gap_analysis`: status update only, planner picks up at cron-tick. 168 updates in single transaction trivial. ✅ no cap needed.
- For `trend_discovery`: 64.9 introduced `cluster_assignment_required` 409-gate. Brief with `cluster_action='append_to_existing'` requires clusterId before approve. Bulk-approve must skip these OR enforce clusterId per-brief. **Risk:** Marcel selects all 22 trends → 5 need clusterId → bulk fails or skips silently. **Mitigation:** Pre-flight check in modal — "5 of 22 briefs need cluster assignment, approve other 17?"

**Dismiss action analysis:**
- All sources: status update to `rejected`. Trivial. ✅ no cap needed.
- Idempotent — re-dismissing already-rejected brief is no-op.

**Add-to-Plan action analysis:**
- Per §3, recommend dropping. If kept: per-action cap of 20 items (matches 62.4 max_count hard-cap).

### Recommended Volume Strategy

| Action | Cap | Rationale |
|---|---|---|
| Approve | **None** (soft 500 limit as safety) | Single-transaction DB update, no fan-out |
| Dismiss | **None** | Idempotent, terminal status |
| Add-to-Plan (if kept) | **20** | Matches 62.4 plan max_count, prevents blowing planner |

**No hard BullMQ-per-job limit needed** — bulk endpoint is one HTTP call, one transaction. **Unlike** the cluster:full-plan pipeline (D127), there's no per-item BullMQ enqueue for approve/dismiss.

## 6. Trend-Discovery Cluster-Assignment Gotcha

This is the **non-obvious blocker** for bulk-approve.

### 64.9 Pattern Recap

Trend_discovery briefs have `cluster_action` field:
- `create_new` → planner runs cluster:full-plan inline (D127), no clusterId needed
- `append_to_existing` → needs clusterId. Endpoint returns 409 `cluster_assignment_required` if missing.

### Bulk-Approve Problem

If Marcel selects 22 trend briefs and clicks Approve:
- 17 have `cluster_action='create_new'` → fine, set plan_pending
- 5 have `cluster_action='append_to_existing'` and no clusterId → 409

**Options:**

**Option α — Atomic (all-or-nothing):**
- Bulk endpoint pre-checks all briefs
- If any blocker → returns 422 with list of blocked briefs
- Marcel sees "5 briefs blocked, fix them first or deselect"
- No partial-success

**Option β — Best-effort (partial success):**
- Bulk endpoint processes each brief
- Returns `{ approved: 17, blocked: 5, blockedReasons: [...] }`
- Modal shows summary "17 approved, 5 need cluster assignment"

**Recommendation: Option β** — matches Marcel's "review-then-act" workflow (he sees 168 gaps, wants them out of his face, partial success is fine).

**Verify point:**
9. Confirm `cluster_action` field is on `topic_briefs` table for trend_discovery rows (vs metadata jsonb)
