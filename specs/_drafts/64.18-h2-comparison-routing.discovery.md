## 5. Pattern Decision — Three Options Evaluated

### Option 1 — Subcategory-aware comparison-cluster resolution (RECOMMENDED)

**Algorithm** (pure function, no DB writes — runs inside `persistPairs()` transaction):

```typescript
function resolveComparisonCluster(
  toolA: { category: string | null; subcategory: string | null; slug: string },
  toolB: { category: string | null; subcategory: string | null; slug: string },
  comparisonClusters: Array<{ id: string; name: string; matchTokens: string[] }>,
): { clusterId: string; clusterAction: "append_to_existing" } | { clusterAction: "create_new" } {
  // Priority 1: both tools share subcategory → look for cluster named *<subcategory>*
  if (toolA.subcategory && toolA.subcategory === toolB.subcategory) {
    const m = matchClusterByToken(comparisonClusters, toolA.subcategory);
    if (m) return { clusterId: m.id, clusterAction: "append_to_existing" };
  }

  // Priority 2: anchor on the higher-prestige subcategory (chatbots-assistants wins
  //             over research/translation by tool-volume convention).
  //             Find the comparison cluster matching either subcategory.
  for (const sub of [toolA.subcategory, toolB.subcategory].filter(Boolean) as string[]) {
    const m = matchClusterByToken(comparisonClusters, sub);
    if (m) return { clusterId: m.id, clusterAction: "append_to_existing" };
  }

  // Priority 3: category-level fallback (e.g. text-language → first comparison-cluster
  //             whose articles share that category — pre-computed in deps).
  if (toolA.category && toolA.category === toolB.category) {
    const m = matchClusterByCategory(comparisonClusters, toolA.category);
    if (m) return { clusterId: m.id, clusterAction: "append_to_existing" };
  }

  // Cross-category or unmatchable → create_new (router falls through to
  // inline cluster:full-plan path; Marcel reviews resulting plan).
  return { clusterAction: "create_new" };
}
```

`matchClusterByToken(clusters, "chatbots-assistants")` does an `cluster.name.toLowerCase().includes("chatbot")` test (or a `matchTokens` set derived from member-articles' subcategory column). For Toolwiki today: `chatbot-comparisons-2026` contains the token "chatbot" → all 4 stuck briefs route here.

`matchClusterByCategory` would join `clusters` ← `articles.cluster_id` once at function-entry and group by article subcategory/category to derive `matchTokens` per comparison cluster. Deps shape:

```typescript
interface ComparisonClusterIndex {
  clusterId: string;
  name: string;
  subcategories: Set<string>;  // distinct articles.subcategory values
  categories: Set<string>;     // distinct articles.category values
}
```

Built once per `persistPairs()` call (one query for the project's comparison-pillar clusters + their members), reused across all pair iterations.

**Pros**:
- ✅ Stamps `clusterId` at brief-creation time → no late-binding magic
- ✅ Uses Toolwiki's existing 8 comparison clusters cleanly
- ✅ Generalizes to other tenants (Bellemann/BK) as long as they have a `comparisons` pillar with category-named clusters
- ✅ `create_new` fallback routes through existing inline `cluster:full-plan` path (no new code path)
- ✅ Test surface is pure-function — DI for `comparisonClusters` makes unit tests trivial
- ✅ Spec 64.18 §3.3 "comparisonMetadata is the only structured tool-field today" pattern is preserved

**Cons**:
- Heuristic ordering (subcategory > category) is opinionated. If Marcel's editorial intent differs ("ChatGPT vs DeepL should NOT live under chatbot-comparisons-2026 because it's a translation use-case"), the heuristic produces the wrong default.
  - **Mitigation**: per-project override via `project_planner_config.comparison_routing_overrides jsonb` (forward-compat — not needed for V1). For V1, Marcel can move the resulting article cluster_id post-generation via the existing Cluster-Picker UI.
- Adding a new tenant requires their `comparisons` pillar to be set up before this resolver yields good defaults. Acceptable per spec §5.1.

**Multi-Domain**: works for any tenant with:
1. `articles.subcategory` populated (Spec 54.8 promotion — already done for Toolwiki; future tenants follow same pattern).
2. A `comparisons` pillar (or equivalent) with at least one cluster per major subcategory.

Bellemann: pillar `comparisons`, clusters `bmw-vergleiche`, `audi-vergleiche`, etc. → resolver picks `bmw-vergleiche` for any pair where one tool's subcategory matches "bmw".
Balkon: pillar `comparisons`, clusters `inverter-comparisons`, `panel-comparisons`. Same algorithm.

### Option 2 — Route to existing tool-cluster (REJECTED)

Map each comparison brief to one of its tools' natural cluster (e.g. Claude vs Perplexity → `chatbots-2026`, since Claude lives there).

**Why rejected**:
- ❌ Mixes content shapes within one cluster: `chatbots-2026` currently holds 20 tool-spotlight articles (one per chatbot); adding comparison-articles would break the hub-spoke purity (hub = tool, spokes = use-cases for that tool).
- ❌ Same-cluster pairs (Claude vs ChatGPT, both in `chatbots-2026`) are easy; cross-cluster pairs (Claude vs Perplexity) need a tiebreaker which adds complexity without semantic value.
- ❌ Astro `chatbots-2026` template doesn't know how to render comparison-articles alongside tool-spotlights (editorial-incoherence).

### Option 3 — New cluster per pair (REJECTED)

Auto-create `claude-vs-perplexity-cluster` for each brief.

**Why rejected**:
- ❌ Cluster explosion: 4 briefs today, C(20, 2) = 190 potential pairs at Toolwiki's tool count. Cluster pollution kills the planner UI.
- ❌ One-article-per-cluster defeats the SEO purpose of clusters (hub-spoke aggregation of related content).
- ❌ Cluster creation requires `cluster:full-plan` LLM call (~€4.20 per cluster). 190 × €4.20 = €798 just for clusters.
