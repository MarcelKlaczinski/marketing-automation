## Discovery-Schritte

### Schritt 1 — Weekly Plans + Planned Items Audit

```sql
-- Alle weekly_plans im Toolwiki
SELECT 
  id, week, year, status, total_budget_eur, total_cost_eur,
  approved_at, created_at,
  (SELECT COUNT(*) FROM planned_items WHERE weekly_plan_id = wp.id) AS items_total,
  (SELECT COUNT(*) FROM planned_items WHERE weekly_plan_id = wp.id AND article_id IS NOT NULL) AS items_with_article
FROM weekly_plans wp
WHERE project_id = (SELECT id FROM projects WHERE slug='toolwiki')
ORDER BY year DESC, week DESC;
```

```sql
-- Alle planned_items
SELECT 
  status, content_type,
  COUNT(*) AS total
FROM planned_items pi
WHERE weekly_plan_id IN (
  SELECT id FROM weekly_plans WHERE project_id = (SELECT id FROM projects WHERE slug='toolwiki')
)
GROUP BY status, content_type
ORDER BY total DESC;
```

**Dokumentieren:**
- N weekly_plans (KW21 Draft + frühere?)
- M planned_items (verteilt nach status)
- CASCADE-Sequence: planned_items → weekly_plans

### Schritt 2 — Topic-Briefs ALL Status Audit

```sql
-- Komplette Brief-Verteilung
SELECT 
  status, content_type, intent_type,
  COUNT(*) AS total,
  COUNT(*) FILTER (WHERE routed_article_id IS NOT NULL) AS with_article,
  COUNT(*) FILTER (WHERE routed_cluster_id IS NOT NULL) AS with_cluster
FROM topic_briefs
WHERE project_id = (SELECT id FROM projects WHERE slug='toolwiki')
GROUP BY status, content_type, intent_type
ORDER BY total DESC;
```

**Dokumentieren:**

- Affected counts pro status
- Plus: briefs.metadata sub-types (trendMetadata, gapMetadata, refreshMetadata, comparisonMetadata) — werden mit-gelöscht via CASCADE

### Schritt 3 — Pipeline-Runs Decision

```sql
-- Pipeline-runs aufgeschlüsselt
SELECT 
  pipeline_name,
  status,
  COUNT(*) AS total,
  MIN(created_at) AS first,
  MAX(created_at) AS last
FROM pipeline_runs
WHERE project_id = (SELECT id FROM projects WHERE slug='toolwiki')
GROUP BY pipeline_name, status
ORDER BY total DESC;
```

**Dokumentieren:**
- N pipeline_runs total
- Per Pipeline-Type (article:blog, cluster:full-plan, planner-weekly-generation, etc.)
- **Marcel-Decision:** Phase 0 empfahl pipeline_runs ERHALTEN. Marcel hat jetzt "alles" gesagt — wirklich auch pipeline_runs? Oder erhalten?
- Argument für Erhalten: historischer Audit, kein Conflict mit fresh generation
- Argument für Löschen: clean slate, falls referenced FK von gelöschten articles
- **Empfehlung:** Erhalten (FK ist project_id, nicht article_id direct). Wenn article gelöscht, pipeline_runs.input wird stale aber kein Crash.

### Schritt 4 — Cost-Logs Decision


Basierend auf allem oben — sequenz dokumentieren:

```sql
BEGIN;

-- Pipeline_runs + cost_logs ERHALTEN (history)

-- Verify
SELECT 
  (SELECT COUNT(*) FROM articles WHERE project_id = (SELECT id FROM projects WHERE slug='toolwiki') AND collection = 'blog') AS blog_articles,
  (SELECT COUNT(*) FROM clusters WHERE project_id = (SELECT id FROM projects WHERE slug='toolwiki')) AS clusters,
  (SELECT COUNT(*) FROM topic_briefs WHERE project_id = (SELECT id FROM projects WHERE slug='toolwiki')) AS briefs,
```

- ❌ imported tools/usecases/authors auch nur in Erwägung ziehen
