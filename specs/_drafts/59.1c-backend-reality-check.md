# 59.1c Backend Reality Check — Pre-Spec Discovery

**Goal:** Verify backend assumptions before writing 59.1c spec. ~10-15 min of code exploration, no implementation.

**Why:** 59.1c will surface UI for: ProductHunt, HackerNews, Reddit (59.1a), GitHub (59.1b), vendor-rss. Some adapters have credentials, some have only operational config (subreddits, topics, etc), some are public APIs. Before writing the UI spec, we need ground truth on what's wired in the backend.

---

## Investigation Tasks

For each section below: report findings in a short markdown document. **No code changes.** Just discovery.

### Task 1 — System Credentials Verify Endpoint

**File:** `apps/api/src/routes/system.ts` (or wherever the verify dispatcher lives)

**Find:**
1. The `POST /api/system/verify/:adapter` (or equivalent) endpoint handler.
2. How does it dispatch by adapter name? Lookup table? Switch statement? Registry?
3. List all adapter names currently registered for verify:
  - Confirmed working: anthropic, voyage, dataforseo, replicate (per 56.3 spec)
  - Question: producthunt? hackernews? reddit? github?
4. For each missing adapter (especially ProductHunt + HackerNews), is the **adapter package** itself ready? Look in `packages/adapters/<name>/src/verify.ts` for an exported `verifyXxx` function.

**Report:**
- Path of the dispatcher
- Dispatch mechanism (e.g. switch, lookup table)
- Currently-supported verify adapters
- Adapters where the adapter package has `verifyXxx` but the system route doesn't dispatch to it
- Adapters where the adapter package lacks `verifyXxx` (need new verify function)

### Task 2 — System Credentials Set/Delete Endpoints

**File:** same as Task 1

**Find:**
1. `POST /api/system/credentials` — what's the payload shape? Does it validate adapter names against an allowlist, or accept any string?
2. `DELETE /api/system/credentials/:service/:key` — same question on `:service`
3. Is there an enum of valid credential types in the DB layer (`packages/db/src/schema/...`)? Look for `credential_type` enum or similar.
4. Confirmed values in that enum?

**Report:**
- POST + DELETE payload schemas (or short summary)
- Whether they validate adapter names or accept anything
- DB enum location and current values
- Whether `reddit` + `github` need to be added (per 59.1a/b they should be) or are already there from those specs' migrations

### Task 3 — Per-Source Operational Config

**File:** `packages/db/src/schema/project-config.ts` (per memory pattern)

**Find:**
1. The `signal_sources` block in the Zod schema. What sub-objects exist today?
2. After 59.1a: `reddit` with subreddits/sortMode/timeWindow/minUpvotes/etc.
3. After 59.1b: `github` with topics/timeWindowDays/etc.
4. Existing pre-Theme-59: `producthunt`, `hackernews`, `vendor_rss` — what config fields?
5. For each: which fields are user-editable per project?

**Report:**
- Current shape of `signalSources` block (compact list per source: enabled, plus key config fields)
- Whether endpoints exist to update individual signal_sources sub-blocks, or if it goes through generic `PATCH /api/projects/:slug` with full config replace, or `PATCH /api/projects/:slug/config` with partial merge

### Task 4 — Vendor-RSS feeds CRUD

**Find:**
1. Where are vendor-rss feed URLs stored? In `project_config.signal_sources.vendor_rss.feeds` (array of URLs)? Or a separate table?
2. Endpoints to add/edit/delete individual feeds? Or only full-array replace via project config?
3. Validation of RSS URLs (URL format, fetch-on-add to verify the feed parses)?
4. Per-feed metadata: name/label, enabled flag, category tags?

**Report:**
- Storage location (config block vs table)
- Available CRUD endpoints, if any
- What's needed to support the UI workflow: list, add (with validation), edit (label/enabled), remove

### Task 5 — HackerNews / Algolia Verify

**File:** `packages/adapters/hackernews/src/`

**Find:**
1. Does HN adapter have a `verify` function? It's a public API (Algolia) — no credentials, but a verify call could still ping the API to confirm reachability.
2. If not, can a trivial verify be added (call `https://hn.algolia.com/api/v1/search?query=test&hitsPerPage=1`, expect 200)?

**Report:**
- Current verify state
- Recommended verify approach (or "no verify needed, it's a public API and we just check it doesn't 5xx")

### Task 6 — ProductHunt Verify

**File:** `packages/adapters/producthunt/src/`

**Find:**
1. Does PH adapter have a `verify` function?
2. What credentials does it accept (developer token? OAuth? both)?
3. Is verify dispatched from `POST /api/system/verify/:adapter`?

**Report:**
- Current verify state in the adapter package
- Current dispatch state in the system route
- Gap: adapter has verify but system doesn't dispatch / adapter lacks verify / both missing

### Task 7 — i18n Coverage Gap

**File:** `apps/web/src/i18n/de/` + `apps/web/src/i18n/en/`

**Find:**
1. Current keys under `settings.credentials.*` and `settings.signalSources.*`
2. Which adapters have name + description translations
3. Whether there's a pattern for adapter-specific translations (e.g. `settings.credentials.adapters.anthropic.name` vs flat structure)

**Report:**
- Existing key structure for credentials/signal-sources
- Naming convention to follow for new adapter entries (reddit, github, producthunt, hackernews, vendor_rss)

### Task 8 — Frontend Settings Sidebar

**File:** `apps/web/src/pages/SettingsPage.vue` or wherever the sidebar lives

**Find:**
1. How are settings sections registered? Hardcoded array in `data()` / `computed()`? Or dynamic from somewhere?
2. The existing 4 sections: project, brand-tokens, brand-assets, credentials. How would a 5th (signal-sources) be added?
3. Route registration: where in `apps/web/src/router/` do settings sub-routes live?

**Report:**
- Section registration mechanism
- Route file location
- Estimated complexity of adding "signal-sources" as a new section (just add to array + new route + new page, or more involved?)
