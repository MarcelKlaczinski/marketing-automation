## 2. Item A — GitHub enabled-JSON vs cron-state aligning

### Symptom

Toolwiki `signal_sources` JSON in project_config:
```json
{ "github": { "enabled": true, "repos": [...] } }
```

Aber `cron_state` Tabelle:
```sql
SELECT * FROM cron_state WHERE job_type = 'signal_collector_github';
-- is_active: false
```

Cron-Flag ist der echte Trigger. JSON-`enabled:true` ist dead content das nichts triggert.

### Root Cause

Vermutlich aus Spec 59.1c Project-Create-Default — `seedProjectConfig()` setzt JSON-Default `enabled:true` aber `seedCronState()` setzt `is_active:false` (per-source default off).

### Fix

**Option A1:** Project-Create-Default aligning — neue Projekte bekommen JSON-`enabled` und cron-state `is_active` synchron (beide entweder true oder false).

**Option A2:** Existing Toolwiki Project — `cron_state.signal_collector_github` row updaten auf `is_active=true` (wenn GitHub aktiv sein soll) ODER JSON auf `enabled:false` (wenn nicht aktiv).

**Empfehlung:** beides.

- Marcel entscheidet: ist GitHub aktuell aktiv? Phase 0 prüft (war GitHub-Adapter-Run heute? `external_signals` Tabelle SELECT mit source='github').
- Wenn ja → cron-state `is_active=true`, JSON bleibt `enabled:true` (aligned).
- Wenn nein → JSON `enabled:false`, cron-state bleibt `is_active=false` (aligned).
- Plus seedProjectConfig() Code-Change damit neue Projects beide synchron seeden.

### Phase 0

```sql
-- Ist GitHub-Adapter aktuell aktiv für Toolwiki?
SELECT COUNT(*), MAX(seen_at) 
FROM external_signals 
WHERE project_id = (SELECT id FROM projects WHERE slug='toolwiki')
  AND source='github';
```

Wenn 0 Rows oder seen_at vor 7+ Tagen → GitHub inactive → JSON auf false.
Wenn frische Rows → cron-state auf is_active=true.

### Touched Files

- `apps/api/src/routes/project-create.ts` oder `packages/db/src/helpers/seed-project-config.ts` (Phase 0 findet)
- Plus 1 DB-UPDATE für Toolwiki

### Tests

- Project-Create Test: neue Projects haben synchrone JSON + cron-state
- Manuell: SELECT auf cron_state nach Migration zeigt aligned values

### Akzeptanzkriterien A

1. ✅ Toolwiki signal_sources.github.enabled aligned mit cron_state.signal_collector_github.is_active
2. ✅ seedProjectConfig erweitert um sync-seeding für signal_collector_* cron-states
3. ✅ Test für project-create dokumentiert synchron-seeding

## 3. Item B — ProductHunt votes-Key-Mismatch

### Symptom

ProductHunt-Adapter (`packages/adapters/producthunt/src/index.ts` oder ähnlich) schreibt in `external_signals.metrics` JSON:

```json
{ "votes": 142, "comments": 18 }
```

Planner-Heuristik (vermutlich `packages/planner/src/scoring/...` oder `signal-top-n.ts`) liest:

```ts
const votes = signal.metrics?.votes_count ?? signal.metrics?.votes ?? 0;
const comments = signal.metrics?.comments_count ?? signal.metrics?.comments ?? 0;
```

Funktioniert wegen Fallback, aber:
- primärer Lookup `votes_count` misst nie
- Inkonsistenz zwischen Adapter (`votes`) und Planner-Erwartung (`votes_count`)
- Konvention im Repo (Phase 0 prüft): vermutlich snake_case bevorzugt (z.B. `comments_count`)

### Root Cause

Vermutlich aus initial ProductHunt-Adapter-Erstellung — API-Response-Mapping war direkt `data.votes_count` → `metrics.votes` (Truncation). Planner wurde nach generischer Konvention geschrieben.

### Fix

**Adapter-Update:** ProductHunt-Adapter schreibt `votes_count` und `comments_count` (snake_case, aligned mit Planner-Erwartung).

```ts
// Vorher:
metrics: {
  votes: rawData.votes_count,
  comments: rawData.comments_count,
}

// Nachher:
metrics: {
  votes_count: rawData.votes_count,
  comments_count: rawData.comments_count,
}
```

**Planner-Fallback bleibt erhalten** für existing rows mit alter Notation. Backward-compat.

### Phase 0

```bash
# ProductHunt Adapter Location
grep -rn "metrics.*votes\|votes.*metrics" packages/adapters/producthunt/

# Wie viele existing rows haben alte vs neue Notation?
```

```sql
SELECT 
  COUNT(*) FILTER (WHERE metrics ? 'votes') AS old_notation,
  COUNT(*) FILTER (WHERE metrics ? 'votes_count') AS new_notation
FROM external_signals
WHERE source='producthunt'
  AND project_id = (SELECT id FROM projects WHERE slug='toolwiki');
```

Wenn beide Spalten Rows haben: Planner-Fallback wichtig. Wenn nur alte: nach Adapter-Fix neue Rows verwenden new notation, alte bleiben unverändert.

### Touched Files

- `packages/adapters/producthunt/src/index.ts` (vermutlich) — metrics-Key-Names
- Planner heuristic kann unverändert bleiben (existing Fallback)
- Optional: Backfill-Script für existing Rows (lassen wir weg — Fallback handles it)

### Tests

- Adapter unit-test: response → metrics hat votes_count + comments_count
- Planner heuristic test: liest votes_count primary + votes fallback

### Akzeptanzkriterien B

1. ✅ Adapter schreibt votes_count + comments_count (snake_case)
2. ✅ Planner Fallback für alte votes/comments bleibt
3. ✅ Backward-compat: existing rows weiterhin gepicked von Planner
4. ✅ Adapter-Tests grün

### Phase 0 Diagnose (NUR Diagnose, kein Code-Change!)

```sql
-- HN-Volumen letzte 14 Tage
SELECT 
  date_trunc('day', seen_at) AS day,
  COUNT(*) AS items_per_day
FROM external_signals
WHERE source='hackernews'
  AND project_id = (SELECT id FROM projects WHERE slug='toolwiki')
  AND seen_at > NOW() - INTERVAL '14 days'
GROUP BY 1
ORDER BY 1 DESC;
```
