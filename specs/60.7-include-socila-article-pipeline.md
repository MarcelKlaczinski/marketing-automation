# Spec 60.7 — Social in Article Pipeline: Full Integration

**Date:** 2026-05-19
**Theme:** 60 — Social System Completion
**Prerequisite:** 60.6 done
**Estimated effort:** ~1 day

---

## TL;DR

60.6 wired the UI picker and planted the `bridge()` pattern + `isOverrideTemplateKey`
guard. 60.7 completes the loop: social generation becomes a first-class optional
step in the article pipeline, driven by project config. After this spec:

- A project can set `socialAutoRenderLocales` + `socialAutoTemplates` → article
  generation automatically triggers social renders for the top-N suggested
  templates without any manual UI interaction
- The Content Planner (Theme 62) can schedule full article+social batches in
  one job
- `template_renders` and `social_posts` are reconciled into a clear single
  write path

## Section C — Reconcile `template_renders` vs `social_posts`

### C.1 Current confusion (from 60.6 D.1 deviation)

- `POST /generate-templates` → writes `template_renders`
- `POST /social-posts/generate` → writes `social_posts`
- Both exist, both track renders, both have R2 URLs
- The picker UI (60.6) uses `generate-templates` → `template_renders`
- The old pipeline uses `social-posts/generate` → `social_posts`

### C.2 Decision: `template_renders` is the canonical table

Going forward:
- All new render paths write to `template_renders`
- `social_posts` is retained for backward compat (existing rows, re-render)
  but no new rows are created via the article pipeline
- `ArticleSocialTab.vue` already uses `template_renders` via picker — consistent
- `SocialGenerationStep` (new, see Section D) writes to `template_renders`

### C.3 Migration: re-render endpoint

`POST /social-posts/:id/re-render` — this still works against `social_posts`
rows. For rows created via the new path (`template_renders`), a new endpoint is
needed:

```
POST /api/articles/:articleId/template-renders/:renderId/re-render
```

Add this endpoint in 60.7. Old `social-posts/:id/re-render` stays for legacy rows.

### D.2 Step position in BlogPipeline

```

Step 8:   GenerateImageStep
...
```

Note: `GenerateImageStep` runs after social because image generation is slower
and social doesn't need the image URL.

### D.3 Step guard — only runs when configured

```typescript
// packages/pipelines/src/article/steps/social-generation.step.ts

export class SocialGenerationStep extends PipelineStep<
  SocialGenerationInput,
  SocialGenerationOutput
> {
  readonly key = 'social-generation';

  async shouldRun(ctx: PipelineContext): Promise<boolean> {
    const project = await projectReadHelpers.findById(ctx.projectId);
    return !!project?.socialAutoRenderLocales;
  }

  async execute(input: SocialGenerationInput, ctx: PipelineContext): Promise<SocialGenerationOutput> {
    const project = await projectReadHelpers.findById(ctx.projectId);
    const article = await articleReadHelpers.findById(input.articleId);
    const discovery = await articleDiscoveryReadHelpers.findByArticleId(input.articleId);

    const templateKeys = resolveAutoTemplates(
      project!.socialAutoTemplates,
      discovery?.suggestedTemplates ?? [],
    );

    if (templateKeys.length === 0) {
      return { socialRenderJobIds: [] };
    }

    const locales = project!.socialAutoRenderLocales === 'one'
      ? [article.locale]
      : ['de', 'en'];

    const jobIds: string[] = [];

    for (const templateKey of templateKeys) {
      for (const locale of locales) {
        // Eligibility check before enqueue
        const eligible = templateRegistry.isEligible(templateKey, article, discovery);
        if (!eligible) continue;

        const suggestion = (discovery?.suggestedTemplates ?? [])
          .find(s => s.templateKey === templateKey);

        const jobId = await enqueueSocialRenderJob({
          articleId: input.articleId,
          projectId: ctx.projectId,
          locale,
          theme: 'dark',
          templateKey,
          suggestionMeta: suggestion
            ? {
                suggestedTemplate: suggestion.templateKey,
                suggestionConfidence: suggestion.confidence,
                suggestionReason: null,    // no justification in DB type — by design
              }
            : undefined,
        });

        jobIds.push(jobId);
      }
    }

    return { socialRenderJobIds: jobIds };
  }
}
```

### D.4 `resolveAutoTemplates` helper

```typescript
// packages/pipelines/src/article/steps/social-generation.step.ts

function resolveAutoTemplates(
  config: string[],
  suggestions: Array<{ templateKey: string; confidence: number }>,
): string[] {
  // Empty config → top-1 suggestion (60.6 backward compat)
  if (config.length === 0) {
    const top1 = suggestions
      .filter(s => s.confidence >= 0.6)
      .sort((a, b) => b.confidence - a.confidence)[0];
    return top1 ? [top1.templateKey] : [];
  }

  // Special token → all suggestions above threshold
  if (config.includes('__suggested__')) {
    return suggestions
      .filter(s => s.confidence >= 0.6)
      .sort((a, b) => b.confidence - a.confidence)
      .map(s => s.templateKey);
  }

  // Explicit list → use as-is (eligibility checked at enqueue time)
  return config;
}
```

## Section I — Patterns Established by 60.7

**(102) `SocialGenerationStep.shouldRun()` is the canonical guard for optional
steps. Any future optional pipeline step should implement `shouldRun()` returning
`false` to skip cleanly — never use an `if` inside `execute()` for this.**

**(103) `resolveAutoTemplates()` is the single source of truth for which
templates get auto-generated. Always call it — never inline the resolution logic
in the step or pipeline. Config `[]` = top-1 suggestion, `['__suggested__']` =
all above threshold, explicit array = as-is with eligibility gate.**

**(104) `template_renders` is canonical going forward. `social_posts` is legacy.
No new rows should be written to `social_posts` after 60.7. Both tables are read
during the transition period via `mergeRenderHistory()`.**

## Section K — Deviations from Spec (Discovered During Implementation)

### K.1 `SocialGenerationInputSchema` carries pass-through fields

**Spec said:** `socialGenerationInputSchema = z.object({ articleId: z.string().uuid() })`

**Actual:** `SocialGenerationInputSchema = z.object({ articleId, wordCount, selfReviewScore })`

**Why:** `SocialGenerationStep` is the last step in `BlogPipeline`. The pipeline runner passes the final step's Zod-validated output directly as the pipeline result without calling `bridge()`. `BlogPipelineOutputSchema` expects `{ articleId, wordCount, selfReviewScore }`. Adding `SocialGenerationStep` as the last step requires its output schema to include those three fields, so its input schema must accept them too (pass-through pattern). Omitting them causes a `Zod invalid_type` error at pipeline completion.

**Pattern established:** see `packages/pipelines/CLAUDE.md` "Optional Steps — Pattern 102" and the new `DO NOT` entry about narrower last-step schemas.

### K.2 `skipOutput()` override added to `BaseStep`

**Spec said:** `shouldRun()` only.

**Actual:** Both `shouldRun()` and `skipOutput()` are implemented on `SocialGenerationStep`. The `BaseStep` contract was extended with an optional `skipOutput(input): Output` method that the engine calls when `shouldRun()` returns false, giving the pipeline a valid output shape with zero cost incurred.

**Why:** Without `skipOutput()`, returning `undefined` from a skipped step produces a `Zod parse error` at pipeline output validation. The `skipOutput` pattern gives the step full control over the no-op output shape (spreading all pass-through fields).

### K.3 Locale mapped as BCP-47 (`de-DE`/`en-US`), not short code

**Spec said:** `locales = ['de', 'en']`

**Actual:** The step maps `article.locale` to BCP-47 (`de` → `de-DE`, `en` → `en-US`) and iterates `renderLocales: string[]` in that format. The `template_renders` table stores `locale` as BCP-47.

**Why:** `template_renders.locale` is typed as BCP-47 (e.g. `"de-DE"`, `"en-US"`) throughout the codebase. Storing short codes would require a migration and break the existing render-worker's locale handling.

### K.4 Sibling article lookup for multi-locale renders

**Spec said:** "`locales = ['de', 'en']`" — no detail on how to get the content article in the right locale.

**Actual:** When `socialAutoRenderLocales === 'all'` and the target locale differs from the source article's locale, the step queries for a sibling article via `translationKey + locale` join (the same pattern as `TranslationSetupStep`). If no sibling exists for a given locale+template combination, that combination is silently skipped with a log entry.

### K.5 `BlogPipeline.runWithSocial()` stub NOT implemented

**Spec E.1 said:** Add a stub method with a TODO comment.

**Actual:** Not implemented. The stub is for the Content Planner (Theme 62), which is explicitly out of scope for Theme 60 (Spec H). Added here to track that this was a deliberate skip, not an oversight.
