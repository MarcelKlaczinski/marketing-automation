## 2. Issue 1 — Sibling-Locale-Modell als ein Task

### Aktuell

`ApplySiblingLocaleStep` (62.4 §4.2.7) erzeugt für jeden DE-Cluster ein zweites planned_item:
- locale='en'
- source_kind='sibling_locale'
- slot_date = parent.slot_date + 1 day
- parent_item_id = DE-Item.id

Im Kalender visuell verdoppelt sich die Anzahl Cluster-Cards.

### Soll

Ein planned_item pro Cluster, locale=null (oder weggelassen), Pipeline produziert intern DE+EN.

### Migration `0075_remove_sibling_locale_planning.sql`

```sql
-- 1) Add locale column to planned_items as nullable (default null)
ALTER TABLE planned_items
  ADD COLUMN locale text NULL;
-- locale values used by executor: null = "all locales bundled in one pipeline run",
-- 'de'/'en' = single-locale runs (legacy/explicit)

-- 2) Mark sibling_locale source_kind as deprecated but keep enum value for migration safety
-- (data migration below moves existing sibling rows, then we never insert new ones)
-- Note: keeping the enum value because historical plans may reference it

-- 3) Data migration: for any existing draft/approved plans with sibling_locale items,
--    delete the sibling rows (the parent will handle both locales going forward).
--    Only safe for plans NOT yet in 'running' or beyond — running plans must stay as-is.
DELETE FROM planned_items
WHERE source_kind = 'sibling_locale'
  AND weekly_plan_id IN (
    SELECT id FROM weekly_plans WHERE status IN ('draft', 'approved')
  );
```

**Rationale:** historische Plans die schon `running` oder `completed` sind, sollen ihren existierenden Zustand behalten (Audit-Trail). Nur draft/approved werden bereinigt.

### Code-Changes

**`packages/pipelines/src/planning/steps/apply-sibling-locale.ts`:**

Step wird **gelöscht**. Pipeline-Liste in `PlanWeekPipeline` verkürzt sich um diesen Step.

**`packages/pipelines/src/planning/steps/select-floor-items.ts` (und select-overage):**

Wenn `goal.contentType === 'cluster'` ein planned_item für ein topic_brief erzeugt wird, dann mit `locale=null` (Pipeline handelt beide). Kein Sibling-Spawn mehr.

**ClusterGenerationPipeline (62.0a oder wherever):**

Muss DE+EN intern produzieren. Discovery für Claude Code: prüfen ob ClusterGenerationPipeline aktuell:
- (A) nur DE produziert und Translation als separater Step danach läuft
- (B) bereits DE+EN intern produziert

Falls (A): ClusterGenerationPipeline muss erweitert werden um TranslationStep am Ende. Hängt von `articles.skipAutoTranslationUntil`-Flag aus 62.0a-followup ab — wenn gesetzt, EN-Phase skippen.

Falls (B): keine Änderung nötig, Sibling-Removal reicht.

### Tests

- Unit-Test: PlanWeekPipeline produziert für `cluster`-Goal mit min=1, cadence=per_day genau 7 planned_items, nicht 14
- Unit-Test: kein planned_item hat `source_kind='sibling_locale'` für neue Plans
- Integration-Test: Plan-Generation → 7 Cluster-Items, alle mit locale=null
- Manuelle Verifikation: alter Plan (KW 21) regenerieren mit force, neuer Plan zeigt 7 Cluster

### Caveats aus 62.5

- **Detail-Page-Scan ±4 Wochen:** Detail-Page nutzt aktuell `usePlanItemContext`-Composable das Items über ±4 Wochen vom aktuellen ISO-Week scannt. Nach Migration kann `parent_item_id` auf ein gelöschtes Sibling-Item zeigen (für Items die noch im historischen Plan referenziert sind). Detail-Page muss diesen Fall handhaben: wenn `parent_item_id` auf nicht-mehr-existierende Row zeigt, einfach kein "Sibling-Locale-Items"-Section rendern statt Error.
- **TanStack-Cache-Invalidierung:** 62.5 nutzt optimistic cache patching via `qc.setQueryData(...)`. Nach Sibling-Removal-Migration: die `["planner", "plan-detail", slug, planId]` Cache-Entries für aktive Plans müssen invalidiert werden (sonst zeigt UI weiter die Sibling-Items). Lösung: einmaliges `qc.invalidateQueries({ queryKey: ['planner'] })` beim ersten Page-Load nach Followup-Deploy. Pragmatisch: User reloadet die Page, dann ist alles synchron.

### Akzeptanz

## 3. Issue 2 — social_post Items fehlen

### Aktuelle Diagnose

`matchBriefToContentType` Heuristik (62.4 Deviation 5):
- comparison_discovery / cluster_action='comparison' → comparison
- intentType in (knowledge, tutorial) → ki_wissen
- else → cluster

**Kein Pfad zu social_post.** Goals sagen `social_post: per_day, min=3` aber kein topic_brief matched.

### Soll

Social Posts werden **nicht aus topic_briefs erzeugt**, sondern aus drei separaten Quellen:
1. **Articles die heute geplant sind** (heutige Cluster → 1 social_post pro DE-Article)
2. **Refresh-Pool** (Pre-flight Task 3 hat `refresh_suggestions` aktiviert)
3. **Suggestion-Pool** (existing articles via 54l/60.6 SocialPostsPanel-suggestions tab)

### Neuer Step: `SelectSocialPostItemsStep`

Eigener Step in PlanWeekPipeline, läuft nach `SelectFloorItems` + `SelectOverageItems` (die heute-geplanten Cluster sind dann bekannt):

```ts
class SelectSocialPostItemsStep extends BaseStep<...> {
  async run(input, ctx, priorOutputs) {
    const { goals, config } = priorOutputs.validateGoals;
    const socialGoal = goals.find(g => g.contentType === 'social_post');
    if (!socialGoal) return { socialItems: [] };
    
    const targetCount = socialGoal.cadenceUnit === 'per_day'
      ? socialGoal.minCount * 7
      : socialGoal.minCount;
    
    // Mix-Strategie aus initial Marcel-Anforderung:
    // - 1/3 aus heute-geplanten Cluster-Items
    // - 1/3 aus refresh_suggestions
    // - 1/3 aus suggestion-pool (existing articles)
    
    const fromTodayPlans = pickFromTodaysClusters(priorOutputs.selectFloor, Math.ceil(targetCount / 3));
    const fromRefreshPool = await pickFromRefreshSuggestions(input.projectId, Math.ceil(targetCount / 3));
    const fromSuggestionPool = await pickFromSuggestionPool(input.projectId, targetCount - fromTodayPlans.length - fromRefreshPool.length);
    
    return { socialItems: [...fromTodayPlans, ...fromRefreshPool, ...fromSuggestionPool] };
  }
}
```

**Helper-Funktionen** in `packages/planner/src/social-source-selectors.ts`:
- `pickFromTodaysClusters` — produziert social_post-Items aus Cluster-Items des aktuellen Plans
- `pickFromRefreshSuggestions` — liest `refresh_suggestions` Tabelle, sortiert nach Score/Recency
- `pickFromSuggestionPool` — liest `template_renders` (60.6) oder vergleichbare Suggestion-Source

### Discovery vor Implementation

Claude Code Phase 0:
1. Check ob `template_renders` Tabelle bereits Social-Post-Suggestions enthält (60.6) und wie sie strukturiert sind
2. Check ob es eine dedizierte "social_post-pending-suggestions" View gibt
3. Wenn keine Suggestion-Pool-Source identifizierbar: Phase 1 = nur Today's Clusters + Refresh-Pool, Suggestion-Pool als Phase-E-Backlog

### Tests

- Unit-Test: SelectSocialPostItemsStep produziert min × 7 Items wenn alle Quellen reichen
- Unit-Test: SelectSocialPostItemsStep fällt zurück auf weniger Items wenn Quellen leer (analog Floor-Cadence partial-fill)
- Integration-Test: Plan-Generation mit social_post Goal produziert ≥1 social_post Item pro Tag

### Akzeptanz

- [ ] `SelectSocialPostItemsStep` als BaseStep implementiert
- [ ] In PlanWeekPipeline integriert
- [ ] Toolwiki-Re-Plan zeigt ≥1 social_post Item pro Tag (mind. 7/Woche bei min=3/Tag, wenn Quellen reichen)

### Code-Changes

`apps/web/src/components/planner/PlannerItemCard.vue`:

```ts
function sourceKindLabel(kind: SourceKind, locale: string): string {
  switch (kind) {
    case 'floor': return t('planner.itemCard.scheduled');
    case 'overage_signal': return t('planner.itemCard.trend');
```

**Wichtig (62.5 Discovery #1):** vue-i18n v10 mit `legacy: false` interpretiert `$t(key, fallback)` zweiten Param als **named params, NICHT als fallback-message**. Stattdessen: i18n-Key in `de.ts` UND `en.ts` definieren, dann nur `$t('planner.itemCard.scheduled')`.

i18n-Updates in `apps/web/src/i18n/{de,en}/planner.ts`:

```ts
itemCard: {
  scheduled: { de: "Geplant", en: "Scheduled" },
  trend: { de: "Trend", en: "Trend" },

```

## 11. Deviations from Spec

### D1. i18n Naming — kein eigener `itemCard.*` Namespace

**Spec sagte**: neue Keys unter `planner.itemCard.scheduled`, `planner.itemCard.trend`, `planner.itemCard.enVersion`.

**Tatsächlich**: existierende Keys unter `planner.sourceKind.{floor,overage_signal,sibling_locale}` mit den User-Strings überschrieben. Card-Template referenziert dieselben Keys wie vorher — keine Code-Änderung im `<span class="source-kind-badge">` Innenleben nötig. Sauberer Namespace, kein Parallel-Dictionary.

### D2. ClusterGenerationPipeline-Erweiterung NICHT nötig

**Spec § 2 Phase 0** hatte die offene Frage: produziert `cluster:full-plan` (heute "ClusterGenerationPipeline" genannt) intern DE+EN oder muss ein TranslationStep angehängt werden?

**Discovery in `packages/pipelines/src/cluster/full-plan/enqueue-spokes.ts`**: `cluster:full-plan` ist die LLM-Planning-Pipeline (54.12), produziert keine Artikel. Stattdessen kickt `enqueueClusterSpokes` für jeden Spoke ein `enqueueBlogGeneration({ briefId, projectId })` an. Die `BlogPipeline` triggert in `afterComplete` automatisch `enqueueTranslationPipeline` (Spec 59.2 bidirektional) — sofern `project.targetLocales` die Gegen-Locale enthält UND `project.translationAutoTrigger === true` UND `article.skipAutoTranslationUntil` nicht aktiv (Spec 62.0a-followup Issue 1).

Damit ist die DE+EN-Produktion bereits bidirektional verkabelt und braucht im 62.4-followup keine zusätzliche Pipeline-Verlängerung. Issue 1 reduziert sich auf den Planner-Side: Sibling-Spawn löschen.

### D3. `parentDraftId` für Social-Items aus heutigen Clustern

**Spec § 3 sagte**: "1/3 aus heute-geplanten Cluster-Items". Implementation-Detail offen.

**Tatsächlich**: Pro genommenem Cluster-Item ein Social_Post-Draft erzeugt mit:
- `parentDraftId = cluster.draftId` (in-memory link)
- `parentItemId = cluster.draftId` (DB-link nach `PersistPlanStep`, denn der Step nutzt `draftId AS id` für die INSERT-row-id)
- `pipelineInput = { projectId, parentDraftId: cluster.draftId, parentBriefId: cluster.sourceBriefId }`
- `slotDate = cluster.slotDate` (Social läuft am selben Tag — Executor 62.8 sequenced post-publish)

Der Executor (Spec 62.8) löst beim Ausführen `parentItemId → articleId` über die `plannedItems`-Row + den parent's `pipelineRunId → articles.id` Lookup auf. Im 62.4-followup-Scope nicht implementiert — der Planner schreibt nur die Calendar-Rows.

### D4. Cluster-Counter bleibt in `selection_reason`

**Spec § 4 sagte**: "Cluster-Counter '#1/7' bleibt entfernen — ist Audit-Detail, gehört in Detail-Page nicht in Card."

**Tatsächlich**: Counter bleibt im DB-Feld `selection_reason` (z.B. `"Floor cluster #2/7"`), wird aber NICHT mehr im Card-Title gerendert — er erscheint nur noch in 2 Surfaces:
- Source-Kind-Badge-Tooltip (Hover, 200ms Delay)
- PlannerItemDetailPage Audit-Section

Die Card zeigt stattdessen den user-friendly `sourceKind`-Label. Damit bleibt Audit-Info erhalten ohne UI-Lärm.

### D5. Suggestion-Pool: `template_renders` als Datenquelle bestätigt

**Spec § 3 Phase 0 Frage**: ob `template_renders` (Spec 60.6) als Suggestion-Pool-Source nutzbar ist.

**Discovery**: Ja — `template_renders` hat `article_id`, `template_key`, `locale`, `theme`, `status` + `created_at`. `pickFromSuggestionPool` queryt published articles, die in den letzten 14 Tagen KEINEN template_render hatten (`NOT EXISTS (SELECT 1 FROM template_renders WHERE article_id = ... AND created_at > cutoff)`). Recente-Render-Cutoff ist konfigurierbar via `recentRenderCutoff` Param.

## 12. Discovered

### Dis-1. Drizzle `sql.join()` für IN-Listen statt naive `inArray()` Cast

Beim `excludeClause` in `pickFromSuggestionPool` ist `inArray(articles.id, [...ids])` korrekt — aber das spezifische Pattern `${articles.id} NOT IN (...)` musste manuell gebaut werden weil das innerhalb eines `sql\`NOT EXISTS (...)\``-Templates lebt. Pattern: `sql.join(ids.map(id => sql\`${id}\`), sql\`, \`)`. Verhindert SQL-Injection und Drizzle parametrisiert weiterhin.

### Dis-2. PlannerItemDetailPage-Composable hat keine separate Sibling-Lookup-Fn

Beim Defensive-Null-Check in 62.5 Detail-Page war ein neues `computed parentItem()` nötig (suchte vorher `item.parentItemId` direkt im Template). Composable `usePlanItemContext` selbst hat keine Sibling-Resolver — der Detail-Page-Component löst das inline aus `items[]`. Bei zukünftigem Sibling-Pattern (z.B. wenn locale='de' + 'en' irgendwann doch wieder als separate Items modelliert werden) wäre ein dedizierter Helper sinnvoll.

### Dis-3. Stale Sibling-Test in `apps/api/test/plan-generation.test.ts` Scenario 6

Beim Test-Suite-Lauf nach Issue 1 fiel der Integration-Test "Scenario 6: DE cluster items get an EN sibling item with parent_item_id linked" um. Wurde zu "Scenario 6 (Spec 62.4-followup Issue 1): cluster items emit one planned_item with locale=null — no EN sibling" umgeschrieben — assertiert jetzt das neue Invariant (1 Cluster-Item, `locale=null`, `sourceKind='floor'`, kein `sibling_locale` Row).

### Dis-4. `distribute-slot-dates.test.ts` zu Social-Item-Path migriert

Die alten Sibling-Test-Cases (Tests 4 + 5 — `places sibling at parent.slotDate + 1 day` und `clamps sibling that would overflow into next week to Sunday`) wurden gelöscht und durch zwei neue Social-bezogene Tests ersetzt: `distributes social_post items across Mon..Sun rotation` + `preserves pre-assigned slotDate from social-source selectors`. Letzterer testet die wichtige Invariante dass `DistributeSlotDatesStep` ein vorbelegtes `slotDate` (gesetzt durch SelectSocialPostItemsStep wenn Parent-Cluster bereits ein Datum hat) NICHT überschreibt.

### Dis-5. `q-tooltip` in `.item-title` ersetzt redundantes `:title="title"`

Während der Implementation gemerkt: das alte `<p class="item-title" :title="title">{{ title }}</p>` zeigte sowohl native Browser-Tooltip als auch (jetzt) das styled `q-tooltip`. Pattern ist redundant. `:title` entfernt — nur noch `q-tooltip` Child mit Quasar-Styling.
