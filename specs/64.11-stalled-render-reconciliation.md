## 1. Problem

Aus Discovery Phase-E Backlog Reality Check (2026-05-23) Section 6 Top-1:

> "Both items hit Marcel's daily UX directly. Stalled-render is the silent-loss case (a render crashes during the 5-10 min Remotion job and the post is stuck forever; user has no way to retry without finding it manually). Push-notifications close the long-running-blog feedback loop (Marcel walks away during a 7-min `article:blog` run and currently has no completion signal)."

Plus Discovery Recommendation §1:
> "Bundling them keeps the worker-restart cost amortized — both share the same `social-render.worker.ts` + worker `index.ts` surface."

### Finding A: Stalled-Render Silent Loss

**Symptom:**
- Remotion render job läuft 5-10 Minuten
- Worker crashes mid-render (OOM, container restart, network blip)
- `social_posts.render_status` bleibt auf `'rendering'`
- BullMQ stall-detect setzt sich aber kein app-level recovery existiert
- Marcel sieht "rendering..." spinner forever
- Manuelles retry nur via DB-edit oder UI re-trigger

**Konsequenz:**
- Lost work (Article-Cost ist bezahlt, render-Cost wird beim retry erneut anfallen)
- Marcel-Confusion bei "ist der Render hängen oder läuft noch?"
- Plus: stuck rows blockieren queue-throughput in BullMQ (stall-detect setzt Job auf failed nach timeout, aber row bleibt orphaned)

**Aus doc2 §3.3 Hardening:**
> "BullMQ stall detection set, but no app-level reset for `renderStatus='rendering'` after worker crash."

### Finding B: Pipeline-Completion Push-Notification Gap

**Symptom:**
- `article:blog` Pipeline läuft 5-10 Minuten
- Marcel triggert Generation, geht weg
- Beim zurückkommen kein Signal "fertig"
- Manual refresh / dashboard-checks nötig

**Aus doc2 §3.3:**
> "Infrastructure fully built (`packages/core/src/notifications/`, `apps/api/src/routes/notifications.ts`, VAPID, push-subscriptions). Only wiring missing — connect `Worker.on('completed')` for `article:blog` + `social-render`."

- `createNotification()` helper in `packages/core/src/notifications/` ✅
- SSE channel for in-browser notifications ✅
- Nur fehlt: `Worker.on('completed')` listeners

Beide items berühren:

## 2. Ziel

**Fix A: Stalled-Render Reconciliation**

- Worker-startup runs reconciliation step
- Findet rows mit `render_status='rendering' AND render_started_at < NOW() - INTERVAL '15 minutes'`
- Reset `render_status` zu `pending`
- Plus: `cluster:full-plan` und `article:blog` analog check für stuck pipeline_runs
- Idempotent (kann beliebig oft laufen)

**Fix B: Pipeline-Completion Push-Notifications**

- `Worker.on('completed')` listener für 3 pipelines:
  - `article:blog` (5-10 min runs, biggest UX-win)
  - `social-render` (3-5 min runs)
  - `cluster:full-plan` (10-15 min runs)
- Listener calls `createNotification()` from `packages/core/src/notifications/`
- Notification-Payload: pipeline-name, articleId/socialPostId, completion-status
- User sees Browser/PWA push + in-app SSE update

**In Scope:**
- Worker startup reconciliation (~30 min code)
- Worker completion listener wiring (~1 day code)
- Tests: reconciliation (2 cases), notification trigger (3 cases per pipeline)
- Plus: timeout config via getEnv() für reconciliation threshold
- Plus: notification-payload schema in `packages/shared/notifications/types.ts`
- Plus: documentation in `apps/api/CLAUDE.md` "Worker Lifecycle"

**Out of Scope:**
- Reconciliation für andere pipelines (translation, refresh) — gleiche worker-surface aber nicht in Discovery Top-1 scope
- Push-notif für article:translation, article:refresh, article:hero-generation — kürzere runs, kein UX-pain
- Worker process recycling (`maxJobsPerWorker`) — doc2 Tier 1 item, eigene Spec
- Reconciliation-Cron (periodic running) — startup-only reicht laut Discovery
- Notification-Preferences UI (mute, channel-select) — eigene future Spec
- Notification-History persistierte Liste — SSE only für jetzt
- Push-notif für mobile native apps — PWA-push reicht

**Aufwand:** ~1.5 Tage Implementation + ~45 Min Tests + ~15 Min manual verification.

## 3. Architektur

### 3.1 Reconciliation Helper (Fix A)

**File:** `apps/api/src/workers/lib/render-reconciliation.ts` (neu)

**Pattern:** Pure helper invoked at worker startup, mirror existing patterns from `convert-existing-heroes.ts`.

**Code Skeleton:**

```ts
import { db, socialPosts, pipelineRuns } from "@marketing-auto/db";
import { eq, and, lt, isNotNull, sql } from "@marketing-auto/db";
import { log } from "@marketing-auto/shared/logger";
import { getEnv } from "@marketing-auto/shared/config";

interface ReconciliationSummary {
  socialPostsReset: number;
  pipelineRunsReset: number;
}

/**
 * Resets render_status='rendering' rows that have exceeded the timeout
 * to 'pending', allowing user re-render trigger.
 * 
 * Idempotent — runs at worker startup, can be invoked any time.
 */
export async function reconcileStalledRenders(): Promise<ReconciliationSummary> {
  const env = getEnv();
  const timeoutMinutes = env.RENDER_RECONCILIATION_TIMEOUT_MINUTES ?? 15;
  const cutoff = sql`NOW() - INTERVAL '${sql.raw(String(timeoutMinutes))} minutes'`;
  
  // Step 1: Reset stalled social_posts
  const socialResult = await db
    .update(socialPosts)
    .set({ 
      renderStatus: "pending",
      renderStartedAt: null,  // CRITICAL: clear so next reconciliation doesn't re-pick
    })
    .where(and(
      eq(socialPosts.renderStatus, "rendering"),
      isNotNull(socialPosts.renderStartedAt),
      lt(socialPosts.renderStartedAt, cutoff),
    ))
    .returning({ id: socialPosts.id });
  
  // Step 2: Reset stalled pipeline_runs (article:blog + cluster:full-plan)
  const pipelineResult = await db
    .update(pipelineRuns)
    .set({ status: "pending" })
    .where(and(
      eq(pipelineRuns.status, "running"),
      lt(pipelineRuns.startedAt, cutoff),
    ))
    .returning({ id: pipelineRuns.id });
  
  const summary: ReconciliationSummary = {
    socialPostsReset: socialResult.length,
    pipelineRunsReset: pipelineResult.length,
  };
  
  if (summary.socialPostsReset > 0 || summary.pipelineRunsReset > 0) {
    log.warn({ summary, cutoffMinutes: timeoutMinutes }, 
      "render reconciliation reset stalled rows");
  } else {
    log.info({ cutoffMinutes: timeoutMinutes }, 
      "render reconciliation: no stalled rows");
  }
  
  return summary;
}
```

**Decision-Rationale:**
- 15 min default (configurable) — Remotion renders max ~10 min, +5 min Sicherheitspuffer
- `renderStartedAt = null` muss mit-cleared werden (sonst would re-pick on next reconciliation)
- Idempotent: zweite Aufruf findet 0 rows, ist no-op
- Plus: pipeline_runs.status mapping respectiert existing schema (`pending`/`running`/`success`/`failed`)

### 3.2 Worker Startup Integration

**File:** `apps/api/src/workers/index.ts`

**Current pattern (existing):**

```ts

  // ... existing worker initializations ...
}
```

**Patch:**

```ts
import { reconcileStalledRenders } from "./lib/render-reconciliation";

export async function startAllWorkers() {
  // NEW: Reconciliation FIRST, before workers spawn
  log.info("starting render reconciliation on worker startup");
  const summary = await reconcileStalledRenders();
  if (summary.socialPostsReset > 0 || summary.pipelineRunsReset > 0) {
    log.warn({ summary }, "worker startup reset stalled rows");
  }
  
  // ... existing worker initializations ...
}
```

**Decision-Rationale:**
- Reconciliation BEFORE worker spawn — rows sind `pending` wenn neue workers polling starten
- Sequential, nicht parallel — pure DB-write, ~10ms latency
- Log-output zeigt admins was reset wurde nach crash-restart

### 3.3 Notification Trigger Helper (Fix B)

**File:** `apps/api/src/workers/lib/pipeline-notification.ts` (neu)

**Pattern:** Wrapper für `createNotification()` mit pipeline-aware payload-shapes.

**Code Skeleton:**

```ts
import { createNotification } from "@marketing-auto/core/notifications";
import { db, articles, socialPosts } from "@marketing-auto/db";
import { eq } from "@marketing-auto/db";
import { log } from "@marketing-auto/shared/logger";

interface PipelineCompletedEvent {
  pipelineName: "article:blog" | "social-render" | "cluster:full-plan";
  pipelineRunId: string;
  articleId?: string | null;
  socialPostId?: string | null;
  clusterId?: string | null;
  status: "success" | "failed";
  errorMessage?: string;
}

export async function notifyPipelineCompletion(
  event: PipelineCompletedEvent,
): Promise<void> {
  try {
    const { projectId, payload, deepLink } = await buildNotificationPayload(event);
    
    await createNotification({
      projectId,
      type: `pipeline_completed:${event.pipelineName}`,
      payload,
      deepLink,
      sentVia: ["push", "sse"],
    });
    
    log.info({ event }, "pipeline completion notification dispatched");
  } catch (err) {
    log.error({ event, err }, "failed to dispatch pipeline notification");
    // Don't throw — notification failure should NOT fail the worker
  }
}

async function buildNotificationPayload(event: PipelineCompletedEvent) {
  switch (event.pipelineName) {
    case "article:blog": {
      if (!event.articleId) throw new Error("article:blog requires articleId");
      const [article] = await db
        .select({ projectId: articles.projectId, title: articles.title, slug: articles.slug })
        .from(articles)
        .where(eq(articles.id, event.articleId));
      
      return {
        projectId: article.projectId,
        payload: {
          title: event.status === "success" 
            ? `Article fertig: ${article.title}` 
            : `Article failed: ${article.title}`,
          body: event.status === "success"
            ? "Klick zum Review"
            : event.errorMessage ?? "Generation failed",
        },
        deepLink: `/projects/<slug>/articles/${article.slug}`,
      };
    }
    
    case "social-render": {
      if (!event.socialPostId) throw new Error("social-render requires socialPostId");
      const [post] = await db
        .select({ projectId: socialPosts.projectId, title: socialPosts.title })
        .from(socialPosts)
        .where(eq(socialPosts.id, event.socialPostId));
      
      return {
        projectId: post.projectId,
        payload: {
          title: event.status === "success" ? "Social-Post gerendert" : "Render failed",
          body: post.title,
        },
        deepLink: `/projects/<slug>/social/${event.socialPostId}`,
      };
    }
    
    case "cluster:full-plan": {
      if (!event.clusterId) throw new Error("cluster:full-plan requires clusterId");
      // ... similar shape with cluster table query ...
    }
    
    default: {
      const _exhaustive: never = event.pipelineName;
      void _exhaustive;
      throw new Error("unknown pipeline name");
    }
  }
}
```

**Decision-Rationale:**
- Notification-Builder per-pipeline weil deepLink + title divergieren
- Try/catch um ganzen wrapper — notification failure NICHT als worker-failure
- Plus: `sentVia: ["push", "sse"]` deklariert beide Kanäle (Push für offline / Mobile, SSE für in-browser live update)

### 3.4 Worker Completion Listeners

**Files:**
- `apps/api/src/workers/social-render.worker.ts`
- `apps/api/src/workers/article-pipeline.worker.ts`
- (cluster:full-plan worker — wenn separater worker existiert, sonst article-pipeline.worker)

**Pattern:**

```ts
import { notifyPipelineCompletion } from "./lib/pipeline-notification";

// Existing worker definition...
const worker = new Worker(
  "social-render",
  async (job) => {
    // ... existing job handler ...
  },
  workerConfig,
);

// NEW: Completion listener
worker.on("completed", async (job, result) => {
  await notifyPipelineCompletion({
    pipelineName: "social-render",
    pipelineRunId: job.id ?? "unknown",
    socialPostId: job.data.socialPostId,
    status: "success",
  });
});

worker.on("failed", async (job, error) => {
  if (!job) return;  // job could be undefined per BullMQ types
  await notifyPipelineCompletion({
    pipelineName: "social-render",
    pipelineRunId: job.id ?? "unknown",
    socialPostId: job.data.socialPostId,
    status: "failed",
    errorMessage: error.message,
  });
});
```

**Decision-Rationale:**
- Both `completed` + `failed` listeners — Marcel sieht success UND failure notifications
- Async listener — fire-and-forget, doesn't block job-processing
- `job.id ?? "unknown"` defensive für BullMQ edge-cases

## 7. Risiken

| Risk | Mitigation |
|---|---|
| 15 min timeout too aggressive — kills legitimate long renders | Default ist 15 min, configurable via env. Remotion renders nach Discovery max ~10 min, +5 min puffer. Wenn renders länger werden → env raise. |
| Reconciliation läuft während worker bereits aktiv — race condition | Reconciliation läuft ONCE at startup, BEFORE workers spawn. Plus: idempotent — kein damage if double-run. |
| Notification dispatch zu chatty — Marcel ist überflutet | Initial: completed + failed both. Wenn zu viel → future preferences UI. Plus: PIPELINE_NOTIFICATIONS_ENABLED env als kill-switch. |
| Push-notification permission nicht granted im Browser → silent failure | SSE channel ist immer da als fallback. Plus: notification failure doesn't fail worker (try/catch). Marcel siehe in-app SSE-updates auch ohne push-permission. |
| createNotification() throws on DB-down → worker job marked failed | try/catch um whole notify-call. Notification failure ist nicht business-critical. |
| pipeline_runs reset könnte production-running pipelines unterbrechen | NUR rows mit `startedAt < cutoff` werden reset. Active pipelines haben recent `startedAt` → unangetastet. |
| Tests-Race: test seed läuft + worker startup race | Tests use isolated test-project + transactional rollback. Real worker startup-chain runs OUTSIDE tests. |
| `cluster:full-plan` worker file existence unklar | Phase 0 verifiziert. Wenn inline in article-pipeline.worker → 1 file edit. Wenn separater file → 2 files. Acceptable. |
| `Worker.on('completed')` could miss events during high-throughput | BullMQ guarantees these events fire — confirmed pattern in existing codebase. Plus: SSE in-app sieht every status change unabhängig. |

## 8. Anschluss

Nach Spec 64.11:
- Stalled renders self-recover bei worker-restart (no manual DB-edit nötig)
- Marcel bekommt completion-notification für article:blog / social-render / cluster:full-plan
- Daily UX deutlich besser für long-running operations
- Plus: pattern dokumentiert für künftige worker-additions

## 10. Discovered & Deviations

| # | Discovery | Decision |
|---|---|---|
| 1 | Spec §3.1 reset target `"pending"` is invalid — `pipelineRunStatusEnum` has no `pending` value (only `queued | running | completed | failed | cancelled | batch_pending | paused | superseded`). | Reset to `failed` with `errorMessage` = `"reconciled: worker startup detected stalled run (BullMQ job lost; pipeline_runs row was orphaned)"` + stamp `completedAt`. Semantically accurate — BullMQ job is gone, re-execute is a Marcel-side decision. |
| 2 | Spec §3.3 assumed `createNotification({projectId, payload, deepLink, sentVia})` but the real signature is `({userId, type, severity, title, message, link?, metadata?})`. Notifications are keyed by `userId`; severity drives channel (Web Push only on `critical`; SSE always). | Mirror `notifyStepPaused` pattern: fan out to `users.role='owner'`, build link from `projects.slug`. Severity = `info` (success) / `critical` (failure) so push wakes Marcel on the rare-but-important failure. |
| 3 | `apps/api/src/workers/article-pipeline.worker.ts` (named in spec §3.4) does not exist. Article generation runs through the shared `startPipelineWorker` in `packages/pipelines/src/engine/queue.ts`. | Add a `RICH_COMPLETION_PIPELINES` set inside that one shared listener — single integration point covers any future content pipeline added to the set. |
| 4 | The shared `queue.ts` listener already wired `MEANINGFUL_PIPELINES` (info-level success for outline/draft/sync/cold-start) AND `pipeline_failure` (critical for all pipelines). Adding my helper naively would double-notify on `article:blog` failures. | Wrap both legacy fan-outs with `if (RICH_COMPLETION_PIPELINES.has(name)) { … return; }` — selected pipelines get the rich-payload path, everyone else keeps the legacy path. No legacy regression. |
| 5 | Spec §2 "In Scope" listed `cluster:full-plan` notifications, but Phase 0 discovery confirmed cluster:full-plan runs inline via `runClusterFullPlanFromBrief()` (Memory D127). No `worker.on('completed')` to hook. | Drop from V1. Successful spokes already fire their own `article:blog` notification, so a cluster-level summary is redundant. Documented in `apps/api/CLAUDE.md` + helper's pipelineName union restricted to `article:blog | social-render`. |
| 6 | Spec §3.5 proposed `packages/shared/notifications/types.ts`. That module doesn't exist; existing notification types live in `packages/core/src/notifications/`. | Added `pipeline-completion.ts` as a sibling of `step-pause.ts` inside `packages/core/src/notifications/` and re-exported from `index.ts` — keeps `@marketing-auto/core/notifications` as the single subpath consumers already use. |
| 7 | Spec §4.2 tests use Vitest (`vi.spyOn`, `vi.mocked`), but apps/api uses `bun:test` with real DB. | Tests query the `notifications` table directly. Real-DB tests caught a subtle bug the mocks would have hidden: the helper coalesces ACROSS users on `(type, pipelineRunId)`, so static run IDs (`"run-success-1"`) collide with prior test runs' notifications attached to undeleted tenant owners. Fixed by stamping every test's `pipelineRunId` with `Date.now()+random`. |
| 8 | Fan-out tests assumed exactly 2 owners exist, but the test DB has ~10 pre-existing tenant owners. `expect(rows.length).toBe(2)` failed. | Switched fan-out assertion from "exact count" to "both my newly-created owners received their slice" — query each user's notifications individually by `(userId, metadata->>'pipelineRunId' = my-unique-id)` and assert each = 1. |
| 9 | Drizzle/postgres.js rejects bound parameters inside SQL INTERVAL literals (root CLAUDE.md DO-NOT rule). | Use `sql\`NOW() - INTERVAL '${sql.raw(String(cutoffMinutes))} minutes'\`` — safe because `cutoffMinutes` is env-validated as a positive integer (no user input reaches `sql.raw`). |
| 10 | `social_posts.content` is `notNull` with `$type<SocialPostContent>` requiring `kind`, `slides`, `caption`, `hashtags`. Test fixtures with only `{kind, slides}` failed typecheck. | Minimal valid shape: `{kind: "carousel", slides: [], caption: "", hashtags: []}` in all test fixtures. |
| 11 | Pre-existing 2/53 `buildHashtagInstructions` test failures in `@marketing-auto/core` (Spec 57.4 territory) appeared in the workspace test run. | Verified via `git stash` baseline that these fail on `master` too — not a regression. Flagged for a separate cleanup, not blocking this spec. |
| 12 | `articles.status` enum does not include `"draft"` (test fixtures used it). Valid values per `articles` schema: `drafting | outline_review | final_review | …`. | Switched fixtures to `status: "drafting"`. |
