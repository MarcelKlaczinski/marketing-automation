## Goal

Produce a **single Markdown document** that captures the codebase facts needed to write subsequent Theme 54 specs (54.8, 54.9, Phase E backlog specs) without the Schema-vs-Reality drift that caused 7 deviations in Spec 54.7. The document is checked into the repo at `specs/_reference/codebase-reference.md` and updated whenever underlying schemas, routes, or conventions change.

This is **not** a refactor task. Pure inspection + documentation. No code changes outside the new reference file.

After this task:
- Every future spec opens with a "verified against codebase-reference.md as of <date>" line
- The reference file is **the source of truth** for column names, file paths, FK relationships, naming conventions, and pattern locations
- Spec-vs-reality deviations should drop from 7 (Spec 54.7) to 0-2 per subsequent spec

## What this is NOT

- Not refactoring any code
- Not changing any schemas
- Not creating new tests
- Not documenting external libraries (Drizzle, Hono, Quasar internals)
- Not a stylistic code review
- Not a full project README — focused on what specs need

specs/_reference/codebase-reference.md

### 10. Recurring Patterns & Lessons Learned

A pattern library distilled from Theme 54 implementation reports:

```markdown
## Recurring Patterns

### TypeScript: strict-mode insertion
When inserting Zod-validated data into Drizzle:
\`\`\`typescript
const drizzleRow = Object.fromEntries(
  Object.entries(zodValidated).filter(([, v]) => v !== undefined)
) as typeof table.$inferInsert;
\`\`\`

### TypeScript: optional function parameters
With `exactOptionalPropertyTypes` enabled:
\`\`\`typescript
// Don't:  callFunc({ pipelineRunId })  // string | undefined fails
// Do:     callFunc({ ...(pipelineRunId !== undefined && { pipelineRunId }) })
\`\`\`

### Zod: stored config evolution
When extending a schema whose JSONB blob is already stored (e.g. TopicScopeSchema):
- Use .default() on new fields
- ENSURE loadActiveConfig() (or equivalent loader) parses through the schema, not raw return
- Otherwise callers see undefined for new fields → crashes

### Zod: post-parse mutation
\`\`\`typescript
// parsed.data is readonly
// Mutate via spread:
const proposal = { ...parsed.data };
proposal.foo = corrected;
\`\`\`

### Zod: .default() under exactOptionalPropertyTypes
When a Zod schema uses .default() and matches a typed interface:
\`\`\`typescript
const _InputSchema = z.object({ x: z.string().default("...") });
export const InputSchema = _InputSchema as z.ZodType;
\`\`\`

### Zod: defaults-only inputs (`{} as never`)
For sources called with no explicit input (HN signal source pattern from 54.4).

### Drizzle: targetWhere for partial indexes
\`onConflictDoUpdate({ target: [...], targetWhere: ... })\` — must match the partial index WHERE predicate BYTE-EXACTLY.

### Drizzle: external API in transaction
Never call external APIs inside db.transaction() — holds transaction open during network roundtrip. Compute outside, persist inside.

### Drizzle: FK declarations
Declare FKs via raw SQL migration (not Drizzle .references()) when there's any risk of circular imports.

### Custom Error classes
NEVER use `kind` or `cause` as property name (ES2022 reserved). Use `Kind`.

### LLM output validation
\`\`\`typescript
.max(soft_limit + 50%).transform(s => s.slice(0, soft_limit))
\`\`\`
For LLM-emitted strings with char limits — LLMs occasionally exceed. Transform is cheaper than BullMQ retry.

### i18n: never hardcoded in templates
Including Quasar rule messages. Always go through $t() / i18n. Strings live in i18n//.ts.

### vue-i18n v10 Composition API
$tc() removed. Use $t(key, { n: count }, count) — named first, plural count second.

### Composables vs Options API
useXxx composables that need a function-at-call-time can't compose cleanly into Options API setup(). Use manual setInterval + beforeUnmount instead of generic polling composables when this(=Options API instance) is needed.

### TopicSource pattern
- Implements TopicSource
- emit(input, ctx): Promise
- Does NOT persist itself — caller owns transaction

### ExternalSignalSource pattern (mirror)
- Implements ExternalSignalSource
- fetch(input, ctx): Promise
- Does NOT persist itself

### Adapter package structure
- packages/adapters//src/{index,client,verify}.ts
- ./verify subpath export
- credentials.ts when vault-stored
- Vault-first, env-fallback pattern in main client function

### Project config evolution
- All JSONB columns (topic_scope, master_prompts, signal_sources) parsed via loadActiveConfig
- Adding new fields requires .default() in Zod schema
- No DB migration needed for backward-compat (defaults apply on parse)

### Test fixtures
- ALWAYS mixed-source data (multiple `source`, multiple `approval_status`)
- Single-source fixtures hide cross-cutting bugs (54.3, 54.5 lessons)
```

## How to Generate the Document

### Step 1: Inspect each Theme-54-relevant table

For every table in section 1's list:
1. Open `packages/db/src/schema/<file>.ts`
2. Find the `pgTable("table_name", { ... })` declaration
3. List every column with EXACT names (Drizzle field name AND SQL column name)
4. Look at exported types (`type X = typeof table.$inferSelect`, `type NewX = typeof table.$inferInsert`)
5. Scan migrations folder for FK and partial index declarations not in Drizzle code
6. Capture as Markdown per the template

### Step 2: Inspect every JSONB column

For each JSONB column found in Step 1:
1. Find its Zod schema (search for the column name in the schema file)
2. Paste literal schema
3. grep for files that read/write the column

### Step 3: Map relationships

Trace foreign keys to produce the ER diagram. Pay particular attention to `clusters.pillar_id`, `articles.cluster_id`, `articles.project_config_version_id`, `topic_briefs.cluster_id`, `topic_briefs.routed_article_id`, `topic_briefs.routed_cornerstone_spec_id`, `external_signals.processed_into`, `cornerstone_specs.cluster_id`.

### Step 4: Inspect routing decisions

1. Open `packages/pipelines/src/routing/types.ts` (or equivalent)
2. Find the discriminated union of `RoutingDecision`
3. List every `kind`
4. For each, check `execute-decision.ts` to see if there's a real handler or a `throw new RoutingNotImplementedError`
5. Document caller chains

### Step 5: Topic sources

`grep -r "implements TopicSource" packages/pipelines/src/topic-sources/` and document each.

### Step 6: cluster_action enum

`grep -rn "cluster_action" packages/` and `grep -rn "clusterAction" packages/` to find where the enum is validated. List all values.

### Step 7: Filesystem layout

Sample a few existing route files, worker files, component files to verify the documented conventions. Pay attention to:
- Where `app.route(...)` calls live (server.ts vs index.ts)
- Where `new Worker(...)` is registered
- Page component naming convention
- Composable file location

### Step 8: Env vars and COST_OPS

1. Open `packages/shared/src/config.ts` (or equivalent) — list all env var consumers
2. Open `packages/shared/src/cost.ts` (or operations.ts) — list all registered operations with estimates

### Step 9: Compile lessons

Pull the "Discovered" and "Deviations" sections from all completed Spec implementation reports (54.1-54.7) and distill into "Recurring Patterns" section.

### Step 10: Tech debt snapshot

Open `specs/POST-54-BACKLOG.md` and summarize current contents.
