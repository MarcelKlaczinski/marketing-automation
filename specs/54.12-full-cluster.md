# Spec 54.12: Full Cluster Generation (Hub + Spokes)

**Phase:** 54 / D — Phase D opener
**Estimated Effort:** ~3-4 days (~24 focused hours across 6 sessions)
**Dependencies:**
- Spec 54.7 (Cluster Creator — being extended)
- Spec 54.9 (Blog Generator — reused for each article)
- Spec 54.10 (Translation Pipeline — auto-triggers per DE article)
- Codebase Reference Pack

**Status:** Ready for implementation
**Recommended Model:** Sonnet 4.6 for implementation work. Pipeline itself uses **Sonnet 4.6 for Cluster-Plan-Generation**, plus existing Blog Pipeline models from 54.9 (Sonnet+Haiku).

---

## Goal

Extend the Cluster Creator (Spec 54.7) to produce a **full content cluster** instead of a single article. When Marcel approves a trend brief for full cluster generation:

1. **Cluster-Plan-LLM** expands the trend topic into Hub + 4-6 Spokes with strategic intent variation
2. **Backend API** lets Marcel review, edit, or remove proposed spokes
3. **Atomic approval** generates 5-7 DE articles (1 Hub + 4-6 Spokes) using existing Blog Pipeline
4. **Hub-first sequencing**: Hub generated to completion before Spokes start (enables voice-continuity)
5. **Spokes parallel**: all spokes enqueued simultaneously after Hub completion
6. **Translation Pipeline (54.10) auto-triggers** per DE article for EN siblings — runs parallel in background

After this spec lands, toolwiki can produce 10-14 fully-linked articles (Hub + Spokes × DE+EN) from a single trend brief approval. Per-cluster cost ~€4.20-4.80, wall-clock ~15 minutes.

## What this is NOT

- Not auto-cluster-generation (no "trigger when trend score > X" automation) — Phase E backlog
- Not manual Hub-Topic entry (separate UI form to start from scratch without a trend brief) — Phase E backlog
- Not full Edit-UI for spokes — Backend API in 54.12, full Stepper UI in 54.11
- Not introducing new article generation steps — reuses Blog Pipeline + Translation Pipeline unchanged
- Not bidirectional sync between Cluster Plan and individual Spoke Briefs after generation starts
- Not changing the cornerstone_spec architecture — only Hub gets cornerstone_spec, Spokes are regular articles

### Section B: Backend API for Cluster-Plan Editing

## Section A: Cluster-Plan LLM Generation

### A.1 Trigger flow

Marcel clicks "Full Cluster" button (Section E) on a trend brief in the Cluster Creator UI. The UI POSTs to:

```
POST /api/projects/:slug/clusters/full-plan
Body: { 
  triggerBriefId: string,  // existing trend_discovery brief
}
```

The endpoint:
1. Validates the brief exists, is `trend_discovery` source, and has `approval_status='pending'`
2. Calls Cluster-Plan-LLM to expand brief into Hub + 4-6 Spokes proposal
3. Creates `clusters` row with `generation_status='plan_proposed'`
4. Returns the cluster + proposed spokes for review (no articles generated yet)

### A.2 Cluster-Plan-LLM Call

```typescript
// packages/pipelines/src/cluster/full-plan/llm-call.ts

export interface ClusterPlanInput {
  triggerBrief: TopicBrief;
  project: Project;
  existingPillars: ContentPillar[];
  existingClusters: Cluster[];  // for similarity check / pillar suggestion
}

export interface ClusterPlanOutput {
  pillarId: string | "new";
  pillarSuggestedName: string | null;  // if pillarId === "new"
  cluster: {
    name: string;
    primaryKeyword: string;
    embedding: number[];
  };
  hub: {
    title: string;
    primaryKeyword: string;
    intentType: "overview" | "general";
    estimatedWordCount: number;
    h2Outline: string[];
  };
  spokes: ProposedSpoke[];  // 4-6 spokes
}

export interface ProposedSpoke {
  proposedTitle: string;
  primaryKeyword: string;
  intentType: "review" | "comparison" | "pricing" | "tutorial" | "use-cases" | "features";
  estimatedWordCount: number;
  rationale: string;  // why this spoke for this cluster
  position: number;  // ordering
}

export async function generateClusterPlan(input: ClusterPlanInput): Promise<ClusterPlanOutput> {
  const prompt = buildClusterPlanPrompt(input);
  
  const response = await anthropic.messages.create({
    model: "claude-sonnet-4-6-20251022",
    max_tokens: 3000,  // larger than single article — full plan
    messages: [{ role: "user", content: prompt }],
  });
  
  await logCost({
    projectId: input.project.id,
    service: "anthropic",
    operation: COST_OPS.CLUSTER_PLAN_GENERATION,
    costEur: 0.40,  // estimate; refined from real runs
  });
  
  return parseAndValidateClusterPlan(response);
}
```

### A.3 Prompt structure

Three sections in the prompt:

**1. Context: brand, audience, existing pillars/clusters**
- Project's `brand_identity` for voice
- `target_audience` for persona
- List of existing pillars with cluster counts (for pillar assignment decision)
- 10-20 existing cluster names (for novelty / overlap check)

**2. The trigger brief**
- topic_title, primary_keyword
- trend_metadata (signals, freshness, scoreBreakdown)
- The brief is the **seed**, not the final Hub

**3. Task: produce cluster plan**

```
TASK:
Expand this trend topic into a complete content cluster:

1. Decide whether this fits an existing pillar (return pillarId) or needs a new one
2. Define the cluster's name + primary keyword + 1024-dim embedding placeholder
3. Define the Hub article (cornerstone, intent='overview' or 'general')
4. Generate 4-6 Spokes covering different search intents

INTENT VARIATION FOR SPOKES:
Pick the intents that make most SEO sense for this topic. Available intents:
- 'review' — deep dive into one specific tool/approach
- 'comparison' — compares 2+ tools/approaches  
- 'pricing' — pricing analysis, cost comparison
- 'tutorial' — how-to guide, step-by-step
- 'use-cases' — practical applications
- 'features' — feature-focused deep dive

CHOOSE BASED ON TOPIC:
- For tool-heavy topics ("Coding Tools 2026"): comparison + pricing + review work well
- For concept topics ("Was ist RAG"): tutorial + use-cases + features work well
- For trend topics ("AI Agents Breaking News"): review + use-cases + comparison
- Don't force-fit unsuitable intents. Skip what doesn't make sense.

SPOKE COUNT:
- Minimum 4, maximum 6
- Narrow topics: 4 spokes
- Broad topics: 6 spokes
- Aim for distinct intent coverage, not overlap

ARTICLE TITLES:
- Hub: cornerstone-style ("Was ist X 2026: Der vollständige Leitfaden")
- Spokes: specific to intent ("X vs Y im Praxistest", "X Pricing Vergleich 2026")
- All in German (locale='de')

OUTPUT FORMAT: strict JSON, no preamble or commentary.
```

The full prompt template lives in `packages/pipelines/src/cluster/full-plan/prompts.ts`.

### A.4 Cluster row creation

After LLM returns plan, atomically create:

```typescript
await db.transaction(async (tx) => {
  // 1. Resolve or create pillar
  let pillarId = planOutput.pillarId;
  if (pillarId === "new") {
    const [newPillar] = await tx.insert(contentPillars).values({
      projectId: project.id,
      name: planOutput.pillarSuggestedName!,
      position: await getNextPillarPosition(tx, project.id),
    }).returning();
    pillarId = newPillar.id;
  }
  
  // 2. Create cluster
  const [cluster] = await tx.insert(clusters).values({
    projectId: project.id,
    pillarId,
    name: planOutput.cluster.name,
    pillar: existingPillar?.name ?? planOutput.pillarSuggestedName,  // denormalized
    primaryKeyword: planOutput.cluster.primaryKeyword,
    cornerstoneKeywords: [planOutput.hub.primaryKeyword],
    satelliteKeywords: [],  // populated as spokes get refined
    status: "proposed",
    generationStatus: "plan_proposed",  // NEW column, Section D
    position: 0,
    embedding: planOutput.cluster.embedding,
  }).returning();
  
  // 3. Mark trigger brief as 'routed' (consumed by cluster plan)
  await tx.update(topicBriefs)
    .set({
      approvalStatus: "routed",
      approvedAt: new Date(),
      routedClusterId: cluster.id,  // NEW: link back
    })
    .where(eq(topicBriefs.id, triggerBriefId));
  
  // 4. Store proposed spokes in clusters.proposed_spokes JSONB
  await tx.update(clusters)
    .set({
      proposedSpokes: planOutput.spokes,  // NEW column, Section D
      proposedHub: planOutput.hub,         // NEW column, Section D
    })
    .where(eq(clusters.id, cluster.id));
  
  return cluster;
});
```

**Important**: at this stage NO briefs for spokes exist yet, NO articles exist yet. Only the cluster row + proposed spokes JSONB. Marcel can edit/approve before any expensive generation runs.

## Section B: Backend API for Cluster-Plan Editing

### B.1 Endpoints

After Section A creates a cluster with `generation_status='plan_proposed'`:

```
GET    /api/projects/:slug/clusters/:id/plan
       → Returns full plan (cluster, hub, spokes[])

PATCH  /api/projects/:slug/clusters/:id/plan/spokes/:spokeIndex
       Body: { proposedTitle?, primaryKeyword?, intentType?, estimatedWordCount? }
       → Updates one spoke in clusters.proposed_spokes JSONB

DELETE /api/projects/:slug/clusters/:id/plan/spokes/:spokeIndex
       → Removes one spoke from clusters.proposed_spokes JSONB

PATCH  /api/projects/:slug/clusters/:id/plan/hub
       Body: { title?, primaryKeyword?, intentType?, estimatedWordCount? }
       → Updates hub in clusters.proposed_hub JSONB

POST   /api/projects/:slug/clusters/:id/plan/regenerate
       → Calls Cluster-Plan-LLM again with refined input (e.g., "make spokes more pricing-focused")
       Body: { refinementHint?: string }
       
POST   /api/projects/:slug/clusters/:id/plan/approve
       → Transitions generation_status: plan_proposed → plan_approved
       → Triggers Section C generation flow (Hub-first, spokes parallel)
```

### B.2 Validation rules

**Spoke editing constraints**:
- `spokeIndex` must be 0-based valid index into `clusters.proposed_spokes`
- `intentType` must be one of the valid intents from A.3
- `proposedTitle` min 10 chars, max 200
- `primaryKeyword` min 3 chars, max 100
- Cannot edit/delete if `generation_status != 'plan_proposed'` (status is locked once approved)

**Spoke count constraints**:
- After DELETE: cluster must have minimum 4 spokes left (else: 400 error "min 4 spokes required")
- After PATCH: cluster must have maximum 6 spokes (else: 400 error)

**Approval constraints**:
- `generation_status` must be `plan_proposed` (idempotent: approving twice rejects)
- All spokes must have valid required fields (no nulls in title/keyword/intent)
- Hub must be valid

### B.3 Audit trail

Each PATCH/DELETE writes to a new `cluster_plan_edits` JSONB array on the cluster row, with timestamp + diff. This is **append-only audit data**, not consulted by pipeline. For future debugging.

```typescript
proposedSpokes: jsonb("proposed_spokes").$type<ProposedSpoke[] | null>(),
proposedHub: jsonb("proposed_hub").$type<ProposedHub | null>(),
planEdits: jsonb("plan_edits").$type<PlanEdit[] | null>().default(sql`'[]'::jsonb`),

interface PlanEdit {
  timestamp: string;
  action: "patch_spoke" | "delete_spoke" | "patch_hub" | "regenerate";
  spokeIndex?: number;
  before?: ProposedSpoke | ProposedHub;
  after?: ProposedSpoke | ProposedHub;
  hint?: string;  // for regenerate
}
```

## Section C: Atomic Generation Trigger + Hub-First Sequencing

### C.1 Approval triggers generation

`POST /clusters/:id/plan/approve`:

```typescript
async function approveClusterPlan(clusterId: string): Promise<ApprovalResult> {
  await db.transaction(async (tx) => {
    // 1. Lock cluster status
    await tx.update(clusters)
      .set({ generationStatus: "plan_approved" })
      .where(and(
        eq(clusters.id, clusterId),
        eq(clusters.generationStatus, "plan_proposed"),  // idempotency
      ));
    
    // 2. Create briefs for Hub + each Spoke (Q4 decision: all as briefs)
    const cluster = await loadCluster(tx, clusterId);
    
    const hubBrief = await createHubBrief(tx, cluster);
    const spokeBriefs = await createSpokeBriefs(tx, cluster);
    
    // 3. Create cornerstone_spec only for Hub (Q7 decision)
    const hubCornerstoneSpec = await tx.insert(cornerstoneSpecs).values({
      projectId: cluster.projectId,
      clusterId: cluster.id,
      locale: "de",
      translationKey: generateTranslationKey(),
      cornerstoneKeyword: cluster.proposedHub.primaryKeyword,
      proposedTitle: cluster.proposedHub.title,
      proposedSlug: slugify(cluster.proposedHub.title),
      metaDescription: cluster.proposedHub.metaDescription ?? "",
      estimatedWordCount: cluster.proposedHub.estimatedWordCount,
      h2Outline: cluster.proposedHub.h2Outline,
      status: "approved",
    }).returning();
    
    // 4. Update cluster: pillar_article_id, generation_status
    await tx.update(clusters)
      .set({
        generationStatus: "running",
        status: "active",
      })
      .where(eq(clusters.id, clusterId));
    
    // 5. Enqueue Hub generation FIRST (no spokes yet)
    await enqueueBlogGeneration({
      briefId: hubBrief.id,
      projectId: cluster.projectId,
      clusterGenerationId: cluster.id,  // NEW: track cluster-level
      role: "hub",
    });
    
    // 6. Store spoke brief IDs for later enqueueing after Hub completion
    await tx.update(clusters)
      .set({
        pendingSpokeBriefIds: spokeBriefs.map(b => b.id),  // NEW column
      })
      .where(eq(clusters.id, clusterId));
    
    return { 
      clusterId,
      hubBriefId: hubBrief.id,
      spokeBriefIds: spokeBriefs.map(b => b.id),
      generationStatus: "running",
    };
  });
}
```

### C.2 Hub-first sequencing

When Hub Blog Pipeline completes, it triggers Spokes via finalize hook. This is the **critical sequencing pattern**:

```typescript
// In Blog Pipeline finalize step:
async function finalizeBlogPipeline(article: Article): Promise<void> {
  // ... existing logic (Translation auto-trigger) ...
  
  // NEW: Cluster-Generation continuation
  if (article.role === "hub" && article.clusterGenerationId) {
    await enqueueClusterSpokes({
      clusterId: article.clusterGenerationId,
      hubArticleId: article.id,
    });
  }
}
```

`enqueueClusterSpokes` fetches pendingSpokeBriefIds and enqueues all in parallel:

```typescript
async function enqueueClusterSpokes(input: { clusterId: string, hubArticleId: string }) {
  const cluster = await loadCluster(input.clusterId);
  const spokeBriefIds = cluster.pendingSpokeBriefIds ?? [];
  
  // Update pillar_article_id on cluster (Hub is now the pillar article)
  await db.update(clusters)
    .set({ pillarArticleId: input.hubArticleId })
    .where(eq(clusters.id, input.clusterId));
  
  // Enqueue all spokes in parallel — BullMQ handles concurrency
  await Promise.all(
    spokeBriefIds.map(briefId =>
      enqueueBlogGeneration({
        briefId,
        projectId: cluster.projectId,
        clusterGenerationId: input.clusterId,
        role: "spoke",
      })
    )
  );
  
  // Clear pending list
  await db.update(clusters)
    .set({ pendingSpokeBriefIds: [] })
    .where(eq(clusters.id, input.clusterId));
}
```

**Voice continuity bonus**: when spokes run their Blog Pipeline, the Voice-Reference Loader (Spec 54.10 D.1) queries `articles WHERE cluster_id = X AND locale = 'de' AND id != currentArticle.id`. The Hub article exists by this point and becomes the **primary voice reference** for spokes. Automatic cluster voice consistency.

### C.3 Translation cascade

Each generated DE article (Hub and Spokes) triggers its own Translation Pipeline per Spec 54.10. With 1 Hub + 5 Spokes = 6 DE articles, 6 EN translations run in parallel background.

**Sequencing**:
```
Wall-clock 0-5min:  Hub DE generates
Wall-clock 5-10min: Hub EN starts, Spokes DE start in parallel (5 spokes parallel)
Wall-clock 10-15min: Spokes EN translations complete

Total: ~15 min for 12 articles
```

### C.4 Completion detection

A cluster is "completed" when:
- All articles (DE + EN) for Hub + Spokes are in status `final_review` or further
- No pipeline_runs with status='failed' for this cluster

Detection logic runs after each article finalize:

```typescript
async function checkClusterCompletion(clusterId: string): Promise<void> {
  const cluster = await loadCluster(clusterId);
  if (cluster.generationStatus !== "running") return;  // already final
  
  const expectedArticleCount = 
    1 + (cluster.proposedSpokes?.length ?? 0);  // Hub + Spokes (DE only)
  
  const projectHasTranslation = cluster.project.targetLocales.includes("en-US");
  const expectedTotal = projectHasTranslation 
    ? expectedArticleCount * 2 
    : expectedArticleCount;
  
  const generatedArticles = await db.select().from(articles)
    .where(and(
      eq(articles.clusterId, clusterId),
      eq(articles.source, "generated"),
      sql`${articles.bodyMd} IS NOT NULL`,
    ));
  
  const failedRuns = await db.select().from(pipelineRuns)
    .where(and(
      sql`${pipelineRuns.input}->>'clusterGenerationId' = ${clusterId}`,
      eq(pipelineRuns.status, "failed"),
    ));
  
  if (generatedArticles.length === expectedTotal && failedRuns.length === 0) {
    await db.update(clusters)
      .set({ generationStatus: "completed", status: "active" })
      .where(eq(clusters.id, clusterId));
  } else if (failedRuns.length > 0 && generatedArticles.length + failedRuns.length === expectedTotal) {
    // All runs ended, some failed
    await db.update(clusters)
      .set({ generationStatus: "partial" })
      .where(eq(clusters.id, clusterId));
  }
  // Else: still running, status unchanged
}
```

## Section D: Cluster-Level Status Tracking

### D.1 generation_status state machine

```
manual              → existing clusters created via Spec 54.7 single-article flow
plan_proposed       → Section A created cluster + plan, awaiting Marcel review
plan_approved       → Section B approve hit, briefs created, Hub queued
running             → Hub generating OR spokes generating
completed           → All articles generated successfully
partial             → Some articles generated, some failed
failed              → Cluster-Plan-LLM failed or pre-generation error (no articles started)
```

### D.3 Partial-failure retry endpoint

Q10 decision: when cluster is `partial`, Marcel can retry failed spokes manually.

```
POST /api/projects/:slug/clusters/:id/retry-failed-spokes
```

Endpoint:
1. Verifies cluster.generation_status = 'partial'
2. Finds failed pipeline_runs for this cluster
3. Re-enqueues the briefs from those failed runs
4. Updates generationStatus back to 'running'

```typescript
async function retryFailedSpokes(clusterId: string): Promise<RetryResult> {
  const cluster = await loadCluster(clusterId);
  if (cluster.generationStatus !== "partial") {
    throw new Error(`Cannot retry: cluster status is ${cluster.generationStatus}`);
  }
  
  // Find failed pipeline runs for this cluster
  const failedRuns = await db.select().from(pipelineRuns)
    .where(and(
      sql`${pipelineRuns.input}->>'clusterGenerationId' = ${clusterId}`,
      eq(pipelineRuns.status, "failed"),
    ));
  
  // Extract brief IDs from failed runs
  const briefIdsToRetry = failedRuns
    .map(r => (r.input as any)?.briefId)
    .filter((id): id is string => !!id);
  
  // Re-enqueue
  await Promise.all(
    briefIdsToRetry.map(briefId =>
      enqueueBlogGeneration({
        briefId,
        projectId: cluster.projectId,
        clusterGenerationId: cluster.id,
        role: "spoke",  // retry presumes spoke (Hub failures are rare and need manual investigation)
      })
    )
  );
  
  // Reset cluster status
  await db.update(clusters)
    .set({ generationStatus: "running" })
    .where(eq(clusters.id, cluster.id));
  
  return { retriedBriefCount: briefIdsToRetry.length };
}
```

### F.2 Estimate computation

```typescript
async function computeCostEstimate(clusterId: string): Promise<CostEstimate> {
  const cluster = await loadCluster(clusterId);
  const project = await loadProject(cluster.projectId);
  
  const spokeCount = cluster.proposedSpokes?.length ?? 0;
  const articleCount = 1 + spokeCount;  // Hub + Spokes
  const hasTranslation = project.targetLocales?.includes("en-US") 
    && (project.translationAutoTrigger !== false);
  const totalArticleCount = hasTranslation ? articleCount * 2 : articleCount;
  
  const clusterPlanLLM = 0.40;  // historical cost from cost_logs
  const hubGeneration = 0.39;
  const spokesGeneration = 0.39 * spokeCount;
  const translations = hasTranslation ? 0.21 * articleCount : 0;
  
  const totalEstimateEur = 
    clusterPlanLLM + hubGeneration + spokesGeneration + translations;
  
  // Wall-clock: Hub (5min) + Spokes parallel (5min) + Translations parallel (5min)
  const wallClockMinEstimate = 10;  // best case
  const wallClockMaxEstimate = 20;  // worst case with retries
  
  return {
    articleCount,
    totalArticleCount,
    costBreakdown: {
      clusterPlanLLM,
      hubGeneration,
      spokesGeneration,
      translations,
    },
    totalEstimateEur,
    wallClockMinEstimate,
    wallClockMaxEstimate,
  };
}
```

## Open Questions / Decisions Made

**Decision 1: Spoke count is LLM-decided 4-6 (Q1b).**
Topic-aware decision. Narrow topics get 4, broad get 6. Cap prevents cost explosion, floor ensures cluster identity.

**Decision 2: Intent variation is LLM-picked (Q2b).**
SEO intent strategy is topic-specific. Force-fitting intents produces weak content. LLM chooses what makes sense per topic.

**Decision 3: Trigger from existing trend brief (Q3a).**
Manual hub topic entry deferred to Phase E. Trend briefs are the established entry point from 54.5/54.6/54.7.

**Decision 4: All as briefs — 1 Hub + N Spokes (Q4a).**
Each generated article has a brief. Consistent with 54.7 + 54.9. Single audit trail pattern.

**Decision 5: Spoke editing via Backend API in 54.12, full UI in 54.11 (Q5 Option A).**
Editing is essential capability — Backend exposes it now. UI Stepper with drag-edit features comes in 54.11. Marcel uses Postman/curl in interim.

**Decision 6: Cost preview before approval (Q6b).**
Marcel sees expected cost + time before committing. Avoids surprise expenses.

**Decision 7: Only Hub gets cornerstone_spec (Q7a).**
Cornerstone is "the One" per cluster. Spokes are support content. Future promotion possible.

**Decision 8: Translation auto-trigger per article, no special cluster-level handling (Q8a).**
Reuses 54.10 pattern. Parallel execution is faster than batch-after-completion.

**Decision 9: Cluster-level generation_status column (Q9b).**
Aggregates article-level state into cluster-level summary. UI can show "Cluster X: running/partial/completed" without manual aggregation.

**Decision 10: Partial status + manual retry (Q10b).**
Failed spokes don't trigger rollback. Marcel retries via endpoint. Failed Hub is rare and indicates deeper issue (manual investigation).

**Decision 11: Cluster-Plan-LLM uses Sonnet 4.6.**
Cluster planning is strategy + structure work. Sonnet validated in 54.9. Opus is overkill for proposal-level work.

**Decision 12: Read-only plan view in 54.12 UI, edit only via API.**
Trigger button is 1-hour job. Edit UI (Stepper, inline edits) is 54.11 scope. Marcel can use API in interim if needed.

**Decision 13: Voice continuity emerges from Hub-first sequencing.**
No explicit voice cache or special wiring needed. Hub completes → exists in DB → becomes voice reference for spokes via existing 54.10 D.1 loader. Architectural elegance.

**Decision 14: cluster_generation_id distinct from cluster_id on articles.**
cluster_id = membership (set by SyncClustersFromFrontmatterStep). cluster_generation_id = which generation run produced this article. Useful for partial-retry logic.

**Decision 15: plan_edits is append-only audit data.**
Not consulted by pipeline. Future debugging tool. Cheap to maintain (JSONB array, no FK).

## Discovered During Implementation

**Session 1 (DB):**
- `Cluster` and `NewCluster` inferred-type aliases were missing from `packages/db/src/schema/identity.ts` — added them. Rule: every table must export `$inferSelect` / `$inferInsert` aliases (see DB CLAUDE.md).
- `ContentPillar` is NOT a named exported type from `@marketing-auto/db`. The correct type is `typeof contentPillars.$inferSelect`. For function parameters that only need a subset, use an inline object shape `{ id: string; name: string }` — do not attempt to import `ContentPillar`.

**Session 2 (LLM):**
- `ClusterPlanOutputSchema` needed a `.refine()` for distinct `intentType` across spokes — Zod does not validate cross-item constraints automatically. Added `.refine((spokes) => new Set(spokes.map(s => s.intentType)).size === spokes.length, ...)`.
- `h2Outline` bounds in the schema were initially coded as `min(3).max(12)` but the prompt specifies 4-10. Fixed to `min(4).max(10)`. Spec + schema bounds must always match.
- The spec's `ClusterPlanInput` included `embedding: number[]` in the cluster output — removed, since cluster embeddings are computed by Voyage AI after plan creation, not by the planning LLM.

**Session 3 (API endpoints):**
- Hub article is pre-created inside the approve transaction (not by `enqueueBlogGeneration`) so `triggerWithPreRunId` can use `articleId` as the idempotency uniqueKey. Spoke articles are NOT pre-created — they're created lazily by `enqueueBlogGeneration` when Hub completes (Session 4).
- `checkTriggerAllowed` (not `triggerWithPreRunId`) used for the `POST /clusters/full-plan` endpoint — the plan LLM call is a one-shot operation, not a pipeline run, so there's no `pipeline_runs` row to pre-insert. The cost + pause guards still fire.
- `clusters` table has no `updatedAt` column — all cluster `.update().set()` calls must omit it. `topicBriefs` and `articles` both have `updatedAt`.
- Raw `ANY(ARRAY[...])` SQL is a SQL injection risk. Use `inArray()` from `@marketing-auto/db` for any `IN` clause that spans a list of IDs (even internal UUIDs).

**Session 4 (Hub completion hook):**
- Spoke articles have `clusterGenerationId` + `role="spoke"` set AFTER `enqueueBlogGeneration` returns their `articleId` — `createBlogArticleFromBrief` inside the enqueue function does not accept those fields. The additional `db.update(articles)` call is safe because the worker hasn't read the article yet.
- `BlogPipeline.afterComplete` loads article fields (`locale`, `role`, `clusterGenerationId`) in a single query shared by all three hook paths (translation, spoke-enqueue, completion-check), wrapped in one try-catch. If this query fails, all three hooks skip gracefully.

## Deviations

**Section A.2 — LLM call signature:** The spec shows `anthropic.messages.create()` (direct SDK). Implementation uses `anthropic.messages()` from `@marketing-auto/adapter-anthropic` per the CLAUDE.md adapter rule. The adapter handles cost tracking, caching headers, and jsonMode parsing.

**Section A.2 — embedding field removed from ClusterPlanOutput:** The spec included `embedding: number[]` in the cluster output. Embeddings are computed by Voyage AI (not Claude), so the field was removed from `ClusterPlanOutputSchema`. The `clusters.embedding` column will be populated separately after cluster row creation (same pattern as the cluster-creator flow in 54.7).

**Section C.1 — Hub article pre-created at approve time:** The spec pseudocode shows `createHubBrief → enqueueBlogGeneration → article created`. Implementation pre-creates the hub article in the approval transaction and sets `brief.routedArticleId` before enqueueing, so `triggerWithPreRunId` can use `articleId` as the uniqueKey. The `createBlogArticleFromBrief` call inside `enqueueBlogGeneration` finds `routedArticleId` already set and only updates status to `"generating"`.

**Section C.1 — Spoke articles NOT pre-created at approve time:** The spec implies all spoke articles are created atomically at approval. Implementation creates spoke briefs only, storing them in `pendingSpokeBriefIds`. Spoke articles are created when `enqueueClusterSpokes` calls `enqueueBlogGeneration` per brief (lazy creation). This avoids 4-6 additional `articles` rows existing with no pipeline run during the Hub generation window.

**Section E.1 — Full-cluster button placed next to Cluster Creator button (not replacing it):** The spec showed an example `TrendBriefActions` sub-component. Implementation adds the button directly in `TrendBriefDetail.vue`'s `create_new` action template alongside the existing "Einzelartikel erstellen" button — no new sub-component needed. Both buttons coexist; Marcel can choose the single-article flow (54.7) or the full-cluster flow (54.12).

**Section E.2 — Plan review page navigates back to trends (not cluster list):** On approve or back-button, the page navigates to `project-trends` (the brief's origin). The spec showed no explicit back-destination — trends is the natural return path since the brief was triggered from there.

**Section E.3 — i18n namespace is `clusters.fullCluster` (not `clusterCreator`/`clusterPlan`):** The spec proposed `clusterCreator.*` and `clusterPlan.*` namespaces but these overlap with the existing `clusters.create.*` namespace. Consolidated under `clusters.fullCluster.*` to keep all cluster i18n in one file.
