# Spec 57.4 — Hashtag Generation Refactor

**Theme:** 57 (Social Media + Remotion Refinement)
**Status:** Draft
**Estimated effort:** 2-3 days
**Prerequisite discovery:** `specs/_drafts/57-0-hashtag-research-decisions.md`

---

## Goal

Replace the broken `ResearchHashtagsStep` (cheap Haiku call with poor prompt, producing low-quality hashtags) by merging hashtag generation into `GenerateCaptionStep` using shared logic between the social-image pipeline and the existing discovery worker. Eliminate code duplication, fix production hashtag quality issues, and improve semantic coherence between caption and hashtags.

## Non-Goals

- DataForSEO integration for hashtags (rejected per Spec 57.0 discovery — search volume doesn't model social community dynamics)
- Per-platform hashtag strategies (Instagram vs TikTok vs LinkedIn customization) — deferred to Phase E
- Hashtag performance tracking / engagement metrics — deferred to Phase E
- Hashtag library / curated catalog — rejected per discovery (high maintenance, low advantage)
- DiscoveryWorker hashtag logic changes (the better-than-pipeline logic in hookPrompt.ts stays as-is)

---

## Background

Per Spec 57.0 discovery output, three quality issues exist in production:

1. **Misleading step name**: `ResearchHashtagsStep` doesn't research anything — it calls Haiku 4.5 with a thin prompt (article title + tool names only, no brand voice, no content-type awareness).

2. **Output quality is objectively bad**: Production samples show 20 tags per post (Instagram optimal is 5-15), year-anchored tags (`#Programming2024`, `#KI2026`) that age out, hyphenated tags (`#KI-Tools`) that are unclickable on Instagram, generic padding (`#WebDevelopment`), and same hashtag mix regardless of content type.

3. **Code duplication with quality gap**: `packages/core/src/social-hooks/hookPrompt.ts::buildCaptionSection()` already implements significantly better hashtag logic (7 bilingual tags, content-type aware, anchor tags, anti-spam rules) but is only used by the discovery worker, never ported to the pipeline.

Decoupled generation produces incoherent posts: caption LLM (Sonnet 4.6) and hashtags LLM (Haiku 4.5) run as separate steps with no shared context. The caption can mention tools or themes that the hashtags miss entirely.

**Part A: Shared Hashtag Logic** — Extract reusable hashtag-instruction builder into `@marketing-auto/core`
**Part B: Merge Hashtags into GenerateCaptionStep** — Single LLM call returns caption + hashtags as JSON
**Part C: Remove ResearchHashtagsStep** — Clean removal, schema updates, cost ops housekeeping

## Part A: Shared Hashtag Logic

### A.1 Why Shared

Two systems need hashtag generation:
- **Pipeline**: `article:social-image` pipeline rendering carousels for articles
- **Discovery worker**: `discoveryWorker.ts` generates social hooks from trend signals before article creation

Both should produce semantically consistent hashtag styles (same anchor tags, same anti-spam rules, same count). Duplicating logic guarantees drift over time.

### A.2 Extraction

**Location**: `packages/core/src/social-hashtags/buildHashtagInstructions.ts` (new file)

Pure function, no dependencies on pipeline or worker state:

```typescript
export type HashtagContext = {
  locale: string;              // "de-DE" | "en-US" — primary locale of the post
  contentType: ContentType;    // "comparison" | "review" | "general" — derived from article.intentType
  toolNames: string[];         // ["Cursor", "Windsurf", "Codeium"]
  toolCategory?: string;       // optional category hint, e.g. "code-editors"
};

export type ContentType = "comparison" | "review" | "general";

/**
 * Builds the HASHTAGS section of an LLM prompt — to be appended to caption-generation prompts.
 * Returns a string that instructs the LLM how to produce a hashtag array as part of its JSON output.
 *
 * Single source of truth for hashtag rules across pipeline + discovery worker.
 */
export function buildHashtagInstructions(ctx: HashtagContext): string {
  const isGermanPrimary = ctx.locale.startsWith("de");
  const anchorDE = ctx.contentType === "comparison"
    ? ["#KITools", "#KIVergleich"]
    : ["#KITools", "#KIFürBusiness"];
  const anchorEN = ctx.contentType === "comparison"
    ? ["#AITools", "#AIComparison"]
    : ["#AITools", "#AIForBusiness"];

  return `
HASHTAGS (exactly 7 tags, bilingual mix for dual search intent on Instagram):
- German anchor tags: ${anchorDE.join(", ")}
- English anchor tags: ${anchorEN.join(", ")}
- Plus 1 niche German tag matching tool category (e.g. ${ctx.toolCategory ? `#${pascalCase(ctx.toolCategory)}` : "#SoftwareTest, #Produktivität"})
- Plus 1 niche English tag matching tool category
- Plus 1 tool-name tag if a tool name reads naturally as a hashtag: ${ctx.toolNames.slice(0, 3).join(", ")}
- Total: EXACTLY 7 tags

RULES:
- NO hyphens in hashtags (Instagram does not parse #KI-Tools as a single tag — write #KITools)
- NO year tags (#KI2026, #2026Tech, #AI2026 — these age out within months)
- NO self-promotional tags (#Toolwiki, #ToolwikiAI, #ToolwikiBlog)
- NO redundant variants of the same concept (avoid #DeveloperTools AND #DevTools AND #CodingTools in the same post)
- Mix German and English freely — German users searching in either language should find the post`;
}

// Helper: snake-case or kebab → PascalCase for hashtag form
function pascalCase(input: string): string {
  return input.split(/[-_\s]+/).map(w => w.charAt(0).toUpperCase() + w.slice(1)).join("");
}
```

Add to `packages/core/src/index.ts`:


### A.4 Discovery Worker Migration (Optional, Same-Spec)

The existing `hookPrompt.ts::buildCaptionSection()` currently inlines its hashtag logic. **Migrating it to call `buildHashtagInstructions()` is in scope** of this spec because:

- It validates the shared utility against the working production system
- Discovery worker and pipeline output will be semantically identical going forward
- Future hashtag tuning only needs to touch one file

**Migration**:
```typescript
// packages/core/src/social-hooks/hookPrompt.ts
// BEFORE: inline HASHTAGS section with hardcoded German+English mix

// AFTER:
import { buildHashtagInstructions } from "../social-hashtags/buildHashtagInstructions";

export function buildCaptionSection(input: BuildCaptionInput): string {

    locale: input.locale,
```

## Part B: Merge Hashtags into GenerateCaptionStep

### B.1 Step Behavior Change

`GenerateCaptionStep` returns `{ caption: string; hashtags: string[] }` instead of `{ caption: string }`.

Single Sonnet 4.6 call replaces previous two calls (Sonnet caption + Haiku hashtags). Cost approximately equal to the previous Sonnet-only caption cost — `maxTokens` increases by ~150 to accommodate hashtag JSON output, but no separate API call overhead.

### B.2 Updated Prompt

```typescript
// packages/pipelines/src/article/social-image/steps.ts

import { buildHashtagInstructions } from "@marketing-auto/core";

async execute(input, ctx) {
  const brandVoice = input.brandTokens?.voice;
  const signaturePhrases = brandVoice?.signaturePhrases?.join(", ") ?? "redaktionell verifiziert, ehrlich";
  const addressForm = brandVoice?.addressForm ?? "du";
  const contentType = deriveContentType(input.intentType);  // see B.4
  const toolNames = input.resolvedTools.map(t => t.name);

  const hashtagSection = buildHashtagInstructions({
    locale: input.locale,
    contentType,
    toolNames,
    toolCategory: input.cluster?.category,
  });

  const captionLocale = input.locale.startsWith("de") ? "GERMAN" : "ENGLISH";

  const prompt = `Write an Instagram post in ${captionLocale} for a carousel about: "${input.articleTitle}"

The post shows ${input.resolvedTools.length} AI tools in a visual list-carousel format.
Brand voice: ${signaturePhrases}. Use "${addressForm}" form. Max 300 characters in caption. Use 1-2 fitting emojis.
End caption with: Link in Bio → ${input.articleUrl}

${hashtagSection}

Return JSON object:
{
  "caption": "<the caption text>",
  "hashtags": ["#Tag1", "#Tag2", ...]  // exactly 7 entries
}`;

  const response = await anthropic.messages({
    operation: COST_OPS.SOCIAL_IMAGE_CAPTION,  // single op now
    model: "claude-sonnet-4-6",
    systemSuffix: "Return only valid JSON matching the requested shape.",
    userMessage: prompt,
    maxTokens: 600,  // was 400 — accommodate hashtags
    jsonMode: true,
  });

  const parsed = parseJsonResponse(response.raw);  // reuse existing pattern
  const validated = generateCaptionOutputSchema.parse(parsed);

  return { ...input, caption: validated.caption, hashtags: validated.hashtags };
}
```

### B.3 Output Schema (Zod)

```typescript
// packages/pipelines/src/article/social-image/schemas.ts (new or existing)

export const generateCaptionOutputSchema = z.object({
  caption: z.string().min(20).max(2200),  // Instagram caption limit
  hashtags: z.array(z.string().regex(/^#\w+$/, "Hashtag must start with # and contain only word characters"))
    .min(5)
    .max(10),
});

export type GenerateCaptionOutput = z.infer<typeof generateCaptionOutputSchema>;
```

**Hashtag validation**:
- Min 5 / max 10 instead of strict 7 — gives LLM room to deviate by 1-2 without failing the pipeline
- Regex `/^#\w+$/` blocks hyphens (forces the LLM to follow the no-hyphens rule)
- If validation fails, retry once with stricter prompt; if retry fails, use fallback (see B.5)

### B.4 Content Type Derivation

Investigator's Risk #3: `input.intentType` may not flow through `LoadArticleStep` → `GenerateCaptionStep`.

**Audit**: Verify `pipeline.ts` step input/output types pass `intentType` (or equivalent) from `LoadArticleStep` through to `GenerateCaptionStep`. If missing, add it.

**Derivation function** (in shared utility or inline):
```typescript
// packages/core/src/social-hashtags/buildHashtagInstructions.ts (alongside main function)

export function deriveContentType(intentType: string | null | undefined): ContentType {
  if (!intentType) return "general";
  const lower = intentType.toLowerCase();
  if (lower.includes("compar") || lower.includes("vergleich") || lower.includes("vs")) return "comparison";
  if (lower.includes("review") || lower.includes("bewertung") || lower.includes("test")) return "review";
  return "general";
}
```

Tests for this function — small, fast, valuable for documenting the mapping.

### B.5 Fallback Strategy

If JSON parsing or schema validation fails twice, the pipeline currently fails. With merged step, both caption + hashtags are at risk.

**Fallback**: Return safe defaults but mark `social_posts.warnings = ['hashtag_generation_fallback']`:

```typescript
// On second parse failure:
return {
  ...input,
  caption: `${input.articleTitle} → ${input.articleUrl}`,  // minimal viable caption
  hashtags: ["#KITools", "#AITools", "#Produktivität", "#DigitalTools", "#KünstlicheIntelligenz", "#TechReview", "#SoftwareTest"],
  warnings: [...(input.warnings ?? []), "hashtag_generation_fallback"],
};
```

UI surfaces `warnings` so Marcel can see which posts had degraded generation.

## Cross-cutting Concerns

### CC.1 Backward Compatibility

Existing `social_posts.content.hashtags` rows with 20 tags remain valid JSONB. The change only affects newly generated posts. No migration needed.

Old posts with `#KI-Tools` (hyphenated, year-anchored) stay visible in UI history but are not re-generated unless the user manually re-renders.

### CC.2 Discovery Worker Output Parity

After Part A.4 migration, discovery worker hooks and pipeline social posts will use identical hashtag rules. This is intentional and desirable.

**Side-effect**: If Marcel has been visually distinguishing pipeline-generated vs discovery-generated posts by hashtag style, that signal is gone. Per Spec 57.0 discovery, the existing hookPrompt logic is the *target* quality; converging on it is the goal.

### CC.3 i18n / Localization

No new user-facing strings in this spec. Hashtag content is data, not UI labels. UI shows `social_posts.content.hashtags` array as-is.

Per Spec 57.1 (locale-multi-render), the pipeline already passes `locale` per render. `buildHashtagInstructions()` reads `locale` and adapts anchor tags. **Cross-spec dependency**: Spec 57.1 must land before this can leverage multi-locale hashtag generation. **Order: 57.1 → 57.4** (current Theme 57 sequencing).

### CC.4 Tests

**Unit (fast, valuable):**
- `buildHashtagInstructions.test.ts` — assert correct anchor tags for each locale × contentType combination
- `deriveContentType.test.ts` — assert mapping of intentType strings to ContentType
- `generateCaptionOutputSchema.test.ts` — assert schema rejects hyphenated tags, accepts valid tags

**Integration (slower, also valuable):**
- `social-image.pipeline.test.ts`:
  - Generate full pipeline with mocked LLM returning valid `{caption, hashtags}` JSON → assert step count = 7, social_posts row has both fields

**Visual / manual smoke (post-deploy):**
- Generate 3 carousels for different content types (comparison / review / general) — assert hashtags differ appropriately
- Generate same article in DE + EN — assert hashtags adapt to locale (anchor tag distribution changes)

### CC.5 Monitoring

After deploy, sample 10 new posts and review hashtag quality manually:
- Count: 7 ± 1
- No hyphens
- No year tags
- Content-type appropriate
- Tool names present where natural

If quality is below threshold, tune `buildHashtagInstructions()` system suffix. No DB migration needed — prompt-level changes propagate to all future renders.

## Risks & Mitigations

**Risk 1: Sonnet 4.6 doesn't reliably return JSON when prompt is longer**
- *Mitigation*: Use `jsonMode: true` + `systemSuffix: "Return only valid JSON matching the requested shape."` + retry-once-then-fallback. Existing pattern from current `ResearchHashtagsStep` (regex match) can also be used as a parsing safety net.

**Risk 2: 7-tag count drifts (LLM returns 6 or 8)**
- *Mitigation*: Zod schema allows 5-10 (not strict 7) — accommodates natural LLM variance. If count consistently drifts down to ≤4, tune prompt.

**Risk 3: hookPrompt.ts migration changes discovery worker output unexpectedly**
- *Mitigation*: Visual regression check pre/post migration (Session 3 step 6). Output should match semantically; if it doesn't, revert that specific migration step and keep duplication temporarily.

**Risk 4: intentType not in step chain — silent fallback to "general"**
- *Mitigation*: Audit in Session 2 step 1 confirms intentType flow. If missing, add it. `deriveContentType("general")` is the safe default; pipeline does not break.

**Risk 5: Existing pipeline tests break due to step count change**
- *Mitigation*: Test updates are part of Session 3 step 4. Tests likely have soft assertions on step count; updates are mechanical.

## Open Questions

1. **Discovery worker migration: required or optional?**
   Current spec includes it in scope (Part A.4). Alternative: leave discovery worker untouched, duplicate logic temporarily, migrate in separate cleanup spec. **Recommendation: include in this spec** — the test of the shared utility is using it in both places. Confirm.

2. **Fallback hashtags — what should they be?**
   Current spec uses 7 generic German+English AI tags. Alternative: derive from article title via simple keyword extraction. **Recommendation: generic fallback** — fallback is an error path, simplicity > sophistication. Confirm.

3. **Should `warnings` field be exposed in UI?**
   The fallback path sets `warnings: ['hashtag_generation_fallback']` on `social_posts`. Two options: (a) silent — only visible in DB / logs, (b) visible in UI as a badge on the render history item. **Recommendation: silent first** — if Marcel sees too many fallbacks, expose in UI. Confirm.

4. **Year-tag detection — schema-enforced or prompt-only?**
   Schema regex blocks hyphens but allows years (e.g. `#KI2026` matches `/^#\w+$/`). Options: (a) keep prompt-only restriction, (b) add schema regex like `/^#(?!\d{4}|\w*\d{4}\w*)\w+$/` to enforce. **Recommendation: prompt-only first** — if year tags persist after deploy, escalate to schema. Confirm.

5. **Bilingual mix on monolingual locale renders**
   Per Spec 57.1, locales are explicit per render. If user generates a DE-only post, should the hashtag mix still include English anchor tags? Today's hookPrompt does (DE + EN bilingual always). **Recommendation: always bilingual** — Instagram users searching in either language should find DE posts. Confirm.
