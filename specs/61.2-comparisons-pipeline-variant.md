# Spec 61.2 — `comparisons` Article Generator Variant

**Date:** 2026-05-19
**Theme:** 61 — Article Generator Variants
**Prerequisite:** 61.1 done (`collectionType` enum + `COLLECTION_FOLDER` map in place)
**Estimated effort:** ~1.5 days

---

## TL;DR

Add a full `comparisons` article generation variant to the pipeline. A comparison
article requires structured frontmatter that blog articles don't have (`toolSlugs`,
`winner`, `verdict`, `testMethodology`, `useCaseVerdicts`), a specific body
structure (TL;DR → feature matrix → use-case verdicts → tool portraits → Methodik),
and minimum 2,000 words + 5 FAQs. The pipeline branches at the `collectionType`
level — same steps, collection-specific prompts and frontmatter schemas.

## Session 1 — DB: `articles.collection` column

### 1.1 Gap from 61.1

61.1 deliberately left `articles.collection` (the Astro routing text column)
always set to `"blog"`. For comparisons articles to render at `/vergleiche/{slug}/`,
the column must be set to `"comparisons"`.

// In PersistArticleStep.execute():

> **Note:** `COLLECTION_ASTRO_NAME` and `COLLECTION_FOLDER` (from 61.1 in

> - `COLLECTION_FOLDER` → filesystem path for MDX output
> - `COLLECTION_ASTRO_NAME` → value stored in `articles.collection` DB column
    > They should be identical in values — but kept separate per their concern.

the write value changes.

## Session 2 — Frontmatter Schema: `comparisons`

### 2.1 Required fields for LLM to generate

Based on the Astro collection schema (from discovery Q2 + Q4):

```typescript
// packages/pipelines/src/article/frontmatter/comparison.frontmatter.ts

export interface ComparisonFrontmatter {
  // Required
  title:           string;          // max 80 chars
  description:     string;          // max 200 chars — shown in card/meta

  // Comparison-specific required
  toolSlugs:       string[];        // min 2, max 4 — kebab-case slugs
  winner:          ComparisonWinner;
  verdict:         string;          // multi-sentence decision summary, max 400 chars

  // Strongly recommended (E-E-A-T)
  testMethodology: string;          // 1–3 sentences, max 200 chars
  useCaseVerdicts: UseCaseVerdict[]; // required when winner = "depends"
  comparedAt:      string;          // YYYY-MM-DD

  // SEO
  seoTitle:        string;          // max 70 chars
  seoDescription:  string;          // max 180 chars

  // Standard
  locale:          'de' | 'en';
  translationKey:  string;
  updatedAt:       string;          // YYYY-MM-DD
  author:          string;          // default 'toolwiki – Redaktion'
  faq:             FaqEntry[];      // min 5, max 15

  // Optional cluster
  clusterKey?:     string;
  clusterRole?:    'hub' | 'spoke';
  parentSlug?:     string;

  // Auto-injected by schema (do NOT generate):
  // adsenseSlots: ['mid']
  // hasAffiliateLinks: true
  // noindex: false
}

export type ComparisonWinner =
  | 'tool-a' | 'tool-b' | 'tool-c' | 'tool-d'
  | 'depends' | 'tie';

export interface UseCaseVerdict {
  useCase: string;   // max 40 chars
  winner:  string;   // tool slug or "depends"
  reason:  string;   // max 120 chars
}

export interface FaqEntry {
  question: string;  // max 100 chars
  answer:   string;  // max 300 chars
}
```

### 2.2 `winner` semantics

The `winner` enum uses positional labels (`tool-a`, `tool-b`, etc.) not tool slugs.
Position maps to `toolSlugs` order:
- `tool-a` = `toolSlugs[0]`
- `tool-b` = `toolSlugs[1]`
- etc.

When `winner: "depends"`, `useCaseVerdicts` must be present (Astro schema
enforces this — validate in pipeline before persisting).

### 2.3 ContentBounds for LLM

```typescript
export const comparisonFrontmatterBounds = {
  title:           { maxChars: 80 },
  description:     { maxChars: 200 },
  toolSlugs:       { countMin: 2, countMax: 4, each: { maxChars: 40 } },
  verdict:         { maxChars: 400 },
  testMethodology: { maxChars: 200 },
  useCaseVerdicts: {
    countMin: 3,
    countMax: 9,
    each: {
      useCase: { maxChars: 40 },
      reason:  { maxChars: 120 },
    },
  },
  seoTitle:        { maxChars: 70 },
  seoDescription:  { maxChars: 180 },
  faq: {
    countMin: 5,
    countMax: 15,
    each: {
      question: { maxChars: 100 },
      answer:   { maxChars: 300 },
    },
  },
};
```

### 3.3 Prompt injection in pipeline

The comparison body prompt requires the frontmatter to be available before the
body is generated. This means:

**Step order for comparisons:**
1. `GenerateFrontmatterStep` — generates comparison frontmatter JSON
2. `GenerateBodyStep` — receives frontmatter as context, generates body

This is already the correct order in `BlogPipeline`. No reordering needed.
The `GenerateBodyStep` receives the frontmatter output from the previous step
via the pipeline's step-chaining mechanism.

## Session 4 — Pipeline Branching

### 4.1 Where branching happens

Two steps need collection-specific prompts:
- `GenerateFrontmatterStep` → different prompt + schema per collection
- `GenerateBodyStep` / `GenerateDraftStep` → different structure per collection

### 4.2 Implementation pattern

**Option A — prompt selector function (recommended):**

```typescript
// packages/pipelines/src/article/prompts/index.ts

export function selectFrontmatterPrompt(
  collectionType: ArticleCollectionType,
): FrontmatterPromptFn {
  switch (collectionType) {
    case 'comparison': return buildComparisonFrontmatterPrompt;
    case 'ki-wissen':  return buildKiWissenFrontmatterPrompt;  // 61.3
    default:           return buildBlogFrontmatterPrompt;
  }
}

export function selectBodyPrompt(
  collectionType: ArticleCollectionType,
): BodyPromptFn {
  switch (collectionType) {
    case 'comparison': return buildComparisonBodyPrompt;
    case 'ki-wissen':  return buildKiWissenBodyPrompt;         // 61.3
    default:           return buildBlogBodyPrompt;
  }
}
```

**In `GenerateFrontmatterStep.execute()`:**
```typescript
const promptFn = selectFrontmatterPrompt(ctx.collectionType ?? 'blog');
const prompt = promptFn(input, ctx);
```

This avoids subclassing steps — the same step instances handle all collection
types by switching the prompt function.

### 4.3 Frontmatter validation gate

After `GenerateFrontmatterStep`, add a validation check specific to comparisons:

```typescript
// In GenerateFrontmatterStep or a new ValidateFrontmatterStep:

if (collectionType === 'comparison') {
  const fm = parsedFrontmatter as ComparisonFrontmatter;

  // winner = "depends" requires useCaseVerdicts
  if (fm.winner === 'depends' && (!fm.useCaseVerdicts || fm.useCaseVerdicts.length === 0)) {
    throw new PipelineValidationError(
      'comparison: winner="depends" requires at least one useCaseVerdict'
    );
  }

  // toolSlugs 2–4
  if (fm.toolSlugs.length < 2 || fm.toolSlugs.length > 4) {
    throw new PipelineValidationError(
      `comparison: toolSlugs must have 2–4 entries, got ${fm.toolSlugs.length}`
    );
  }
}
```

## Session 5 — MDX Assembly

### 5.1 Frontmatter serializer

The existing frontmatter serializer writes blog-specific fields. Extend it to
handle comparison-specific fields:

```typescript
// packages/pipelines/src/article/steps/assemble-mdx.step.ts

function serializeFrontmatter(
  fm: BlogFrontmatter | ComparisonFrontmatter,
  collectionType: ArticleCollectionType,
): string {
  const base = serializeBaseFrontmatter(fm);

  if (collectionType === 'comparison') {
    const cf = fm as ComparisonFrontmatter;
    return [
      base,
      `toolSlugs: [${cf.toolSlugs.map(s => `"${s}"`).join(', ')}]`,
      `winner: "${cf.winner}"`,
      `verdict: "${cf.verdict}"`,
      `comparedAt: "${cf.comparedAt}"`,
      cf.testMethodology
        ? `testMethodology: "${cf.testMethodology}"`
        : null,
      cf.useCaseVerdicts?.length
        ? serializeUseCaseVerdicts(cf.useCaseVerdicts)
        : null,
    ].filter(Boolean).join('\n');
  }

  return base;
}
```

## Section — Patterns Established by 61.2

**(109) Collection-specific prompts are selected via `selectFrontmatterPrompt(collectionType)`
and `selectBodyPrompt(collectionType)` — never branch inside the step itself. The
switch lives in `packages/pipelines/src/article/prompts/index.ts`. Adding a new
collection type = add one case per switch, nothing else changes in the step.**

**(110) Comparison `winner` uses positional labels (`tool-a` … `tool-d`), not tool
slugs. The position maps to `toolSlugs[]` index. Always document this mapping in
the LLM prompt — the LLM will use slug names if not told otherwise.**

**(111) `useCaseVerdicts` is mandatory when `winner = "depends"`. Validate this
in the pipeline after frontmatter generation — never trust the LLM to enforce it
automatically. Throw `PipelineValidationError` not a generic error.**

## Section — Deviations from Original Spec

1. **No separate `GenerateFrontmatterStep` / `GenerateBodyStep`** — the spec
   proposed splitting frontmatter and body into two LLM calls (with the body
   reading the frontmatter as context). In practice the blog pipeline already
   uses a single-shot `DraftStep` that emits body + a `FRONTMATTER_EXTRAS`
   HTML-comment block; we extended that pattern instead of adding a new step.
   Same number of LLM calls, no new schema, no pipeline reordering. Trade-off:
   the body cannot literally reference the frontmatter, but it has all the same
   context (tool list, outline, voice) via the same user message.

2. **No `assemble-mdx.step.ts` change** (Session 5) — MDX assembly lives in
   `packages/adapters/astro-sync/src/steps/render-mdx.ts`, not in
   `packages/pipelines/src/article/steps/`. That step already merges
   `articles.frontmatterExtras` first when building YAML — so toolSlugs,
   winner, verdict etc. flow through transparently once the DraftStep emits
   them. No serializer code change required.

3. **`enqueueBlogGenerationPipeline` extended in place** — the spec did not
   call out that the thin enqueue wrapper drops fields not in its parameter
   type. We updated the wrapper signature to forward `collectionType`,
   `comparisonToolSlugs`, `comparisonToolNames`. This is now documented as a
   Common Mistake in `packages/pipelines/CLAUDE.md`.

4. **Inline tool picker, no `ToolMultiPicker.vue` component** (Session 6) —
   the spec sketched a reusable tool picker. We kept the picker inline in
   `ArticleGenerateTab.vue` until a second caller exists; native checkboxes
   styled with the comparison-row layout (touch-target compliant at 44px).

5. **`articles-standalone.ts` is the integration point**, not a new
   `ArticleGenerateModal.vue` — the existing standalone generator already had
   `collection: "comparisons"` in its dropdown but never mapped to
   `collectionType`. We mapped `collection ("comparisons")` →
   `collectionType ("comparison")` via `ASTRO_FOLDER_TO_COLLECTION_TYPE`,
   added the refine-rule for `toolSlugs` (2-4) and forwarded the new fields
   through `triggerWithPreRunId.extraInput`.

6. **Locale-aware section labels** — the original spec only mentioned
   `Sprache: {locale === 'de' ? 'Deutsch …' : 'English …'}` but kept all H2
   names hardcoded in German. The implementation accepts `locale: "de" | "en"`
   on the prompt builder and looks up section names ("Auf einen Blick" vs
   "At a glance", "Pricing-Stand" vs "Pricing as of", etc.) from a typed
   `LOCALE_LABELS` map in `comparison.ts`. Required for the spec's
   stated-but-out-of-scope EN comparisons to actually render correctly when
   they ship.

## Section — Discovered During Implementation

**`winner` enum vs `useCaseVerdicts[].winner` use different value spaces**

The top-level `winner` field uses positional labels (`tool-a`..`tool-d`,
`depends`, `tie`). Each `useCaseVerdicts[].winner` uses an actual tool slug
(`chatgpt`, `claude`, …). Without explicitly stating both rules in the prompt,
the LLM will use slugs in both places (or positional in both). The fix is
documented inline in both `buildComparisonContextFragment` and the prompt's
FRONTMATTER_EXTRAS section. Schema-level enforcement is intentionally narrow:
top-level `winner` is a strict Zod enum; `useCaseVerdicts[].winner` is
`z.string()` so a non-strict slug is accepted.

**`comparedAt` and `testMethodology` are optional in our Zod schema even though
the Astro collection treats them as recommended fields.** Rationale: the LLM
may legitimately omit `testMethodology` when no hands-on testing happened (a
purely doc-driven comparison). `comparedAt` defaults to today's date inside
the prompt template; if the LLM still omits it, the MDX renderer falls back to
the article's `updatedAt`. Validation rejects `winner === "depends"` without
`useCaseVerdicts` but tolerates absent optional fields.

**`triggerWithPreRunId.extraInput` does NOT auto-forward to the BullMQ job**

The `extraInput` payload lands in `pipeline_runs.input` JSONB but the
`enqueue` callback is free to reshape what reaches BullMQ. `enqueueBlogGenerationPipeline`
explicitly destructures and forwards only its declared fields. Adding new
pipeline inputs requires updating the wrapper signature AND the conditional
spread inside it — checked in Spec 61.2 review by adding the field to the
wrapper's parameter type and a `if (input.x) pipelineInput.x = input.x` line.

**`articles.collection` (text) vs `articles.collectionType` (enum) are two
distinct columns with different concerns** — 61.1 deliberately left
`articles.collection` set to `"blog"` for all rows; 61.2 wires it to the
`COLLECTION_ASTRO_NAME` map inside `PersistArticleStep`. Both columns now
move together when a pipeline completes. Routes that INSERT articles directly
(e.g. `blog/persist.ts`) still write `collection: "blog"` on initial insert —
the final PersistArticleStep update reconciles both columns. This matters for
any code path that reads `articles.collection` mid-pipeline (e.g.
`voice-reference/loader.ts` filters `collection = "blog"` — that filter is
still correct for source-locale voice references and unaffected by 61.2).
