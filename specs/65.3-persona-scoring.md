## 1. Mental Model

**Part A — Persona-Scoring:**

LLM-rated relevance score (0-10) per tool per persona, cached in `tool_persona_scores`. Consumed by brief-generators für persona-targeted content (Family B `persona_top_n` V1.5, Family A `top_n_comparison` mit persona-filter).

**Part B — Tool-Data Refresh:**

Web-search-driven freshness check für `tools.metadata` (pricing, features, recent-release-info). Tools 30+ Tage stale → cron triggert refresh, auto-apply + admin notification.

**Coupling zwischen A und B:**

- Tool-Data-Refresh detected material change → triggert Persona-Score-Invalidation für betroffenes tool
- Memory-Effekt: persona-score TTL ist hybrid — 6 Monate OR earlier wenn tool-data changed
- Beide nutzen LLM-calls + cost-tracking (Memory D14 Adapter-Shape pattern)

**Strategischer Fit:**

- Unblockt 65.5 brief-generators die persona-filtered tool-selection brauchen
- Stellt sicher dass "Top 5 LLMs Juni 2026" content faktisch aktuell ist (Part B refreshes pricing/features)
- Etabliert LLM-classifier-pattern für künftige enrichment-layers (z.B. tool-difficulty, use-case-tagging)

## 3. Part A — Persona-Scoring Architecture

### 3.1 Batch-Strategy Evaluation (Marcel: Discovery evaluiert)

**Option α — Per-Tool batch mit allen Personas (1 call → alle 10 scores):**

```typescript
// LLM input: { tool: {name, description, use_cases}, personas: [{name, definition}, ...] }
// LLM output: { scores: [{persona, score, reasoning}, ...] }
```

Pros:
- 108 tools × 1 call = **108 LLM-calls** (initial backfill)
- Context-coherent: LLM scored holistic across personas (e.g. consistent "Claude is great for developers AND students but less for parents")
- Cost: 108 calls × ~€0.01 = **~€1.08**

Cons:
- Output-token-heavy (10 scores × reasoning per response)
- One bad call → 10 personas missing per tool (vs 1 missing in per-persona)

**Option β — Per-Persona batch mit allen Tools (1 call → alle 108 scores):**

```typescript
// LLM input: { persona: {name, definition}, tools: [{name, description}, ...] }
// LLM output: { scores: [{toolId, score, reasoning}, ...] }
```

Pros:
- 10 personas × 1 call = **10 LLM-calls** (initial backfill)
- Persona-coherent: LLM ranked tools relative within persona (e.g. "for parents, ChatGPT > Claude > Midjourney")
- Cost: 10 calls × ~€0.03 = **~€0.30** (cheapest)

Cons:
- Massive input-token-load (108 tool descriptions per call)
- Output-token-bloat (108 scores per response)
- Hit Haiku context-limit at scale (200K input window OK, but output cap 4096 tokens — 108 × ~50 chars reasoning = ~5400 chars ≈ ~1800 tokens, fits but tight)
- Schema-bloat risk: LLM might lose track which tool-id maps to which score

**Option γ — Per-Tool-Persona einzelner Call (max parallel):**

- 1080 LLM-calls
- Pros: max parallelism, isolated failures
- Cons: ~€5.40 cost (5× α), no coherence, slow due to per-call overhead

### Discovery-Recommendation: **Option α (per-tool, all-personas)**

Reasoning:

1. **Coherence ist wertvoller als isolation** — "Claude scored 8 for developers and 3 for parents" innerhalb eines context-windows ist semantisch konsistenter
2. **Cost-balance:** €1.08 ist vernachlässigbar, β ist nur 0.78€ günstiger
3. **Failure-Isolation per tool ist actually fine** — wenn 1 tool failed, retry für nur dieses tool (vs retry 108 tools wenn 1 persona-call failed)
4. **Output cap ist comfortable:** 10 personas × ~50 chars reasoning = ~500 chars ≈ ~150 tokens output, weit unter 4096

### 3.2 LLM-Provider Evaluation (Marcel: Discovery evaluiert)

**Option α — Haiku 4.5:**

- Pros: Consistency mit 65.4 hook-picker, classification-task, supports `jsonMode: true`, ~10× cheaper than Sonnet
- Cons: Möglicherweise weniger nuanced bei subtle persona-judgements ("ist Claude eher für 'developers' oder 'creators'?")
- Cost: ~€0.01/call

**Option β — Sonnet 4.6:**

- Pros: Better nuanced reasoning, important für persona-edge-cases
- Cons: Doesn't support `jsonMode: true` (per 65.4 D2 — reject assistant prefill)
- Cost: ~€0.05/call → 108 × €0.05 = ~€5.40 initial backfill

**Option γ — Opus 4.7:**

- Pros: Best judgment for nuanced persona-targeting
- Cons: Same jsonMode rejection as Sonnet (per CLAUDE.md DO-NOT rule, modulo 65.4 §14 out-of-scope discovery flag)
- Cost: ~€0.15/call → ~€16 initial backfill

### Discovery-Recommendation: **Option α (Haiku 4.5)**

Reasoning:

1. **Pattern-Consistency mit 65.4** — wenn Haiku 4.5 für classification (hook-pick) gut ist, dann ist persona-scoring (auch classification) similar
2. **Score-Quality bei classification-tasks ist hoch** — Haiku ist designed für categorical-judgment-with-reasoning
3. **Cost-Difference** — €1.08 (Haiku) vs €5.40 (Sonnet) vs €16 (Opus). For V1 mit unsicherem ROI: Haiku
4. **JsonMode wichtig** — strukturiertes Zod-parsed output ist robuster als markdown parsing
5. **Memory D27 watch:** Wenn 65.3 auch Haiku nutzt → "Haiku for classification, Sonnet/Opus for content-generation" wird etabliertes 2-Spec-Pattern (Memory-worthy)

### 3.3 Initial Backfill-Strategy Evaluation (Marcel: Discovery evaluiert)

**Option α — Eager (alle 108 Tools × 10 Personas direkt nach onboarding):**

- 108 LLM-calls upfront
- Cost: ~€1.08 (mit Option α batching)
- Time: ~108 × ~3s/call = ~5 Min total (kann parallel laufen)
- Pros: V1.5 `persona_top_n` ready aus dem Stand
- Cons: ~€1 frontloaded ohne immediate ROI (Family A V1 nutzt keine persona-filter)

**Option β — Lazy:**

- Nur Tools die in plan-pending briefs verlangt werden bekommen Scores
- Brief-generator-time triggert `listToolsMissingPersonaScores` → on-demand score
- Pros: Pay-as-you-use, kein upfront-cost
- Cons: First brief mit persona-filter blockt 5-10 sec für scoring 5-10 tools

**Option γ — Lazy + Backfill-Script:**

- V1 default: Lazy (Option β)
- Marcel kann via Settings-UI button "Backfill all persona-scores" triggern
- Pros: Both worlds — Marcel-controlled, no surprises
- Cons: Slight extra implementation (button + worker)

### Discovery-Recommendation: **Option γ (Lazy + Backfill-Script)**

Reasoning:

1. **V1 nutzt persona-scoring noch nicht aktiv** — Family A `top_n_comparison` ist V1, hat keine persona-filter; `persona_top_n` ist V1.5
2. **Lazy-on-demand ist robust** — wenn 65.5 brief-generator persona-filter braucht, ruft helper → missing-tools werden gescored
3. **Backfill-script gibt Marcel control** — wenn er weiß "ich plane persona-heavy content next week", kann er upfront-batchen
4. **Pattern-Consistency mit 65.2** — backfill-script mit dry-run + apply-mode (Memory D23 backfill pattern)

### 3.4 TTL-Handling (Marcel-Decision: Hybrid)

Per Marcel: "Hybrid: 6 Monate default + Trigger via Part B refresh."

**Implementation:**

```typescript
async function pickPersonaScoredTools(input: {
  projectId: string;
  persona: string;
  toolIds: string[];
  minScore?: number;
}): Promise<{ scoredTools: ToolPersonaScore[]; rescoredCount: number }> {
  // 1. Get fresh scores (< 6 months)
  const fresh = await listFreshPersonaScores({
    projectId: input.projectId,
    persona: input.persona,
    toolIds: input.toolIds,
    olderThanDays: 180,
  });
  
  // 2. Identify missing OR stale
  const missingOrStale = input.toolIds.filter(
    id => !fresh.find(f => f.toolId === id),
  );
  
  // 3. On-demand re-score for missing/stale
  if (missingOrStale.length > 0) {
    await triggerPersonaScoringBatch({
      projectId: input.projectId,
      personas: [input.persona],  // single persona for this lazy-call
      toolIds: missingOrStale,
    });
    // Re-fetch
    const justScored = await listPersonaScoresForTools({
      projectId: input.projectId,
      persona: input.persona,
      toolIds: missingOrStale,
    });
    fresh.push(...justScored);
  }
  
  return {
    scoredTools: fresh.filter(s => s.score >= (input.minScore ?? 5)),
    rescoredCount: missingOrStale.length,
  };
}
```

**Part B Coupling:**

```typescript
// In Part B's apply-tool-changes step:
async function applyToolDataChanges(toolId: string, changes: ToolDataChanges) {
  await updateTool(toolId, changes);
  
  if (changes.materialChange) {
    // Invalidate persona-scores for this tool → next brief-gen re-scores
    await deletePersonaScoresForTool(toolId);
    log.info('Persona-scores invalidated for material tool-change', { toolId });
  }
}
```

## 4. Part B — Tool-Data Refresh Architecture

### 4.1 Refresh-Worker Design

Per Memory D17 — Cron-based Coordinator Pattern:

```typescript
// apps/api/src/workers/tool-data-refresh.cron.ts

const TOOL_REFRESH_INTERVAL_MS = 6 * 60 * 60 * 1000; // 6h
const STALE_THRESHOLD_DAYS = 30;  // Marcel-Decision

export function startToolDataRefreshCron() {
  setInterval(async () => {
    const stale = await listToolsStaleForRefresh({
      olderThanDays: STALE_THRESHOLD_DAYS,
      limit: 5,  // throttle: 5 tools per 6h = 20/day max
    });
    
    for (const tool of stale) {
      await enqueueToolRefreshJob({ toolId: tool.id });
    }
  }, TOOL_REFRESH_INTERVAL_MS).unref();
}
```

**Worker:**

```typescript
// apps/api/src/workers/tool-data-refresh.worker.ts
import { Worker } from 'bullmq';

const worker = new Worker('tool-data-refresh', async (job) => {
  const { toolId } = job.data;
  const tool = await getTool(toolId);
  if (!tool) return { status: 'skipped', reason: 'tool-deleted' };
  
  // 1. Web-search for fresh data
  const searchResults = await fetchToolFreshness({
    toolName: tool.name,
    slug: tool.slug,
    homepage: tool.homepage_url,
    queries: [
      `${tool.name} pricing 2026`,
      `${tool.name} features`,
      `${tool.name} latest update`,
    ],
  });
  
  // 2. LLM extract structured updates
  const extracted = await extractToolDataFromSearchResults({
    tool,
    searchResults,
  });
  
  // 3. Diff against current tool.metadata
  const diff = computeDiff(tool.metadata, extracted);
  
  if (diff.materialChange) {
    await applyToolDataChanges(toolId, diff.changes);
    await notifyAdminToolChanged({
      toolId,
      toolName: tool.name,
      diff: diff.changes,
    });
  }
  
  // 4. Mark refreshed regardless of change
  await markToolRefreshed(toolId);
  
  return { status: 'refreshed', materialChange: diff.materialChange };
});
```

### 4.2 Material-Change Threshold Evaluation (Marcel: Discovery evaluiert)

**Option α — Diff-Threshold high (nur "material" changes):**

Material = pricing-tier hinzu/raus, free-tier removed/added, major-feature added/removed
Non-material = pricing-€ shift ±5%, marketing-copy changes, FAQ-updates

Pros: Minimal admin-notification-noise (Marcel sieht nur "real" changes), kein notification-burnout
Cons: Subtle but-important changes invisible (e.g. €19→€29 is silent)

**Option β — Diff-Threshold low (jede change surfaced):**

Pros: Max-completeness, Marcel sieht alles
Cons: Notification-fatigue (5-10 notifications/day für trivial changes)

**Option γ — Adaptive:**

- Marcel-flagged "fast-moving" tools (LLMs, image-gens) → low threshold
- Non-flagged tools → high threshold

Pros: Best of both
Cons: Marcel-effort for tagging fast-moving tools

### Discovery-Recommendation: **Option α (high threshold)**

Reasoning:

1. **Notification-fatigue ist real Risk** — wenn Marcel 5-10 notifications/day kriegt für trivial-changes, ignored alle
2. **Material changes catch SEO-relevant things** — pricing-tier-changes, free-tier-removal sind die wirklich content-relevant updates
3. **Auto-apply ist still applied auch bei non-material** — DB ist immer up-to-date, notification ist nur surfacing-decision
4. **Marcel kann später Threshold adjusten** — wenn er feels "ich vermisse subtle changes", kann threshold lowered werden via env-var

**Concrete "material change" definition (in Spec):**

```typescript
interface MaterialChangeRules {
  pricingTierAdded: true;
  pricingTierRemoved: true;
  freeTierStatus: true;          // free-tier added/removed
  majorFeatureAdded: true;       // LLM-judged "would affect comparison-article content"
  apiAccessChanged: true;        // public API added/removed
  pricingShiftPercent: 20;       // >20% price change
  modelLineupChanged: true;      // for LLM-tools: new model released
}
```

LLM-as-judge approach: extract step asks LLM "would this change affect a comparison-article published last month?" → boolean.

### 4.3 Web-Search Adapter Selection

Marcel-Decision: "LLM extract aus web-search-results (3-5 searches per tool, ~€0.05)".

**Web-search-provider verify-points:**

8. Welcher web-search-adapter existiert? (Toolwiki nutzt vermutlich Tavily oder Serper basierend auf bestehender Memory)
9. Cost per search: ~€0.005-0.01 für most providers
10. Result-quality: Tavily ist content-extraction-friendly, Serper ist Google-equivalent

**Default-Annahme** (verify): Tavily existiert als adapter im codebase.

**Cost-Estimate:**

- 3 searches × €0.008 = €0.024 search-cost
- 1 LLM-extract call (Haiku, ~3000 input tokens, ~500 output) = €0.025
- **Total per tool refresh: ~€0.05** ✓ (matches Marcel-decision)

**Monthly cost (108 tools × 30-day refresh):**

- 108 tools / 30 days = ~3.6 refreshes/day average
- 3.6 × €0.05 = €0.18/day = **~€5.40/month** ✓ (matches Master-Spec estimate)

## 10. Multi-Domain Considerations

Per 65.1 — `tool_persona_scores` ist **project-scoped** (Marcel-Decision Q5):
- Composite PK: `(tool_id, project_id, persona)`
- BK + Toolwiki haben unterschiedliche persona-scores für gleiche tools

**Implication:**
- Backfill-script is project-scoped (Memory D23 — mandatory)
- Each project has independent persona-scoring TTL
- Tool-data refresh ist project-AGNOSTIC (tools is global table)
- BUT: Tool-change-triggered persona-invalidation cascades to ALL projects (alle scores für changed tool sind invalidated)

**Trade-off accepted:** Project-A and Project-B might both have to re-score after tool-change. That's correct behavior — material-change affects all comparison-articles.

## 11. Risk Analysis

| Risk | Severity | Mitigation |
|---|---|---|
| Haiku output-format-drift for 10-persona batch | Medium | Strict Zod schema + fallback to per-persona-call on schema-fail |
| Web-search-results stale/SEO-spam | Medium | LLM-as-judge filters; multi-source-diagnosis (Memory D9) |
| Material-change-threshold too strict, misses updates | Medium | Marcel-feedback-loop: notification "low confidence material change" surfaces edge-cases |
| Persona-scoring cost-overflow if eager backfill multiple projects | Low | Backfill-script is project-scoped, opt-in |
| Tool-data-refresh cron blocks if web-search hangs | Low | 30s timeout per search, AbortController |
| Notification-spam wenn material-changes häufig | Medium | Batching every 6h, summary-format |
| LLM hallucinates pricing-changes that aren't real | High | Source-attribution in extracted data; auto-apply has rollback-button (V1.1) |
| Persona-scoring drift over time (LLM model updates) | Medium | TTL (6 months) auto-rescore catches drift |

## 17. Implementation Record + Deviations (2026-05-26)

Implementiert in einem Tag (~6h). Commit `c118173`. Full apps/api 447 pass / 8 skip / 0 fail; workspace typecheck 0 errors across 24 packages.

### Discovery-Recommendations ratified
- **Q2 Batch-Strategy** → Option α (per-tool, all-personas in one Haiku call) ✓
- **Q3 LLM-Provider** → Option α (Haiku 4.5 + `jsonMode: true`) ✓ — mirrors 65.4 Hook-Picker
- **Q5 Backfill-Strategy** → Option γ (Lazy + opt-in Backfill-Script) ✓ — surfaced via Settings UI button

### Deviations from spec narrative

1. **No `tools` table.** Spec §2.2 verify-point 1 + §5 SQL `ALTER TABLE tools` were structurally wrong. Tools live as `articles WHERE collection='tools'` (per 65.1 `tool_persona_scores.tool_id → articles.id` FK + `assertArticleIsTool` guard). Migration 0119 adds `tool_data_refresh_metadata jsonb` to `articles`, not a separate table.

2. **No `tools.refreshed_at` column.** Spec §5 proposed adding it; reused existing `articles.lastRefreshedAt` (Spec 54.10) — same semantics, no duplication. The `articles_last_refreshed_at_idx` partial index (migration 0052) backs the staleness scan.

3. **Web-search adapter dissolved.** Spec §4.3 verify-points 6-8 + Q6 anticipated a Tavily/Serper adapter wire-up. The Anthropic adapter already supports `web_search_20250305` via `webSearch: {enabled: true, maxUses: 3}` ([client.ts](../packages/adapters/anthropic/src/client.ts)). Used inline in [`extract-tool-data.ts`](../apps/api/src/lib/tool-data-refresh/extract-tool-data.ts) — no new package or vault entry.

4. **Material-change threshold simplified to LLM-as-judge boolean.** Spec §4.2 contemplated three options (high, low, adaptive); V1 uses Option α (LLM-as-judge boolean from strict Zod schema) only. Per-project adaptive threshold + Marcel-tunable percent shift deferred to V1.1. Pricing/feature fingerprints (SHA-256 truncated to 16 chars) are computed + persisted for observability but don't drive the material flag.

5. **Conservative write strategy — additive, not destructive.** Spec §4.4 framed "auto-apply" as "DB updated". Implementation writes the LLM extract under `domain_extras.toolDataRefresh` via `jsonb_set` (additive, preserves Marcel-owned sibling keys like `existingSibling`); audit + 5-event ring buffer + fingerprints into the new `tool_data_refresh_metadata` column. **Marcel-owned `tool_pricing` / `tool_price_from` columns are NEVER overwritten** — those stay Astro-imported. Future workflow could promote `domain_extras.toolDataRefresh.pricing` into the canonical columns via Marcel-approved UI (V1.1).

6. **Cross-project persona-score cascade (Marcel-Decision §10 ratified).** `invalidatePersonaScoresForTool` deletes scores for the tool across **every project** (not just the project the refresh fired in). Verified live by `apply-changes.test.ts:152-181` (4-row delete across 2 test projects). Re-scoring trade-off accepted — material tool-changes affect comparison content in all tenants.

7. **Batched notification, severity-aware.** Spec §4.4 + Memory D21 implemented in [`notify-batch.ts`](../apps/api/src/lib/tool-data-refresh/notify-batch.ts): one notification per tick to every `users.role='owner'` row. Severity `critical` (triggers Web Push) when ≥1 material change fired; else `info` (SSE only). Kill-switch via `PIPELINE_NOTIFICATIONS_ENABLED=false`.

8. **`PERSONA_DEFINITIONS` shipped alongside.** Spec §7 sketched the persona-definition map inline; promoted to a first-class export in [`packages/shared/src/recurring-content/personas.ts`](../packages/shared/src/recurring-content/personas.ts). Same hot-path consumed by the LLM prompt in `score-tool-for-personas.ts`. Future per-tenant overrides (e.g. BK's Solar-Eigentümer persona) extend this constant.

### Footguns surfaced (now CLAUDE.md DO-NOTs)

1. **PostgreSQL ASC defaults to NULLS LAST.** `selectStaleTools` initially used `asc(articles.lastRefreshedAt)` which placed never-refreshed rows at the END — opposite of "cold-candidates-first" semantics. Fix: `sql\`${col} ASC NULLS FIRST\`` + `asc(t.id)` tiebreaker. Documented in root CLAUDE.md + packages/db/CLAUDE.md.

2. **`'draft'` is NOT a valid `article_status` enum value.** Test fixtures defaulted to `status: "draft"` (semantically "freshly created"); enum has only `proposed | approved | generating | … | superseded`. Symptom: `PostgresError: invalid input value for enum article_status: "draft"`. Fix: `'proposed'` for the same intent. Documented in root CLAUDE.md.

3. **Bun's `it()` timeout signature is 3rd-positional-arg, not Vitest options object.** Cleared a pre-existing Vitest-style `it("name", { timeout: 15_000 }, fn)` in [briefs-bulk-actions.test.ts](../apps/api/test/routes/briefs-bulk-actions.test.ts) — Bun expects `it("name", fn, 15_000)`. Documented in apps/api/CLAUDE.md.

### Patterns surfaced

1. **"Haiku-for-classification" 2-spec pattern.** 65.4 hook-pick + 65.3 persona-score both use Haiku 4.5 + `jsonMode: true` + Zod validation + soft-fail. Heuristic for any future pick-N-of-M or score-X-of-N task: Haiku is sufficient; reserve Sonnet/Opus for content-generation. Candidate for Memory slot D28 if a 3rd spec ratifies it.

2. **Cron worker with material-change cascade.** Extract → diff → apply tuple where the material flag triggers a downstream cache invalidation across projects. Reusable for any future enrichment that affects shared cached state (e.g. tool category re-classification invalidating Cluster-Toolification mappings).

3. **`domain_extras` `jsonb_set` for additive enrichment.** Write LLM extracts under a named bucket key (`toolDataRefresh`, `toolBrandColors`, etc.) so Astro-imported siblings survive untouched. Pattern 143 applied — typed jsonb bucket per concern, never a single mutex column.
