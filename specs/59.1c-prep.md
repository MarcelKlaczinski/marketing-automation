# Spec 59.1c-prep — Backend Bug Fixes (Prerequisite for 59.1c)

**Theme:** 59 (Tier 3 Pre-Launch Foundation)
**Status:** Draft
**Estimated effort:** 5-10 minutes (single commit)
**Prerequisite:** None (immediate)
**Successor:** 59.1c System Credentials + Signal Sources UI

---

## Goal

Fix two backend bugs identified in the 59.1c reality check (G1, G3) so that the 59.1c main spec can land cleanly without bundling unrelated backend fixes. **This is a 2-file, ~5 minute commit.** Bundling these with 59.1c would muddy the diff and make the credentials UI spec harder to review.

The remaining backend fixes (G2 cron toggle, G4 frontend adapter list, G7 i18n, G8 sidebar section) are scoped into 59.1c proper because they're tightly coupled to the UI work.

## Non-Goals

- No UI changes
- No new endpoints
- No migrations (just enum value additions + JSONB default fix)
- No scope creep into G2/G4

---

## Background

The 59.1c reality check (`/specs/_drafts/59-1c-backend-reality.md`) found:

**G1** — `reddit` and `github` are missing from `credentialSchema.service` enum + `validServices` array in `apps/api/src/routes/system.ts`. POST /api/system/credentials and DELETE /api/system/credentials/:service/:key both return 400 for reddit/github today, even though the verify dispatcher accepts them. This blocks the 59.1c credentials UI for these adapters.

**G3** — `apps/api/src/routes/projects.ts` line 236 initializes new projects with `signalSources.github: false`, but the Zod schema `SignalSourcesSchema` expects `github` to be an object with default subfields. The Drizzle insert bypasses Zod validation at write time, so the bug only surfaces later when `SignalSourcesSchema.parse()` is called on the stored row (which then throws). Has been latent because no UI code calls `.parse()` on the field yet — 59.1c will.

Both are 1-2 line fixes. Bundling them in their own commit keeps 59.1c diff focused on UI work.

## Optional sanity check: existing projects

If any existing rows in `project_configurations` have `signal_sources.github = false` (likely just dev/staging projects created after 59.1b but before this fix), they will fail `SignalSourcesSchema.parse()` once 59.1c calls it.

**Two options:**

**Option A — Lazy fix (recommended):** Do nothing now. The 59.1c UI will surface the bad data when the user opens the Signal Sources page, fail to render, and we'll patch the affected project's config manually via SQL or admin tool.

**Option B — Proactive backfill:** Add a one-shot SQL migration that updates existing rows:

```sql
UPDATE project_configurations
SET signal_sources = jsonb_set(
  signal_sources,
  '{github}',
  '{"enabled":false,"topics":["ai-tools","llm","ai-agents","chatbot","ai-assistant","langchain","llamaindex","rag","prompt-engineering","vector-database"],"timeWindowDays":7,"minStarsNew":20,"minStarsEstablished":500,"maxAgeDays":14,"cronPattern":"0 3 * * *"}'::jsonb
)
WHERE signal_sources->'github' = 'false'::jsonb;
```

**Decision:** Option A — solo dev environment, low row count, manual patch is fine. Backfill migration not needed.

## Risks

**Risk 1: `github_app` vs `github` confusion in a future PR**
- *Mitigation*: The enum names stay distinct. Anyone adding a new astro-sync feature should use `github_app`. Anyone adding signal-source code should use `github`. Code review catches mix-ups.

**Risk 2: Existing projects break when 59.1c surfaces them**
- *Mitigation*: Per Option A above, lazy fix via manual SQL when encountered. Solo dev environment, ~3 projects max affected.

**Risk 3: The Zod schema defaults drift from this spec**
- *Mitigation*: The fix copies from `packages/db/src/schema/project-config.ts` at implement time, not from this spec text. Schema is source of truth.
