## Goal

Visually refresh the `single-tool-spotlight` template to match the new toolwiki Design System, port the Cover slide from the Claude Design HTML into the same composition, and establish the **patterns** that Specs 60.2-60.5 will mechanically apply to the other four templates.

2. The Cover slide (HTML at `cover-*.html` per Claude Design bundle) is implemented as a new slide within the spotlight template — NOT as a separate `TemplateKey`. Per Spec 60.0c Section C.2.1: cover bounds land here.

4. `<DsGlow>`, `<DsTop>`, `<DsFoot>`, and `deriveDsTokens()` from Spec 60.0b v2 are consumed for the first time end-to-end
5. Inter Variable font loaded via `@remotion/google-fonts/Inter`
6. `buildConstraintBlock(bounds, locale)` helper implemented and consumed by the template's LLM prompt
7. Visual baselines for spotlight (12 PNGs: 4 slides × 3 fixtures, dark theme only by default — light theme baselines added when first project requests light render)

This is the **reference template**. The next four specs (60.2-60.5) will be substantially shorter and follow this one's pattern.

## Section A — Slide Structure + Composition Tree

### A.1 The slide sequence

The HTML inspection of `single-tool-spotlight-dark.html` and `cover-dark.html` shows two **distinct visual structures** that this template renders:

```
Slide 1: COVER          (cover-dark.html structure — hero / logos / stats / byline / swipe / foot)
Slide 2: SPOTLIGHT BODY (single-tool-spotlight-dark.html — hero-tool / verdict-line / stats-row / body-grid / foot)
Slide 3 [optional]: EXTENDED COMPARISON (future, deferred)
Slide 4: END            (CTA-only slide reusing existing end-slide pattern)
```

For 60.1: render slides 1, 2, and 4. The "Extended Comparison" slide variant is deferred — single-tool-spotlight is primarily a deep dive on one tool; the cover does the "who is this article about?" framing, body does the verdict + strengths/weaknesses, end gives the CTA.

**3-slide default**, overridable via `overrides.layout.includeCover: false` (drops cover, becomes 2-slide) or `overrides.layout.includeEnd: false` (drops end, becomes 2-slide).

### A.2 Canvas + safe zones

Both cover and body inherit from existing convention (`CAROUSEL_SAFE_ZONES` in `packages/social/src/compositions/list-carousel/safeZones.ts`):

```
CANVAS_W:  1080
CANVAS_H:  1350         (4:5 Instagram feed)
PADDING:   56           (all sides — matches DS HTML `.template { padding: 56px }`)
INNER_W:   968
INNER_H:   1238
```

## Section B — Composition Prop Schema Rename + Zod Validation

### B.1 Why the rename

Per Spec 60.0c Section C.3, the `*Bounds` objects now use REMOTION.md naming (`strengths`, `weaknesses`, `verdict`, `winnerName`) but composition internals stayed at the older names (`pros`, `cons`, `tagline`). That carry-over is now resolved here because the composition is being rewritten anyway.

## Section C — Per-Slide Implementation

### C.1 Top-level dispatcher

```tsx
// SingleToolSpotlight.tsx
import { AbsoluteFill } from "remotion";
import type { SingleToolSpotlightInput } from "./types";
import { CoverSlide } from "./CoverSlide";
import { BodySlide } from "./BodySlide";
import { EndSlide } from "./EndSlide";

export const SingleToolSpotlight: React.FC<SingleToolSpotlightInput> = (props) => {
  // slideIndex 0 = cover, 1 = body, 2 = end (when all three are present)
  // If overrides drop cover/end, indices shift
  const slides = computeSlideOrder(props);
  const slide = slides[props.slideIndex];

  if (slide === "cover" && props.cover) {
    return <CoverSlide content={props.cover} {...sharedProps(props)} />;
  }
  if (slide === "body" && props.body) {
    return <BodySlide content={props.body} {...sharedProps(props)} />;
  }
  if (slide === "end" && props.end) {
    return <EndSlide content={props.end} {...sharedProps(props)} />;
  }

  // Defensive: render a blank canvas if slide config is incomplete
  return <AbsoluteFill style={{ background: "black" }} />;
};

function computeSlideOrder(props: SingleToolSpotlightInput): Array<"cover" | "body" | "end"> {
  const order: Array<"cover" | "body" | "end"> = [];
  if (props.cover) order.push("cover");
  if (props.body) order.push("body");
  if (props.end) order.push("end");
  return order;
}

function sharedProps(props: SingleToolSpotlightInput) {
  return {
    theme: props.theme,
    locale: props.locale,
    brandTokens: props.brandTokens,
    overrides: props.overrides,
    slideTotal: props.slideTotal,
    slideIndex: props.slideIndex,
  };
}
```

### C.2 CoverSlide

The HTML structure is straightforward — port 1:1 from `cover-dark.html`. Inline most of it; consume `<DsGlow>` (dual-glow per Spec 60.0b v2 Section B.6), `<DsTop>` (with `updateBadge` prop variant), `<DsFoot>` (logoHeight 48 vs default 44 — see Spec 60.0b v2 Section C.4).

```tsx
// CoverSlide.tsx (sketch — refer to cover-dark.html for exact CSS)
import { AbsoluteFill, Img } from "remotion";
import { useMemo } from "react";
import { deriveDsTokens } from "@/social/brand-tokens/derive";
import { DsGlow, DsTop, DsFoot } from "@/social/ds-components";
import { resolveBrandTokens } from "@/social/lib/brand-tokens";
import type { CoverProps } from "./types";

interface Props {
  content: CoverProps;
  theme: "dark" | "light";
  locale: "de" | "en";
  brandTokens?: unknown;
  slideIndex: number;
  slideTotal: number;
}

const CANVAS_W = 1080;
const CANVAS_H = 1350;
const PAD = 56;

export const CoverSlide: React.FC<Props> = ({ content, theme, brandTokens, slideIndex, slideTotal }) => {
  const tokens = useMemo(
    () => deriveDsTokens(resolveBrandTokens(brandTokens), theme),
    [brandTokens, theme],
  );

  return (
    <AbsoluteFill style={{
      width: CANVAS_W, height: CANVAS_H,
      background: tokens.surface.base,
      color: tokens.ink.base,
      fontFamily: tokens.typography.fontFamily,
      overflow: "hidden",
      position: "relative",
    }}>
      {/* Dual glow per cover-dark.html — see Spec 60.0b v2 Section B.6 */}
      <DsGlow tokens={tokens} theme={theme} corner="top-right" color="brand"
              size={880} inset={{ x: -200, y: -120 }}
              alpha={theme === "dark" ? 42 : 28} blur={70} />
      <DsGlow tokens={tokens} theme={theme} corner="bottom-left" color="accent"
              size={880} inset={-200}
              alpha={theme === "dark" ? 22 : 16} blur={70} />

      <div style={{
        position: "relative", zIndex: 1,
        padding: PAD, boxSizing: "border-box",
        display: "grid",
        gridTemplateRows: "auto auto 1fr auto auto auto auto auto",  // top / hero / spacer / logos / stats / byline / swipe / foot
        rowGap: 24, height: "100%",
      }}>
        <DsTop tokens={tokens}
               eyebrow={content.eyebrow}
               rightText={`${String(slideIndex + 1).padStart(2, "0")} / ${String(slideTotal).padStart(2, "0")}`}
               num={content.headerNum}
               updateBadge={content.updateBadge} />

        <Hero tokens={tokens} title={content.heroTitle} kicker={content.kicker} />

        <div /> {/* spacer */}

        <ToolLogos tokens={tokens} logos={content.toolLogos} moreText={content.toolsMoreText} />

        <StatsRow tokens={tokens} stats={content.stats} />

        <Byline tokens={tokens} byline={content.byline} />

        <SwipeIndicator tokens={tokens} text={content.swipeText} />

        <DsFoot tokens={tokens} logoUrl="/assets/logo-light.svg"
                ctaLead={content.footer.ctaLine}
                ctaBold={content.footer.url}
                logoHeight={48} />
      </div>
    </AbsoluteFill>
  );
};

// Hero, ToolLogos, StatsRow, Byline, SwipeIndicator — inline subcomponents
// or in shared/ subfolder if they grow past 30 lines each
```

If a project sets `brand_tokens.typography.fontFamily = "Helvetica Neue, sans-serif"`, that wins. Inter is only loaded as the system-level option; Remotion's font system handles the fallback chain.

## Section F — `buildConstraintBlock` Helper + LLM Prompt Update

### F.1 Why this lands here

Per Spec 60.0c Discovery (Section D.3 of report): "All 4 in-scope templates use `generateContentWithGate()` which has no template-specific prompt strings... The `buildConstraintBlock` helper does not yet exist."

The single-tool-spotlight visual refresh changes the **content shape** the LLM must produce. Previously it generated `caption + hashtags` only; now it also needs structured content for `verdictQuote`, `strengths`, `weaknesses`, `scoreLabel`, etc. — REMOTION.md's full SpotlightProps shape minus the static parts (eyebrow, footer.url, etc., which come from the article).

This forces the helper into existence. 60.1 implements it.

### F.2 Helper specification

```typescript
// packages/social/src/templates/lib/buildConstraintBlock.ts

import type { ContentBounds, FieldBound, ListBound } from "../types";

/**
 * Format a bounds object as an LLM-prompt section listing every field's
 * character/count constraints. Locale-aware (DE uses "Zeichen", EN "chars").
 *
 * Output is a markdown-ish block ready to inline into a prompt.
 */
export function buildConstraintBlock(
  bounds: ContentBounds,
  locale: "de" | "en",
  options?: {
    /** Subset of fields to include. Default: all top-level fields */
    fields?: string[];
    /** Header text override */
    header?: string;
  },
): string {
  const fields = options?.fields ?? Object.keys(bounds);
  const lines: string[] = [];

  for (const key of fields) {
    const bound = bounds[key];
    if (!bound) continue;
    lines.push(...formatBound(key, bound, locale, 0));
  }

  const header = options?.header ?? (
    locale === "de"
      ? "ZEICHENLIMITS (strikt einhalten):"
      : "CHARACTER LIMITS (must be respected):"
  );

  return `${header}\n${lines.join("\n")}`;
}

function formatBound(
  key: string,
  bound: FieldBound | ListBound | ContentBounds | number,
  locale: "de" | "en",
  depth: number,
): string[] {
  const indent = "  ".repeat(depth);

  if (typeof bound === "number") {
    return [`${indent}- ${key}: ${locale === "de" ? "exakt" : "exactly"} ${bound}`];
  }

  if (isFieldBound(bound)) {
    const unit = locale === "de" ? "Zeichen" : "chars";
    return [`${indent}- ${key}: ${bound.min}–${bound.max} ${unit}`];
  }

  if (isListBound(bound)) {
    // List with count + per-item bounds
    const unit = locale === "de" ? "Zeichen" : "chars";
    const countLabel = bound.count !== undefined
      ? (locale === "de" ? `exakt ${bound.count}` : `exactly ${bound.count}`)
      : (locale === "de"
          ? `${bound.countMin}–${bound.countMax} Einträge`
          : `${bound.countMin}–${bound.countMax} items`);
    const perItem = bound.each
      ? (locale === "de"
          ? `, jeder ${bound.each.min}–${bound.each.max} ${unit}`
          : `, each ${bound.each.min}–${bound.each.max} ${unit}`)
      : "";
    return [`${indent}- ${key}: ${countLabel}${perItem}`];
  }

  // Nested ContentBounds — recurse
  const childLines = Object.entries(bound).flatMap(([k, v]) =>
    formatBound(k, v as any, locale, depth + 1)
  );
  return [`${indent}- ${key}:`, ...childLines];
}

function isFieldBound(b: unknown): b is FieldBound {
  return typeof b === "object" && b !== null && "min" in b && "max" in b && !("each" in b) && !("count" in b);
}

function isListBound(b: unknown): b is ListBound {
  return typeof b === "object" && b !== null && ("each" in b || "count" in b || "countMin" in b);
}
```

## Deviations

**DS component visual isolation uses proxy slides, not standalone compositions** — `<DsGlow>`, `<DsTop>`, and `<DsFoot>` are tested by rendering them within realistic slide contexts (DsGlow via BodySlide, DsTop via CoverSlide, DsFoot via EndSlide) rather than as standalone Remotion compositions. This follows REMOTION.md guidance to avoid restructuring the layout when porting. The visual render harness (Section G) does not register separate "DsGlow Harness" compositions in `src/index.tsx` — baselines are generated directly via `visual-render-ds-components.ts` using minimal `<AbsoluteFill>` wrappers. This ensures DS components are tested in realistic context rather than artificial test harnesses.

## Open Questions

1. **Composition registration ID**: should the registered Remotion composition stay `SingleToolSpotlight` (existing) or change to reflect the multi-slide nature? Default: keep `SingleToolSpotlight` to avoid breaking existing render-server logic; slide-variant dispatching happens inside.

2. **Slide naming in worker logs**: when worker logs "rendering slide X for post Y", should the slide identifier be `0/1/2` or `cover/body/end`? Default: stick with numeric `slideIndex` per existing convention; logs can show both via formatter.

3. **Cover slide for tools-collection articles only?** Cover content (with byline, swipe indicator, byline.role) implies an authored article context. Articles in `tools` collection have author metadata; spotlight is restricted to `tools` per `singleToolSpotlightTemplate.eligibility()`. Confirm.

4. **`buildConstraintBlock` `fields` option default**: I made it "all top-level fields" with optional subset. Alternative: "no default, must specify" — forces explicit thought. Default: include-all stays since most templates want full constraints.

5. **Inter Variable subsets**: I specified `["latin", "latin-ext"]`. `latin-ext` covers German umlauts. Other potential needs (Cyrillic, Greek, etc.) — confirm not in scope, or add subsets as needed.

6. **`color-mix(in oklab, ...)` rendering** in Remotion Chromium — verified in 60.0b v2 baselines (if they were rendered). If 60.0b v2 hit issues, those should already be documented in its Discovered section. Re-verify here as cover uses `color-mix` heavily.
