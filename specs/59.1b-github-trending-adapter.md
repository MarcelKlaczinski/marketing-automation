# Spec 59.1b — GitHub Trending Signal Source Adapter

**Theme:** 59 (Tier 3 Pre-Launch Foundation)
**Status:** Draft (updated post-59.1a with established adapter patterns)
**Estimated effort:** 1 day
**Prerequisite:** 59.1a Reddit Adapter complete (establishes adapter pattern for this theme)

---

## Goal

Add GitHub as an external signal source for trend discovery via the **REST API + custom trending heuristic** approach (NOT scraping `github.com/trending`). Backend-only spec: implements token-authenticated adapter, two-query trending heuristic, project-config integration, and cron registration. UI for configuration deferred to 59.7 Polish.

## Non-Goals

- HTML scraping of `github.com/trending` (rejected — fragile, breaks existing adapter pattern)
- gharchive.org / BigQuery integration (rejected — overkill, $$$)
- GraphQL API (REST is sufficient for search)
- Repo activity beyond stars (no contributor analysis, no commit velocity)
- Per-language trending (could be future extension)
- GitHub configuration UI (deferred to 59.7)

### Why GitHub via REST + Heuristic

**Rejected: HTML scraping**
- Fragile (HTML structure changes)
- Breaks adapter pattern (all others use real APIs)
- Silent failure mode (cron dies, you notice weeks later)

**Chosen: REST API + own heuristic**
- Official API, stable contract
- Token-based, clear rate limits (5000/hour)
- "Trending" definition stays under our control
- Consistent with HN-Algolia, ProductHunt, vendor-rss patterns

### What "Trending" Means Here

For toolwiki, trending means **AI tool repos with significant recent traction**. Two queries per run:

1. **Rising new repos**: Created in last N days, sorted by absolute stars
  - Catches: new AI tools launching
  - Query: `created:>{N days ago} stars:>20 topic:ai-tools topic:llm ...`

2. **Active established repos**: Recently pushed, sorted by stars
  - Catches: significant updates to existing AI tools
  - Query: `pushed:>{N days ago} stars:>500 topic:ai-tools topic:llm ...`

Deduplicated by `full_name` (avoid double-counting repos in both queries).

## Patterns from 59.1a (apply to this spec)

The Reddit adapter (59.1a) established these conventions which MUST be followed here:

| Pattern | Application |
|---------|-------------|
| **Class-based adapter** | `class GitHubSignalSource implements ExternalSignalSource<Input>` with `.fetch(input, ctx)` — NOT a standalone function. Worker dispatches via `new Adapter().fetch(...)`. |
| **Naming convention** | `verifyGitHub` (not `verifyGitHubCredentials`) — consistent with `verifyAnthropic`, `verifyReplicate`, `verifySmtp`. |
| **Inline normalization** | Normalization logic lives in `src/index.ts` as a private function. `src/types.ts` holds only Zod schemas. No separate `normalize.ts`. |
| **Return type** | `Promise<RawSignal[]>` directly. Errors logged via `pino.warn`, run continues. No `errors` array in return. |
| **No token cache needed** | GitHub PAT is permanent — no OAuth refresh flow like Reddit. Skip the Map-based cache pattern. |
| **COST_OPS registered, no log row** | Register `COST_OPS.GITHUB_SIGNAL_COLLECT` for observability/discoverability. Worker does NOT call cost-tracked functions, so no DB row emitted. Matches HN, ProductHunt, Reddit. |

### A.2 Authentication

GitHub REST API requires **Personal Access Token** (PAT) for higher rate limits:
- Anonymous: 60 requests/hour (insufficient)
- Authenticated: 5000 requests/hour (plenty)

With 2 search queries per run + daily cron, total usage: 2 requests/day per project. Vast margin.

```typescript
// packages/adapters/github-trending/src/client.ts

export interface GitHubCredentials {
  personalAccessToken: string;  // PAT with `public_repo` scope (read-only)
}

const API_BASE = "https://api.github.com";

export async function searchRepositories(
  query: string,
  credentials: GitHubCredentials,
  perPage: number = 30,
): Promise<GitHubSearchResponse> {
  const url = `${API_BASE}/search/repositories?q=${encodeURIComponent(query)}&sort=stars&order=desc&per_page=${perPage}`;

  const response = await fetch(url, {
    headers: {
      "Authorization": `Bearer ${credentials.personalAccessToken}`,
      "Accept": "application/vnd.github+json",
      "X-GitHub-Api-Version": "2022-11-28",
      "User-Agent": "toolwiki-signal-collector",
    },
  });

  if (response.status === 401) {
    throw new GitHubAuthError("Invalid GitHub PAT");
  }
  if (response.status === 403) {
    const remaining = response.headers.get("x-ratelimit-remaining");
    if (remaining === "0") {
      throw new GitHubRateLimitError("GitHub API rate limit exceeded");
    }
    throw new GitHubAuthError("GitHub API forbidden");
  }
  if (!response.ok) {
    throw new Error(`GitHub API ${response.status}: ${response.statusText}`);
  }

  const data = await response.json();
  return searchResponseSchema.parse(data);
}
```

**No token caching needed**: GitHub PAT is the bearer token directly (no OAuth refresh). Unlike Reddit's `getAccessToken(creds)` with Map cache, GitHub uses the PAT as-is per request.

**Custom Error classes** (per memory pattern #ES2022-reserved-property-names):

### A.3 Trending Heuristic

```typescript
// packages/adapters/github-trending/src/heuristic.ts

export interface TrendingQueryInput {
  topics: string[];                  // ["ai-tools", "llm", "ai-agents", ...]
  timeWindowDays: number;            // e.g. 7
  minStarsNew: number;               // for "rising new repos", e.g. 20
  minStarsEstablished: number;       // for "active established", e.g. 500
}

export function buildTrendingQueries(input: TrendingQueryInput): {
  newRisingQuery: string;
  activeEstablishedQuery: string;
} {
  const sinceDate = new Date(Date.now() - input.timeWindowDays * 24 * 60 * 60 * 1000);
  const sinceIso = sinceDate.toISOString().split("T")[0]; // YYYY-MM-DD

  // GitHub search query syntax: AND-by-default between qualifiers, OR for topics
  const topicQuery = input.topics.map(t => `topic:${t}`).join(" ");

  return {
    newRisingQuery: `${topicQuery} created:>${sinceIso} stars:>${input.minStarsNew}`,
    activeEstablishedQuery: `${topicQuery} pushed:>${sinceIso} stars:>${input.minStarsEstablished}`,
  };
}
```

**Important**: GitHub's search API uses **OR** between topic qualifiers when there are multiple `topic:` segments separated by spaces, AND between different qualifier types. So `topic:ai topic:llm stars:>20` means "(topic:ai OR topic:llm) AND stars:>20".

Verify in implementation; if wrong, switch to multi-query approach (one query per topic, merge results).

### A.4 Class-based Adapter

Following 59.1a's established pattern, the adapter is a class implementing `ExternalSignalSource<Input>`:

```typescript
// packages/adapters/github-trending/src/index.ts

import type { ExternalSignalSource, RawSignal } from "@marketing-auto/signal-sources";
import { z } from "zod";
import pino from "pino";
import { searchRepositories, GitHubAuthError, GitHubRateLimitError, type GitHubCredentials } from "./client";
import { buildTrendingQueries } from "./heuristic";
import { searchResponseSchema, type RawGitHubRepo } from "./types";

const log = pino({ name: "github-signal-source" });

// Input schema for this adapter
export const githubFetchInputSchema = z.object({
  topics: z.array(z.string()).min(1),
  timeWindowDays: z.number().int().positive(),
  minStarsNew: z.number().int().nonneg(),
  minStarsEstablished: z.number().int().nonneg(),
  maxAgeDays: z.number().int().positive(),
  perQueryLimit: z.number().int().positive().max(100).default(30),
  credentials: z.object({
    personalAccessToken: z.string().min(1),
  }),
});

export type GitHubFetchInput = z.infer<typeof githubFetchInputSchema>;

type TrendingCategory = "new_rising" | "active_established";

/**
 * GitHub Trending signal source adapter.
 * Fetches AI-tool repos via two REST API queries (new rising + active established),
 * deduplicates by full_name, and returns normalized RawSignal entries.
 */
export class GitHubSignalSource implements ExternalSignalSource<GitHubFetchInput> {
  readonly source = "github" as const;

  async fetch(input: GitHubFetchInput, _ctx?: unknown): Promise<RawSignal[]> {
    const queries = buildTrendingQueries(input);
    const seen = new Set<string>();
    const signals: RawSignal[] = [];

    // Run new-rising query
    try {
      const newRising = await searchRepositories(
        queries.newRisingQuery,
        input.credentials,
        input.perQueryLimit,
      );
      for (const raw of newRising.items) {
        if (seen.has(raw.full_name)) continue;
        seen.add(raw.full_name);

        const signal = normalizeRepo(raw, "new_rising", input);
        if (signal) signals.push(signal);
      }
    } catch (err) {
      log.warn(
        { err, query: queries.newRisingQuery },
        "GitHub new-rising query failed; continuing",
      );
    }

    // Run active-established query
    try {
      const activeEstablished = await searchRepositories(
        queries.activeEstablishedQuery,
        input.credentials,
        input.perQueryLimit,
      );
      for (const raw of activeEstablished.items) {
        if (seen.has(raw.full_name)) continue;
        seen.add(raw.full_name);

        const signal = normalizeRepo(raw, "active_established", input);
        if (signal) signals.push(signal);
      }
    } catch (err) {
      log.warn(
        { err, query: queries.activeEstablishedQuery },
        "GitHub active-established query failed; continuing",
      );
    }

    log.info(
      {
        topics: input.topics.length,
        uniqueRepos: signals.length,
      },
      "GitHub signal collection complete",
    );

    return signals;
  }
}

/**
 * Normalize a raw GitHub repo into a RawSignal entry.
 * Returns null if the repo fails post-filter (archived, NSFW, too old).
 * Inlined here (not in separate normalize.ts) per established adapter convention.
 */
function normalizeRepo(
  raw: RawGitHubRepo,
  category: TrendingCategory,
  input: GitHubFetchInput,
): RawSignal | null {
  // Filter: archived repos = not actively maintained
  if (raw.archived) return null;

  // Filter: max age check (defensive — GitHub query already filters by created/pushed)
  const referenceDate = category === "new_rising"
    ? new Date(raw.created_at)
    : new Date(raw.pushed_at);
  const ageDays = (Date.now() - referenceDate.getTime()) / (1000 * 60 * 60 * 24);
  if (ageDays > input.maxAgeDays) return null;

  return {
    source: "github",
    externalId: `gh_${raw.full_name.replace("/", "_")}`,
    url: raw.html_url,
    title: raw.full_name,
    description: raw.description,
    capturedAt: new Date(),
    externalCreatedAt: new Date(raw.created_at),
    metadata: {
      name: raw.name,
      homepage: raw.homepage,
      language: raw.language,
      topics: raw.topics ?? [],
      stars: raw.stargazers_count,
      forks: raw.forks_count,
      watchers: raw.watchers_count,
      openIssues: raw.open_issues_count,
      license: raw.license?.spdx_id ?? null,
      trendingCategory: category,
      pushedAt: raw.pushed_at,
    },
  };
}
```

### A.5 Verify Function

```typescript
// packages/adapters/github-trending/src/verify.ts

import type { GitHubCredentials } from "./client";

const API_BASE = "https://api.github.com";

/**
 * Verifies GitHub PAT credentials by calling /user endpoint.
 * Function name follows convention: verifyXxx (not verifyXxxCredentials).
 */
export async function verifyGitHub(
  credentials: GitHubCredentials,
): Promise<{ ok: boolean; error?: string }> {
  try {
    const response = await fetch(`${API_BASE}/user`, {
      headers: {
        "Authorization": `Bearer ${credentials.personalAccessToken}`,
        "Accept": "application/vnd.github+json",
        "User-Agent": "toolwiki-verify",
      },
    });

    if (response.status === 401) {
      return { ok: false, error: "Invalid PAT" };
    }
    if (!response.ok) {
      return { ok: false, error: `Verify failed: ${response.status}` };
    }
    return { ok: true };
  } catch (err) {
    return {
      ok: false,
      error: err instanceof Error ? err.message : String(err),
    };
  }
}
```

```typescript
async function collectAdapter(job: CollectAdapterJob): Promise<CollectResult> {
  const config = await loadActiveConfig(job.projectId);

  switch (job.adapter) {
    case "producthunt": return collectProductHunt(job.projectId, config);
    case "hackernews": return collectHackerNews(job.projectId, config);
    case "vendor_rss": return collectVendorRss(job.projectId, config);

    case "github": return collectGitHub(job.projectId, config);  // NEW

async function collectGitHub(projectId: string, config: ActiveConfig): Promise<CollectResult> {
  const githubConfig = config.signalSources.github;
  if (!githubConfig.enabled) {
    return { adapter: "github", projectId, signalsAdded: 0, skipped: "disabled" };
  }

  const credentials = await loadCredentials(projectId, "github");
  if (!credentials) {
    throw new Error("GitHub credentials not configured");
  }

  const source = new GitHubSignalSource();
  const signals = await source.fetch({
    topics: githubConfig.topics,
    timeWindowDays: githubConfig.timeWindowDays,
    minStarsNew: githubConfig.minStarsNew,
    minStarsEstablished: githubConfig.minStarsEstablished,
    maxAgeDays: githubConfig.maxAgeDays,
    perQueryLimit: 30,
    credentials,
  });

  // Persist signals (idempotent upsert by source + external_id)
  const inserted = await upsertExternalSignals(projectId, signals);

  return {
    adapter: "github",
    projectId,
    signalsAdded: inserted,
  };
}
```

### CC.3 Rate Limit Handling

GitHub search API: **30 requests/minute** (more restrictive than the general 5000/hour). With 2 requests per run + daily cron, vast margin.

Parse rate limit headers when needed:
- `x-ratelimit-remaining`: requests remaining in current window
- `x-ratelimit-reset`: epoch when window resets

If `x-ratelimit-remaining < 5`, log warning. If 403 + remaining=0, raise `GitHubRateLimitError` and let cron retry on next schedule (no in-process retry — adapter doesn't sleep).

## Risks & Mitigations

**Risk 1: GitHub topic query syntax interpreted differently than expected**
- *Mitigation*: Session 1 explicit verification step against real API. If AND-by-default, switch to multi-query merge approach.

**Risk 2: PAT scope too narrow / too broad**
- *Mitigation*: `public_repo` scope is correct (read-only public). Documented in setup wizard / 59.1c UI later.

**Risk 3: GitHub changes search API contract**
- *Mitigation*: API versioning via `X-GitHub-Api-Version` header (`2022-11-28`). Stable for years.

**Risk 4: Topic filtering returns too many results**
- *Mitigation*: `perQueryLimit: 30` caps result size. With min-stars thresholds, expected ~10-30 repos per run.

**Risk 5: Some repos lack `topics` array**
- *Mitigation*: Default to `[]` in normalize. Search-by-topic ensures matched repos have at least one topic.

**Risk 6: Repo deleted / made private between collection and downstream use**
- *Mitigation*: Existing `external_signals` table is append-only with `processedAt` flag. If trend-synthesizer encounters dead URL, it can mark and skip.

**Risk 7: Token revoked silently**
- *Mitigation*: First 401 fails the run loudly via `GitHubAuthError`. Verify endpoint regularly checks token validity. Manual revocation visible via 59.1c Settings UI.

## Open Questions

  - **Recommendation**: don't filter by language by default. Topics cover the relevant filtering. Marcel can add language constraint via custom query if needed (future).

2. **Archived repos**: handled — `raw.archived === true` filtered out in normalize.

3. **Description language**: GitHub descriptions are usually English but can be German/Chinese/etc.
  - **Recommendation**: no filter. Let trend-synthesizer handle multilingual processing.

4. **Star history**: GitHub doesn't return star velocity in basic API. Need separate API call.
  - **Recommendation**: defer. Absolute stars + recency filtering sufficient for v1.

5. **Owner type filter**: GitHub repos can be `User` or `Organization`. Filter out user-owned repos?
  - **Recommendation**: no. Individual developers often launch important AI tools (e.g. ggerganov/llama.cpp started solo).

## Deviations from Spec

### D1: No `credential_type` enum migration needed

**Spec said:** Part C.1 called for `ALTER TYPE credential_type ADD VALUE 'github'` and a `system_credentials` table.

**Reality:** The codebase uses a `globalCredentials` table keyed by `service: string` (not a PostgreSQL enum). See `apps/api/src/lib/system-service.ts` → `readAdapterCreds(service)`. No migration needed. Credentials are stored with `service: "github"` and `key: "personal_access_token"` via the existing credential save endpoint.

### D2: `github` field in `SignalSourcesSchema` promoted from `z.boolean()` placeholder

**Spec said:** Nothing — assumed field didn't exist.

**Reality:** A `github: z.boolean().default(false)` stub already existed in `project-config.ts`. Promoting a boolean stub to a full Zod object also required updating the inline `signalSources` initializer in `apps/api/src/routes/projects.ts` (line ~236). Any future field promotions in `SignalSourcesSchema` must do the same.
