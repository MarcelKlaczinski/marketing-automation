## Goal

Build the **Content Discovery input surface** — the missing half of toolwiki's content pipeline. Today Marcel can see output (briefs, articles, clusters) but cannot interact with the discovery mechanisms (trends, gaps, refresh) that feed it.

Three discovery views land in this spec:

1. **Trends View** — eigene Route. List discovered trend candidates sorted by score, with signal breakdown + manual approve/dismiss. Per-project config to opt into auto-approval (default off). Manual trigger button + cron status display.

2. **Content Gaps in Cluster Detail** — Section auf existing Cluster Detail (zwischen Spokes und Cost-Panel). LLM-identified missing spokes within cluster. Per-cluster trigger button + suggest/generate flow.

3. **Refresh Queue View** — eigene Route. List articles needing refresh based on simple staleness heuristic (`daysSinceLastUpdate > threshold`). Plus Article Card badges. Per-project staleness threshold config.

Plus backend additions:
- **Runtime cron toggle** for trends + (new) refresh detection (per-project DB flag, worker watches)
- **Auto-approval flag** for gaps (`autoApproveGaps`, default off)
- **Refresh detection pipeline** (simple SQL-based, not LLM)
- **SSE extension** with discovery events (trends.discovered, gaps.detected, refresh.flagged)

After this spec lands: Marcel sees the full content pipeline lifecycle from discovery → brief → article. Sidebar shows live discovery activity. Settings centralizes all discovery automation toggles.

## What this is NOT

- Not LLM-based refresh detection (using simple staleness heuristic per C3). Full LLM-based detection is Phase E.
- Not auto-cron for refresh detection. Manual trigger only in 56.6. Cron is Phase E (per C1 backlog).
- Not Trends auto-approval. Trends require human brand-fit judgment (per B3 decision).
- Not push notifications to email/mobile. SSE channel extension only.
- Not staleness scoring on article write. Detection is on-demand only.
- Not Pillars-as-a-view (Pi-B decision, filter dimension only).
- Not bulk operations on Trends/Gaps. Single-item actions only. Bulk is Phase E.

### A.2 Runtime cron toggle (Q-A: A2)

Backend cron infrastructure currently requires worker restart to toggle. We need runtime control per-project.

**Pattern**: Worker watches a `cron_state` table for active cron configurations.

```sql
-- packages/db/src/schema/cron.ts (new)
CREATE TABLE cron_state (
  id UUID PRIMARY KEY,
  project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
  job_type TEXT NOT NULL CHECK (job_type IN ('trends_synthesizer', 'refresh_detector')),
  is_active BOOLEAN DEFAULT FALSE,
  cron_pattern TEXT NOT NULL,  -- e.g. "30 1 * * *"
  last_run_at TIMESTAMP,
  last_run_status TEXT,
  last_run_error TEXT,
  next_run_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  UNIQUE(project_id, job_type)
);

CREATE INDEX idx_cron_state_active ON cron_state(is_active, job_type);
```

**Worker watcher pattern** (`apps/api/src/workers/cron-orchestrator.ts`):

```typescript
/**
 * Cron orchestrator watches cron_state table and synchronizes BullMQ repeating jobs.
 * Runs every 60s. Removes inactive jobs, adds new active jobs, updates patterns.
 */
async function syncCronJobs(): Promise<void> {
  const desired = await db.select().from(cronState).where(eq(cronState.isActive, true));
  
  for (const job of desired) {
    const queue = getQueue(job.jobType);
    const existingRepeats = await queue.getRepeatableJobs();
    const existing = existingRepeats.find(r => r.name === `${job.jobType}:${job.projectId}`);
    
    if (!existing || existing.pattern !== job.cronPattern) {
      // Remove old, add new
      if (existing) await queue.removeRepeatableByKey(existing.key);
      await queue.add(
        `${job.jobType}:${job.projectId}`,
        { projectId: job.projectId },
        { repeat: { pattern: job.cronPattern } }
      );
    }
  }
  
  // Remove jobs no longer in desired state
  const allRepeats = await Promise.all([
    getQueue("trends_synthesizer").getRepeatableJobs(),
    getQueue("refresh_detector").getRepeatableJobs(),
  ]).then(arrays => arrays.flat());
  
  for (const repeat of allRepeats) {
    const isWanted = desired.some(d => `${d.jobType}:${d.projectId}` === repeat.name);
    if (!isWanted) {
      const queue = getQueue(repeat.name.split(":")[0]);
      await queue.removeRepeatableByKey(repeat.key);
    }
  }
}

// Register orchestrator on worker startup
export function registerCronOrchestrator(): void {
  const queue = getQueue("cron-orchestrator");
  queue.add(
    "sync-cron-state",
    {},
    {
      repeat: { pattern: "* * * * *" },  // every minute
      removeOnComplete: true,
    }
  );
}
```

**Trigger sync on settings change**: when Settings updates `trends_cron_enabled` or `refresh_cron_enabled`, also upsert `cron_state` row immediately (no need to wait for next orchestrator tick).

### A.3 Refresh Detection pipeline (simple staleness — Q-C: C3)

New worker: `apps/api/src/workers/refresh-detector.ts`.

**Detection logic** (no LLM, pure SQL):

```typescript
/**
 * Detects articles needing refresh based on simple staleness heuristic.
 * Triggered manually via /api/projects/:slug/refresh-detection/run
 * OR via cron when trends_cron_enabled = true (orchestrated by cron-orchestrator).
 */
async function detectStaleArticles(projectId: string): Promise<RefreshDetectionResult> {
  const project = await loadProject(projectId);
  const thresholdDays = project.refreshStalenessThresholdDays ?? 90;
  const cutoff = new Date(Date.now() - thresholdDays * 24 * 60 * 60 * 1000);
  
  // Find published articles older than threshold without recent refresh
  const stale = await db.select({
    id: articles.id,
    title: articles.title,
    slug: articles.slug,
    locale: articles.locale,
    collection: articles.collection,
    clusterId: articles.clusterId,
    publishedAt: articles.publishedAt,
    updatedAt: articles.updatedAt,
    lastRefreshedAt: articles.lastRefreshedAt,
  })
    .from(articles)
    .where(and(
      eq(articles.projectId, projectId),
      eq(articles.status, "published"),
      lt(
        sql`COALESCE(${articles.lastRefreshedAt}, ${articles.publishedAt}, ${articles.updatedAt})`,
        cutoff
      ),
    ))
    .orderBy(asc(articles.lastRefreshedAt));
  
  // Auto-create briefs only if config flag enabled
  const briefsCreated: string[] = [];
  if (project.autoApproveGaps) {
    for (const article of stale) {
      const daysSinceUpdate = Math.floor(
        (Date.now() - new Date(article.updatedAt).getTime()) / (24 * 60 * 60 * 1000)
      );
      
      // Skip if brief already exists for this article in pending
      const existing = await db.select().from(topicBriefs)
        .where(and(
          eq(topicBriefs.source, "refresh_detection"),
          sql`${topicBriefs.refreshMetadata}->>'targetArticleId' = ${article.id}`,
          eq(topicBriefs.approvalStatus, "pending"),
        ))
        .limit(1);
      
      if (existing.length > 0) continue;
      
      const [brief] = await db.insert(topicBriefs).values({
        projectId,
        source: "refresh_detection",
        topicTitle: `Refresh: "${article.slug}"`,
        clusterId: article.clusterId,
        clusterAction: "refresh",
        generationMode: "refresh",
        approvalRequired: false,
        approvalStatus: "auto_approved",
        refreshMetadata: {
          targetArticleId: article.id,
          reason: "auto-detected staleness",
          staleness: {
            daysSinceLastUpdate: daysSinceUpdate,
            rankingChange: null,
            competitorRefreshed: false,
          },
        },
      }).returning();
      
      briefsCreated.push(brief.id);
    }
  }
  
  // Publish SSE event
  await publishPipelineEvent(projectId, {
    type: "refresh.detected",
    candidateCount: stale.length,
    autoApprovedCount: briefsCreated.length,
    timestamp: new Date().toISOString(),
  });
  
  return {
    projectId,
    candidateCount: stale.length,
    autoApprovedCount: briefsCreated.length,
    candidates: stale,
  };
}
```

### A.4 Auto-approval implementation (Q-B: B1 — Gaps only)

```typescript
// In existing /api/projects/:slug/content-gaps/:id/generate handler
async function handleGapGenerate(c: Context) {
  const { slug, id } = c.req.param();
  const project = await loadProjectBySlug(slug);
  if (!project) return c.json({ ok: false, error: "project_not_found" }, 404);
  
  const gap = await loadGap(id, project.id);
  if (!gap) return c.json({ ok: false, error: "gap_not_found" }, 404);
  
  // Existing logic creates brief + calls decideRoute + executeDecision
  const result = await processGapToArticle({ gap, project });
  
  return c.json({ ok: true, data: result }, 202);
}

// New: cron-driven gap auto-approval
async function autoApproveGapsForProject(projectId: string): Promise<void> {
  const project = await loadProject(projectId);
  if (!project.autoApproveGaps) return;
  
  // Find all open gaps that have suggestions populated
  const ready = await db.select().from(contentGaps)
    .where(and(
      eq(contentGaps.projectId, projectId),
      eq(contentGaps.status, "open"),
      // Has metadata.suggestedTitle (was suggested at some point)
      sql`${contentGaps.metadata}->>'suggestedTitle' IS NOT NULL`,
    ));
  
  for (const gap of ready) {
    try {
      await processGapToArticle({ gap, project });
    } catch (err) {
      log.error({ err, gapId: gap.id }, "Auto-approval failed");
    }
  }
}
```

**Trigger points for auto-approval**:
1. When a gap's `/suggest` endpoint completes AND `autoApproveGaps = true` → auto-generate immediately
2. Daily cron (separate from trends): scan for any "open + suggested" gaps and auto-generate

No new endpoint — auto-approval happens inline with existing suggest/detect flows.

```vue
    trend: { type: Object as PropType<TopicBrief>, required: true },

      if (score >= 40) return "score-medium";

    },
  },
```

### D.4 useClusterGaps composable

```typescript
// apps/web/src/composables/useClusterGaps.ts
export function useClusterGaps(clusterId: string) {
  const route = useRoute();
  const queryClient = useQueryClient();
  const slug = route.params.slug as string;
  
  const { data, isLoading, refetch } = useQuery({
    queryKey: ["content-gaps", slug, clusterId],
    queryFn: () => apiGet(`/api/projects/${slug}/content-gaps`, { clusterId, status: "open" }),
  });
  
  const gaps = computed(() => data.value?.gaps ?? []);
  
  const detecting = ref(false);
  const detectGaps = async () => {
    detecting.value = true;
    try {
      await apiPost(`/api/projects/${slug}/clusters/${clusterId}/detect-gaps`);
      await refetch();
    } finally {
      detecting.value = false;
    }
  };
  
  const suggestGap = async (gapId: string) => {
    await apiPost(`/api/projects/${slug}/content-gaps/${gapId}/suggest`);
    await refetch();
  };
  
  const generateGap = async (gapId: string) => {
    await apiPost(`/api/projects/${slug}/content-gaps/${gapId}/generate`);
    await refetch();
    queryClient.invalidateQueries({ queryKey: ["cluster-generation-status", clusterId] });
  };
  
  const dismissGap = async (gapId: string) => {
    await apiPatch(`/api/projects/${slug}/content-gaps/${gapId}`, { status: "dismissed" });
    await refetch();
  };
  
  return {
    gaps,
    detecting,
    isLoading,
    detectGaps,
    suggestGap,
    generateGap,
    dismissGap,
  };
}
```

**Backend addition needed**: `POST /api/projects/:slug/clusters/:id/detect-gaps` — currently this is internal. Make it public-callable.

### E.5 useRefreshCandidates composable

Standard infinite-query composable per 56.2 pattern:

```typescript
export function useRefreshCandidates() {
  const projectStore = useProjectStore();
  
  const query = useInfiniteQuery({
    queryKey: computed(() => ["refresh-candidates", projectStore.currentSlug]),
    queryFn: ({ pageParam }) => apiGet(
      `/api/projects/${projectStore.currentSlug}/refresh-candidates`,
      { cursor: pageParam, limit: 20 }
    ),
    initialPageParam: undefined as string | undefined,
    getNextPageParam: (lastPage) => lastPage.data.nextCursor ?? undefined,
  });
  
  return {
    candidates: computed(() => query.data.value?.pages.flatMap(p => p.data.candidates) ?? []),
    hasMore: computed(() => !!query.data.value?.pages[query.data.value.pages.length - 1]?.data.hasMore),
    isLoading: query.isLoading,
    isFetchingMore: query.isFetchingNextPage,
    loadMore: query.fetchNextPage,
    refetch: query.refetch,
  };
}
```

## Decisions Made

**Decision 1: Runtime cron toggle via cron_state table (Q-A: A2).**
Frontend toggle has real backend effect. Worker orchestrator watches table every 60s. Per-project cron schedules. Worth the complexity since user explicitly chose A2 (complete implementation over speed).

**Decision 2: Auto-approval for Gaps only (Q-B: B1 + B3 hybrid).**
Implementation supports auto-approval flag. Default off. Marcel enables in Settings when comfortable. Only applies to Gaps (low-risk, cluster-bound context). Trends remain manual-approval-only (need brand-fit judgment).

**Decision 3: Refresh Detection as simple SQL heuristic (Q-C: C3).**
`daysSinceLastUpdate > project.refreshStalenessThresholdDays`. No LLM. No ranking-change detection. Per-project threshold default 90 days. Phase E adds LLM-based content-quality analysis.

**Decision 4: SSE extension for discovery events (Q-D: D1).**
3 new event types: trends.discovered, gaps.detected, refresh.detected. Frontend invalidates relevant query caches. Sidebar badges update live.

**Decision 5: No Pillars view (Pi-B).**
Pillars remain filter dimension in Clusters/Articles. Phase E if explicit need emerges.

**Decision 6: refresh_dismissed table for sticky dismissals.**
Once Marcel dismisses an article from refresh queue, it stays dismissed until manually un-dismissed via API. Prevents re-appearing on every detection run.

**Decision 7: Manual trigger always available regardless of cron.**
Both trends + refresh have manual "Run Now" buttons in Settings + their respective views. Cron is convenience, not requirement.

**Decision 8: No bulk operations in 56.6.**
Single-item approve/dismiss/generate. Bulk is Phase E pattern (already deferred from 56.2 multi-pane).

**Decision 9: Gap dismissal via PATCH status, not DELETE.**
Existing pattern from `/content-gaps/:id` PATCH endpoint. Keeps soft-delete semantics.

**Decision 10: ArticleCard shows StalenessBadge inline (per Q6 b+c).**
Plus eigene RefreshQueue view. Two surfaces for same data — RefreshQueue is "all stale articles", ArticleCard badge is "this specific article is stale".

**Decision 11: Discovery section in sidebar between Content and Platform.**
Mental model: Discovery (input) → Content (output) → Platform (config). Trends + Refresh Queue + Gaps-context-in-Cluster.

**Decision 12: TrendCard shows top 3 signals + overflow.**
Avoids card height explosion when signal count varies (1-15+).

**Decision 13: Manual sync after Settings toggle save.**
Backend PATCH to project also writes to cron_state. Frontend doesn't need separate call.

**Decision 14: 60s orchestrator sync interval.**
Balance between responsiveness (user expects toggle to "just work") and DB load. 60s is reasonable for user-driven settings changes (not real-time critical).

**Decision 15: refresh_staleness_threshold_days range 7-365.**
Below 7 days is unrealistic (article hasn't settled). Above 365 is functionally "never refresh". Validates on backend + frontend.

## Discovered During Implementation

**Sessions 1–2:**

- `articles.lastRefreshedAt` does not exist on the articles table (never added by spec 54.10). All refresh staleness detection uses `COALESCE(publishedAt, updatedAt)` instead. The spec's detection query referenced this column as if it existed.

- `cronJobTypeEnum` defined inline in `packages/db/src/schema/cron.ts` rather than `_enums.ts`. Acceptable because the enum is only referenced by `cron_state`; moving it to `_enums.ts` would require importing it back from there without benefit.

- Excluding dismissed articles from detection/list queries requires a **LEFT JOIN + `isNull(joinedTable.id)`** pattern — not a subquery passed to `isNull()`. The subquery form compiles but produces wrong SQL. Canonical location: `refresh.ts` and `refresh-detector.ts`.

- `INTERVAL` with a per-project dynamic value (e.g. 90 days) cannot use Drizzle parameter binding — use `sql.raw(String(n))` inside the template literal: `INTERVAL '${sql.raw(String(thresholdDays))} days'`. Bare interpolation fails because postgres.js receives the value as a bind parameter, not inline SQL.

- `detectStaleArticles()` is shared between the worker (BullMQ job) and the HTTP route (`POST /refresh-detection/run`). Export it from the worker file; the route imports it directly. This avoids duplicating the detection logic.
