# Spec 54.7: Cluster Creator

**Phase:** 54 / C — Cluster Creator & Generator Modes (1 of 2)
**Estimated Effort:** 2.5–3 days (~18-20 focused hours across 5 sessions)
**Dependencies:** Spec 54.0 (ADR), 54.2 (Project Config + cornerstone_specs), 54.3 (Routing Policy), 54.5 (clusters.embedding column + trend_discovery briefs), 54.6 (UI infrastructure)
**Status:** Ready for implementation
**Recommended Model:** Opus 4.7 (LLM-prompt-heavy spec — cluster proposal generation is high-leverage)

---

## Goal

Unblock all `cluster_action='create_new'` briefs by building the **Cluster Creator** — an LLM-assisted preview-and-approve flow that turns a pending brief into a new cluster with cornerstone_spec, lazy-backfills missing cluster embeddings (to prevent false `create_new` decisions), and auto-routes the originating brief through the existing pipeline.

This is the spec that turns Phase B's queue of `create_new` briefs into actual articles. After 54.7 lands, Marcel can take a trend brief like "Codex: OpenAIs Coding-Agent erobert die Unternehmen" → review an LLM-proposed cluster (name, primary keyword, pillar cornerstone_spec, intent taxonomy) → edit if needed → click "Create & Generate" → cluster + cornerstone_spec are persisted, the originating brief is auto-approved, the spoke article gets queued through `/automate`.

Spec 54.7 delivers:

1. **Cluster lazy-backfill** integrated into `findMatchingCluster` — clusters with `embedding IS NULL` get embeddings computed on-demand, persisted, and used for matching. Fixes the false-`create_new` problem from 54.5's deviation.
2. **Cluster proposal LLM** — given a brief, propose cluster shape (name, primary keyword, intent taxonomy override, pillar cornerstone_spec content). One Anthropic Opus call per cluster-create attempt.
3. **Cluster Creator route** — Quasar page at `/projects/:slug/clusters/new?fromBrief=:id` showing the LLM proposal with editable form fields and a single "Create & Generate" CTA.
4. **Backend endpoints**:
  - `POST /projects/:slug/clusters/propose` — generates a fresh proposal for a brief (LLM call)
  - `POST /projects/:slug/clusters/create-from-brief` — atomically creates cluster + cornerstone_spec + auto-approves brief + routes spoke
5. **Routing policy extension** — `executeDecision` learns to handle `kind: 'create_cluster'` (currently throws `RoutingNotImplementedError`). Behavior: it's only reachable through the new endpoint; the legacy `/automate` route still rejects `create_cluster` with 400 (manual approval required).
6. **UI integration in `TrendBriefDetail.vue`** — `create_new` briefs no longer show disabled approve button. Instead, primary CTA is "Create Cluster & Generate" → navigates to the new route. Approve & Generate / Approve & Queue for `append_to_existing` briefs remain unchanged.

After deploy:
- The two currently-pending `create_new` briefs (RAG-Tools, Codex) become approvable through the Cluster Creator
- Every existing cluster gets a lazy embedding on first synthesis run, fixing future trend briefs to find matches instead of always emitting `create_new`
- Cornerstone specs created via Cluster Creator flow into the existing cornerstone approval pipeline (per 54.2)

## What this is NOT

- Not the full automated cluster creation flow (decision Q1's option a). Per user direction (Q1c): LLM proposes, Marcel reviews, single confirm. No fully-automated path.
- Not implementing **Cluster Creator from scratch** (without a brief origin). Per user direction (Q7b): the route is `/clusters/new?fromBrief=<id>`. From-scratch creation (no brief) is a future spec, possibly part of 54.9 UI redesign. Until then, Marcel can only create clusters in response to a `create_new` brief.
- Not building **Generator Modes** (refresh, translation handling) — that's 54.8.
- Not auto-merging similar `create_new` briefs (decision Q8). The deduplication is **sequential**: first create_new brief becomes a cluster; subsequent briefs that match (via embedding) get re-routed automatically by the existing `findMatchingCluster` logic in 54.5. No new merge UI needed.
- Not changing the `clusters` table beyond what's needed for embeddings (column exists since 54.5).
- Not changing `cornerstone_specs` — uses existing schema, only writes via the new endpoint.
- Not handling cluster deletion or merging (out-of-scope for v1).
- Not multi-language clusters in v1. The Cluster Creator creates clusters in the project's primary language only (from `topic_scope.languages[0]`). Translation handling is 54.8.
- Not changing the existing GapsPanel or any 54.6 components beyond `TrendBriefDetail.vue`.

### The proposal LLM call

One Opus call per "view this proposal" action. The LLM gets:

- The full brief (topic_title, primary_keyword, secondary_keywords, suggested_meta, hero_image_prompt, trend_metadata)
- The full project context (intent taxonomy, language, exclusions, primary_themes, existing cluster names list)
- Marketing context for the project (existing pattern from cornerstone generation)

Returns a structured cluster proposal:

```typescript
type ClusterProposal = {
  // Cluster fields
  cluster_name: string;                    // e.g., "OpenAI Codex Enterprise"
  cluster_slug: string;                    // e.g., "openai-codex"
  primary_keyword: string;                 // e.g., "OpenAI Codex"
  description: string;                     // 1-2 sentence cluster summary
  intent_taxonomy_override: string[] | null; // e.g., ["definition","use_cases","comparison","pricing","tutorial"]
                                             // null = use project default
  language: "de" | "en";                   // primary language

  // Pillar cornerstone_spec fields
  pillar_title: string;                    // e.g., "OpenAI Codex: Der Coding-Agent für Unternehmen"
  pillar_slug: string;                     // pillar URL slug
  pillar_meta: string;                     // 50-160 chars
  pillar_hero_image_prompt: string;        // 80-800 chars
  pillar_outline: string[];                // 5-10 H2-level section titles
  pillar_target_keywords: string[];        // 3-5 secondary keywords for pillar

  // Routing hint
  spoke_intent_for_originating_brief: string;  // which intent_type the originating brief should be filed as
                                                // e.g., "review" or "use_cases" — must be in intent_taxonomy_override (or project default)

  // Reasoning (for audit, not displayed by default)
  reasoning: string;                       // why this cluster shape, why these intents
};
```

This is generated **on the fly** when Marcel navigates to the route. Not pre-computed. Re-generation possible via "Regenerate Proposal" button.

Costs: ~€0.20-0.30 per proposal (Opus, structured output, smaller context than synthesis).

### Cluster lazy-backfill (decision Q6)

Extend `findMatchingCluster` in `cluster-match.ts`:

```typescript
export async function findMatchingCluster(
  projectId: string,
  candidate: SynthesisTopicCandidate,
): Promise<ClusterMatch> {
  // BEFORE matching: lazy-backfill any clusters missing embeddings
  const clustersNeedingEmbeddings = await db
    .select({ id: clusters.id, name: clusters.name, primaryKeyword: clusters.primaryKeyword })
    .from(clusters)
    .where(and(
      eq(clusters.projectId, projectId),
      isNull(clusters.embedding),
    ));

  if (clustersNeedingEmbeddings.length > 0) {
    log.info({ count: clustersNeedingEmbeddings.length }, "lazy-backfilling cluster embeddings");
    const texts = clustersNeedingEmbeddings.map(c =>
      `${c.name}: ${c.primaryKeyword}`
    );
    const embeddings = await embedBatch(texts, { projectId, operation: "cluster-embed-backfill" });

    await db.transaction(async (tx) => {
      for (const [i, c] of clustersNeedingEmbeddings.entries()) {
        await tx.update(clusters)
          .set({ embedding: embeddings[i] })
          .where(eq(clusters.id, c.id));
      }
    });
  }

  // EXISTING matching logic continues...
}
```

Same pattern as article-embedding lazy-backfill from 54.5b. Idempotent — if all clusters already have embeddings, the SELECT returns zero rows, no API call.

**One-time cost** at synthesis time: number-of-clusters × ~15 tokens × €0.06/1M = negligible (~€0.0001 per cluster). Lifetime fix for all future synthesis runs.

### Backend endpoint: propose

`POST /projects/:slug/clusters/propose`

Body: `{ fromBriefId: string }`

Flow:
1. Validate brief exists, belongs to project, has `cluster_action='create_new'`, status=`pending`
2. Load brief + project config + existing cluster names
3. Call cluster proposal LLM
4. Return `ClusterProposal` JSON

Idempotency: each call generates fresh proposal. Marcel can hit "Regenerate" to get a different angle. Cost ~€0.20 per call.

### Backend endpoint: create-from-brief

`POST /projects/:slug/clusters/create-from-brief`

Body:
```typescript
{
  fromBriefId: string,
  proposal: ClusterProposal,         // possibly edited by Marcel
  generateMode: 'queue' | 'now',     // matches Approve flow from 54.6
}
```

Flow (all in one transaction):

```
1. Validate brief still pending + create_new
2. Insert clusters row:
     - name, slug, primary_keyword from proposal
     - intent_taxonomy_override (if set)
     - description, language
     - embedding: computed inline from "${name}: ${primary_keyword}" (no lazy-backfill needed)

3. Insert cornerstone_specs row (using existing schema from Phase A):
     - cluster_id = newly created cluster.id
     - title, slug, meta, hero_image_prompt, target_keywords from proposal
     - outline = JSON-stringified proposal.pillar_outline
     - approval_status = 'pending' (existing cornerstone flow still requires approval)

4. Update brief:
     - approval_status = 'approved'
     - cluster_id = newly created cluster.id
     - cluster_action stays 'create_new' (audit trail of where it came from)
     - intent_type = proposal.spoke_intent_for_originating_brief

5. Call existing routing policy executeDecision({ kind: 'create_article', clusterId, mode: queue|now }, brief, tx)
     - Brief's spoke article enters /automate or /generate path

6. Return:
     {
       clusterId,
       cornerstoneSpecId,
       briefStatus: 'approved',
       routedArticleId | routedChainId
     }
```

The entire chain is atomic. If any step fails, transaction rolls back — no half-created clusters.

### Routing policy: create_cluster handler

In `packages/pipelines/src/routing/execute.ts`, the `executeDecision` switch currently has:

```typescript
case "create_cluster":
  throw new RoutingNotImplementedError(
    "create_cluster decisions require the Cluster Creator UI (54.7)"
  );
```

After 54.7, this stays exactly the same. The Cluster Creator endpoint does NOT route through `executeDecision({ kind: 'create_cluster' })`. Instead, the endpoint orchestrates the cluster+spec creation itself, then calls `executeDecision({ kind: 'create_article', clusterId, mode })` for the spoke article.

Why this split: `create_cluster` as a decision kind was always a "this needs human input" placeholder. The UI flow IS the human input. Once cluster exists, only `create_article` decisions happen — the existing flow handles them.

**The `executeDecision` `create_cluster` branch keeping the error means**: any legacy `/automate` call with a `create_new` brief still gets a clear error directing to the new flow. That's correct guardrail behavior.

### Step 1 form: ClusterShapeForm

Fields:
- `cluster_name` — text input, 2-100 chars
- `cluster_slug` — text input, regex validation, auto-derived from name by default with manual override
- `primary_keyword` — text input, 2-100 chars
- `description` — textarea, max 500 chars
- `intent_taxonomy_override` — multi-select chip-input. Pre-filled from proposal. Options: project's default taxonomy + any custom user-added. Marcel can add new ones or remove.
- `language` — read-only (matches project primary)

### Step 2 form: PillarSpecForm

Fields:
- `pillar_title` — text input, 10-200 chars
- `pillar_slug` — text input, regex validation
- `pillar_meta` — textarea, 50-160 chars, character counter
- `pillar_hero_image_prompt` — textarea, 80-800 chars, character counter
- `pillar_outline` — drag-orderable list of section titles, each 5-150 chars, 5-10 items required
- `pillar_target_keywords` — chip-input, 3-5 keywords

### Step 3: ClusterCreateConfirm

Summary view:
- Cluster summary (name, slug, primary keyword, intents)
- Pillar summary (title, slug, meta, outline preview)
- Originating brief summary (with the routed spoke intent highlighted)
- Generation mode selector: "Queue (recommended)" vs "Generate Now"
- Big "Create & Generate" button → calls create-from-brief endpoint

On success: navigation to `/projects/<slug>/articles/<newSpokeArticleId>` (if generate=now) or `/projects/<slug>/trends?tab=pending` (if queue).

### Backend route skeleton

`apps/api/src/routes/projects/clusters.ts`:

```typescript
import { Hono } from "hono";
import { z } from "zod";
import { and, eq } from "@marketing-auto/db";
import { db, clusters, cornerstoneSpecs, topicBriefs } from "@marketing-auto/db";
import { proposeCluster } from "@marketing-auto/pipelines/cluster-creator";
import { executeDecision } from "@marketing-auto/pipelines/routing";
import { embedBatch } from "@marketing-auto/adapter-voyage";

const clustersRoute = new Hono();

clustersRoute.post("/propose", async (c) => {
  const projectId = c.get("projectId");
  const { fromBriefId } = await c.req.json();

  const [brief] = await db.select().from(topicBriefs)
    .where(and(
      eq(topicBriefs.id, fromBriefId),
      eq(topicBriefs.projectId, projectId),
    ))
    .limit(1);

  if (!brief) return c.json({ error: "Brief not found" }, 404);
  if (brief.clusterAction !== "create_new") {
    return c.json({ error: "Brief does not have cluster_action=create_new" }, 400);
  }
  if (brief.approvalStatus !== "pending") {
    return c.json({ error: "Brief is no longer pending" }, 400);
  }

  const proposal = await proposeCluster({
    projectId,
    brief,
  });

  return c.json({ proposal });
});

clustersRoute.post("/create-from-brief", async (c) => {
  const projectId = c.get("projectId");
  const body = await c.req.json();
  // ... parse + validate proposal via Zod

  const result = await db.transaction(async (tx) => {
    // 1. Re-fetch brief inside tx
    const [brief] = await tx.select().from(topicBriefs)
      .where(and(
        eq(topicBriefs.id, body.fromBriefId),
        eq(topicBriefs.projectId, projectId),
        eq(topicBriefs.approvalStatus, "pending"),
      ))
      .limit(1);
    if (!brief) throw new Error("Brief no longer pending");

    // 2. Compute cluster embedding
    const [embedding] = await embedBatch(
      [`${body.proposal.cluster_name}: ${body.proposal.primary_keyword}`],
      { projectId, operation: "cluster-create-embed" }
    );

    // 3. Insert cluster
    const [cluster] = await tx.insert(clusters).values({
      projectId,
      name: body.proposal.cluster_name,
      slug: body.proposal.cluster_slug,
      primaryKeyword: body.proposal.primary_keyword,
      description: body.proposal.description,
      intentTaxonomyOverride: body.proposal.intent_taxonomy_override,
      language: body.proposal.language,
      embedding,
    }).returning();

    // 4. Insert cornerstone_spec
    const [spec] = await tx.insert(cornerstoneSpecs).values({
      projectId,
      clusterId: cluster.id,
      title: body.proposal.pillar_title,
      slug: body.proposal.pillar_slug,
      meta: body.proposal.pillar_meta,
      heroImagePrompt: body.proposal.pillar_hero_image_prompt,
      outline: body.proposal.pillar_outline,
      targetKeywords: body.proposal.pillar_target_keywords,
      approvalStatus: "pending",
    }).returning();

    // 5. Update brief
    await tx.update(topicBriefs)
      .set({
        approvalStatus: "approved",
        clusterId: cluster.id,
        intentType: body.proposal.spoke_intent_for_originating_brief,
      })
      .where(eq(topicBriefs.id, brief.id));

    // 6. Route the spoke article
    const routingResult = await executeDecision(
      {
        kind: "create_article",
        clusterId: cluster.id,
        intentType: body.proposal.spoke_intent_for_originating_brief,
        mode: body.generateMode === "now" ? "generate" : "queue",
      },
      { ...brief, clusterId: cluster.id, intentType: body.proposal.spoke_intent_for_originating_brief },
      tx,
    );

    return {
      clusterId: cluster.id,
      cornerstoneSpecId: spec.id,
      briefStatus: "approved",
      ...routingResult,
    };
  });

  return c.json(result);
});

export default clustersRoute;
```

### Cluster lazy-backfill integration

`packages/pipelines/src/topic-sources/trend-discovery/cluster-match.ts`:

```typescript
import { and, eq, isNull } from "@marketing-auto/db";
import { db, clusters } from "@marketing-auto/db";
import { embedBatch } from "@marketing-auto/adapter-voyage";
import { createLogger } from "@marketing-auto/shared";

const log = createLogger("cluster-match");

export async function findMatchingCluster(
  projectId: string,
  candidate: SynthesisTopicCandidate,
): Promise<ClusterMatch> {
  // Lazy-backfill any clusters missing embeddings
  await backfillMissingClusterEmbeddings(projectId);

  // Existing matching logic (cosine similarity against clusters.embedding)
  // ...
}

async function backfillMissingClusterEmbeddings(projectId: string): Promise<void> {
  const needsBackfill = await db
    .select({
      id: clusters.id,
      name: clusters.name,
      primaryKeyword: clusters.primaryKeyword,
    })
    .from(clusters)
    .where(and(
      eq(clusters.projectId, projectId),
      isNull(clusters.embedding),
    ));

  if (needsBackfill.length === 0) return;

  log.info({ count: needsBackfill.length }, "lazy-backfilling cluster embeddings");

  // Batch embed (Voyage supports up to 128 per call)
  const texts = needsBackfill.map((c) => `${c.name}: ${c.primaryKeyword}`);
  const embeddings = await embedBatch(texts, {
    projectId,
    operation: "cluster-embed-backfill",
  });

  await db.transaction(async (tx) => {
    for (const [i, c] of needsBackfill.entries()) {
      await tx.update(clusters)
        .set({ embedding: embeddings[i] })
        .where(eq(clusters.id, c.id));
    }
  });
}
```

This runs on every synthesis call but is idempotent — after first run, all clusters have embeddings, future calls return zero from the SELECT.

## Open Questions / Decisions Made

**Decision 1: Hybrid trigger model (LLM proposes, Marcel reviews+confirms).**
Per user direction (Q1c). Single Opus call generates proposal; Marcel can edit any field; one atomic create. Avoids both blackbox automation and excessive clicking.

**Decision 2: Pillar always created with cluster.**
Per user direction (Q2a). Hub-Spoke architecture requires the hub. No orphan clusters.

**Decision 3: Pillar implemented as cornerstone_spec, not article.**
Per user direction (Q3c). Reuses existing Phase A cornerstone flow. Spec created with `approval_status=pending`; Marcel approves separately for actual article generation. This separation respects the existing cornerstone approval discipline (cornerstones are strategic; need explicit human review beyond the cluster-creation moment).

**Decision 4: LLM proposes intent taxonomy, Marcel edits via chip input.**
Per user direction (Q4b). LLM understands topical area + recommends intent fit. Marcel can override if domain knowledge differs. Stored as `intent_taxonomy_override` per cluster (from 54.2 schema).

**Decision 5: Originating brief is auto-approved as spoke in new cluster.**
Per user direction (Q5a). Single intention from Marcel ("create cluster for this brief") triggers full chain. No double-confirmation.

**Decision 6: Cluster lazy-backfill in this spec.**
Per user direction (Q6a). Without backfill, all future trend briefs would still emit `create_new` against clusters that exist but lack embeddings. Self-defeating.

**Decision 7: Own route, not modal.**
Per user direction (Q7b). Three-step stepper is substantial UI; modal would feel cramped. Browser-back-navigation works naturally. Future from-scratch flow reuses route.

**Decision 8: Sequential conflict resolution (no merge UI).**
Per user direction (Q8b). First create_new brief → cluster exists. Subsequent matching briefs → `findMatchingCluster` finds the new cluster → routes as `append_to_existing`. Natural deduplication via existing logic.

**Decision 9: Proposal is generated on-demand, not pre-computed.**
Briefs don't carry stored proposals. When Marcel opens Cluster Creator, fresh proposal generated. Regenerate button re-triggers. Avoids stale proposal data and lets project context evolve between brief creation and cluster decision.

**Decision 10: Generate mode (queue/now) is per-cluster-create, not per-brief setting.**
Marcel chooses at the Cluster Creator confirm step. Default is "Queue" (consistent with TrendBriefDetail's default in 54.6).

**Decision 11: Cluster Creator only reachable from trend brief in v1.**
No from-scratch cluster creation. The route requires `?fromBrief=<id>`. From-scratch flow tracked in POST-54-BACKLOG.

**Decision 12: Single language per cluster (project primary).**
No multilingual clusters in v1. Translation handling is 54.8 (which produces `cluster_action='translation'` decisions).

**Decision 13: executeDecision retains its `create_cluster` error path.**
The error case is a guardrail for legacy callers (e.g., /automate route directly fed a create_new brief). Cluster Creator orchestrates directly without going through that decision kind. The error path being unreachable in normal flow is fine — it remains for defensive correctness.

**Decision 14: Reasoning field in proposal is stored but not displayed by default.**
Audit trail. Could be surfaced in a "Why this proposal?" tooltip in 54.9 redesign.

**Decision 15: Three-step stepper for clarity, not one big form.**
Each step represents a coherent decision: shape (what), content (how), confirm (when). One big form would overwhelm.
