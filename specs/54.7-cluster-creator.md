**Dependencies:** Spec 54.0 (ADR), 54.2 (Project Config + cornerstone_specs), 54.3 (Routing Policy), 54.5 (clusters.embedding column + trend_discovery briefs), 54.6 (UI infrastructure)

## Goal

Unblock all `cluster_action='create_new'` briefs by building the **Cluster Creator** — an LLM-assisted preview-and-approve flow that turns a pending brief into a new cluster with cornerstone_spec, lazy-backfills missing cluster embeddings (to prevent false `create_new` decisions), and auto-routes the originating brief through the existing pipeline.

This is the spec that turns Phase B's queue of `create_new` briefs into actual articles. After 54.7 lands, Marcel can take a trend brief like "Codex: OpenAIs Coding-Agent erobert die Unternehmen" → review an LLM-proposed cluster (name, primary keyword, pillar cornerstone_spec, intent taxonomy) → edit if needed → click "Create & Generate" → cluster + cornerstone_spec are persisted, the originating brief is auto-approved, the spoke article gets queued through the existing pipeline.

Spec 54.7 delivers:

1. **Cluster lazy-backfill** integrated into `findMatchingCluster` — clusters with `embedding IS NULL` get embeddings computed on-demand, persisted, and used for matching. Fixes the false-`create_new` problem from 54.5's deviation.
2. **Cluster proposal LLM** — given a brief, propose cluster shape (name, primary keyword, intent taxonomy override, pillar cornerstone_spec content). One Anthropic Opus call per cluster-create attempt.
3. **Cluster Creator route** — Quasar page at `/projects/:slug/clusters/new?fromBrief=:id` showing the LLM proposal with editable form fields and a single "Create & Generate" CTA.
4. **Backend endpoints**:
  - `POST /projects/:slug/clusters/propose` — generates a fresh proposal for a brief (LLM call)
  - `POST /projects/:slug/clusters/create-from-brief` — atomically creates cluster + cornerstone_spec + auto-approves brief + routes spoke
5. **Routing policy**: `executeDecision` `create_cluster` error path left unchanged — Cluster Creator orchestrates directly, then calls `executeDecision({ kind: 'create_article' })` for the spoke.
6. **UI integration in `TrendBriefDetail.vue`** — `create_new` briefs no longer show disabled approve button. Instead, primary CTA is "Create Cluster & Generate" → navigates to the new route.

After deploy:
- The pending `create_new` briefs become approvable through the Cluster Creator
- Every existing cluster gets a lazy embedding on first synthesis run, fixing future trend briefs to find matches instead of always emitting `create_new`
- Cornerstone specs created via Cluster Creator flow into the existing cornerstone approval pipeline (per 54.2)

## What this is NOT

- Not the full automated cluster creation flow. Per user direction (Q1c): LLM proposes, Marcel reviews, single confirm. No fully-automated path.
- Not implementing **Cluster Creator from scratch** (without a brief origin). The route is `/clusters/new?fromBrief=<id>`. From-scratch creation is a future spec.
- Not building **Generator Modes** (refresh, translation handling) — that's 54.8.
- Not multi-language clusters in v1. Creates clusters in the project's primary language only (from `topic_scope.languages[0]`).

## Architecture

### Decision flow (from user choices)

```
1. Trigger model: (c) Hybrid — LLM proposes, Marcel reviews+edits, atomic create
2. Pillar gen:    (a) Always — cluster without pillar is illogical
3. Pillar writer: (c) Cornerstone spec — reuse Phase A cornerstone flow
4. Intent taxonomy: (b) LLM proposes, Marcel edits via form
5. Trend brief fate: (a) Auto-approve as spoke article in new cluster
6. Lazy backfill: (a) Yes (was already done — see Discoveries)
7. UI:           (b) Own route /clusters/new?fromBrief=<id>
8. Conflicts:    (b) Sequential — second matching brief becomes append_to_existing
```

### The proposal LLM call

One Opus call per "view this proposal" action (justification: open-ended strategic proposal — cluster shape, pillar structure, intent taxonomy — requires multi-step reasoning; Sonnet produced low-quality cluster names). The LLM gets:

- The full brief (topic_title, primary_keyword, secondary_keywords, suggested_meta, trend_metadata)
- The project config (intent taxonomy, language, existing cluster names)

Returns a structured cluster proposal — **pruned from spec** (see Deviations):

```typescript
type ClusterProposal = {
  // Maps to contentPillars row
  cluster_name: string;
  primary_keyword: string;
  description: string;
  intent_taxonomy_override: string[] | null;   // null = use project default

  // Maps to cornerstoneSpecs row
  pillar_title: string;
  pillar_slug: string;
  pillar_meta: string;
  pillar_outline: string[];                     // 5-10 H2-level section titles

  // Routing hint
  spoke_intent_for_originating_brief: string;  // must be in intent_taxonomy_override or project default

  // Audit
  reasoning: string;
};
```

Costs: ~€0.20-0.30 per proposal (Opus, structured output, `estimatedCostEur: 0.25`).

### Cluster lazy-backfill

`backfillClusterEmbeddings()` was **already implemented** in `cluster-match.ts` before this spec started (see Discoveries section). No code change required for deliverable #1.

### Transaction structure (create-from-brief)

The atomic transaction creates four rows in order:

```
1. contentPillars  { projectId, name, description, intentTaxonomyOverride }
2. clusters        { projectId, pillarId, name, primaryKeyword }
   ↓ (embedding set via raw SQL UPDATE outside tx — Voyage is external API)
3. cornerstoneSpecs { projectId, clusterId, locale, translationKey, cornerstoneKeyword,
                      proposedTitle, proposedSlug, metaDescription, h2Outline,
                      estimatedWordCount: 2000, status: 'proposed' }
4. topicBriefs     SET approvalStatus='approved', clusterId, intentType
5. executeDecision({ kind: 'create_article', clusterId, intentType, mode: 'spoke' }, brief, tx)
```

The embedding is computed **before** opening the transaction (Voyage is an external API, cannot be inside a DB transaction). Inserted into the cluster via raw SQL `UPDATE ... SET embedding = ${JSON.stringify(vec)}::vector`.

### Backend endpoints

`apps/api/src/routes/projects/clusters.ts` — registered at `/api/projects` in `server.ts`:

**`POST /:slug/clusters/propose`**
- Auth: `requireAuth`
- Body: `{ fromBriefId: string }` (Zod validated)
- Validates: project exists, brief is `create_new` + `pending`
- Calls `proposeCluster({ projectId, brief })`
- Also calls `loadActiveConfig(proj.id)` (free — 60s cache hit) to return `projectDefaultIntents` alongside the proposal
- Returns: `{ ok: true, data: { proposal: ClusterProposal, projectDefaultIntents: string[] } }`

**`POST /:slug/clusters/create-from-brief`**
- Auth: `requireAuth`
- Body: `{ fromBriefId, proposal: ClusterProposal, generateMode: 'queue' | 'now' }` (Zod validated with `ClusterProposalSchema`)
- Re-verifies brief is still pending inside transaction
- Full atomic transaction (see above)
- Post-transaction: `triggerWithPreRunId` for article:outline pipeline if `generateMode='now'`
- Returns: `{ ok: true, data: { clusterId, articleId: string | null } }`

### ClusterCreatorPage

Three-step `q-stepper` shell at `/projects/:slug/clusters/new`:
- `created()`: extracts `fromBriefId` from `$route.query['fromBrief']` (array-safe: `Array.isArray(raw) ? raw[0] ?? '' : raw ?? ''`)
- On mount: calls `/propose`, populates `proposal` and `projectDefaultIntents`
- "Regenerate Proposal" button re-calls `loadProposal()`
- Navigation to article detail (if `generateMode=now` and `articleId` returned) or `/projects/:slug/trends?tab=pending` (queue)

**Step 1 — ClusterShapeForm:** cluster_name, primary_keyword, description, intent taxonomy chip-input (with `useProjectDefault` checkbox), spoke_intent q-select.

**Step 2 — PillarSpecForm:** pillar_title (auto-derives slug via `slugify()` handling German umlauts), pillar_slug, pillar_meta (with char counter), pillar_outline drag-reorder (native HTML5 drag-and-drop events).

**Step 3 — ClusterCreateConfirm:** cluster summary card, pillar summary card (outline `<ol>`), brief summary, `q-btn-toggle` for generate mode, "Create & Generate" button.

### TrendBriefDetail.vue update

For `clusterAction === 'create_new'`: removed disabled banner + disabled approve buttons. Replaced with a single "Create Cluster & Generate" CTA that calls `goToClusterCreator()` → `$router.push({ name: 'cluster-creator', params: { slug: projectSlug }, query: { fromBrief: brief.id } })`.

## Discovered During Implementation

1. **`backfillClusterEmbeddings()` was already implemented.** `cluster-match.ts` already contained the lazy-backfill logic and `findMatchingCluster` already called it. Deliverable #1 required zero code changes.

2. **`execute-decision.ts` not `execute.ts`.** The spec referenced `packages/pipelines/src/routing/execute.ts` but the actual file is `execute-decision.ts`. The `RoutingNotImplementedError` for `create_cluster` was already correct.

3. **`routes/projects/` directory did not exist.** Created new subdirectory `apps/api/src/routes/projects/` for the new project-scoped route file.

4. **Route registered in `server.ts`, not `routes/index.ts`.** The spec said to modify `routes/index.ts` but the codebase pattern is `app.route(...)` in `server.ts`. Registered there instead.

5. **`ClusterProposalSchema` needed a mutable copy before correction.** Zod output is readonly by default. The `spoke_intent` correction had to use `const proposal = { ...parsed.data }` before mutating — direct mutation of `parsed.data` fails under strict mode.

## Deviations

### 1. `ClusterProposal` type pruned (4 fields removed)

The spec's `ClusterProposal` included fields with no matching DB columns:

| Spec field | Actual DB | Resolution |
|---|---|---|
| `cluster_slug` | No `slug` column on `clusters` | Removed |
| `language` | No `language` column on `clusters` | Removed; locale derived from `topicScope.languages[0]` |
| `pillar_hero_image_prompt` | No column in `cornerstoneSpecs` | Removed |
| `pillar_target_keywords` | No column in `cornerstoneSpecs` | Removed |

### 2. `contentPillars` row auto-created (spec never mentioned this)

`clusters.pillarId` is `NOT NULL` FK to `content_pillars`. The spec's backend skeleton never created a `contentPillars` row, which would have made the cluster INSERT fail at runtime. The transaction now creates a `contentPillars` row first and uses its ID for `clusters.pillarId`. This is architecturally correct: each new topical cluster IS its own pillar grouping.

### 3. `cornerstoneSpecs` field names differ from spec skeleton

Spec's INSERT skeleton used wrong column names. Actual mapping:

| Spec skeleton field | Actual DB column |
|---|---|
| `title` | `proposedTitle` |
| `slug` | `proposedSlug` |
| `meta` | `metaDescription` |
| `outline` | `h2Outline` |
| `heroImagePrompt` | _(omitted — no column)_ |
| `targetKeywords` | _(omitted — no column)_ |
| `approvalStatus: 'pending'` | `status: 'proposed'` |
| _(not in spec)_ | `cornerstoneKeyword` ← `primary_keyword` |
| _(not in spec)_ | `locale` ← `topicScope.languages[0]` |
| _(not in spec)_ | `translationKey` ← `crypto.randomUUID()` |
| _(not in spec)_ | `estimatedWordCount: 2000` |

### 4. Embedding computed outside transaction

Spec's backend skeleton computed the cluster embedding inside the transaction block. Voyage AI is an external API — calling it inside a DB transaction would hold the transaction open during a network round-trip. The actual implementation computes `clusterEmbedding` before `db.transaction()`, then applies it via `UPDATE ... SET embedding = ${JSON.stringify(vec)}::vector` as the first statement inside the transaction.

### 5. `projectDefaultIntents` added to /propose response (caught in review)

The ClusterShapeForm's "Use project default" taxonomy toggle required the project's `intentTaxonomyDefault`. This was not in the spec's endpoint design. The `/propose` endpoint now calls `loadActiveConfig()` (60s cache — free after `proposeCluster` warms it) and returns `projectDefaultIntents` alongside the proposal. The page stores this and passes it to `ClusterShapeForm`.

### 6. PillarSpecForm validation used hardcoded German strings (caught in review)

Four Quasar rule messages in `PillarSpecForm.vue` were hardcoded German strings. Caught in `/review-task` and fixed: validation keys `pillarTitleTooShort`, `slugInvalid`, `metaTooShort`, `metaTooLong` added to both `de/clusters.ts` and `en/clusters.ts`, rules updated to use `$t()`.

### 7. SDK regeneration not performed

The spec called for OpenAPI spec regeneration and `@hey-api/openapi-ts` SDK regen after adding the two new endpoints. This was not done — the endpoints follow the same `{ ok: true, data: ... }` envelope as all others and the frontend uses direct `api.post()` Axios calls (not the generated SDK client). SDK regen is deferred.

## Open Questions / Decisions Made

**Decision 1: Hybrid trigger model (LLM proposes, Marcel reviews+confirms).**
Per user direction (Q1c). Single Opus call generates proposal; Marcel can edit any field; one atomic create.

**Decision 2: Pillar always created with cluster.**
Per user direction (Q2a). Hub-Spoke architecture requires the hub. No orphan clusters.

**Decision 3: Pillar implemented as cornerstone_spec, not article.**
Per user direction (Q3c). Reuses existing Phase A cornerstone flow. Created with `status='proposed'`; Marcel approves separately for actual article generation.

**Decision 4: LLM proposes intent taxonomy, Marcel edits via chip input.**
Per user direction (Q4b). LLM understands topical area + recommends intent fit. Marcel can override.

**Decision 5: Originating brief is auto-approved as spoke in new cluster.**
Per user direction (Q5a). Single intention from Marcel triggers full chain.

**Decision 6: Cluster lazy-backfill in this spec.**
Per user direction (Q6a). Was already done before this spec started.

**Decision 7: Own route, not modal.**
Per user direction (Q7b). Three-step stepper would feel cramped in a modal.

**Decision 8: Sequential conflict resolution (no merge UI).**
Per user direction (Q8b). First create_new brief → cluster exists. Subsequent matching briefs → `findMatchingCluster` finds the new cluster → routes as `append_to_existing`.

**Decision 9: Proposal is generated on-demand, not pre-computed.**
Regenerate button re-triggers LLM. Avoids stale proposal data.

**Decision 10: Generate mode (queue/now) chosen at Cluster Creator confirm step.**
Default is "Queue" (consistent with TrendBriefDetail's default in 54.6).

**Decision 11: Cluster Creator only reachable from trend brief in v1.**
Route requires `?fromBrief=<id>`.

**Decision 12: `executeDecision` retains its `create_cluster` error path.**
Guardrail for legacy callers. Cluster Creator orchestrates directly without going through that decision kind.
