## 1. Ziel

62.0a hat Step-Pause + Cost-Estimator + 7 Actions als Mechanik etabliert. 62.6 macht das ergonomisch nutzbar:

1. **Top-Level `/runs` Page** — Liste aller Pipeline-Runs des Projekts
2. **Run-Detail-Page `/runs/:runId`** — Step-by-Step Inspection, JSON-Editor, Step-Pause-Resolution
3. **8 Actions auf jeder pausierten Step** (7 aus 62.0a + 1 neue):
  - `approve` — Step-Output akzeptieren, Pipeline weiter
  - `edit-input` — Input editieren, Step neu ausführen
  - `edit-output` — Output editieren, weiter mit modifiziertem State
  - `edit-prompt` — Prompt-Override setzen (62.0b), Step neu ausführen
  - `abort` — Pipeline-Run cancellen, alle nachfolgenden Steps superseded
  - `promote` — Aktuellen Prompt als Project-/Global-Golden persistieren (62.0b)
  - `extract` — Extract-for-Optimization, landet in Inbox (62.0b)
  - `rerun` — **NEU:** ab diesem Step neu ausführen, nachfolgende Step-Outputs invalidieren
4. **Live-SSE-Updates** — neue Step-Pauses erscheinen sofort ohne Refresh
5. **Optimization-Request-Inbox** — Liste der via `extract` gesammelten Optimization-Requests
6. **Generic-Architektur:** UI funktioniert für jede Pipeline die step_pauses produziert, Phase 1 Filter-Default auf `PlanWeekPipeline`

**Geschätzter Aufwand:** 3-4 Tage. Größte UI-Spec von Theme 62 wegen 8 Actions + Re-run-Rollback-Mechanik + SSE.

**In Scope:**
- Pages: `/projects/:slug/runs` (Liste) + `/projects/:slug/runs/:runId` (Detail)
- Step-Card mit allen 8 Actions
- Codemirror JSON-Editor für Input/Output/Prompt
- SSE für Live-Updates
- Optimization-Request-Inbox-Page
- Re-run-from-step mit Rollback-Logic

**Out of Scope:**
- Multi-Project-Runs-View
- Run-Performance-Analytics (kommt mit Daten)
- Compare-Two-Runs side-by-side
- Bulk-Actions auf mehreren Pauses gleichzeitig
- Re-run für Pipelines außerhalb PlanWeekPipeline (Phase 2 via Followup falls nötig)

## 2. Architektur-Entscheidungen

### 2.1 Generic-by-Default

UI baut auf `pipeline_runs` + `step_pauses` Tabellen generisch auf. Filter-Dropdown im UI zeigt verfügbare Pipelines (aus existierenden runs gequeryt). **Phase 1 Default-Filter:** `pipelineName = 'planning:weekly'`. Andere Pipelines erscheinen automatisch im Dropdown sobald sie step_pauses produzieren.

### 2.2 Re-run-Rollback-Semantik

**Definition:** "Re-run from step N" heißt:
- step_pauses für steps N+1...end auf `superseded` setzen
- step_outputs in `pipeline_runs.step_outputs` JSONB ab step N+1 entfernen
- idempotency_outputs Cache-Entries für steps N...end deleten
- Pipeline-Status zurück auf `running`, current_step auf N
- BullMQ-Job re-enqueued mit prior input

**Destructive Cases mit User-Confirm:**
- Wenn nachfolgende Steps DB-Writes hatten (z.B. PersistPlanStep): explicit Warning + extra Confirm. Spec listet known-destructive Steps.
- Wenn Plan schon approved und Items enqueued: harte Warning "X items will be cancelled", Confirm-Dialog mit Item-Count.

**Safety Net:** Re-run UI-Action ist nur enabled wenn:
- Pipeline-Run-Status in (`running`, `paused`, `failed`)
- Nicht `completed` (sonst Re-run sinnlos, Re-Trigger ist die richtige Aktion)

### 2.3 SSE für Live-Updates

Bestehender `/api/projects/:slug/pipeline-events` SSE-Endpoint (aus 62.5 Discovery, scheint vorhanden) wird genutzt. Events:
- `step.paused` — neue Step-Pause erstellt
- `step.resolved` — Pause aufgelöst (durch Action)
- `run.statusChanged` — Pipeline-Status flippt (running ↔ paused ↔ completed/failed)

Frontend nutzt bestehenden `useRealtimeSync` Composable oder Variante davon.

### 2.4 Codemirror Setup

`@codemirror/lang-json` + `@codemirror/state` + `@codemirror/view` + `@codemirror/theme-one-dark` (oder match Glassmorphism). Lazy-loaded weil ~200KB Bundle-Größe. Editor-Component als shared `PipelineJsonEditor.vue`.

### 2.5 Wo lebt was?

- **Frontend:** `apps/web/src/pages/runs/`, `apps/web/src/components/runs/`, `apps/web/src/composables/runs/`
- **Backend Routes:** `apps/api/src/routes/projects/runs.ts`, `apps/api/src/routes/projects/optimization-requests.ts`
- **Pipeline-Mechanik:** lebt schon in `packages/pipelines` (62.0a). Erweitert um Re-run-Logic falls noch nicht vorhanden.

## 4. API-Endpoints

`apps/api/src/routes/projects/runs.ts`:

```ts
// GET /api/projects/:slug/runs
// Query: pipelineName?, status?, limit?, before?
// Returns: paginated list of pipeline_runs
//   { runs: [{ id, pipelineName, status, triggeredAt, completedAt?, pauseCount, currentStepName? }] }

// GET /api/projects/:slug/runs/:runId
// Returns: full run with step_outputs + pauses
//   { run: {...}, steps: [{name, index, status, input?, output?, prompt?, pause? }], pauses: [...] }

// POST /api/projects/:slug/runs/:runId/pauses/:pauseId/resolve
// Body: discriminated union per action type
//   { action: 'approve' }
//   | { action: 'edit-input', input: <json> }
//   | { action: 'edit-output', output: <json> }
//   | { action: 'edit-prompt', prompt: <string> }
//   | { action: 'abort', reason?: <string> }
//   | { action: 'promote', scope: 'project' | 'global' }
//   | { action: 'extract', note: <string> }
//   | { action: 'rerun', confirmDestructive?: boolean }
// Returns: { ok: true, runStatus: <new_status> }
```

**Rerun-Endpoint detailed flow:**

1. Pre-flight Check: ist re-run safe? (siehe §2.2)
2. Wenn destructive UND `confirmDestructive !== true`: 409 mit `{ ok: false, reason: 'destructive_confirm_needed', impact: { itemsToCancel: N, dbWritesToRevert: [...] } }`
3. Wenn safe ODER confirmed: Transaction:
  - step_pauses für nachfolgende steps → superseded
  - pipeline_runs.step_outputs ab N+1 entfernen
  - idempotency_outputs für nachfolgende steps deleten
  - planned_items / weekly_plans cleanup (wenn Re-run vor PersistPlan-Step für gleichen Plan war)
  - BullMQ job re-enqueue mit step-pointer = N
4. SSE event `run.statusChanged` firen

**Optimization-Requests Endpoint:**

```ts
// GET /api/projects/:slug/optimization-requests
// Query: status? ('open' | 'resolved' | 'dismissed'), limit?, before?
// Returns: list of step_optimization_requests with full context

// PATCH /api/projects/:slug/optimization-requests/:requestId
// Body: { status: 'resolved' | 'dismissed', note?: string }
```

## 6. Actions im Detail

### 6.1 Approve

**Trigger:** Button click  
**API:** `POST /pauses/:id/resolve` with `{action: 'approve'}`  
**Result:** Pipeline-Worker liest pause, dispatched continuation. Step-Status flippt zu `completed`, nachfolgender Step beginnt.  
**SSE:** `step.resolved` event fired.

### 6.2 Edit-Input

**Trigger:** Edit-Button → Codemirror öffnet mit current input → Save  
**Validation:** Input wird gegen `step.inputSchema` (Zod) validated bevor submit  
**API:** `POST /pauses/:id/resolve` with `{action: 'edit-input', input: <json>}`  
**Result:** Pipeline läuft Step erneut mit modifiziertem Input. NEUE step_pause wird erstellt (alte als `resolved`).  
**Implication:** Step muss replay-fähig sein. Side-Effect-Steps (z.B. PersistPlanStep) sind das normalerweise nicht — UI warnt explizit.

### 6.3 Edit-Output

**Trigger:** Edit-Button → Codemirror mit current output → Save  
**Validation:** Output gegen `step.outputSchema`  
**API:** `POST /pauses/:id/resolve` with `{action: 'edit-output', output: <json>}`  
**Result:** Step gilt als completed mit modifiziertem Output. Nachfolgende Steps nutzen den modifizierten Output.  
**Use-Case:** LLM-Output hat Halluzination, Marcel korrigiert hand.

### 6.4 Edit-Prompt

**Trigger:** Edit-Prompt-Button → Codemirror mit current prompt (resolved per 62.0b Hybrid) → Save  
**API:** `POST /pauses/:id/resolve` with `{action: 'edit-prompt', prompt: <string>}`  
**Result:** Step neu ausgeführt mit Prompt-Override. NEUE step_pause.  
**Note:** Prompt-Override gilt nur für diesen Run, wird nicht persistiert. Wenn Marcel das Ergebnis behalten will → danach `promote`.

### 6.5 Abort

**Trigger:** Abort-Button + Confirm-Dialog  
**API:** `POST /pauses/:id/resolve` with `{action: 'abort', reason?: 'string'}`  
**Result:** Run-Status → `failed`. Alle nachfolgenden step_pauses → superseded. BullMQ-Job cancelled.  
**SSE:** `run.statusChanged` → failed.

### 6.6 Promote

**Trigger:** Promote-Dropdown → "Promote to Project Golden" / "Promote to Global Golden" → Confirm  
**API:** `POST /pauses/:id/resolve` with `{action: 'promote', scope: 'project' | 'global'}`  
**Result:** Aktueller Prompt (potentially edited via §6.4) wird in `prompt_versions` als `is_golden=true` persistiert (62.0b mechanism). Nachfolgende Runs nutzen automatisch diese Version.  
**Plus:** approve-Logic läuft im gleichen Call (Step gilt als completed).

### 6.7 Extract

**Trigger:** Extract-Button → Modal mit Textarea für Begründung → Submit  
**API:** `POST /pauses/:id/resolve` with `{action: 'extract', note: <string>}`  
**Result:** `step_optimization_requests` Row geschrieben mit kompletter Step-Context (input + output + prompt + note). Step bleibt pausiert für weitere Action (z.B. nach extract → edit-prompt → promote).  
**Note:** Extract resolved die pause NICHT. Marcel kann danach weitere Action triggern.

### 6.8 Rerun (NEU)

**Trigger:** Rerun-Button → Pre-flight-Check via `GET /pauses/:id/rerun-preflight`  
**Pre-flight Response:**
```ts
{
  safe: boolean;
  impact: {
    stepsToInvalidate: string[];     // ['select-overage-items', 'distribute-slot-dates', ...]
    dbWritesToRevert: string[];      // ['weekly_plans.123', 'planned_items.5x...']
    itemsToCancel: number;           // approved-items waiting in BullMQ
    requiresConfirm: boolean;        // true if destructive
  };
}
```
**Submit:** `POST /pauses/:id/resolve` with `{action: 'rerun', confirmDestructive: true}`  
**Backend Workflow:**
1. Validate Run-Status in (`running`, `paused`, `failed`)
2. Begin Transaction:
  - Find Step-Index N
  - UPDATE step_pauses SET status='superseded' WHERE run_id=X AND step_index > N
  - UPDATE pipeline_runs SET step_outputs = step_outputs[:N], current_step_index = N
  - DELETE FROM idempotency_outputs WHERE run_id=X AND step_index >= N
  - Cleanup-Hooks pro Pipeline-Type (Discovery Phase 0):
    - PlanWeekPipeline: wenn N <= PersistPlanStep-Index → DELETE FROM planned_items + UPDATE weekly_plans SET status='cancelled' for affected planId
3. BullMQ enqueue mit step-pointer=N
4. SSE `run.statusChanged` → running

**UI-Warnings:**
- "This will invalidate N subsequent steps."
- Wenn `dbWritesToRevert.length > 0`: "This will revert N DB writes including: [list]"
- Wenn `itemsToCancel > 0`: "X approved items in execution queue will be cancelled"
- Bei `requiresConfirm`: zweite Confirm-Box mit Type-the-word-DELETE-style protection

## 11. Risiken

| Risiko | Mitigation |
|---|---|
| Re-run Cleanup-Hooks unvollständig → DB-Inkonsistenz | Phase 0 Audit aller Pipeline-Steps mit DB-Writes. Pro Pipeline-Type expliziter Cleanup-Hook in Code. Tests pro destructive Scenario. |

| Rerun während BullMQ-Job aktiv läuft | Pre-flight check: wenn `pipeline_runs.bullmq_job_id` aktiv → erst BullMQ-Job cancellen, dann Re-run. Race-condition möglich aber sehr unwahrscheinlich (Worker pollt step_pauses). |

| Extract-Action bleibt aktiv aber Step-Pause-Status verwirrt | Extract resolved Pause NICHT (§6.7). UI muss klar zeigen "extracted, still paused, choose next action". |
| SSE-Events kommen schneller als Frontend rendert → State-Drift | TanStack `setQueryData` mit incremental patches statt vollem refetch. Falls drift: invalidate. |
| Plan-Run mit 0 step_pauses (no debug-mode) sichtbar in /runs aber kein "useful" Detail | Detail-Page handhabt completed Runs auch sinnvoll (zeigt step_outputs read-only). Kein Pause-Action UI dann. |
| Cmd+K-Action "Pipeline Runs" deep-linkt aber keine Runs da → User-Confusion | Empty-state-Card "No runs yet — generate a plan to see runs here" mit Link zu Planner |

## 14. Implementation deviations + discoveries

### 14.1 No migration needed (§3 confirmed in Phase 0)

The 62.0a + 62.0b tables (`pipeline_runs`, `step_pauses`, `idempotency_outputs`, `prompt_versions`, `step_optimization_requests`) already cover every field the spec required. `pipeline_runs` does NOT have a `step_outputs` JSONB or `current_step_index` column — they aren't needed: per-step outputs live as child `pipeline_runs` rows (parent_run_id + step_name), and `suspensionCheckpoint.accumulatedOutput` carries the at-suspend snapshot the runner uses for resume.

### 14.2 PlanWeekPipeline rerun is structurally safe in all currently-possible paused states

Audit during Phase 0: `PersistPlanStep.pausableInDebug() === false` AND it is the LAST step in PlanWeekPipeline. That means a paused PlanWeekPipeline run can never have executed `PersistPlanStep` (which would have written `weekly_plans` + `planned_items`). So no destructive cleanup hook is registered for `planning:weekly` in 62.6 — the architecture (`registerRerunCleanupHook` + `RerunCleanupHook` interface in [`packages/pipelines/src/engine/rerun.ts`](../packages/pipelines/src/engine/rerun.ts)) is forward-compat for future pipelines that pause AFTER a DB-write step.

### 14.3 Reused existing endpoints rather than building parallel `/runs/...` API

Spec §4 sketched fresh `POST /api/projects/:slug/runs/:runId/pauses/:pauseId/resolve`. Implementation reused the existing 62.0a `POST /api/pipeline-runs/:id/step-pauses/:stepPauseId/resolve` (same payload shape with `"rerun"` added to the action enum) and the 62.0b `GET /api/projects/:slug/optimization-requests` + `PATCH /api/optimization-requests/:id`. Net change: ONE new endpoint added — `GET /api/pipeline-runs/:id/step-pauses/:stepPauseId/rerun-preflight`. The slug-prefixed shape from the spec would have been redundant.

### 14.4 Two-source action enum gotcha

The `STEP_ACTIONS` constant lives in two places that must stay in sync: [`packages/shared/src/types/step-pause.ts`](../packages/shared/src/types/step-pause.ts) (HTTP boundary + runner type) AND [`packages/pipelines/src/engine/queue.ts`](../packages/pipelines/src/engine/queue.ts) `stepActionSchemaJob` (BullMQ payload Zod). The queue can't import from `shared` due to TypeScript variance under `exactOptionalPropertyTypes`. Adding `"rerun"` required updates to both. Documented in root CLAUDE.md as a permanent gotcha.

### 14.5 Codemirror lazy-load deferred

Spec §2.4 called for explicit lazy-loading via `defineAsyncComponent` to keep the ~200KB bundle out of the main chunk. Implementation imports CodeMirror eagerly in [`PipelineJsonEditor.vue`](../apps/web/src/components/runs/PipelineJsonEditor.vue) (matching the existing `BrandTokensJsonEditor.vue` pattern from Spec 60.0). Vite code-splits the `runs` pages route by default, so the bundle ends up in the route chunk anyway. Revisit if bundle-analyzer reports an issue.

### 14.6 `usePauseActions` uses raw fetch, not `apiPost`

The 409 + `{ error: "destructive_confirm_needed", impact }` response from the rerun-confirm-destructive gate carries a structured `impact` payload that the confirm dialog needs. The shared `apiPost` wrapper throws `Error(body.error)` and drops sibling fields on non-OK responses, so the rerun handler in [`usePauseActions.ts`](../apps/web/src/composables/runs/usePauseActions.ts) uses raw fetch + `res.json()` and inspects status + body before returning. Documented in `apps/web/CLAUDE.md` and the root CLAUDE.md gotcha list.

### 14.7 `RerunConfirmDialog` lives in 62.6 not a Phase-5 successor

The spec's phasing (§10) split "Re-run UI" into Phase 5. Implementation built the dialog component during Phase 4 (StepCard imports it directly) because StepCard's `onOpenRerun` flow needs to surface the dialog on a 409 response. Pure refactor decision — no scope change.

### 14.8 `/paused-runs` route is now a redirect, not a stub page

62.0a left a stub page at `/projects/:slug/paused-runs`. 62.6 replaces the route with a router-level `redirect` that maps to `/runs?status=paused`. The original `PausedRunsStubPage.vue` is left in `apps/web/src/pages/paused-runs/` as dead code (no route references it; Vite tree-shakes it from the bundle). A future cleanup PR can delete the file + the `pausedRuns` i18n namespace.

### 14.9 Manual E2E (Spec §9.2) deferred to integration testing

The 547 pipeline tests pass — including the new [`packages/pipelines/test/engine/rerun.test.ts`](../packages/pipelines/test/engine/rerun.test.ts) covering safe rerun, destructive hook impact + execute, and pause supersession. Manual E2E items 1–13 from §9.2 need a real worker + browser session against Toolwiki and are out of automated scope.
