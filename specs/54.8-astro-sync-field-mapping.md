## Goal

Patch the existing Astro-Sync import to capture three currently-dropped frontmatter fields (`date`, `updated`, `name`), add a collection-aware default for `intent_type` on tools, and promote six tool-relevant fields from JSONB into dedicated DB columns to enable efficient filtering/sorting.

After this spec lands:
- Every blog article has a real `publishedAt` and `frontmatterUpdatedAt` (currently all `null` for the 60 imported blog rows)
- Every author article has a real `title` (currently all `null` for 10 author rows)
- Every tool article has `intent_type = "review"` (currently all `null` for 108 tool rows)
- Tools can be queried/sorted/filtered by `pricing`, `priceFrom`, `rating`, `votes`, `affiliateSlug`, `website` via indexed columns
- Spec 54.9 (Blog Generator) has all the data it needs without additional MDX reads or JSONB acrobatics

This is **NOT** an "extract tools/authors to own tables" spec. The original 54.8 concept of building dedicated tools/authors tables was abandoned after the Astro-Sync Import Audit revealed the existing import already captures all 272 MDX files completely into `articles` with `collection`-based discrimination. The data lives in the right place; it just needs better mapping and selective column promotion for query performance.

## What this is NOT

- Not creating new `tools` or `authors` tables — they stay as `articles` rows with `collection IN ('tools', 'authors')`
- Not changing the existing Astro-Sync architecture or pipeline step ordering
- Not rebuilding any UI on top of the new columns (that's downstream specs)
- Not introducing new MDX schema fields (only mapping existing ones)
- Not handling DE heroImage backfill via re-import (already done in pre-54.8 hygiene)
- Not promoting `seoTitle`/`seoDescription` to dedicated columns (deferred to backlog per audit Section 7)
- Not addressing `usecases` cluster gap (out of scope; backlog)
- Not fixing the `dall-e` broken reference or other content issues (done in pre-54.8 hygiene or backlog)

## Architecture

### Why patch instead of replace

The Astro-Sync Import Audit established:

1. The existing import pipeline (9 steps in `packages/adapters/astro-sync/src/import/`) works correctly for the bulk of content
2. All 272 MDX files are in DB with correct `collection`, `locale`, `translationKey`, `slug` matching
3. The cluster auto-linking (`SyncClustersFromFrontmatterStep`) correctly creates `cluster_id` FKs for tools, blog, comparisons, ki-wissen
4. `frontmatter_extras` JSONB catches all collection-specific fields cleanly (faq, pricing, pros, cons, expertise, useCaseVerdicts, etc.)

The only structural issues are:
- 4 specific TYPED_FIELDS mappings are missing (`date`, `updated`, `name`, plus collection-aware `intent_type` default)
- 6 tool-specific fields stuck in JSONB that would benefit from indexed columns

Both are surgical patches, not architectural rewrites.

### Field mapping changes (Deliverables 1+2)

**Current `TYPED_FIELDS` in `parse-frontmatter.ts`** (from audit Section 1, code excerpt):

The current Zod schema typed-parses:
- `title`, `description`, `slug`, `locale`, `translationKey`, `publishedAt`, `updatedAt`, `author`, `category`, `subcategory`, `tags`, `noindex`, `clusterKey`, `clusterRole`, `intentType`

**Patched `TYPED_FIELDS`** (after this spec):

Add these mappings (and keep the existing ones):

| New typed field | YAML format | Coerced to | Goes to DB column | Fallback if missing |
|---|---|---|---|---|
| `date` | string `"2026-03-28"` | `Date` | `articles.publishedAt` | Existing `publishedAt` if set; else `null` |
| `updated` | string `"2026-04-15"` | `Date` | `articles.frontmatterUpdatedAt` | Existing `updatedAt` if set; else `null` |
| `name` | string `"Anna Weidner"` | `string` | `articles.title` (fallback only) | Existing `title` if set; else `null` |

For collection-aware `intentType` default — done in `upsert-articles.ts`, not in the parser:

```typescript
// During UpsertArticlesStep.execute(), after typed parse:
const intentType = typed.intentType
  ?? (collection === "tools" ? "review" : null);
```

### Why `name → title` as fallback (not override)

Other collections may incidentally have a `name` field (e.g., a hypothetical "company name" in a future schema). The mapping prefers `title` if present, falls back to `name` if `title` is null. In practice today: only authors have `name` without `title` — so for authors, `name → title`; for everything else, behavior unchanged.

```typescript
title: typed.title ?? typed.name ?? null,
```

### Tool column promotion (Deliverables 3+4)

The audit's Section 7 recommended 6 columns. Migration 0043 adds them as nullable to the `articles` table:

```sql
ALTER TABLE articles
  ADD COLUMN tool_pricing TEXT,
  ADD COLUMN tool_price_from NUMERIC(10,2),
  ADD COLUMN tool_rating NUMERIC(3,1),
  ADD COLUMN tool_votes INTEGER,
  ADD COLUMN tool_affiliate_slug TEXT,
  ADD COLUMN tool_website TEXT;

-- Indexes for the expected query patterns
CREATE INDEX articles_tool_pricing_idx ON articles(project_id, tool_pricing)
  WHERE collection = 'tools';
CREATE INDEX articles_tool_rating_idx ON articles(project_id, tool_rating DESC NULLS LAST)
  WHERE collection = 'tools';
CREATE INDEX articles_tool_price_from_idx ON articles(project_id, tool_price_from NULLS LAST)
  WHERE collection = 'tools';
```

**Partial indexes** (predicate `WHERE collection = 'tools'`) keep the index size proportional to the 108 tool rows, not the full ~280 article rows.

In `upsert-articles.ts`, when `collection === 'tools'`:

```typescript
// After typed parse, before INSERT:
const toolColumns = collection === "tools" ? {
  toolPricing: typed.extras.pricing ?? null,
  toolPriceFrom: typed.extras.priceFrom != null
    ? parseFloat(String(typed.extras.priceFrom))
    : null,
  toolRating: typed.extras.rating != null
    ? parseFloat(String(typed.extras.rating))
    : null,
  toolVotes: typeof typed.extras.votes === "number"
    ? typed.extras.votes
    : (typed.extras.votes != null ? parseInt(String(typed.extras.votes), 10) : null),
  toolAffiliateSlug: typed.extras.affiliateSlug ?? null,
  toolWebsite: typed.extras.website ?? null,
} : {};

await db.insert(articles).values({
  // ... existing fields ...
  intentType,
  ...toolColumns,
}).onConflictDoUpdate({ ... });
```

The fields stay duplicated in `frontmatter_extras` (no breaking change for any existing reader). The new columns are the **canonical queryable representation** for queries; JSONB stays as the byte-exact source of truth.

### Type coercion safety

`priceFrom`, `rating`, and `votes` are stored as JSONB numbers in `frontmatter_extras` (per audit Section 2.2 — preserved correctly as numbers, not strings). But because gray-matter occasionally produces string-typed numbers from YAML, the coercion is defensive:

```typescript
parseFloat(String(value))  // handles both `39` and `"39"`
```

If `parseFloat` returns `NaN` (e.g. the value is `"enterprise"` not a number), the column becomes `null`. The original value is preserved unmodified in `frontmatter_extras` either way.

### `upsert-articles.ts` patch sketch

```typescript
async function buildArticleRow(p: ParsedFile, projectId: string) {
  const collection = extractCollection(p.filePath, contentRoot);
  const locale = p.typed.locale ?? extractLocaleFromPath(p.filePath);
  const slug = p.typed.slug ?? extractSlugFromPath(p.filePath);

  // NEW: collection-aware intent_type default
  const intentType = p.typed.intentType ?? (collection === "tools" ? "review" : null);

  // NEW: title fallback to name (for authors collection)
  const title = p.typed.title ?? p.typed.name ?? null;

  // NEW: publishedAt fallback to date (for blog collection)
  const publishedAt = p.typed.publishedAt ?? p.typed.date ?? null;

  // NEW: frontmatterUpdatedAt fallback to updated (for blog collection)
  const frontmatterUpdatedAt = p.typed.updatedAt ?? p.typed.updated ?? null;

  // NEW: tool-specific column promotion
  const toolColumns = collection === "tools"
    ? buildToolColumns(p.typed.extras)
    : {};

  return {
    projectId,
    source: "imported" as const,
    collection,
    locale,
    slug,
    cornerstoneKeyword: null,
    title,
    metaDescription: p.typed.description ?? null,
    translationKey: p.typed.translationKey ?? null,
    filePath: p.filePath,
    gitSha: p.gitSha,
    publishedAt,
    frontmatterUpdatedAt,
    author: p.typed.author ?? null,
    category: p.typed.category ?? null,
    subcategory: p.typed.subcategory ?? null,
    tags: p.typed.tags ?? [],
    noindex: p.typed.noindex ?? false,
    clusterKey: p.typed.clusterKey ?? null,
    clusterRole: p.typed.clusterRole ?? null,
    intentType,
    frontmatterExtras: p.typed.extras,
    importMetadata: computeImportMetadata(p.body),
    status: "published" as const,
    approvalMode: "manual" as const,
    ...toolColumns,
  };
}

function buildToolColumns(extras: Record<string, unknown>): {
  toolPricing: string | null;
  toolPriceFrom: number | null;
  toolRating: number | null;
  toolVotes: number | null;
  toolAffiliateSlug: string | null;
  toolWebsite: string | null;
} {
  return {
    toolPricing: typeof extras.pricing === "string" ? extras.pricing : null,
    toolPriceFrom: coerceToNumber(extras.priceFrom),
    toolRating: coerceToNumber(extras.rating),
    toolVotes: coerceToInteger(extras.votes),
    toolAffiliateSlug: typeof extras.affiliateSlug === "string" ? extras.affiliateSlug : null,
    toolWebsite: typeof extras.website === "string" ? extras.website : null,
  };
}

function coerceToNumber(value: unknown): number | null {
  if (value == null) return null;
  const n = parseFloat(String(value));
  return Number.isFinite(n) ? n : null;
}

function coerceToInteger(value: unknown): number | null {
  if (value == null) return null;
  const n = parseInt(String(value), 10);
  return Number.isFinite(n) ? n : null;
}
```

### Helper library

`packages/db/src/helpers/articles-read.ts`:

```typescript
import { and, eq, isNull, desc, sql } from "drizzle-orm";
import { db } from "../client";
import { articles } from "../schema/content";

type Locale = "de" | "en";

export async function resolveToolBySlug(
  projectId: string,
  slug: string,
  locale: Locale,
): Promise<typeof articles.$inferSelect | null> {
  const [row] = await db.select().from(articles)
    .where(and(
      eq(articles.projectId, projectId),
      eq(articles.collection, "tools"),
      eq(articles.slug, slug),
      eq(articles.locale, locale),
    ))
    .limit(1);
  return row ?? null;
}

export async function resolveAuthorBySlug(
  projectId: string,
  slug: string,
  locale: Locale,
): Promise<{
  slug: string;
  name: string;
  jobTitle: string | null;
  description: string | null;
  expertise: string[];
  image: string | null;
  yearsExperience: number | null;
} | null> {
  const [row] = await db.select().from(articles)
    .where(and(
      eq(articles.projectId, projectId),
      eq(articles.collection, "authors"),
      eq(articles.slug, slug),
      eq(articles.locale, locale),
    ))
    .limit(1);
  if (!row) return null;

  const extras = (row.frontmatterExtras ?? {}) as Record<string, unknown>;
  return {
    slug: row.slug,
    name: row.title ?? String(extras.name ?? ""),
    jobTitle: typeof extras.jobTitle === "string" ? extras.jobTitle : null,
    description: row.metaDescription,
    expertise: Array.isArray(extras.expertise) ? extras.expertise as string[] : [],
    image: typeof extras.image === "string" ? extras.image : null,
    yearsExperience: typeof extras.yearsExperience === "number" ? extras.yearsExperience : null,
  };
}

export async function getEntryByTranslationKey(
  projectId: string,
  collection: string,
  translationKey: string,
  locale: Locale,
): Promise<typeof articles.$inferSelect | null> {
  const [row] = await db.select().from(articles)
    .where(and(
      eq(articles.projectId, projectId),
      eq(articles.collection, collection),
      eq(articles.translationKey, translationKey),
      eq(articles.locale, locale),
    ))
    .limit(1);
  return row ?? null;
}

export async function listToolsByCategory(
  projectId: string,
  category: string,
  locale: Locale,
  options?: {
    pricing?: string;
    minRating?: number;
    orderBy?: "rating" | "votes" | "name";
  },
): Promise<typeof articles.$inferSelect[]> {
  const conditions = [
    eq(articles.projectId, projectId),
    eq(articles.collection, "tools"),
    eq(articles.category, category),
    eq(articles.locale, locale),
  ];
  if (options?.pricing) {
    conditions.push(eq(articles.toolPricing, options.pricing));
  }
  if (options?.minRating != null) {
    conditions.push(sql`${articles.toolRating} >= ${options.minRating}`);
  }

  let query = db.select().from(articles).where(and(...conditions));

  if (options?.orderBy === "rating") {
    query = query.orderBy(desc(articles.toolRating));
  } else if (options?.orderBy === "votes") {
    query = query.orderBy(desc(articles.toolVotes));
  } else {
    query = query.orderBy(articles.title);
  }

  return await query;
}

export async function listToolsByPricing(
  projectId: string,
  pricing: string,
  locale: Locale,
): Promise<typeof articles.$inferSelect[]> {
  return await db.select().from(articles)
    .where(and(
      eq(articles.projectId, projectId),
      eq(articles.collection, "tools"),
      eq(articles.toolPricing, pricing),
      eq(articles.locale, locale),
    ))
    .orderBy(desc(articles.toolRating));
}
```

## Open Questions / Decisions Made

**Decision 1: No new tools/authors tables — keep articles single-table.**
The original 54.8 concept was abandoned per audit findings. All 272 MDX files are already cleanly imported into `articles` with proper `collection` discrimination. Building separate tables would be high effort with marginal benefit; the JSONB+column hybrid handles all needed query patterns.

**Decision 2: 6 tool columns, not all JSONB-promoted fields.**
The audit suggested up to 10+ candidates for column promotion. This spec promotes only the 6 with clearest query/filter use cases. Others (`seoTitle`, `seoDescription`, `tags` for tools) stay in JSONB; if Spec 54.9+ needs them as columns, separate promotion spec.

**Decision 3: `intent_type = "review"` for all tools.**
Tools are conceptually reviews. This makes them consistent with `articles.intent_type` semantics for Trend Discovery coverage check (Spec 54.5) and for Author-Picker logic in Spec 54.9. Alternative was `null` with downstream code accommodation; chose explicit default for simpler downstream code.

**Decision 4: Force-re-import once, not progressive.**
The corrected mappings affect 60 blog + 10 author + 108 tool rows = 178 rows that need backfill. The upsert pipeline handles all 272 idempotently in a single run, so a force-re-import is simpler than a partial backfill SQL script. ~2-3 minute job.

**Decision 5: Column-promotion data stays in JSONB too.**
We don't remove the promoted fields from `frontmatter_extras` after column promotion. Two reasons: (1) backward compat for any code reading the JSONB; (2) source-of-truth for re-import is the MDX, and JSONB is the closest DB analog. Some redundancy, very low storage cost.

**Decision 6: Partial indexes on tool columns.**
The 3 indexes have `WHERE collection = 'tools'` predicate. Reduces index size from ~280 rows to ~108 (toolwiki) — even smaller for other projects without tools. PostgreSQL partial-index syntax verified.

**Decision 7: Helpers in `packages/db/src/helpers/`, not in `apps/api/src/services/`.**
The helpers are pure read functions over the schema. Putting them in `packages/db` means any package (api, workers, pipelines) can use them. No business logic — just typed reads.

**Decision 8: Author helper returns reshaped object, not raw Article row.**
For `resolveAuthorBySlug`, the consumer (Spec 54.9 author picker) needs `name`, `expertise`, `image`, etc. — all of which require JSONB extraction. Doing this once in the helper is cleaner than every caller doing it.

**Decision 9: No new TypeScript type alias for "Tool" or "Author."**
The helpers return `Article` rows (or reshaped objects for authors). No `Tool` or `Author` type alias to maintain because there's no separate table. Type-narrowing via collection field in callers if needed.

**Decision 10: `name → title` is a fallback, not an override.**
For collections where both `name` and `title` might exist in future schemas, `title` wins. For authors (only `name`, no `title`), the fallback fires. Safe for backward compatibility.

## Discovered During Implementation

**Drizzle `numeric` columns require string values on insert, not numbers.**
The spec pseudocode showed `buildToolColumns` returning `toolPriceFrom: number | null` and `toolRating: number | null`. In practice, Drizzle's `numeric()` column type is `string | null` both at read and insert time — passing a JS `number` causes a TypeScript error. The implementation uses `coerceToNumericString()` (returns `String(n)`) instead of `coerceToNumber()` (returns `n`). At read sites, call `parseFloat(row.toolRating)` if arithmetic is needed.

**`priceFrom` in toolwiki MDX is always a JS number, never a string.** gray-matter preserves YAML number literals correctly. The defensive `parseFloat(String(value))` path for string inputs was not exercised in practice but is correct to keep for forward compatibility.

**All 8 validation queries passed on first import run.** No content shape surprises. 272 files processed in ~14 seconds (0 failures).

## Deviations

**`buildToolColumns` return type uses `string | null` for numeric fields** (not `number | null` as shown in spec pseudocode). Required by Drizzle's `numeric()` column contract. The function is named `coerceToNumericString` accordingly. No behavioral difference — PostgreSQL stores and queries NUMERIC correctly either way.
