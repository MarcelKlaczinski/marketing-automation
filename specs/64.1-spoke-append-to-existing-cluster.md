# Spec 64.1 — Neuer content_type 'cluster_spoke' für append_to_existing Briefs

_Theme 64 Sub-Spec — Sauberer Split zwischen cluster (create_new, neuer Hub+Spokes) und cluster_spoke (append_to_existing, einzelner Spoke unter existing Hub). Plan-Goals und Pipeline-Router gleichermaßen._
_Status: Draft._
_Voraussetzung: 63.7b deployed (Router-level dispatch), 63.7c durch (Index-Widening), 63.5 deployed (Diversity)._

---

## 1. Problem

Aktuell (post-63.7b) ist `content_type='cluster'` semantisch überladen:

| Variante | Cost | Outcome |
|---|---|---|
| `cluster_action='create_new'` | €4.20 | Neuer Cluster mit Hub + N Spokes (cluster:full-plan) |
| `cluster_action='append_to_existing'` | €1.06 | Ein einzelner Spoke unter existing Cluster (article:blog) |

**Plan-Goal `cluster: min=7/Woche` zählt beide gleich** — heißt:
- Floor kann 7 Spokes picken, 0 neue Cluster → Plan erfüllt Goal numerisch
- Aber semantisch: kein neuer Hub gebaut, nur isolierte Spokes
- Marcel hat keine Kontrolle über das Verhältnis create_new vs append_to_existing

**Konsequenz heute KW22-Plan (2026-05-22):**
- Budget: €18.64 vs €43.90 vorher (gut — durch 63.7b Cost-Reduktion)
- Aber: 7× cluster items alle €1.06 → alle append_to_existing Spokes
- Plus 1 Trend-Overage als create_new (€4.20)
- Marcel will: **explizite Trennung** der zwei Sorten als separate Plan-Goals

## 2. Ziel

Neuer content_type `cluster_spoke` für append_to_existing Briefs. Plan-Goals haben separates min/max für `cluster` (= create_new) und `cluster_spoke` (= append_to_existing).

**In Scope:**
- content_type Enum erweitern um `'cluster_spoke'`
- matchBriefToContentType: append_to_existing → 'cluster_spoke' (statt 'cluster')
- Pipeline-Router: 'cluster_spoke' → article:blog (gleiches Routing wie 63.7b, nur expliziter content_type)
- Plan-Goals: separates `cluster_spoke` Goal in project_goals, default min=5/Woche
- Cost-Estimation: cluster_spoke deterministisch €1.06 (article:blog Step-Sum)
- Plan-UI: Badge "Spoke" für cluster_spoke Items (visuell unterschieden)
- SettingsPlannerPage: cluster_spoke Goal sichtbar + konfigurierbar
- Validation: project_goals akzeptiert cluster_spoke als first-class

**Out of Scope:**
- Auto-Convert wenn Pool leer (strict: Goals unterfüllen)
- cluster_translation, cluster_refresh als weitere Varianten — eigene Specs falls nötig
- Backfill existing planned_items mit cluster_spoke (alte Plans bleiben cluster)
- Cost-Estimation für create_new ändern (bleibt €4.20)
- Floor-Diversity Score-Berechnung ändern (63.5 funktioniert weiter)

**Aufwand:** ~1 Tag.

## 3. Architektur-Entscheidungen

### 3.1 Enum-Widening vs neue Tabelle

**Entscheidung: Enum erweitern.**

Begründung:
- content_type ist schon ein Enum/CHECK in DB
- planned_items.content_type, project_goals.content_type, project_planner_config-relevante Spalten existieren schon
- Migration ist klein (ADD VALUE + UPDATE CHECK)
- Memory D124: Enum-Widening + Data-Seed in separater Migration

### 3.2 Plan-Goal cardinality

content_type='cluster_spoke' ist semantisch sinnvoll als:
- Per-Day Cadence (1 Spoke/Tag = 7/Woche) → analog social_post
- Oder Per-Week Cadence (5 Spokes/Woche) → analog cluster_new

**Default: per_week mit minCount=5, maxCount=10.** Marcel kann später via Settings UI auf per_day umstellen.

cluster_new (= 'cluster') bleibt:
- per_week, minCount=1, maxCount=2

Diese Defaults werden bei `seedProjectGoals()` für neue Projekte gesetzt. Für existing Projekte (Toolwiki) Migration via Seed.

### 3.3 matchBriefToContentType Update

`packages/pipelines/src/planning/steps/select-floor-items.ts`:

```ts
function matchBriefToContentType(brief: TopicBrief): ContentType | null {
  // existing rules unchanged:
  
  // Comparison (63.3b)
  if (brief.source === 'comparison_discovery'
      || brief.clusterAction === 'comparison'
      || (brief.intentType === 'comparison' && hasComparisonToolSlugs(brief))) {
    return 'comparison';
  }
  
  // Knowledge (63.4)
  if (brief.intentType === 'knowledge') return 'ki_wissen';
  if (brief.intentType === 'tutorial' && brief.clusterAction === 'standalone') return 'ki_wissen';
  
  // NEU 64.1: append_to_existing → cluster_spoke (separater Bucket)
  if (brief.clusterAction === 'append_to_existing') return 'cluster_spoke';
  
  // create_new + everything else → cluster
  return 'cluster';
}
```

**Wichtige Konsequenz:** wenn Brief append_to_existing UND comparison ist (theoretisch möglich), gewinnt comparison-Branch (steht zuerst). Phase 0 prüft ob dieser Case existiert. Vermutlich nein (comparison-Briefs sind eigene Pipeline mit pair-uniqueness).

-- Seed cluster_spoke goal für existing projects mit sinnvollen defaults

INSERT INTO project_goals (

| Risiko | Mitigation |
|---|---|
| content_type-Enum widening bricht existing planned_items rows | UPDATE constraint mit IF EXISTS / IF NOT EXISTS Pattern. Backward-compat: 'cluster' bleibt valid. |

Cluster + Spoke werden getrennt diversifiziert. Akzeptiert — semantisch sinnvoll (Hub und Spoke sind verschiedene Plan-Items, dürfen ähnliche Themen haben). |

| Marcel will später cluster_spoke per_day cadence statt per_week | UI erlaubt cadenceUnit Toggle (existing pattern). Migration setzt nur Default. |

## 10. Anschluss

Nach 64.1:
- Plan-Goals klar getrennt: cluster (new Hub+Spokes) vs cluster_spoke (single Spoke)
- Marcel kann via Settings UI feinjustieren (z.B. 2 neue Cluster + 7 Spokes pro Woche)
- Cost-Estimation transparent: SPOKE-heavy plans sind sichtbar billiger
- 63.7b Router-Logic für append_to_existing bleibt unverändert, nur via expliziterem content_type
- KW22 Plan kann generiert werden mit erwarteter Verteilung

Phase E Items die jetzt aktiviert werden können:
- cluster_translation (DE→EN cluster) — analog cluster_spoke Pattern
- cluster_refresh (existing cluster update) — analog
- Plus mehr content_type-Splits möglich (z.B. social_post → social_carousel vs social_single)

**Bewusst NICHT in 64.1:**
- Cost-Estimation für create_new ändern
- Plan-Goal-UI Redesign
- Backfill alter planned_items mit cluster_spoke
- Auto-Convert bei leerem Pool (strict Goals)
- ki_wissen → ki_wissen_standalone + ki_wissen_spoke (Knowledge-Hub-Spoke ist eigene Story)
