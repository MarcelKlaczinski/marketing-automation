# Spec 62.3.5 — Planner Package Refactor

_Theme 62 Mini-Spec — establishes `packages/planner`, migrates `goal-validator` from `cost-tracker`._
_Status: Draft._
_Empfohlene Reihenfolge: vor oder parallel zu 62.3. Falls 62.3 zuerst merged, wird 62.3.5 ein Rename-Pass ohne Substanz._

---

## 1. Ziel

Ein einziger Zweck: **Boundary-Cleanup**.

`packages/cost-tracker` hat in 62.0a/62.2 mehr aufgenommen als sein Name hergibt: Cost-Estimator (passt), Article-Freshness (passt), Goal-Validator (passt nicht — der validiert Planner-Konfiguration, nicht Cost). 62.3 wird `refreshSignalsForProject` und `discoverComparisonPairs` neu bauen — die gehören sicher nicht in `cost-tracker`.

Statt das Problem zu vergrößern, etabliert 62.3.5 das **Planner-Package** als neues Zuhause für Planner-Foundation-Code. Anschließend wandert `goal-validator` als erster Resident dahin.

**In Scope:**
- Neues Workspace-Package `packages/planner` mit Standard-Setup
- Migration von `goal-validator.ts` aus `cost-tracker` nach `planner`
- Migration von `CONTENT_TYPE_TO_PIPELINE` map (gehört konzeptionell zu goal-validator)
- Migration aller goal-validator-Tests
- Update aller Importer (Consumer der goal-validator API)

**Out of Scope:**
- `weekly-budget.ts` bleibt in `cost-tracker` (Name passt zu Inhalt)
- `article-freshness.ts` bleibt in `cost-tracker` (Pre-flight-Task-3 kanonisch dort)
- Neuer Code (62.3 baut den)
- Verhaltens-Änderungen (rein mechanischer Rename + Move)

**Geschätzter Aufwand:** 1-2 Stunden. Wenn Workspace-Setup glatt läuft: nichts dazwischen.

## 2. Architektur-Entscheidungen

- **`packages/planner` kann von `packages/cost-tracker` abhängen** (directed, no cycle). **`packages/planner` darf NICHT von `packages/pipelines` abhängen** (62.0a-Lesson D15). Andersrum: pipelines kann planner consumen, planner consumed pipelines NICHT.
- **Dependencies-Whitelist für `packages/planner`:**
  - `@<scope>/db` (für DB-Helpers)
  - `@<scope>/shared` (für Zod-Schemas)
  - `@<scope>/cost-tracker` (für `estimateWeeklyPlanCost` etc. — directed dep, kein Cycle)
  - `drizzle-orm`
  - `zod`
  - NICHTS aus dem App-Layer (`apps/api`, `apps/web`)
- **Reasoning:** Die ursprüngliche §2-Formulierung "planner ist strictly leaf" war zu streng. Die echte Constraint ist "no cycle", nicht "no upstream dep on cost-tracker". planner → cost-tracker ist sauber gerichtet. DI-Callback wäre premature abstraction (eine Strategie, ein Caller). 62.0a D15's `resolvePipelineSteps` callback existiert weil dort ein echter Cycle (pipelines ↔ cost-tracker) zu vermeiden war — andere Situation, nicht 1:1 übertragbar.
- **Test-Framework:** gleich wie der Rest des Workspaces (Pattern-Discovery zeigt: bun:test in `packages/social`, ggf. vitest woanders — Phase 0 verifiziert).
- **Imports werden flat aktualisiert:** keine Re-Export-Bridge in `cost-tracker`, kein "deprecated, use new path" — straight Rename. Workspace-typecheck fängt jeden vergessenen Import.

## 3. Schritte

### 3.1 Package-Setup (Phase 0)

Neue Verzeichnis-Struktur:

```
packages/planner/
├── package.json
├── tsconfig.json
├── README.md
├── src/
│   ├── index.ts                  (barrel)
│   └── goal-validator.ts         (migriert)
└── test/
    └── goal-validator.test.ts    (migriert)
```

**package.json template** (analog zu `packages/cost-tracker/package.json`):

```jsonc
{
  "name": "@<scope>/planner",
  "version": "0.0.1",
  "type": "module",
  "main": "./src/index.ts",
  "types": "./src/index.ts",
  "exports": {
    ".": "./src/index.ts"
  },
  "scripts": {
    "test": "<gleicher Befehl wie cost-tracker>",
    "typecheck": "<gleicher Befehl>"
  },
  "dependencies": {
    "@<scope>/db": "workspace:*",
    "@<scope>/shared": "workspace:*",
    "drizzle-orm": "<version aus root>",
    "zod": "<version aus root>"
  },
  "devDependencies": {
    "<test-framework>": "<version>",
    "typescript": "<version>"
  }
}
```

**tsconfig.json** soll `extends`-on root tsconfig haben (Pattern aus existierenden Packages prüfen). Wichtig: `composite: true` falls Workspace das nutzt, sonst weglassen.

**Workspace-Registrierung:** root `package.json` workspaces-Array oder `bun.workspaces` muss `packages/planner` einschließen. Pattern: gleicher Eintrag wie für `packages/cost-tracker`.

### 3.3 Imports im migrierten Code prüfen (Phase 1.5)

`goal-validator.ts` nutzt aktuell aus `cost-tracker`:
- `estimateWeeklyPlanCost` (aus 62.0a §5)
- Eventuell `effectiveFreshness` (unwahrscheinlich, aber prüfen)

Diese Calls in `goal-validator.ts` werden zu **cross-package imports**:

```ts
// Vorher (innerhalb cost-tracker):
import { estimateWeeklyPlanCost } from "./weekly-budget";

// Nachher (planner ruft cost-tracker auf):
import { estimateWeeklyPlanCost } from "@<scope>/cost-tracker";
```

**Wichtig:** das ist OK weil planner → cost-tracker keine Cycle erzeugt (cost-tracker hat aktuell keine Abhängigkeit zu planner). Falls Claude Code beim Build merkt dass cost-tracker indirekt von planner abhängen würde, ist ein Architektur-Issue da — kommt aber nicht erwartet.

## 5. Risiken

| Risiko | Mitigation |
|---|---|
| Workspace-Tool kennt `packages/planner` nicht | Phase 0 root-config-Update; `bun install` (oder pnpm install) muss laufen |
| Dep-Cycle planner → cost-tracker → planner | Klar dass cost-tracker KEINEN planner-Import haben darf. Falls verbaut: 62.3.5 ist blockiert, separate Untersuchung |
| Test-Framework-Mismatch (planner nutzt bun:test, cost-tracker nutzt vitest oder umgekehrt) | Phase 0 prüft welches Framework cost-tracker nutzt, planner spiegelt das 1:1 |
| Vergessener Import in einer obskuren App-Route | Workspace-typecheck fängt das sofort. Grep-Verifikation (4.3) als zusätzlicher Check |
| Re-Export-Bridge wird vermisst (jemand erwartet alten Pfad) | Bewusst NICHT eingebaut. Straight Rename. Wenn nötig: einmaliger one-liner re-export in cost-tracker, aber Default no |

## 8. Discovered During Implementation

### §2 Dependency-Whitelist rule clarified mid-task

The original §2 wording said `packages/planner` **darf NICHT von `packages/cost-tracker` abhängen` — but §3.3 immediately walked it back ("das ist OK weil planner → cost-tracker keine Cycle erzeugt"). The two rules contradicted each other at the operational level (goal-validator calls `estimateWeeklyPlanCost`, which stays in cost-tracker per §1's Out-of-Scope).

Resolved during implementation: §2 now reads "planner CAN depend on cost-tracker (directed, no cycle); planner CANNOT depend on pipelines (62.0a D15)." Reasoning baked into §2: the real constraint is "no cycle," not "strictly leaf." DI-callback would have been premature abstraction (one strategy, one caller). 62.0a D15's `resolvePipelineSteps` callback exists because pipelines ↔ cost-tracker is a real cycle — different situation.

`goal-validator.ts` after migration imports `estimateWeeklyPlanCost` from `@marketing-auto/cost-tracker` directly. `packages/planner/package.json` lists `@marketing-auto/cost-tracker` as a workspace dep.

### Out of scope but discovered

Stage B (Spec 62.3) needed to extend `upsertProjectPlannerConfig` with an optional `signalMaxAgeHours` parameter. That helper lives in `packages/db/src/helpers/project-planner-config-write.ts` and didn't move in 62.3.5 — it stays in `packages/db` as the canonical write helper for `project_planner_config`. Not a deviation, just confirms that planner-config write helpers don't belong in `packages/planner` itself.
