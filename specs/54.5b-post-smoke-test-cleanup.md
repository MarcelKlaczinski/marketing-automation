Fix 3: Score model rebalancing for RSS-dominated signal pools
Root cause discovered in smoke test: The smoke test produced 8 candidate topics, scored 11–44. Most landed in the 22–32 band. Investigation showed a structural bias: 71% of toolwiki's signals are vendor_rss (OpenAI, DeepMind, Hugging Face, Google AI), which carry no engagement metrics (no points, no votes). This forces community_buzz = 0 for any topic clustered primarily from RSS — losing the entire 30-point weight block. Valid content topics (GitHub Copilot pricing, ChatGPT Ads, Voice Agents, GPT-5.5) all rejected as a result. The score model was evaluating "virality" but missing "cross-source validation" — a topic confirmed by 3 sources is a stronger trend signal than one with high buzz in one source.
Two changes:

(b) Add source_diversity component:
A topic that appears in multiple distinct sources is a stronger trend than one with high engagement in a single source. Formula:
typescriptfunction computeSourceDiversity(signals: ExternalSignal[]): number {
const uniqueSources = new Set(signals.map((s) => s.source));
if (uniqueSources.size === 1) return 0;
if (uniqueSources.size === 2) return 50;
return 100;  // 3+ sources
}

Discovered During Implementation
- `computeSourceDiversity([])` returned 100 instead of 0 — the empty-set case (size=0) fell through the `=== 1` check straight to the `return 100` (3+ sources) branch. Fixed by changing `=== 1` to `<= 1`. Caught immediately by the new unit test.
- Author fallback for signals without URLs (`if signals lack a url, fall back to author field`) was pre-existing gap (original code already had `if (!s.url) continue`). Not in the acceptance criteria checklist; deferred to POST-54-BACKLOG.

Deviations
- `prompts.ts` ?? removal introduced three local variable aliases (`const exclusions = scope.exclusions` etc.) rather than direct inline removal. This is strictly equivalent; the intermediates make the function slightly more readable and easier to test.
