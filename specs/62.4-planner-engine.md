# Spec 62.4 — Planner-Engine: PlanWeekPipeline

_Theme 62 Sub-Spec — generates a weekly content plan from goals + signals + topic_briefs._
_Status: Draft._
_Voraussetzung: 62.0a + 62.0a-followup + 62.0b + 62.2 + 62.3.5 + 62.3 sind gemerged._

---

## 1. Ziel

Das Herzstück von Theme 62. Eine Pipeline die:

1. Goals + Config eines Projekts liest (62.2)
2. Signals frisch zieht (62.3 `refreshSignalsForProject`)
3. topic_briefs unified queue liest (62.3)
4. Mit Floor-Cadence + Top-N-Signal-Übererfüllung Plan-Items selektiert
5. Sibling-Locale-aware Scheduling über die Woche verteilt
6. Cost-Pre-flight gegen weekly_budget_eur Hardstop
7. `weekly_plans` Row + N × `planned_items` Rows persistiert
8. Status `'draft'` setzt, wartet auf Approval

**In Scope:**
- `PlanWeekPipeline` als BaseStep-Pipeline (folgt 62.0a Pattern)
- Selektions-Algorithmus mit Floor-Cadence + Top-N-Overage
- Sibling-Locale-Scheduling
- Cost-Pre-flight-Gate
- Snapshot-Persistenz der Input-Daten
- API-Endpoint zum manuellen Triggern
- Approve/Reject-State-Transitions (UI kommt in 62.5)

**Out of Scope:**
- Kalender-UI + Approval-Flow-UI (62.5)
- Step-Pause-UI für Plan-Debugging (62.6)
- Cron-Auto-Trigger (62.7)
- Item-Execution (Items werden persistiert mit status='pending', NICHT enqueued)
- Production-Run mit Batch-API (62.8)
- Quarantäne-View für failed Items (62.7)

**Geschätzter Aufwand:** 2-3 Tage. Größte Sub-Spec von Theme 62.

## 2. Architektur-Entscheidungen

Aus Marcel-Antworten + bestehender Foundation:

- **BaseStep-Pipeline:** jeder Plan-Step ist debug-pausierbar via 62.0a Mechanik. Steps sind deterministisch (keine LLM-Calls in 62.4), Idempotency-Cache aus 62.0a wird automatisch greifen wenn gleicher Input.
- **Cron-Pfad vorbereitet, default off:** 62.4 unterstützt Trigger via API-Endpoint. Cron-Setup in 62.7. Toggle in 62.7 SettingsPlannerPage.
- **Daten-Snapshot zum Trigger-Zeitpunkt:** `weekly_plans.input_snapshot` JSONB enthält Goals + Config + Signal-Top-N + topic_briefs zum Generierungszeitpunkt. Reproduzierbar.
- **Status-Lifecycle für weekly_plans:** `draft → approved → running → completed | partially_failed | cancelled`. Plus `superseded` wenn re-generiert.
- **Status-Lifecycle für planned_items:** `pending → enqueued → in_progress → completed | failed | skipped`. Plus `cancelled` wenn Plan abgebrochen.
- **Re-Generation überschreibt Vorgänger:** UNIQUE-Index auf `(project_id, year, iso_week)` mit `WHERE status NOT IN ('superseded', 'cancelled')`. Neuer Trigger setzt alten Plan auf `superseded`, schreibt neuen Plan.
- **Pipeline-Blacklist konfigurierbar:** `project_planner_config.excluded_pipelines` JSONB-Array. Default `["article:pagespeed-validation", "article:pagespeed-api-validation"]` aus 62.0a-Spec-Hinweis.
- **Score-Normalisierung als simple Heuristik:** pro Source `rank / total_in_source` → 0-1-Score. Top-N global gemerged. Keine ML, keine Feature-Engineering — pragmatic baseline aus 62.3-Empfehlung.
- **Plan-Steps als selbständige BaseSteps:** jeder pipeline-step macht eine klar abgrenzte Sub-Aufgabe. Erlaubt step-level edit-input im Debug-Mode (z.B. Marcel kann nach `SelectFloorItems` Items entfernen bevor Top-N-Overage läuft).

);

  ON weekly_plans (project_id, year, iso_week)

CREATE INDEX weekly_plans_status_idx ON weekly_plans (project_id, status, week_start_date DESC);

-- 2) planned_items: N rows per weekly_plan
CREATE TABLE planned_items (
                             id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),

                             project_id      uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,  -- denormalized for queries

                             content_type    text NOT NULL,                 -- 'cluster' | 'comparison' | 'social_post' | 'ki_wissen'

  -- Source linkage
                             source_kind     text NOT NULL                  -- 'floor' | 'overage_signal' | 'sibling_locale'

                             pipeline_input  jsonb NOT NULL,                -- exact input the pipeline will receive

  -- Cost
                             estimated_cost_eur numeric(10, 6) NOT NULL,
                             actual_cost_eur    numeric(10, 6) NULL,

  -- Selection score (for debugging "why was this picked")
                             selection_score   numeric(5, 4) NULL,           -- 0-1, only for signal/comparison overage items
                             selection_reason  text NULL,                    -- "Floor cluster #3", "Top-1 signal (score 0.85)", etc.

  -- Lifecycle
                             status          text NOT NULL DEFAULT 'pending'

                             pipeline_run_id uuid NULL,                      -- set when enqueued (links to pipeline_runs)

#### 4.2.5 SelectFloorItemsStep

Wesentlicher Algorithmus. Pro `goal.contentType`:

```ts
class SelectFloorItemsStep extends BaseStep<...> {
  async run(input, ctx, priorOutputs) {
    const { goals, config } = priorOutputs.validateGoals;
    const { topicBriefs } = priorOutputs.loadTopicBriefs;
    const items: PlanningItemDraft[] = [];

    for (const goal of goals) {
      const targetCount = goal.cadenceUnit === "per_day"
        ? goal.minCount * 7
        : goal.minCount;

      const candidates = filterCandidatesForContentType(topicBriefs, goal.contentType);
      const selected = selectByPriority(candidates, targetCount);  // FIFO by topic_briefs.created_at

      for (const brief of selected) {
        items.push(planningItemFromBrief(brief, "floor", goal.contentType));
      }

      // If not enough candidates: warning but no error (planner produces what it can)
      if (selected.length < targetCount) {
        log.warn({
          contentType: goal.contentType,
          requested: targetCount,
          available: selected.length,
        }, "Floor cadence not fully reachable");
      }
    }

    return { floorItems: items };
  }
}
```

**Edge-Cases:**
- Wenn `selected.length < targetCount`: Plan wird trotzdem erzeugt, mit weniger items, warning in `generation_notes`
- Wenn ein goal `min_count=0` hat: skip (no items needed)
- Wenn `topic_briefs` für content_type leer: warning, skip

#### 4.2.6 SelectOverageItemsStep

Top-N-Signal-Übererfüllung gemäß 62.2 Policy:

```ts
class SelectOverageItemsStep extends BaseStep<...> {
  async run(input, ctx, priorOutputs) {
    const { config } = priorOutputs.validateGoals;
    const { snapshot } = priorOutputs.snapshot;
    const { floorItems } = priorOutputs.selectFloor;

    // Eligible signals: top-N by normalized score, not already used in floor
    const overageItems: PlanningItemDraft[] = [];

    for (const signal of snapshot.signalTopN.slice(0, config.topNSignalsAllowedOverage)) {
      // Skip if already represented (e.g. signal-derived brief is in floor items)
      if (signalAlreadyInFloor(signal, floorItems)) continue;

      // Each qualifying signal unlocks +maxOveragePerSignal item (default 1)
      for (let i = 0; i < config.maxOveragePerSignal; i++) {
        const contentType = inferContentTypeFromSignal(signal);
        if (!contentType) continue;

        const item = planningItemFromSignal(signal, "overage_signal", contentType);
        item.selectionScore = signal.normalizedScore;
        item.selectionReason = `Top-${i+1} signal: ${signal.title} (score ${signal.normalizedScore.toFixed(2)})`;
        overageItems.push(item);
      }
    }

    return { overageItems };
  }
}
```

**`inferContentTypeFromSignal`:** heuristic mapping. ProductHunt → social_post; HackerNews → ki_wissen (long-form); RSS → cluster. Tunable later.

#### 4.2.7 ApplySiblingLocaleStep

Für jedes `floor` oder `overage_signal` item mit DE-Locale: zweites Item für EN-Sibling +1 Tag.

```ts
class ApplySiblingLocaleStep extends BaseStep<...> {
  async run(input, ctx, priorOutputs) {
    const sourceItems = [...priorOutputs.selectFloor.floorItems, ...priorOutputs.selectOverage.overageItems];
    const siblingItems: PlanningItemDraft[] = [];

    for (const item of sourceItems) {
      if (item.contentType !== "cluster") continue;  // only cluster has siblings for now
      if (item.locale !== "de") continue;

      // Check skip_auto_translation_until (from 62.0a-followup)
      if (await isSiblingSkipped(item)) {
        log.info({ itemId: item.draftId }, "Sibling skipped due to skip_auto_translation_until");
        continue;
      }

      siblingItems.push({
        ...item,
        draftId: generateId(),
        locale: "en",
        sourceKind: "sibling_locale",
        parentItemId: item.draftId,
        // slot_date wird in DistributeSlotDates angepasst
      });
    }

    return { siblingItems };
  }
}
```

#### 4.2.8 DistributeSlotDatesStep

Verteilung über die Wochentage:

```ts
class DistributeSlotDatesStep extends BaseStep<...> {
  async run(input, ctx, priorOutputs) {
    const allItems = [
      ...priorOutputs.selectFloor.floorItems,
      ...priorOutputs.selectOverage.overageItems,
      ...priorOutputs.applySiblings.siblingItems,
    ];

    const weekStart = isoWeekStartDate(input.targetYear, input.targetIsoWeek);

    for (const item of allItems) {
      // per_day items: spread evenly across week
      // per_week items: mid-week slot (e.g. Wednesday)
      // sibling_locale items: parent slot_date + 1 day
      item.slotDate = computeSlotDate(item, weekStart, allItems);
    }

    return { distributedItems: allItems };
  }
}
```

**Distribution-Heuristik:**
- Cluster (per_day): Tag 1 = Montag, Tag 2 = Dienstag, etc.
- Social Post (per_day, ⌀3/Tag): füllt verbleibende slots
- Comparison (per_week): Mittwoch slot
- KI-Wissen (per_week): Donnerstag/Freitag slot
- Sibling: `parent.slot_date + 1 day`. Falls Sonntag: nächste Woche Montag (overflow → next plan)

#### 4.2.11 PersistPlanStep

```ts
class PersistPlanStep extends BaseStep<...> {
  async run(input, ctx, priorOutputs) {
    const { distributedItems } = priorOutputs.distributeSlots;
    const { snapshot } = priorOutputs.snapshot;
    const { finalEstimate } = priorOutputs.budgetGate;

    return await db.transaction(async (tx) => {
      // 1. Supersede existing active plan for this week (if any)
      const existing = await tx.select().from(weeklyPlans).where(
        and(
          eq(weeklyPlans.projectId, input.projectId),
          eq(weeklyPlans.year, input.targetYear),
          eq(weeklyPlans.isoWeek, input.targetIsoWeek),
          notInArray(weeklyPlans.status, ["superseded", "cancelled"]),
        )
      ).limit(1);

      if (existing.length > 0 && !input.force) {
        throw new PlanAlreadyExistsError(existing[0].id);
      }

      // 2. Insert new plan
      const [plan] = await tx.insert(weeklyPlans).values({
        projectId: input.projectId,
        year: input.targetYear,
        isoWeek: input.targetIsoWeek,
        weekStartDate: isoWeekStartDate(input.targetYear, input.targetIsoWeek),
        weekEndDate: isoWeekEndDate(input.targetYear, input.targetIsoWeek),
        status: "draft",
        estimatedCostEur: finalEstimate.bufferedEstimateEur.toFixed(2),
        inputSnapshot: snapshot,
        generationNotes: buildGenerationNotes(priorOutputs),
      }).returning();

      // 3. Insert planned_items
      const itemsToInsert = distributedItems.map(item => ({
        weeklyPlanId: plan.id,
        projectId: input.projectId,
        ...itemDraftToPersist(item),
      }));
      await tx.insert(plannedItems).values(itemsToInsert);

      // 4. If existing, mark superseded
      if (existing.length > 0) {
        await tx.update(weeklyPlans)
          .set({ status: "superseded", supersededAt: new Date(), supersededBy: plan.id })
          .where(eq(weeklyPlans.id, existing[0].id));
      }

      return {
        weeklyPlanId: plan.id,
        itemCount: itemsToInsert.length,
        estimatedCostEur: parseFloat(plan.estimatedCostEur),
        status: "draft" as const,
      };
    });
  }
}
```

## 8. Risiken

|---|---|
| ISO-Week-Handling falsch (Edge-Cases Year-Boundary) | Bestehende Helper aus codebase nutzen, `date-fns` o.ä. Tests für KW=1/53/Year-Wechsel |

| Sibling-Item Slot überschreitet Wochenende | Cluster am Sonntag → Sibling-Slot in nächste Woche. Spec sagt: skip, log warning. Marcel kann manuell anpassen via item-edit |
| Re-Generation mid-execution kollidiert (Plan läuft schon, jemand triggert force) | Status='running' supersede nur erlaubt wenn alle items in pending/cancelled. Sonst error |
| Idempotency-Cache aus 62.0a hält stale Plan-Steps | Plan-Steps sind nicht idempotency-key-tagged (kein BaseStep.idempotencyKey override). Cache greift nicht, jeder Run frisch. Korrekt für Planning |

| Test-Fixtures für topic_briefs sind aufwändig | Test-Helper `seedTestProject()` baut konsistente Fixtures. Pattern aus 62.2 |
| BaseStep + Idempotency-Cache: ein "deterministischer" Plan-Step (z.B. SnapshotInputs) hat Date.now() → cache key inconsistent | Plan-Steps haben keinen idempotencyKey, cache wird nicht gechecked |

## 11. Deviations from the original spec

Captured at implementation time so the spec body and the codebase don't drift.

1. **Supersede UPDATE runs BEFORE INSERT in `persistWeeklyPlanInTx`.** Spec §4.2.11 listed the order as "INSERT new plan → INSERT items → UPDATE prior to superseded". That order trips `weekly_plans_one_active_per_week` (both rows are active during the INSERT). The helper now UPDATEs the prior row first, then INSERTs the new one, then back-fills `supersededBy`. Documented as a workspace rule in [packages/db/CLAUDE.md](packages/db/CLAUDE.md).
2. **`draftId` used AS the `planned_items.id` value.** Spec §4.2.11 had a post-INSERT UPDATE pass to resolve sibling `parent_item_id` after the helper returned. That pass ran outside the helper's transaction (atomicity gap) and was N+1. Replaced by pre-allocating UUIDs in `PlanningItemDraft.draftId` and passing them as the `id` column on INSERT — `parent_item_id` is set inline. Documented as a workspace rule in [packages/pipelines/CLAUDE.md](packages/pipelines/CLAUDE.md).
3. **Sibling `skipAutoTranslationUntil` check moved to 62.8 executor.** Spec §4.2.7 checks `articles.skipAutoTranslationUntil` at planning time. The article doesn't exist yet for fresh cluster work (62.4 plans BEFORE generation), so we always emit the EN sibling at planning time. 62.8's per-item executor checks the flag on the freshly-generated DE article and marks the sibling item `skipped` if needed. Inline comment in [apply-sibling-locale.ts](packages/pipelines/src/planning/steps/apply-sibling-locale.ts).
4. **Budget overrun caught at `validate-goals` first.** Spec §4.2.10 wired `BudgetGateStep` as the budget hard-stop. In practice `validateProjectGoals` (step 1) already runs `estimateWeeklyPlanCost` on the goal expansion and throws `FLOOR_EXCEEDS_BUDGET` when the floor exceeds budget — `BudgetGateStep` is the second safety net. Integration scenario 3 asserts "no plan persists" regardless of which guard catches the overrun. `BudgetGateStep` still owns its unit test (per-type warnings + the explicit `BudgetExceededError` throw).
5. **`matchBriefToContentType` heuristic added.** Spec §4.2.5 left the brief→content-type routing rule open ("matchBriefToContentType"). Rule: `comparison_discovery` or `cluster_action='comparison'` → comparison; `translation` / `refresh` cluster_actions → null (handled outside 62.4); `standalone` + `intentType in ('knowledge','tutorial')` → ki_wissen; everything else → cluster. Exposed from the step file for future tuning.
6. **`PLANNER_HANDLED_SOURCES` defensive filter.** Spec §4.2.3 implied `loadPendingTopicBriefs` would return all pending briefs. The helper now also filters `source IN (5 known values)` so a future source enum value can't sneak into the planner before `matchBriefToContentType` learns to handle it. Kept in lockstep with the bucket logic in [select-floor-items.ts](packages/pipelines/src/planning/steps/select-floor-items.ts).
7. **`mergeAndTopN` pure helper extracted for testability.** Spec §4.2.6 referenced "top-N by normalized score". The sort+slice was inlined inside `computeSignalTopN` (DB-dependent), so directionality (best=1.0, worst=1/n) couldn't be unit-tested. Refactored to a pure helper with an explicit test that guards `SelectOverageItemsStep` against ever picking the worst signals.
8. **`ki_wissen` floor mapping uses `intentType`, not `clusterAction`.** Spec §4.2.5 didn't specify how briefs match the `ki_wissen` content type. Current rule: brief.intentType IN (`knowledge`, `tutorial`) AND `clusterAction='standalone'`. Tunable when real ki-wissen briefs flow through.

## 12. Discovered During Implementation

Things the spec didn't anticipate that future planning-related work should know.

- **`date-fns` is not in the workspace.** ISO-week math was hand-rolled in [`packages/planner/src/iso-week.ts`](packages/planner/src/iso-week.ts). 60 LoC, covered by year-boundary tests (KW1 of 2025 = 2024-12-30; KW53 of 2020). Adding date-fns later is fine but the hand-rolled helper has zero deps and is exhaustively tested — leave it.
- **`signal_sources` is a JSONB column on `project_configurations`, not its own table.** All signal source config lives in one JSONB blob keyed by `SignalSourcesSchema` in `project-config.ts`. The signal-refresh planner helper loads it once per call.
- **`numeric()` columns convention is `String(n)`, NOT `.toFixed(N)`.** Worked across `cost-tracker` already; the planner follows the same — `estimatedCostEur: estimate.bufferedEstimateEur.toFixed(2)` only because `.toFixed()` happens to produce a `string` here.
- **`c.var.user` is already typed via Hono `Variables`.** Other routes use `c.var.user?.email` directly without `as` casts; the `apps/api/src/routes/projects/plans.ts` initial draft had needless casts that were removed in /review-task.
- **`buildSignalFetcherMap()` is shared between routes and worker.** Originally inlined in `apps/api/src/routes/projects/signals.ts` for the 62.3 trigger endpoint; extracted to [`apps/api/src/lib/signal-fetcher-map.ts`](apps/api/src/lib/signal-fetcher-map.ts) so the PlanWeekPipeline worker can construct the same adapter wiring at pipeline-register time.
- **`Pipeline.bridge()` returning a minimal `{projectId}` shape is valid.** When most data flow happens via `ctx.getStepOutput(name)` because steps have multi-step dependencies (snapshot reads from validate-goals + refresh-signals + load-topic-briefs), the bridge can just return `{projectId, ...stepSpecific}` to satisfy each step's `inputSchema`. See `PlanWeekPipeline.bridge()` for the switch-on-toStep.name pattern.
- **CHECK constraints (not `pgEnum`) for status columns.** Following the 62.0a Lesson D12 ("text+CHECK rather than pgEnum"), `weekly_plans.status` and `planned_items.status` + `source_kind` use SQL `CHECK ... IN (...)`. The Drizzle `$type<>()` casts must stay in sync — `WEEKLY_PLAN_STATUSES` / `PLANNED_ITEM_STATUSES` arrays in [`packages/shared/src/types/weekly-plan.ts`](packages/shared/src/types/weekly-plan.ts) are the single source of truth.
- **`planned_items.pipeline_run_id` deliberately has no FK.** Following the same convention as other operations-table → content-table back-references (62.0a Lesson D), the column is a plain UUID with a partial index `WHERE pipeline_run_id IS NOT NULL`. The app layer reconciles when 62.8 wires execution.
