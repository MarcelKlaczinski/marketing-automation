# Spec E.1a — Article Refresh Tracking + Auto-Refresh Detection (Time + Quality)

**Theme:** Phase E (post-Theme-57 backlog)
**Status:** Sessions 1-6 complete (fully implemented)
**Estimated effort:** 5-6 days

---

## Goal

Replace the approximated `COALESCE(publishedAt, updatedAt)` refresh-staleness detection from Spec 56.6 with a proper `articles.lastRefreshedAt` column tracking when each article was last meaningfully refreshed. Add a quality-based refresh trigger: an LLM analyzes article content standalone and surfaces refresh suggestions with reasoning. Both time-based and quality-based triggers feed into the existing Refresh Queue UI (per 56.6), distinguished by a new `source` field and `reasoning` text.

## Non-Goals

- External-signal-based refresh triggering (deferred to Phase E.1b — needs production experience with B.1 first to calibrate)
- Comparison against web-search results (Strategy B.2 — deferred unless B.1 proves too thin)
- Tool-specific fact checking via DataForSEO (effectively Strategy C — Phase E.1b)
- Auto-execution of refresh (suggestions remain manual approval, matching 56.6 behavior)
- Refresh-quality scoring beyond "has reasoning" (no numeric quality score in this spec)
- Bulk approve/dismiss UI for refresh suggestions (Phase E backlog has this listed separately)

## Background

### Current State (post Theme 56 + 57)

From Spec 56.6 + memory pattern #16:

- `articles.lastRefreshedAt` column **doesn't exist** — was assumed in spec but never added
- Refresh-staleness today uses `COALESCE(publishedAt, updatedAt)` as approximation
- Refresh Queue UI exists, shows time-based suggestions
- `refresh_dismissed` table tracks user-dismissed suggestions per (article, source)
- `cron_state` table + orchestrator pattern exists (Spec 56.6) — runtime toggle via Settings
- SSE infrastructure via `usePipelineEvents` composable handles real-time updates

### Why This Spec

Three converging needs:

1. **Schema debt**: `COALESCE` approximation conflates "published" with "refreshed". When an article gets minor metadata edits (typo fix, frontmatter tweak), `updatedAt` changes — but the content didn't refresh. Real `lastRefreshedAt` requires deliberate signal.

2. **Pure time-based suggestions are weak**: "this article is 90 days old" tells you nothing about whether refresh is actually worth doing. An evergreen "history of computing" article aged 365 days needs less refresh than a "best AI tools 2025" article aged 30 days.

3. **Manual content audit doesn't scale**: Marcel has 268+ imported + 13+ generated articles. Manually reviewing each for refresh-need is hours of work. LLM standalone analysis is cheap (~€0.03/article via Sonnet) and surfaces concrete reasoning Marcel can decide on.

// packages/db/src/migrations/<num>_articles_last_refreshed_at.ts
export async function up(db: DrizzleDB) {
  await db.execute(sql`
    ALTER TABLE articles
      ADD COLUMN last_refreshed_at timestamp;

    -- Backfill: use publishedAt as initial lastRefreshedAt for existing articles
    -- Rationale: published articles have been "fresh" at publication time;
    -- treating publishedAt as initial refresh point matches user intent.
    -- Articles never published (drafts) stay NULL.
    UPDATE articles
    SET last_refreshed_at = published_at
    WHERE published_at IS NOT NULL;

    -- Index for staleness queries (replaces COALESCE-based approach)
    CREATE INDEX articles_last_refreshed_at_idx ON articles(last_refreshed_at)
      WHERE last_refreshed_at IS NOT NULL;
  `);
}
```

**Nullable column**: drafts can stay NULL until publish. Staleness queries treat NULL as "infinitely stale" (or filtered out — see A.4).

### A.4 Update Points — When to Bump `lastRefreshedAt`

The whole point of this column is **deliberate signal**. Updating it on every UPDATE defeats the purpose. Defined update points:

**Set to NOW() when:**
1. Article body content changes (markdown body, frontmatter SEO content) — via direct edit or pipeline regenerate
2. Article gets re-translated (54.10 translation pipeline produces refreshed sibling)
3. User manually marks article as refreshed via new UI action (Part C)
4. Refresh-suggestion approved AND user confirms refresh-complete

**Do NOT update on:**
- Status changes (draft → published etc.)
- Metadata-only changes (cluster assignment, tags reorder)
- Social-post additions (those don't refresh the article)
- Frontmatter changes that aren't body-content (publishedAt edit, slug change)

// BEFORE:
const staleArticles = await db
  .select()
  .from(articles)
  .where(
    and(
      eq(articles.status, "published"),
      lt(sql`COALESCE(${articles.publishedAt}, ${articles.updatedAt})`,

const staleArticles = await db
  .select()
  .from(articles)
  .where(
    and(
      eq(articles.status, "published"),
      isNotNull(articles.lastRefreshedAt),  // exclude drafts/never-refreshed
      lt(articles.lastRefreshedAt,
         sql`NOW() - INTERVAL '${sql.raw(thresholdDays)} days'`)
    )
  );
```

## Part B: Quality Analysis Pipeline

### B.1 Data Model: `refresh_suggestions` Extension

Per discovery — Spec 56.6 should have a refresh-suggestions table or similar. Verify:

```bash
# Find where refresh suggestions are stored today
grep -rn "refresh.*suggest\|refresh_suggest" packages/db/src/schema/
```

**Two possibilities**:

**Case 1**: Suggestions are computed on-the-fly (no table). UI queries staleness, displays.
→ This spec adds a table to persist quality-based suggestions (LLM output needs to live somewhere).

**Case 2**: A `refresh_suggestions` (or similarly named) table already exists from 56.6.
→ This spec extends it with `source` + `reasoning` fields.

**Assume Case 1 (table doesn't exist) unless Session 1 verification finds otherwise.** New table:

```sql
CREATE TYPE refresh_suggestion_source AS ENUM ('time', 'quality');

CREATE TABLE refresh_suggestions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  article_id uuid NOT NULL REFERENCES articles(id) ON DELETE CASCADE,
  source refresh_suggestion_source NOT NULL,
  reasoning text,                              -- nullable: time-based has no LLM reasoning
  staleness_days int,                          -- for source='time': how many days stale
  quality_findings jsonb,                      -- for source='quality': structured LLM output
  generated_at timestamp NOT NULL DEFAULT NOW(),
  dismissed_at timestamp,                      -- null = active suggestion
  approved_at timestamp,                       -- null = not yet approved
  approved_run_id uuid,                        -- FK to pipeline_runs once user triggers refresh
  CONSTRAINT refresh_suggestions_article_source UNIQUE (article_id, source)
);

CREATE INDEX refresh_suggestions_active_idx ON refresh_suggestions(article_id)
  WHERE dismissed_at IS NULL AND approved_at IS NULL;
```

**Unique constraint on `(article_id, source)`** means each article can have at most one time-based suggestion + one quality-based suggestion at a time. New analysis run for same article + source = UPDATE existing, not new row.

**`quality_findings` JSONB shape** (defined by LLM output schema):
```typescript
{
  outdatedClaims: Array<{ snippet: string; reason: string }>,
  missingCoverage: string[],                  // topics/tools the article doesn't cover but should
  staleReferences: Array<{ entity: string; note: string }>, // tools/products mentioned that may have changed
  overallRecommendation: "refresh-now" | "refresh-soon" | "no-action",
  confidence: "high" | "medium" | "low"
}
```

### B.2 BullMQ Queue: `article-quality-analysis`

Per memory pattern #31 (Theme 57): queue lives in producer package.

```typescript
// packages/pipelines/src/engine/article-quality-analysis-queue.ts
import { Queue } from "bullmq";

export type QualityAnalysisJobData = {
  articleId: string;
  projectId: string;
  triggeredBy: "manual-batch" | "cron";
};

export type QualityAnalysisJobResult = {
  articleId: string;
  recommendation: "refresh-now" | "refresh-soon" | "no-action";
  findingsCount: number;
};

export const articleQualityAnalysisQueue = new Queue<QualityAnalysisJobData, QualityAnalysisJobResult>(
  "article-quality-analysis",
  {
    connection: redisConnection,
    defaultJobOptions: {
      attempts: 2,
      backoff: { type: "fixed", delay: 5000 },
      removeOnComplete: { count: 100 },
      removeOnFail: { count: 200 },
    },
  }
);

export async function enqueueQualityAnalysis(data: QualityAnalysisJobData): Promise<string> {
  const job = await articleQualityAnalysisQueue.add("analyze", data, {
    jobId: `qa-${data.articleId}-${Date.now()}`, // allow re-analysis (no jobId-based dedup)
  });
  return job.id!;
}
```

**No jobId-based dedup** (unlike social-render): re-analyzing the same article later is desirable behavior (article body may have changed since prior analysis).

### B.3 Worker: Quality Analysis

```typescript
// apps/api/src/workers/article-quality-analysis.worker.ts
import { Worker } from "bullmq";
import { db } from "@marketing-auto/db";
import { articles, refreshSuggestions } from "@marketing-auto/db/schema";
import { eq, and } from "drizzle-orm";

export function startArticleQualityAnalysisWorker(logger: Logger) {
  const worker = new Worker<QualityAnalysisJobData, QualityAnalysisJobResult>(
    "article-quality-analysis",
    async (job) => {
      const { articleId, projectId } = job.data;

      const [article] = await db
        .select()
        .from(articles)
        .where(eq(articles.id, articleId))
        .limit(1);

      if (!article) {
        throw new Error(`Article not found: ${articleId}`);
      }

      // Compose LLM prompt
      const prompt = buildQualityAnalysisPrompt({
        title: article.title,
        body: article.body,        // markdown content
        frontmatter: article.frontmatter,
        locale: article.locale ?? "de-DE",
        publishedAt: article.publishedAt,
        lastRefreshedAt: article.lastRefreshedAt,
      });

      // NOTE: jsonMode: false per Memory #21 (Sonnet 4.6 rejects prefill)
      const response = await anthropic.messages({
        operation: COST_OPS.ARTICLE_QUALITY_ANALYSIS,
        model: "claude-sonnet-4-6",
        systemSuffix: "Return only valid JSON matching the schema. Be specific and actionable.",
        userMessage: prompt,
        maxTokens: 2000,
      });

      const parsed = parseJsonResponse(response.raw);  // raw.indexOf("{") pattern from Memory #21
      const findings = qualityFindingsSchema.parse(parsed);

      // Upsert refresh_suggestions row for source='quality'
      await db
        .insert(refreshSuggestions)
        .values({
          articleId,
          source: "quality",
          reasoning: buildReasoningString(findings),
          qualityFindings: findings,
        })
        .onConflictDoUpdate({
          target: [refreshSuggestions.articleId, refreshSuggestions.source],
          set: {
            reasoning: buildReasoningString(findings),
            qualityFindings: findings,
            generatedAt: new Date(),
            dismissedAt: null,    // reset dismissal — new analysis supersedes
            approvedAt: null,
          },
        });

      // Emit SSE
      emitSseEvent({
        type: "refresh.suggestion.created",
        articleId,
        projectId,
        source: "quality",
        recommendation: findings.overallRecommendation,
      });

      return {
        articleId,
        recommendation: findings.overallRecommendation,
        findingsCount: findings.outdatedClaims.length + findings.missingCoverage.length + findings.staleReferences.length,
      };
    },
    {
      connection: redisConnection,
      concurrency: 3,  // LLM calls don't block each other; 3 parallel is safe
    }
  );

  return worker;
}
```

### B.4 LLM Prompt

```typescript
// packages/pipelines/src/article-quality/prompt.ts

export function buildQualityAnalysisPrompt(input: {
  title: string;
  body: string;
  frontmatter: Record<string, any>;
  locale: string;
  publishedAt: Date | null;
  lastRefreshedAt: Date | null;
}): string {
  const daysSinceRefresh = input.lastRefreshedAt
    ? Math.floor((Date.now() - input.lastRefreshedAt.getTime()) / (1000 * 60 * 60 * 24))
    : "unknown";

  return `You are reviewing a published article to identify if it needs refreshing. Analyze for outdated claims, missing coverage, and stale references based on your general knowledge.

ARTICLE METADATA:
- Title: ${input.title}
- Locale: ${input.locale}
- Days since last refresh: ${daysSinceRefresh}
- Cluster/category: ${input.frontmatter.cluster ?? "n/a"}

ARTICLE BODY:
"""
${input.body.slice(0, 8000)}
${input.body.length > 8000 ? "\n[... article truncated for analysis ...]" : ""}
"""

ANALYSIS INSTRUCTIONS:
1. Identify outdated claims: factual statements that may have changed (pricing, features, market position, version numbers).
2. Identify missing coverage: topics, tools, or developments the article should cover but doesn't.
3. Identify stale references: mentions of tools, products, or companies that may have evolved.
4. Recommend an overall action: "refresh-now" (clearly outdated), "refresh-soon" (some staleness), or "no-action" (still accurate).
5. State your confidence: high (clear evidence), medium (some uncertainty), low (you're guessing).

IMPORTANT CONSTRAINTS:
- Only flag concrete issues. "Article is old" alone is NOT a finding — there must be specific outdated content.
- If the article is evergreen content (historical, conceptual, mathematical), recommend "no-action".
- Do not invent issues. If the article looks current, say so.
- Limit each finding's snippet to ~100 chars of relevant article text.

Return JSON matching this schema:
{
  "outdatedClaims": [{ "snippet": "...", "reason": "..." }],
  "missingCoverage": ["...", "..."],
  "staleReferences": [{ "entity": "...", "note": "..." }],
  "overallRecommendation": "refresh-now" | "refresh-soon" | "no-action",
  "confidence": "high" | "medium" | "low"
}`;
}

export function buildReasoningString(findings: QualityFindings): string {
  // Human-readable summary for UI display
  const parts: string[] = [];

  if (findings.overallRecommendation === "no-action") {
    return `LLM: No refresh needed (${findings.confidence} confidence)`;
  }

  if (findings.outdatedClaims.length > 0) {
    parts.push(`${findings.outdatedClaims.length} outdated claim(s)`);
  }
  if (findings.missingCoverage.length > 0) {
    parts.push(`${findings.missingCoverage.length} missing topic(s)`);
  }
  if (findings.staleReferences.length > 0) {
    parts.push(`${findings.staleReferences.length} stale reference(s)`);
  }

  return `${findings.overallRecommendation} (${findings.confidence}): ${parts.join(", ")}`;
}
```

  if (articleIds && articleIds.length > 0) {

      .where(and(

  for (const articleId of targetIds) {
    const jobId = await enqueueQualityAnalysis({
      articleId,
      projectId: project.id,
      triggeredBy: "manual-batch",
    });
    jobIds.push(jobId);
  }

  return res.json({
    enqueued: targetIds.length,
    estimatedCostEur: 0.03 * targetIds.length,
    jobIds,
  });
});

// GET /api/projects/:slug/refresh-suggestions
// Lists all active refresh suggestions for the project
router.get("/projects/:slug/refresh-suggestions", async (req, res) => {
  const project = await getProjectBySlug(req.params.slug);

  const suggestions = await db
    .select({
      suggestion: refreshSuggestions,
      article: {
        id: articles.id,
        title: articles.title,
        slug: articles.slug,
        locale: articles.locale,
        lastRefreshedAt: articles.lastRefreshedAt,
      },
    })
    .from(refreshSuggestions)
    .innerJoin(articles, eq(refreshSuggestions.articleId, articles.id))
    .where(and(
      eq(articles.projectId, project.id),
      isNull(refreshSuggestions.dismissedAt),
      isNull(refreshSuggestions.approvedAt)
    ))
    .orderBy(
      // High-priority quality findings first, then time-based
      sql`CASE
        WHEN ${refreshSuggestions.source} = 'quality' AND ${refreshSuggestions.qualityFindings}->>'overallRecommendation' = 'refresh-now' THEN 1
        WHEN ${refreshSuggestions.source} = 'quality' AND ${refreshSuggestions.qualityFindings}->>'overallRecommendation' = 'refresh-soon' THEN 2
        WHEN ${refreshSuggestions.source} = 'time' THEN 3
        ELSE 4
      END`,
      desc(refreshSuggestions.generatedAt)
    );

  return res.json(suggestions);
});

### C.3 Cron Toggle Integration

Per 56.6 pattern: add new cron handler to existing orchestrator.

```typescript
// packages/pipelines/src/cron/quality-analysis-cron.ts
export async function runQualityAnalysisCron(ctx: CronContext) {
  // Find articles published >= 30 days ago that haven't been quality-analyzed recently
  const dueArticles = await db
    .select({ id: articles.id, projectId: articles.projectId })
    .from(articles)
    .leftJoin(refreshSuggestions,
      and(
        eq(refreshSuggestions.articleId, articles.id),
        eq(refreshSuggestions.source, "quality")
      )
    )
    .where(and(
      eq(articles.status, "published"),
      isNotNull(articles.lastRefreshedAt),
      lt(articles.lastRefreshedAt, sql`NOW() - INTERVAL '30 days'`),
      or(
        isNull(refreshSuggestions.id),  // never analyzed
        lt(refreshSuggestions.generatedAt, sql`NOW() - INTERVAL '7 days'`)  // analyzed >7d ago
      )
    ))
    .limit(50);  // sanity bound — don't burst more than 50/run

  for (const article of dueArticles) {
    await enqueueQualityAnalysis({
      articleId: article.id,
      projectId: article.projectId,
      triggeredBy: "cron",
    });
  }

  ctx.logger.info("quality-analysis cron enqueued", { count: dueArticles.length });
}
```

**Registration in cron orchestrator**: per 56.6 pattern, registered as `disabled` (commented out) consistent with all other global crons. Marcel enables via Settings UI cron toggle.

## Discovered During Implementation

### Dual-shape BullMQ queue requires a union type + separate enqueue type
The spec described a single `ArticleQualityAnalysisJobData` type. The worker's cron-triggered batch path needed a different shape (`{ type: "cron-triggered", projectId }`) vs the per-article path (`{ articleId, projectId, projectSlug }`). Solution: `ArticleQualityAnalysisJobData` became a union; a separate `ArticleQualityAnalysisPerArticleData` type was exported for callers that only enqueue per-article jobs. This avoids exposing the internal cron shape to callers like the batch HTTP route. See `packages/pipelines/CLAUDE.md` → "Standalone BullMQ Workers" for the canonical pattern.

### Spreading two composables in setup() that both return `isLoading` causes collision
`RefreshQueuePage.vue` calls both `useRefreshCandidates()` and `useRefreshSuggestions()` in `setup()`. Both return `isLoading`. Spreading both (e.g. `{ ...useRefreshCandidates(), ...useRefreshSuggestions() }`) silently drops one. Workaround: return both without spread (use named keys), or disambiguate in a `computed` property. The page uses a `suggestionsLoading` computed that reads `(this as unknown as ...).isLoading.value` — acceptable for a one-off case but confirms the rule: do not merge two composables via `...spread` when both may return same-named fields.

### New SSE event type requires 3 file updates
Adding `refresh.suggestion.created` required: (1) `packages/core/src/events/pipeline-events.ts` (the PipelineEvent union), (2) `apps/web/src/types/ui.ts` (the PipelineEventType union), (3) `apps/web/src/composables/usePipelineEvents.ts` (addEventListener + handler). Missing any one causes either a TypeScript error or silent event loss. Per existing CLAUDE.md rule (which already documents this for other event types).

**Risk 6: SSE batch progress events overwhelm UI**
- *Mitigation*: Progress events fire every 10 articles (not per article). UI debounces updates to ~500ms. If still noisy, suppress and just show "running…" without exact counts.

**Risk 7: 56.6 refresh_dismissed table conflict with new refresh_suggestions table**
- *Mitigation*: Session 1 verification. If `refresh_dismissed` exists with overlapping responsibility, merge or migrate; do not duplicate.

## Discovered During Implementation (Sessions 1-2)

### D.1 `refresh_suggestions` needs `project_id`
Spec A.1 didn't include `project_id` on `refresh_suggestions`. Caught in `/review-task`. Every tenant-scoped table needs its own `project_id FK`, even child tables that already reference `articles.id`. The existing `refresh_dismissed` table was the reference — it has `project_id`. Fixed in migration 0053 and Drizzle schema before first commit.

### D.2 No `repos/` directory exists in `packages/db`
Spec A.5 placed `markArticleRefreshed` in `packages/db/src/repos/articles.repo.ts`. That directory doesn't exist. The established pattern is `packages/db/src/helpers/*-write.ts` (alongside `articles-read.ts`). Function placed there and exported via `packages/db/src/index.ts`.

### D.3 Body-edit call site: inline is cleaner than calling `markArticleRefreshed()`
Spec A.5 listed `apps/api/src/routes/articles/edit-body.routes.ts` as a `markArticleRefreshed()` call site. The actual body-edit handler is in `apps/api/src/routes/articles.ts` (`POST /:id/body`), and it already builds a `.set()` call. Adding `lastRefreshedAt: now` inline to that call is cleaner than calling a separate function — avoids a second DB round-trip and keeps the update atomic. `markArticleRefreshed()` is used where the call site doesn't own the initial `.set()` (Refresh pipeline `afterComplete`).

### D.4 `PersistBodyStep` is shared — cannot unconditionally set `lastRefreshedAt`
`PersistBodyStep` is used as an intermediate checkpoint in the blog pipeline (step 8 of 13) AND as the final write in the refresh pipeline (step 6 of 8). Setting `lastRefreshedAt` in the step itself would incorrectly mark every blog pipeline checkpoint as a refresh. Instead: `PersistArticleStep` sets it inline (blog + translation final persist), and `RefreshPipeline.afterComplete` calls `markArticleRefreshed()` after the pipeline succeeds.


### D.5 MessagesInput requires `systemPrefix` + `systemSuffix` + `userMessage` (not `system`/`messages`)
`systemPrefix: ""` is required even when unused — it cannot be omitted. The worker initially used `system:` and `messages:` fields which don't exist on MessagesInput, causing the adapter type-check to reject them. Fixed by using correct field names + providing empty string for prefix.

### D.6 Batch non-pipeline routes should call `assertCostBudget()` directly before the enqueue loop
The `triggerWithPreRunId` helper is pipeline-specific (manages pipeline_runs row + cost check + idempotency). BullMQ-only operations like batch quality analysis should call `assertCostBudget()` from `@marketing-auto/core/cost` directly in the route, returning 402 if budget exceeded. Caught when the batch endpoint needed pre-flight cost check.

### D.7 BullMQ worker dual-shape pattern — use Zod `.safeParse()` to discriminate between job types
The quality-analysis worker handles two job shapes in one queue: cron-batch `{ projectId, type: "cron-triggered" }` (fans out per-article jobs) and per-article `{ articleId, projectId, projectSlug }` (does the real work). Use Zod `.safeParse()` with a discriminated union or separate schemas to detect which shape arrived. This avoids creating a separate "dispatch" queue and keeps the worker simple.
