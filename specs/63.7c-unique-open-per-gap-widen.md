# Mini-Task 63.7c — Partial Unique Index `topic_briefs_unique_open_per_gap` um `plan_pending` erweitern

**Modus: DB-Migration. Kleines Code-Change (Drizzle-Schema-Sync optional). ~30 Min.**

**Voraussetzung: 63.7a Cleanup durch, 63.7b Code-Fix gemerged. Sonst tritt das Problem ggf. wieder auf bevor der Fix landet.**

## Kontext

Während des 63.7a Cleanups trat ein Partial-Unique-Index-Konflikt auf, der die ursprüngliche Strategie "plan_pending → pending" für 4 gap_analysis Briefs blockierte.

**Root cause:**

Der partial unique index `topic_briefs_unique_open_per_gap` wurde in Migration `0032_topic_briefs.sql` eingeführt:

```sql
CREATE UNIQUE INDEX "topic_briefs_unique_open_per_gap"
  ON "topic_briefs"("gap_id")
  WHERE "gap_id" IS NOT NULL
    AND "approval_status" IN ('pending', 'approved', 'auto_approved', 'routed');
```

Spec 63.6 hat den Status `plan_pending` als Zwischenzustand ("Marcel approved, awaiting Planner pickup") eingeführt — aber das `WHERE` des Index NICHT erweitert. Konsequenz: Gap-Detection sieht Briefs in `plan_pending` als "nicht mehr offen" und produziert legal neue Twin-Briefs für denselben `gap_id` mit `approval_status='pending'`. Wenn Marcel später diese plan_pending Briefs zurück in den Pool flippen will (Cleanup, Rejection-Reset, etc.), trippt der Index.

**Symptom 2026-05-21:**

```
ERROR: duplicate key value violates unique constraint "topic_briefs_unique_open_per_gap"
DETAIL: Key (gap_id)=(e0f1c362-...) already exists.
```

4 Toolwiki Briefs waren von 2026-05-21 19:54 bis 20:48 in `plan_pending`. In dieser Zeit lief Gap-Detection und erzeugte 4 frische pending-Twins. Der 63.7a Cleanup musste die Originals stattdessen `superseded` machen statt sie zurück in den Pool zu flippen.

## Ziel

Index-WHERE erweitern, sodass `plan_pending` als "offen" zählt:

```sql
WHERE "gap_id" IS NOT NULL
  AND "approval_status" IN ('pending', 'plan_pending', 'approved', 'auto_approved', 'routed');
```

Damit blockiert ein `plan_pending` Brief korrekterweise Twin-Erzeugung durch Gap-Detection.

## Aufgabe

### Phase 0 — Pre-Migration Audit

```sql
-- Sicherstellen, dass KEINE überlappenden (plan_pending, pending) Twins existieren,
-- sonst trippt die neue Index-Erstellung. Erwartung post-63.7a: 0 Konflikte.
SELECT
  gap_id,
  COUNT(*) AS rows_in_new_open_set,
  array_agg(approval_status) AS statuses,
  array_agg(id) AS brief_ids
FROM topic_briefs
WHERE gap_id IS NOT NULL
  AND approval_status IN ('pending', 'plan_pending', 'approved', 'auto_approved', 'routed')
GROUP BY gap_id
HAVING COUNT(*) > 1;
```

**Erwartung:** 0 Rows. Falls > 0: Konflikte zuerst aufräumen (analog zur 63.7a-Strategie: ältere/redundante Briefs auf `superseded`). Nach Aufräumen Audit wiederholen.

### Phase 1 — Migration `0084_topic_briefs_open_per_gap_widen.sql`

`DROP INDEX` + `CREATE UNIQUE INDEX` (PostgreSQL erlaubt kein `ALTER INDEX ... SET WHERE`).

```sql
-- Spec 63.7c — widen "open" set on topic_briefs_unique_open_per_gap
-- to include plan_pending (Spec 63.6 status added without index update).
DROP INDEX IF EXISTS "topic_briefs_unique_open_per_gap";

CREATE UNIQUE INDEX "topic_briefs_unique_open_per_gap"
  ON "topic_briefs"("gap_id")
  WHERE "gap_id" IS NOT NULL
    AND "approval_status" IN (
      'pending', 'plan_pending', 'approved', 'auto_approved', 'routed'
    );
```

Plus journal-Eintrag in `packages/db/drizzle/meta/_journal.json`:

```json
{ "idx": 84, "version": "7", "when": 1786200000000, "tag": "0084_topic_briefs_open_per_gap_widen", "breakpoints": true }
```

### Phase 2 — Drizzle-Schema-Sync (optional)

Der Index ist aktuell NICHT in `packages/db/src/schema/content.ts` deklariert (Migration 0032 hat ihn als raw SQL angelegt). Es gibt zwei Optionen:

**Option A — Status quo halten.** Der Index lebt weiter nur in SQL-Migration. Vorteil: minimal-invasiv. Nachteil: niemand sieht beim Schema-Lesen, dass es diesen Index gibt.

**Option B — Drizzle-Schema spiegeln.** Im `(t) => ({...})` Block von `topicBriefs` einen `uniqueIndex(...).where(sql\`...\`)` hinzufügen. Vorteil: SSoT. Nachteil: `drizzle-kit check` würde versuchen den Index im nächsten `generate`-Lauf neu zu erstellen (weil er nicht im Snapshot ist) — muss man manuell verifizieren.

**Empfehlung: Option A für 63.7c.** Die Migration ist klein und atomar. Drizzle-Schema-Sync kann ein eigener Aufräum-Spec sein, falls Marcel SSoT-Konsistenz erzwingen will (würde dann ALLE raw-SQL-only-Indizes betreffen, nicht nur diesen — eigener Scope).

### Phase 3 — Verifikation

```sql
-- Index existiert mit neuem WHERE?
SELECT indexdef FROM pg_indexes
WHERE schemaname='public'
  AND indexname='topic_briefs_unique_open_per_gap';
-- Erwartung: WHERE-Clause enthält 'plan_pending'

-- Smoke-Test: kann ich einen plan_pending Brief inserten und der blockiert dann pending Twin?
BEGIN;
  INSERT INTO topic_briefs (
    project_id, source, topic_title, cluster_action, approval_status, gap_id
  )
  VALUES (
    (SELECT id FROM projects WHERE slug='toolwiki'),
    'gap_analysis', 'TEST 63.7c smoke', 'append_to_existing',
    'plan_pending', gen_random_uuid()
  )
  RETURNING id, gap_id \gset

  -- Sollte FAIL mit unique constraint violation:
  INSERT INTO topic_briefs (
    project_id, source, topic_title, cluster_action, approval_status, gap_id
  )
  VALUES (
    (SELECT id FROM projects WHERE slug='toolwiki'),
    'gap_analysis', 'TEST 63.7c twin', 'append_to_existing',
    'pending', :'gap_id'
  );
ROLLBACK;
```

Erwartung: Zweites INSERT trippt mit `duplicate key value violates unique constraint`. Wenn nicht: Index hat den neuen Status nicht aufgenommen — Migration prüfen.

## Datenbank-Migration Rollout

- Bun-CLI: `bun run db:migrate` aus repo-root, picks up `0084_*.sql` automatisch.
- Worker-Restart **nicht nötig** — Index-Änderung ist transparent für die App, betrifft nur INSERT/UPDATE-Pfade von Gap-Detection.

## Anti-Patterns

- DROP INDEX in einer Transaction mit Bulk-INSERTs zu mischen — Index-Recreation kann auf großen Tabellen sehr lange dauern; in einer TX hängt das alles
- Den Index zu `CREATE INDEX IF NOT EXISTS` umändern statt vorher `DROP IF EXISTS` — PostgreSQL aktualisiert das `WHERE` nicht in-place
- Status zur Whitelist hinzufügen, der **nicht** als "blockierend für neue Twins" gedacht ist (z.B. `rejected`, `superseded`) — die "open"-Semantik des Index ist absichtlich eng

## Memory-Update Vorschlag

Bestehender D-Eintrag (62.0a Pattern 116-ähnlich) erweitern oder neuer Eintrag:

> Partial unique index `topic_briefs_unique_open_per_gap` (Migration 0032 + 0084) keyt auf `gap_id` mit dem "offen"-Set `{pending, plan_pending, approved, auto_approved, routed}`. Wenn `topic_briefs.approval_status` jemals einen weiteren "awaiting-action" Zwischenzustand kriegt (z.B. `awaiting_revision`), MUSS der Index in derselben Migration erweitert werden. Sonst produziert Gap-Detection legale Twin-Briefs für denselben Gap.
