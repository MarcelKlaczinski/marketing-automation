## Goal

Build a **source-aware Blog Generator** that converts approved topic briefs into draft blog articles with auto-assigned authors and intelligently linked tool references. The generator integrates into the existing Article Pipeline (Outline → Draft → SelfReview → Localize) but adds three Blog-specific capabilities:

1. **Source-aware prompt construction**: Different brief sources (`gap_analysis`, `trend_discovery`, `manual`) get different framing in Outline and Draft prompts, leveraging source-specific metadata (gap context, trend signals, manual hints).
2. **Author-Picker**: Score-based historic-pattern matching against existing blog articles (`articles WHERE collection='blog'`), with Voyage embedding fallback against author `expertise[]` for new clusters/intents. No LLM call.
3. **Tool-Linking**: Two-phase tool integration — pre-generation context injection (LLM gets relevant tools list) + post-draft markdown linkification (`ChatGPT` → `[ChatGPT](/tools/chatgpt)` for first occurrence per H2 section).

After this spec lands:
- Marcel can approve any blog-intent brief (from any source) → article enters generation pipeline → comes out with author assigned, tools linked, ready for review
- The 30 historical DE blog articles' author distribution informs all future author assignments
- Tool references in blog drafts are first-class markdown links, no manual cleanup needed
- Comparison-intent briefs (`intent_type='comparison'`) generate with a warning logged but proceed (per Q3 decision; clean separation deferred to comparisons-collection generator)
- **Per-article cost target: ~€1.17 (Sonnet for Outline+Draft, Haiku for SelfReview)** — validated with voice-quality smoke test in Session 5, with Opus upgrade path documented if needed

## What this is NOT

- Not a refresh-mode generator (article modifications) — that's Spec 54.10
- Not a translation-mode generator (DE→EN sibling creation) — that's Spec 54.10
- Not a comparisons-collection generator — those briefs route here with a warning; clean separation in 54.9b (Phase E backlog)
- Not a ki-wissen, usecases, or tool-categories generator — Phase E backlog specs
- Not a Hero-Image generation step — uses existing `HeroImageStep` from article pipeline unchanged
- Not a Cornerstone-Spec generator — `create_cornerstone_spec` routing kind unchanged
- Not changing the existing `executeDecision` routing logic
- Not adding new UI — generator runs server-side via existing article pipeline triggers
- Not promoting more fields to dedicated columns (deferred to backlog)
- Not building author profile pages or expertise editing UI
- Not introducing a new `blog_articles` table or splitting `articles` table

### Source-aware prompt construction (Deliverables 3+4)

The `OutlineStep` and `DraftStep` currently take a single prompt template per step. Spec 54.9 adds a **source-context section** that gets interpolated into the existing prompts based on `brief.source`.

Three new prompt fragments:

```typescript
// packages/pipelines/src/article/outline/prompts.ts

function buildSourceContextFragment(brief: TopicBrief): string {
  switch (brief.source) {
    case "gap_analysis":
      return buildGapContextFragment(brief.gapMetadata);
    case "trend_discovery":
      return buildTrendContextFragment(brief.trendMetadata);
    case "manual":
      return ""; // No source-specific framing; uses brief fields as-is
    case "refresh_detection":
      // Should not reach here in 54.9 (refresh is 54.10); throw defensively
      throw new Error("refresh_detection briefs are not handled by blog generator yet");
    default:
      return "";
  }
}

function buildGapContextFragment(gap: GapMetadata): string {
  return `
**Cluster Context:**
This article fills a gap in the existing content cluster "${gap.clusterName}".
${gap.spokesPresent ? `Existing articles in this cluster: ${gap.spokesPresent.join(", ")}.` : ""}
The article should complement (not duplicate) these existing pieces.
Gap type: ${gap.gapType}.
${gap.suggestedCornerstoneKeyword ? `Suggested cornerstone keyword: "${gap.suggestedCornerstoneKeyword}".` : ""}
`;
}

function buildTrendContextFragment(trend: TrendMetadata): string {
  const sourceList = trend.signals.map(s => s.source).filter((v, i, a) => a.indexOf(v) === i).join(", ");
  return `
**Trend Context:**
This article responds to a current trend (freshness: ${trend.freshnessWindow}).
Trend score: ${trend.trendScore}/100.
Detected via: ${sourceList} (${trend.signals.length} signals).
${trend.relatedEvent ? `Related event: ${trend.relatedEvent}.` : ""}
Lead with the timely angle. Don't bury the news in evergreen framing.
`;
}
```

These fragments get inserted into the existing outline/draft prompt at a designated `{{SOURCE_CONTEXT}}` placeholder. If the placeholder isn't in the master prompt (legacy projects), the fragment is silently dropped.

For toolwiki specifically, master prompts will be updated to include `{{SOURCE_CONTEXT}}` between project context and brief context sections.

**Step 1: Historic Score (primary)**

```typescript
// packages/pipelines/src/article/author-picker/historic.ts

export async function historicAuthorScore(
  projectId: string,
  clusterKey: string | null,
  intentType: string | null,
  locale: "de" | "en",
): Promise<Array<{ slug: string; score: number; matchedOnCluster: number; matchedOnIntent: number; totalPosts: number }>> {
  // Query: for each author who has written blog articles, count:
  //  - matchedOnCluster: posts with same clusterKey
  //  - matchedOnIntent: posts with same intentType
  //  - totalPosts: total blog posts (for tie-breaking)
  // Score = (matchedOnCluster * 3) + (matchedOnIntent * 2) + (totalPosts * 0.1)
  // Returns top 5 by score, with explicit breakdown
}
```

SQL implementation (concrete query):

```sql
SELECT
  a.author AS slug,
  COUNT(*) FILTER (WHERE a.cluster_key = $cluster_key) AS matched_on_cluster,
  COUNT(*) FILTER (WHERE a.intent_type = $intent_type) AS matched_on_intent,
  COUNT(*) AS total_posts
FROM articles a
WHERE a.project_id = $project_id
  AND a.collection = 'blog'
  AND a.source = 'imported'  -- only historical data, not freshly generated
  AND a.author IS NOT NULL
  AND a.author NOT LIKE 'toolwiki%'  -- exclude org placeholders
  AND a.locale = $locale
GROUP BY a.author
HAVING COUNT(*) > 0
ORDER BY
  (COUNT(*) FILTER (WHERE a.cluster_key = $cluster_key) * 3) +
  (COUNT(*) FILTER (WHERE a.intent_type = $intent_type) * 2) +
  (COUNT(*) * 0.1) DESC
LIMIT 5;
```

If the top result has `matched_on_cluster + matched_on_intent >= 1` (some historic signal), return it. Otherwise, fall through to embedding fallback.

**Step 2: Embedding Fallback (secondary)**

```typescript
// packages/pipelines/src/article/author-picker/embedding.ts

export async function embeddingAuthorMatch(
  projectId: string,
  brief: TopicBrief,
  locale: "de" | "en",
): Promise<{ slug: string; name: string; score: number } | null> {
  // 1. Build query text from brief: topic_title + primary_keyword + first 3 secondary_keywords
  // 2. Compute Voyage embedding for query text
  // 3. For each author in `articles WHERE collection='authors' AND locale=?`:
  //    - Read expertise[] from frontmatter_extras
  //    - Compute Voyage embedding for joined expertise string
  //    - Cache embedding per author (don't recompute every time)
  // 4. Compute cosine similarity, return top match if similarity > 0.55
  // 5. Return null if no match passes threshold
}
```

**Caching note**: Author expertise embeddings change rarely (only when MDX is updated and re-imported). Cache them in a new column `frontmatter_extras.expertiseEmbedding` (JSONB) or in Redis with key `author:{slug}:{locale}:expertise:embedding`. For toolwiki: 10 author embeddings cached after first call; subsequent author-picks for new clusters cost ~€0.0001 (one query embedding) + 10 cosine ops.

**Step 3: Default Fallback (tertiary)**

If both historic SQL returns nothing useful AND embedding match fails:
- For DE: default to `anna-weidner` (highest blog post count in audit)
- For EN: default to `anna-weidner` (locale sibling exists)

Document this in DB as `matchStrategy: "default_fallback"` for audit trail. Log a warning so Marcel can see when author-picking fell to defaults.

**Cost**:
- Historic SQL: ~$0 (one indexed query, ~ms)
- Embedding fallback: ~€0.0001 per brief (one query embed + cached author embeds)
- Default fallback: ~$0

Per cluster lifetime: typically <1 embedding call (first article in cluster) then all historic.

**Phase 2: Post-Draft Linkification**

```typescript
// packages/pipelines/src/article/tool-linker/post-generation.ts

export async function linkifyMarkdown(
  bodyMd: string,
  projectId: string,
  locale: "de" | "en",
): Promise<{
  bodyMd: string;       // modified markdown
  linksAdded: number;
  linkedTools: string[]; // slugs of tools that got linked
}> {
  // 1. Fetch all tools for project + locale (108 in toolwiki)
  // 2. Build name-to-slug map: { "ChatGPT": "chatgpt", "Claude": "claude", ... }
  //    - Use exact title match (case-sensitive for unique names)
  //    - Include common aliases (Claude → claude, GPT-4 → chatgpt if frontmatter_extras has aliases field, etc.)
  // 3. Parse markdown by H2 sections (split on /^## /m)
  // 4. For each section:
  //    - Track which tools have already been linked in this section
  //    - For each tool name in the name-to-slug map:
  //      - Find FIRST occurrence in section that is NOT already inside markdown link `[...](...)` or code block
  //      - Replace with [Name](/tools/slug)
  //      - Mark this tool as linked-in-this-section
  // 5. Return modified bodyMd + linksAdded count + which tools got linked
}
```

**Linkification rules**:
- Skip if already linked: regex check `\[[^\]]*Name[^\]]*\]\(` before replacing
- Skip inside code blocks: track ``` fences
- Skip inside existing markdown links: `[text](url)` patterns left alone
- Skip inside inline code: `` `text` `` patterns left alone
- Case-sensitive matching to avoid linking "claude" (lowercase) when only "Claude" should link
- First-occurrence-per-section only (avoids over-linking; SEO best practice)
- URL pattern: `/de/tools/{slug}` for DE, `/en/tools/{slug}` for EN (verify against toolwiki URL convention)

**Edge cases to handle**:
- Tool name appears in heading (e.g., `## ChatGPT vs Claude`) — DO link in heading
- Tool name is part of larger word (e.g., "OpenAI's ChatGPT") — link "ChatGPT" only, leave "OpenAI's"
- Same tool name in DE + EN tool entries with same slug — match locale's name only

**Costs**: $0 — pure string manipulation, no LLM.

### Blog Pipeline orchestration (Deliverable 5)

```typescript
// packages/pipelines/src/article/blog/pipeline.ts

export interface BlogPipelineInput {
  briefId: string;
  projectId: string;
  pipelineRunId: string;
}

export interface BlogPipelineOutput {
  articleId: string;
  authorSlug: string;
  authorPickStrategy: "historic_score" | "embedding_fallback" | "default_fallback";
  toolsLinked: string[];
  warnings: string[];  // e.g., "comparison intent passed through without proper handling"
}

export async function runBlogPipeline(
  input: BlogPipelineInput,
): Promise<BlogPipelineOutput> {
  const warnings: string[] = [];

  // 1. Load brief
  const brief = await loadBrief(input.briefId);

  // 2. Q3: warn if comparison intent
  if (brief.intentType === "comparison") {
    warnings.push("comparison intent passed through blog generator; consider 54.9b for proper comparisons-collection routing");
    log.warn({ briefId: brief.id }, "comparison-intent brief in blog generator");
  }

  // 3. Pick author
  const author = await pickAuthor(input.projectId, brief);

  // 4. Resolve relevant tools
  const tools = await resolveRelevantTools(input.projectId, brief, brief.locale);

  // 5. Run Outline step with source context + tools context
  const outline = await runOutlineStep({
    brief,
    sourceContext: buildSourceContextFragment(brief),
    toolsContext: buildToolsContextFragment(tools),
    pipelineRunId: input.pipelineRunId,
  });

  // 6. Run Draft step
  const draft = await runDraftStep({
    brief,
    outline,
    sourceContext: buildSourceContextFragment(brief),
    toolsContext: buildToolsContextFragment(tools),
    pipelineRunId: input.pipelineRunId,
  });

  // 7. Linkify
  const linkified = await linkifyMarkdown(draft.bodyMd, input.projectId, brief.locale);

  // 8. Persist article with author
  const article = await persistArticle({
    brief,
    outline,
    bodyMd: linkified.bodyMd,
    author: author.authorSlug,
    metadata: {
      authorPickStrategy: author.matchStrategy,
      toolsLinked: linkified.linkedTools,
      warnings,
    },
  });

  // 9. Run remaining existing steps (SelfReview, SchemaExtension, etc.)
  await runSelfReviewStep({ articleId: article.id, pipelineRunId: input.pipelineRunId });
  await runSchemaExtensionStep({ articleId: article.id });
  // HeroImage handled by chain orchestrator

  return {
    articleId: article.id,
    authorSlug: author.authorSlug,
    authorPickStrategy: author.matchStrategy,
    toolsLinked: linkified.linkedTools,
    warnings,
  };
}
```

### Linkification — concrete algorithm

```typescript
// packages/pipelines/src/article/tool-linker/post-generation.ts

import type { Article } from "@marketing-auto/db";

const CODE_FENCE = /^```/;
const MARKDOWN_LINK = /\[([^\]]+)\]\(([^)]+)\)/g;
const INLINE_CODE = /`[^`]+`/g;

export async function linkifyMarkdown(
  bodyMd: string,
  projectId: string,
  locale: "de" | "en",
): Promise<LinkifyResult> {
  // 1. Fetch all tools for this project + locale
  const tools = await fetchAllTools(projectId, locale);  // Array<{slug, name}>

  // 2. Build name regex (case-sensitive, word-boundary)
  //    Sort by length DESC so "GitHub Copilot" matches before "GitHub"
  const sortedTools = tools.sort((a, b) => b.name.length - a.name.length);

  // 3. Split markdown by H2 sections (preserving the headers)
  const sections = splitByH2(bodyMd);

  // 4. Process each section
  const linkedTools = new Set<string>();
  let linksAdded = 0;
  const processedSections = sections.map(section => {
    const linkedInThisSection = new Set<string>();
    const result = processSection(section, sortedTools, locale, linkedInThisSection);
    linkedInThisSection.forEach(slug => linkedTools.add(slug));
    linksAdded += linkedInThisSection.size;
    return result;
  });

  return {
    bodyMd: processedSections.join(""),
    linksAdded,
    linkedTools: Array.from(linkedTools),
  };
}

function processSection(
  section: string,
  tools: Array<{ slug: string; name: string }>,
  locale: "de" | "en",
  linkedInThisSection: Set<string>,
): string {
  let result = section;
  let inCodeBlock = false;

  // Token-by-token approach (line-level for code blocks, regex for inline)
  // Simplified pseudocode here; real implementation tokenizes properly

  for (const tool of tools) {
    if (linkedInThisSection.has(tool.slug)) continue;

    // Build regex: word boundary + literal name + word boundary
    const regex = new RegExp(`\\b${escapeRegex(tool.name)}\\b`, "");
    const match = result.match(regex);

    if (!match) continue;

    // Check if match is inside code block or existing link or inline code
    const matchIndex = result.indexOf(match[0]);
    if (isInsideCodeOrLink(result, matchIndex)) continue;

    // Replace first occurrence with markdown link
    const url = `/${locale}/tools/${tool.slug}`;
    result = result.replace(regex, `[${tool.name}](${url})`);
    linkedInThisSection.add(tool.slug);
  }

  return result;
}
```

`isInsideCodeOrLink` is the tricky bit — needs proper markdown-aware parsing. Recommended: use `marked` or `remark` AST traversal instead of regex-only, but if that pulls too many dependencies, a simpler line-based heuristic works (track ``` fences, skip lines starting with `    ` for indented code, regex-detect existing links).

Reference implementation lesson from existing `LinkRebuildStep` (Spec 24) in `packages/pipelines/src/internal-linking/` — that step already linkifies internal article links. The tool linker can reuse its markdown parsing infrastructure.

): Promise<Array<typeof articles.$inferSelect>> {
  return await db.select().from(articles)
    .where(and(
      eq(articles.projectId, projectId),
      eq(articles.collection, "tools"),
      eq(articles.clusterKey, clusterKey),
      eq(articles.locale, locale),
    ))
    .orderBy(desc(articles.toolRating));
}

export async function listAuthorsByLocale(
  projectId: string,
  locale: Locale,
): Promise<Array<{ slug: string; name: string; expertise: string[]; expertiseEmbedding?: number[] }>> {
  const rows = await db.select().from(articles)
    .where(and(
      eq(articles.projectId, projectId),
      eq(articles.collection, "authors"),
      eq(articles.locale, locale),
    ));
  return rows.map(r => {
    const extras = (r.frontmatterExtras ?? {}) as Record<string, unknown>;
    return {
      slug: r.slug,
      name: r.title ?? String(extras.name ?? ""),
      expertise: Array.isArray(extras.expertise) ? extras.expertise as string[] : [],
      expertiseEmbedding: Array.isArray(extras.expertiseEmbedding)
        ? extras.expertiseEmbedding as number[]
        : undefined,
    };
  });
}
```

## Open Questions / Decisions Made

**Decision 1: Source-aware prompt fragments, not entirely separate prompts.**
Per Q2(c). Three brief sources × two steps (outline+draft) = 6 specialized prompt sections instead of 6 totally separate prompts. Reuse maximally; differentiate only in source-context fragment. Maintainability wins over edge-case optimization.

**Decision 2: Author-Picker is SQL-first, embedding-fallback, no LLM.**
Per Q4(c) + (α). Historic data is most reliable signal. Embedding handles cold-start. LLM author selection adds cost without measurable quality gain over score-based.

**Decision 3: Tool-Linking is two-phase, post-draft linkification is pure string ops.**
Per Q5(d). Pre-generation context teaches the LLM which tools to mention; post-generation linkifier handles syntax mechanically. No LLM round-trip needed for linkification.

**Decision 4: Comparison-intent briefs pass through with warning.**
Per Q3(c). Don't strand briefs awaiting 54.9b. Warning surfaces in logs and in article metadata so Marcel can see and route manually.

**Decision 5: Refresh and translation are explicitly NOT in 54.9.**
Per Q1(a). Separate spec (54.10) for those, building on the foundation.

**Decision 6: Hero-image step unchanged.**
Existing `HeroImageStep` is collection-agnostic and produces images from brief's `hero_image_prompt`. No reason to fork.

**Decision 7: Master prompt placeholders required, not optional.**
Toolwiki master prompts MUST be updated to include `{{SOURCE_CONTEXT}}` and `{{TOOLS_CONTEXT}}` for 54.9 to produce its expected output. Migration script handles this for toolwiki; other projects get default behavior (no source/tools context, behaves like current pipeline).

**Decision 8: Tool-Linker uses existing markdown parsing infra from Spec 24's LinkRebuildStep.**
Reuse `remark` AST or similar from internal-linking module if available. Avoid pulling in new dependencies. If LinkRebuildStep uses pure regex, tool-linker matches that style.

**Decision 9: Cost target ~€2.98 per blog article is the planning estimate, not hard limit.**
Variance ±20% expected based on brief complexity. Hard budget enforced via `costLimits` on project, not per-article.

**Decision 10: No new article status enum values.**
Generated articles keep existing status flow: `proposed` → `outline_done` → `draft_done` → `self_review_done` → `published` (or whichever exact enum values exist). Blog pipeline just orchestrates these transitions.

**Decision 11: Author embedding cached in JSONB, not in dedicated column.**
Storage: `frontmatter_extras.expertiseEmbedding` (1024-element number array). Per author: ~8KB. 10 authors × 8KB = 80KB total. No need for vector column with HNSW index — 10 cosine ops per pick is trivial.

**Decision 12: Linkification is locale-aware.**
DE blog gets `/de/tools/slug`, EN blog gets `/en/tools/slug`. Tool slugs are locale-stable (same `chatgpt` slug for DE and EN tools).

**Decision 13: Tool-Linker queries `articles WHERE collection='tools'` directly, not via helper.**
The helper `listToolsByCategory` is for category-bounded lists. The linkifier needs ALL tools (108 for toolwiki). Direct query is more efficient than a cascading set of helper calls.

**Decision 14: Author-pick output stored in article's metadata column.**
Optional but valuable for audit: `articles.metadata` or `frontmatterExtras.authorPickStrategy`. Helps debugging "why was X chosen as author?"

**Decision 15: Model selection per step — Sonnet for generation, Haiku for classification.**

Step-by-step model selection diverges from the original article pipeline (which uses Opus across the board):

| Step | Model | Why |
|---|---|---|
| Outline | Sonnet 4.6 | Strategic structure + source-aware adaptation. Strong enough; Opus overkill. |
| Draft | Sonnet 4.6 | Voice + differentiation matters; pilot with Sonnet, validate in Session 5 manual smoke test, upgrade to Opus only if voice flattens (per Decision 16). |
| SelfReview | Haiku 4.5 | Pure classification: severity (3 values) × category (9 values) + location text. Haiku exzellent for this; ~10x cheaper than Opus. |
| Schema Extension | Sonnet 4.6 | Unchanged from existing pipeline. |
| Hero Image | Replicate SDXL | Unchanged. |

This reduces per-article cost from €2.98 (all-Opus) to ~€1.17. Annual savings at 30 articles/month: ~€650. At 100 articles/month: ~€2200.

The decision intentionally deviates from `COST_OPS.ARTICLE_OUTLINE` (€0.50 Opus estimate) and `ARTICLE_DRAFT` (€1.50 Opus estimate) — those constants describe the legacy generic article pipeline. Blog pipeline gets its own cost-op constants if needed, or reuses them with overridden estimates per pipeline.

**Decision 16: Voice-quality validation in Session 5 smoke test.**

Sonnet for Draft is the **planning assumption**, not a guaranteed final choice. Toolwiki's brand voice (pragmatic, anti-hype, differentiated recommendations) is the quality bar.

Validation procedure during Session 5 manual smoke test:
1. Generate 3 articles using Sonnet Draft (one each for `gap_analysis`, `trend_discovery`, `manual` source)
2. Marcel reviews against 2-3 reference imported blog articles (e.g., `ai-agents-2026-claude-operator-atlas-vergleich.mdx`)
3. Marcel evaluates: voice match, anti-hype tone, differentiated angle, anglicism level, concrete €/$ examples
4. **If Sonnet Draft is acceptable**: ship as-is, document evaluation
5. **If Sonnet Draft is noticeably flat**: switch Draft step to Opus 4.7 via single config change in `packages/pipelines/src/article/draft/pipeline.ts`. Cost goes back up by ~€1.10 per article. Document the upgrade trigger.

Cost of validation: ~€3.50 for 3 test articles. Cheaper than committing to a wrong choice for months.

**Decision 17: SelfReview categorization with Haiku — no change to issue schema.**

`SelfReviewIssue` Zod schema (from codebase-reference.md, Section 2):
- severity: critical/warning/suggestion (3 enum values)
- category: 9 enum values (voice_drift, factual_concern, weak_intro, etc.)
- location: free-text describing where in article
- description + suggestion: short text

Haiku handles this output shape natively with strict JSON mode. No schema modifications needed; only the model parameter in the SelfReview step changes from Opus to Haiku.

## Discovered During Implementation

**`buildSourceContextFragment` is synchronous — never wrap in `Promise.all`**

The function does pure string interpolation with no I/O. An initial `Promise.all([resolveRelevantTools(...), Promise.resolve(buildSourceContextFragment(...))])` pattern was introduced in `ToolRelevanceStep` and caught in review. Fix: call sync function directly, await the async one separately. Symptom of the mistake: no runtime error, but unnecessary micro-task overhead and confusing code.

**`ToolLinkerStep` always runs in `BlogPipeline` — no fallback to draft output**

The pipeline bridge for `assembly → persist-article` originally had `getStepOutput("tool-linker") ?? getStepOutput("draft")!`. The fallback is wrong: `ToolLinkerStep` is step 9 and always executes; a fallback to draft silently corrupts the body if it ever fires. Fixed to `getStepOutput("tool-linker")!` with an explanatory comment.

**`translation_created` routing kind must be excluded from `isBlogBrief` detection**

Translation briefs have both `locale !== null` and `clusterId !== null`, so a naive `isBlogBrief` check routes them to `article:blog`. Translation mode is out of scope for 54.9 (Spec 54.10). Fix: gate on `routeResult.kind === "article_created" && brief.locale !== null && brief.clusterId !== null`. Found and fixed in the Session 5+6 review pass.

## Deviations

**Session 1 — `listToolsByClusterId` instead of `listToolsByClusterKey`**

Spec pseudocode (line 647) referenced `listToolsByClusterKey(clusterKey: string)` matching on `articles.cluster_key` (frontmatter text). Implementation uses `listToolsByClusterId(clusterId: string)` matching on `articles.cluster_id` (UUID FK). Reason: the FK is the authoritative link between articles and clusters; `cluster_key` is a denormalized string from Astro frontmatter that may not be set on newly generated articles. `TopicBrief.clusterId` (UUID) maps directly to `articles.cluster_id`. More robust, no behaviour change for callers.

**Sessions 4–5 — `BlogPipelineInput` uses `articleId`, not `briefId` alone**

Spec shows `BlogPipelineInput = { briefId, projectId, pipelineRunId }`. Implementation is `{ articleId, projectId, briefId, modelOverride? }`. The article row is created by `enqueueBlogGeneration` (or `executeDecision`) before the pipeline is enqueued, so `articleId` is known at enqueue time and passed directly. `pipelineRunId` is injected by the pipeline engine, not passed as caller input — this is consistent with all other article pipelines in the codebase.

**Session 5 — `/automate` still uses `article:outline`, not `article:blog`**

Spec says to hook into the chain orchestrator's trigger function. Instead, only `/generate` and the trend-brief approval endpoint route to `article:blog`. The `/automate` endpoint (`startChain()`) still enqueues `article:outline` as chain step 1. Reason: adding `"blog"` to the `ChainStep` DB enum requires a migration, deferred to Spec 54.10. Impact: briefs approved via `/automate` go through the old outline+draft pipeline chain, not the new 13-step blog pipeline. This is intentional and documented in `apps/api/CLAUDE.md`.
