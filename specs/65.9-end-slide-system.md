_Pluggable end-slide-components für alle Theme 65 carousels. Letzter slide jedes carousels._

## 1. Mental Model

**Was 65.9 IST:**

7 pluggable end-slide-components die als **last slide** jedes Theme 65 carousels gerendered werden. Selection-logic picks one per render based on:
1. Definition's `endSlideStrategy` (already in schema per 65.1)
2. Definition's `end_slide_pool` (array of end_slide_definition IDs)
3. Format-type's `defaultEndSlides` (from 65.4 registry as fallback pool)
4. LRU tracking via existing `template_usage_log` extension OR new column

**Was 65.9 NICHT IST:**

- Kein ManyChat-wire-up (→ 65.13)
- Kein Settings-UI für CRUD (→ V1.1 / 65.11)
- Kein impact auf existing brief-generators beyond endSlide-selection hook
- Kein animation (static slides V1)

**Strategischer Fit:**

- **Last carousel-component before V1-launch** — alle other templates rendern through this
- Etabliert **pluggable-component pattern** im template-system
- Etabliert **comment-to-get CTA-pattern** der in 65.13 (ManyChat) wire-up bekommt
- Schließt **engagement-loop**: Cover hook viewers, End-slide drives action

## 3. Architecture Decisions

### 3.1 Render-Architecture Evaluation (Marcel: Discovery evaluiert)

**Option α — End-Slides als eigene Remotion-Compositions (own template-registry entries):**

```typescript
// Each end-slide-type registered as standalone template:
packages/social/src/end-slide-templates/
├── follow-cta/
│   ├── composition.tsx
│   └── template.config.ts
├── comment-to-get/
├── link-in-bio/
└── ... etc
```

Pros:
- End-slides could be rendered standalone (e.g. as own Story posts)
- Clean separation in template-registry
- Each end-slide has own preview-endpoint

Cons:
- 7 new entries in `templates` DB-table cluttering Settings-UI Templates-Page
- Render-pipeline becomes 2-stage (compose end-slide separately, then composite)
- Filesystem-sync churn

**Option β — End-Slides als data-binding-layer auf existing carousel templates:**

End-slides aren't components at all — just data-fields on the parent template's last slide.

```typescript
// composition.tsx of carousel-template
<LastSlide
  type={endSlideData.type}
  payload={endSlideData.payload}
/>
// LastSlide internally switch-case renders based on type
```

Pros:
- No new component-tree
- All rendering happens in one composition
- Easier to ensure visual-consistency with carousel theme

Cons:
- LastSlide-component becomes 7-way switch-case
- Hard to test end-slide-types in isolation
- Less pluggable — adding new end-slide-type requires changing LastSlide in every template

**Option γ — End-Slides als shared React components (composed into any template):**

```typescript
// packages/social/src/end-slide-components/
├── shared/
│   ├── EndSlideBase.tsx        # provides bg, theme, layout common to all
│   └── types.ts                # EndSlideData discriminated union
├── FollowCtaSlide.tsx
├── CommentToGetSlide.tsx
├── LinkInBioSlide.tsx
├── TagFriendSlide.tsx
├── SaveShareCtaSlide.tsx
├── SwipeUpSlide.tsx
└── HostSlide.tsx               # dispatches to correct sub-component
```

Each end-slide is a React-component with typed props (no Remotion-composition layer).

Pros:
- Each template imports `<HostSlide>` and renders its last frame
- End-slides aren't templates themselves — they're slide-components like Cover, Verdict
- Easy to add new types (just new component)
- Isolated testing per component
- Bi-theme propagation naturally inherits from parent template

Cons:
- Not as decoupled as Option α (still coupled to carousel-template render-loop)
- No standalone-preview unless we add separate preview-endpoint

### Discovery-Recommendation: **Option γ (Shared React components)**

Reasoning:

1. **Symmetric with 65.7's slide-component pattern** — Cover, Compare-Header, Tool, Verdict, EndSlide are all React-components, EndSlide is just one more
2. **No template-registry pollution** — end-slides aren't user-facing in Templates-Page
3. **Bi-theme inheritance** — parent template's CSS-vars cascade naturally
4. **Discriminated-union props** — type-safe at compile-time
5. **Pluggable via dispatching component** — `<HostSlide>` does `switch (data.type)` once, sub-components stay pure
6. **Easy V1.1 path** — when Settings-UI lands, CRUD acts on `end_slide_definitions` rows; components don't need changes

**Trade-off accepted:** Not standalone-renderable as own carousel-post. V1.5 if needed: add `<StandaloneEndSlideHost>` wrapper.

### 3.3 End-Slide-Selection Logic

```typescript
// apps/api/src/lib/recurring-content/brief-generators/shared/select-end-slide.ts

export interface SelectEndSlideInput {
  definitionId: string;
  formatType: string;
  projectId: string;
}

export interface SelectedEndSlide {
  endSlideDefinitionId: string;
  endSlideType: EndSlideType;
  config: Record<string, unknown>;
  selectedVia: 'fixed' | 'lru-within-pool' | 'format-type-default';
}

export async function selectEndSlideForRecurringBrief(input: SelectEndSlideInput): Promise<SelectedEndSlide> {
  const definition = await getRecurringDefinition(input.definitionId);
  
  // Strategy 1: Fixed end-slide (V1.5 — definition.fixedEndSlideId)
  // Skipped V1 — recurring_content_definitions doesn't have this field yet
  
  // Strategy 2: Definition's own pool (definition.end_slide_pool)
  if (definition.endSlidePool && definition.endSlidePool.length > 0) {
    const eligible = await listEndSlideDefinitions({
      projectId: input.projectId,
      includeInactive: false,
    });
    const inPool = eligible.filter(e => definition.endSlidePool.includes(e.id));
    
    if (inPool.length > 0) {
      // LRU within pool
      const lruPicked = pickLruEndSlide(inPool, input.definitionId);
      return {
        endSlideDefinitionId: lruPicked.id,
        endSlideType: lruPicked.type as EndSlideType,
        config: lruPicked.config,
        selectedVia: 'lru-within-pool',
      };
    }
  }
  
  // Strategy 3: Format-type's defaultEndSlides (from 65.4 registry)
  const formatTypeDef = FORMAT_TYPES[input.formatType];
  if (!formatTypeDef?.defaultEndSlides?.length) {
    throw new Error(`No defaultEndSlides for format-type: ${input.formatType}`);
  }
  
  const allEndSlides = await listEndSlideDefinitions({
    projectId: input.projectId,
    includeInactive: false,
  });
  const eligibleByDefault = allEndSlides.filter(e => 
    formatTypeDef.defaultEndSlides.includes(e.type)
  );
  
  if (eligibleByDefault.length === 0) {
    throw new Error(`No active end_slide_definitions match defaultEndSlides: ${formatTypeDef.defaultEndSlides.join(', ')}`);
  }
  
  // LRU among defaults
  const lruPicked = pickLruEndSlide(eligibleByDefault, input.definitionId);
  return {
    endSlideDefinitionId: lruPicked.id,
    endSlideType: lruPicked.type as EndSlideType,
    config: lruPicked.config,
    selectedVia: 'format-type-default',
  };
}

async function pickLruEndSlide(
  candidates: EndSlideDefinition[],
  definitionId: string,
): Promise<EndSlideDefinition> {
  // Use existing template_usage_log (extend with end_slide_type column per 65.1 schema)
  const recentlyUsed = await listRecentTemplateUsage({
    recurringDefinitionId: definitionId,
    limit: candidates.length,
  });
  
  // Get the most-recently-used end_slide_type
  const recentlyUsedTypes = new Set(
    recentlyUsed.map(r => r.end_slide_type).filter(Boolean),
  );
  
  // Pick first candidate not recently used
  return candidates.find(c => !recentlyUsedTypes.has(c.type)) ?? candidates[0];
}
```

**Logging:** After end-slide-selection, extend the existing `logTemplateUsage` call (already in 65.5) to include `endSlideType`:

```typescript
await logTemplateUsage({
  recurringDefinitionId: ctx.definition.id,
  templateKey: selectedTemplate.templateKey,
  endSlideType: selectedEndSlide.endSlideType,  // NOW POPULATED
});
```

Per 65.1 schema — `template_usage_log.end_slide_type` column already exists.

## 11. Risk Analysis

| Risk | Severity | Mitigation |
|---|---|---|
| LRU-pick degenerate if pool has 1 element | Low | Falls back to that 1 element (acceptable — no choice to make) |
| LRU never picks a type if it's "most recent across all definitions" | Medium | LRU is per-definitionId not global — each definition has own rotation |
| Format-type defaultEndSlides reference types not in seed | High | 65.4 registry hardcoded types; seed-migration must produce all 7 |
| comment-to-get CTA confusing without ManyChat (viewer comments but nothing happens) | Medium | Marcel manually DMs in V1 (low volume manageable); V1.5 ManyChat-wire-up |
| Schema-drift between EndSlideData types and end_slide_definitions.config jsonb | Medium | Single shared types-file imported by 65.5 + 65.9 + 65.7 |
| New end-slide-type added but not in HostSlide switch (exhaustive-check fail) | Low | TypeScript `never`-check catches at compile-time |
| Dark-theme white-on-white text-vanishing | Medium | EndSlideBase uses CSS-var-based bg; theme cascades from parent |
