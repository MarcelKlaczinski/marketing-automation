# Spec 64.2 — `max_count` als echter Cap im Floor + Overage-Selector

_Mini-Task Follow-up nach 64.1 KW21-Generation. `project_goals.max_count` wird heute nur vom Validator (max >= min) geprüft und in den `inputSnapshot` persistiert — die Selektoren ignorieren es. Marcel erwartet aus der Settings-UI ("Min" + "Max"), dass max ein Hard-Cap ist._
_Status: Draft._
_Voraussetzung: 64.1 deployed (cluster_spoke split bringt das Problem ans Licht)._

---

## 1. Problem

Marcel setzt `cluster: per_day, min=1, max=1` und erwartet **1 Cluster pro Woche**. Tatsächlich produziert der Planner:

- **7 Floor cluster** (`min=1 × 7 days = 7` per `targetWeeklyCount(goal)` in `select-floor-items.ts:122`)
- **+ N Overage cluster** (Trend-Signale, gecap'd nur durch `project_planner_config.topNSignalsAllowedOverage × maxOveragePerSignal`, NICHT durch `goal.max_count`)

`max_count` wird heute referenziert in:
- `packages/planner/src/goal-validator.ts:151` — sanity-check `max >= min`
- `packages/pipelines/src/planning/steps/snapshot-inputs.ts:58` — frozen ins `inputSnapshot`
- **Nirgendwo enforced** in Floor- oder Overage-Selektoren

Die Settings-UI hat eine `Max`-Spalte ([SettingsPlannerPage.vue:66](apps/web/src/pages/settings/SettingsPlannerPage.vue:66)), die suggeriert "Hard-Cap" — UX-Realität: das Feld macht zur Laufzeit nichts.

## 2. Ziel

`max_count` als Hard-Cap pro `(project, content_type)` enforcen, gemeinsam über Floor + Overage. Der Planner darf für einen Content-Type höchstens `max_count` `planned_items` (Floor + Overage zusammen) produzieren.

**In Scope:**
- Floor-Cap auf `min(targetWeeklyCount, maxCount)` falls `maxCount !== null`
- Overage-Cap auf `maxCount - alreadyPickedByFloor` für den gleichen Content-Type
- `max_count = 0` heißt explizit "diesen Content-Type komplett deaktivieren" (auch wenn `min > 0` — der Validator erlaubt das schon nicht, aber dokumentieren)
- `null` (kein Cap) bleibt valide → keine Begrenzung jenseits der existierenden Overage-Topology
- Generation-Notes auf dem WeeklyPlan logging WENN Floor durch max_count downsized wurde (transparency für Marcel)

**Out of Scope:**
- `social_post` max_count cap-Verhalten anders machen (heute über `SelectSocialPostItemsStep` mit eigener `target`-Logik — neu durchdenken in eigenem Spec)
- Per-Day-Cap (vs per-Week-Cap) — `max_count` Cadence-Unit folgt der gleichen Logik wie `min_count` (per_day × 7 = wöchentlich)
- Cost-Cap-Interaktion ändern (`perTypeMaxEur` bleibt orthogonal)
- UI-Tooltip oder Help-Text zur Max-Semantik (eigenes UX-Mini)

**Aufwand:** ~2 Stunden.

## 3. Architektur

### 3.1 Floor-Cap

`packages/pipelines/src/planning/steps/select-floor-items.ts` — innerhalb der Goal-Loop ab Zeile ~276:

```ts
const target = targetWeeklyCount(goal);
const cap = goal.maxCount !== null ? Math.min(target, weeklyMaxFromGoal(goal)) : target;
// ↑ neuer Helper analog zu targetWeeklyCount
```

Neue pure Helper:

```ts
export function weeklyMaxFromGoal(goal: Pick<ProjectGoal, "cadenceUnit" | "maxCount">): number | null {
  if (goal.maxCount === null) return null;
  return goal.cadenceUnit === "per_day" ? goal.maxCount * 7 : goal.maxCount;
}
```

Wenn `cap < target`: append zu `shortfalls[contentType]` mit Note `"capped by max_count"` (transparency).

### 3.2 Overage-Cap

`packages/pipelines/src/planning/steps/select-overage-items.ts` — nach dem `inferContentTypeFromSignal`-Bucketing, vor dem Diversity-Pick:

```ts
// Per-content-type remaining capacity = maxCount - floor.count(contentType)
const floorCountByCT = new Map<PlanningContentType, number>();
for (const fi of floorItems) {
  floorCountByCT.set(fi.contentType, (floorCountByCT.get(fi.contentType) ?? 0) + 1);
}

candidates = candidates.filter(({ contentType }) => {
  const goal = goals.find((g) => g.contentType === contentType);
  if (!goal || goal.maxCount === null) return true;
  const weeklyMax = weeklyMaxFromGoal(goal);
  if (weeklyMax === null) return true;
  const used = floorCountByCT.get(contentType) ?? 0;
  return used < weeklyMax;
});
```

Plus eine zweite Pass nach dem Pick um zu verhindern dass mehrere Overage-Signale denselben Content-Type über den Cap füllen.

Alternativ: pro-Pick-Decrement, sauberer aber mehr Code.

### 3.3 Validator-Erweiterung (optional, ggf. mit drin)

`packages/planner/src/goal-validator.ts` — neuer Warn-Code `MAX_BELOW_FLOOR_WEEKLY`:

> Wenn `weeklyMaxFromGoal(goal) < targetWeeklyCount(goal)` UND `maxCount !== null` UND `minCount > 0` — warne dass die Floor-Pflicht durch max_count beschnitten wird. Heute durch `max >= min` Validator nicht erlaubt, aber die Cadence-Multiplikation hebelt das aus (`per_day min=1 max=1 → floor=7, cap=7` ist OK, aber `per_day min=2 max=10` → floor=14, cap=10 wäre flagged).

Optional in eigenem Mini falls 64.2 zu lang wird.

## 11. Implemented

**Helper** ([packages/pipelines/src/planning/steps/select-floor-items.ts:130](packages/pipelines/src/planning/steps/select-floor-items.ts:130)):
- `weeklyMaxFromGoal(goal): number | null` — mirrors `targetWeeklyCount` shape; null = uncapped; per_day → maxCount × 7. Exported via `packages/pipelines/src/planning/index.ts` for cross-step reuse.

**Floor cap** ([packages/pipelines/src/planning/steps/select-floor-items.ts:312](packages/pipelines/src/planning/steps/select-floor-items.ts:312)):
- Computes `cap = min(target, weeklyMax)` inside the goal loop; picker driven by `cap` instead of `target`.
- `useDiversity` predicate gated on `pool.length > cap` (not `target`) so the diversity pass is skipped when the cap already reduces below pool size.
- `selectionReason` cites `cap` so the detail-page tooltip reflects the effective target.
- `shortfalls[contentType]` reports `target - picked.length`; the log line now includes both `cap` and `requested` for transparency.
- Defensive log `"select-floor-items: floor target capped by max_count"` fires when `cap < target` — never under normal validator-gated input (validator enforces `max >= min` in raw integers + single cadence per goal), only via direct DB insert.

**Overage cap** ([packages/pipelines/src/planning/steps/select-overage-items.ts:104](packages/pipelines/src/planning/steps/select-overage-items.ts:104)):
- New `goals` read from `validate-goals` step output (was previously only `config`).
- `remainingCapByCT: Map<PlanningContentType, number | null>` built per content_type: `null` = uncapped; `Math.max(0, weeklyMax - floorPicked(C))` = remaining capacity. Content_types without a matching goal default to "uncapped" (preserves pre-64.2 unlimited overage behaviour for orphan signals).
- Emit loop gates each pick: `remaining === 0` → skip with info log; `remaining === null` → uncapped emit of `maxOveragePerSignal` items; otherwise `Math.min(maxOveragePerSignal, remaining)` items emitted and `remainingCapByCT` decremented so the next signal of the same type sees the updated budget.

**Validator** ([packages/planner/src/goal-validator.ts](packages/planner/src/goal-validator.ts)):
- Dropped during implementation (see §12 Discovery #1). The proposed `MAX_BELOW_FLOOR_WEEKLY` warning was dead code — under the existing `INVALID_MIN_MAX` error contract + single-cadence-per-goal invariant, weeklyMin > weeklyMax is structurally impossible.

**Tests** (10 new):
- [packages/pipelines/test/planning/select-floor-items-step.test.ts:198](packages/pipelines/test/planning/select-floor-items-step.test.ts:198) — 4 `weeklyMaxFromGoal` unit tests (null, per_day, per_week, zero) + 4 Floor-cap behaviour tests (uncapped goal, cap >= target no-op, per_day min=1 max=1 → 7 items, downsizing reports correct selectionReason).

## 12. Discovered & Deviations

| # | Discovery | Decision |
|---|---|---|
| 1 | Validator warning `MAX_BELOW_FLOOR_WEEKLY` (spec §3.3) is dead code. Under our single-cadence-per-goal contract, both `min` and `max` multiply by the same factor (×7 for per_day), so the ordering `weeklyMin ≤ weeklyMax` is preserved iff `min ≤ max`. `INVALID_MIN_MAX` already catches the latter as an error before any warning would fire. My original spec text "per_day min=2 max=10 → floor=14 cap=10" was a math error — `cap = 10 × 7 = 70`, not 10. | Dropped the warning. Documented in spec deviations + memory rather than shipping noise that can never fire. Validator stays unchanged in 64.2. |
| 2 | Floor cap is similarly defensive — under validator-gated input `cap === target` always (because `weeklyMax ≥ weeklyMin`). The cap only binds for hand-crafted DB rows where `INVALID_MIN_MAX` is bypassed. | Kept the cap as defensive backstop (with comment explaining when it fires) — the test "selectionReason reflects cap (not target) when downsizing" exercises the path even though production validator-gated callers never hit it. Same defense-in-depth pattern as pipeline-router's legacy `case "cluster"` backstop. |
| 3 | Spec §3.2 proposed `floorCountByCT` then "second pass for emit-time clamp". Implementation collapsed both into a single mutating `remainingCapByCT` map — the emit loop decrements per emission, so the second-pass guard is naturally embedded in the per-signal cap check. Simpler and avoids double-counting. | Kept the single-map approach. Tested explicitly with the "decrements per emit so multi-emit doesn't blow past cap" case. |
| 4 | Spec §3.2 said "Content_types without a matching goal default to null (preserves pre-64.2 unlimited behaviour)". `Map.get()` returns `undefined` not `null` for missing keys — needed an extra check `remaining === null \|\| remaining === undefined` in the emit loop. Both treated as uncapped. | Documented in inline comment. Test "emits uncapped when no matching goal exists" verifies the orphan-signal path. |
| 5 | `social_post` deliberately out-of-scope (spec §2). `SelectSocialPostItemsStep` builds its own `target` from goal then mixes 3 sources (refresh + pool + today-plans) — wiring max_count there would need a different cap model. The current 64.2 change doesn't affect social_post selection at all (Overage's `remainingCapByCT` includes social_post but Overage never emits social_post from signals — `inferContentTypeFromSignal` maps producthunt/reddit → social_post which IS in the map). | No social_post changes. If Marcel sets `social_post: max=N`, ProductHunt/Reddit overage signals will be capped together with whatever SelectSocialPostItemsStep already produced — but the social_post step runs AFTER overage, so its own pool isn't constrained. Documented limitation for a future spec. |
| 6 | First-pass implementation cast `goal.contentType as PlanningContentType` directly into the `remainingCapByCT` map — caught by /review-task as unsafe (DB-level `text` column could carry a future un-handled value, silently putting garbage into the cap map). | Fixed: copied the canonical runtime-guard pattern from `SelectFloorItemsStep` (`PLANNING_CONTENT_TYPES.includes(...)` → narrow + warn-and-skip on miss). Same defense as 62.4's original cast handling so DB-drift can't corrupt the cap map. |
