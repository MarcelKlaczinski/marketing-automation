# Spec 64.2 — `max_count` als echter Cap im Floor + Overage-Selector

_Mini-Task Follow-up nach 64.1 KW21-Generation. `project_goals.max_count` wird heute nur vom Validator (max >= min) geprüft und in den `inputSnapshot` persistiert — die Selektoren ignorieren es. Marcel erwartet aus der Settings-UI ("Min" + "Max"), dass max ein Hard-Cap ist._
_Status: Draft._
_Voraussetzung: 64.1 deployed (cluster_spoke split bringt das Problem ans Licht)._

---

## 1. Problem

Marcel setzt `cluster: per_day, min=1, max=1` und erwartet **1 Cluster pro Woche**. Tatsächlich produziert der Planner:

- **7 Floor cluster** (`min=1 × 7 days = 7` per `targetWeeklyCount(goal)` in `select-floor-items.ts:122`)
- **+ N Overage cluster** (Trend-Signale, gecap'd nur durch `project_planner_config.topNSignalsAllowedOverage × maxOveragePerSignal`, NICHT durch `goal.max_count`)

`max_count` wird heute referenziert in:
- `packages/planner/src/goal-validator.ts:151` — sanity-check `max >= min`
- `packages/pipelines/src/planning/steps/snapshot-inputs.ts:58` — frozen ins `inputSnapshot`
- **Nirgendwo enforced** in Floor- oder Overage-Selektoren

Die Settings-UI hat eine `Max`-Spalte ([SettingsPlannerPage.vue:66](apps/web/src/pages/settings/SettingsPlannerPage.vue:66)), die suggeriert "Hard-Cap" — UX-Realität: das Feld macht zur Laufzeit nichts.

## 2. Ziel

`max_count` als Hard-Cap pro `(project, content_type)` enforcen, gemeinsam über Floor + Overage. Der Planner darf für einen Content-Type höchstens `max_count` `planned_items` (Floor + Overage zusammen) produzieren.

**In Scope:**
- Floor-Cap auf `min(targetWeeklyCount, maxCount)` falls `maxCount !== null`
- Overage-Cap auf `maxCount - alreadyPickedByFloor` für den gleichen Content-Type
- `max_count = 0` heißt explizit "diesen Content-Type komplett deaktivieren" (auch wenn `min > 0` — der Validator erlaubt das schon nicht, aber dokumentieren)
- `null` (kein Cap) bleibt valide → keine Begrenzung jenseits der existierenden Overage-Topology
- Generation-Notes auf dem WeeklyPlan logging WENN Floor durch max_count downsized wurde (transparency für Marcel)

**Out of Scope:**
- `social_post` max_count cap-Verhalten anders machen (heute über `SelectSocialPostItemsStep` mit eigener `target`-Logik — neu durchdenken in eigenem Spec)
- Per-Day-Cap (vs per-Week-Cap) — `max_count` Cadence-Unit folgt der gleichen Logik wie `min_count` (per_day × 7 = wöchentlich)
- Cost-Cap-Interaktion ändern (`perTypeMaxEur` bleibt orthogonal)
- UI-Tooltip oder Help-Text zur Max-Semantik (eigenes UX-Mini)

**Aufwand:** ~2 Stunden.

## 3. Architektur

### 3.1 Floor-Cap

`packages/pipelines/src/planning/steps/select-floor-items.ts` — innerhalb der Goal-Loop ab Zeile ~276:

```ts
const target = targetWeeklyCount(goal);
const cap = goal.maxCount !== null ? Math.min(target, weeklyMaxFromGoal(goal)) : target;
// ↑ neuer Helper analog zu targetWeeklyCount
```

Neue pure Helper:

```ts
export function weeklyMaxFromGoal(goal: Pick<ProjectGoal, "cadenceUnit" | "maxCount">): number | null {
  if (goal.maxCount === null) return null;
  return goal.cadenceUnit === "per_day" ? goal.maxCount * 7 : goal.maxCount;
}
```

Wenn `cap < target`: append zu `shortfalls[contentType]` mit Note `"capped by max_count"` (transparency).

### 3.2 Overage-Cap

`packages/pipelines/src/planning/steps/select-overage-items.ts` — nach dem `inferContentTypeFromSignal`-Bucketing, vor dem Diversity-Pick:

```ts
// Per-content-type remaining capacity = maxCount - floor.count(contentType)
const floorCountByCT = new Map<PlanningContentType, number>();
for (const fi of floorItems) {
  floorCountByCT.set(fi.contentType, (floorCountByCT.get(fi.contentType) ?? 0) + 1);
}

candidates = candidates.filter(({ contentType }) => {
  const goal = goals.find((g) => g.contentType === contentType);
  if (!goal || goal.maxCount === null) return true;
  const weeklyMax = weeklyMaxFromGoal(goal);
  if (weeklyMax === null) return true;
  const used = floorCountByCT.get(contentType) ?? 0;
  return used < weeklyMax;
});
```

Plus eine zweite Pass nach dem Pick um zu verhindern dass mehrere Overage-Signale denselben Content-Type über den Cap füllen.

Alternativ: pro-Pick-Decrement, sauberer aber mehr Code.

### 3.3 Validator-Erweiterung (optional, ggf. mit drin)

`packages/planner/src/goal-validator.ts` — neuer Warn-Code `MAX_BELOW_FLOOR_WEEKLY`:

> Wenn `weeklyMaxFromGoal(goal) < targetWeeklyCount(goal)` UND `maxCount !== null` UND `minCount > 0` — warne dass die Floor-Pflicht durch max_count beschnitten wird. Heute durch `max >= min` Validator nicht erlaubt, aber die Cadence-Multiplikation hebelt das aus (`per_day min=1 max=1 → floor=7, cap=7` ist OK, aber `per_day min=2 max=10` → floor=14, cap=10 wäre flagged).

Optional in eigenem Mini falls 64.2 zu lang wird.

## 4. Tests

Neue Cases in `packages/pipelines/test/planning/select-floor-items-step.test.ts`:

- `goal: per_week min=1 max=1` + 5 briefs → 1 picked, 0 shortfall, generation_notes ohne max_count Mention

Marcel will wahrscheinlich `per_day min=1 max=0.14` und das ist nicht möglich. → echte Lösung: Marcel muss per_week verwenden wenn er Wochen-Caps will. Test deckt aber das Math ab.)

- `goal: per_week min=2 max=5` + 3 briefs → 2 picked (capped by supply, not max)
- `goal: per_week min=2 max=5` + 10 briefs → 2 picked (floor=2), max=5 leaves 3 capacity for Overage

- Goal `max=null` → Overage uneingeschränkt (existing behaviour)
