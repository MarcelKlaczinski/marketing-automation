# Spec 61.4 — Anthropic Batch API Worker

**Date:** 2026-05-19
**Theme:** 61 — Article Generator Variants
**Prerequisite:** 61.3 done
**Estimated effort:** ~1.5 days

---

## TL;DR

Add Anthropic MessageBatch API support for bulk article generation. Three LLM
calls per article (OutlineStep, DraftStep, SelfReviewStep) currently run
synchronously at ~$0.05/article. With Batch API: 50% cost reduction, 24h
turnaround. This is the foundation the Content Planner (Theme 62) needs to
generate a week of articles overnight at half price.

Two modes coexist after this spec:
- **Sync mode** (default, unchanged): `anthropic.messages()` — immediate result
- **Batch mode** (opt-in per project): `anthropic.batches.create()` → poll →
  resume pipeline

## Session 2 — BatchLlmClient

### 2.1 Interface

```typescript
// packages/pipelines/src/engine/batch-llm-client.ts

export type LlmMode = 'sync' | 'batch';

export interface LlmCallResult {
  mode:      LlmMode;
  content:   string;           // response text — same in both modes
  batchRequestId?: string;     // only in batch mode — DB row ID
  inputTokens:  number;
  outputTokens: number;
}

export interface BatchLlmClient {
  /**
   * Call LLM. In sync mode: returns immediately with content.
   * In batch mode: persists request, returns empty content + batchRequestId.
   * Caller must handle both cases.
   */
  call(params: {
    model:      string;
    messages:   MessageParam[];
    system?:    string;
    maxTokens:  number;
    stepKey:    string;
    projectId:  string;
    articleId?: string;
    runId:      string;
    mode:       LlmMode;
  }): Promise<LlmCallResult>;
}
```

### 2.2 Implementation

```typescript
// packages/pipelines/src/engine/batch-llm-client.ts

export class AnthropicBatchLlmClient implements BatchLlmClient {
  constructor(
    private readonly anthropic: Anthropic,
    private readonly db: DrizzleDb,
  ) {}

  async call(params): Promise<LlmCallResult> {
    if (params.mode === 'sync') {
      return this.callSync(params);
    }
    return this.enqueueBatch(params);
  }

  private async callSync(params): Promise<LlmCallResult> {
    const res = await this.anthropic.messages.create({
      model:      params.model,
      max_tokens: params.maxTokens,
      system:     params.system,
      messages:   params.messages,
    });
    return {
      mode:         'sync',
      content:      res.content[0].type === 'text' ? res.content[0].text : '',
      inputTokens:  res.usage.input_tokens,
      outputTokens: res.usage.output_tokens,
    };
  }

  private async enqueueBatch(params): Promise<LlmCallResult> {
    const customId = `${params.runId}:${params.stepKey}`;

    const [row] = await this.db.insert(batchRequests).values({
      projectId:         params.projectId,
      articleId:         params.articleId,
      pipelineRunId:     params.runId,
      anthropicCustomId: customId,
      status:            'pending',
      model:             params.model,
      stepKey:           params.stepKey,
      requestBody: {
        model:      params.model,
        max_tokens: params.maxTokens,
        system:     params.system,
        messages:   params.messages,
      },
    }).returning();

    return {
      mode:           'batch',
      content:        '',            // empty — pipeline must check batchRequestId
      batchRequestId: row.id,
      inputTokens:    0,
      outputTokens:   0,
    };
  }
}
```

### 3.3 OutlineStep + DraftStep changes

Both steps currently call `anthropic.messages.create()` directly. Replace with
`BatchLlmClient.call()`:

```typescript
// In OutlineStep.execute():

const result = await this.llmClient.call({
  model:     OUTLINE_MODEL,
  messages:  buildOutlineMessages(input, ctx),
  system:    resolvedSystemPrompt,
  maxTokens: OUTLINE_MAX_TOKENS,
  stepKey:   'outline',
  projectId: ctx.projectId,
  articleId: input.articleId,
  runId:     ctx.runId,
  mode:      ctx.llmMode,
});

if (result.mode === 'batch') {
  // Suspend pipeline — return a "batch_pending" signal
  return {
    ...passThroughFields,
    batchPending: true,
    batchRequestId: result.batchRequestId,
  };
}

// Sync mode — parse result.content as before
const outline = parseOutlineResponse(result.content);
```

### 3.4 Pipeline suspension pattern

When a step returns `batchPending: true`, the pipeline engine:
1. Persists the current pipeline state to `pipeline_runs` with
   `status: 'batch_pending'`
2. Stores `{ stepKey, batchRequestId }` in `pipeline_runs.batch_checkpoint`
3. Returns control to the caller (BullMQ job completes successfully)

The pipeline does NOT continue — it waits for the batch processor to resume it.

```typescript
// packages/pipelines/src/engine/pipeline-runner.ts

// After each step output, check for batch_pending signal:
if (stepOutput.batchPending) {
  await db.update(pipelineRuns).set({
    status: 'batch_pending',
    batchCheckpoint: {
      stepKey:        stepKey,
      batchRequestId: stepOutput.batchRequestId,
      accumulatedOutput: currentOutput,  // all prior step outputs
    },
  }).where(eq(pipelineRuns.id, ctx.runId));
  return { suspended: true };
}
```

### 4.1 Worker location


### 4.2 Worker logic

```typescript
// apps/api/src/workers/batch-processor.worker.ts

export async function processBatches(): Promise<void> {
  // 1. Find all submitted batch_requests grouped by anthropic_batch_id
  const pendingBatches = await db
    .selectDistinct({ anthropicBatchId: batchRequests.anthropicBatchId })
    .from(batchRequests)
    .where(inArray(batchRequests.status, ['submitted', 'processing']));

  for (const { anthropicBatchId } of pendingBatches) {
    if (!anthropicBatchId) continue;
    await processSingleBatch(anthropicBatchId);
  }
}

async function processSingleBatch(anthropicBatchId: string): Promise<void> {
  // 2. Poll Anthropic batch status
  const batch = await anthropic.batches.retrieve(anthropicBatchId);

  if (batch.processing_status !== 'ended') {
    // Update status to 'processing' if not already
    await db.update(batchRequests)
      .set({ status: 'processing', updatedAt: new Date() })
      .where(eq(batchRequests.anthropicBatchId, anthropicBatchId));
    return;  // Not ready yet — check next cron cycle
  }

  // 3. Fetch results
  const results = await anthropic.batches.results(anthropicBatchId);

  for await (const result of results) {
    await processResult(result);
  }
}

async function processResult(result: BatchResultItem): Promise<void> {
  // 4. Match result to batch_request row via custom_id
  const [row] = await db
    .select()
    .from(batchRequests)
    .where(eq(batchRequests.anthropicCustomId, result.custom_id));

  if (!row) return;

  if (result.result.type === 'succeeded') {
    const msg = result.result.message;
    const content = msg.content[0].type === 'text' ? msg.content[0].text : '';

    await db.update(batchRequests).set({
      status:       'completed',
      responseBody: { content, usage: msg.usage },
      inputTokens:  msg.usage.input_tokens,
      outputTokens: msg.usage.output_tokens,
      costEur:      calculateBatchCostEur(row.model, msg.usage),
      completedAt:  new Date(),
      updatedAt:    new Date(),
    }).where(eq(batchRequests.id, row.id));

    // 5. Resume suspended pipeline
    await resumePipeline(row);

  } else {
    await db.update(batchRequests).set({
      status:    'failed',
      errorBody: result.result,
      updatedAt: new Date(),
    }).where(eq(batchRequests.id, row.id));
  }
}
```

### 4.3 Batch submission — when to submit

Individual `batch_requests` rows start as `pending`. They need to be batched
together and submitted to Anthropic. Two strategies:

**Strategy A — Submit-on-threshold (recommended for Content Planner):**
When a BullMQ job finishes generating articles for a Content Plan, a final
`SubmitBatchStep` collects all `pending` batch_requests for that `planId` and
calls `anthropic.batches.create()` with up to 10,000 requests per batch.

**Strategy B — Submit-on-schedule (for ad-hoc generation):**
A cron job every 30 minutes collects all `pending` batch_requests older than
15 minutes and submits them.

For 61.4, implement **Strategy B** (simpler, works without Content Planner).
Strategy A is added in Theme 62.

```typescript
// Cron: every 30 minutes
async function submitPendingRequests(): Promise<void> {
  const cutoff = new Date(Date.now() - 15 * 60 * 1000);

  const pending = await db
    .select()
    .from(batchRequests)
    .where(
      and(
        eq(batchRequests.status, 'pending'),
        lt(batchRequests.createdAt, cutoff),
      )
    )
    .limit(10_000);  // Anthropic batch limit

  if (pending.length === 0) return;

  // Build Anthropic batch
  const requests = pending.map(row => ({
    custom_id: row.anthropicCustomId,
    params: {
      model:      row.model,
      max_tokens: (row.requestBody as any).max_tokens,
      system:     (row.requestBody as any).system,
      messages:   (row.requestBody as any).messages,
    },
  }));

  const batch = await anthropic.batches.create({ requests });

  // Update all pending rows with anthropic_batch_id
  const ids = pending.map(r => r.id);
  await db.update(batchRequests).set({
    anthropicBatchId: batch.id,
    status:           'submitted',
    submittedAt:      new Date(),
    expiresAt:        new Date(Date.now() + 24 * 60 * 60 * 1000),
    updatedAt:        new Date(),
  }).where(inArray(batchRequests.id, ids));
}
```

## Session 5 — Pipeline Resume

### 5.1 `resumePipeline()` function

```typescript
// packages/pipelines/src/engine/batch-resume.ts

export async function resumePipeline(batchRow: BatchRequest): Promise<void> {
  if (!batchRow.pipelineRunId) return;

  const run = await db.query.pipelineRuns.findFirst({
    where: eq(pipelineRuns.id, batchRow.pipelineRunId),
  });

  if (!run || run.status !== 'batch_pending') return;

  const checkpoint = run.batchCheckpoint as BatchCheckpoint;
  const content = (batchRow.responseBody as any)?.content ?? '';

  // Re-enqueue the BullMQ job with the batch result injected
  await enqueueBlogGenerationPipeline({
    articleId:     batchRow.articleId!,
    projectId:     batchRow.projectId,
    resumeFromStep: checkpoint.stepKey,
    batchResult:   { stepKey: checkpoint.stepKey, content },
    priorOutput:   checkpoint.accumulatedOutput,
  });
}
```

### 5.2 Pipeline resume handling in BlogPipeline

When `resumeFromStep` is present in the job data, BlogPipeline skips all steps
before `resumeFromStep` and injects the `batchResult.content` as the LLM
response for that step — bypassing the actual LLM call.

```typescript
// In BlogPipeline step execution:

if (ctx.resumeFromStep === stepKey) {
  // Use pre-supplied batch result instead of calling LLM
  rawLlmContent = ctx.batchResult.content;
} else if (ctx.resumeFromStep && !ctx.passedResumePoint) {
  // Skip steps before the resume point
  return priorOutput[stepKey];  // replay from checkpoint
}
```

## Session 6 — Cost Tracking

### 6.1 Batch cost rates

```typescript
// packages/pipelines/src/engine/cost-calculator.ts

const BATCH_COST_RATES: Record<string, { inputPer1M: number; outputPer1M: number }> = {
  'claude-sonnet-4-6':       { inputPer1M: 1.50,  outputPer1M: 7.50  },  // 50% of sync
  'claude-haiku-4-5-20251001': { inputPer1M: 0.125, outputPer1M: 0.625 }, // 50% of sync
};

export function calculateBatchCostEur(
  model: string,
  usage: { input_tokens: number; output_tokens: number },
): number {
  const rates = BATCH_COST_RATES[model];
  if (!rates) return 0;
  const usd =
    (usage.input_tokens  / 1_000_000) * rates.inputPer1M +
    (usage.output_tokens / 1_000_000) * rates.outputPer1M;
  return usd * EUR_PER_USD;  // use existing EUR_PER_USD constant
}
```

### 6.2 Cost tracker integration

## Section — Patterns Established by 61.4

**(118) Batch mode uses `batchPending: true` signal in step output to suspend
the pipeline. The pipeline engine detects this, checkpoints state to DB, and
returns cleanly. Never use exceptions for flow control in batch mode.**

**(119) `anthropic_custom_id` format: `{runId}:{stepKey}`. This is the
correlation key between Anthropic's batch result and our `batch_requests` row.
Always construct it this way — never use just `runId` or just `stepKey`.**

**(120) Cost tracking for batch uses a separate `batch_api` service key at 50%
of sync rates. Never re-use sync cost rates for batch calls.**
