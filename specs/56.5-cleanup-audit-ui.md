# Spec 56.5: Theme-56 Cleanup-Audit

**Theme:** 56 / UI Refactoring — Sub-spec 5 of 5 (AUDIT PASS)
**Phase:** Post-Implementation Quality Pass
**Estimated Effort:** ~1.5-2 days (~10-12 focused hours across 3 sessions)
**Dependencies:**
- Spec 56.1 (Dashboard MVP)
- Spec 56.2 (Multi-pane Views Redesign)
- Spec 56.3 (Settings + Costs + Article Tools)
- Spec 56.4 (Cold-Start Polish)

**Status:** Ready when 56.4 implementation completes
**Recommended Model:** Sonnet 4.6 for systematic audit work.

---

## Goal

After 56.1–56.4 ship, run a systematic audit pass to find and fix all the "almost-done but not quite" issues that accumulated during the UI refactor. This is **not** a new feature spec — it's a quality gate before declaring Theme 56 truly complete.

The audit covers 8 distinct dimensions:
1. **UI Stubs** — placeholder components, "Coming soon" empty states, TODO markers
2. **Route Coverage** — every defined route actually loads + works
3. **Page Reachability** — every Vue page is reachable from somewhere in the UI navigation (no orphan pages)
4. **Functional Completeness** — no critical workflow is broken or missing
5. **Backend-UI Contract** — every UI-consumed endpoint is real, returns expected shape
6. **i18n Final Sweep** — no hardcoded English strings remain in templates
7. **SDK Freshness** — generated SDK reflects latest backend
8. **clusterAction Specific** — verify D1 deviation from 56.3 handles both branches

Goal is **zero open issues** at the end. Anything found that's not fixable in this audit goes to Phase E backlog with clear repro steps.

## What this is NOT

- Not a new spec writing patterns or components — those are done
- Not redesigning anything — visual is locked
- Not refactoring composables for taste — only for correctness
- Not performance tuning — separate concern, Phase E
- Not accessibility audit — separate concern, Phase E (already at Lighthouse ≥ 90)
- Not adding test coverage — separate concern, Phase E
- Not browser compatibility testing — separate concern, Phase E

## Dimension 1: UI Stubs Inventory + Removal

### 1.1 Search patterns

Run these systematic searches to find stub markers:

```bash
# TODO/FIXME/XXX markers in .vue files
rg -n "TODO|FIXME|XXX|HACK|@todo" apps/web/src --type vue --type ts

# Coming soon / placeholder text
rg -n "coming soon|Coming Soon|placeholder|Placeholder|not implemented|Not implemented" apps/web/src

# Empty function bodies (only `// TODO` or empty)
rg -n "^\s*//\s*TODO" apps/web/src --type vue --type ts

# Console.log left in code
rg -n "console\.log\(" apps/web/src --type vue --type ts

# Commented-out routes/components/imports
rg -n "^\s*//\s*<" apps/web/src --type vue

# Empty <template></template> sections
rg -n "<template>\s*</template>" apps/web/src --type vue
```

### 1.2 Per-finding triage

For each finding, categorize:

- **A. Real placeholder** — incomplete feature, no value to user yet
  - Action: Remove the component entirely OR replace with proper EmptyState
  - If routes depend on it, remove the route too
- **B. Intentional TODO** — known limitation tracked elsewhere
  - Action: Add to Phase E backlog with clear context, remove the TODO comment
- **C. Forgotten cleanup** — dead code from earlier iteration
  - Action: Delete

### 1.3 EmptyState audit

Even non-stub EmptyStates can be misleading. Check each EmptyState component usage:

```bash
rg -n "<EmptyState" apps/web/src --type vue
```

For each: does it accurately describe what the user should do? Or is it a polite "nothing here yet" that hides a real bug (e.g. API call failing silently)?

### 1.4 Stub removal commit

Single commit per dimension: `chore(web): remove stubs + placeholders (spec 56.5 dimension 1)`. Don't bundle with other dimensions — easier to revert if needed.

### 5.3 Bug class taxonomy

Findings should be categorized into one of these five classes:

**Class A — Endpoint does not exist at all** (HIGH priority)
- UI calls endpoint that returns 404
- Examples already found:
  - `GET /api/projects/:slug/activity-summary` (Dashboard)
  - `GET /api/articles/:id/runs` (Article Detail Runs tab)
  - `GET /api/articles/:id/costs` (Article Detail Cost tab)
  - All `/api/cold-start/*` endpoints (per 56.4 Deviation)
- Fix: Spec the endpoint in 56.6 Implementation-Completion, build backend

**Class B — Endpoint exists but wrong path**
- UI calls `/api/foo/bar` but backend has `/api/projects/:slug/foo/bar`
- UI uses old query-param scoping but backend deprecated those routes
- Fix: Update UI to use correct path

**Class C — Endpoint shape mismatches** (any of):
- Param shape mismatches (e.g. UI sends `projectSlug` in body, backend expects `slug` in path)
- Response wrapper mismatches (UI accesses `response.data.items` but backend returns `response.items`)
- Naming case mismatches (camelCase vs snake_case)
- Type mismatches (UI expects `number` but backend sends `string` per Drizzle numeric)
- Null vs empty array vs undefined inconsistencies
- Fix: Align UI and backend types

**Class D — Auth/scoping bugs**
- UI calls scoped endpoint but backend doesn't filter by project
- UI calls unscoped endpoint that should be project-scoped
- Cross-project data leakage possible
- Fix: Add scoping at backend, update UI to pass slug

**Class E — Stubbed/empty response**
- Endpoint returns 200 but always returns empty `[]` or `null`
- UI shows EmptyState while real data should exist
- Backend handler is `// TODO` stub
- Fix: Implement actual handler logic

**For each finding, document**:
- Class (A/B/C/D/E)
- UI file + line that calls the endpoint
- Backend file + line where endpoint should be (or note "missing")
- Suggested fix approach

## Dimension 6: i18n Final Sweep

### 6.1 Search patterns for hardcoded strings

```bash
# Capitalized words inside JSX-like text in templates (catches "Save", "Cancel", "Yes", etc.)
rg -n ">[A-Z][a-z]+(\s[A-Z]?[a-z]+){0,3}<" apps/web/src --type vue

# String literals in computed return values
rg -n "return '[A-Z][a-z]" apps/web/src/components --type vue
rg -n "return \"[A-Z][a-z]" apps/web/src/components --type vue

# String literals as Record<string, string> values
rg -n ":\s*['\"][A-Z][a-z]+['\"]" apps/web/src --type vue --type ts

# notify({ message: "..." }) with raw strings
rg -n "notify\(\{[^}]*message:\s*['\"][A-Z]" apps/web/src

# Confirm dialogs with raw strings
rg -n "dialog\(\{[^}]*title:\s*['\"][A-Z]" apps/web/src
rg -n "dialog\(\{[^}]*message:\s*['\"][A-Z]" apps/web/src

# Hardcoded option labels
rg -n "<option [^>]*>[A-Z]" apps/web/src --type vue
```

### 6.2 i18n key inventory check

Compare keys present in `apps/web/src/i18n/de/*.ts` vs `apps/web/src/i18n/en/*.ts`:

```bash
# Extract all keys from DE
node -e "const de = require('./apps/web/src/i18n/de'); console.log(JSON.stringify(de, null, 2))" | jq -r '. | paths(scalars) | join(".")' | sort > /tmp/de-keys.txt

# Extract all keys from EN
node -e "const en = require('./apps/web/src/i18n/en'); console.log(JSON.stringify(en, null, 2))" | jq -r '. | paths(scalars) | join(".")' | sort > /tmp/en-keys.txt

# Diff to find missing translations
diff /tmp/de-keys.txt /tmp/en-keys.txt
```

Goal: identical key sets in both languages.

### 6.3 Unused i18n keys

```bash
# Find all $t() calls
rg -n "\\\$t\(['\"]([^'\"]+)['\"]" apps/web/src -o -r '$1' | sort -u > /tmp/used-keys.txt

# Compare with defined keys
comm -23 /tmp/de-keys.txt /tmp/used-keys.txt > /tmp/unused-keys.txt
```

Unused keys = dead translation work. Either remove them or check if they're used via dynamic key construction (e.g. `$t(\`articles.status.\${status}\`)`).

### 6.4 Dynamic key audit

Find dynamic `$t()` usages and verify all possible values are in i18n:

```bash
# Dynamic key patterns

```

For each dynamic pattern (e.g. `$t(\`articles.status.\${status}\`)`):
- List all possible runtime values of `status`
- Verify each `articles.status.<value>` key exists in both DE and EN
- If missing key, add with fallback to raw value

## Decisions Made

**Decision 1: Audit is its own spec, not bundled into 56.4.**
Cleanup pass is fundamentally different work — systematic verification, not feature implementation. Separating it makes scope and findings clearer.

**Decision 2: Three-session structure (UI/Functional/Quality).**
Group related dimensions to allow focused mental mode per session. Stub removal mindset is different from contract verification mindset.

**Decision 3: Findings triage triple-pattern (Fix Now / Defer / Defer with Repro).**
Not everything will be fixed in audit. Honest triage with repro steps prevents lost issues.

**Decision 4: Single commit per dimension.**
Easier to revert one dimension's changes if it caused regression. Bundled commits hide the structure.

**Decision 5: Workflow smoke tests are the truth, not test suite passing.**
Automated tests can pass while user experience is broken. Manual workflow walkthrough catches real issues.

**Decision 6: i18n sweep at the end, not the beginning.**
Other dimensions may add/remove translatable strings. Sweep after stabilization is more efficient.

**Decision 7: SDK regen is its own dimension, not lumped into contracts.**
Type drift from SDK regen is a specific class of finding with specific fix pattern. Worth its own dimension.

**Decision 8: clusterAction gets dedicated dimension because of known D1 concern.**
Per user note: "behalte das einfach mal im hinterkopf". This is the explicit verification of that concern.

**Decision 9: Phase E backlog at `specs/_backlog/post-theme-56.md`.**
Single document with all deferred findings. Triaged with severity + repro. Inventory for future planning sessions.

**Decision 10: Audit checklist added to apps/web/CLAUDE.md.**
Reusable pattern for future Theme audits. Codify the lessons learned.
