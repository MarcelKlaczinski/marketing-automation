# Spec 59.3 — pro-con-verdict Social Template

**Theme:** 59 (Tier 3 Pre-Launch Foundation)
**Status:** Draft
**Estimated effort:** 3 days (~22 focused hours across 5 sessions)
**Prerequisite:** 59.3-prep (template naming refactor)
**Successor:** 59.4 news-slide template

---

## Goal

Add a new social template `pro-con-verdict` that produces a multi-slide Instagram carousel optimized for one specific content pattern: **balanced tool/concept evaluation with explicit pros, cons, and final verdict.**

The template has a **signature visual element**: split-screen cover (Pro-side / Con-side, color-coded green/red diagonal). This makes it instantly recognizable in the Instagram grid as distinct from existing templates (comparison-grid covers show 4-up tool grid, verdict-per-use-case covers show use-case-prominent header, single-tool-spotlight covers show one tool hero portrait).

After 59.3 lands, toolwiki has 5 templates in production. The eligible content surface expands to articles with structured pros/cons data — primarily `tools` collection articles where `frontmatterExtras.pros` and `frontmatterExtras.cons` are populated.

## What this is NOT

- Not a side-by-side tool comparison (that's `comparison-grid-*` for 3-4 tools)
- Not a use-case-driven verdict (that's `verdict-per-use-case`)
- Not a deep dive into one tool's features (that's `single-tool-spotlight`)
- Not auto-template-suggestion (that's a separate Phase E backlog item)
- Not bilingual translation of pros/cons via separate LLM call — uses what's already in `frontmatterExtras` per locale

The pro-con-verdict template is for **explicit decision content**: "Is this tool worth it?" / "Lohnt sich X?" patterns. Strong visual contrast between pros and cons reflects the article's structure.

## Section A: Slide Structure + Composition

### A.1 Slide count + role per slide

5 slides, fixed structure:

```
Slide 1: COVER (split-screen pro/con, tool name + verdict-snippet)
Slide 2: PROS (3-5 strongest pros, list-style with check icons)
Slide 3: CONS (3-5 weakest cons, list-style with x icons)
Slide 4: VERDICT (final recommendation, "When to use" + "When to skip")
Slide 5: END (CTA — "Mehr im Artikel" / "Read more")
```

**Why fixed not dynamic**: pro-con structure is intrinsically symmetric. Variable pros/cons counts within a single slide work better than splitting across multiple slides (a 2-slide pros section feels imbalanced vs 1-slide cons).

### A.2 Canvas + safe zones

Uses the same canvas dimensions as existing templates (per audit Section 5):
```
CANVAS_W:      1080px
CANVAS_H_4_5:  1350px  (4:5 Instagram feed)
PAD_X:         60px
PAD_Y_TOP:     140px
PAD_Y_BOTTOM:  140px
INNER_W:       960px
INNER_H:       1070px
```

Inherit from `packages/social/src/compositions/_shared/safeZones.ts` or create per-composition file matching existing pattern.

### A.3 Cover slide (signature visual)

**The differentiating element.** This cover must read at glance in the Instagram grid as "pro/con format".

**Layout**:
```
┌─────────────────────────────────────────┐
│  EYEBROW (de: "BEWERTUNG" / en: "REVIEW") │  ← top
│                                          │
│  ┌────────────────┬────────────────┐    │
│  │                │                │    │  ← diagonal split
│  │   PROS         │       CONS     │    │
│  │   ✓ ✓ ✓        │       ✗ ✗ ✗   │    │
│  │                │                │    │
│  │   green tint   │    red tint   │    │
│  │                │                │    │
│  └────────────────┴────────────────┘    │
│                                          │
│  TOOL NAME (large, centered, bridges     │  ← below split
│  the split visually)                     │
│                                          │
│  Verdict-snippet (1 line, italic)        │
│                                          │
│  [Logo]                                  │
└─────────────────────────────────────────┘
```

**Diagonal split implementation**:
- SVG clipPath dividing canvas into two diagonal halves (top-left to bottom-right)
- Left half: pro-color tint (oklch green from brand-tokens, low alpha)
- Right half: con-color tint (oklch red from brand-tokens, low alpha)
- Icons (✓ for pros, ✗ for cons) float in each half at consistent positions
- Tool name overlays the split at the bottom-center, large typography, brand foreground color
- Verdict-snippet below tool name in italic, max 1 line (~60 chars)

**Brand-token integration** — see Section A.8 for full mapping.

For cover specifically:
- Pros half tint: derived from `prosColor` (optional) OR `accent` (fallback if accent looks green-ish) OR oklch default green
- Cons half tint: derived from `consColor` (optional) OR oklch default red
- Tool name color: `foreground` from existing brand-tokens
- Background base (under the tint): `background` from existing brand-tokens
- Eyebrow color: `accent` from existing brand-tokens
- Logo treatment: same logoUrl resolution as existing templates use

- CTA text from overrides
- "Mehr im Artikel" / "Read more" link visual
- Background: brand primary color

### A.8 Brand-token consumption (explicit mapping)

**Principle**: pro-con-verdict consumes the **same brand-token keys** as the existing 4 templates by default. This ensures:
1. Visual consistency across templates in the Instagram grid (same font, accent, foreground/background)
2. Setting `accent` once in project settings reflects across all templates
3. Per-template differentiation is **structural** (layout, cover signature), not **chromatic** (different palettes)

**Existing brand-token keys consumed** (must match what comparison-grid + verdict-per-use-case + single-tool-spotlight already read):

| Token Key | Used For | Cover | Pros | Cons | Verdict | End |
|---|---|---|---|---|---|---|
| `background` | Slide base color | ✓ (under tint) | ✓ | ✓ | ✓ | (overridden by primary) |
| `foreground` | Body text + headers | tool name + verdict snippet | header + bullets | header + bullets | tool name + section labels | CTA text |
| `accent` | Eyebrow + small highlights | eyebrow + tool-name underline | eyebrow | eyebrow | eyebrow | small accent line |
| `primary` | End-slide background + CTA button | — | — | — | — | full background + CTA |
| `logoUrl` | Brand logo on slides | corner | (none) | (none) | bottom-center | center large |
| `fontFamily` | All typography | ✓ | ✓ | ✓ | ✓ | ✓ |

**New optional brand-token keys** (additive to existing schema, **never required**):

| Token Key | Default | Used For |
|---|---|---|
| `prosColor` | `oklch(0.78 0.15 145)` (green) | Cover left half tint, Pros slide tint, ✓ icon color, "When to use" label color |
| `consColor` | `oklch(0.68 0.18 25)` (red) | Cover right half tint, Cons slide tint, ✗ icon color, "When to skip" label color |

**Why these can't be `accent`**: pros must be visually distinct from cons (semantic encoding via color). Using `accent` for both would collapse the visual meaning. Independent green/red is mandatory for the template's structural purpose.

**Brand-aware fallback chain for prosColor/consColor** (per Section A.3 `colors.ts`):

```typescript
// packages/social/src/compositions/pro-con-verdict/colors.ts

import type { BrandTokens } from "@/social/types";

const DEFAULT_PROS_COLOR = "oklch(0.78 0.15 145)";  // balanced green
const DEFAULT_CONS_COLOR = "oklch(0.68 0.18 25)";   // balanced red

export function resolveProsColor(brandTokens?: BrandTokens): string {
  // Explicit prosColor wins if set
  if (brandTokens?.prosColor) return brandTokens.prosColor;

  // Otherwise: default. NEVER fall back to accent (would collapse pros/cons semantically)
  return DEFAULT_PROS_COLOR;
}

export function resolveConsColor(brandTokens?: BrandTokens): string {
  if (brandTokens?.consColor) return brandTokens.consColor;
  return DEFAULT_CONS_COLOR;
}
```

**Default behavior for projects without `prosColor`/`consColor`**:
- toolwiki today has only the standard 5 brand-token keys (background, foreground, accent, primary, logoUrl)
- pro-con-verdict will render correctly using `background` + `foreground` + `accent` from project + green/red oklch defaults for pros/cons tints
- **No project setup required** before using pro-con-verdict — defaults are sensible

**Tint alpha values** (hardcoded in composition, not in brand-tokens):
- Cover tint over each half: 12% alpha
- Pros/Cons slide background tint: 6% alpha
- Icon color: 100% alpha
- Verdict label colors: 100% alpha

These are visual constants of the template, not tunable. If projects need different intensities, that's an `override.layout.backgroundIntensity` value (already defined in Section D).

**Theme handling** (dark vs light):
- `theme: "dark"` (default): `background` consumed as dark color, `foreground` as light
- `theme: "light"`: `background` as light, `foreground` as dark
- prosColor/consColor unchanged across themes (same green/red, alpha tints work on both backgrounds)
- This matches existing templates' theme handling per audit Section 5

**What this means for Marcel's existing toolwiki brand-tokens**:
- He doesn't need to add anything to project settings
- pro-con-verdict will use his existing `background` / `foreground` / `accent` / `primary` / `logoUrl`
- Pros/cons get sensible oklch green/red by default
- If he later wants brand-specific green/red (e.g. lime green for pros), he adds `prosColor` and `consColor` to project brand-tokens — but it's purely optional

## Section B: TemplateDefinition Contract

### B.1 Definition file

**File:** `packages/social/src/templates/definitions/proConVerdict.ts`

**Naming convention** (verified from 59.3-prep): exported definition constant uses `*Template` suffix, **not** `*Definition`. This matches existing `comparisonGrid4Template`, `singleToolSpotlightTemplate`, `verdictPerUseCaseTemplate` exports established post-59.3-prep refactor.

```typescript
import type { TemplateDefinition } from "../types.js";
import type { ProConVerdictInput } from "../../compositions/pro-con-verdict/types.js";

export const proConVerdictTemplate: TemplateDefinition<ProConVerdictInput> = {
  templateKey: "pro-con-verdict",

  plannerMeta: {
    displayName: { de: "Pro/Con + Verdikt", en: "Pro/Con + Verdict" },
    description: {
      de: "Ausgewogene Bewertung mit Vor-/Nachteilen und finaler Empfehlung",
      en: "Balanced evaluation with pros/cons and final recommendation",
    },
    suitableFor: ["tools"],  // primarily tools collection
    slideCount: 5,
    coverSignature: "split-screen",
  },

  eligibility(article, discovery) {
    // Eligibility: article must have structured pros + cons in frontmatterExtras
    const pros = article.frontmatterExtras?.pros as string[] | undefined;
    const cons = article.frontmatterExtras?.cons as string[] | undefined;

    if (!pros || !cons) {
      return {
        eligible: false,
        reason: "Article has no pros/cons in frontmatterExtras",
      };
    }

    if (pros.length < 3 || cons.length < 3) {
      return {
        eligible: false,
        reason: `pros.length=${pros.length}, cons.length=${cons.length}; need ≥3 each`,
      };
    }

    if (article.collection !== "tools" && article.collection !== "blog") {
      return {
        eligible: false,
        reason: `collection=${article.collection}, only tools/blog supported`,
      };
    }

    return { eligible: true, reason: "" };
  },

  buildInput(article, discovery, overrides) {
    const pros = (article.frontmatterExtras?.pros ?? []) as string[];
    const cons = (article.frontmatterExtras?.cons ?? []) as string[];

    // Apply override bounds
    const maxPros = overrides?.eligibility?.maxPros ?? 5;
    const maxCons = overrides?.eligibility?.maxCons ?? 5;

    return {
      tool: {
        name: article.title ?? "",
        logoUrl: article.frontmatterExtras?.logoUrl as string | undefined,
      },
      pros: pros.slice(0, maxPros),
      cons: cons.slice(0, maxCons),
      // verdict.whenToUse + whenToSkip filled by generateContent()
      verdict: null,  // set in generateContent
      locale: article.locale as "de" | "en",
      theme: "dark",  // default; override-tunable
      brandTokens: undefined,  // resolved at render time
      overrides: overrides ?? undefined,
    };
  },

  async generateContent(article, input, locale, llmCaller) {
    // Single Sonnet 4.6 call: produces verdict snippet + hook + caption + hashtags
    // See Section C for prompt design
    return generateProConVerdictContent({ article, input, locale, llmCaller });
  },

  async render(input, context) {
    // Dynamic import per audit Section 10
    const { renderProConVerdict } = await import("../../render-server.js");
    return renderProConVerdict(input, context);
  },

  mockFixtures: {
    characteristic: characteristicFixture,
    "edge-min": edgeMinFixture,
    "edge-max": edgeMaxFixture,
  },
};
```

## Section C: LLM Prompt Design

### C.1 What the LLM produces

Pros + cons are already extracted by article generation (from `frontmatterExtras`). The LLM only needs to produce:

1. **Verdict snippet** (1 line, ≤120 chars) — for cover
2. **When-to-use** (2-3 sentences) — for verdict slide
3. **When-to-skip** (2-3 sentences) — for verdict slide
4. **Hook** (1-2 sentences) — for caption
5. **Caption body** (1-2 paragraphs) — for caption
6. **Hashtags** (7 bilingual mix) — per existing `buildHashtagInstructions.ts`

Single Sonnet 4.6 call. Output JSON.

### C.2 Prompt structure

```typescript
// packages/social/src/templates/definitions/proConVerdict.ts (continued)

async function generateProConVerdictContent(input: {
  article: Article;
  input: ProConVerdictInput;
  locale: "de" | "en";
  llmCaller: LlmCaller;
}): Promise<GeneratedContent> {
  const localeDirective = input.locale === "de"
    ? "Output in German, du-form, B2B but conversational"
    : "Output in English, concise and direct";

  const hashtags = buildHashtagInstructions(input.locale);

  const prompt = `
You are creating Instagram carousel content for a balanced tool review.

ARTICLE TITLE: ${input.article.title}
ARTICLE INTRO: ${input.article.bodyMd?.substring(0, 800) ?? ""}

PROS (already extracted, don't change):
${input.input.pros.map((p, i) => `${i + 1}. ${p}`).join("\n")}

CONS (already extracted, don't change):
${input.input.cons.map((c, i) => `${i + 1}. ${c}`).join("\n")}

TASK: Produce these elements:

1. verdict_snippet — 1 short line for the cover slide. State the bottom-line judgment in
   ≤120 chars. NOT a generic "depends on use case" — actually take a position. Examples:
   - "Solid für Tutorial-Macher, schwach für Live-Streaming"
   - "Worth it for serious teams, overkill for solo founders"

2. when_to_use — 2-3 sentences. Concrete situations where this tool wins. Reference specific
   user types or workflows from the pros. Don't repeat the pros verbatim — synthesize.

3. when_to_skip — 2-3 sentences. Concrete situations where to look elsewhere. Reference the
   cons. Don't be cowardly: name specific better alternatives if they exist.

4. hook — 1-2 sentences for caption opening. Pattern question or sharp claim. Avoid "Hast du
   schon mal gehört von X?" — too generic. Reference the most counter-intuitive pro or con.

5. caption_body — 1-2 paragraphs. Frame the trade-off. Mention 1-2 specific pros AND 1-2
   specific cons. End with the verdict_snippet (slightly rephrased, not verbatim).

6. hashtags — exactly 7 hashtags. ${hashtags}

${localeDirective}

OUTPUT FORMAT (strict JSON, no preamble):
{
  "verdict_snippet": "string",
  "when_to_use": "string",
  "when_to_skip": "string",
  "hook": "string",
  "caption_body": "string",
  "hashtags": ["#tag1", "#tag2", "#tag3", "#tag4", "#tag5", "#tag6", "#tag7"]
}
`;

  const response = await input.llmCaller({
    model: "claude-sonnet-4-6-20251022",
    maxTokens: 1500,
    messages: [{ role: "user", content: prompt }],
    // NOT jsonMode:true per Memory #21 (Sonnet 4.6 rejects prefill)
  });

  // Manual JSON extraction per Memory #21
  const raw = response.content;
  const jsonStart = raw.indexOf("{");
  const jsonEnd = raw.lastIndexOf("}");
  if (jsonStart === -1 || jsonEnd === -1) {
    throw new Error(`LLM did not return JSON for proConVerdict: ${raw.substring(0, 200)}`);
  }
  const parsed = JSON.parse(raw.substring(jsonStart, jsonEnd + 1));

  // Validate with Zod
  const validated = proConVerdictLlmOutputSchema.parse(parsed);

  return {
    caption: `${validated.hook}\n\n${validated.caption_body}`,
    hashtags: validated.hashtags,
    verdict: {
      snippet: validated.verdict_snippet,
      whenToUse: validated.when_to_use,
      whenToSkip: validated.when_to_skip,
    },
  };
}

const proConVerdictLlmOutputSchema = z.object({
  verdict_snippet: z.string().min(20).max(120),
  when_to_use: z.string().min(30).max(280),
  when_to_skip: z.string().min(30).max(280),
  hook: z.string().min(20).max(280),
  caption_body: z.string().min(80).max(800),
  hashtags: z.array(z.string().regex(/^#[^\s\-#]+$/u)).length(7),
});
```

export async function renderProConVerdict(
  input: ProConVerdictInput,
  context: RenderContext,
): Promise<RenderedSlides> {
  const serveUrl = await ensureBundleServer();
  const compositions = await getCompositions(serveUrl, {
    inputProps: { ...input, brandTokens: context.brandTokens },
  });
  const composition = compositions.find(c => c.id === "ProConVerdict");
  if (!composition) throw new Error("ProConVerdict composition not found");

  const slideCount = input.overrides?.layout?.includeEndSlide === false ? 4 : 5;
  const slides: RenderedSlide[] = [];

  for (let i = 0; i < slideCount; i++) {
    const buffer = await renderStill({
      composition,
      serveUrl,
      inputProps: { ...input, slideIndex: i, brandTokens: context.brandTokens },
      outputLocation: null,
      imageFormat: "png",
    });
    slides.push({ buffer, slideIndex: i, width: 1080, height: 1350 });
  }

  return { slides };
}

## Decisions Made

**Decision 1: Fixed 5-slide structure, not dynamic.**
Pro-con structure is intrinsically symmetric (pros vs cons). 1 slide per side is balanced; variable counts feel asymmetric.

**Decision 2: Split-screen cover as signature visual.**
Differentiates from existing 4 templates' cover styles. Color-coded (green/red) reinforces the article's structural promise to viewers.

**Decision 3: LLM produces only narrative content, not pros/cons.**
Pros/cons already exist in `frontmatterExtras` from article generation. LLM extracts: verdict snippet, when-to-use, when-to-skip, hook, caption, hashtags. Reduces cost + uses existing structured data.

**Decision 4: Eligibility = pros ≥ 3 AND cons ≥ 3.**
Below 3 each, the visual structure breaks (one bullet looks weak). Above 5, slides feel cluttered. Override-tunable.

**Decision 5: Collections supported: `tools` + `blog`.**
Tools have native pros/cons in frontmatterExtras. Blog articles can opt-in by adding pros/cons to their frontmatter. Other collections (use-cases, comparisons, etc.) lack the data structure.

**Decision 6: New brand-token keys `prosColor`/`consColor` are OPTIONAL with sensible defaults; existing brand-token keys are consumed unchanged.**
The template consumes the same brand-token keys (background, foreground, accent, primary, logoUrl, fontFamily) as existing 4 templates — visual consistency in the Instagram grid is maintained. The new `prosColor`/`consColor` keys are additive and optional; defaults are oklch green/red that work on both dark and light themes. Marcel's existing toolwiki project requires no brand-tokens changes — pro-con-verdict renders correctly out-of-the-box using his existing tokens + oklch defaults. See Section A.8 for full mapping.

**Decision 7: Verdict slide mirrors cover's split-language.**
Two horizontal sections (when-to-use / when-to-skip) reinforce the cover's pro/con structure. Visual repetition aids comprehension across slides.

**Decision 8: End slide reuses existing CTA pattern.**
No reason to reinvent. Same component as comparison-grid + verdict-per-use-case.

**Decision 9: No layout-tunable "vertical split" cover variation in 59.3.**
Override exists (`coverSplitDirection: "diagonal" | "vertical" | "horizontal"`), but only diagonal implemented in first version. Vertical/horizontal are scaffolding for future iteration.

**Decision 10: Bilingual via existing pattern (override copy + locale-driven LLM prompt).**
No new mechanism. Follows comparison-grid + verdict-per-use-case patterns. Audit Section 6 documents the existing pattern.

**Decision 11: Cost ~€0.02-0.03 per generation.**
Single LLM call, comparable to existing templates. No optimizations needed in v1.

**Decision 12: Re-render via 58.2 snapshot pattern works automatically.**
Audit Section 7 confirms: re-render flow is template-agnostic. 59.3 just needs to be registered in the worker switch, then re-render uses existing pipeline.

**Decision 13: Test fixtures cover characteristic + edge-min + edge-max per audit pattern.**
Same 3-fixture convention as existing templates. Edge-max validates layout under maximum content load.

**Decision 14: Composition directory name `pro-con-verdict/` matches template key.**
Per audit Section 10 file pattern. Consistency with existing template directories.

## Risks & Mitigations

**R1: Diagonal SVG clipPath performs poorly in Chromium render.**
- *Mitigation*: Standard SVG path with simple polygon, no animations. Chromium handles 1 path per render fine. If slow: fallback to vertical split.

**R2: Pros/cons text exceeds 120 chars (max slide width).**
- *Mitigation*: Zod schema enforces max 120. Fixtures test edge-max. Article-generation step should also enforce this in frontmatter validation (deferred to article-side spec if needed).

**R3: Articles lack `frontmatterExtras.pros`/`cons` (recently-imported or older articles).**
- *Mitigation*: Eligibility predicate returns false with clear reason. Template doesn't appear in picker. Future: spec 59.6 article-gen-variants might add pros/cons extraction step for articles missing them.

**R4: LLM verdict-snippet is too generic ("depends on use case").**
- *Mitigation*: Prompt explicitly forbids generic verdicts ("NOT a generic 'depends on use case'"). Two example patterns provided. If still bad: post-generation review or Haiku grading step.

**R5: Cover's color contrast fails accessibility.**
- *Mitigation*: oklch defaults chosen for sufficient contrast on dark theme. Manual smoke verifies. Light theme tested in edge-min fixture.

**R6: Tool name too long for cover layout.**
- *Mitigation*: edge-max fixture tests "Maximum Length Tool Name That Tests Layout Wrapping". CSS clamp() + responsive font sizing handles overflow.

**R7: When-to-use / when-to-skip content collides on verdict slide.**
- *Mitigation*: Zod max 280 chars each = ~2-3 sentences. Layout uses fixed-height sections with overflow:hidden. Tested in edge-max fixture.

**R8: New brand-token keys `prosColor`/`consColor` not in existing brand_tokens JSONB.**
- *Mitigation*: Optional with oklch defaults. **All existing projects render correctly without any brand-tokens changes** — pro-con-verdict consumes the same standard brand-tokens (background/foreground/accent/primary/logoUrl) as existing 4 templates, plus oklch green/red defaults for pros/cons. Settings UI later (Phase E?) exposes editing.

## Discovered During Implementation

**D1: `ContentType` for `buildHashtagInstructions` does not include `"tool-spotlight"`.**
The actual union is `"comparison" | "review" | "general"` (from `packages/core/src/social-hashtags/buildHashtagInstructions.ts`). Using `"tool-spotlight"` causes a TypeScript error. Single-tool evaluation templates should use `contentType: "review"`. The spec's LLM section should specify `contentType: "review"` explicitly — now documented in `packages/social/src/templates/CLAUDE.md`.

**D2: `HookOutput.pattern` enum values differ from intuitive names.**
Actual valid values: `"superlative_question" | "number_promise" | "negative_frame" | "identity_frame" | "curiosity_gap"` (from `list-carousel/types.ts`). Any fallback hookOutput in custom `generateContent()` must use one of these — `"negative_frame"` is the safe default.

**D3: `GeneratedContent` is a fixed type; templates needing extra LLM data must use the `_verdict` extension pattern.**
`GeneratedContent = { hookOutput, caption, hashtags }` cannot be extended. The canonical approach is `type Extended = GeneratedContent & { _verdict: VerdictData | null }`, returning `as unknown as GeneratedContent` from `generateContent()` and casting back in `render()`. Documented in `packages/social/src/templates/CLAUDE.md`.

## Deviations from Spec

**Dev-1: Override copy strings parsed in each slide component, not in the dispatcher.**
The spec (Section D) implied override copy would be passed down from the dispatcher. In the implementation, each slide component that uses override-controlled strings calls `proConVerdictOverridesSchema.parse(input.overrides ?? {})` directly. This avoids changing slide prop types and keeps each slide self-contained. The behavior is identical; the difference is architectural.

**Dev-2: `safeZones.ts` not created as a new file — reuses `list-carousel/safeZones.ts`.**
The spec listed `safeZones.ts` in the composition directory (F.6). All slides import `CAROUSEL_SAFE_ZONES` from `../list-carousel/safeZones.ts` directly — no duplication needed since canvas dimensions are shared across all templates.

**Dev-3: `prosColor`/`consColor` stored on `brandTokens.colors.*` not top-level.**
The spec described `prosColor`/`consColor` as top-level brand-token keys. The implementation adds them to `brandTokensSchema.colors.prosColor` / `brandTokensSchema.colors.consColor` (in `list-carousel/types.ts`), consistent with where other non-standard color extensions live. `resolveProsColor()` reads `brandTokens?.colors?.prosColor`.
