## 3. Architecture Decisions

### 3.1 Cron Implementation

Per Marcel-Decision: `*/15 * * * *`.

**File:** `apps/api/src/workers/recurring-content.cron.ts`

```typescript
// Per Memory D17 — Cron-based Coordinator Pattern
const CRON_INTERVAL_MS = 15 * 60 * 1000;
const BATCH_SIZE = 10;  // limit per-tick, prevents stampede

export function startRecurringContentCron() {
  setInterval(async () => {
    try {
      const due = await listDueRecurringDefinitions({ limit: BATCH_SIZE });
      
      if (due.length === 0) return;
      
      logger.info('Recurring content cron triggered', { dueCount: due.length });
      
      for (const definition of due) {
        await routeBriefGeneration({
          kind: 'recurring',
          definitionId: definition.id,
          projectId: definition.projectId,
        });
      }
    } catch (err) {
      logger.error('Recurring content cron failed', err);
    }
  }, CRON_INTERVAL_MS).unref();
}
```

**Single-instance enforcement:** Cron lebt nur in API process, nicht workers (per Memory D17).

**Race-buffer per Memory D17:** `listDueRecurringDefinitions` filters `created_at < NOW() - INTERVAL '30 seconds'` to avoid transaction-races.

### 3.2 Brief-Generation Trigger Evaluation (Marcel: Discovery evaluiert)

**Option α — Pipeline-Router Extension (62.8 discriminator pattern):**

Add `kind: 'recurring'` als 3rd case zu router union.

```typescript
type PipelineRoute =
  | { kind: 'enqueue'; pipelineName: string; input: PipelineInput }
  | { kind: 'inline'; pipelineName: string; input: PipelineInput }
  | { kind: 'recurring'; definitionId: string; projectId: string };  // NEW

async function routeBriefGeneration(route: PipelineRoute) {
  switch (route.kind) {
    case 'recurring':
      await enqueueRecurringBriefJob({
        definitionId: route.definitionId,
        projectId: route.projectId,
      });
      break;
    // ... existing cases
  }
}
```

Pros:
- Consistent mit existing 62.8 pattern (Memory D5)
- Single dispatch-point for all pipeline-style operations
- Future-extensible (BK adds own kinds)

Cons:
- Router gets broader scope (was: pipeline-input; is: pipeline-input + recurring)
- Semantic-shift: 'kind' meant "execution mode" (enqueue/inline), now also means "trigger type" (recurring)

**Option β — Standalone Worker (parallel to router):**

```typescript
// apps/api/src/workers/recurring-brief-generator.worker.ts
const worker = new Worker('recurring-brief-generator', async (job) => {
  const { definitionId, projectId } = job.data;
  const definition = await getRecurringDefinition(definitionId);
  await generateBriefForRecurringDefinition({ definition, projectId });
});
```

Pros:
- Clean separation — router unchanged, recurring lives in own worker
- Easier to test isolated
- Easier to add recurring-specific concerns (rate-limiting, cost-budgets)

Cons:
- Two dispatch-paths (router for ad-hoc, recurring-worker for cron)
- Slight duplication if BK later adds different recurring-source

**Option γ — Inline im Cron (no worker abstraction):**

```typescript
for (const definition of due) {
  await generateBriefForRecurringDefinition({ definition });
  await markRecurringDefinitionRun(definition.id, { newNextRunAt: ... });
}
```

Pros:
- Simplest, no Redis-overhead
- Direct error-propagation

Cons:
- Cron-tick blocked if 10 generators run sequentially (~3-5s each = 30-50s/tick → could overflow 15min window if 60+ briefs/tick someday)
- No retry-machinery (BullMQ retries für free in α+β)
- Failed generator blocks subsequent definitions in batch

### Discovery-Recommendation: **Option β (Standalone Worker)**

Reasoning:

1. **Existing router (62.8) ist semantically tied to brief-pipeline routing** — adding 'recurring' diluted its purpose
2. **BullMQ-native = retries, dead-letter, observable** — recurring-jobs that fail get retry mit exp-backoff
3. **Recurring has unique concerns** — cost-budgets, definition-locking (prevent parallel runs of same definition), persona-cache-warming
4. **Pattern matches 65.3 tool-data-refresh** — also has own worker (`tool-data-refresh.worker.ts`)
5. **Future BK-flexibility** — wenn BK adds different recurring-source (z.B. seasonal solar-content), recurring-worker can dispatch to multiple generator-strategies

**Implementation:**

```typescript
// apps/api/src/workers/recurring-brief-generator.worker.ts
import { Worker } from 'bullmq';

const worker = new Worker('recurring-brief-generator', async (job) => {
  const { definitionId, projectId } = job.data;
  
  // 1. Acquire definition-lock (prevent concurrent runs same definition)
  const lockKey = `recurring-def:${definitionId}`;
  const acquired = await tryAcquireRedisLock(lockKey, { ttlSec: 300 });
  if (!acquired) return { status: 'skipped', reason: 'already-running' };
  
  try {
    const definition = await getRecurringDefinition(definitionId);
    if (!definition || !definition.isActive) {
      return { status: 'skipped', reason: 'inactive-or-deleted' };
    }
    
    const result = await generateBriefForRecurringDefinition({ definition, projectId });
    
    await markRecurringDefinitionRun(definitionId, {
      newNextRunAt: computeNextRun(definition.frequency),
    });
    
    return result;
  } finally {
    await releaseRedisLock(lockKey);
  }
});
```

### 3.4 3-Layer Template-Selection (replaces 65.6)

Per Marcel-Decision: full 3-Layer in 65.5 = 65.6 obsolet.

**File:** `apps/api/src/lib/recurring-content/brief-generators/shared/select-template.ts`

```typescript
export interface SelectTemplateInput {
  definitionId: string;
  formatType: string;
  projectId: string;
  briefContext: {
    toolIds: string[];
    persona?: string;
    angle?: string;
  };
}

export interface SelectedTemplate {
  templateKey: string;
  selectedVia: 'fixed' | 'lru' | 'llm-rank';
  reasoning?: string;
}

export async function selectTemplateForRecurringBrief(input: SelectTemplateInput): Promise<SelectedTemplate> {
  const definition = await getRecurringDefinition(input.definitionId);
  
  // FIXED strategy — bypass layers
  if (definition.templateSelectionStrategy === 'fixed' && definition.fixedTemplateKey) {
    return { templateKey: definition.fixedTemplateKey, selectedVia: 'fixed' };
  }
  
  // Layer 1: Eligible templates per format-type (from 65.4 registry)
  const formatTypeDef = FORMAT_TYPES[input.formatType];
  if (!formatTypeDef) throw new Error(`Unknown format-type: ${input.formatType}`);
  
  const eligible = formatTypeDef.eligibleTemplates;
  if (eligible.length === 0) {
    throw new Error(`No eligible templates for format-type: ${input.formatType}`);
  }
  
  // Single-eligible shortcut
  if (eligible.length === 1) {
    return { templateKey: eligible[0], selectedVia: 'lru' };  // trivially LRU
  }
  
  // Layer 2: LRU strategy — pick least-recently-used among eligible
  if (definition.templateSelectionStrategy === 'lru') {
    const recentlyUsed = await listRecentTemplateUsage({
      recurringDefinitionId: input.definitionId,
      limit: eligible.length - 1,  // keep at least 1 candidate
    });
    const recentlyUsedKeys = new Set(recentlyUsed.map(r => r.templateKey));
    const lruCandidate = eligible.find(t => !recentlyUsedKeys.has(t)) ?? eligible[0];
    return { templateKey: lruCandidate, selectedVia: 'lru' };
  }
  
  // Layer 3: LLM-rank — Haiku 4.5 + jsonMode (per Memory D27 watch-pattern)
  if (definition.templateSelectionStrategy === 'llm-picks') {
    const ranked = await llmRankTemplates({
      formatType: input.formatType,
      candidates: eligible,
      briefContext: input.briefContext,
    });
    return { templateKey: ranked.pickedTemplateKey, selectedVia: 'llm-rank', reasoning: ranked.reasoning };
  }
  
  // Default: LRU
  const recentlyUsed = await listRecentTemplateUsage({
    recurringDefinitionId: input.definitionId,
    limit: eligible.length - 1,
  });
  const recentlyUsedKeys = new Set(recentlyUsed.map(r => r.templateKey));
  const lruCandidate = eligible.find(t => !recentlyUsedKeys.has(t)) ?? eligible[0];
  return { templateKey: lruCandidate, selectedVia: 'lru' };
}
```

**LLM-Rank prompt:**

```typescript
async function llmRankTemplates(input: LlmRankInput): Promise<LlmRankResult> {
  const prompt = `
Pick the best template for this brief from the candidates.

Format-type: ${input.formatType}
Brief context:
- Tools featured: ${input.briefContext.toolIds?.join(', ')}
- Persona: ${input.briefContext.persona ?? 'general'}
- Angle: ${input.briefContext.angle ?? 'standard'}

Candidate templates:
${input.candidates.map(t => `- ${t}`).join('\n')}

Pick the template that best fits the brief context.
Return JSON: { pickedTemplateKey: "<key>", reasoning: "<why>" }
`;
  
  const result = await anthropic.messages({
    model: 'claude-haiku-4-5-20251001',
    jsonMode: true,
    messages: [{ role: 'user', content: prompt }],
  });
  
  const parsed = LLM_RANK_OUTPUT_SCHEMA.safeParse(result.json);
  if (!parsed.success) {
    // Fallback to LRU on schema-fail
    return { pickedTemplateKey: input.candidates[0], reasoning: 'LLM schema-fail fallback' };
  }
  
  // Validate LLM didn't hallucinate non-eligible template
  if (!input.candidates.includes(parsed.data.pickedTemplateKey)) {
    return { pickedTemplateKey: input.candidates[0], reasoning: 'LLM hallucination fallback' };
  }
  
  return parsed.data;
}
```

```typescript
export interface PickToolsInput {
  projectId: string;
  formatType: string;
  formatConfig: {
    categorySlug?: string;
    manualToolIds?: string[];      // Marcel override per definition
    topN?: number;
    excludeRecentlyUsed?: boolean;
  };
  previousRunToolIds?: string[];   // from definition's last run
}

export async function pickToolsForBrief(input: PickToolsInput): Promise<string[]> {
  // Manual override path
  if (input.formatConfig.manualToolIds?.length) {
    return input.formatConfig.manualToolIds.slice(0, input.formatConfig.topN ?? 5);
  }
  
  // LLM-curated path (Master-Spec default)
  const candidatePool = await listToolsForCategory({
    projectId: input.projectId,
    categorySlug: input.formatConfig.categorySlug,
    excludeIds: input.formatConfig.excludeRecentlyUsed ? input.previousRunToolIds : undefined,
    limit: 20,  // oversample for LLM-pick
  });
  
  if (candidatePool.length < (input.formatConfig.topN ?? 5)) {
    throw new Error(`Insufficient tool-pool: ${candidatePool.length} < ${input.formatConfig.topN}`);
  }
  
  // LLM-curate top-N from pool
  const curated = await llmCurateTopTools({
    formatType: input.formatType,
    candidatePool,
    topN: input.formatConfig.topN ?? 5,
  });
  
  return curated.map(c => c.toolId);
}
```

## 6. Frequency Parsing

```typescript
import { addDays, addMonths } from 'date-fns';

export function computeNextRun(frequency: string, lastRunAt: Date = new Date()): Date {
  switch (frequency) {
    case 'weekly':
      return addDays(lastRunAt, 7);
    case 'biweekly':
      return addDays(lastRunAt, 14);
    case 'monthly':
      return addMonths(lastRunAt, 1);
    default:
      // Cron-expression — use cron-parser library
      return parseCronExpression(frequency).next().toDate();
  }
}
```

### Deviations from spec narrative

1. **Content-type naming.** Spec §5 listed `recurring-content` (kebab-case); existing `CONTENT_TYPES` convention is snake_case (`cluster_spoke`, `social_post`, `ki_wissen`). Renamed to `recurring_content` for consistency. All 11 registration sites use the snake_case form.

V1 routes through the existing `article:social-image` pipeline because `output_targets` defaults to `{article:false, social:true}` (Spec 65.1 schema). The router branches to `article:blog` when `outputTargets.article === true && social !== true`. No new pipeline class needed for V1.

3. **No "Settings UI" creation flow.** Spec §5 (out-of-scope) deferred to 65.11/65.12. For now, definitions can be inserted via DB; the SettingsPlannerPage's "Recurring" content-type column lets Marcel set min/max planner goals against the bucket. End-to-end create-from-UI lands later.

4. **`addMonths` requires explicit day-clamp.** Spec §6 referenced `addMonths from date-fns`. To avoid a new dep, implemented inline with `setUTCMonth` — but JS `setUTCMonth` does NOT clamp day-of-month (Jan 31 + 1 month overflows into March because Feb has 28/29 days). Fix: store original day, set day=1, advance month, then `min(originalDay, lastDayOfNewMonth)`. Regression test in `compute-next-run.test.ts:25` locks down Feb 28 / Feb 29 leap-year semantics.

5. **Backend notification text English, not German.** Spec §4.1 used German user-facing strings. Switched to English in `notify-skipped.ts` to match the existing `notify-batch.ts` convention (Spec 65.3 Part B). Admin notifications render directly in the panel — no i18n routing.

7. **Pipeline-Router `cluster_assignment_required`-style gate not added.** Recurring briefs land as `clusterAction: 'standalone'` per spec — no cluster anchor needed, so the 64.9 plan-vs-immediate gate predicate doesn't apply. Plan-pending flow inherits the existing `approveBrief()` path.

For Toolwiki's expected scale (~14 recurring briefs/month per definition, ≤20 definitions total) this is fine. ### Footguns surfaced (now CLAUDE.md DO-NOTs)

1. **JSDoc block comments and cron `*/15` syntax conflict.** Writing `` `*/15 * * * *` `` inside a `/** ... */` block comment ends the comment prematurely at `*/`, producing 11 TS1109/TS1005/TS1160 errors. Fix: escape the slash as `*\/15` inside the JSDoc literal. The backtick + escaped-slash form parses cleanly, while the rendered docstring still reads correctly. Documented in root CLAUDE.md DO-NOTs.

2. **JS `setUTCMonth` does NOT clamp day-of-month.** `new Date('2026-01-31').setUTCMonth(1)` → `2026-03-03`, not Feb 28. Universally true in JS — bites any monthly-cadence helper. Fix in §16 Deviation 4 above. Documented as inline comment in `compute-next-run.ts`.

3. **Drizzle batch insert with union types fails.** `db.insert(table).values([{a, b}, {a, c}])` rejects the call when the two objects' types diverge (e.g. `logoUrl: string` vs `logoUrl: null`). Fix: split into separate `.values({...})` calls. Caught in `check-brand-assets.test.ts` when seeding two tool_brand_assets rows with different logoUrl types.

4. **`tool_brand_assets` has NO `project_id` column.** Spec §4 spec narrative implied project-scoping. The schema header docstring (Spec 65.1 `tool-brand-assets.ts:7`) explicitly says tool-scoped — "same Claude logo serves every project that mentions Claude". My test seeds initially included `projectId`; column doesn't exist. Memory D5 multi-tenant exception per Spec 65.1.

### Patterns surfaced

1. **Cron-coordinator + standalone BullMQ worker split.** `setInterval` in `server.ts` (API-process only) drives discovery; per-item jobs enqueue into a BullMQ queue consumed by a worker in `workers/index.ts`. Memory D17 + D24. Same shape as `template-usage-log-prune.cron.ts` (Spec 65.1) — reusable for any future "fire per-row on a fixed cadence" workflow that needs retries + observability per item.

2. **Redis-lock per-entity via `SET NX EX` + Lua release.** `tryAcquireRedisLock(key, ttl)` returns a unique token; `releaseRedisLock(key, token)` uses a Lua script (`if get == token then del`) to release only if we still own the lock. Prevents wrong-release after TTL expiration. Reusable for any future "one-active-run-per-entity" coordinator.

3. **3-Layer template-selector with hallucination fallback.** `fixed → LRU → LLM-rank` with each layer falling through on failure. The LLM-rank Layer 3 explicitly returns `null` on Zod-fail / hallucination / throw, and the caller falls back to the LRU pick. Same defense-in-depth shape as 65.4 Hook-Picker's fallback to first LRU candidate.

4. **Frozen `format_config` snapshot in `topic_briefs.recurring_metadata`.** `persist-brief.ts` writes a snapshot that mirrors the definition's `format_config` PLUS the selected template + hook + tool IDs at emit time. Downstream replay never needs to re-query the definition row. Same pattern as `weekly_plans.input_snapshot` (Spec 62.5.1).
