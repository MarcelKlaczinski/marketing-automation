### 3.7 Image-Usage Evaluation (Marcel: Discovery evaluiert)

**Option α — Every slide has image (5-7 images per carousel):**

Pros:
- Most visual richness, maximum "viral" potential
- Consistent visual-language across slides

Cons:
- 5-7 LLM image-pick calls per render = ~€0.15-0.25 image-LLM-cost alone
- Render-time +30-45s (LLM-pick takes 5-8s each)
- Increased provider-rate-limit consumption

**Option β — Cover-only photographic, narrative slides use gradient:**

Pros:
- 1 LLM-pick call only (~€0.02-0.05)
- Fast render
- Brand-color consistency in narrative slides

Cons:
- "Viral" intent compromised — single image vs full photographic carousel
- Visual-monotony for slides 2-7

**Option γ — Hybrid: emotion-heavy slides photographic, transition-slides gradient:**

Per template, define which slides need image vs gradient:

- **story_arc:** Cover + Conflict + Resolution + Payoff = 4 images (slides 1, 3, 4, 5)
  - Setup (slide 2), Lesson (slide 6) = gradient
- **lifestyle_listicle:** Cover + each Item-slide = 4 images (slides 1, 3, 4, 5)
  - Intro (slide 2) = gradient
- **opinion_recommendation:** Cover + Hot-Take + Top-Pick = 3 images (slides 1, 2, 5)
  - Reasoning slides = gradient (text-heavy, image distracts)

**Cost-impact Option γ:** Avg 3-4 images per carousel = ~€0.10-0.15 image-LLM + ~€0.05 query-keywords.

### Discovery-Recommendation: **Option γ (Hybrid: emotion-heavy slides only)**

Reasoning:

1. **Best signal-to-noise ratio** — emotion-driving slides get images, transition-slides keep text-focus
2. **Cost-aligned with Marcel's €0.30-0.50/post budget** — Option α might overshoot
3. **Visual-rhythm pattern** — alternating image/gradient creates narrative-pacing (cf. magazine-design)
4. **Render-time stays <90s** — Option α might push >120s (Engine abort-controller risk)
5. **Provider-rate-limit headroom** — 3-4 queries × ~14 posts/month = ~50 req/month, far below 50/h limits

### 3.8 Image-Query-Strategy (Marcel-Decision: Hybrid hook-variables + LLM-enrichment)

**Implementation:**

```typescript
// packages/social/src/photographic/generate-query-keywords.ts

interface QueryKeywordsInput {
  hookContext: FamilyBHookContext;
  narrativeBeat: string;             // e.g. "setup", "conflict", "resolution"
  beatText: string;                  // LLM-generated narrative for this beat
  formatType: string;
}

export async function generateImageQueryKeywords(
  input: QueryKeywordsInput,
): Promise<string[]> {
  // Haiku batch-call for cost-efficiency (per D28)
  const response = await callLLM({
    model: 'claude-haiku-4-5',
    messages: [{
      role: 'user',
      content: `
Generate 3 image-search-query keywords for this carousel-slide.

Context:
- Hook: "${input.hookContext.rendered}"
- Variables: ${JSON.stringify(input.hookContext.variables)}
- Narrative beat (${input.narrativeBeat}): "${input.beatText}"

Generate queries that match emotional tone of beat:
- Setup: scene-setting, contextual
- Conflict: tension, frustration, problem-state
- Resolution: discovery, breakthrough, hope
- Payoff: success, transformation, outcome

Return JSON array of 3 query-strings (English, since most provider-APIs index English):
["query1", "query2", "query3"]

Each query 3-6 words. Prefer concrete nouns + emotional adjectives.
`,
    }],
    response_format: { type: 'json_object' },
  });
  
  return ImageQueryKeywordsSchema.parse(JSON.parse(response.content));
}
```

**Cost per slide:** ~€0.01-0.02 (Haiku, ~300 tokens output).

**Why hybrid pattern:**
- Hook variables anchor query in story-context (e.g. profession="Texter" → query includes "writer")
- LLM-enrichment adds emotional-tone matching narrative-beat
- 3 queries per slide give provider-search variety (some return better hits for one phrasing)

### 3.9 Provider-Strategy (Marcel-Decision: parallel-search + LLM picks best)

**Implementation:**

```typescript
// packages/social/src/photographic/providers/index.ts

interface ProviderSearchResult {
  provider: 'pexels' | 'unsplash' | 'pixabay';
  imageUrl: string;
  thumbnailUrl: string;
  photographer?: string;        // For attribution-tracking (Unsplash)
  license: 'pexels' | 'unsplash' | 'pixabay';
  width: number;
  height: number;
  description?: string;         // Alt-text from provider
}

export async function searchAllProviders(
  queries: string[],
): Promise<ProviderSearchResult[]> {
  // Parallel-search all 3, all 3 queries
  // = 3 providers × 3 queries × 5-10 results-per-query = ~50 candidates
  
  const allResults = await Promise.all([
    searchPexels(queries),
    searchUnsplash(queries),
    searchPixabay(queries),
  ]);
  
  return allResults.flat();
}

async function searchPexels(queries: string[]): Promise<ProviderSearchResult[]> {
  const results = await Promise.all(
    queries.map(q => fetch(`https://api.pexels.com/v1/search?query=${encodeURIComponent(q)}&per_page=5&orientation=portrait`, {
      headers: { Authorization: env.PEXELS_API_KEY },
    }).then(r => r.json()))
  );
  
  return results.flatMap(r => r.photos.map(p => ({
    provider: 'pexels' as const,
    imageUrl: p.src.large,
    thumbnailUrl: p.src.medium,
    photographer: p.photographer,
    license: 'pexels' as const,
    width: p.width,
    height: p.height,
    description: p.alt,
  })));
}

// Similar for Unsplash and Pixabay
```

**Rate-limit management:**

- Pexels 200 req/h = 3 providers × 3 queries × 3-4 image-slides × 14 posts/month = ~500 req/month = ~17/day = trivial
- Unsplash 50 req/h = ~17 req/day = OK
- Pixabay no realistic limit (100 req/min)

**LLM image-pick:**

```typescript
// packages/social/src/photographic/pick-image-llm.ts

export async function pickBestImage(
  candidates: ProviderSearchResult[],
  context: {
    beatText: string;
    hookContext: FamilyBHookContext;
    theme: 'light' | 'dark';
    brandPrimaryColor: string;
  },
): Promise<ProviderSearchResult> {
  // Sonnet 4.7 vision-call with all candidate-thumbnails
  
  const imageMessages = candidates.map((c, idx) => ({
    type: 'image' as const,
    source: { type: 'url', url: c.thumbnailUrl },
  }));
  
  const response = await callLLM({
    model: 'claude-sonnet-4-7',
    messages: [{
      role: 'user',
      content: [
        ...imageMessages,
        {
          type: 'text',
          text: `
Pick the best image (1-${candidates.length}) for this carousel slide.

Context:
- Hook: "${context.hookContext.rendered}"
- Narrative beat: "${context.beatText}"
- Theme: ${context.theme}
- Brand color overlay (semi-transparent): ${context.brandPrimaryColor}

Criteria:
1. Emotional match with beat-text mood
2. Composition allows text-overlay (negative-space or single subject)
3. Quality: avoid stock-photo-cliche, prefer authentic moments
4. Brand-fit: image-tones harmonize with brand color (no jarring contrast)
5. ${context.theme === 'dark' ? 'Darker images preferred (dark theme)' : 'Brighter images preferred (light theme)'}

Return JSON:
{
  "selectedIndex": 1-${candidates.length},
  "reasoning": "1 sentence why"
}
`,
        },
      ],
    }],
    response_format: { type: 'json_object' },
  });
  
  const pick = PickResponseSchema.parse(JSON.parse(response.content));
  return candidates[pick.selectedIndex - 1];
}
```

**Cost per LLM-pick:** Sonnet vision with ~10 thumbnails + reasoning ≈ €0.02-0.04 per call.

**Why parallel-search vs fallback-chain:**

- **Parallel maximizes candidate-quality** — Pexels might have authentic-emotion shots Unsplash lacks for specific query
- **LLM is the curator** — Marcel-Decision "LLM picks best match" requires multi-provider candidate pool
- **Rate-limit not a concern at V1 scale** (~50 req/month per provider max)
- **License-diversity** — LLM might prefer Pixabay/Pexels (no attribution) when Unsplash-quality is on-par

### 3.10 Image-Caching Evaluation (Marcel: Discovery evaluiert)

**Option α — R2 stage per slide-id:**

```typescript
// Stage chosen image to R2 with key: <projectSlug>/families/family-b/<articleId>/slide-<idx>.jpg
// Re-renders use same image (no surprise change)
// Marcel can toggle "refresh images" flag in re-render endpoint
```

Pros:
- Re-render consistency
- Reduces provider-API-calls on re-render
- License-metadata travels with image (license-tracker)

Cons:
- R2-storage costs (~€0.001/image; ~14 posts × 4 images × 12 months = 672 images ≈ €0.70/year — vernachlässigbar)
- Cache-invalidation needs manual flag

**Option β — Inline fetch at render-time:**

Pros:
- Always-fresh images (re-renders pick different image each time)
- No R2-storage overhead

Cons:
- Re-render produces different content (Marcel-confusion)
- Provider-API-calls duplicated on every render
- Latency on every render

**Option γ — Cache provider-result for 30 days (same query → same image):**

Cache LLM-pick-result by `hash(queries + hookContext) → ProviderSearchResult`.

Pros:
- Idempotent: same input → same image
- No R2-overhead (just key-value cache in Redis or similar)

Cons:
- Doesn't survive cache-clear
- Different cron-runs might query slightly differently → cache-miss

### Discovery-Recommendation: **Option α (R2 stage per slide-id)**

Reasoning:

1. **Re-render consistency is critical UX** — Marcel re-renders nach LLM-narrative-failure expects SAME images
2. **R2-cost vernachlässigbar** — €0.70/year for full image-cache
3. **License-metadata preservation** — license-tracker reads R2-object-metadata; not possible without staging
4. **"Refresh images" flag in re-render UI** — gives Marcel control when needed
5. **Idempotent renders** — same brief + same slide-id = same image; matches engineering-discipline

**Implementation:**

```typescript
// packages/social/src/photographic/r2-image-cache.ts

export async function stageImageToR2(
  imageUrl: string,
  meta: { articleId: string; projectSlug: string; slideIndex: number },
  license: { provider: string; photographer?: string },
): Promise<{ r2Key: string; cdnUrl: string }> {
  // Fetch from provider
  const buffer = await fetch(imageUrl).then(r => r.arrayBuffer());
  
  // Optimize: resize to 1080×1350 (4:5), JPEG q80
  const optimized = await optimizeForCarousel(buffer);
  
  // Upload to R2
  const r2Key = `${meta.projectSlug}/articles/${meta.articleId}/images/slide-${meta.slideIndex.toString().padStart(2, '0')}.jpg`;
  
  await r2Client.putObject({
    Bucket: env.R2_BUCKET,
    Key: r2Key,
    Body: optimized,
    ContentType: 'image/jpeg',
    Metadata: {
      'license-provider': license.provider,
      'license-photographer': license.photographer ?? '',
      'cached-at': new Date().toISOString(),
    },
  });
  
  return {
    r2Key,
    cdnUrl: `https://${env.R2_CDN_DOMAIN}/${r2Key}`,
  };
}

export async function getCachedImageForSlide(
  articleId: string,
  projectSlug: string,
  slideIndex: number,
): Promise<{ cdnUrl: string; license: License } | null> {
  const r2Key = `${projectSlug}/articles/${articleId}/images/slide-${slideIndex.toString().padStart(2, '0')}.jpg`;
  
  try {
    const head = await r2Client.headObject({ Bucket: env.R2_BUCKET, Key: r2Key });
    return {
      cdnUrl: `https://${env.R2_CDN_DOMAIN}/${r2Key}`,
      license: {
        provider: head.Metadata['license-provider'],
        photographer: head.Metadata['license-photographer'],
      },
    };
  } catch {
    return null;
  }
}
```

### Discovery-Recommendation: **Option δ (Variable per slide-type)**

Reasoning:

1. **Each slide-anatomy has different communicative-priority** — Cover needs impact, narrative-slides need immersion, item-slides need brand-context
2. **Single composition-rule is one-size-fits-none** — Option α-γ each have legitimate use-cases
3. **Magazine-editorial visual-language emerges naturally** — variable layouts is signature of editorial-design
4. **Implementation-cost low** — 3 composition-variants in `_shared/family-b/SlideComposition.tsx`
5. **Pattern matches Family A** — Family A also has variable per-slide layouts (Cover vs Tool-slide vs Verdict differ visually)

interface SlideCompositionProps {
  variant: 'cover' | 'immersive' | 'product-context' | 'editorial';
  image?: { cdnUrl: string };
  brandTokens: BrandTokens;
  ds: EmotionalDsTokens;
  children: React.ReactNode;
}

export const SlideComposition: React.FC<SlideCompositionProps> = ({ variant, image, brandTokens, ds, children }) => {
  if (!image) {
    // Gradient-fallback (no image for this slide-type)
    return <GradientBackground ds={ds}>{children}</GradientBackground>;
  }
  
  switch (variant) {
    case 'cover':
      return <SplitLayoutComposition image={image} ds={ds}>{children}</SplitLayoutComposition>;
    case 'immersive':
      return <ImmersiveComposition image={image} ds={ds}>{children}</ImmersiveComposition>;
    case 'product-context':
      return <BrandOverlayComposition image={image} brandTokens={brandTokens} ds={ds}>{children}</BrandOverlayComposition>;
    case 'editorial':
      return <SplitLayoutComposition image={image} ds={ds}>{children}</SplitLayoutComposition>;
  }
};

// When fetching article-output for Instagram-post:
function buildInstagramCaption(article, narrativePayload, licenseMetadata) {
  let caption = narrativePayload.caption;
  
  const unsplashImages = licenseMetadata.filter(l => l.provider === 'unsplash');
  if (unsplashImages.length > 0) {
    caption += '\n\n📸 Photos: ' + unsplashImages
      .map(l => `${l.photographer} via Unsplash`)
      .join(', ');
  }
  
  return caption;
}

## 4. End-to-End Render Flow

```
1. brief approved → article-output worker triggered
2. createRecurringContentArticle (idempotent)
3. Template's generateContent():
   a. extractHookContext (from brief.recurring_metadata)
   b. loadToolsWithBrandAssets
   c. 1 LLM-call full narrative (Sonnet)
   d. For each image-needing-slide (per §3.7 Option γ):
      i.   Haiku query-keywords-call (3 queries)
      ii.  Parallel-search Pexels + Unsplash + Pixabay (3 × 3 = ~30-50 candidates)
      iii. Sonnet vision-LLM picks best
      iv.  stageImageToR2 (or use cached if exists)
   e. Store license-metadata in article.domain_extras.familyBImages
4. Render carousel via Remotion (existing 65.10 flow)
5. R2-upload slide-PNGs (existing)
6. article.status = 'published'
```

| Cost-Source | Amount |
|---|---|

| Provider-API calls | €0.00 (free tiers) |
| R2 image stage (4 images × ~150KB) | ~€0.001 |
| R2 slide-PNG output (existing 65.10) | covered |

## 10. Risk Analysis

| Risk | Severity | Mitigation |
|---|---|---|
| LLM-narrative hallucination corrupts entire carousel (1-call) | High | Zod refinement + deterministic fallback |
| Provider-API down (Pexels/Unsplash/Pixabay) | Medium | Parallel-search: if 1 down, others still return candidates |
| All 3 providers return 0 results for niche query | High | Fallback: drop-image-slide to gradient-only via Option β graceful-degradation |
| Vision-LLM picks low-quality image (LLM-blindspot) | Medium | Curate test-cases; if quality-issues surface, add quality-rules in pick-prompt |
| License-attribution miss (legal-risk for Unsplash) | High | License-tracker storage mandatory; caption-attribution test-coverage |
| Render-time exceeds 120s Engine timeout | Medium | Parallel image-pipeline; if approaches 100s, drop-image-slides as graceful-degradation |
| R2-storage bills if image-cache grows unbounded | Low | ~€0.70/year at V1 scale; revisit at 100× volume |
| Provider rate-limit-hit during burst (e.g. backfill 50 articles) | Medium | Shared Redis-counter (V1.5); for V1, batch-jobs sequential not parallel |
| Photographic-quality looks "stock-photo-AI-generic" | High | Multi-provider + LLM-curation reduces this; Marcel-feedback drives prompt-tuning |
| Vision-LLM costs spike (Sonnet × N images × N renders) | Medium | Caching minimizes re-render costs; budget-monitoring per project |
| Image-license-changes after caching (Unsplash photographer requests removal) | Low | V1.5: license-revalidation cron; V1 cached-image stays until manual purge |
| Cross-template visual-language drift | Medium | Shared deriveEmotionalDsTokens + SlideComposition enforces |
| Family B "AI-generic" feel despite photographic-bg | Medium | Hook-driven content + curated images is best-anti-generic-defense; iterate based on Marcel feedback |
