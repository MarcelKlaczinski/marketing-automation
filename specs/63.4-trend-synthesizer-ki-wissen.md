# Spec 63.4 — Trend-Synthesizer ki_wissen Support

_Theme 63 Sub-Spec — Trend-Synthesizer erzeugt ki-wissen-fähige Briefs. Plus Cron-Aktivierung._
_Status: Draft._
_Voraussetzung: 63.6 gemerged (Brief-Plan-Workflow steht), Discovery 2026-05-21._

---

## 1. Problem

Trend-Synthesizer produziert **strukturell keine ki_wissen-fähigen Briefs:**

1. LLM-Prompt erlaubt `intent_type: tutorial|use_case|news|review|comparison|best_practices|...` — NICHT `knowledge`
2. `emit-brief.ts` setzt `cluster_action = matched ? 'append_to_existing' : 'create_new'` — NIE `'standalone'`
3. `matchBriefToContentType` routet zu ki_wissen NUR bei `cluster_action='standalone' AND intentType IN ('knowledge','tutorial')`
4. Cron `registerTrendSynthesizerCron()` ist auskommentiert in `apps/api/src/workers/index.ts:307`

**Konsequenz:** Kein Trend-Brief wird je zu ki_wissen-Item. Marcel sieht ki_wissen-Bucket im Plan immer leer (außer Overage von HN/GitHub).

## 2. Ziel

Trend-Synthesizer kann ki-wissen-fähige Briefs produzieren. Plus optional Cron-Aktivierung.

**In Scope:**
- LLM-Prompt erweitern um `intent_type='knowledge'`
- emit-brief.ts erlaubt `cluster_action='standalone'` für knowledge-Briefs
- Hub-Spoke-Strategie: wenn Cluster-Match (gegen ki-wissen/grundlagen-ki Hub-Embeddings) → append_to_existing, sonst standalone
- Cron-Toggle in SettingsPlannerPage analog 62.7 + 63.3b
- Klare ki-wissen vs tutorial Definition im Prompt

**Out of Scope:**
- Neue Cluster für ki-wissen aufbauen — Bestand reicht (ki-wissen, grundlagen-ki, evtl. mehr)
- Knowledge-Brief Quality-Eval (Marcel reviewt via 63.6 plan_pending Workflow)
- Cluster-Matching-Algorithmus erweitern (existing match-cluster.ts wiederverwenden)

**Aufwand:** 0.5-1 Tag.

## 3. Architektur-Entscheidungen

### 3.1 ki-wissen vs Tutorial — die Trennung

**ki-wissen** = themen-zentriert, nicht-tool-spezifisch:
- Concept-Erklärungen: "Was ist RAG?", "Wie funktionieren neuronale Netze?"
- Patterns/Konzepte: "8 Prompt-Engineering-Patterns", "Bias-Typen in der KI"
- Trends: "Sechs KI-Trends 2026"
- Praktiker-Leitfäden: "Bias-Tests mit Fairlearn"
- Regulatorik: "Was bedeutet der EU-AI-Act für mich?"

**Tutorial** = tool-zentriert, workflow-spezifisch:
- "Wie nutze ich Claude für Präsentationen?"
- "ChatGPT in meinen Workflow integrieren"
- "Prompts für Cursor schreiben"

**Trennung im Prompt:** LLM bekommt 3-4 Beispiele pro Kategorie. Definition explizit: ki-wissen = themen-zentriert ohne Tool-Fokus, Tutorial = tool-zentriert + Schritt-für-Schritt.

### 3.2 cluster_action-Strategie für knowledge-Briefs

```
matchBriefAgainstClusters(brief) → existing matched_cluster | null

if matched && matched.collection_type IN ('ki-wissen', 'grundlagen-ki'):
  brief.cluster_action = 'append_to_existing'   // Spoke unter ki-wissen-Hub
  brief.parent_cluster_id = matched.id
elif matched && matched.collection_type IN ('tools', 'comparisons'):
  // Sollte für knowledge NICHT passieren — wenn doch, fallback:
  brief.cluster_action = 'standalone'           // ki-wissen-Artikel ohne Cluster
else (no match):
  brief.cluster_action = 'standalone'           // neuer eigenständiger ki-wissen-Artikel
```

**Hub-Spoke-Pattern:** Wenn ein knowledge-Brief inhaltlich zu existing ki-wissen Hub passt (z.B. neuer Aspekt zu "Bias und Fairness" Cluster) → Spoke. Wenn völlig neues Thema → standalone Hub für zukünftige Spokes.

### 3.3 matchBriefToContentType Update

Aktuelle Routing-Logic (vermutet aus Discovery):

```ts
if (clusterAction === 'standalone' && intentType IN ('knowledge', 'tutorial')) {
  return 'ki_wissen';
}
```

**Problem:** standalone Tutorial-Brief würde auch zu ki_wissen routen. Das ist falsch — Tutorial sollte nicht in ki-wissen-Collection landen.

**Neu:**
```ts
// knowledge-intent → immer ki_wissen (egal cluster_action)
if (intentType === 'knowledge') {
  return 'ki_wissen';
}

// tutorial-intent + standalone → ki_wissen (für tool-agnostische Tutorials)
// tutorial-intent + cluster → blog/article (tool-spezifisches Tutorial unter Tool-Cluster)
if (intentType === 'tutorial' && clusterAction === 'standalone') {
  return 'ki_wissen';
}

// rest of routing rules...
```

**Edge Case:** standalone Tutorial ohne Tool-Cluster ist legitim ki-wissen-Material ("Wie schreibt man gute Prompts?" ist Tutorial-Format aber themen-zentriert).

### 3.4 Cron-Toggle (analog 62.7 + 63.3b)

Pattern wiederverwenden:
- `cron_job_type` Enum-Erweiterung um `trend_synthesizer`
- Migration für Enum-Widening (eigene Migration, Memory D124)
- Migration für Seed in cron_state
- project_planner_config Erweiterung um `trend_synth_cron_*` Felder
- SettingsPlannerPage Section mit Toggle + dayOfWeek + hourUTC

**Cron-Default:** OFF. Marcel toggelt bewusst an.

**Empfohlene Cadence im Settings-Hint:** Daily 01:30 UTC. Begründung:
- Trend-Synthesizer arbeitet auf Signals die täglich frisch reinkommen (HN, ProductHunt, Vendor-RSS)
- Wenn Signals stale werden, verlieren sie Relevanz
- Daily ist die natürliche Cadence für news-driven content

**Aber:** Cost-Caveat im Hint: "Trend-Synthesizer macht LLM-Calls pro Signal-Gruppe (~€0.05-0.15 pro Run). Daily ~€2-5/Monat, Weekly ~€0.50-1/Monat. Bei kleinem Signal-Volumen reicht Weekly."

## 5. Backend — Implementation

### 5.1 LLM-Prompt erweitern

`packages/pipelines/src/topic-sources/trend-discovery/synthesize-brief.ts` (oder wo der Prompt lebt — Phase 0 findet):

```ts
const SYSTEM_PROMPT = `
Du analysierst eine Gruppe verwandter Signale (HackerNews-Posts, ProductHunt-Launches,
Vendor-Blog-Posts, Reddit-Diskussionen) und erstellst einen Topic-Brief für einen
Content-Artikel.

**intent_type** muss eines der folgenden sein:

- **knowledge** — Themen-zentrierter Wissens-Artikel ohne Tool-Fokus:
  - Concept-Erklärungen: "Was ist RAG?", "Wie funktionieren Reasoning-Modelle?"
  - Patterns/Konzepte: "Sechs Bias-Typen in der KI", "Vier Agent-Architekturen"
  - Trends: "Drei KI-Entwicklungen, die 2026 produktiv werden"
  - Praktiker-Leitfäden: "Bias-Tests in der ML-Pipeline", "RAG-Architekturen vergleichen"
  - Regulatorik: "EU-AI-Act für Hochrisiko-Systeme"
  
  Knowledge-Artikel beantworten "Was ist X?", "Wie funktioniert X?", "Welche Arten von X?"

- **tutorial** — Tool-zentrierte Schritt-Anleitung:
  - "Wie nutze ich Claude für Präsentationen?"
  - "ChatGPT-API in TypeScript-Projekt integrieren"
  - "Cursor Composer für Refactoring nutzen"
  
  Tutorial-Artikel beantworten "Wie nutze ich Tool X für Use-Case Y?"

- **comparison** — Tool-Pair-Vergleich (wird über comparison_discovery erzeugt, hier selten)

- **news** — Aktuelle Releases/Ankündigungen: "Anthropic released Claude 4.7"

- **review** — Konkrete Tool-Bewertung mit Pro/Contra

- **use_case** — Branchen-/Persona-spezifischer Anwendungsfall: "KI für Anwaltskanzleien"

- **best_practices** — Tipps/Empfehlungen für etablierte Praxis

**Wichtige Trennung:**
- knowledge vs tutorial: knowledge ist themen-zentriert ohne Tool-Fokus, tutorial ist tool-zentriert
- knowledge vs news: news beschreibt aktuelles Event, knowledge erklärt Konzept (kann auch zeitlos sein)
- tutorial vs use_case: tutorial ist Schritt-Anleitung, use_case beschreibt Anwendung in Kontext

Gib deinen Output als JSON zurück:
{
  "topic_title": "...",
  "suggested_title": "...",
  "intent_type": "knowledge" | "tutorial" | "comparison" | "news" | "review" | "use_case" | "best_practices",
  "rationale": "kurze Erklärung warum dieses intent_type",
  ...
}
`;
```

**Test-Beispiele für Few-Shot oder Prompt-Description:**

```
Signal-Gruppe 1: "Claude 4.7 released with new tool use" + "Anthropic blog: Tool use improvements"
→ intent_type: "news"

Signal-Gruppe 2: "Reasoning models compute scaling" + "OpenAI o3 benchmarks" + "DeepMind paper on test-time compute"
→ intent_type: "knowledge" (Konzept-Erklärung über Reasoning-Modelle als Klasse)

Signal-Gruppe 3: "How to use Claude Code for refactoring" + "Cursor vs Claude Code"
→ intent_type: "tutorial" (Tool-konkret) ODER "comparison" (wenn LLM Tool-Pair erkennt)
```

### 5.2 emit-brief.ts erweitern

```ts
// Aktuell:
const clusterAction = matched ? 'append_to_existing' : 'create_new';

// Neu:
let clusterAction: ClusterAction;
let parentClusterId: string | null = null;

if (matched && KNOWLEDGE_INTENT_TYPES.includes(intentType)) {
  // Knowledge-Briefs: bevorzugt Hub-Spoke wenn ki-wissen Cluster, sonst standalone
  if (matched.collectionType === 'ki-wissen' || matched.collectionType === 'grundlagen-ki') {
    clusterAction = 'append_to_existing';
    parentClusterId = matched.id;
  } else {
    // Match aber falsches Cluster-Type → standalone für sauberes Routing
    clusterAction = 'standalone';
  }
} else if (intentType === 'knowledge') {
  // Knowledge ohne Match → standalone
  clusterAction = 'standalone';
} else {
  // Bestehende Logik für tutorial/news/comparison/etc.
  clusterAction = matched ? 'append_to_existing' : 'create_new';
  parentClusterId = matched?.id ?? null;
}
```

**KNOWLEDGE_INTENT_TYPES = ['knowledge', 'tutorial']** — für die Pattern-Konsistenz. Tutorial-Briefs sollten auch von Hub-Spoke profitieren wenn ein Tutorial-Cluster existiert.

**Aber Vorsicht:** Tutorial + Tools-Cluster sollte `append_to_existing` ergeben (Tool-Tutorial als Spoke unter Tool-Cluster). Knowledge + Tools-Cluster ist semantisch unsauber → standalone.

### 5.3 matchBriefToContentType Update

`packages/pipelines/src/planning/steps/select-floor-items.ts`:

```ts
function matchBriefToContentType(brief: TopicBrief): ContentType {
  // Comparison via source / cluster_action / typed metadata (existing 63.3b)
  if (
    brief.source === 'comparison_discovery'
    || brief.clusterAction === 'comparison'
    || (brief.intentType === 'comparison' && hasComparisonToolSlugs(brief))
  ) {
    return 'comparison';
  }
  
  // NEU: knowledge → immer ki_wissen
  if (brief.intentType === 'knowledge') {
    return 'ki_wissen';
  }
  
  // NEU: standalone tutorial → ki_wissen
  // (tool-spezifisches tutorial mit Cluster geht weiter zu blog/article)
  if (brief.intentType === 'tutorial' && brief.clusterAction === 'standalone') {
    return 'ki_wissen';
  }
  
  // existing rules für blog/article/cluster
  return 'cluster';  // default
}
```

### 5.4 Cron-Worker

`apps/api/src/workers/trend-synthesizer.worker.ts` (analog 63.3b ComparisonDiscovery-Worker):

```ts
export const trendSynthesizerQueue = new Queue<{ projectId: string }>('trend-synthesizer', {
  connection: getRedisConnection(),
});

export const trendSynthesizerWorker = new Worker(
  'trend-synthesizer',
  async (job) => {
    const { projectId } = job.data;
    return await runTrendSynthesizer({ projectId });
  },
  { connection: getRedisConnection(), concurrency: 1 },
);

export async function seedTrendSynthesizerCron() {
  // Per-project seed via cron_state
  await db.execute(sql`
    INSERT INTO cron_state (project_id, job_type, cron_pattern, is_active, created_at, updated_at)
    SELECT p.id, 'trend_synthesizer', '30 1 * * *', false, NOW(), NOW()
    FROM projects p
    ON CONFLICT (project_id, job_type) DO NOTHING
  `);
}
```

## 8. Risiken

| Risiko | Mitigation |
|---|---|
| LLM erkennt knowledge vs tutorial unsicher | 3-4 Few-Shot-Beispiele im Prompt. Marcel reviewt pending Briefs vor approve, kann false positives discardden. |
| Knowledge-Brief matched fälschlich zu Tools-Cluster | `if matched.collectionType IN ('ki-wissen','grundlagen-ki') → spoke, else → standalone` — Schutz im emit-brief. |
| Bestehende non-knowledge Trend-Briefs werden nach Prompt-Update anders kategorisiert | Phase 0 erst Sample existing Brief-Outputs. Falls Risiko: A/B-Test mit alten vs neuen Prompts. |
| Cron läuft täglich, generiert zu viele Briefs | Pending-Default + Marcel reviewt. Plus Settings-Toggle daily/weekly/off. |
| Tutorial mit cluster wird falsch zu cluster-Bucket statt blog/article geroutet | matchBriefToContentType-Order: comparison rules first, then knowledge, then existing rules. Phase 0 verifiziert bestehende cluster vs blog/article Trennung. |
| Cluster-Embedding-Match findet falsche ki-wissen-Hubs (semantisch ähnlich aber unpassend) | Reuse existing match-cluster.ts (battle-tested via 54.x specs). Plus standalone-Fallback wenn unklar. |
| Knowledge-Briefs bekommen primary_keyword aus Trend-Signal das Tool-spezifisch ist | LLM-Prompt erweitern: für knowledge soll primary_keyword themen-zentriert sein (z.B. "RAG", "Bias in KI"), nicht tool-spezifisch ("Claude RAG"). |
