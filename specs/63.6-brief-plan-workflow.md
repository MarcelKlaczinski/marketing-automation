# Spec 63.6 — Brief-Approve mit Plan-vs-Immediate Dispatch

_Theme 63 Sub-Spec — trennt Brief-Approve vom direkten Article-Trigger. Default-Pfad geht durch Plan-Workflow (Budget-Gate aktiv). Direct-Generate bleibt als bewusster Override._
_Status: Implemented 2026-05-21._
_Voraussetzung: 62.8 gemerged (Plan-Workflow steht), Diagnose 2026-05-21 (Workflow-Konflikt verstanden)._

---

## 1. Problem

Aktuell macht `POST /api/projects/:slug/briefs/bulk-approve`:

```
pending → routed (sofort) + article-INSERT + pipeline-enqueue
```

Theme 62 hat einen Plan-Layer eingeführt mit Budget-Gate (90%), Scheduling, llmMode-Snapshot. Aber Brief-Approve bypasst diesen Layer komplett. Marcel kann unbeabsichtigt Geld verbrennen wenn er Briefs außerhalb des Plan-Flows approved.

Konkretes Symptom (heute): 7 missing_hub Briefs approved → 7 article:blog Pipelines gestartet → alle failed via Anthropic-400 → in 'routed' Status festgenagelt. Aus Planner-Sicht "weg". Hätte ohne Error €3-14 Spend verursacht ohne Plan-Visibility.

## 2. Ziel

Zwei explizite Dispatch-Modi am bulk-approve Endpoint:

- **`dispatch: 'plan'`** (DEFAULT): Brief flippt zu `plan_pending`, wartet auf Planner-Pickup, kein Article-Insert, kein Pipeline-Enqueue
- **`dispatch: 'immediate'`** (Override): bestehende Mechanik — sofort Article-Insert + Pipeline-Enqueue

**Marcel's UX:**
- Default-Click in BriefsPage → "In nächsten Plan eingeplant"
- Separater "Jetzt generieren"-Button → bestehender Direct-Flow (1-2x pro Monat)

**In Scope:**
- Backend: dispatch-Param, neuer Brief-Status `plan_pending`, Migration
- Backend: Planner-Loader erweitern um plan_pending zu picken
- Backend: alle bestehenden Caller (Single-Approve, autoApproveGaps, ...) auf explizites dispatch umstellen
- Frontend: zweite Button-Variante "Jetzt generieren" in BriefsPage + BriefDetailPage
- Status-Übergang plan_pending → routed beim Plan-Pickup (Planner-Step)

**Out of Scope:**
- Article-Retry-Pfad ändern (existing /articles/:id/retry bleibt)
- Quarantäne erweitern für gescheiterte article-from-brief Runs (separate Spec falls nötig)
- 7 routed Briefs cleanen (Marcel macht via Anthropic-Fix-Retry separat, β-Pfad)

**Aufwand:** 0.5-1 Tag.

## 3. Architektur-Entscheidungen

### 3.1 Brief-Lifecycle erweitert

```
                                    ┌─── (dispatch: immediate) ──┐
                                    │                              │
pending ──(bulk-approve)──┬─────────┘                              ↓
                          │                                     routed ──→ article exists
                          └─── (dispatch: plan, default) ──┐       ↑
                                                            ↓       │
                                                     plan_pending ──┘
                                                            │
                                                            ↓ (planner-step picks up)
                                                       (item created, brief stays plan_pending until plan-execute marks routed)
```

**Wichtig:** `plan_pending → routed` Transition passiert in **2 Stufen**:
1. **Plan-Generation:** SelectFloorItemsStep zieht plan_pending Brief, erstellt planned_item, Brief **bleibt** plan_pending (Marcel kann Plan noch verwerfen + Brief landet zurück im Pool)
2. **Plan-Execute (62.8):** wenn planned_item zu generating wechselt, Brief flippt zu routed

Lebt-noch-im-Pool-Property bewahrt: Briefs bleiben im plan_pending bis tatsächliche Generation startet, kein "stranded" State bei Plan-Cancel.

### 3.2 Status-Enum-Erweiterung

`topic_briefs.approval_status` aktueller Wert-Set (vermutet aus Discovery):
- `pending`
- `routed`
- `dismissed` (vermutet — Phase 0 verifiziert)
- `skipped` (vermutet — Phase 0 verifiziert)

Neu:
- `plan_pending` — Marcel approved, wartet auf Plan-Pickup

Migration via CHECK-Widening (Memory D134: eigene Migration nötig, nicht inline mit anderen ALTER TABLE).

### 3.5 Planner-Loader erweitern

`packages/planner/src/load-topic-briefs.ts`:

```ts
// VORHER:
.where(eq(topicBriefs.approvalStatus, 'pending'))

// NACHHER:
.where(inArray(topicBriefs.approvalStatus, ['pending', 'plan_pending']))
```

**Begründung pending zu behalten:** Trend-Synthesizer-Briefs sind direkt nach Erzeugung im `pending` und können vom Planner gepicked werden (Cold-Start-fähig). plan_pending ist für Marcel-explicitly-approved Briefs.

**Eventuelles Refactor später:** mit 63.4 (Trend-Synthesizer ki_wissen support) kommt vielleicht auch ein neuer Workflow wo Trend-Briefs eine "approval"-Stufe brauchen. Aktuell noch nicht.

### 3.6 Status-Transition beim Plan-Execute

`packages/pipelines/src/planning/steps/execute-item.ts` (oder wo planned_item zu 'generating' flippt — Phase 0 findet exakte Stelle):

```ts
async function markItemGenerating(item, ctx) {
  await markPlannedItemInProgress(item.id);
  
  // NEU: Brief-Status-Update wenn Item auf Brief basiert
  if (item.sourceKind === 'topic_brief' && item.sourceId) {
    await markBriefRoutedFromPlan(item.sourceId, item.id);
  }
}
```

`markBriefRoutedFromPlan` analog `markBriefRouted` aber:
- Filtert WHERE `approval_status = 'plan_pending'` (CAS)
- Setzt routed_article_id NICHT (kein Article existiert noch — wird vom article:blog Pipeline-Run später erzeugt)
- Setzt `routed_via_plan_item_id` als neue Column (oder reused: `routed_from`)

**Wichtig:** plan_pending Brief hat KEINE routed_article_id. Wenn Marcel im UI eines anschaut: "Wartet auf Plan-Pickup" Status, kein Article-Link.

### 3.7 Bestehende Caller migrieren

Phase 0 Discovery zeigt alle Stellen. Vermutete Liste:

| Caller | Aktueller dispatch | Soll-dispatch |
|---|---|---|
| BriefsPage Bulk-Approve | (kein Param) | 'plan' (default) |
| BriefDetailPage Single-Approve | (kein Param) | 'plan' (default) |
| `/suggest?autoApproveGaps=true` (Spec 49c) | (kein Param) | 'plan' (Cron-driven, kein Sofort-Spend) |
| Trend-Brief auto-approval (falls existiert) | (kein Param) | wahrscheinlich 'plan' |

**Strategie:** alle bestehenden Caller passen kein dispatch — kriegen Default 'plan'. Wer Direct-Generate will, muss explizit `dispatch: 'immediate'` setzen.

**Audit-Pfad:** `grep "dispatch.*immediate"` zeigt alle Direct-Generate-Stellen. Aktuell wahrscheinlich nur 1: ein neuer "Jetzt generieren"-Button in UI.

### 5.2 Brief-Service-Branch

`apps/api/src/lib/brief-service.ts`:

```ts
export type Dispatch = 'plan' | 'immediate';

export async function approveBriefs({
  projectId,
  briefIds,
  dispatch = 'plan',
}: {
  projectId: string;
  briefIds: string[];
  dispatch?: Dispatch;
}) {
  // CAS-WHERE pending only (idempotent)
  const briefs = await db.query.topicBriefs.findMany({
    where: and(
      eq(topicBriefs.projectId, projectId),
      inArray(topicBriefs.id, briefIds),
      eq(topicBriefs.approvalStatus, 'pending'),
    ),
  });
  
  if (briefs.length === 0) {
    return { processed: [], skipped: briefIds };
  }
  
  if (dispatch === 'plan') {
    return await markBriefsPlanPending(briefs);
  } else {
    return await approveBriefsAndEnqueue(briefs);  // existing
  }
}

async function markBriefsPlanPending(briefs: TopicBrief[]) {
  const ids = briefs.map(b => b.id);
  await db
    .update(topicBriefs)
    .set({
      approvalStatus: 'plan_pending',
      approvedAt: new Date(),
    })
    .where(inArray(topicBriefs.id, ids));
  
  return {
    processed: briefs.map(b => ({ id: b.id, kind: 'plan_pending' as const })),
    skipped: [],
  };
}
```

### 5.4 Planner-Loader

`packages/planner/src/load-topic-briefs.ts`:

```ts
export async function loadPendingTopicBriefs(projectId: string) {
  return await db.query.topicBriefs.findMany({
    where: and(
      eq(topicBriefs.projectId, projectId),
      inArray(topicBriefs.approvalStatus, ['pending', 'plan_pending']),
    ),
    orderBy: [
      sql`CASE WHEN approval_status = 'plan_pending' THEN 0 ELSE 1 END`,  // prefer plan_pending
      desc(topicBriefs.createdAt),
    ],
  });
}
```

**ORDER BY:** plan_pending Briefs werden bevorzugt — Marcel hat sie explizit approved, also höhere Priorität.

## 9. Risiken

| Risiko | Mitigation |
|---|---|
| Bestehende Caller setzen kein dispatch → bekommen Default 'plan' → User wundert sich warum direkter Article-Trigger nicht mehr passiert | Phase 3 Discovery findet alle Caller. Vor Merge alle expliziert auf gewünschten dispatch setzen. |
| Plan-Generation pickt plan_pending Brief, aber Marcel verwirft den Plan → Brief im Limbo? | plan_pending Brief bleibt im Pool bis tatsächliche Generation startet. Marcel kann plan-cancel → Briefs sind wieder im Pool. |
| Brief-Status-Transition race mit Plan-Cancel | plan_pending → routed nur via CAS-Update (WHERE status='plan_pending'). Concurrent Cancel kann Status nicht in Vergangenheit ändern. |
| Marcel klickt "Jetzt sofort generieren" ohne Confirm zu lesen → Budget verbrennt | Confirm-Dialog mit "Budget-Gate wird umgangen" Wording. Override hinter zwei Klicks. |
| autoApproveGaps Cron (Spec 49c) generiert weiter sofort, weil noch kein dispatch=plan gesetzt | Phase 3 expliziter Code-Change: autoApproveGaps callt mit dispatch='plan'. Plus Test. |
| Plan-Execute Hook race mit anderen Brief-Updates | CAS-Pattern: Update mit WHERE approval_status='plan_pending'. Lost-update wird im DB-Layer abgefangen. |
| 7 routed Briefs aus dem heutigen Bulk-Approve sind jetzt im Limbo | Marcel cleant via Article-Retry (β-Pfad) wenn Anthropic-Fix kommt. Außerhalb 63.6-Scope. |

## 13. Discovered & Deviations

| # | Discovery | Decision |
|---|---|---|
| 1 | **Actual CHECK values** were `pending, approved, rejected, auto_approved, superseded, routed` — the spec's "vermutet" set (`pending, routed, dismissed, skipped`) was wrong (`dismissed`/`skipped` don't exist; `approved`/`auto_approved`/`rejected`/`superseded` do). | Used the real list verbatim in migration 0082, just added `plan_pending`. |
| 2 | The spec §3.6 located the status-flip in `packages/pipelines/src/planning/steps/execute-item.ts`. That file doesn't exist — the canonical site is `packages/pipelines/src/execution/status-publisher.ts` `transitionItemInProgress`, called from both `execute-plan.ts:291` AND the shared queue worker at `engine/queue.ts:226`. | Extended the publisher (covers both paths in one place) instead of touching each worker. |
