## 3. Architecture Decisions

### 3.1 Form-Strategy Evaluation (Marcel: Discovery evaluiert)

**Option α — Generic Form-Engine (Zod-Schema → Form fields):**

```vue
<ZodForm
  :schema="topNComparisonConfigSchema"
  v-model="formData"
  @submit="handleSubmit"
/>
```

The form-engine introspects the Zod schema and auto-renders:
- `z.string()` → text input
- `z.number().int().min(3).max(10)` → number input with constraints
- `z.enum([...])` → select dropdown
- `z.array(z.string().uuid())` → multi-select (with custom resolver for tool-uuid → tool-name)
- `z.boolean()` → checkbox

Pros:
- Add a new format-type → form auto-renders, zero UI-code
- Schema is single source of truth (validation + rendering)
- Reusable beyond Theme 65 (e.g. BK config-screens later)

Cons:
- Tool-UUID multiselect needs custom-resolver (form-engine can't know "this UUID-array refers to tools")
- Visual-design constraints harder (everything looks "form-engine-generated")
- z.union and conditional-fields complicated
- Build-time work significant (~1d alone)

**Option β — Hardcoded 5 forms (one per format-type):**

```vue
<TopNComparisonForm v-model="formData" />
<HeadToHeadForm v-model="formData" />
<StoryArcClickbaitForm v-model="formData" />
<LifestyleListicleForm v-model="formData" />
<OpinionRecommendationForm v-model="formData" />
```

Plus a switch-case dispatcher in CreateDefinitionWizard.

Pros:
- Each form can have ideal UX (visual tool-picker for top_n_comparison, profession-pool-tagger for story_arc, etc.)
- No form-engine build-time
- Easy V1.5 enhancements per format-type without engine-refactor

Cons:
- 5 forms is 5x boilerplate
- Adding format-type V2 requires UI-work (no auto-render)
- Risk of validation-drift (schema in 65.4, form-rules in 65.11)

**Option γ — Hybrid: Form-engine for primitive fields + custom-slots:**

```vue
<DefinitionForm :format-type="formatType">
  <template #custom-fields>
    <!-- Per-format-type custom controls -->
    <TopNComparisonCustomFields v-if="formatType === 'top_n_comparison'" />
    <HeadToHeadCustomFields v-else-if="formatType === 'head_to_head'" />
    <!-- etc -->
  </template>
</DefinitionForm>
```

Form-engine handles common fields (name, frequency, output_targets), custom-slots handle format-specific.

Pros:
- Reduces boilerplate by ~60%
- Custom slots for the parts that need bespoke UX
- Schema-driven validation, custom-rendering where it matters

Cons:
- More complex than either α or β
- "Custom-slot" definition fuzzy — what's "common" vs "custom"?

### Discovery-Recommendation: **Option γ (Hybrid)**

Reasoning:

1. **Form-engine is overkill for 5 format-types V1** — boilerplate-cost of α exceeds savings
2. **Hardcoded β has worst-of-both** — boilerplate AND validation-drift risk
3. **Hybrid captures common patterns** — `name`, `frequency`, `output_targets`, `template_selection_strategy`, `end_slide_strategy` are SHARED across all 5 format-types. Custom-slot only for `format_config` (the per-type Zod-validated jsonb)
4. **Tool-UUID multiselect + visual-cards are bespoke per-format anyway** — Option α would need custom-resolvers, so we'd build hybrid-ish anyway

### 3.2 Wizard Flow (Marcel-Decision: 4 steps)

**Step 1: Pick Format-Type (Visual Cards)**

```vue
<template>
  <div class="row q-col-gutter-md">
    <FormatTypeCard
      v-for="formatType in formatTypes"
      :key="formatType.key"
      :format-type="formatType"
      :selected="selectedFormatType === formatType.key"
      @click="selectedFormatType = formatType.key"
    />
  </div>
</template>
```

Each card shows:
- Format name (e.g. "Top N Comparison")
- Family badge (A — Data-driven / B — Hook-driven)
- 2-3 example carousel-preview thumbnails (static images cached from sample-renders)
- Brief description (1 sentence)

**Step 2: Configure**

- Common fields top: `name` (text), `frequency` (select: weekly/biweekly/monthly/custom)
- Custom slot: format-specific configForm renders below
- Live-validation per Zod-schema (debounced on-change)

**Step 3: Schedule**

- `next_run_at` (datetime picker, default = NOW())
- `output_targets` (checkboxes: article + social, social default-on)
- `template_selection_strategy` (select: lru | fixed | llm-picks — default lru)
- `fixed_template_key` (only shown if strategy=fixed; dropdown of `formatType.eligibleTemplates`)
- `end_slide_strategy` (select: rotation | default — default rotation)
- `end_slide_pool` (multi-select of `end_slide_definitions` filtered by format-type's `defaultEndSlides`)

**Step 4: Review & Create**

- Summary cards für alle config-values
- "Test mit Dry-Run" button (calls dry-run endpoint, shows generated brief without persisting)
- "Erstellen" submit button → POST /definitions

### 3.4 Definition-Actions (Marcel-Decision: All 3)

**Toggle (is_active):**

Simple PATCH endpoint. Inactive definitions: greyed in list, cron skips them.

**Run-Now:**

```typescript
// POST /api/projects/:slug/recurring-content/definitions/:id/run-now
export async function runDefinitionNow(req, res) {
  const { id } = req.params;
  const definition = await getRecurringDefinition(id);
  
  // Enqueue immediate brief-generation job (skip schedule)
  await enqueueRecurringBriefJob({
    definitionId: id,
    projectId: definition.projectId,
    forceImmediate: true,  // skips next_run_at check
  });
  
  return res.json({ status: 'enqueued', jobId: '...' });
}
```

**Worker-side**: extend job-data with `forceImmediate?: boolean`. When true, worker doesn't update `next_run_at` (since this is an out-of-band run). Verify-point §2.4 #7.

**Dry-Run:**

```typescript
// POST /api/projects/:slug/recurring-content/definitions/:id/dry-run
export async function dryRunDefinition(req, res) {
  const { id } = req.params;
  const definition = await getRecurringDefinition(id);
  
  // Invoke brief-generator with dryRun=true (skips persist + log + next-run-update)
  const result = await generateBriefForRecurringDefinition({
    definition,
    projectId: definition.projectId,
    dryRun: true,
  });
  
  return res.json({
    preview: result.briefPreview,  // not persisted to topic_briefs
    selectedTemplate: result.selectedTemplate,
    selectedEndSlide: result.selectedEndSlide,
    selectedHook: result.selectedHook,
    estimatedCost: result.llmCost,
  });
}
```

**Worker/Generator-side:** Extend `generateBriefForRecurringDefinition` and all 5 brief-generators with `dryRun: boolean` parameter. When true:
- LLM-calls happen normally
- Tool-picks happen normally
- Template + end-slide selection happen normally
- **Skip:** persist-brief, log-template-usage, mark-definition-run

Return the `briefPreview` so UI can show generated content.

**Cost:** Dry-run costs same as real run (LLM-calls are real). Show estimated-cost to Marcel before dry-run-button. Maybe: limit dry-runs to N per day per project (env-var).

### Discovered & Carry-overs

- **Hardcoded `q-stepper` ban (root CLAUDE.md DO-NOT) wasn't in the spec's Architecture Decisions §3.2.** Spec proposed `<q-stepper v-model="step" header-nav animated>`; implementor reads root CLAUDE.md FIRST and falls back to the InstallerLayout pattern OR a single-page modal. Documented as V1.5 deviation §1.
- **`q-calendar` install state assumption** — root CLAUDE.md's tech-stack list doesn't mention `@quasar/quasar-ui-qcalendar`; Marcel-Decision §0 Q7 ("Monday week-start") implied it'd be installed. Verified absence in `apps/web/package.json` during Phase 0. Documented as V1.5 deviation §3.
- **No `topic-briefs-read.ts` helper existed** — the worker uses inline `db.select()` for `computeNextRunNumber` / `loadPreviousRunToolIds`. The new helper is the first DB-layer abstraction for `topic_briefs` reads (consistent with the rest of `packages/db/src/helpers/` per-entity convention).
- **`$q.notify({ dark: true })` rejected by Quasar types** — only `$q.dialog()` accepts the `dark` prop. The notify caller falls back to the global dark theme via `quasar.config.ts` `Dark: true`. Caught during the first web typecheck pass.
- **`data()` can't call `this.<method>`** — root CLAUDE.md DO-NOT. The `defaultConfigForType` helper was inline in components first, then extracted to module-level (`defaultConfigForFormatType`, `defaultConfigForEndSlideType`) when typecheck flagged TS2722.
- **`@marketing-auto/social/end-slide-components` barrel re-exports `.tsx` files** — apps/api typecheck rejects the import even when only types are pulled (`--jsx` not set). New subpath `@marketing-auto/social/end-slide-components/types` exposes `END_SLIDE_TYPES + END_SLIDE_CONFIG_SCHEMAS + EndSlideType` only. Added the matching `paths` mapping in apps/api/tsconfig.json — same pattern as `@marketing-auto/social/templates/overrides`.
- **Format-type config Zod validators** — `validateFormatConfig` from `@marketing-auto/shared/format-types` is permissive on unknown types but strict on the 5 registered ones. The route's 422 surfaces the Zod `error.message` verbatim — UI shows it as caption on the negative Quasar notify.
- **`forceImmediate` is worker-level**, not generator-level — generators don't know about the run-now flag; the worker decides whether to advance `next_run_at` after dispatch returns. Dry-run is generator-level because it requires changing the persist-vs-preview branch inside each generator.
