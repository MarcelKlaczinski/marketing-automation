## 1. Problem

Discovery 2026-05-23 hat einen **latenten Carry-Over-Bug** aus Spec 63.6 identifiziert: der `cluster_assignment_required` 409-Gate aus dem Pre-63.6 immediate-only Pfad wurde verbatim ins Plan-Dispatch-Modell kopiert, ohne die geänderte Routing-Architektur zu berücksichtigen.

**Symptom (Marcel-erlebt 2026-05-23):**
- Brief vom Trend-Synthesizer (`source='trend_discovery'`) mit `cluster_action='create_new'`
- Click "Genehmigen & Warteschlange" in `TrendDetailPage.vue`
- API gibt 409 mit `error: "cluster_assignment_required"`
- UI zeigt Notice-Banner mit Cluster-Creator-Link
- **Erwartung:** Planner kann `create_new` nativ via `cluster:full-plan` inline erstellen (Spec 64.1 Design-by-Choice)

**Schaden:** 0. Brief bleibt `status='pending'`. Kein DB-Cleanup nötig.

### Root Cause

Discovery hat zwei betroffene Endpoints identifiziert:

**1. `apps/api/src/routes/trends.ts:221-236`** — legacy single-brief approve

```ts
// PRE-63.6 era (immediate-only):
if (brief.clusterAction === "create_new" || !brief.clusterId) {
  return c.json({ ok: false, error: "cluster_assignment_required", ... }, 409);
}
```

Pre-63.6 war immediate-only der einzige Pfad → Gate war korrekt. Spec 63.6 hat trends.ts **gar nicht angefasst**.

**2. `apps/api/src/lib/brief-service.ts:68-73`** — Spec 63.6 dispatch refactor

```ts
// Plan-Dispatch-Branch:
if (dispatch === "plan") {
  if (brief.clusterAction === "create_new" || !brief.clusterId) {
    return { kind: "cluster_assignment_required" };  // ← copy-paste aus immediate-Pfad
  }
  return await markBriefPlanPending(briefId, project.id);
}
```

Hier hat Spec 63.6 (commit f22269a) den Gate **verbatim kopiert** statt path-aware zu prüfen. **Plan-Dispatch braucht den Gate nicht für `create_new`** weil:
- Planner picked Brief via `loadPendingTopicBriefs`
- `matchBriefToContentType(brief)` → `"cluster"` (Spec 64.1 routing)
- `pipeline-router.ts:87-120` case `"cluster"` + `clusterAction === "create_new"` → `cluster:full-plan` inline
- Planner-LLM erstellt cluster + spokes selbst

### Discrepancy Spec 64.1 Documentation vs Implementation

Aus Spec 64.1 CLAUDE.md (Memory D147+D148):
> "keeps `create_new` (€4.20 cluster:full-plan)"

Plus Memory D148:
> "content_type Checklist: 11 sync-points die alle synchron sein müssen"

Spec 64.1 hat das Routing dokumentiert aber **die UI-/Approve-Surface NICHT mit-migriert**. Der validation gate ist eine "12. sync-point" die Memory D148 nicht aufgezählt hat.

### 3.1 brief-service.ts — Path-aware Gate (Fix B)

**File:** `apps/api/src/lib/brief-service.ts`

**Current (Buggy):**

```ts

  briefId: string,
  project: Project,
  dispatch: "plan" | "immediate",
): Promise<ApproveBriefResult> {

  if (!brief) return { kind: "not_found" };

    return { kind: "cluster_assignment_required" };

  }
  
  // immediate dispatch
  return await executeDecision(brief, project);
}
```

**Nachher (Path-Aware):**

```ts
export async function approveBrief(
  briefId: string,
  project: Project,
  dispatch: "plan" | "immediate",
): Promise<ApproveBriefResult> {
  const brief = await getBriefById(briefId);
  if (!brief) return { kind: "not_found" };
  
  if (dispatch === "plan") {
    // Plan-Dispatch: Planner regelt create_new via cluster:full-plan inline.
    // Nur append_to_existing OHNE clusterId ist editorial gap.
    if (brief.clusterAction === "append_to_existing" && !brief.clusterId) {
      return { kind: "cluster_assignment_required" };
    }
    return await markBriefPlanPending(briefId, project.id);
  }
  
  // immediate dispatch braucht clusterId für direct execution
  if (brief.clusterAction === "create_new" || !brief.clusterId) {
    return { kind: "cluster_assignment_required" };
  }
  
  return await executeDecision(brief, project);
}
```

**Decision-Rationale:**
- Plan-Dispatch erlaubt `create_new` (Planner-auto-route)
- Plan-Dispatch erlaubt `append_to_existing` MIT clusterId (Spoke-membership)
- Plan-Dispatch blockt `append_to_existing` OHNE clusterId (editorial gap — Marcel muss cluster wählen)
- Immediate-Dispatch behält strenge Validation (direct pipeline braucht clusterId)

**Nachher (Thin Wrapper):**

```ts
app.post("/projects/:slug/trends/briefs/:briefId/approve", async (c) => {
  const { slug, briefId } = c.req.param();
  const { mode } = await c.req.json();
  
  const project = await getProjectBySlug(slug);
  if (!project) return c.json({ ok: false, error: "project_not_found" }, 404);
  
  const dispatch = mode === "queue" ? "plan" : "immediate";
  const result = await approveBrief(briefId, project, dispatch);
  
  switch (result.kind) {
    case "not_found":
      return c.json({ ok: false, error: "brief_not_found" }, 404);
    case "cluster_assignment_required":
      return c.json({
        ok: false,
        error: "cluster_assignment_required",
        next_action: { url: `/projects/${slug}/clusters/new?fromBrief=${briefId}` },
      }, 409);
    case "plan_pending":
      return c.json({ ok: true, status: "plan_pending", briefId });
    case "executed":
      return c.json({ ok: true, status: "executed", pipelineRunId: result.pipelineRunId });
    default:
      const _exhaustive: never = result;
      return c.json({ ok: false, error: "unexpected_result" }, 500);
  }
});
```

**Decision:** Endpoint bleibt erhalten als Single-Brief-Convenience-API (Marcel UX). Aber Logic ist DRY mit bulk-approve.
