# Discovery 64.8 — Image-Prompt Quality Audit (Results)

**Date:** 2026-05-22  **Mode:** read-only (no code changes)  **Cost:** ~€0.12 (one live Gemini Pro 1K probe).

## TL;DR — Order of Operations

> ⚠️ **Spec 64.8 cannot ship as a Post-Draft Refactor until the underlying adapter is fixed.**
> Live verify proved the Nano Banana 2 / Pro adapter is **broken in production**: every call returns HTTP 400. The current `responseFormat.image.{aspectRatio,imageSize}` request shape does not exist in the real Gemini API. Until this is fixed, refactoring the prompt-generation flow is dressing up a corpse — every new prompt would graceful-skip into an empty hero.

Recommended sequence:

1. **Pre-64.8a (urgent, ~1 day):** fix `model-inputs.ts` to the minimal shape proven live; storage extension JPEG vs WebP follow-up.
2. **Re-bake 3-5 fresh samples** on the fixed adapter + post-64.6 outline.ts ("no text labels" rule). Spec 64.8 architecture decision hinges on whether the new samples still show pseudo-script / brand-mismatch.
3. **Then** decide Post-Draft Refactor scope based on the fresh samples.

## Section 1 — Quality Audit (5 sample images)

**Important context:** Toolwiki's `articles` table was re-imported via Astro-sync after Spec 64.6 deployed. Side-effects:

- All 272 articles are now `source='imported'`; `articles.outline = NULL` for every row.

## Section 4 — Live Gemini API Verify (CRITICAL — adapter broken)

**Step 7a — Key validity (free, models.list):** ✅ Key in vault works. 52 models accessible.

**Step 7b — Available image models (verified live):**
- `models/gemini-3-pro-image-preview` (alias "Nano Banana Pro") — exists, accepts the slug
- `models/nano-banana-pro-preview` — alias for Pro
- `models/gemini-3.1-flash-image-preview` — exists, accepts the slug
- `models/gemini-3-flash-image-preview` — **does not appear in `/v1beta/models` listing** but routes correctly (Gemini accepts the slug; probably an alias not exposed in the public list)
- → Adapter's `MODEL_SLUGS` (`"nano-banana-2" → "gemini-3-flash-image-preview"`) is fine functionally; the slug routes. ⚠️ But may break silently if Google removes the unlisted alias.

**Step 7c — Request shape (probed with three variants):**

```
Adapter's current shape (model-inputs.ts:38-56) — HTTP 400:
{
  contents: [...],
  generationConfig: {
    candidateCount: 1,
    responseModalities: ["TEXT", "IMAGE"],
    responseFormat: { image: { aspectRatio: "16:9", imageSize: "1K" } }  // ← REJECTED
  }
}

Error: Invalid value at 'generation_config.response_format.image.aspect_ratio' (...), "16:9"
       Invalid value at 'generation_config.response_format.image.image_size' (...), "1K"
```

Tested via direct `generateImage()` adapter call against Toolwiki project — fails at every model variant (Flash + Pro, both slug variants). The retry table says 4xx fails fast → no retries → graceful skip at step layer → article lands in `final_review` with empty hero.

**Working minimal shape (HTTP 200, returned an image):**

```json
{
  "contents": [{ "role": "user", "parts": [{ "text": "<prompt>" }] }],
  "generationConfig": {
    "candidateCount": 1,
    "responseModalities": ["TEXT", "IMAGE"]
  }
}
```

- Latency: 16.8 s (Pro 1K, single-image).
- Response: `candidates[0].content.parts[].inlineData.{ mimeType, data }` — base64-encoded.
- `inlineData.mimeType: "image/jpeg"` ← **NOT webp.** Adapter stores under `.webp` extension but bytes are JPEG. Content-type header reads correctly from `inlineData.mimeType` so browsers render OK, but R2 key extension lies. (This was already documented in Spec 64.6b §10 Row 14 as deferred; now confirmed.)
- `usageMetadata.candidatesTokenCount: 1219` (image token billing, 1120 IMAGE + 99 TEXT).
- `outputMimeType` field: **does not exist** in either request or response. The previous Spec-64.6b assumption that Gemini might expose it under a different path is now disproved — there is no API surface for it.

**What this means for aspect-ratio and resolution:**

Aspect-ratio + resolution cannot be set via API config the way the adapter currently tries. The Gemini Image API derives them from the **prompt text alone**. The probe used `"a single red apple on white background"` with no aspect hint and got a square 614 KB JPEG. To get 16:9 + 1K, the prompt must say so explicitly: e.g. `"…studio photography, 16:9 widescreen aspect, high resolution"`.

→ **Spec 64.8 finding #2:** the per-tenant `image_generation_resolution` toggle (Spec 64.6b migration 0089) is currently a no-op on Nano Banana — the resolution is whatever the prompt + model defaults negotiate. Either delete the toggle or move resolution hints into the augment-step (since augment-step has the room to inject `"16:9 widescreen, high-resolution editorial photography"` deterministically without bloating outline.ts).

**Cost verify:**
- Real cost of one Pro 1K image: not exposed in `usageMetadata` (no `costUsd` field — Google bills offline). Cost-tracker estimate `$0.134/€0.123` for Pro 1K is the table rate. Token-based actual billing may diverge; reconcile against Google Cloud Console after first ~50 generations.
