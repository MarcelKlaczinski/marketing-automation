# Spec 57.2 — BullMQ Migration for Remotion Rendering

**Theme:** 57 (Social Media + Remotion Refinement)
**Status:** Draft
**Estimated effort:** 5-7 days

---

## Goal

Move Remotion server-side rendering out of the synchronous pipeline step (`RenderSlidesStep`) into a dedicated BullMQ queue (`social-render`) with its own worker. After this spec, triggering a render returns immediately with a `renderJobId`; the actual rendering happens asynchronously in a separate worker process. UI tracks render state via SSE events. The pipeline worker is freed up after enqueueing — eliminating worker-pool contention when multiple article renders trigger in parallel.

## Non-Goals

- New hosting infrastructure (single Node.js process, BullMQ + Redis already in place)
- Pipeline behavior changes other than `RenderSlidesStep` (other steps unchanged)
- Container/process isolation for Chromium (out of scope — `concurrency: 1` in worker config provides job-level isolation)
- Render-job priority/scheduling (FIFO is sufficient for current scale)
- Multi-region or distributed worker pools (single-server scope)
- Render job retry/failure UI beyond status display (manual re-trigger via existing UI is acceptable v1)
- Migration of other pipeline steps to BullMQ (deferred to future arch work if needed)

---

## Background

Per Theme 57 inventory + Marcel's confirmation:

- Heute: `RenderSlidesStep` calls `@remotion/bundler` + `renderStill()` synchronously inline, blocking the pipeline worker for ~10-30 seconds per render
- Multiple parallel article renders compete for pipeline-worker slots → contention
- BullMQ infrastructure already exists in the codebase (`pipelines` queue, other queues per inventory)
- Per Spec 57.1, multi-locale rendering multiplies render time (N locales × 10-30s)
- Per Spec 57.3, `social_posts.status` is a **content lifecycle** enum (`draft | in_review | approved | scheduled | published | failed | replaced`) — NOT a render-status field. A separate field is needed for render lifecycle.

This spec migrates the render step to async via BullMQ Mode B: pipeline step returns immediately with a `renderJobId`, worker performs render in background, SSE notifies UI on completion.

---

## Architectural Model

### State Machine: Render Job

```
pending → rendering → rendered
                   ↘ failed
```

- `pending`: job enqueued but not yet picked up by worker (BullMQ "waiting" state)
- `rendering`: worker actively rendering (BullMQ "active" state)
- `rendered`: render complete, slide URLs persisted to social_post
- `failed`: render failed after BullMQ retry exhaustion (no more retries)

### Pipeline Run vs Render Job — Separate Lifecycles

Pre-57.2:
```
Pipeline Run [running] → RenderSlidesStep [10-30s] → Pipeline Run [complete] → SocialPost [ready]
```

Post-57.2:
```
Pipeline Run [running] → RenderSlidesStep [enqueue, ~100ms] → Pipeline Run [complete]
                          ↓
                          BullMQ social-render queue
                          ↓
                          Render Worker [10-30s] → SocialPost [rendered]
```

**Key implication**: pipeline-run completion no longer implies social-post is ready. UI must show two states distinctly:
- "Pipeline complete, render in progress"
- "Pipeline complete, render complete"

### Data Model: social_posts Extension

Add fields to `social_posts`:
- `render_status`: enum (`pending | rendering | rendered | failed`) — separate from existing `status` (content lifecycle)
- `render_job_id`: text (BullMQ job ID, nullable — null after BullMQ cleanup)
- `render_started_at`: timestamp (nullable)
- `render_completed_at`: timestamp (nullable)
- `render_error`: jsonb (nullable — error details on failure)

`status` (content lifecycle) and `render_status` (render lifecycle) are orthogonal. A post can be `render_status: 'rendered'` AND `status: 'draft'` (rendered but not yet reviewed). Filter rules:
- "Posts ready for review" = `render_status: 'rendered' AND status IN ('draft', 'in_review')`
- "Posts published" = `status: 'published'` (renders must have completed earlier, but `render_status` is not the gate)

```typescript
// packages/db/src/migrations/57_2_social_posts_render_status.ts
export async function up(db: DrizzleDB) {
  await db.execute(sql`
    -- Render status enum
    CREATE TYPE social_render_status AS ENUM ('pending', 'rendering', 'rendered', 'failed');

    -- New columns on social_posts
    ALTER TABLE social_posts
      ADD COLUMN render_status social_render_status NOT NULL DEFAULT 'pending',
      ADD COLUMN render_job_id text,
      ADD COLUMN render_started_at timestamp,
      ADD COLUMN render_completed_at timestamp,
      ADD COLUMN render_error jsonb;

    -- Backfill: existing rows have slides already; mark them rendered
    UPDATE social_posts
    SET render_status = 'rendered',
        render_completed_at = updated_at
    WHERE content->'slides' IS NOT NULL
      AND jsonb_array_length(content->'slides') > 0;

    -- Index for queue/UI queries
    CREATE INDEX social_posts_render_status_idx ON social_posts(render_status)
      WHERE render_status IN ('pending', 'rendering');
  `);
}
```

**Backfill rationale**: Existing posts already have rendered slides (per inventory). Marking them `render_status: 'rendered'` ensures UI shows them correctly and they're not picked up as "pending" by any consistency check.

**Partial index** on (pending, rendering) only: makes "find active renders" queries fast without bloating the index with completed rows.

## Part B: Render Queue + Worker

### B.1 Queue Definition

```typescript
// packages/queue/src/queues/social-render.queue.ts
import { Queue } from "bullmq";
import { redisConnection } from "../redis";

export type SocialRenderJobData = {
  socialPostId: string;        // FK to social_posts row
  projectId: string;
  articleId: string;
  templateKey: TemplateKey;
  locale: string;              // "de-DE" | "en-US"
  brandTokens: BrandTokens;    // serialized snapshot at enqueue time
  overrides: TemplateOverrides; // resolved overrides snapshot
  resolvedTools: ToolData[];   // pre-resolved tool data
  articleTitle: string;
  articleUrl: string;
  cluster?: ClusterContext;
  hook?: HookData;             // pre-generated hook (from upstream step)
};

export type SocialRenderJobResult = {
  socialPostId: string;
  slideUrls: string[];
  totalSlides: number;
};

export const socialRenderQueue = new Queue<SocialRenderJobData, SocialRenderJobResult>(
  "social-render",
  {
    connection: redisConnection,
    defaultJobOptions: {
      attempts: 2,                  // 1 retry — Remotion failures are usually deterministic
      backoff: { type: "fixed", delay: 5000 },
      removeOnComplete: { count: 100 },   // keep last 100 completed jobs for debugging
      removeOnFail: { count: 500 },       // keep more failures for diagnosis
    },
  }
);
```

**`attempts: 2`** — Remotion render failures are typically deterministic (bad template input, missing asset, OOM). Retrying once handles transient failures (Redis blip, Chromium startup race) without infinite retry loops on broken inputs. Per established pattern from Spec 51a Lessons-Learned (`attempts=1` for paid jobs).

**Job data is a complete snapshot**: brand tokens, overrides, resolved tools all serialized into the job payload. Why: when worker picks up job (could be seconds later), no race against DB updates (e.g. brand tokens edited between enqueue and render). Snapshot-at-enqueue is the canonical input.

### B.2 Worker Process

```typescript
// packages/queue/src/workers/social-render.worker.ts
import { Worker } from "bullmq";
import { renderSlidesViaRemotion } from "@marketing-auto/social/renderer";
import { redisConnection } from "../redis";
import { socialRenderQueue, type SocialRenderJobData, type SocialRenderJobResult } from "../queues/social-render.queue";
import { db } from "@marketing-auto/db";
import { socialPosts } from "@marketing-auto/db/schema";
import { eq } from "drizzle-orm";

export function startSocialRenderWorker(logger: Logger) {
  const worker = new Worker<SocialRenderJobData, SocialRenderJobResult>(
    "social-render",
    async (job) => {
      const { socialPostId, ...renderInput } = job.data;

      // Mark as rendering
      await db
        .update(socialPosts)
        .set({
          renderStatus: "rendering",
          renderStartedAt: new Date(),
        })
        .where(eq(socialPosts.id, socialPostId));

      // Emit SSE event
      emitSseEvent({
        type: "social.render.started",
        socialPostId,
        projectId: renderInput.projectId,
        articleId: renderInput.articleId,
      });

      try {
        // Actual render (existing Remotion bundle + renderStill)
        const result = await renderSlidesViaRemotion(renderInput, {
          progressCallback: (progress) => {
            // Optional: emit progress events
            emitSseEvent({
              type: "social.render.progress",
              socialPostId,
              progress: progress.frameCount / progress.totalFrames,
            });
          },
        });

        // Update DB on success
        await db
          .update(socialPosts)
          .set({
            renderStatus: "rendered",
            renderCompletedAt: new Date(),
            content: sql`jsonb_set(content, '{slides}', ${JSON.stringify(result.slideUrls)}::jsonb)`,
          })
          .where(eq(socialPosts.id, socialPostId));

        // Emit completion
        emitSseEvent({
          type: "social.render.completed",
          socialPostId,
          projectId: renderInput.projectId,
          articleId: renderInput.articleId,
          slideCount: result.slideUrls.length,
        });

        return { socialPostId, slideUrls: result.slideUrls, totalSlides: result.slideUrls.length };
      } catch (error) {
        logger.error("Render failed", { socialPostId, error });

        const renderError = {
          code: error.code ?? "RENDER_FAILED",
          message: error.message ?? "Unknown render error",
          stack: error.stack,
          attemptedAt: new Date().toISOString(),
        };

        // If this is the last attempt, persist failure to DB
        // Otherwise, BullMQ will retry — keep DB in 'rendering' state
        if (job.attemptsMade >= (job.opts.attempts ?? 1)) {
          await db
            .update(socialPosts)
            .set({
              renderStatus: "failed",
              renderError,
              renderCompletedAt: new Date(),  // marks end of render lifecycle
            })
            .where(eq(socialPosts.id, socialPostId));

          emitSseEvent({
            type: "social.render.failed",
            socialPostId,
            projectId: renderInput.projectId,
            articleId: renderInput.articleId,
            error: renderError.message,
          });
        }

        throw error;  // re-throw to let BullMQ handle retry vs final-fail
      }
    },
    {
      connection: redisConnection,
      concurrency: 1,  // serialize renders per worker — Chromium memory hygiene
    }
  );

  worker.on("ready", () => logger.info("social-render worker ready"));
  worker.on("error", (err) => logger.error("social-render worker error", { err }));

  return worker;
}
```

**`concurrency: 1`** — critical for memory hygiene. Chromium / Remotion uses substantial memory per render; parallel renders in same Node process risk OOM. If more throughput needed, run multiple worker processes (BullMQ handles distribution across workers natively).

**Snapshot strategy**: worker reads all render inputs from `job.data`, NOT from DB. The only DB writes are status transitions. This isolates render outcome from DB state at enqueue time.

### B.3 Worker Process Lifecycle

Where does this worker run? Per Marcel: single Node.js process. Options:

**Option B.3.a — Same process as API server**
- Worker started during API boot via `startSocialRenderWorker()`
- Pros: simple, no new process to deploy
- Cons: render OOM crashes API process

**Option B.3.b — Separate worker process**
- New entrypoint `apps/worker/src/index.ts` that starts all background workers
- Same codebase, separate process via process manager (PM2, systemd, or `bun run`)
- Pros: render crashes isolated from API
- Cons: needs deploy config update

**Recommendation: B.3.b** for production. Render is the most resource-intensive operation in the system; isolating it from request handling is straightforward and standard. Verify whether `apps/worker` (or equivalent) already exists in the codebase from prior pipeline worker setup — if so, just add the new worker to the existing entrypoint.

**Verification step (Session 1, Task 1)**: check existing worker entrypoint location. Spec implementation follows established pattern.

### B.4 Enqueue Helper

```typescript
// packages/queue/src/queues/social-render.queue.ts
export async function enqueueSocialRenderJob(data: SocialRenderJobData): Promise<string> {
  const job = await socialRenderQueue.add("render", data, {
    jobId: `render-${data.socialPostId}`,  // idempotency: same socialPostId can only have one active render
  });

  // Persist jobId to social_posts immediately for query/SSE-reconciliation
  await db
    .update(socialPosts)
    .set({ renderJobId: job.id, renderStatus: "pending" })
    .where(eq(socialPosts.id, data.socialPostId));

  return job.id!;
}
```

**`jobId` based on socialPostId** — prevents duplicate enqueues. If user clicks "render" twice quickly, second enqueue is no-op (BullMQ rejects duplicate jobId).

**Re-render flow**: to re-render an existing social_post (e.g. after editing brand tokens), the caller must first set `renderJobId: null` + `renderStatus: 'pending'` in DB, then enqueue new job with same socialPostId. Alternatively: append a version suffix to jobId. Phase E concern — current spec assumes one render per post.

### C.2 PersistSocialPostStep Adjustment

Pre-57.2: `PersistSocialPostStep` inserted social_post rows with all data (caption, hashtags, slides). Post-57.2: rows are already inserted by `RenderSlidesStep` (without slides). `PersistSocialPostStep` updates caption/hashtags onto the row:

```typescript
async execute(input, ctx) {
  for (const enqueued of input.enqueuedRenders) {
    const caption = input.perLocaleOutputs.find(o => o.locale === enqueued.locale)?.caption;
    const hashtags = input.perLocaleOutputs.find(o => o.locale === enqueued.locale)?.hashtags;

    await db
      .update(socialPosts)
      .set({ caption, hashtags })
      .where(eq(socialPosts.id, enqueued.socialPostId));
  }
  return input;
}
```

**Alternative ordering**: GenerateCaptionStep runs FIRST, then RenderSlidesStep enqueues with all data ready (including caption/hashtags going into social_post row at insert time). This is cleaner — only one INSERT per post, no subsequent UPDATE. **Recommendation: this ordering** — confirm step chain reordering is acceptable.

## Cross-cutting Concerns

### CC.1 Schema Verification Pattern

Per accumulated lessons (56.6, 57.1): **always verify schema fields exist before referencing them in spec implementation**.

### CC.2 Memory + Process Hygiene

Render worker runs Chromium internally (Remotion). Memory hygiene:

- **`concurrency: 1`** per worker process
- **Job-level cleanup**: ensure `@remotion/renderer` releases browser resources between jobs (check Remotion docs / existing render code for `cleanup()` calls)
- **Optional**: restart worker process every N completed jobs (e.g. 50) to fully reset memory. Configure via BullMQ worker option `removeOnComplete + max-jobs-per-worker` if needed. Phase E if first version is stable.

### CC.3 Error Handling

Three failure modes:
1. **Render error (deterministic)**: e.g. invalid template input. After 2 attempts, mark failed in DB + emit SSE.
2. **Transient error (e.g. Redis blip)**: BullMQ retry handles this; DB stays in `rendering` until retry resolves.
3. **Worker crash (e.g. OOM)**: BullMQ marks job as failed after timeout; on worker restart, BullMQ re-queues if `attempts` remaining.

`renderError` JSONB contains code + message + stack for diagnosis. UI surfaces error message to user; full stack available via API for support.

**Cost tracking unchanged**: Sonnet caption call (in pipeline step, not worker) is metered as `COST_OPS.SOCIAL_IMAGE_CAPTION`. Worker doesn't make LLM calls, so no new cost ops.

## Risks & Mitigations

**Risk 1: Worker process crashes leave jobs stuck in `rendering` state**
- *Mitigation*: BullMQ "stalled job" detection re-queues active jobs when worker dies. Worker startup logic on next boot picks up where it left off. If `renderStartedAt` > 5 minutes ago AND BullMQ has no active job for it, that's a stale state — add a startup reconciliation job that resets such rows to `pending`. Phase E concern if first version proves stable.

**Risk 2: Memory leaks across renders in same worker process**
- *Mitigation*: `concurrency: 1` + cleanup between jobs (Session 3). Manual stress test in Session 7 (10+ back-to-back). If issues, configure BullMQ to recycle worker after N jobs.

**Risk 3: Race between pipeline-step enqueue and worker pickup**
- *Mitigation*: Worker reads ALL render inputs from `job.data` (snapshot), NOT from DB. Even if DB state changes between enqueue and pickup, render uses snapshot values.

**Risk 4: SSE events lost during reconnect**
- *Mitigation*: UI's `usePipelineEvents` composable already handles reconnection (per 56.6 pattern). On reconnect, refetch active renders via `GET /render-status`. Active = `renderStatus IN ('pending', 'rendering')`.

**Risk 5: Pipeline step reordering breaks downstream**
- *Mitigation*: Verify in Session 4 that `PersistSocialPostStep` (or its replacement) handles both old and new step output shapes. Tests cover the chain.

**Risk 6: Existing renders (pre-57.2) display incorrectly**
- *Mitigation*: Backfill marks all existing rows with slides as `rendered`. Visual smoke test confirms render history shows historical posts correctly.

**Risk 7: Render-status enum mismatch with existing `status` confuses UI**
- *Mitigation*: Per Spec 57.1 memory pattern #26 — `status` is content lifecycle, `render_status` is render lifecycle. UI never confuses them: render-status chip is visually distinct (in-flight states use spinner), content status badge separate. Clear visual + semantic separation.

1. **Worker process: same-process (B.3.a) or separate-process (B.3.b)?**
   Spec recommends B.3.b for crash isolation. Confirm — depends on whether existing worker entrypoint exists.

2. **Pipeline step reordering: GenerateCaptionStep before RenderSlidesStep?**
   Recommendation: yes — caption/hashtags ready at social_post insert time, single INSERT per post. Confirm step chain reorder acceptable.

3. **Re-render flow for existing posts**
   Spec leaves re-render of existing rendered post to Phase E. Marcel may want this sooner (re-render after editing brand tokens). Decision:
  - (a) v1 has no UI for re-render — Marcel manually edits DB if needed
  - (b) v1 adds "Re-render" button on rendered posts that sets renderStatus → pending + enqueues
  - Recommendation: (a) for now, (b) when first request actually comes up

4. **Render progress events: emit or skip?**
   `social.render.progress` events add value for long renders. But Remotion progress callbacks may not be granular enough for short renders. Recommendation: skip in v1, add in Phase E if user feedback wants progress bar.

5. **Stalled job reconciliation: v1 or Phase E?**
   If worker dies mid-render, row stays `rendering` until manual fix. BullMQ has stalled-job detection but interaction with DB needs explicit reconciliation. Recommendation: Phase E unless Session 7 shows this happens in practice.

## Discovered During Implementation (Sessions 1–2)

### D.1 `packages/queue` does not exist
The spec referenced `packages/queue/src/queues/social-render.queue.ts`. No such package exists in the monorepo. Queue definition and worker were co-located in `apps/api/src/workers/` alongside all other BullMQ workers, which is the established pattern. No new package needed.

### D.2 `sql` import source for Drizzle partial-index `.where()`
The `sql` template tag used in schema files for partial-index `.where(sql\`...\`)` conditions must be imported from `drizzle-orm`, not `drizzle-orm/pg-core`. The latter does not export `sql` and TypeScript errors immediately (`Module has no exported member 'sql'`). Added to `packages/db/CLAUDE.md` Common Mistakes.

### D.3 Zod parse → `as T` cast for BullMQ job.data under `exactOptionalPropertyTypes`
`zodSchema.parse(job.data)` returns `T | undefined` for optional fields, which is structurally incompatible with `field?: T` in the target type under `exactOptionalPropertyTypes`. Pattern: `zodSchema.parse(job.data) as TargetType`. The `.parse()` enforces the shape at runtime; the cast resolves only the TypeScript variance check. Added to root `CLAUDE.md`.

### D.4 `totalSlides: 0` placeholder at INSERT — worker sets real count (Sessions 3-5)
The spec's `content: { slides: [] }` implied an empty placeholder but didn't specify the `totalSlides` column behavior. At INSERT time the pipeline sets `totalSlides: 0`; the render worker calls `.set({ totalSlides: slideUrls.length, ... })` when marking `rendered`. UI must use `content.slides.length` (or the `totalSlides` column from the render-status endpoint) rather than trusting `totalSlides` on a `pending/rendering` post — it will be 0.

### D.5 Dynamic import of `@marketing-auto/social/render-server` requires `as unknown as` cast (Session 3)
`render-server.ts` uses JSX internally; TypeScript can't infer its export types from the API tsconfig context (which has no `--jsx`). The dynamic import `await import("@marketing-auto/social/render-server")` must be cast: `as unknown as { renderListCarouselStunning: (...) => Promise<...> }`. Justification comment required at call site. Added `"@marketing-auto/social/render-server"` subpath export to `packages/social/package.json` and a matching `paths` entry in `apps/api/tsconfig.json`.

## Deviations from Spec

### Dev.1 Queue co-location (B.3 path)
Spec proposed `packages/queue/src/queues/` and `packages/queue/src/workers/`. Actual implementation: queue definition at `packages/pipelines/src/engine/social-render-queue.ts`; worker at `apps/api/src/workers/social-render.worker.ts`. Worker process is B.3.a (same process as API — existing pattern). No functional difference; simplifies the dependency graph.

### Dev.2 Queue definition moved to `packages/pipelines/src/engine/`
Spec (post Dev.1 update) placed the queue file in `apps/api/src/workers/`. During Session 4, the pipeline step needed to call `enqueueSocialRenderJob()` — but `packages/pipelines` cannot import from `apps/api` (direction violation). Queue definition was moved to `packages/pipelines/src/engine/social-render-queue.ts` with a `./social-render-queue` subpath export. The worker imports via `@marketing-auto/pipelines/social-render-queue`. Both `packages/pipelines/package.json` and `apps/api/tsconfig.json` required the corresponding export/paths entries.

### Dev.3 `PersistSocialPostStep` eliminated, not updated
Spec C.2 said to update `PersistSocialPostStep` to write caption/hashtags via UPDATE after the INSERT. Implementation: `PersistSocialPostStep` was deleted entirely; `RenderSlidesStep` now does a single INSERT with caption/hashtags (from `GenerateCaptionStep` output) and `renderStatus: 'pending'`, `totalSlides: 0`, `slides: []`. The worker fills `totalSlides` and `slides` on completion. One INSERT instead of INSERT + UPDATE — cleaner and reduces round-trips. The `totalSlides: 0` placeholder at INSERT time is intentional; worker sets `totalSlides: slideUrls.length` when marking `rendered`.
