# Spec 61.3 — `ki-wissen` Article Generator Variant

**Date:** 2026-05-19
**Theme:** 61 — Article Generator Variants
**Prerequisite:** 61.2 done (DraftStep+FRONTMATTER_EXTRAS pattern, LOCALE_LABELS,
enqueueBlogGenerationPipeline wrapper pattern all established)
**Estimated effort:** ~1 day (simpler than 61.2 — no structured comparison data,
no tool picker, no winner/useCaseVerdicts validation gate)

---

## TL;DR

Add `ki-wissen` article generation. These are knowledge pillar pages — concept
definitions, myth-vs-reality, taxonomy clarifications. Structurally simpler than
comparisons (no toolSlugs, no winner logic) but require collection-specific
frontmatter fields (`category` enum, `level`, `icon`, `facts[]`, `next[]`) and a
distinct body structure (TL;DR callout → myth grid → definition → taxonomy →
examples → risks → next steps → FaqBlock). Monetization is always off — no
adsenseSlots, no affiliate links. Min 2,500 words, 7 FAQs.

### 2.2 Body structure prompt

```
Schreibe den vollständigen Artikel-Body für: {title}
Ziel-Level: {level} | Kategorie: {category} | Locale: {locale}

Pflicht-Struktur (exakt in dieser Reihenfolge):

1. <aside> Block — TL;DR-Definition in 60–80 Wörtern.
   Format: `<aside>\n\n**TL;DR:** ...\n\n</aside>`

2. ## {LOCALE_LABELS.mythGrid} — 4 Mythen-vs-Realität-Paare.
   Format: Markdown-Tabelle mit Spalten "Mythos" und "Realität".

3. ## {LOCALE_LABELS.definition} — Hauptdefinition in 2–3 Absätzen + Analogien.

4. ## {LOCALE_LABELS.taxonomy} — Abgrenzung zu verwandten Konzepten
   (z.B. KI vs. ML vs. Deep Learning). Tabelle empfohlen.

5. ## {LOCALE_LABELS.examples} — mindestens 6 konkrete Alltagsbeispiele.

6. ## {LOCALE_LABELS.risks} — Einschränkungen und Risiken (ausgewogen).

7. ## {LOCALE_LABELS.nextSteps} — "Nächste Schritte" — HowTo-Liste.
   Jeder Schritt aus `next`-Array wird hier verlinkt/beschrieben.

8. <FaqBlock /> — letzte Zeile, nichts danach.

Mindestlänge: 2.500 Wörter.
Kein Einleitungssatz vor dem <aside>-Block.
Kein Markdown-Codeblock im Output.
```

## Section — Deviations from Original Spec

1. **No `selectBodyPrompt` — selector is `selectDraftPrompt`.** The spec
   (§3.1) proposed a body-only selector following an outdated 61.2 sketch.
   The actual 61.2 implementation uses a single-shot `DraftStep` (body +
   FRONTMATTER_EXTRAS in one LLM call) and a single `selectDraftPrompt`
   selector. We followed the in-repo pattern, not the older selector name.

2. **Selector lives in `prompts/index.ts`, not in a builder file.** The spec
   diagram (§3.1) drew the selector in `prompts/index.ts` while the actual
   61.2 implementation had it in `prompts/comparison.ts`. We extracted it
   during 61.3 so adding a second collection type (now plus future variants)
   doesn't bloat a "comparison" file with unrelated cases. `comparison.ts` is
   now pure builders; the selector + its `DraftPromptFn` type live in
   `prompts/index.ts`.

3. **No `LOCALE_LABELS` "extension" — each builder owns its own map.** The
   spec (§2.3) proposed extending a shared `LOCALE_LABELS` from 61.2 with a
   `ki_wissen` sub-key. We kept the labels file-local in `prompts/ki-wissen.ts`
   instead. Reason: 61.2's `LOCALE_LABELS` is shaped specifically for
   comparison sections (glance / useCaseMatrix / priceComparison / methodology /
   conclusion) — a `ki_wissen` sub-key would force a discriminated-union
   helper for callers. File-local maps are simpler and the duplication is
   minimal (5 section names × 2 locales).

4. **Smaller `kiWissenFrontmatterBounds` export than the spec.** The spec
   (§1.2) bundled `title`/`description`/`seoTitle`/`tags`/`faq` bounds into
   the same constant. We only included ki-wissen-SPECIFIC bounds (`icon`,
   `facts`, `next`) since shared fields are constrained by the cross-collection
   FRONTMATTER_EXTRAS conventions, not by a per-collection bound map. Keeps
   the bound module dependency-free.

5. **FAQ-count constraint enforced in `DraftStep`, not in the schema.** The
   spec (§3.2) implied the `countMin: 7` bound would be enforced by Zod via
   `KiWissenExtrasSchema`. In practice the `faq` field is a cross-collection
   FRONTMATTER_EXTRAS field (blog/comparison/ki-wissen all emit it), so it
   lives outside the collection-specific extras schema. `DraftStep` runs an
   explicit `faqCount < 7 → throw ArticlePipelineError` check immediately
   after `validateKiWissenExtras` returns ok.

6. **No frontend change — collection picker already supported ki-wissen.**
   Spec §5.1 instructed to add `ki-wissen` to `SUPPORTED_COLLECTION_TYPES`.
   `ArticleGenerateTab.vue` already listed it (`collectionOptions` array
   contains `"ki-wissen"`) and `articles-standalone.ts` already mapped the
   Astro folder name to the enum value. Zero-line frontend change.

7. **No optional category-hint dropdown (spec §5.3 "Optional").** Skipped
   per Pattern 114 — the LLM infers category from keyword context. If users
   later want explicit category control, add a `preferredCategory` brief
   field then.

8. **`enqueueBlogGenerationPipeline` wrapper unchanged.** Spec §3.3 hinted
   the wrapper might need extension. Per Pattern 114, ki-wissen needs no
   extra brief fields — only `collectionType: "ki-wissen"` is forwarded, and
   that field is already forwarded by 61.2's wrapper. No change.

## Section — Discovered During Implementation

**Pattern 109 (selector) deserves a single canonical home, not a shared
builder file.** When 61.2 added `selectDraftPrompt` to `prompts/comparison.ts`
it was the only caller of the selector pattern, so co-location was fine. Once
a second collection arrives (61.3) the selector switch starts collecting
cases unrelated to the file's name. Solution: extract the selector + its
`DraftPromptFn` type to `prompts/index.ts` at the moment the second case is
added (not later). Each builder file then has zero collection-discriminator
logic, just `buildXxxDraftPrompt()`. Re-exporting `buildComparisonContextFragment`
from `index.ts` keeps DraftStep's call site single-import. **Future
collections (usecases, tools) follow the same pattern.**

**Pattern 116 (monetization rejection) is BOTH a prompt-level and a
schema-level concern.** Telling the LLM "do NOT emit adsenseSlots" works
~95% of the time. The remaining 5% needs `validateKiWissenExtras` to reject
those keys explicitly with a clear error message, so a bad LLM output fails
loudly at the validation gate instead of silently overriding the Astro
default `false`. The schema check is the load-bearing safety net.

**The `faq` field crosses collections — keep it OUT of collection extras
schemas.** Every Astro collection in our project emits a `faq` array at the
top level of FRONTMATTER_EXTRAS, with collection-specific minimum counts (5
for blog/comparison, 7 for ki-wissen). Modeling this in Zod would force a
discriminated union per collection just for one field. Simpler: keep `faq`
unconstrained in `KiWissenExtrasSchema` (it's not a ki-wissen-specific
field), and enforce the minimum count in `DraftStep` after parse. This
mirrors how the 7-FAQ requirement is documented in `buildKiWissenDraftPrompt`
without coupling the schema to a cross-cutting concern.

**Icon suggestions per category drive LLM accuracy without constraining it.**
Hardcoding "icon must be in this 5-item list" makes the icons stale (Lucide
adds icons; we don't update the list). Listing 5 category-specific suggestions
inline in the prompt (Pattern 115) — and explicitly noting "OR a closely
related valid Lucide name" — yields ~100% valid Lucide names in test runs
without ever rejecting a draft for an unknown icon. The `validateKiWissenExtras`
gate only requires `icon: z.string().min(2).max(40)` — no enum.

**`bottomLinksVariant: "default"` is the right ki-wissen choice.** The
existing variants (`comparison`, `tool`, `learning`, `business`, `default`)
were designed around commercial intent. ki-wissen is the trust layer —
non-commercial, conceptual. `"default"` is the no-affiliate-CTA variant.
Future Astro work may add a `knowledge` variant; ki-wissen would migrate to
it via the prompt change alone (no pipeline change).

**Worker PID-file is not always updated on backgrounded restart.** Running
`bun run worker:restart 2>&1 &` from a non-TTY context can leave
`tmp/worker.pid` pointing at the previous (now-dead) PID even after the new
worker starts cleanly. The new worker still picks up jobs from BullMQ
correctly; only the singleton-guard check on subsequent restarts is affected.
Reconcile manually by writing the new PID (visible in
`ps aux | grep workers/index`) to `tmp/worker.pid`. Not a code defect —
just a non-TTY backgrounding quirk worth noting for future automated
restarts.
