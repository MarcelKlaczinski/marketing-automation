# Spec 62.0b — Prompt Versions + Optimization Requests (Minimal)

_Theme 62 Sub-Spec — Part 2 of merged 62.0a/0b foundation._
_Status: Draft._
_Voraussetzung: 62.0a + 62.0a-followup sind gemerged. Issue 3 manuelle Verifikation darf parallel laufen._

---

## 1. Ziel

Schließt die zwei No-Op-Stellen aus 62.0a:
- `promote-golden` Action: heute identisch zu `approve` (D8 aus 62.0a). Soll: Prompt-Version persistieren und aktiv setzen.
- `extract-for-optimization` Action: heute nur `step_pauses.userNote` (D8/D27). Soll: eigene Tabelle, queryable.

**Bewusster Scope-Cut gegenüber Voll-62.0b:**
- **Kein** Auto-Sampling von Approve-Outputs (kommt wenn wir konkreten Bedarf erlebt haben)
- **Kein** LLM-as-Judge Regression-Worker (kommt mit Erfahrung wann das wirklich gebraucht wird)
- **Kein** Quarantäne-Marker (kein Regression-Check = kein Quarantäne-Trigger)
- **Kein** Auto-Rollback (gleiche Begründung)

Was bleibt: das **Datenmodell** so designen, dass diese Erweiterungen additiv möglich sind. Spec 62.0c (oder Inline-Erweiterung in 62.4) kann später drauf bauen, ohne 62.0b-Schema zu brechen.

---

## 2. Architektur-Entscheidungen

Aus Marcel-Antworten + 62.0a/followup-Foundation:

- **Hybrid-Resolution für Prompts (Wurf C aus Beratung):** File-Defaults bleiben, DB-Goldens überschreiben, Project-Overrides sind möglich, Debug-Run-Override (62.0a `ctx.promptOverride`) gewinnt immer.
- **Promote-Action ist sofort live**: schreibt `prompt_versions` Row mit `is_golden=true`, alle nachfolgenden Runs nutzen es. Kein Deploy nötig. Kein Regression-Check (verschoben).
- **Override betrifft nur `prompt.variableSuffix`** (62.0a D19) — `prompt_versions.body` enthält nur den Suffix, nicht den ganzen System-Prompt. Bleibt konsistent zur 62.0a-Mechanik.
- **`step_optimization_requests` Tabelle minimal**: User-Note + frozen Snapshot (Input/Output/Prompt). Keine Claude-Code-Response-Persistenz (das kann später additiv).
- **`kind: "prompt_pause"` Wert in `suspension_checkpoint`** wird NICHT in 62.0b eingeführt — solange wir keinen separaten Pause-Flow für Prompt-Editing brauchen, ist `kind: "step_pause"` ausreichend. Vermeidet vorzeitige Discriminator-Erweiterung.
- **Cache-Layer für DB-Goldens:** In-Process-Cache pro `(stepName, projectId)` mit 5-Min-TTL. Invalidation bei jedem Promote. LLM-Call darf nicht jedes Mal die DB pingen.

## 3. Datenbank-Migrationen

### 3.1 Migration `0070_prompt_versions.sql`

```sql
-- 1) prompt_versions: stores promoted prompt overrides
CREATE TABLE prompt_versions (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  step_name       text NOT NULL,
  project_id      uuid NULL REFERENCES projects(id) ON DELETE CASCADE,  -- NULL = global override

  -- Content
  body            text NOT NULL,                  -- the variableSuffix replacement (NOT the full system prompt)
  source_pause_id uuid NULL REFERENCES step_pauses(id) ON DELETE SET NULL,  -- the pause that triggered this promote

  -- Lifecycle
  is_golden       boolean NOT NULL DEFAULT false, -- only one is_golden=true per (step_name, project_id)
  created_at      timestamptz NOT NULL DEFAULT now(),
  created_by      text NULL,                      -- 'marcel' for now; future: user_id
  superseded_at   timestamptz NULL,               -- set when a newer golden replaces this one

  -- Notes (for audit)
  promote_note    text NULL                       -- free text from the UI promote dialog
);

-- Only one golden per (step, project) — including NULL project for globals
CREATE UNIQUE INDEX prompt_versions_one_golden_per_step
  ON prompt_versions (step_name, COALESCE(project_id::text, 'GLOBAL'))
  WHERE is_golden = true;

CREATE INDEX prompt_versions_step_project_idx
  ON prompt_versions (step_name, project_id, created_at DESC);

-- 2) step_optimization_requests: snapshot of "this output wasn't good, here's why"
CREATE TABLE step_optimization_requests (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  step_pause_id   uuid NOT NULL REFERENCES step_pauses(id) ON DELETE CASCADE,
  step_name       text NOT NULL,                  -- denormalized for query-without-join
  pipeline_name   text NOT NULL,                  -- denormalized
  project_id      uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,

  -- Frozen snapshot at request time (copied from step_pauses for immutability)
  step_input      jsonb NOT NULL,
  step_output     jsonb NOT NULL,
  prompt_used     text NULL,

  -- User context
  user_note       text NOT NULL,                  -- WHY was this output not good (required)
  requested_at    timestamptz NOT NULL DEFAULT now(),
  requested_by    text NULL,                      -- 'marcel' for now

  -- Lifecycle (for future: claude-code response, status tracking)
  status          text NOT NULL DEFAULT 'open',   -- 'open' | 'addressed' | 'discarded'
  addressed_at    timestamptz NULL,
  addressed_note  text NULL                       -- e.g. "fixed in v4 prompt", "discarded — was a one-off"
);

CREATE INDEX step_optimization_requests_open_idx
  ON step_optimization_requests (project_id, requested_at DESC)
  WHERE status = 'open';

CREATE INDEX step_optimization_requests_step_idx
  ON step_optimization_requests (step_name, project_id, requested_at DESC);
```

## 4. Prompt-Resolution: Hybrid

### 4.1 Lookup-Reihenfolge

```ts
// packages/pipelines/src/engine/prompt-resolver.ts (62.0a) wird erweitert
export async function resolvePrompt(
  ctx: StepContext,
  stepName: string,
  buildDefault: () => string
): Promise<string> {
  // 1. Debug-Run Override (62.0a, höchste Priorität)
  if (ctx.promptOverride?.[stepName]) {
    return ctx.promptOverride[stepName];
  }

  // 2. Project-specific golden
  const projectGolden = await getGoldenPromptCached({
    stepName,
    projectId: ctx.projectId,
  });
  if (projectGolden) {
    return projectGolden.body;
  }

  // 3. Global golden (project_id IS NULL)
  const globalGolden = await getGoldenPromptCached({
    stepName,
    projectId: null,
  });
  if (globalGolden) {
    return globalGolden.body;
  }

  // 4. File default (Fallback, always available)
  return buildDefault();
}
```

**Wichtig:** `resolvePrompt()` wird async. Das ist eine **breaking API change** für die 62.0a-Caller — alle 27 Step-Sites müssen `await` davorsetzen. Discovery-Check ob das tatsächlich überall sauber möglich ist (`execute()` ist sowieso schon async, also unproblematisch — aber Helper-Functions wie `enrichToolUseCaseTokens()` müssen ggf. ihre Signature anpassen).

### 4.2 Cache-Layer

```ts
// packages/pipelines/src/engine/golden-prompt-cache.ts
type CacheKey = string;  // `${stepName}::${projectId ?? "GLOBAL"}`
type CacheEntry = { body: string; cachedAt: number };

const cache = new Map<CacheKey, CacheEntry>();
const TTL_MS = 5 * 60 * 1000;  // 5 minutes

export async function getGoldenPromptCached(input: {
  stepName: string;
  projectId: string | null;
}): Promise<{ body: string } | null> {
  const key = `${input.stepName}::${input.projectId ?? "GLOBAL"}`;
  const cached = cache.get(key);

  if (cached && Date.now() - cached.cachedAt < TTL_MS) {
    return { body: cached.body };
  }

  // Miss: load from DB
  const row = await getGoldenPrompt({ stepName: input.stepName, projectId: input.projectId });

  if (!row) {
    // Negative cache: also cache "not found" to avoid hammering DB
    cache.set(key, { body: "__NULL__", cachedAt: Date.now() });
    return null;
  }

  cache.set(key, { body: row.body, cachedAt: Date.now() });
  return { body: row.body };
}

// Called from promote-golden handler
export function invalidateGoldenPromptCache(input: {
  stepName: string;
  projectId: string | null;
}) {
  const key = `${input.stepName}::${input.projectId ?? "GLOBAL"}`;
  cache.delete(key);
}
```

**Caveat:** Multi-process deployments (mehrere BullMQ-Worker-Instanzen) hätten je eigenen In-Process-Cache. Promote auf Worker A invalidiert nicht Worker B. **Für 62.0b akzeptiert:** Toolwiki läuft single-instance. Wenn das je mehr wird, migrieren wir zu Redis-Pub-Sub-Invalidation (additiv, kein Schema-Change).

`promoteToGolden()` in `packages/db/src/helpers/prompt-version-write.ts`:

```ts
export async function promoteToGolden(input: {
  stepName: string;
  projectId: string | null;
  body: string;
  sourcePauseId: string;
  promoteNote: string | null;
  createdBy: string;
}): Promise<{ id: string }> {
  return await db.transaction(async (tx) => {
    // 1. Mark all existing goldens for (step, project) as superseded
    await tx.update(promptVersions)
      .set({ isGolden: false, supersededAt: new Date() })
      .where(and(
        eq(promptVersions.stepName, input.stepName),
        input.projectId === null
          ? isNull(promptVersions.projectId)
          : eq(promptVersions.projectId, input.projectId),
        eq(promptVersions.isGolden, true),
      ));

    // 2. Insert new golden
    const [inserted] = await tx.insert(promptVersions).values({
      stepName: input.stepName,
      projectId: input.projectId,
      body: input.body,
      sourcePauseId: input.sourcePauseId,
      isGolden: true,
      createdBy: input.createdBy,
      promoteNote: input.promoteNote,
    }).returning({ id: promptVersions.id });

    return inserted;
  }).then((result) => {
    // 3. Invalidate cache (outside tx)
    invalidateGoldenPromptCache({ stepName: input.stepName, projectId: input.projectId });
    return result;
  });
}
```

**Edge-Case:** Race-Condition wenn zwei Promotes für gleichen (step, project) gleichzeitig laufen. Lösung: UNIQUE-Index aus 3.1 (`prompt_versions_one_golden_per_step`) wird die zweite Insert ablehnen. Transaction failed, User sieht Fehler "another promote happened in parallel, please retry". Akzeptabel für single-user-Setup.

| Risiko | Mitigation |
|--------|-----------|
| `resolvePrompt()` async-Konversion bricht 62.0a-Tests | Phase 2.6 grep verifiziert dass alle Caller `await` haben; Workspace-typecheck zeigt missing-await sofort |

## 11. Anschluss

Nach 62.0b sind die zwei No-Op-Stellen aus 62.0a geschlossen. Funktional vollständige Step-Pause + Promote + Optimization-Request Foundation.

**Was 62.0b bewusst NICHT macht (Erfahrung sammeln zuerst):**
- Auto-Sampling von Approve-Outputs in `prompt_golden_samples` → eigene Mini-Spec wenn du nach 1-2 Wochen Nutzung merkst dass du Regression-Schutz brauchst
- LLM-as-Judge Regression-Worker → gleicher Trigger
- Quarantäne-Marker bei Regression-Fail → braucht Regression-Check zuerst
- Auto-Rollback → würde nur mit Regression-Check Sinn machen

**Aktivitäten zwischen 62.0b und Folgespecs (62.2 / 62.3 / 62.4):**
- Echte Debug-Runs auf Toolwiki sammeln (mind. 3-5 Promote-Golden-Aktionen, 5-10 Extract-for-Optimization)
- Beobachten: wie oft wird ein Prompt promoted und dann wieder rückgängig gemacht? → Falls häufig: Regression-Check ist gerechtfertigt
- Beobachten: stapeln sich Optimization-Requests ungenutzt? → Falls ja: Claude-Code-Integration in 62.6 priorisieren

**Nächste Sub-Specs (Reihenfolge bleibt wie geplant):**
- **62.2:** project_goals + Cadence-DSL (kann parallel zu Folgespecs)
- **62.3:** Signal-Refresh + ComparisonDiscovery
- **62.4:** Planner-Engine
- **62.5:** Kalender-UI + Approval-Flow
- **62.6:** Debug-Run Step-Inspector UI (konsumiert 62.0a + 62.0b Backend, plus optional Claude-Code-Integration für extract-for-optimization)
- **62.7:** Cron-Trigger + Quarantäne-View
- **62.8:** Production-Run + Batch-API-Integration
