# Spec 62.3 — Signal-Refresh + ComparisonDiscovery

_Theme 62 Sub-Spec — provides fresh signals + tool comparison candidates as input for the Planner (62.4)._
_Status: Draft._
_Voraussetzung: 62.0a + 62.0a-followup + 62.0b + 62.2 sind gemerged._

---

## 1. Ziel

62.3 liefert zwei Daten-Foundations, die der Planner-Engine (62.4) konsumiert:

1. **Signal-Refresh-Mechanik** — `refreshSignalsForProject(projectId)` als Library-Funktion, die der Planner als ersten Step seiner Pipeline aufruft. Garantiert dass Signale aktuell sind bevor geplant wird.

2. **ComparisonDiscovery** — Modul das Tool-Paare findet, scored und als `discovery_type='comparison_pair'` in `article_discovery` persistiert. Output: priorisierte Liste von "welche Comparisons könnten wir schreiben".

**Out of Scope:**
- Signal-Score-Normalisierung über Sources hinweg (kommt in 62.4 als simple Heuristik)
- Signal-Decay-Funktion (kommt in 62.4 falls nötig)
- Reddit-Adapter-Aktivierung (Code bleibt drin, Auth fehlt, kommt zurück sobald Key da ist)
- GitHub-Filter-Tuning oder Tool-Inventory-Use-Case (Phase-E-Theme)
- DataForSEO als optionale ComparisonDiscovery-Quelle (Phase 2)

**Geschätzter Aufwand:** 1.5-2 Tage. Etwas größer als 62.2 weil ComparisonDiscovery konzeptionell neu ist.

## 2. Architektur-Entscheidungen

Aus Marcel-Antworten + Codebase-Kontext:

- **Trigger via Planner-Engine, nicht Cron:** 62.3 baut keine neue Cron-Registrierung. Der Refresh läuft on-demand als Pipeline-Step in 62.4 (oder via API-Endpoint für manuelles Triggern). Crons bleiben optional-extension für 62.7.
- **ComparisonDiscovery persistiert in `article_discovery`** (existierende Tabelle) mit neuem `discovery_type='comparison_pair'`. Kein neues Schema.
- **Score-Range pro Source heterogen erlaubt:** ProductHunt votes (0–∞), HackerNews points (0–∞), VendorRSS recency (0–7d). 62.3 normalisiert NICHT — 62.4 macht das als pragmatische Heuristik (Top-N pro Source merge).
- **Reddit + GitHub bleiben im Code aktiv:** Beide Adapter werden bei jedem Refresh aufgerufen. Sie liefern aktuell 0 Rows (Reddit: no creds, GitHub: filter zu strikt). Refresh-Funktion behandelt das als no-op pro Source, nicht als Error. Code-Path bleibt warm.
- **ComparisonDiscovery-Datenquelle Phase 1: Co-Mention aus `article_discovery.referenced_tools`.** Kostenlos, deterministisch, lokal. DataForSEO als Phase-2-Option dokumentiert aber nicht implementiert.
- **Stale-Threshold per Project konfigurierbar:** `project_planner_config.signal_max_age_hours` (default 24). Refresh-Funktion entscheidet pro Source ob refresh nötig basierend auf `external_signals.collected_at`.

## 4. Signal-Refresh-Mechanik

### 4.1 Public API

Neue Library-Funktion in `packages/cost-tracker/src/signal-refresh.ts` (oder `packages/signals/` falls Claude Code das sauberer findet):

```ts
export interface SignalRefreshResult {
  projectId: string;
  triggeredAt: Date;
  sourceResults: Array<{
    source: string;         // 'producthunt' | 'hackernews' | 'vendor_rss' | 'reddit' | 'github'
    status: "fresh" | "refreshed" | "skipped" | "no_credentials" | "filter_no_results" | "error";
    rowsAdded: number;
    lastCollectedAt: Date | null;
    notes?: string;         // human-readable explanation
    error?: string;         // when status='error'
  }>;
  totalRowsAdded: number;
  durationMs: number;
}

export async function refreshSignalsForProject(input: {
  projectId: string;
  force?: boolean;          // if true, refresh all sources regardless of staleness
}): Promise<SignalRefreshResult>;
```

### 4.2 Verhalten

Für jede registrierte Source:

1. **Staleness-Check:** `MAX(collected_at) WHERE project_id=X AND source=Y` vs. `signal_max_age_hours` aus `project_planner_config`. Wenn nicht stale UND `force=false` → status='fresh', skip.
2. **Refresh-Call:** Adapter-Funktion ausführen (analog zu Pre-flight Task 2).
3. **Source-Status-Mapping:**
  - Adapter returnt > 0 rows → status='refreshed'
  - Adapter returnt 0 rows, no error → status='filter_no_results' (z.B. heutiger GitHub-Filter)
  - Adapter throws "no credentials" → status='no_credentials' (z.B. Reddit ohne Key)
  - Adapter throws other → status='error', error string captured

**Wichtig:** keine Source bricht die ganze Funktion ab. Alle Sources werden versucht, Result-Object hat per-source-Status. Caller entscheidet was zu tun ist.

### 4.3 API-Endpoint (Manual Trigger)

`apps/api/src/routes/signals.ts`:

## 5. ComparisonDiscovery-Modul

### 5.1 Konzept

Findet Tool-Paare, die in vorhandenen Toolwiki-Artikeln gemeinsam erwähnt wurden (Co-Mention) und schlägt sie als Comparison-Kandidaten vor. Beispiele aus dem Toolwiki-Kontext: "Claude vs. GPT-4", "Midjourney vs. DALL-E", "Cursor vs. Copilot".

### 5.2 Datenquelle

Phase 1 nutzt **vorhandene Daten aus `article_discovery.referenced_tools`** (oder analoge Spalte/Tabelle wo Tool-References pro Artikel gespeichert sind).

**Discovery-Aufgabe für Claude Code (Phase 0 der Implementierung):**

```bash
# Find where article -> tool references live in the schema
grep -rE "referenced_tools|tool_references|article_tools" packages/db/src/schema/
# Or: check articles table for a JSON column with tool slugs
```

Drei mögliche Schemas die Claude Code finden könnte:

- **Variante A:** `article_discovery.referenced_tools jsonb` (Array von tool_slugs)
- **Variante B:** Junction-Tabelle `article_tools (article_id, tool_id)`
- **Variante C:** `articles.frontmatter` JSONB mit `tools: [...]`

Spec adaptiert sich an Realität. Algorithmus bleibt gleich.

### 5.3 Algorithmus

```ts
// packages/cost-tracker/src/comparison-discovery.ts (oder neues Modul)

export interface ComparisonDiscoveryResult {
  projectId: string;
  pairsFound: number;
  pairsScored: number;
  pairsAboveThreshold: number;
  topPairs: ComparisonPairPayload[];   // top 20 by score
  durationMs: number;
}

export async function discoverComparisonPairs(input: {
  projectId: string;
  minCoMentionCount?: number;   // default 2 — at least 2 articles must reference both tools
  minScore?: number;            // default 0.3 — exclude weak pairs
  excludeExistingComparisons?: boolean;  // default true — skip pairs that already have a comparison article
}): Promise<ComparisonDiscoveryResult>;
```

**Algorithmus-Steps:**

1. **Sammle alle (article, tool)-Paare** aus dem identifizierten Schema.
2. **Berechne Co-Mention-Matrix:** für jedes Tool-Paar (A, B) zähle wie viele Artikel BEIDE erwähnen.
3. **Filter:** mindestens `minCoMentionCount` Artikel (default 2). Eliminiert noise.
4. **Score-Berechnung pro Paar:**

   ```
   score = (coMentionCount / maxCoMention) * 0.6
         + (categoryOverlap ? 0.2 : 0)
         + (recentMentionsBoost) * 0.2

   - coMentionCount: how often both tools appear together
   - maxCoMention: highest co-mention count in this project (for normalization)
   - categoryOverlap: do both tools share a category tag (binary boost)
   - recentMentionsBoost: 1.0 if any article < 30 days old, decays to 0 at 180 days
   ```

5. **Exclude existing:** wenn `excludeExistingComparisons=true`, skip pairs wo bereits ein Comparison-Article existiert (Toolwiki hat 22 Comparisons in der Bestand).
6. **Persistieren:** Top-N (z.B. 50) als `article_discovery` rows mit `discovery_type='comparison_pair'` und payload aus 3.2.
7. **Upsert-Semantik:** wenn das Paar bereits als `comparison_pair` discovered ist, update den score + updatedAt statt insert. Pattern aus refresh-detector pre-flight: `onConflictDoUpdate` via partial unique index auf `(project_id, discovery_type, payload->>'toolASlug', payload->>'toolBSlug')`.

### 5.4 API-Endpoint

`apps/api/src/routes/comparison-discovery.ts`:

```ts
// Body: { force?: boolean, minScore?: number, minCoMentionCount?: number }

// Query params: minScore? sortBy? limit?

// Used by 62.4 Planner to select Comparison candidates
```

### 5.5 Edge-Cases

- **Tool-Paare in Reverse-Order:** `(A, B)` und `(B, A)` sind das gleiche Paar. Algorithm muss kanonisieren — z.B. immer alphabetisch sortiert speichern (`toolASlug < toolBSlug`).
- **Self-Pair:** Tool referenziert sich selbst (kann passieren bei FAQ-Articles). Skip.
- **Comparisons-of-Comparisons:** Wenn ein Comparison-Article selbst zwei Tools referenziert, zählt das? Phase 1: ja, mit gleichem Gewicht. Falls Daten zu noisy: später downweighten oder excluden.
- **Existing Comparisons-Match-Logic:** wie matchen wir "existiert schon"? Über `frontmatter.tools` der Comparison-Articles oder `frontmatter.comparedTools` (Schema-spezifisch). Claude Code grept in Phase 0.

## 10. Anschluss

Nach 62.3:
- **62.4 (Planner-Engine):** Erster Pipeline-Step ist `refreshSignalsForProject()`. Zweiter Step liest `article_discovery WHERE discovery_type IN ('trend', 'gap', 'refresh', 'comparison_pair')` als Input-Pool. - **62.5 (Kalender):** kann zusätzlich `/comparison-pairs` Endpoint anzeigen ("Diese Comparison-Pairs warten auf Planung")

- Cron-Setup (62.7 entscheidet ob nötig basiert auf Erfahrung)

## 11. Deviations + Discovered During Implementation

### Deviation 1: ComparisonDiscovery persists to `topic_briefs`, not `article_discovery`

Spec §3.1 + §10 assumed `article_discovery` had a `discovery_type` discriminator column and would host comparison_pair rows. Phase 0 discovery (`packages/db/src/schema/content.ts:572`) showed `article_discovery` is the per-article enrichment metadata table (Spec 53c) with `UNIQUE(article_id)` and no project_id/discovery_type/payload columns. The canonical discovery-queue table is `topic_briefs` (Spec 54.1), which already carries `source: gap_analysis | trend_discovery | refresh_detection | manual` and was the natural place to add `comparison_discovery`.

Implemented:
- Extended `topic_briefs.source` text union with `"comparison_discovery"` and `cluster_action` with `"comparison"` (no DDL except CHECK widening — see Deviation 4)
- Added `topic_briefs.comparison_metadata jsonb` column with the `ComparisonMetadataSchema` payload (toolASlug, toolBSlug, scores, etc.)
- Partial-unique-index for upsert: `(project_id, comparison_metadata->>'toolASlug', comparison_metadata->>'toolBSlug') WHERE source='comparison_discovery' AND comparison_metadata IS NOT NULL`
- `TopicBriefInsertSchema.superRefine` enforces canonicalization (`toolASlug < toolBSlug`) at write time

Bonus: 62.4 Planner now reads a single discovery queue (`topic_briefs`) for all 4 source types instead of merging two tables.

### Deviation 2: DI-callback for adapter fetchers (planner stays adapter-free)

Spec §4.1 sketched a flat `refreshSignalsForProject({ projectId, force })` signature, implying planner imports adapter classes directly. But every signal adapter package (`adapter-producthunt` etc.) depends on `@marketing-auto/pipelines` (for `ExternalSignalSource` / `RawSignal` types). Direct adapter deps in planner would chain a cycle once 62.4 wires `pipelines → planner`:

  `pipelines → planner → adapter-producthunt → pipelines` ← cycle

Implemented: `refreshSignalsForProject` accepts a `fetchers: Partial<Record<SignalSourceName, SignalFetcher>>` map. Caller (the new `apps/api/src/routes/projects/signals.ts` route) wires adapter instances. Same DI pattern as 62.0a's `PipelineStepResolver` / 62.2's `validateProjectGoals`. `packages/planner/package.json` has zero adapter deps.

`RawSignal` is re-declared as a local `RefreshableSignal` interface in planner (mirror of `packages/pipelines/src/signal-sources/types.ts`) to avoid importing the type from pipelines. Structurally compatible with adapter `.fetch()` return values.

### Deviation 3: SELECT-then-INSERT/UPDATE instead of `onConflictDoUpdate`

Drizzle's `onConflictDoUpdate.target` field accepts only `PgColumn` references, not `SQL` expressions. The partial-unique index on `(project_id, (comparison_metadata->>'toolASlug'), (comparison_metadata->>'toolBSlug'))` can't be specified as a `target`. Worked around by checking existence with a SELECT (predicate matches the partial-index predicate verbatim) inside a transaction, then INSERT or UPDATE. The partial unique index still backstops concurrent writers via DB-level constraint.

### Deviation 4: Migration split 0072 + 0073 (CHECK constraint discovery)

Migration `0032_topic_briefs.sql` hardcoded CHECK constraints on `source` and `cluster_action`:
- `CHECK (source IN ('gap_analysis', 'trend_discovery', 'refresh_detection', 'manual'))`
- `CHECK (cluster_action IN ('append_to_existing', 'create_new', 'translation', 'refresh', 'standalone'))`

Widening the Drizzle TypeScript `$type<>()` union is not enough — the DB rejects inserts with the new values at runtime. The CHECK widening landed as `0073_topic_briefs_comparison_constraints.sql` (DROP CONSTRAINT IF EXISTS + ADD CONSTRAINT). It's a separate file because 0072 was already in `__drizzle_migrations` on local DBs before the constraint discovery; splitting avoids the manual-edit-of-applied-migration footgun. Fresh installs run both back-to-back.

### Adjacent enabler: `signalMaxAgeHours` on `upsertProjectPlannerConfig`

`packages/db/src/helpers/project-planner-config-write.ts` `upsertProjectPlannerConfig` gained an optional `signalMaxAgeHours?: number` parameter so tests (and future Settings UI) can configure the staleness threshold. Backward compatible — when omitted, the DB default (24) wins; on update, the previous value is preserved. The helper stays in `packages/db` (write-side helper for `project_planner_config`), not `packages/planner`.

### Review fix: SELECT predicate matches partial unique index

`/review-task` found that the existence-check SELECT in `persistPairs` was missing `isNotNull(comparisonMetadata)`. The partial unique index predicate is `WHERE source='comparison_discovery' AND comparison_metadata IS NOT NULL`. PostgreSQL's planner can't prove that `comparison_metadata->>'toolASlug'` returning a value implies `IS NOT NULL`, so the partial index might not be used for the lookup. Fixed in commit `4835ac9` by adding the explicit `isNotNull` to the WHERE clause. No behaviour change.
