## 3. Architecture Decisions

### 3.1 Composition-Wrapper Conflict — Family-A has no shared wrapper

**Problem (Marcel chose "inject in composition-wrapper, 1 edit-point"):**

- Family-B HAS `SlideComposition.tsx` wrapper → clean single inject
- Family-A has NO shared wrapper → per-template Cover-slides

**Three resolution-options:**

**Option α — DsBrandStamp component, manually placed in each Cover + End:**

```tsx
// Each Cover-slide adds:
<DsBrandStamp logoUrl={brandTokens.logoUrl} />
```

Pros: Works für both families uniformly
Cons: NOT "1 edit-point" — N Cover-slides + N End-slides to touch (~7-9 sites)

**Option β — Extend Family-B SlideComposition + create Family-A wrapper:**

Create `_shared/family-a/SlideWrapper.tsx` mirroring Family-B's SlideComposition. Both inject stamp.

Pros: Establishes symmetric wrapper-pattern, central per-family
Cons: Family-A refactor (wrap all existing compositions) = scope-creep beyond brand-stamp

**Option γ — Stamp at render-server level (post-composition overlay):**

Inject stamp in the Remotion render-pipeline AFTER composition renders, as final overlay-layer on Cover + End frames only.

Pros: TRUE single edit-point (render-server), family-agnostic, slide-position-aware
Cons: Render-server complexity, needs slide-index awareness (which frame is Cover/End)

### Discovery-Recommendation: **Option α (DsBrandStamp component) BUT injected via existing composition-entry-points**

Reasoning:

1. **Marcel's "1 edit-point" intent ist about component-definition, not zero-call-sites** — DsBrandStamp is defined once, called at Cover+End
2. **Family-A + Family-B both have Cover-slide + RenderEndSlide** — 2 logical inject-points per family, not N
3. **Option β (Family-A wrapper refactor) ist scope-creep** — brand-stamp shouldn't trigger composition-rewrite
4. **Option γ (render-server overlay) ist over-engineered** — slide-index-awareness adds fragility for a watermark
5. **Cleanest real-shape:**
  - `DsBrandStamp.tsx` defined once in `_shared/`
  - Family-B: inject in `SlideComposition` when `variant === 'cover'` + in `RenderEndSlide`
  - Family-A: inject in each template's Cover-slide (4 templates) + shared `RenderEndSlide`

**Realistic edit-count:** 1 component + Family-B SlideComposition cover-branch + Family-B RenderEndSlide + 4 Family-A Cover-slides + Family-A RenderEndSlide = ~7 sites. NOT 1, but each is a 1-line `<DsBrandStamp />` insertion.

**If Marcel insists on true-1-edit-point:** Option γ (render-server overlay) is the only path, but adds slide-index-detection complexity. Recommend Option α pragmatically.

### 3.2 DsBrandStamp Component

```tsx
// packages/social/src/compositions/_shared/DsBrandStamp.tsx

interface DsBrandStampProps {
  logoUrl: string | null;       // brandTokens.logoUrl (R2 CDN)
  position?: 'bottom-right';    // V1 fixed, future: configurable
  marginPx?: number;            // default 48
  opacity?: number;             // default 0.7
  maxWidthPx?: number;          // logo max-width, default 120
}

export const DsBrandStamp: React.FC<DsBrandStampProps> = ({
  logoUrl,
  marginPx = 48,
  opacity = 0.7,
  maxWidthPx = 120,
}) => {
  // Graceful: no logo → render nothing (not a broken-image)
  if (!logoUrl) return null;
  
  return (
    <div style={{
      position: 'absolute',
      bottom: marginPx,
      right: marginPx,
      opacity,
      zIndex: 100,  // above content, below nothing
      pointerEvents: 'none',
    }}>
      <Img 
        src={logoUrl} 
        style={{ 
          maxWidth: maxWidthPx, 
          height: 'auto',
          display: 'block',
        }} 
      />
    </div>
  );
};
```

**Graceful-degradation:** `logoUrl === null` → renders nothing. Toolwiki must have logo set (verify §2.1 Q4).

### 3.3 Logo-Variant Selection (light vs dark slides)

**Problem:** Slide backgrounds vary (dark gradient, photographic, light editorial). A single logo-PNG might disappear on matching-color background.

**Per Marcel Q3 decision:** "Fixed opacity 0.7" — NOT adaptive (Marcel chose subtle watermark, not contrast-aware).

**Verify:** Does brand-asset have light + dark logo variants (§2.1 Q1)?

**If light+dark variants exist:**
```tsx
const logoUrl = theme === 'dark' ? brandTokens.logoLightUrl : brandTokens.logoDarkUrl;
```

**If single logo only:**
- V1: use the single logo at 0.7 opacity (Marcel's choice, accept risk on matching-bg)
- Note for V1.7: contrast-aware variant if recognition suffers on certain backgrounds

### Discovery-Recommendation: **Use theme-appropriate variant IF available, else single-logo + 0.7 opacity**

Reasoning: Marcel chose "fixed opacity" but theme-variant-selection is free if brand-assets already have both (no extra Marcel-decision needed, just smart-default).

## 14. Discovered During Implementation

Phase-0 verifications + implementation findings that the discovery doc did not anticipate:

1. **End-slides have a generic monogram, NOT the project logo** — `FollowCtaSlide.tsx` + siblings render a brand-gradient circle with a generic icon (user, save, link, etc.) per Spec 65.9 `EndSlideBase` design. NOT project-logo branding. Marcel's Cover+End choice IS non-redundant → both get stamped.
2. **Pre-existing UI/schema mismatch** — `SettingsBrandAssetsPage.vue` had `key: "logo"` while `brandTokens.social.logoAssetKey` defaults to `"main"`. Uploads via the existing UI never resolved via `resolveLogo()`. Fixed in passing as part of the slot-list rename.
3. **`resolveLogo` already existed** at `apps/api/src/lib/brand-asset-service.ts:159` (Spec 52b). Extended in-place for theme variants. NEW: added a sibling `resolveLogoUrl(projectId, theme): string | null` that returns a ready-to-use URL string (R2 URL OR `data:image/svg+xml;base64,…`) — skips wordmark + lobe-icons branches because neither is appropriate as a corner watermark.
4. **Family-A multi-slide carousels share one Cover slide** — `comparison-grid-3/slides/CoverSlide.tsx` is imported by grid-5 + h2h-vs + h2h-deep-dive too. So 4 multi-slide templates = 1 inject site for Cover (plus the shared `_shared/family-a/RenderEndSlide.tsx` for End).
5. **Total inject sites = 9, not 7** — `DsBrandStamp` defined once; 1 component import sites: Family-B `SlideComposition` (cover-variant branch) + Family-B `RenderEndSlide` + Family-A `RenderEndSlide` + Family-A shared `CoverSlide` + 4 single-still slides (grid-4 / verdict-per-use-case / single-tool-spotlight cover & end / pro-con-verdict). Discovery §3.1 hypothesized "~7 sites"; reality 9 once "ALL single-still Covers" per Marcel's Q2-revised answer.
6. **`exactOptionalPropertyTypes` required explicit `| undefined` on prop types** — `DsBrandStampProps.logoUrl?: string | null | undefined` and `SlideCompositionProps.logoUrl?: string | null | undefined`. Callers that pass-through with conditional spreads (`...(stampLogoUrl !== null && { logoUrl: stampLogoUrl })`) trigger TS2375 without the explicit `| undefined`.
7. **`resolveLogoUrl` lives in TWO files** — one in `apps/api/src/lib/brand-asset-service.ts` (for HTTP-route callers if any), one in `packages/pipelines/src/_lib/resolve-logo-url.ts` (consumed by `RenderSlidesStep`). Package-direction rule forbids `packages/pipelines → apps/api`; same pattern as `resolveToolIcon`.

## 15. Deviations

1. **Bookend scope widened to all single-still covers (Marcel Q2-revised, mid-implementation)** — discovery doc Q5 said "Bookend only Cover + End"; Marcel widened to "Stamp auf ALL single-still Covers" (8 templates total), so the 4 single-still templates also stamp their cover (which IS the only slide for those). End-slides only stamped where they exist as a distinct frame (single-tool-spotlight + the 4 Family-A multi-slide via shared RenderEndSlide + 3 Family-B via shared RenderEndSlide). For pro-con-verdict / verdict-per-use-case / comparison-grid-4 the "cover" IS the slide.

2. **Three-tier theme-variant fallback chain (Marcel Q2 verbatim)** — discovery §3.3 hypothesized a 2-tier chain (`<key>-<theme>` → `<key>`). Marcel's Q2 answer explicitly said "Fallback: wenn nur ein Variant da ist, nutze ihn für beide Themes" — so the chain has a third tier: `<key>-<theme>` → `<key>` → `<key>-<oppositeTheme>`. Caught during /review-task self-audit; would have shipped a real bug otherwise (Marcel uploads only `main-dark` → light-theme renders had no stamp).

3. **Settings UI slot renamed `logo` → `main` (+ `main-light` + `main-dark` siblings)** — discovery §0 + Q1 said "Reuse vorhandene Brand-Assets UI (kein neues Card)". The existing slot uses `assetKey="logo"` but the resolver expected `"main"` (from the schema default `brandTokens.social.logoAssetKey`). Renamed instead of adding a separate card type — still ONE card type (`assetType="logo"`), just three slot instances. No new component, no new schema field.

4. **`https://pub.toolwiki.ai/${sourceRef}` stays hardcoded** — both new `resolveLogoUrl` copies (apps/api + pipelines) inherit the existing toolwiki-specific custom-domain literal from `resolveLogo` + `resolveToolIcon`. Flagged in /review-task as pre-existing tech debt; multi-tenant fix is out of 65.15 scope (BK Solar / Bellemann will need a separate Spec to route via `R2_PUBLIC_BASE_URL`).

5. **Worker dispatch needed ZERO changes** — discovery §3 anticipated possible worker-side changes. Reality: `logoUrl` flows naturally because the worker's snapshot-spread (`{...snapshot.compositionInput, brandTokens, overrides}` for Family-B + Family-A multi-slide; `{...snapshot, brandTokens, overrides}` for flat single-still) doesn't filter fields. The worker file was untouched.

6. **`compositionInput.logoUrl` is set conditionally at the helper layer** — `buildFamilyAMultiSlideRenderInput` and `buildFamilyBRenderInput` both stamp `logoUrl` into the composition input AFTER calling the template's `buildCompositionInput()` (via the per-template snapshot wrappers). The two helpers diverged in style: Family-B injects via the inline `compositionInput` object literal; Family-A multi-slide uses post-assignment `compositionInput.logoUrl = args.logoUrl` because the snapshot wrappers return a frozen-shaped object literal. Both behave identically; the asymmetry exists because the wrapper functions own different parts of the assembly.

7. **`SocialPostRenderInput` canonical type widened** — second-pass /review-task added `logoUrl?: string | null` to the canonical type in [`packages/db/src/schema/content.ts:559`](packages/db/src/schema/content.ts), unlike `endSlideData` (Spec 65.10) which is still cast via `as SocialPostRenderInput`. Removes the per-call cast burden for `logoUrl` going forward; the `endSlideData` widening remains as a follow-up (left in place so the cast comment still makes sense; Spec 65.15 narrows it to "endSlideData only" with a one-liner pointing at the parallel pattern).

8. **Inline TODO comment for multi-tenant `pub.toolwiki.ai` hardcode** — single inline comment added at [`packages/pipelines/src/_lib/resolve-logo-url.ts`](packages/pipelines/src/_lib/resolve-logo-url.ts) line ~67 referencing Deviation §15.4. The mirror site in `apps/api/src/lib/brand-asset-service.ts` doesn't get the same TODO because it already inherits the convention from the pre-existing `resolveLogo` + `resolveToolIcon` next door — adding it only on the NEW resolver matches the "annotate new code" rule without breaking the existing convention.

9. **Reviewer agent's BLOCKER + 3/4 MAJORs were false positives** — the second-pass code-reviewer agent flagged a "signature mismatch in RenderEndSlide" (it calls `resolveLogoUrl` with `assetKey` not `projectId`) — verified via grep: RenderEndSlide does NOT call `resolveLogoUrl` at all, it only receives `logoUrl` as a prop. The reviewer also flagged "RenderSlidesStep call location not verified" (verified at line 1175 BEFORE the loop), "orphan uploads under old assetKey" (verified via live DB query — only ONE logo row exists in the entire project_brand_assets table, with assetKey="main", no migration needed), and "double-stamp risk in single-tool-spotlight" (Cover and End are separate component files dispatched by slideIndex — no double-stamp possible). The only real finding was the `SocialPostRenderInput` type widening (now applied). **Verify-the-narrative rule applies to reviewer agents too** — when a reviewer reports MAJORs without code citations, grep first.
