## Review Tasks (in order)

### Task 1 — Slide dispatcher pattern audit

In `SingleToolSpotlight.tsx`, the dispatcher switches on slideIndex → cover/body/end. Confirm:

- The dispatcher is **template-agnostic** in structure (i.e. the *pattern* — not the specific cover/body/end content — is clearly reusable)
- The `computeSlideOrder()` logic is simple enough to copy
- `sharedProps()` cleanly separates per-slide content from cross-slide context
- The dispatcher does NOT contain any single-tool-spotlight-specific business logic

Flag anything that would resist copy-paste into a comparison-grid dispatcher.

### Task 2 — DS component consumption audit

Each slide should:
- Call `deriveDsTokens(resolveBrandTokens(brandTokens), theme)` once, wrapped in `useMemo`
- Use `tokens.surface.base` / `tokens.ink.base` / `tokens.typography.fontFamily` at the AbsoluteFill root
- Position `<DsGlow>` first inside the AbsoluteFill (background layer)
- Wrap content in a `position: relative; zIndex: 1` container so it sits above the glow

Check all 3 slides (`CoverSlide`, `BodySlide`, `EndSlide`) follow this pattern uniformly. Flag inconsistencies.

### Task 3 — `<DsTop>` and `<DsFoot>` actual usage audit

The 60.0b v2 spec defined `<DsTop>` props: `eyebrow`, `rightText`, `num`, `updateBadge`. Were all four used in 60.1? Specifically:
- Cover uses `updateBadge` (per cover-dark.html)
- Body uses `num` for the date-line under eyebrow
- Both use `rightText` for the slide counter

Same for `<DsFoot>`: `logoUrl`, `logoText`, `ctaLead`, `ctaBold`, `logoHeight`. Confirm cover passes `logoHeight={48}` and body uses default 44.

Flag if any 60.0b v2 prop went unused — this might indicate the prop is overdesigned and should be dropped (relevant for 60.2-60.5 cleanup).

### Task 4 — `buildConstraintBlock` shape coverage audit

`buildConstraintBlock` supports 5 bounds shapes per the implementation report:
1. `FieldBound` (`{min, max}`)
2. `ListBound` with `{max, perItemMaxChars}`
3. `ListBound` with `{countMin, countMax, each}`
4. `count + FieldBound children` (e.g. `tools: { count: 4, name: {...}, ... }`)
5. Nested groups (recursive)

For 60.2-60.5, **all 5 shapes will appear**:
- comparison-grid-4 has `tools: { count: 4, name, verdict, price, flagText }` → shape 4
- comparison-grid-3 has `bullets.pros: { count: 2, each: {min, max} }` → shape 3
- verdict-per-use-case has `rows: { countMin: 5, countMax: 7, label, winnerName }` → mixed shape 3+4
- All have nested `footer: { ctaLine, url }` → shape 5

Read `buildConstraintBlock.ts` + its test snapshots. Confirm:
- All 5 shapes have explicit handling (not just shape 1+2)
- Snapshots include outputs for shape 4 (count+children) — this is the one likely to be missing because single-tool-spotlight's `facts: { count: 4, key, value }` is the only place it appears in 60.1

If shape 4 snapshot is missing or shape 4 logic is untested, that's a blocker for 60.2.

### Task 5 — Dual-schema LLM flow audit

The pattern (per Memory #59): `llmResponseSchema` (snake_case raw) + `generatedSchema` (camelCase post-transform). `validateAndReprompt` runs against the raw schema BEFORE transform.

Read `singleToolSpotlight.ts` generateContent function. Confirm:
- A `spotlightLlmResponseSchema` exists with snake_case fields
- A transform converts to `SpotlightBodyProps` (camelCase)
- `validateAndReprompt` validates the LLM output against the raw schema (not the camelCase one)
- The transform happens exactly once, after validation passes
- The prompt includes `buildConstraintBlock(bounds, locale, { fields: [...] })` with a fields subset (LLM-generated fields only, not structural ones like `eyebrow` that come from the article)

Flag if the dual-schema is sloppy or if the constraint block isn't actually consumed in the prompt.

### Task 6 — Cover-as-slide-variant verification

Per Marcel's decision in 60.0c Section C.2.1: cover is NOT a separate TemplateKey; it's a slide variant inside the existing template.

Confirm in the code:
- `TemplateKey` union does NOT include `"cover"` (still 5 templates)
- `single-tool-spotlight` registration in `social-render.worker.ts` is unchanged
- The cover content shape (`CoverProps`) is template-specific, not shared across all templates

Flag if cover leaked into being treated as a 6th template. (If yes, that's a problem — 60.2-60.5 each need their own cover variant, not a shared one.)

### Task 7 — Template-internal subcomponent pattern

Per 60.0b v2 Section C.6: `<DsScoreNumber>`, `<DsWinnerBadge>`, `<DsToolCard>` are explicitly NOT shared — they live inline per-template.

Read `shared/` subfolder in spotlight composition:
- `HeroTool.tsx`, `VerdictLine.tsx`, `StatsRow.tsx`, `BodyGrid.tsx`, `LivePill.tsx`
- Are these all reasonably scoped (each <100 lines)?
- Do they consume `tokens` props (not raw `brandTokens`)?
- Is there a clear boundary between what's in `shared/` (template-internal) vs what's in `ds-components/` (truly cross-template)?

Flag if the boundary is fuzzy or if any subcomponent looks like it should be promoted to `ds-components/` (and thus needs migration before 60.2).

### Task 8 — Fixture coverage audit

`fixtures.ts` should have `characteristic`, `edge-min`, `edge-max` (kebab-case per Memory #60). Each fixture should:
- Cover both cover content AND body content (or have separate cover/body fixture variants)
- Edge-min: shortest valid content per the prop schemas (3 strengths, 3 weaknesses, min-length strings)
- Edge-max: longest valid content (4 strengths, 4 weaknesses, max-length strings, longest tool name)
- All fixture content passes `coverPropsSchema.parse()` + `spotlightBodyPropsSchema.parse()`

Check the fixture file. Flag if edge-max actually pushes content to the declared maxes (vs. sitting comfortably below).

### Task 9 — Visual baseline coverage

For DS components: 11 baselines committed to `__baselines__/ds-components/` (per 60.0b v2 Section D.3). For the spotlight template: baselines gitignored per Memory #61.

Check:
- `__baselines__/ds-components/` has exactly 11 PNG files
- DS-component baselines render successfully when `RUN_VISUAL=1`
- Spotlight template baselines exist locally but are gitignored (or, equivalently, that `RUN_VISUAL=1 bun test single-tool-spotlight-visual` would generate them cleanly)

If any baseline-related file is missing or the test doesn't actually run, flag as Session 7 incomplete.

### Task 10 — Pattern transferability assessment

Final check: given the patterns above, estimate how much of `single-tool-spotlight/` could be copy-pasted into a new `comparison-grid-4/` folder as a starting skeleton. Answer:

1. **Files that copy verbatim**: e.g. `loadFonts.ts` (Inter Variable load is project-wide, not template-specific)
2. **Files that copy with rename**: e.g. dispatcher structure transfers, content varies
3. **Files that are 100% template-specific**: e.g. `shared/HeroTool.tsx` doesn't exist for comparison-grid-4 (which has `ToolCard`)
4. **Patterns that need promotion to shared**: anything in `shared/` that would be useful for 2+ templates

This gives Marcel a concrete answer to "how mechanical is 60.2 going to be?"
