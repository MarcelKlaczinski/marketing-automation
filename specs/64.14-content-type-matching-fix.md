# Spec 64.14 — ki-wissen Content-Type Matching: Full Fix (Overage Gate + Synthesizer + Manual Briefs)

_Fixes ki-wissen miss-classification aus Discovery 2026-05-23._  
_Status: Draft._  
_Voraussetzung: keine. Spec 64.11 läuft parallel (andere code-base, kein Konflikt). Anthropic planned_item bereits manuell cancelled._  
_Aufwand: ~5-7 Tage Implementation + ~1.5h Tests + ~30 Min manual verification._

---

## 1. Problem

Discovery 2026-05-23 hat den root-cause für "I've joined Anthropic" als ki-wissen identifiziert. Bug ist NICHT bei `matchBriefToContentType()` — Bug ist auf **overage path** in `select-overage-items.ts`.

### Smoking Gun

`packages/pipelines/src/planning/steps/select-overage-items.ts:49`:

```ts
export function inferContentTypeFromSignal(source: string): PlanningContentType | null {
  switch (source) {
    case "producthunt":      return "social_post";
    case "hackernews":       return "ki_wissen";       // ← every HN signal becomes ki_wissen
    case "reddit":           return "social_post";
    case "vendor_rss":       return "cluster";
    case "github":           return "ki_wissen";       // ← same for GitHub-trending
    case "dataforseo_trends":return "cluster";
    default:                 return null;
  }
}
```

30-Sekunden Heuristik. No intent inspection. No LLM gate. No quality filter.

### Empirical Evidence

| Metric | Value |
|---|---|
| Toolwiki briefs with intent_type='knowledge' | **0** (LLM hat NIE so klassifiziert) |
| Toolwiki ki_wissen planned items | **10 total** — 100% HN-overage origin |
| Implied HN→ki_wissen noise rate | **~85%** (3/20 HN titles legit ki-wissen material) |

### Wie "I've joined Anthropic" passierte

1. HN-collector queries enthalten "Anthropic" als single-word query (post-Spec 63.9)
2. Viraler Personal-Post über "joined Anthropic" wird collected mit hohen votes
3. Top-N scoring (raw votes+comments) ranked viralen Personal-Post hoch
4. `select-overage-items.ts` picked top-N → `inferContentTypeFromSignal("hackernews")` → "ki_wissen"
5. planned_item dropped direkt ohne brief, ohne LLM intent-check
6. Erscheint als ki_wissen im Plan

### Plus: Synthesizer Production Gap

Existing LLM-prompt in `trend-discovery/prompts.ts:50` HAT eine knowledge-classification rule:

> "knowledge — theme-centric explainers WITHOUT a tool focus. Concept questions ('Was ist RAG?'), pattern enumerations, evergreen practitioner guides..."

Aber **zero Toolwiki briefs** wurden je als intent_type='knowledge' classified. Possible causes:
- Signal pool ist HN/PH/RSS-heavy auf tools+launches, light auf concept-explainer material
- Few-shot examples biased to news/tutorial/use_case
- Coverage-check rejects knowledge topics (false-positive covered flag bei semantic similarity zu existing tool articles)

### Plus: No Manual Brief Creation Path

Marcel kann heute KEINEN brief manuell erstellen:
- `POST /briefs` endpoint existiert nicht
- `/briefs/new` page existiert nicht
- Briefs kommen NUR aus signal-driven sources (trend_discovery, gap_analysis, comparison_discovery, refresh_detection)

Wenn Marcel "Was ist RAG?" als ki-wissen article will, kann er es nicht direkt anlegen.

### Aus Discovery §5 (Cross-Collection Audit)

Plus: gleicher pattern in `github` → ki_wissen (currently 0 impact weil Toolwiki GitHub `enabled: false`, aber forward-compat-risk).

Plus: `producthunt` → social_post (10 items) — debattierbar ob PH-launches zu social_post oder comparison gehören. Smaller blast radius, nicht in dieser Spec scope.

## 2. Ziel

**Three-Phase Fix:**

**Phase A (Quick Win, 1 Tag):** Strip ki_wissen aus `inferContentTypeFromSignal` defaults. HN+GitHub → null (skip overage emission, signal weiterhin collected für synthesizer). Plus: per-project override-config falls Marcel later anderes mapping will.

**Phase B (Synthesizer Tuning, 1-2 Tage):** Audit warum LLM-synthesizer NIE knowledge-intent klassifiziert. Expand signal pool für concept-explainer material. Plus: tighten classifier prompts mit counter-examples. Real ki-wissen briefs from synthesizer.

**Phase C (Manual Brief Creation, 2-3 Tage):** Backend endpoint + Frontend page. Marcel curates ki-wissen wie tool entries — `topic_title` + `primary_keyword` + `collection_hint` form → `source='manual'` brief. Lands direkt in /briefs für approve.

import type { SignalSourceContentTypeMap } from "@marketing-auto/shared/types/project-config";

export const DEFAULT_SIGNAL_CONTENT_TYPE_MAP: SignalSourceContentTypeMap = {
  producthunt: "social_post",
  hackernews: null,         // ← FIXED: skip overage emission, signal still collected

  vendor_rss: "cluster",

export function inferContentTypeFromSignal(
  source: string,
  override: SignalSourceContentTypeMap | null = null,
): PlanningContentType | null {
  const effectiveMap = override ?? DEFAULT_SIGNAL_CONTENT_TYPE_MAP;
  return effectiveMap[source] ?? null;
}

### 3.2 Phase A — Migration

**File:** `apps/api/migrations/00XX_planner_config_signal_content_type_map.sql` (neu)

ALTER TABLE project_planner_config

COMMENT ON COLUMN project_planner_config.signal_source_content_type_map IS

**Decision-Rationale:**

### 3.4 Phase C — Manual Brief Creation (Backend)

**File:** `apps/api/src/routes/briefs.ts` — neuer endpoint

**Code Skeleton:**

```ts
// POST /api/projects/:slug/briefs
const ManualBriefCreateSchema = z.object({
  topicTitle: z.string().min(10).max(200),
  primaryKeyword: z.string().min(2).max(80),
  collectionHint: z.enum(["blog", "comparison", "ki-wissen", "cluster"]),
  intentType: z.enum([
    "knowledge", "tutorial", "use_case", "comparison",
    "review", "news", "best_practices", "alternatives", "pricing", "risks",
  ]).optional(),
  description: z.string().max(500).optional(),
});

app.post("/projects/:slug/briefs", async (c) => {
  const { slug } = c.req.param();
  const input = ManualBriefCreateSchema.parse(await c.req.json());
  
  const project = await getProjectBySlug(slug);
  if (!project) return c.json({ ok: false, error: "project_not_found" }, 404);
  
  // Derive intent_type from collection_hint if not explicit
  const intentType = input.intentType ?? deriveIntentFromCollection(input.collectionHint);
  
  // Derive cluster_action based on collection
  const clusterAction = input.collectionHint === "cluster" 
    ? "create_new" 
    : "standalone";
  
  const [brief] = await db.insert(topicBriefs).values({
    id: crypto.randomUUID(),
    projectId: project.id,
    topicTitle: input.topicTitle,
    primaryKeyword: input.primaryKeyword,
    intentType,
    clusterAction,
    clusterId: null,
    source: "manual",
    approvalStatus: "pending",
    sourceSignalIds: [],
    description: input.description ?? null,
  }).returning();
  
  return c.json({ ok: true, brief });
});

function deriveIntentFromCollection(
  collection: "blog" | "comparison" | "ki-wissen" | "cluster"
): IntentType {
  switch (collection) {
    case "comparison": return "comparison";
    case "ki-wissen":  return "knowledge";
    case "blog":       return "use_case";  // default; user can override
    case "cluster":    return "use_case";
  }
}
```

<script lang="ts">
import { defineComponent } from 'vue';
import { useBriefStore } from 'src/stores/brief';

export default defineComponent({
  name: 'BriefCreatePage',
  data: () => ({
    form: {
      topicTitle: '',
      primaryKeyword: '',
      collectionHint: 'ki-wissen' as const,
      intentType: 'knowledge' as const,
      description: '',
    },
  }),
  computed: {
    collectionOptions() {
      return [
        { value: 'ki-wissen', label: this.$t('briefs.collections.ki-wissen') },
        { value: 'blog', label: this.$t('briefs.collections.blog') },
        { value: 'comparison', label: this.$t('briefs.collections.comparison') },
        { value: 'cluster', label: this.$t('briefs.collections.cluster') },
      ];
    },
    intentOptions() {
      return [
        { value: 'knowledge', label: this.$t('briefs.intents.knowledge') },
        { value: 'tutorial', label: this.$t('briefs.intents.tutorial') },
        { value: 'use_case', label: this.$t('briefs.intents.use_case') },
        // ... rest
      ];
    },

    'form.collectionHint'(newCollection: string) {
      // Auto-derive intent_type when collection changes

        'comparison': 'comparison',

        'cluster': 'use_case',

  },

## 11. Memory-Update

Three patterns Marcel may want to save:

1. **"Signal-source → content_type mapping must NEVER be a hardcoded heuristic without an LLM intent gate"** — the pre-64.14 default produced ~85% off-topic noise on hackernews/github. Make new mappings opt-in via per-project jsonb override, and put `null` (skip) as the safe default for any source the synthesizer alone can handle. (DO-NOT rule for root CLAUDE.md.)
2. **"Synthesizer LLM classifier needs explicit counter-examples for news vs knowledge distinction"** — single-pass prompt with only positive examples ("knowledge = themes, not tools") let 22 trend_discovery briefs ship with zero `intent_type='knowledge'` over months. Adding 6 counter-examples + 6 positive examples is what closes the gap. Generalizable to any LLM classification step: when the production distribution shows a class is never picked, add counter-examples for the classes that pull from it.
3. **"manual brief creation: no new migration when `'manual'` already in CHECK"** — Memory D134 widening was already done in 0073. Phase 0 grep before writing migration sketches. (Not a new pattern per se — just a Phase-0 due-diligence reminder.)
