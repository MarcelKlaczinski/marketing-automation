# Spec 59.3-prep — Social Template Naming Refactor

**Theme:** 59 (Tier 3 Pre-Launch Foundation)
**Status:** Implemented (commits cbde72c + 41d04d6)
**Estimated effort:** 0.5 days (~3-4 hours, one session)
**Prerequisite:** None (immediate)
**Successor:** 59.3 pro-con-verdict template

---

## Goal

Rename the 4 existing social templates to remove the "stunning" suffix, which is redundant — **all** templates should be stunning by design (they exist to stop the scroll). The current naming bleeds an aspirational adjective into the technical key, making future templates feel second-class if they don't carry the "stunning" suffix, and making the keys longer than necessary.

After this prep lands, all 4 existing templates use semantic-only naming (describes what they are, not how they look), and 59.3-59.5 can adopt the same clean naming convention from the start.

## Non-Goals

- No new templates in this prep — pure renaming
- No visual/style changes — only key names
- No schema migrations — Drizzle types regenerate from string-union changes automatically
- No UI copy changes (display names stay descriptive in DE/EN)

---

## Background

Per audit `audit/social-templates-state.md` (Section 1), current TemplateKey union:

```typescript
// packages/social/src/templates/types.ts:18-26
export type TemplateKey =
  | "comparison-stunning"
  | "comparison-stunning-3"
  | "use-case-verdict-per-tool"
  | "single-tool-spotlight"
  | "news-slide"            // stub
  | "concept-explainer-deck" // stub
  | "price-comparison"       // stub
  | "pro-con-verdict";       // stub
```

**Issues:**
- "stunning" suffix on 2 of 4 implemented templates is redundant
- "comparison-stunning-3" leaks variant number into name — should be cleaner
- "use-case-verdict-per-tool" is verbose
- "single-tool-spotlight" is fine

**Mapping decisions** (semantic names that describe the FORMAT):

| Current Key | New Key | Rationale |
|---|---|---|
| `comparison-stunning` | `comparison-grid-4` | Format: 4-tool grid comparison |
| `comparison-stunning-3` | `comparison-grid-3` | Format: 3-tool grid (variant of grid-4 with different slot count) |
| `use-case-verdict-per-tool` | `verdict-per-use-case` | Format: per-use-case verdict cards |
| `single-tool-spotlight` | `single-tool-spotlight` | Already semantic, keep |
| `news-slide` | `news-slide` | Already semantic, keep |
| `concept-explainer-deck` | `concept-explainer-deck` | Already semantic, keep |
| `price-comparison` | `price-comparison` | Already semantic, keep |
| `pro-con-verdict` | `pro-con-verdict` | Already semantic, keep |

**Why not e.g. "comparison-4-tools" / "comparison-3-tools"?**
"grid" indicates the visual layout signature (4-up grid on cover), which is exactly what differentiates it in the Instagram grid. The number conveys variant differentiation.

**Naming convention going forward** (documented in `packages/social/CLAUDE.md`):

> Template keys describe **format/structure**, not **aspiration**. Use kebab-case. Patterns:
> - `<format>-<modifier>` (e.g., `comparison-grid-4`, `news-slide`)
> - `<role>-per-<unit>` (e.g., `verdict-per-use-case`)
> - `<scope>-<format>` (e.g., `single-tool-spotlight`)
>
> Avoid: aspirational adjectives (stunning, amazing, perfect), trend-coupled words ("2024", "modern", "latest"), and version numbers in the key itself (use variants via modifier).

### Fix 12 — Database migration for existing data

**File:** `packages/db/migrations/0xxx_rename_social_template_keys.sql`

UPDATE social_posts SET template_key = 'comparison-grid-4'
  WHERE template_key = 'comparison-stunning';

  WHERE template_key = 'use-case-verdict-per-tool';

**Idempotency check:** the migration is safe to re-run because once old keys are migrated, subsequent UPDATEs match zero rows.

**social_posts.content.renderInput** (per 58.2 snapshot pattern, Memory #41) may contain old template key strings in nested JSONB. Optional second pass:

```sql
-- Patch JSONB renderInput.templateKey if present (rare but defensive)
UPDATE social_posts
SET content = jsonb_set(
  content,
  '{renderInput,templateKey}',
  CASE content->'renderInput'->>'templateKey'
    WHEN 'comparison-stunning' THEN '"comparison-grid-4"'::jsonb
    WHEN 'comparison-stunning-3' THEN '"comparison-grid-3"'::jsonb
    WHEN 'use-case-verdict-per-tool' THEN '"verdict-per-use-case"'::jsonb
    ELSE content->'renderInput'->'templateKey'
  END
)
WHERE content ? 'renderInput'
  AND content->'renderInput' ? 'templateKey'
  AND content->'renderInput'->>'templateKey' IN (
    'comparison-stunning', 'comparison-stunning-3', 'use-case-verdict-per-tool'
  );
```

Idempotent same as above.

## Risk Mitigation

**R1: Existing social posts in production reference old keys via snapshot renderInput.**
- *Mitigation*: Fix 12 includes JSONB patch for `renderInput.templateKey`. After migration, snapshot re-render still works.

**R2: Renaming Composition `id` in `index.tsx` breaks Remotion lookup.**
- *Mitigation*: Composition `id` and render-server's `getCompositions()` lookup must change together — this is part of Fix 7 + 8. Manual smoke test validates.

**R3: Frontend has dropdown with old keys, user-selected.**
- *Mitigation*: Fix 13 sweeps frontend references. SDK regen after backend type changes ensures TypeScript catches missed sites.

**R4: External integrations (none currently) reference old keys via API.**
- *Mitigation*: N/A for toolwiki solo-dev environment. No external API consumers.

**R5: Migration runs before code deploy → mismatch.**
- *Mitigation*: Standard deploy flow — code deploy precedes migration via `bun run migrate`. Or: run migration last (after code deploy), since old keys still match in old code (transient inconsistency for ~30s during deploy). For solo-dev: acceptable.

## Deviations from Spec

**Fix 9 — worker switch case for `verdict-per-use-case`**: The spec described adding `case "verdict-per-use-case": return renderVerdictPerUseCase(...)` to the worker switch. The actual worker never had a `verdict-per-use-case` case before this PR (the old `renderUseCaseVerdictCarousel` was also absent from the switch). Wiring `verdict-per-use-case` render into the BullMQ worker is deferred to whichever spec adds the verdict pipeline trigger.

**Fix 10 — `comparisonStunning3.fixtures.ts` did not exist**: The spec assumed both grid-3 and grid-4 had separate fixture files. In reality only `comparisonStunning.fixtures.ts` existed and served both templates. After rename, both `comparison-grid-3` and `comparison-grid-4` continue to import from `comparisonGrid4.fixtures.ts`. No `comparisonGrid3.fixtures.ts` was created.

**Fix 7 — render function name discrepancy**: The spec calls the pre-rename function `renderUseCaseVerdictPerTool` but the actual codebase had `renderUseCaseVerdictCarousel`. Target name `renderVerdictPerUseCase` was applied correctly regardless.

**Export naming — `*Template` not `*Definition`**: The spec uses `*Definition` suffix (e.g. `comparisonGrid4Definition`) but the implementation uses `*Template` suffix (e.g. `comparisonGrid4Template`) — consistent with the existing `singleToolSpotlightTemplate` convention in the codebase.
