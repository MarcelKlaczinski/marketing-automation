**Date:** 2026-05-19
**Theme:** 61 — Article Generator Variants
**Prerequisite:** 60.7 done
**Estimated effort:** ~0.5 day

## TL;DR

Single focused change: remove the `collectionName: z.literal("blog")` hardcode
from `RenderMdxStep` and replace it with a proper `collection_type` enum that
flows through the pipeline from brief → DB → render. No new content types yet —
that's 61.2 and 61.3. This spec only lays the foundation so those specs don't
hit a wall.

## Session 1 — DB: `collection_type` Enum

### 1.1 Current state

`articles.collection_type` column exists (confirmed in discovery) but is always
set to `"blog"` — hardcoded in `PersistArticleStep`.

### 1.2 Migration

```sql
-- Migration: 0065_collection_type_enum.sql

-- Create enum (Postgres native, Drizzle pgEnum)
CREATE TYPE article_collection_type AS ENUM (
  'blog',
  'comparison',
  'ki-wissen',
  'tools',
  'usecases'
);

-- Add new typed column alongside existing text column
ALTER TABLE articles
  ADD COLUMN collection_type_enum article_collection_type NOT NULL DEFAULT 'blog';

-- Backfill from existing text column
UPDATE articles
  SET collection_type_enum = collection_type::article_collection_type
  WHERE collection_type IN ('blog','comparison','ki-wissen','tools','usecases');

-- Drop old text column, rename new one
ALTER TABLE articles DROP COLUMN collection_type;
ALTER TABLE articles RENAME COLUMN collection_type_enum TO collection_type;
```

> **Note:** If the existing `collection_type` column is already typed differently
> or named differently in the actual schema, adjust accordingly. Run
> `SELECT column_name, data_type FROM information_schema.columns WHERE table_name = 'articles' AND column_name LIKE '%collection%'`
> before writing the migration.

### 1.3 Drizzle schema

```typescript
// packages/db/src/schema/content.ts

export const articleCollectionTypeEnum = pgEnum('article_collection_type', [
  'blog',
  'comparison',
  'ki-wissen',
  'tools',
  'usecases',
]);

// In articles table definition:
collectionType: articleCollectionTypeEnum('collection_type')
  .notNull()
  .default('blog'),
```

### 1.4 Shared type export

```typescript
// packages/shared/src/types/article-collection.ts

export const ARTICLE_COLLECTION_TYPES = [
  'blog',
  'comparison',
  'ki-wissen',
  'tools',
  'usecases',
] as const;

export type ArticleCollectionType = typeof ARTICLE_COLLECTION_TYPES[number];

export function isArticleCollectionType(v: unknown): v is ArticleCollectionType {
  return ARTICLE_COLLECTION_TYPES.includes(v as ArticleCollectionType);
}
```

Export from `packages/shared/src/index.ts`.

## Session 3 — RenderMdxStep: remove hardcode

This is the core fix. Find and remove:

```typescript
// BEFORE (hardcoded):
collectionName: z.literal("blog")
// or:
collection: "blog"
// or wherever the literal appears in render-mdx.ts / assemble-mdx.ts
```

Replace with:

```typescript
// AFTER:
collectionName: ctx.brief.collectionType ?? 'blog',
```

### 3.1 Find the hardcode

```bash
grep -rn '"blog"\|literal.*blog\|collection.*blog' \
  packages/pipelines/src/article/ --include="*.ts" | grep -v test | grep -v node_modules
```

Paste results before making changes — there may be more than one occurrence.

### 3.2 Astro collection → folder mapping

The rendered MDX file must land in the correct Astro content folder:

```typescript
// packages/pipelines/src/article/steps/render-mdx.step.ts

const COLLECTION_FOLDER: Record<ArticleCollectionType, string> = {
  'blog':        'blog',
  'comparison':  'comparisons',   // Astro collection name from discovery
  'ki-wissen':   'ki-wissen',
  'tools':       'tools',
  'usecases':    'usecases',
};

const folder = COLLECTION_FOLDER[collectionType];
// MDX output path: src/content/{folder}/de/{slug}.mdx
```

> listing before hardcoding.** The discovery confirmed `comparisons` (plural)
> and `ki-wissen` (with hyphen) — but double-check.

## Section — Patterns Established by 61.1

**(106) `collectionType` flows from `BlogPipelineInput` (not `ctx.brief`) through
the pipeline bridge into `PersistArticleStep` input. The bridge conditionally spreads
`collectionType` when present: `if (pipelineInput.collectionType) { return { ...base, collectionType: pipelineInput.collectionType }; }`.
Never read it from the DB mid-pipeline — the pipeline input is the source of truth for
the current run. DB value is the persisted result.**

**(107) `COLLECTION_FOLDER` map is the single source of truth for
`ArticleCollectionType → Astro content folder` mapping. Always look it up here —
never inline the folder name at the call site.**

## Section — Deviations from Original Spec

1. **`ctx.brief.collectionType` does not exist** — `ArticleBrief` is a DB entity (`TopicBrief`)
   managed by `TopicRoutingPolicy`, not a pipeline-level object. `collectionType` was added to
   `BlogPipelineInput` (the HTTP-layer input type) instead and flows into steps via the bridge.
   Pattern 106 updated accordingly.

2. **`ArticleBrief` interface not extended** — The spec proposed extending
   `packages/pipelines/src/article/types.ts`. In reality `ArticleBrief` as a pipeline type does
   not exist; `BlogPipelineInput` (defined inline in `pipeline.ts`) is the canonical pipeline input
   type. No separate types file was needed.

3. **`blog/persist.ts` and `trigger.ts` `collection: "blog"` not changed** — These write
   `articles.collection` (the Astro folder text column used for routing), not `articles.collection_type`
   (the new enum). These two columns are separate concerns. `collection` stays `"blog"` for all
   articles in 61.1 — acceptable since `collectionType` drives the `COLLECTION_FOLDER` MDX routing
   in `RenderMdxStep`. Changing `collection` will happen in 61.2/61.3.

4. **`collectionType: z.string()` not `.optional().default("blog")`** — Using `.default("blog")`
   on a field inside a nested Zod object in a step's `inputSchema` makes `_input` become
   `string | undefined` while `_output` stays `string`. `BaseStep<TInput, TOutput>` requires
   `inputSchema: ZodType<TInput>`, which fails with TS2416 due to this `_input`/`_output` variance.
   Fix: used `z.string()` (non-optional, no default) because `LoadArticleStep` always provides a
   non-null string from the DB enum column (NOT NULL DEFAULT 'blog'). See Discovered section below.

## Section — Discovered During Implementation

**Zod `.default()` on nested fields causes TS2416 on `inputSchema`**

Using `.default(value)` on any field inside a nested `z.object({...})` in a step's `inputSchema`
makes `_input` become `T | undefined` while `_output` stays `T`. `BaseStep<TInput, TOutput>` has the
constraint `inputSchema: ZodType<TInput>`, which fails at the outer schema level because the nested
field's `_input` doesn't match.

There are two fixes depending on context:
- If the upstream step guarantees the value is always present (e.g. a `NOT NULL DEFAULT 'blog'` DB
  column read by `LoadArticleStep`): use `z.string()` without `.optional()` or `.default()`.
- If the field is truly optional: use `z.string().optional()` (no default) and handle `undefined`
  in `execute()` with `?? "blog"`.

The cast-alias pattern (`const InputSchema = _schema as z.ZodType<TInput>`) also works as a last
resort when you need the default for resilience (e.g., LLM output fields). See `packages/pipelines/CLAUDE.md`
for the canonical pattern.
