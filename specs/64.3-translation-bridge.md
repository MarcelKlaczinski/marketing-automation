## 1. Problem

Bug #3 ist eigentlich **drei Sub-Bugs** im Translation-Bridge (`packages/pipelines/src/article/translation/pipeline.ts:184-231`), die alle aus einer Quelle stammen: die Bridge propagiert sprach-spezifische Felder vom DE-Source verbatim zum EN-Translation-Sibling.

### Affected Articles (verified Toolwiki, Discovery Phase 1)

| Sub-Bug | Affected | Severity |
|---|---|---|
| #3a heroImageAltText DE-suffix auf EN | 6 articles | SEO + Accessibility |
| #3b schema_json_ld[Article].description DE | 5 articles | SEO-Schaden (mixed-language signal) |
| #3c schema_json_ld[Article].mainEntityOfPage.@id DE canonical | 5 articles | **SEO-CRITICAL** (wrong canonical signal) |

Note: nach Cleanup-Migration (Reset) sind alle 6/5/5 affected articles weg → der Fix muss **prevent recurrence** für künftige Translation-Runs, nicht historische Daten cleanen.

### 3.4 Shared Canonical-URL Helper (neu — Marcel-Decision 2026-05-23)

**File:** `packages/pipelines/src/article/lib/canonical-url.ts` (neu, isoliert)

**Begründung:** Zwei call-sites (`assembly.ts:46-49` für DE hot path + `translation/pipeline.ts:198` für EN translation bridge) brauchen exakt dieselbe URL-Construction. Wenn beide hardcoded `/blog/` haben (Tech-Debt) oder beide explicit collection-aware sind (clean), muss das synchron sein. Helper-File ist hier the right call weil:
- 2 call-sites mit identischer Logic
- Plus: collection mapping vorhanden in `COLLECTION_ASTRO_NAME` (existing constant — Phase 0 muss verifizieren wo)
- Plus: zukünftig könnten weitere Pipelines URLs bauen (z.B. social-image generation, refresh-pipeline)

```ts
// packages/pipelines/src/article/lib/canonical-url.ts
import type { Locale } from "../translation/lib/locale-strings";
// COLLECTION_ASTRO_NAME from existing constant location (Phase 0 finds)

export interface CanonicalUrlInput {
  projectDomain: string;        // z.B. "toolwiki.ai" — without protocol, without trailing slash
  locale: Locale;
  collection: string;           // 'blog' | 'tools' | 'comparisons' | etc.
  slug: string;
}

/**
 * Build canonical article URL for schema.org + frontend routing.
 * Mirrors Astro routing convention: https://{domain}/{locale}/{collection-astro-name}/{slug}
 */
export function buildCanonicalUrl(input: CanonicalUrlInput): string {
  const collectionPath = COLLECTION_ASTRO_NAME[input.collection] ?? input.collection;
  return `https://${input.projectDomain}/${input.locale}/${collectionPath}/${input.slug}`;
}
```

**Decision:** als shared helper statt inline weil:
- Eliminiert die hardcoded-`/blog/` Tech-Debt in assembly.ts (Marcel: "kein tech debt")
- Single source of truth für canonical URL convention
- COLLECTION_ASTRO_NAME existing constant handles collection→path mapping (z.B. wenn 'comparisons' im Astro `/vergleiche/` heißt)
- Plus: easy testable in isolation

**Assembly.ts Patch (existing hot path):**

```ts

  "@type": "WebPage",

// NACHHER:

```

**Translation-Bridge Patch (siehe §3.2):** nutzt auch `buildCanonicalUrl()` für target-locale URL.

**Test:** isolated unit-test für buildCanonicalUrl mit allen collections:

```ts
describe("buildCanonicalUrl", () => {
  it("produces collection-aware path for blog", () => {
    expect(buildCanonicalUrl({
      projectDomain: "toolwiki.ai",
      locale: "de",
      collection: "blog",
      slug: "test",
    })).toBe("https://toolwiki.ai/de/blog/test");
  });
  
  it("uses COLLECTION_ASTRO_NAME for comparisons", () => {
    // assuming COLLECTION_ASTRO_NAME["comparisons"] === "vergleiche"

      projectDomain: "toolwiki.ai",
```
