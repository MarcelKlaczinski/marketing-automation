## Goal

Build the three content surface views needed for Marcel to answer "where are we, what's the backlog, and where do I need to act":

1. **Articles View** — list + detail. Sees imported MDX + generated articles. Inline Markdown editor for content fixes. Tabs for body / frontmatter / versions / runs / cost.

2. **Briefs View** — backlog management. 3-section layout (Pending / In-Flight / Done) prioritized by trend score. Bulk-approve / bulk-dismiss for fast backlog clearance.

3. **Clusters View** — list + special detail page. Cluster Detail shows Hub prominent + Spoke grid + retry-buttons for failed spokes (matching user's "zur not jobs neustarten" requirement).

After this spec lands, Marcel can:
- Browse all 272 articles, filter by status/collection/locale, drill into any one
- Edit article body_md inline (Markdown editor) and save → triggers Astro sync
- See his full brief backlog at a glance, bulk-approve top trends
- Inspect any cluster's generation state, retry failed spokes directly

What's still missing after 56.2: Settings, Costs, Products views (56.3). Cold-Start (56.4). Bulk-retry for pipeline runs (post-56.x backlog).

## What this is NOT

- Not redesigning Settings / Costs / Products — that's 56.3

## Section A: Backend Additions

### A.1 Bulk-approve briefs

**Endpoint**: `POST /api/projects/:slug/briefs/bulk-approve`

**Use case**: Marcel selects 5 pending trend briefs in the Briefs View, clicks "Approve selected". Each gets approved + enqueued.

**Implementation**:

```typescript
// apps/api/src/routes/projects/briefs-bulk.ts (new file)

const bulkApproveSchema = z.object({
  briefIds: z.array(z.string().uuid()).min(1).max(50),
  mode: z.enum(["assist", "auto"]).default("assist"),
});

async function handleBulkApprove(c: Context) {
  const { slug } = c.req.param();
  const { briefIds, mode } = bulkApproveSchema.parse(await c.req.json());
  
  const project = await loadProjectBySlug(slug);
  if (!project) return c.json({ ok: false, error: "project_not_found" }, 404);
  
  const results = {
    approved: [] as Array<{ briefId: string; runId: string; jobId: string }>,
    skipped: [] as Array<{ briefId: string; reason: string }>,
    failed: [] as Array<{ briefId: string; error: string }>,
  };
  
  // Process each brief; errors don't halt the batch
  for (const briefId of briefIds) {
    try {
      const [brief] = await db.select().from(topicBriefs)
        .where(and(
          eq(topicBriefs.id, briefId),
          eq(topicBriefs.projectId, project.id),
        ))
        .limit(1);
      
      if (!brief) {
        results.skipped.push({ briefId, reason: "not_found" });
        continue;
      }
      
      if (brief.approvalStatus !== "pending") {
        results.skipped.push({ briefId, reason: `already_${brief.approvalStatus}` });
        continue;
      }
      
      // Reuse existing single-approve logic from trends.ts handleApprove
      const result = await approveBriefAndEnqueue({
        brief,
        project,
        mode,
      });
      
      if (result.kind === "cluster_assignment_required") {
        results.skipped.push({ briefId, reason: "cluster_assignment_required" });
      } else if (result.kind === "success") {
        results.approved.push({
          briefId,
          runId: result.runId,
          jobId: result.jobId,
        });
      } else {
        results.failed.push({ briefId, error: result.error });
      }
    } catch (err) {
      results.failed.push({ 
        briefId, 
        error: err instanceof Error ? err.message : "unknown_error" 
      });
    }
  }
  
  return c.json({
    ok: true,
    data: {
      total: briefIds.length,
      approvedCount: results.approved.length,
      skippedCount: results.skipped.length,
      failedCount: results.failed.length,
      results,
    },
  }, 202);
}
```

**Key behaviors**:
- Sequential processing (not parallel) — predictable cost ordering, easier to debug
- Errors don't halt batch — one failed brief doesn't block others
- `create_new` briefs return `cluster_assignment_required` in skipped (per 54.5.1 pattern)
- Returns 202 (async) since pipelines are enqueued

### A.2 Bulk-dismiss briefs

**Endpoint**: `POST /api/projects/:slug/briefs/bulk-dismiss`

Mirror of bulk-approve but marks briefs as `dismissed`. Simple — no pipeline enqueueing.

```typescript
async function handleBulkDismiss(c: Context) {
  const { slug } = c.req.param();
  const { briefIds } = bulkDismissSchema.parse(await c.req.json());
  
  const project = await loadProjectBySlug(slug);
  if (!project) return c.json({ ok: false, error: "project_not_found" }, 404);
  
  const result = await db.update(topicBriefs)
    .set({
      approvalStatus: "dismissed",
      dismissedAt: new Date(),
    })
    .where(and(
      eq(topicBriefs.projectId, project.id),
      inArray(topicBriefs.id, briefIds),
      eq(topicBriefs.approvalStatus, "pending"),  // only dismiss pending
    ))
    .returning({ id: topicBriefs.id });
  
  return c.json({
    ok: true,
    data: {
      requested: briefIds.length,
      dismissed: result.length,
      skipped: briefIds.length - result.length,
    },
  });
}
```

### A.3 Cursor pagination on articles list

**Endpoint**: `GET /api/projects/:slug/articles` (existing, extended)

Per 55.1 D.1: list endpoints use offset+limit. Articles list with 272+ entries benefits from cursor pagination for "Load More" UX.

**Add cursor variant**:

```typescript
const articlesListSchema = z.object({
  // Existing
  status: z.string().optional(),
  collection: z.string().optional(),
  locale: z.enum(["de", "en"]).optional(),
  search: z.string().min(2).optional(),
  
  // Pagination — support BOTH patterns
  limit: z.coerce.number().int().min(1).max(100).default(20),
  // Cursor-based (new — preferred for Load More)
  cursor: z.string().datetime().optional(),
  // Offset-based (kept for backward compat)
  offset: z.coerce.number().int().min(0).optional(),
});

async function handleArticlesList(c: Context) {
  const project = await resolveProject(c);
  const params = articlesListSchema.parse(c.req.query());
  
  const conditions = [eq(articles.projectId, project.id)];
  
  if (params.status) conditions.push(eq(articles.status, params.status));
  if (params.collection) conditions.push(eq(articles.collection, params.collection));
  if (params.locale) conditions.push(eq(articles.locale, params.locale));
  if (params.search) {
    const pattern = `%${params.search}%`;
    conditions.push(or(
      ilike(articles.title, pattern),
      ilike(articles.slug, pattern),
      ilike(articles.cornerstoneKeyword, pattern),
    )!);
  }
  
  if (params.cursor) {
    // Cursor-based: items strictly older than cursor
    conditions.push(lt(articles.updatedAt, new Date(params.cursor)));
  }
  
  const items = await db.select().from(articles)
    .where(and(...conditions))
    .orderBy(desc(articles.updatedAt))
    .limit(params.limit + 1);  // +1 to determine hasMore
  
  const hasMore = items.length > params.limit;
  const returnItems = hasMore ? items.slice(0, params.limit) : items;
  const nextCursor = hasMore 
    ? returnItems[returnItems.length - 1].updatedAt.toISOString()
    : null;
  
  return c.json({
    ok: true,
    data: {
      items: returnItems,
      nextCursor,
      hasMore,
      limit: params.limit,
    },
  });
}
```

Same pattern applied to:
- `GET /api/projects/:slug/clusters` — cursor on `updatedAt`
- `GET /api/projects/:slug/briefs` — sorted by trend score for pending, by createdAt for others

### A.4 Briefs list with 3-section grouping

**Endpoint**: `GET /api/projects/:slug/briefs?section=`

The Briefs View has 3 sections (Pending / InFlight / Done). One endpoint supports filtering by section:

```typescript
const briefsListSchema = z.object({
  section: z.enum(["pending", "in-flight", "done", "all"]).default("all"),
  limit: z.coerce.number().int().min(1).max(100).default(50),
  cursor: z.string().datetime().optional(),
});

async function handleBriefsList(c: Context) {
  const project = await resolveProject(c);
  const params = briefsListSchema.parse(c.req.query());
  
  const conditions = [eq(topicBriefs.projectId, project.id)];
  
  // Section maps to approval_status sets
  if (params.section === "pending") {
    conditions.push(eq(topicBriefs.approvalStatus, "pending"));
  } else if (params.section === "in-flight") {
    conditions.push(inArray(topicBriefs.approvalStatus, ["approved", "routed"]));
  } else if (params.section === "done") {
    conditions.push(inArray(topicBriefs.approvalStatus, ["dismissed", "completed"]));
  }
  
  // Sorting depends on section
  // Pending: by trend score descending (highest priority first)
  // Others: by createdAt descending
  const orderBy = params.section === "pending"
    ? [desc(sql`COALESCE(${topicBriefs.trendMetadata}->'scoreBreakdown'->>'total', '0')::numeric`), desc(topicBriefs.createdAt)]
    : [desc(topicBriefs.createdAt)];
  
  if (params.cursor) {
    conditions.push(lt(topicBriefs.createdAt, new Date(params.cursor)));
  }
  
  const items = await db.select().from(topicBriefs)
    .where(and(...conditions))
    .orderBy(...orderBy)
    .limit(params.limit + 1);
  
  const hasMore = items.length > params.limit;
  const returnItems = hasMore ? items.slice(0, params.limit) : items;
  const nextCursor = hasMore
    ? returnItems[returnItems.length - 1].createdAt.toISOString()
    : null;
  
  return c.json({
    ok: true,
    data: {
      section: params.section,
      items: returnItems,
      nextCursor,
      hasMore,
    },
  });
}
```

```vue
<template>

        v-for="filter in availableFilters"
        :key="filter.key"
        :label="filter.label"
        :active="!!activeFilters[filter.key]"
        :options="filter.options"
        :value="activeFilters[filter.key]"
        @change="onFilterChange(filter.key, $event)"
      />
    </div>
    
    <div class="filter-bar-actions">
      <GlassButton
        v-if="hasActiveFilters"
        variant="ghost"

      >
        {{ $t("common.clearFilters") }}
      </GlassButton>

  </div>

<script lang="ts">
import { defineComponent, PropType } from "vue";

/**
 * Reusable filter bar.
 * Wires search + filters into a consistent pattern.
 * Emits `update:filters` whenever any filter changes.
 */
export default defineComponent({
  name: "FilterBar",
  emits: ["update:filters", "update:search"],
  props: {
    availableFilters: {
      type: Array as PropType<FilterDefinition[]>,
      required: true,
    },
    activeFilters: {
      type: Object as PropType<Record<string, string>>,
      default: () => ({}),
    },
    search: { type: String, default: "" },
  },
  data: () => ({
    searchInput: "",
    searchDebounceTimer: null as ReturnType<typeof setTimeout> | null,
  }),
  computed: {
    hasActiveFilters(): boolean {
      return Object.values(this.activeFilters).some(v => !!v) || this.searchInput.length > 0;
    },
  },
  watch: {
    search: {
      immediate: true,
      handler(newVal: string) {
        this.searchInput = newVal;
      },
    },
  },
  methods: {
    onSearchInput(): void {
      if (this.searchDebounceTimer) clearTimeout(this.searchDebounceTimer);
      this.searchDebounceTimer = setTimeout(() => {
        this.$emit("update:search", this.searchInput);
      }, 300);
    },
    onFilterChange(key: string, value: string): void {
      this.$emit("update:filters", { ...this.activeFilters, [key]: value });
    },
    clearFilters(): void {
      this.searchInput = "";
      this.$emit("update:search", "");
      this.$emit("update:filters", {});
    },
  },
});
</script>
```

### C.2 useArticlesList composable

```typescript
// apps/web/src/composables/useArticlesList.ts
import { ref, computed, watch } from "vue";
import { useInfiniteQuery } from "@tanstack/vue-query";
import { useProjectStore } from "@/stores/project";

interface ArticlesListFilters {
  status?: string;
  collection?: string;
  locale?: "de" | "en";
  search?: string;
}

/**
 * Composable for paginated articles list with filters.
 * Uses TanStack Query infinite query for cursor pagination.
 */
export function useArticlesList(initialFilters: MaybeRef<ArticlesListFilters> = {}) {
  const projectStore = useProjectStore();
  const filters = ref(unref(initialFilters));
  
  const query = useInfiniteQuery({
    queryKey: computed(() => ["articles", projectStore.currentSlug, filters.value]),
    queryFn: async ({ pageParam }) => {
      return apiClient.articles.list({
        slug: projectStore.currentSlug,
        ...filters.value,
        cursor: pageParam,
        limit: 20,
      });
    },
    initialPageParam: undefined as string | undefined,
    getNextPageParam: (lastPage) => lastPage.data.nextCursor ?? undefined,
  });
  
  const articles = computed(() =>
    query.data.value?.pages.flatMap(p => p.data.items) ?? []
  );
  
  const hasMore = computed(() => 
    !!query.data.value?.pages[query.data.value.pages.length - 1]?.data.hasMore
  );
  
  return {
    articles,
    hasMore,
    isLoading: query.isLoading,
    isFetchingMore: query.isFetchingNextPage,
    loadMore: query.fetchNextPage,
    refetch: query.refetch,
    filters,
  };
}
```

<script lang="ts">
import { defineComponent, PropType } from "vue";
import { EditorView, basicSetup } from "codemirror";
import { EditorState } from "@codemirror/state";
import { markdown } from "@codemirror/lang-markdown";
import { oneDark } from "@codemirror/theme-one-dark";

export default defineComponent({
  name: "ArticleBodyTab",
  emits: ["save"],
  props: {
    article: { type: Object as PropType<Article | null>, required: true },
  },
  data: () => ({
    editor: null as EditorView | null,
    currentValue: "",
    originalValue: "",
    saving: false,
  }),
  computed: {
    isDirty(): boolean {
      return this.currentValue !== this.originalValue;
    },
    wordCount(): number {
      return this.currentValue.trim().split(/\s+/).filter(Boolean).length;
    },
    charCount(): number {
      return this.currentValue.length;
    },
  },
  mounted() {
    this.initEditor();
  },
  beforeUnmount() {
    this.editor?.destroy();
  },
  watch: {
    "article.id": {
      handler() { this.initEditor(); },
    },
  },
  methods: {
    initEditor(): void {
      this.editor?.destroy();
      
      const initialDoc = this.article?.bodyMd ?? "";
      this.originalValue = initialDoc;
      this.currentValue = initialDoc;
      
      const state = EditorState.create({
        doc: initialDoc,
        extensions: [
          basicSetup,
          markdown(),
          oneDark,
          EditorView.updateListener.of((update) => {
            if (update.docChanged) {
              this.currentValue = update.state.doc.toString();
            }
          }),
          EditorView.theme({
            "&": { 
              height: "100%",
              fontSize: "14px",
              fontFamily: "var(--font-mono)",
            },
            ".cm-content": { padding: "16px" },
            ".cm-focused": { outline: "none" },
          }),
        ],
      });
      
      const editorEl = this.$refs.editorEl as HTMLElement;
      this.editor = new EditorView({
        state,
        parent: editorEl,
      });
    },
    onCancel(): void {
      this.editor?.dispatch({
        changes: {
          from: 0,
          to: this.editor.state.doc.length,
          insert: this.originalValue,
        },
      });
    },
    async onSave(): Promise<void> {
      this.saving = true;
      try {
        this.$emit("save", { bodyMd: this.currentValue });
        this.originalValue = this.currentValue;
      } finally {
        this.saving = false;
      }
    },
  },
});

## Decisions Made

**Decision 1: Master-detail in URL pattern for Articles + Briefs (Q10c).**
URLs like `/articles/art_abc` keep list visible left, detail right. Deep-linkable. Linear-style.

**Decision 2: Clusters Detail is full-page, NOT master-detail.**
Cluster Detail needs more space — Hub prominent, Spoke grid, Plan, Cost, Runs. Doesn't fit beside a list. Cluster List is a separate view.

**Decision 3: Articles Detail has 5 tabs.**
Body / Frontmatter / Versions / Runs / Cost. Default tab is Body. Each tab is lazy-loaded.

**Decision 4: CodeMirror 6 for Markdown editor.**
Lightweight, native MD highlighting, works with Options API. Monaco rejected as too heavy. Tiptap rejected as overkill for technical content.

**Decision 5: Briefs View uses 3-section layout (not standard list).**
Pending / In-Flight / Done. Pending sorted by trend score descending. Matches Marcel's mental model of "today's queue".

**Decision 6: Bulk endpoints in 56.2 (per user preference).**
Briefs bulk-approve and bulk-dismiss. Matches real workflow (16 trend briefs to triage at once).

**Decision 7: Sequential bulk processing.**
Not parallel. Predictable cost ordering, easier debugging, prevents cost-limit overshoot.

**Decision 8: Failed spoke Retry button is prominent.**
Per user's "zur not jobs neustarten" — Retry button is direct, on the spoke card itself, not buried in pipeline-run-detail.

**Decision 9: Plan editing is API-only (per 54.12 Decision 5).**
56.2 displays the plan read-only. Editing via PATCH /plan/spokes is documented but not in UI. Phase E adds inline edit.

**Decision 10: Cluster Detail is the heaviest page in 56.2.**
By design — clusters are the highest-value unit of content production. Hub + Spokes + Plan + Cost + Runs all visible.

**Decision 11: Cursor pagination, not offset.**
Cursor on updatedAt for articles/clusters, createdAt for briefs. "Load More" button (not infinite scroll). Per 55.1 D.1.

**Decision 12: 3 entity card types share base style.**
ArticleCard, BriefCard, ClusterCard all extend GlassCard. ~120px height. Consistent visual language.

**Decision 13: FilterBar component reusable across 3 views.**
Same filter chip style + search input + clear button. Reduces duplication.

**Decision 14: Sidebar badges show live counts via project-picker endpoint.**
Already exists in 55.1. No new endpoint needed for sidebar counts.

**Decision 15: Existing single-action endpoints reused for bulk operations.**
Bulk-approve calls existing per-brief logic in a loop. Not a new bulk pipeline. Safer.

## Discovered During Implementation

### Options API composable extraction pattern (Sessions 5–7)
The spec said "Options API only" but did not spell out that module-level helper functions defined inside a `.vue` file that call Composition API primitives are equally a violation. Two violations were caught during `/review-task`:

1. **`useBriefSection`** — defined at module level inside `BriefsPage.vue`. Calling `computed()` + `useInfiniteQuery()` inside a module-level function is not automatically valid just because the function is called from `setup()`. Had to extract to `src/composables/useBriefsSection.ts`.

2. **`ClustersListPage.vue`** — called `ref()`, `computed()`, `useInfiniteQuery()` inline in `setup()`. Had to extract to `src/composables/useClustersList.ts`.

Rule: any function that calls Composition API primitives must live in `src/composables/useXxx.ts`.

### Static queryKey for route-mounted components
Route-mounted components (pages) receive route params that are static for the component's lifetime — Vue Router remounts the component when params change. Therefore `computed(() => route.params.articleId)` inside `setup()` is both a Composition API violation AND unnecessary. Pattern used throughout tabs: `const articleId = route.params.articleId as string` (plain string as TanStack Query key).

### `exactOptionalPropertyTypes` + conditional filter objects
When calling `setFilters()` on a composable whose filter type has optional string fields (e.g. `ClustersListFilters.generationStatus?: string`), building the object as `{ generationStatus: someValue | undefined }` is a TS error under `exactOptionalPropertyTypes`. Must build conditionally:
```typescript
const f: ClustersListFilters = {};
if (newFilters.status) f.generationStatus = newFilters.status;
this.setFilters(f);
```

### i18n violations caught in review (Session 7 `/review-task`)

Four violations of the "no hardcoded user-visible strings" rule were found and fixed:

1. **`ArticleDetailPage.vue`** — `STATUS_LABEL` map had English strings (`"Proposed"`, `"Generating"`, etc.) instead of i18n key paths. Fix: changed values to `"articles.status.proposed"` etc. and added `$t()` call in computed.

2. **`ClusterDetailPage.vue`** — same `STATUS_LABELS` map pattern with English strings. Fix: changed to `"clusters.generationStatus.*"` key paths + `$t()`.

3. **`BriefDetailPage.vue`** — `{{ brief.approvalStatus }}` rendered raw enum value in the status chip eyebrow. Fix: added `approvalStatusLabel` computed using dynamic key construction (`$t(\`briefs.approvalStatus.${status}\`)`), added `briefs.approvalStatus.*` i18n keys.

4. **`ArticlesListPage.vue`** — collection and locale filter option labels were hardcoded (`"Blog"`, `"Tools"`, `"DE"`, `"EN"`). Fix: added `articles.filters.collections.*` and `articles.filters.locales.*` i18n keys, wrapped in `$t()`.

**Root cause**: it's easy to write English strings in a `Record<string, string>` map and miss that they need to be i18n key paths, not translated text. The rule exists in `apps/web/CLAUDE.md` but was violated anyway — the two-step pattern (map → key path → `$t()` in computed) must be internalized.

## Discovered During Implementation

### 1. `brief.source` and `brief.clusterAction` require i18n translation
Both are DB enums (`gap_analysis`, `trend_discovery`, `refresh_detection`, `manual` and `create_new`, `append_to_existing`, `translation`, `refresh`, `standalone`). Initial implementation rendered them raw in `BriefCard.vue` and `BriefDetailPage.vue` mono spans. Fixed in review by adding `briefs.source.*` and `briefs.clusterAction.*` i18n keys and using Pattern B (`$t(\`briefs.source.${brief.source}\`)`). Added rule to `apps/web/CLAUDE.md`.

### 2. `STATUS_LABEL_MAP` in BriefCard.vue had hardcoded English strings
The map values were English labels (`"Pending"`, `"Approved"`) instead of i18n key paths. Caught in review; fixed to key paths (`"briefs.approvalStatus.pending"`).

### 3. Hub article status rendered raw in ClusterDetailPage
`{{ hubArticle.status }}` was a leftover from the early inline spoke-card code. Fixed by adding `hubArticleStatusLabel` computed using Pattern B.

### 4. Cluster generation-status endpoint was missing `pillarName` and `primaryKeyword`
The `/clusters/:id/generation-status` response mapped only `id`, `name`, and `generationStatus`. `ClusterDetailPage` needed both for the subtitle. Fixed by adding `pillarName: cluster.pillar ?? null` and `primaryKeyword: cluster.primaryKeyword ?? null`.

### 5. `BulkApproveModal` uses `v-model` + `@confirm` emit pattern
The modal receives `briefIds` as prop and emits `@confirm({ mode })` so the parent controls the API call. This keeps the modal stateless re: API communication — easier to test, easier to show loading state on the parent's `bulkProcessing` flag.
