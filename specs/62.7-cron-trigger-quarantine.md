# Spec 62.7 — Cron-Trigger + Quarantäne-View

_Theme 62 Sub-Spec — automatisiert wöchentliche Plan-Generation via Cron, zeigt failed Pipeline-Runs in einer Quarantäne-Sektion._
_Status: Draft._
_Voraussetzung: 62.0a + 62.2 + 62.4 + 62.5 + 62.6 sind gemerged._

---

## 1. Ziel

Zwei Dinge, beide klein:

1. **Auto-Trigger PlanWeekPipeline via Cron** — konfigurierbar pro Projekt (dayOfWeek + hourUTC), default OFF. Cron triggert nur Plan-Generation, kein Auto-Approve, kein Auto-Execute. Marcel reviewt manuell.

2. **Quarantäne-View** für failed Pipeline-Runs — als zweiter Tab in PlannerPage, mit Retry-Action und Link zur RunDetailPage (62.6).

**In Scope:**
- `project_planner_config` Erweiterung um Cron-Settings
- Cron-State-Row für `planner_weekly_generation` pro Projekt
- Worker-Logic: aktive Crons triggern PlanWeekPipeline mit `{ targetYear, targetIsoWeek: nextWeek, triggeredBy: 'cron' }`
- SettingsPlannerPage UI-Erweiterung: Cron-Toggle + dayOfWeek + hourUTC
- PlannerPage Tab-Layout: "Kalender" / "Quarantäne" mit Badge-Count
- Quarantäne-Section: Liste failed runs mit Retry + Link zu /runs/:id

**Out of Scope:**
- Auto-Approve (Marcel reviewt immer manuell)
- Auto-Execution (kommt mit 62.8)
- Failure-Email-Notifications (out of scope, später)
- Cron für andere Pipelines (nur PlanWeekPipeline)
- Cron mit komplexer Schedule (nur 1×/Woche, fest day-of-week + hour)
- Per-Item Retry-UI (62.7 retriggert ganze failed Runs, nicht einzelne items)

**Geschätzter Aufwand:** 0.5-1 Tag.

---

## 2. Architektur-Entscheidungen

- **Cron via `cron_state` Tabelle:** Pattern aus 59.1c. Neuer `job_type='planner_weekly_generation'` mit `cron_pattern` aus Settings.
- **`cron_pattern` ist computed:** Marcel pflegt `cron_day_of_week` (0-6, Sonntag=0) und `cron_hour_utc` (0-23). Backend rechnet zu `"<minute> <hour> * * <dow>"` Pattern.
- **Cron-Toggle in SettingsPlannerPage:** existing Page aus 62.2 + 62.6 (Debug-Toggle). 62.7 fügt eine weitere Section "Wöchentlicher Plan-Trigger" hinzu.
- **PlannerPage Tab-Layout:** "Kalender" (default, existing) + "Quarantäne" (neu). Tab-State in URL als `?tab=quarantine` für deep-link.
- **Quarantäne = `pipeline_runs WHERE pipelineName='planning:weekly' AND status='failed'`** — pure View ohne neue Tabelle. Filter ist via Run-Status, kein separates Quarantine-Flag.
- **Retry-Action löst neuen Plan-Trigger aus:** kein Re-run-from-step (das ist 62.6 für paused). Failed Runs sind zu Ende gelaufen — Retry heißt "neuer Plan, gleiche Woche, force=true".
- **Worker-Pattern:** Cron-Orchestrator (existing aus 62.0a) polled `cron_state` jede Minute, enqueued BullMQ-Job `planner-weekly-trigger`. Worker macht POST-equivalent zu `/plans/generate`.

## 4. Backend — Cron-Worker Integration

### 4.1 Cron-Pattern computed from settings

Wenn Marcel `cronDayOfWeek` oder `cronHourUtc` updated, muss der `cron_state.cron_pattern` synchronisiert werden. Trigger-Pattern (Option A: in `upsertProjectPlannerConfig` Helper, Option B: separater DB-Trigger):

**Option A (empfohlen):** im write-helper:
```ts
// packages/db/src/helpers/project-planner-config-write.ts
async function upsertProjectPlannerConfig(input) {
  // ... existing upsert ...
  
  // Sync cron_state pattern + is_active
  const pattern = `0 ${input.cronHourUtc} * * ${input.cronDayOfWeek}`;
  await db.update(cronState)
    .set({ 
      cronPattern: pattern, 
      isActive: input.cronEnabled,
      updatedAt: new Date(),
    })
    .where(and(
      eq(cronState.projectId, input.projectId),
      eq(cronState.jobType, 'planner_weekly_generation'),
    ));
}
```

### 4.2 Cron-Orchestrator wiring

Existing cron-orchestrator (aus 62.0a + HN-Cron-Fix vom heutigen Tag) ergänzen um `planner_weekly_generation` job-type:

```ts
// apps/api/src/workers/cron-orchestrator.ts
const JOB_TYPE_HANDLERS = {
  // ... existing handlers (signal_collector_*, etc.) ...
  'planner_weekly_generation': handlePlannerWeeklyGeneration,
};

async function handlePlannerWeeklyGeneration({ projectId }) {
  const nextWeek = computeNextIsoWeek(); // ISO-week + year for "next Monday's week"
  
  await enqueuePlanWeekPipeline({
    projectId,
    targetYear: nextWeek.year,
    targetIsoWeek: nextWeek.week,
    triggeredBy: 'cron',
    force: false,  // existing plan blocks → log warning, don't supersede
  });
}
```

**Important:** Cron uses `force: false`. Wenn existing draft/approved Plan für nextWeek → Cron-Job logged warning, skips. Marcel sieht failed cron-run in logs aber kein Schaden.

### 4.3 ISO-Week-Computation

`computeNextIsoWeek()` — pure helper. Returns ISO week + year for the week starting "next Monday". Edge-cases:
- Wenn heute Sonntag: next Monday ist morgen, gleiche oder nächste ISO-week je nach Jahr-Wechsel
- Wenn heute Donnerstag: next Monday ist in 4 Tagen

Use existing ISO-week helpers from `packages/planner/src/iso-week.ts` (aus 62.4).

### 4.4 Trigger-Audit

Jeder Cron-getriggerte Plan-Generation-Run sollte sich von manuellen unterscheiden lassen via `weekly_plans.triggered_by = 'cron'` (existing field aus 62.4).

PlannerPage Kalender-View kann optional Cron-Plans visuell markieren (z.B. kleines Clock-Icon im Header), aber nicht Pflicht für 62.7.

## 5. Backend — API für Quarantäne

Keine neuen Endpoints nötig. 62.6 hat schon:
- `GET /api/projects/:slug/pipeline-runs?pipelineName=planning:weekly&status=failed` (via 62.6 list endpoint)

62.7 nutzt das mit Filter-Query. Plus für Retry:
- `POST /api/projects/:slug/plans/generate` mit `force: true` (existing aus 62.4) — wenn neuer Plan für gleiche Woche getriggert wird, alter (failed oder superseded) wird zu superseded gemarkt.

**Wichtig:** Failed runs werden NICHT als "superseded" behandelt von der Retry-Logic. Retry triggert einen NEUEN Plan-Run, der failed Run bleibt failed in History. Das ist by-design — failed runs sind Audit-Trail.

### 7.3 Retry-Action

```ts
async function retryFailedRun(failedRun) {
  const confirmed = await confirmDialog({
    title: "Plan-Generation wiederholen?",
    body: `Neuer Plan-Run für KW ${failedRun.targetIsoWeek}/${failedRun.targetYear} wird gestartet. ` +
          `Vorheriger fehlgeschlagener Run bleibt in der Historie.`,
  });
  if (!confirmed) return;
  
  const response = await apiPost(
    `/api/projects/${slug}/plans/generate`,
    { 
      targetYear: failedRun.targetYear,
      targetIsoWeek: failedRun.targetIsoWeek,
      force: true,
      triggeredBy: 'retry-from-quarantine',
    }
  );
  
  // Optimistic: removes failed run from quarantine list visually
  // (TanStack cache patch: failedRun has been "addressed" — Marcel sees it as past)
  // ... patch logic
  
  if (response.weeklyPlanId) {
    router.push(`/projects/${slug}/planner?week=${failedRun.targetIsoWeek}&year=${failedRun.targetYear}`);
  }
}
```

## 10. Risiken

| Risiko | Mitigation |
|---|---|
| Cron-Pattern-Sync zwischen project_planner_config + cron_state.cron_pattern divergiert | Single source of truth in helper. Migration seedet initial-state. Add Test. |
| Cron triggert während existing Plan für nextWeek noch draft ist | Cron nutzt `force: false`, blockt ohne Side-Effect. Log warning, kein Schaden. |
| ISO-week-edge-cases (KW53 / Year-Wechsel) | Tests aus 62.4 für `isoWeekStartDate` cover das. `computeNextIsoWeek` nutzt diese Helpers. |
| Retry-Action wird "Re-run" verwechselt mit 62.6 Re-run-from-step | UI-Wording: "Retry" auf Quarantäne, "Re-run from step" in RunDetailPage. Confirm-Dialogs erklären explizit. |
| Multiple Crons aktiv (signal-collectors + planner) konfligieren | Cron-Orchestrator handhabt job-types parallel via separate BullMQ-queues. Kein Konflikt. |
| Cron-Trigger feuert zur falschen UTC-Stunde wegen Server-Timezone | Cron-Pattern nutzt explizit UTC (no `TZ=`-Override). Server-Timezone irrelevant. |
| Quarantäne-Tab wird laggy bei vielen failed runs | Pagination default 20, lazy-load. Falls > 100 failed runs → eigene Indizes prüfen |
| Cron läuft, aber Worker offline → missed-fire | HN-Cron-Fix Pattern aus heute: catchUpStaleSignalCollectors funktioniert auch für planner_weekly_generation. Erweiterung des bestehenden Hooks erwägen |

## 12. Anschluss

Nach 62.7:
- **62.5.1 (Batch-aware Cost Estimation):** noch defer'd, kommt direkt vor 62.8

- Auto-Approve (Marcel reviewt immer)
- Auto-Execution (62.8)

- Cron für Synthesizer / andere LLM-Pipelines (Hybrid-Mode-Entscheidung bleibt: synthesis manuell)
- Per-Item Retry (Quarantäne ist Run-Level, nicht Item-Level)
