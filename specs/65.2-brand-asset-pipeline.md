## 3. Resolver-Architecture Decision

Marcel-Decision: "Discovery soll evaluieren wo die Logo-Resolver-Chain lebt".

### 3.1 Options Evaluated

**Option A — Standalone module `packages/social/src/brand-asset-resolver/`**

```typescript
// New module separate from existing Engine logic
import { resolveToolBrandAsset } from '@marketing-auto/social/brand-asset-resolver';

const asset = await resolveToolBrandAsset({ toolId, slug });
// → { logoSvg, source, needsReview }
```

**Pros:**
- Clean separation Engine ↔ Brand-Assets
- Each module owns single concern
- Easy to test isolated

**Cons:**
- Duplication: Existing `resolveToolIcon` chain has same logic — would refactor or duplicate
- 2 paths to maintain (preview-render vs brand-backfill could diverge)

**Option B — Erweitere Engine's `resolveToolIcon` zu `resolveToolBrandAsset`**

```typescript
// Same module, broader API
export async function resolveToolBrandAsset(input): Promise<BrandAsset>;
export async function resolveToolIcon(input): Promise<string>;
  // Internal: calls resolveToolBrandAsset, returns .logoSvg only (BC-compat)
```

**Pros:**
- Single source of truth for the resolution chain
- BC-compatible — existing callers untouched
- New brand-asset-specific fields just additive

**Cons:**
- Engine code grows scope from "icon" to "brand-asset"
- Naming consistency question (where do "icons" end and "brand-assets" start?)

**Option C — Migrate Engine to consume `tool_brand_assets` table**

```typescript
// Engine no longer resolves on-the-fly; reads from pre-populated DB
export async function resolveToolIcon(input): Promise<string> {
  const asset = await getBrandAssetsForTool(input.toolId);
  if (asset?.logo_url) return asset.logo_url;
  // Fall back to chain only if DB-row missing → triggers eventual backfill
  return await chainResolve(input);
}
```

**Pros:**
- DB becomes single source of truth — Engine consumes, doesn't resolve
- Marcel-edits in needs_review-UI immediately visible to renders
- Decouples resolution-strategy from consumer

**Cons:**
- DB-dependency in Engine-render path (latency: 1 extra SELECT per slot per render)
- Cache-invalidation needed when Marcel edits → next render gets stale until cache cleared
- Existing renders depend on this being available — migration-coordination matters

### 3.2 Recommendation: **Option C with caching**

Reasoning:

1. **Marcel-edits propagate to renders ohne deploy** — wenn Marcel Brand-Color für `claude` in Settings-UI ändert, next render uses it. Engine-chain hat das nicht (chain is deterministic from slug).
2. **`tool_brand_assets` table is the source-of-truth contract** — Engine-chain wird zum **Population-Mechanism**, nicht zum **Read-Mechanism**.
3. **65.7+65.8 Templates konsumieren die table** — read-from-DB ist konsistent für alle template-render paths.
4. **Cache-Layer mitigates DB-latency** — in-memory cache, invalidated via Redis pub/sub when needs_review-UI updates.

**Trade-off accepted:** 1 extra SELECT per slot in production-render path. Mitigation: batch-load `getBrandAssetsForTools(toolIds[])` per render (1 query for N tools).

**Migration-pattern:**
- Phase 1 (65.2): Backfill `tool_brand_assets` for all 108 tools using existing chain
- Phase 2 (65.2): Add `getBrandAssetsForToolsBatch` helper to packages/db
- Phase 3 (post-65.2 deploy): Engine's `resolveToolIcon` reads from DB first, falls back to chain only if row missing
- Phase 4 (settings-UI invalidation): Redis pub/sub `brand-assets:changed` on PATCH

## 4. Backfill Script

### 4.1 Approach

**File:** `apps/api/src/scripts/backfill-brand-assets.ts`

Mirrors 64.20 H3 backfill-pattern (Memory D26 backfill-script pattern):

- Dry-run via count(*) — shows "X tools needing brand-assets"
- Apply-mode: project-scoped (mandatory per Memory D26 — Toolwiki vs BK isolation)
- Iterates `listToolsMissingBrandAssets({ limit: 50 })` in batches
- Calls existing `resolveToolIcon` chain per tool
- Upserts via `upsertBrandAsset` with `needs_review=true` for color-fields
- Logs progress + final summary

```typescript
// Pseudo
async function backfillBrandAssets({ projectSlug, apply = false }) {
  const project = await getProjectBySlug(projectSlug);
  if (!project) throw new Error(`Project not found: ${projectSlug}`);
  
  if (!apply) {
    const count = await countToolsMissingBrandAssets({ projectId: project.id });
    console.log(`Dry-run: ${count} tools need brand-assets`);
    return;
  }
  
  let totalProcessed = 0;
  let totalFromLobeIcons = 0;
  let totalFromIconify = 0;
  let totalFromSimpleIcons = 0;
  let totalAvatar = 0;
  
  while (true) {
    const batch = await listToolsMissingBrandAssets({ projectId: project.id, limit: 50 });
    if (batch.length === 0) break;
    
    for (const tool of batch) {
      const resolved = await resolveToolBrandAsset({ toolId: tool.id, slug: tool.slug });
      
      await upsertBrandAsset({
        toolId: tool.id,
        logoUrl: resolved.logoUrl, // could be R2-key OR inline-data-uri
        primaryColor: null,
        secondaryColor: null,
        brandNameCanonical: tool.name, // initial seed
        source: resolved.source, // 'lobe-icons' | 'iconify' | 'simple-icons' | 'avatar'
        needsReview: true, // ALL need color-review by Marcel
        fetchedAt: new Date(),
      });
      
      totalProcessed++;
      // count per source...
    }
  }
  
  console.log(`Processed: ${totalProcessed}, lobe-icons: ${totalFromLobeIcons}, ...`);
}
```

### 4.2 Storage Format Decision

**Option α — Inline SVG-data-uri in `logo_url`:**

`logo_url = 'data:image/svg+xml;utf8,<svg>...</svg>'`

**Pros:** No R2-upload needed, immediate available, no extra storage cost
**Cons:** DB-bloat (SVGs ~1-5KB each × 108 = ~200-500KB), cache-overhead per query

**Option β — Upload zu R2, store R2-key:**

`logo_url = 'r2://toolwiki/brand-assets/claude.svg'`

**Pros:** Clean DB, CDN-able for production-renders, separation of concerns
**Cons:** R2-upload per backfilled tool (108 × ~50ms = ~5s total, vernachlässigbar)

**Recommendation:** **Option β — R2-upload.** Pattern matches Memory D20 (Adapter-Shape: R2 + cost-logging intern). Plus: production-render likely already R2-CDN-served.

### 4.3 Cost Estimate

- 108 tools × lobe-icons-resolution: free
- 108 SVG-uploads to R2: ~$0.0001 (vernachlässigbar)
- Initial Marcel-Effort: ~108 × 10min Color-Curation = ~18h Marcel (kann staggered über 1-2 Wochen sein)

→ **Total V1 cost: ~$0 + ~18h Marcel** (massiv günstiger als Master-Spec's Brandfetch-Plan)

## 7. Multi-Domain Considerations

`tool_brand_assets` ist **tool-scoped** (project_id absent, per 65.1 schema). BK + Toolwiki share brand-assets where they share tools.

**Implication:**
- Backfill-script ist project-scoped (Memory D26 — backfill mandates project-id), aber DB-rows sind shared
- If BK adds tool `claude` later: brand-asset already exists from Toolwiki-backfill, no duplicate fetch
- needs_review-UI is project-agnostic ABER scoped to "tools used by this project" (filter by `articles.collection='tools'` && project's tool-references)

**Manual-Edit-Coordination:** Wenn Marcel im Toolwiki UI Color für `claude` ändert, **wird's auch in BK sichtbar** (selbe DB-row). Das ist by-design (shared assets) aber muss UI-side klar kommuniziert werden (vielleicht warning "this edit affects all projects using this tool").

## 15. Discovered During Implementation (2026-05-25)

Worked through several waves of follow-up fixes Marcel surfaced as we shipped against Toolwiki:

- **Schema-Wahl `toolId = articles.id` ist per-locale.** 65.1 schema choice (PK keyed to `articles.id`) means every bilingual tool (Toolwiki since 59.2) has TWO `tool_brand_assets` rows — one per `articles.locale`. V1 fix: filter list + backfill to `projects.targetLocales[0]` so Marcel sees 54 rows not 108. EN-Renders will need sibling-traversal in 65.7/65.8 (deferred to backlog).
- **lobe-icons is structurally richer than simple-icons for AI brands.** Lobe ships 3 variants per brand (`<slug>.svg` mono / `<slug>-color.svg` colored / `<slug>-text.svg` wordmark) + multi-color fills (Gemini, DALL-E) + 223/850 brands with `-color`. Chain re-ordered to lobe-FIRST so Claude/Gemini/DALL-E/OpenAI-family get rich logos + wordmarks; simple-icons + iconify stay as fallback.
- **simple-icons SVGs are monochrome by design.** They use `fill="currentColor"` and emit a separate `icon.hex`. Server-side `fill="${hex}"` injection on root `<svg>` makes them render in-brand without consumer-side styling (Claude #D97757, Perplexity #1FB8CD).
- **lobe-icons `-color` SVGs use gradients for ~50% of brands.** `kling-color.svg` etc. reference `<linearGradient>` / `<radialGradient>` with `<stop stop-color="#...">`. Extractor needs both solid-fill and gradient-stop paths. Multi-color brands (Gemini = 4 paths × 4 hex) need ALL distinct colors → seed `primary/secondary/tertiary`.
- **`tool_brand_assets` needs 3+ color slots, not 2.** Original schema had `primary_color` + `secondary_color`. Brandfetch convention exposes 3-5 colors per brand (primary vivid + dark accent + light tint). Migration 0117 added `tertiary_color`. Marcel-decision: text column over JSONB palette.
- **Templates need wordmark variant for layout flexibility.** Kurzform (icon) vs Wordbild (wordmark) — Marcel can pick per layout space. Migration 0118 added `logo_wordmark_url`; adapter uploads both icon + wordmark when source has `-text.svg`.
- **Brandfetch.com is Cloudflare-protected** — no automated scraping. CDN at `cdn.brandfetch.io` redirects to web pages; public Search API returns brand IDs but the brand-data API needs a token. Workaround: fetch logos from the brand's own website CDN (Webflow/Squarespace) + Marcel supplies the colors manually from the Brandfetch dossier. Reusable [`import-tool-brand-asset.ts`](../apps/api/src/scripts/import-tool-brand-asset.ts) batch-import script accepts both remote URLs and local files.
- **`project_brand_assets` Spec-52b cache shadows new adapter improvements.** `resolveToolIcon` writes its result to the 52b cache as a side-effect; subsequent calls read the cache first. After ANY adapter logic change (mapping, brandColor extraction, wordmark fetch), the cache must be invalidated before a force-backfill or the new logic never executes. `DELETE FROM project_brand_assets WHERE asset_type='tool_icon' AND project_id=X` is the one-shot fix.
- **Force-mode pagination needs an `excludeIds` filter.** The "missing-mode" predicate `WHERE tba.tool_id IS NULL` shrinks as rows get INSERTed, so the page-by-LIMIT loop naturally terminates. Force-mode predicate `WHERE source != 'manual'` is stable (UPDATE doesn't remove rows from the predicate), so the same first-N rows come back every iteration — `seenInRun` Set filters them out → empty fresh-batch → premature break. Fix: pass `notIn(articles.id, excludeIds)` into the query.
- **Vue method named `notify` shadows `$q.notify` visually.** A Vue Options-API method called `notify(row)` on the modal compiled fine but reads ambiguously next to `this.$q.notify({...})` and led to the "Speichern passiert nichts" complaint (cause: missing success-toast, not bad emit). Renamed to `emitSavedAndClose` + added explicit success-toast.
