## 2. Issue 1 — `skip_auto_translation_until` Consumer-Wiring

Akzeptanzkriterium 11 wurde als "✅ (column) / ⏳ (consumer wiring)" markiert — die Spalte existiert, aber `BlogPipeline.afterComplete` triggert die Translation-Pipeline weiterhin unconditionally. Damit ist der Flag tot.

### Was zu tun ist

In `packages/pipelines/src/article/blog/pipeline.ts` (oder wo `BlogPipeline.afterComplete` lebt — Claude Code grept):

```ts
// Pseudo-code, exakte Stelle hängt vom existierenden Code ab
async afterComplete(ctx: PipelineContext, output: BlogPipelineOutput) {
  // ... existing logic ...
  
  // NEW: Check skip_auto_translation_until before triggering translation

    const article = await getArticleById(output.articleId);
    
    if (article.skipAutoTranslationUntil && article.skipAutoTranslationUntil > new Date()) {
      log.info({
        articleId: output.articleId,
        skipUntil: article.skipAutoTranslationUntil,
      }, "Skipping auto-translation due to skip_auto_translation_until flag");
      return;

Idealer Rename-Zeitpunkt: jetzt, vor 62.0b weitere Discriminator-Werte hinzufügt (z.B. `kind: "prompt_pause"`).

## 4. Issue 3 — Orphan-Substep Verifikation in echtem Toolwiki-Batch-Resume

### Background

62.0a Section 4.5 hat `supersedeOldSubstep()` in batch-resume integriert und das in 9 Integration-Tests gegen `TestPipeline` verifiziert (D31 equivalence). Aber: Pre-flight Task 1 cosmetic issue ("orphan outline-substep nach batch-resume") wurde nur "structurally fixed" markiert, nie an einer echten ClusterGenerationPipeline gegen Anthropic-Batch verifiziert.

Risiko: irgendeine Subtilität im echten batch-resume-Flow (z.B. wann genau wird `supersedeOldSubstep` aufgerufen) führt dazu dass der Fix in production doch nicht greift. Würde uns in 62.8 auf die Füße fallen.

### Was zu tun ist

Re-run von Pre-flight Task 1 — gleiches Setup, aber explizite Orphan-Verification:

1. **Setup:** Toolwiki temporarily auf `llmMode='batch'`, `BATCH_API_ENABLED=true`.
2. **Trigger:** `article:outline` über HTTP-Endpoint.
3. **Wait for batch completion** (Anthropic SLA, oft < 1h).
4. **Post-completion verification:**
   ```sql
   SELECT id, status, step_name, started_at, completed_at
   FROM pipeline_runs
   WHERE parent_run_id = '<original-run-id>'
   AND step_name = 'outline'
   ORDER BY started_at;
   ```

   **Expected:** mindestens 2 Rows.
  - Erste Row: `status='superseded'`, `completed_at IS NOT NULL`.
  - Zweite Row (oder weitere): `status='completed'`.

   **NICHT expected:** erste Row mit `status='running'` (das wäre Pre-flight cosmetic issue noch da).

5. **Wenn orphan noch da:** Debug — Code-Check ob `supersedeOldSubstep()` wirklich in `engine/batch-resume.ts` aufgerufen wird vor dem re-enqueue, und ob der WHERE-Clause matched. Issue-Fix.

6. **Reset:** Toolwiki zurück auf `llmMode='sync'`.

### Tests (optional, niedrig-Priorität)

Wenn Issue gefunden und gefixt: Regression-Test in `packages/pipelines/test/engine/batch-resume-supersede.test.ts`:

- Mock-batch-resume-Aufruf mit existierendem Substep in `status='running'` → nach Call: erster Substep `status='superseded'`, neuer Substep `status='running'`.

Wenn Issue NICHT gefunden (Fix funktioniert): kein neuer Test nötig, Acceptance ist erfüllt durch manuelle Verifikation.

### Akzeptanz

- [x] Regression-Test geschrieben — `packages/pipelines/test/engine/batch-resume-supersede.test.ts` (2 tests, both pass): one happy-path (prior substep in `batch_pending` → becomes `superseded` + parent re-queued + checkpoint cleared + batch_requests marked `resume_enqueued`), one edge-case (already-terminal substep → supersede skips it idempotently). Both assert against real DB state, mocking only the `enqueuePipeline` queue call.
- [ ] **Manuelle Verifikation in Toolwiki (Marcel)** — siehe Procedure unten. Der Regression-Test deckt das strukturelle Fix ab (`supersedeOldSubstep()` wird im richtigen Moment aufgerufen und transitioniert die richtigen Rows), aber bestätigt nicht, dass der echte batch-resume-Flow gegen Anthropic im Production-Code-Pfad denselben Code durchläuft. Marcel führt die manuelle Verifikation nach dem Merge aus.

### Manuelle Verifikations-Procedure für Marcel (post-merge)

```bash

## 5. Issue 6 — `makeMockCtx()` Helper-Factory

### Background

62.0a D11: das Hinzufügen von `runMode` als required field in `StepContext` brach 11 mockCtx-Literale workspace-weit (9 in `packages/pipelines/test/`, 1 in `packages/adapters/astro-sync/test/`, 1 inline in `apps/api/src/routes/projects.ts:622`). Jeder zukünftige required-field-Add wird gleiches Problem haben.

Lösung: zentrale Factory in `packages/pipelines/test/fixtures/mock-ctx.ts` (oder analog). Tests konstruieren `makeMockCtx({ ... overrides })` statt Literal. Neue required fields werden in der Factory zentral defaultet.

### Was zu tun ist

#### 5.1 Factory anlegen

```ts
// packages/pipelines/test/fixtures/mock-ctx.ts
import type { StepContext } from "@marketing-auto/pipelines";

const defaultMockCtx: StepContext = {
  projectId: "00000000-0000-0000-0000-000000000001",
  pipelineRunId: "00000000-0000-0000-0000-000000000002",
  stepRunId: "00000000-0000-0000-0000-000000000003",
  runMode: "production",
  llmMode: "sync",
  // ... alle anderen required fields hier defaulten
};

export function makeMockCtx(overrides: Partial<StepContext> = {}): StepContext {
  return { ...defaultMockCtx, ...overrides };
}
```

#### 5.2 Migration der 11 Call-Sites

Grep nach `as StepContext` und `: StepContext = {` workspace-weit. Jeder Treffer wird ersetzt durch `makeMockCtx({ ...overrides })`.

Beispiele:

```ts
// Vorher:
const mockCtx = {
  projectId: "test-proj",
  pipelineRunId: "test-run",
  runMode: "production",
  llmMode: "sync",
  // ... 5 weitere boilerplate fields
} as StepContext;

// Nachher:
const mockCtx = makeMockCtx({
  projectId: "test-proj",
  pipelineRunId: "test-run",
});
```

#### 5.3 Helper für andere Packages

Für `packages/adapters/astro-sync/test/` und ggf. weitere Packages: Re-Export via `@marketing-auto/pipelines/test-fixtures` (oder analog), oder lokale `makeMockCtx` Wrapper, falls Cross-Package-Import nicht sauber geht.

Für `apps/api/src/routes/projects.ts:622` (inline literal in non-test code): das ist ein anderer Fall — wenn dort StepContext gebaut wird, ist es kein Mock sondern echter Build. Sollte vermutlich in einen Helper in `apps/api/src/lib/` extrahiert werden, nicht in die Test-Factory. Claude Code prüft den Kontext.

### Tests

Keine neuen Tests nötig — bestehende Tests müssen grün bleiben mit der neuen Factory. Wenn Factory falsch defaultet, sehen wir es sofort.

## 9. Deviations from spec (implemented)

- **Migration number: 0069, not 0068** — Spec proposed `0068_rename_suspension_checkpoint.sql` but `0068_step_pause_cleanup_enum.sql` was already created in the 62.0a merge. Used `0069` instead. No semantic change.

Mitigated up-front: extracted the gate into a pure helper [`shouldSkipAutoTranslation()`](packages/pipelines/src/article/translation/skip-gate.ts) and wired it into both `BlogPipeline.afterComplete` (fresh-translation enqueue) and `RefreshPipeline.afterComplete` (sibling-propagation enqueue).
- **Issue 3 regression test written unconditionally** — Spec said "Wenn Issue gefunden und gefixt: Regression-Test schreiben". Wrote the test regardless ([batch-resume-supersede.test.ts](packages/pipelines/test/engine/batch-resume-supersede.test.ts), 2 cases). - **Issue 6 migrated 10 literals, not 11** — Spec counted 11 mockCtx literals. Actual: 9 in `packages/pipelines/test/`, 1 in `packages/adapters/astro-sync/test/`. The 11th mention is `apps/api/src/routes/projects.ts:635` which is **production code building a real `StepContext`** — intentionally NOT routed through the test factory. Documented in the new gotcha in [pipelines/CLAUDE.md](packages/pipelines/CLAUDE.md).

- **Known posture, not changed by this PR** — `PATCH /api/articles/:id/skip-translation` follows the existing `articleRoutes` convention: authenticated user can mutate any article by ID. No per-user project-membership check at the route. Same posture as every other `articleRoutes.patch` / `articleRoutes.post` endpoint. Workspace-wide tightening is out of scope; revisit when multi-tenant SaaS posture is introduced.
