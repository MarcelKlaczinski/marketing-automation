## 1. Problem

Phase 2 LANG_INDEPENDENT_EXTRAS Audit (2026-05-22) hat eine FAQ-Translation-Asymmetrie aufgedeckt:

**Affected:** 9 von 157 article-pairs (5.7%)
- 4 pairs: FAQ komplett verloren in EN sibling (lost = DE hat FAQs, EN hat keine)
- 5 pairs: FAQ partial in EN sibling (partial = einige FAQ-Items übersetzt, andere verloren)

**Examples (verified Toolwiki, Discovery Phase 2):**
- chatgpt-ads-2026: DE 6 FAQ items, EN 0 (lost)
- prompt-engineering-grundlagen-2026: DE 8 items, EN 3 (partial)

### Root Cause Lokalisierung

**File:** `packages/pipelines/src/article/translation/body-step.ts`

**Hypothesis (Phase 0 muss verifizieren):**
- FAQ-Section ist als markdown block im body content
- Translation-Step übersetzt body markdown via Claude
- LLM verschluckt manchmal FAQ-blocks bei high source-locale token-count (>3500 input tokens)
- Plus: möglicherweise FAQ-spezifisches schema-handling (FAQPage schema_json_ld) wird nicht recreated für EN

**Plus indirekte Discovery aus 64.3 Implementor-Report:**
> "Bug #3 fixed for künftige Translation-Runs. Bridge nutzt jetzt buildTranslationPersistInput() pure helper."

Das heißt: 64.3 hat die schema-bridge gefixt aber FAQPage-spezifisches schema (separates JSON-LD field) ist nicht abgedeckt.

## 2. Ziel

**Drei orthogonale Fixes:**

**Fix A (Prompt Engineering):** Body-Step LLM-prompt explicit anweisen FAQ-blocks 1:1 zu übersetzen, kein Drop, kein Skip.

**Fix B (Post-Translation Validation):** Pure-helper `validateFaqPreservation(sourceBody, targetBody)` der DE FAQ-count vs EN FAQ-count vergleicht. Bei mismatch: Step-level retry mit verstärktem prompt (1 retry max).

**Fix C (FAQPage Schema Bridge):** Wenn DE article FAQPage schema_json_ld hat, muss EN sibling auch FAQPage schema haben mit translated questions/answers. Aktuell wird das nicht gebridged (separate JSON-LD field neben Article schema).

**In Scope:**
- Body-Step prompt erweitern: "FAQ MUST be translated 1:1, no items dropped"
- Pure helper `validateFaqPreservation()` in `translation/lib/faq-validator.ts`
- FAQ-count mismatch → Step retry mit `prompt: prompt + STRONGER_FAQ_GUIDANCE` (1 retry)
- FAQPage Schema Translation in `buildTranslationPersistInput()` (von 64.3 helper)
- Tests: validator (4 cases), bridge-FAQ-schema (3 cases), retry-mechanism (2 cases)

**Out of Scope:**
- Word-Count Drift Cap (separater Bug #1 → Spec 64.5)
- Article schema rebuild (von 64.3 bereits done)
- Historical 9 affected pairs cleanup — durch Reset-Cleanup gelöscht
- Multi-locale FAQ-validation (nur DE↔EN, future-locale wenn nötig)

## 3. Architektur

### 3.1 FAQ Validator Helper (Fix B)

**File:** `packages/pipelines/src/article/translation/lib/faq-validator.ts` (neu)

```ts
/**
 * Counts FAQ items in markdown body using heuristic patterns.
 * 
 * FAQ-Block patterns supported:
 * 1. Heading-based: "## FAQ" or "## Häufige Fragen" oder "## Frequently Asked Questions"
 *    followed by H3 question headers
 * 2. Definition-list style: "### Question?" + answer paragraphs
 * 3. Q/A markers: "**Q:** ... **A:** ..."
 */
export function countFaqItems(body: string): number {
  // Heuristik 1: count H3 headers nach FAQ section heading
  const faqSectionMatch = body.match(/^##\s+(FAQ|Häufige\s+Fragen|Frequently\s+Asked\s+Questions)/im);
  if (!faqSectionMatch) return 0;
  
  const faqSectionStart = faqSectionMatch.index ?? 0;
  const nextH2Match = body.slice(faqSectionStart + 1).match(/^##\s+/m);
  const faqSectionEnd = nextH2Match 
    ? faqSectionStart + 1 + (nextH2Match.index ?? 0)
    : body.length;
  
  const faqSection = body.slice(faqSectionStart, faqSectionEnd);
  const h3Count = (faqSection.match(/^###\s+/gm) || []).length;
  
  return h3Count;
}

/**
 * Validates FAQ preservation: target should have same count as source.
 * Returns mismatch-result with delta if applicable.
 */
export interface FaqValidationResult {
  valid: boolean;
  sourceCount: number;
  targetCount: number;
  delta: number;  // positive = lost in translation
  message: string;
}

export function validateFaqPreservation(
  sourceBody: string,
  targetBody: string,
): FaqValidationResult {
  const sourceCount = countFaqItems(sourceBody);
  const targetCount = countFaqItems(targetBody);
  const delta = sourceCount - targetCount;
  
  const valid = delta === 0;
  const message = valid
    ? `FAQ count preserved: ${sourceCount}`
    : `FAQ asymmetry: source has ${sourceCount}, target has ${targetCount} (lost ${delta})`;
  
  return { valid, sourceCount, targetCount, delta, message };
}
```

### 3.3 Body-Step Retry-Mechanism

**Pattern:** Step retries 1× wenn FAQ-count mismatch detected.

```ts
async execute(ctx: StepContext, input: TranslationBodyInput): Promise<TranslationBodyOutput> {
  const sourceBody = input.sourceBody;
  let attempt = 0;
  let targetBody: string;
  let validation: FaqValidationResult;
  
  while (attempt < 2) {
    const promptSuffix = attempt === 0 ? "" : STRONGER_FAQ_GUIDANCE.replace(
      "{sourceCount}", 
      String(countFaqItems(sourceBody)),
    );
    
    targetBody = await translateBody(sourceBody, {
      sourceLocale: input.sourceLocale,
      targetLocale: input.targetLocale,
      promptSuffix,
    });
    
    validation = validateFaqPreservation(sourceBody, targetBody);
    
    if (validation.valid) {
      log.info({ articleId: input.articleId, attempt }, "translation FAQ preserved");
      break;
    }
    
    log.warn(
      { articleId: input.articleId, attempt, ...validation },
      validation.message,
    );
    
    attempt++;
  }
  
  // Even after retry, if still invalid, log error but don't fail step
  // (Marcel reviews EN sibling manually before publish)
  if (!validation.valid) {
    log.error(
      { articleId: input.articleId, ...validation },
      "translation FAQ asymmetry persists after retry",
    );
  }
  
  return { body: targetBody, faqValidation: validation };
}
```

**Decision:** Step doesn't fail on FAQ mismatch — Marcel reviews EN siblings before publish anyway. But cost-log + warning makes it visible in UI für manual review.

### 3.4 FAQPage Schema Bridge (Fix C)

**File:** `packages/pipelines/src/article/translation/pipeline.ts` — extend `buildTranslationPersistInput()` (von 64.3)

**Discovery muss prüfen:** wie wird FAQPage schema heute persistiert?
- Separates JSON-LD Feld neben Article schema?
- Embedded in schema_json_ld als array?
- Generated by separate step (BuildJsonLdStep)?

**Hypothese:** schema_json_ld in DB ist Array of @types. Article + FAQPage als zwei objects.

**Patch in `buildTranslationPersistInput()`:**

```ts
// In buildTranslationPersistInput() — extend bridge schema construction:

// Detect FAQPage in source schema array
const sourceFaqPageSchema = Array.isArray(sourceSchemaJsonLd)
  ? sourceSchemaJsonLd.find(s => s["@type"] === "FAQPage")
  : null;

let targetFaqPageSchema = null;
if (sourceFaqPageSchema && Array.isArray(sourceFaqPageSchema.mainEntity)) {
  // Translate questions + answers via existing translatedBody parse
  // (FAQ structure is in body markdown — parse target body for translated FAQ)
  targetFaqPageSchema = {
    "@context": "https://schema.org",
    "@type": "FAQPage",
    mainEntity: extractFaqFromBody(targetBody),  // helper: H3 + paragraph extraction
  };
}

const targetSchemaJsonLd = [
  targetArticleSchema,
  ...(targetFaqPageSchema ? [targetFaqPageSchema] : []),
];
```

**Helper:** `extractFaqFromBody(body: string): FaqItem[]` — parsed markdown FAQ section.

```ts
// packages/pipelines/src/article/translation/lib/faq-extractor.ts
export function extractFaqFromBody(body: string): Array<{
  "@type": "Question";
  name: string;
  acceptedAnswer: { "@type": "Answer"; text: string };
}> {
  const faqSectionMatch = body.match(/^##\s+(FAQ|Häufige\s+Fragen|Frequently\s+Asked\s+Questions)[\s\S]*?(?=^##\s+|$)/m);
  if (!faqSectionMatch) return [];
  
  const faqSection = faqSectionMatch[0];
  const items: ReturnType<typeof extractFaqFromBody> = [];
  
  // Parse H3 questions and answer paragraphs
  const questionRegex = /^###\s+(.+?)$\n+([\s\S]+?)(?=^###\s+|$)/gm;
  let match;
  while ((match = questionRegex.exec(faqSection)) !== null) {
    items.push({
      "@type": "Question",
      name: match[1].trim(),
      acceptedAnswer: {
        "@type": "Answer",
        text: match[2].trim(),
      },
    });
  }
  
  return items;
}
```

## 7. Risiken

| Risk | Mitigation |
|---|---|
| FAQ-Heading-Pattern in body markdown variiert (z.B. "FAQs" statt "FAQ") | Regex erweitern; bei unbekanntem Pattern: countFaqItems returns 0, validator passt as "no FAQ" |
| LLM produced extra H3 nicht-FAQ-related → false-positive mismatch | H3-count nur innerhalb FAQ-section. Section-detection via H2 header pattern. |
| Retry-Prompt mit STRONGER_FAQ_GUIDANCE blowed token-count → cost-impact | Retry max 1× pro article. Bei 50 articles/Monat + 5.7% mismatch = ~3 retries/Monat = €0.10 extra. Acceptable. |
| Step doesn't fail → unaware Marcel published EN sibling mit FAQ-loss | Cost-log mit metadata.faqValidation visible. Plus: future Spec könnte UI-Hint im Article-Preview einbauen. |
| extractFaqFromBody regex bricht bei ungewöhnlicher markdown-structure | Tests cover edge cases; fallback returns `[]` (no FAQPage schema = besser als wrong schema). |
| Schema_json_ld nicht Array sondern Object → Bridge müsste anders handhaben | Phase 0 verifiziert exact shape; falls Object: detect "@graph" array oder Article-only. |

## 9. Implemented

- [`packages/pipelines/src/article/translation/lib/faq-validator.ts`](../packages/pipelines/src/article/translation/lib/faq-validator.ts): `countFaqItems(body)` (heuristic: H3 headers under a recognised FAQ H2 section — supports `FAQ` / `FAQs` / `Häufige Fragen` / `Frequently Asked Questions`) + `validateFaqPreservation(source, target)` returning `{valid, sourceCount, targetCount, delta, message}` with positive delta = lost, negative = LLM-hallucinated extra items.
- [`packages/pipelines/src/article/translation/body-step.ts`](../packages/pipelines/src/article/translation/body-step.ts):
  - `FAQ_TRANSLATION_REQUIREMENT` constant injected into BOTH the literal-path prompt AND the adaptive-path draft prompt (the outline call doesn't need it — outlines only carry headings, not the FAQ items themselves).
  - `STRONGER_FAQ_GUIDANCE` template with `{sourceCount}` placeholder, replaced via `String.replaceAll()` so both occurrences inside the template get substituted (single-pass `.replace()` only hit the first one — caught in test, fixed before merging).
  - New private `#runWithFaqRetry(args)` helper wraps the LLM call: 1× retry max when `validateFaqPreservation` reports invalid; logs `warn` on first attempt fail, `error` on retry fail, `info` on retry recovery. Returns `{raw, validation}`; the parse+sanity path is shared after the loop.
  - Both `#runLiteralPath` and `#runAdaptivePath` consume the helper; `OutputSchema` extended with optional `faqValidation: FaqValidationSchema` so downstream callers (and the EN-sibling review UI in a future spec) can see the validation outcome.
  - Step **does NOT throw** on persistent FAQ asymmetry — Marcel reviews EN siblings before publish anyway; the validation result is surfaced rather than failing the pipeline.
- **Fix C (FAQPage Schema Bridge) skipped** — see §10 Deviations row 1.
- Tests: 10 validator + 3 retry = 13 cases. All pass.
- Workspace typecheck: 0 errors in `@marketing-auto/pipelines`.

## 10. Discovered & Deviations

| # | Discovery | Decision |
|---|---|---|
| 1 | **Fix C (FAQPage schema bridge in `buildTranslationPersistInput`) is redundant.** Phase 0 traced the post-translation flow: [`TranslationPipeline.afterComplete`](../packages/pipelines/src/article/translation/pipeline.ts:316) calls `enqueueSchemaExtension({articleId: targetArticle, ...})`. The [`SchemaExtensionPipeline`](../packages/pipelines/src/schema-extension/pipeline.ts) then runs `DetectRichTypesStep` (scans EN bodyMd for FAQ patterns) → `BuildJsonLdStep` ([build-jsonld.ts:93-97](../packages/pipelines/src/schema-extension/steps/build-jsonld.ts:93) emits FAQPage when `hasFaq && faqQuestions.length >= 3`) → `PersistSchemaStep` overwrites the entire `schemaJsonLd` column. So any FAQPage written by the translation bridge would be wiped within seconds. Conversely, if Fix A+B preserve the EN body's FAQ section, schema-extension generates the correct FAQPage automatically from target-locale H3 questions. | **Skipped Fix C entirely.** Implementing it would either be dead code or create a race with schema-extension. The original 9 affected EN siblings have no FAQPage because their EN bodies had no FAQ — schema-extension correctly emitted no FAQPage. Fix A+B is the upstream cure. |
| 2 | `STRONGER_FAQ_GUIDANCE` template has `{sourceCount}` placeholder twice ("article has N items… produce exactly N items"). `String.prototype.replace(literal, repl)` replaces only the first match — the second `{sourceCount}` leaked through to the LLM in test runs. | Use `.replaceAll()` instead. Caught by retry test (`expect(...).toMatch(/exactly 3 FAQ items/)`) before merging. |
| 3 | `TranslationBodyStep` already had a "one override per step" model (Spec 62.0a Section 4.4 — 3 LLM calls share one `resolvePrompt(ctx, this.name, …)` key). The FAQ retry pattern is orthogonal: the *override* swaps `systemPrefix`/`systemSuffix`; the FAQ retry suffix is part of `userMessage`. No conflict, no contract change. | Keep the per-step override semantics. The FAQ retry guidance only appears on the retry attempt, never in the cacheable prefix. |
| 4 | `OutputSchema` previously didn't carry `faqValidation`. The Spec 64.3 `buildTranslationPersistInput()` helper consumes `body: BodyOutput` and doesn't look at `faqValidation` — adding the field downstream is harmless. | Added as `FaqValidationSchema.optional()` so old runs (pre-64.4 deploy) replayed through the runner don't fail Zod validation. Future spec can read it from `pipeline_runs.output` for an EN-sibling review UI hint. |
| 5 | The adaptive path makes 2 LLM calls (outline + draft). The outline call doesn't carry FAQ items — it only emits headings.
