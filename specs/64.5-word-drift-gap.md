# Spec 64.5 — Bug #1: Word-Drift Cap (+25% Max) in Translation Body

_Fixes Bug #1 from Phase 2 LANG_INDEPENDENT_EXTRAS Audit (2026-05-22)._
_Status: Draft._
_Aufwand: ~1h Implementation + ~30 Min Tests._
_Voraussetzung: Discovery Phase 2 done. Spec 64.4 deployed (gleicher body-step.ts file, sequenz beachten — NICHT parallel mergen)._

---

## 1. Problem

Phase 2 LANG_INDEPENDENT_EXTRAS Audit (2026-05-22) hat **monotone Word-Drift** in EN translations aufgedeckt:

**Affected:** 17 von 17 verglichenen pairs (100%) — alle EN siblings sind länger als DE source, im Schnitt **+30-130%** Word-Count.

**Examples (verified Toolwiki, Discovery Phase 2):**

| Slug | DE words | EN words | Drift | Factor |
|---|---|---|---|---|
| chatgpt-ads-2026 | 2142 | 4852 | +127% | 2.3× |
| prompt-engineering-grundlagen-2026 | 1893 | 3247 | +71% | 1.7× |
| (15 weitere) | ... | ... | avg +52% | 1.5× |

**Monoton:** alle 17 pairs hatten **positive** drift (kein einziger EN sibling war kürzer). Das ist nicht statistisches Rauschen — das ist systematic LLM behavior.

### Root Cause Hypothese

**File:** `packages/pipelines/src/article/translation/body-step.ts`

Das Translation-LLM (Claude) bei Übersetzung DE→EN "verbessert" oft den Output:
- Verbose phrasing ("This means that..." statt "So...")
- Hinzugefügte Klarstellungen / Beispiele
- Englische Texte sind in nature etwas länger (Artikel, Hilfsverben) — aber **nicht 2× länger**

**Konsequenzen:**
- SEO-Schaden: EN content drift wird als "AI-generated low-quality" gewertet (Google EEAT)
- Inkonsistenter Lesefluss DE vs EN
- Plus: längere EN articles = höhere Translation-Cost + längere page-load

## 2. Ziel

**Drei orthogonale Fixes:**

**Fix A (Prompt Engineering):** Body-Step LLM-prompt explicit constraint geben: "Target word count: ±25% of source. Aim for concise translation, NOT verbose expansion."

**Fix B (Post-Translation Validation):** Pure-helper `validateWordDriftCap(sourceBody, targetBody, capPct)` der DE word-count vs EN word-count vergleicht. Bei drift > +25%: Step-level retry mit verstärktem prompt (1 retry max).

**Fix C (Validation-Result Threading):** Result als `wordDriftValidation` in OutputSchema (analog zu 64.4's `faqValidation`). Future UI kann beide visualisieren im EN-sibling review.

**In Scope:**
- Body-Step prompt erweitern: "Word-Count Constraint: target ≤ source × 1.25"
- Pure helper `validateWordDriftCap()` in `translation/lib/word-drift-validator.ts`
- Word-drift > +25% → Step retry mit `prompt: prompt + STRONGER_DRIFT_GUIDANCE` (1 retry max)
- OutputSchema erweitert um `wordDriftValidation: WordDriftValidationSchema.optional()`
- Tests: validator (5 cases), retry-mechanism (3 cases), prompt-injection (1 case)
- Plus: Pattern-Reuse from 64.4 — `#runWithFaqRetry` wird zu `#runWithValidationRetry` oder zweiter wrapper
- **Caveat:** wenn FAQ + Word-Drift beide retry triggern → max 1 retry total (nicht 2× retry)

**Out of Scope:**
- Validation auf andere Drift-Patterns (sentence-length, paragraph-count) — eigene future Spec
- Cap-Override per project setting (immer 25% für jetzt) — flat default
- Historical 17 affected articles fix — durch Reset-Cleanup gelöscht
- Cross-lingual word-count normalization (DE compounds vs EN multi-word) — 25% cap accommodates this
- FAQPage Schema (von 64.4 bereits skipped)
- DE→EN only (DE↔EN ist symmetric, EN→DE auch validated)

**Aufwand:** ~1h Implementation + ~30 Min Tests.

## 3. Architektur

### 3.1 Word-Drift Validator Helper (Fix B)

**File:** `packages/pipelines/src/article/translation/lib/word-drift-validator.ts` (neu)

```ts
/**
 * Counts words in markdown body, normalizing for markdown structures.
 * 
 * Excludes:
 * - Code blocks (``` fences)
 * - HTML/JSX tags
 * - Front-matter (---)
 * - Markdown link URLs (only link text counted)
 */
export function countBodyWords(body: string): number {
  let normalized = body;
  
  // Strip code blocks
  normalized = normalized.replace(/```[\s\S]*?```/g, "");
  normalized = normalized.replace(/`[^`]+`/g, "");
  
  // Strip front-matter
  normalized = normalized.replace(/^---[\s\S]*?---\n/m, "");
  
  // Strip HTML/JSX tags but keep inner text
  normalized = normalized.replace(/<[^>]+>/g, " ");
  
  // Markdown link: keep text, drop URL — [text](url) → text
  normalized = normalized.replace(/\[([^\]]+)\]\([^)]+\)/g, "$1");
  
  // Markdown image: drop entirely
  normalized = normalized.replace(/!\[[^\]]*\]\([^)]+\)/g, "");
  
  // Strip markdown syntax markers
  normalized = normalized.replace(/[#*_~`>|-]+/g, " ");
  
  // Count words: whitespace-split + non-empty filter
  return normalized
    .split(/\s+/)
    .filter(w => w.length > 0)
    .length;
}

/**
 * Validates word-drift cap: target should be within ±capPct% of source.
 * 
 * Drift convention: positive = target longer than source (inflation)
 *                   negative = target shorter than source (contraction)
 * 
 * Cap default 25% = target must be ≤ source × 1.25
 * No lower bound check — short translations are allowed (e.g. removed boilerplate).
 */
export interface WordDriftValidationResult {
  valid: boolean;
  sourceWords: number;
  targetWords: number;
  driftPct: number;     // positive = inflation, negative = contraction
  capPct: number;       // configured cap (default 25)
  message: string;
}

export function validateWordDriftCap(
  sourceBody: string,
  targetBody: string,
  capPct: number = 25,
): WordDriftValidationResult {
  const sourceWords = countBodyWords(sourceBody);
  const targetWords = countBodyWords(targetBody);
  
  // Avoid divide-by-zero
  if (sourceWords === 0) {
    return {
      valid: true,
      sourceWords: 0,
      targetWords,
      driftPct: 0,
      capPct,
      message: "Source has no words — drift check skipped",
    };
  }
  
  const driftPct = Math.round(((targetWords - sourceWords) / sourceWords) * 100);
  const valid = driftPct <= capPct;
  
  const message = valid
    ? `Word drift OK: ${sourceWords}→${targetWords} (${driftPct > 0 ? "+" : ""}${driftPct}%, cap ${capPct}%)`
    : `Word drift exceeded: ${sourceWords}→${targetWords} (+${driftPct}%, cap ${capPct}%)`;
  
  return { valid, sourceWords, targetWords, driftPct, capPct, message };
}
```

**Decision-Rationale:**
- **No lower bound** — short translations OK (z.B. EN drops German Modalpartikel "halt", "doch", "ja")
- **25% cap default** — 64.6b discovery zeigt avg drift +52%, so 25% ist aggressive aber realistic für concise translations
- **Code blocks excluded** — code shouldn't be translated (would inflate count irrelevantly)
- **Markdown links stripped** — URL text would inflate count

const WORD_COUNT_CONSTRAINT = `
**Word-Count Constraint (CRITICAL for SEO + readability):**
Aim for a target word count within ±25% of the source. Specifically:
- DO NOT add explanations, examples, or clarifications not in the source.
- DO NOT expand concise source phrases ("zudem", "daher", "etwa") into verbose English equivalents ("In addition to this fact,...", "As a result of which,...", "approximately around about...").
- Prefer concise translations: "Das bedeutet, dass..." → "This means..." (NOT "What this signifies is that...").
- If the source uses a compound noun ("Vertragsverlängerung"), translate to the natural English equivalent ("contract renewal"), not a verbose paraphrase.
- Source word count: {sourceWords}. Target word count should be ≤ {sourceWordsCap}.
`;
```

**Plus STRONGER variant für retry:**

```ts
const STRONGER_DRIFT_GUIDANCE = `
**CRITICAL RETRY: Previous translation exceeded the word-count cap.**
Source has {sourceWords} words. Previous attempt produced {previousTargetWords} words ({previousDriftPct}% over).
You MUST produce a translation with ≤{sourceWordsCap} words.
Strategies:
- Drop unnecessary qualifiers ("very", "really", "quite", "definitely")
- Use contractions where natural ("it is" → "it's", "do not" → "don't")
- Combine short sentences with semicolons or coordinating conjunctions
- Replace verbose phrases with concise equivalents ("at this point in time" → "now")
- Each paragraph should be roughly the same word count as its source paragraph
Re-check the word count BEFORE finalizing. The cap is a hard constraint.
`;
```

### 3.3 Pattern-Reuse: Generic Validation-Retry Helper

**Decision:** Statt 2 separate retry-helpers (`#runWithFaqRetry` + `#runWithDriftRetry`), erweitern wir 64.4's helper zu generic Multi-Validator:

```ts
// Generic shape, replaces #runWithFaqRetry from 64.4
async #runWithValidationRetry(args: {
  sourceBody: string;
  initialPrompt: string;
  validators: Array<{
    name: string;  // "faq" | "word-drift"
    validate: (source: string, target: string) => { valid: boolean; message: string; [key: string]: unknown };
    strongerGuidance: (validationResult: ReturnType<typeof this["validate"]>) => string;
  }>;
}): Promise<{ raw: string; validations: Record<string, unknown> }> {
  let attempt = 0;
  let raw: string;
  const validations: Record<string, unknown> = {};
  
  while (attempt < 2) {
    let promptSuffix = "";
    if (attempt > 0) {
      // Build cumulative stronger guidance for all invalid validators
      for (const v of args.validators) {
        const result = validations[v.name] as { valid: boolean } | undefined;
        if (result && !result.valid) {
          promptSuffix += "\n\n" + v.strongerGuidance(result);
        }
      }
    }
    
    raw = await this.#callLlm({
      prompt: args.initialPrompt + promptSuffix,
    });
    
    // Run all validators
    let allValid = true;
    for (const v of args.validators) {
      const result = v.validate(args.sourceBody, raw);
      validations[v.name] = result;
      if (!result.valid) allValid = false;
    }
    
    if (allValid) {
      log.info({ attempt, validations }, "translation validations all passed");
      break;
    }
    
    log.warn({ attempt, validations }, "translation validation failed");
    attempt++;
  }
  
  // Even after retry, return what we have — Marcel reviews
  if (Object.values(validations).some(v => !(v as { valid: boolean }).valid)) {
    log.error({ validations }, "translation validations persist after retry");
  }
  
  return { raw, validations };
}
```

**Plus calling convention im Body-Step:**

```ts
// In #runLiteralPath and #runAdaptivePath (von 64.4):
const { raw, validations } = await this.#runWithValidationRetry({
  sourceBody: input.sourceBody,
  initialPrompt: prompt,
  validators: [
    {
      name: "faq",
      validate: validateFaqPreservation,
      strongerGuidance: (r) => STRONGER_FAQ_GUIDANCE.replaceAll(
        "{sourceCount}",
        String((r as FaqValidationResult).sourceCount),
      ),
    },
    {
      name: "wordDrift",
      validate: (s, t) => validateWordDriftCap(s, t, 25),
      strongerGuidance: (r) => {
        const result = r as WordDriftValidationResult;
        const cap = Math.floor(result.sourceWords * (1 + result.capPct / 100));
        return STRONGER_DRIFT_GUIDANCE
          .replaceAll("{sourceWords}", String(result.sourceWords))
          .replaceAll("{previousTargetWords}", String(result.targetWords))
          .replaceAll("{previousDriftPct}", String(result.driftPct))
          .replaceAll("{sourceWordsCap}", String(cap));
      },
    },
  ],
});

return {
  body: parsed,
  faqValidation: validations.faq as FaqValidationResult,
  wordDriftValidation: validations.wordDrift as WordDriftValidationResult,
};
```

**Decision:** Max 1 retry total (nicht 2 retries für 2 validators). Wenn beide fail → 1 retry mit kumulativer guidance → either both fixed or both logged as failed. Cost-impact: 1 retry per article at most.

describe("countBodyWords", () => {

describe("validateWordDriftCap", () => {
  it("returns valid when drift is within cap", () => {
    const source = "Das ist ein Test mit zehn Wörtern in deutscher Sprache.";  // 10
    const target = "This is a test with ten words in English language total.";  // 10
    const result = validateWordDriftCap(source, target, 25);
    expect(result.valid).toBe(true);
    expect(result.driftPct).toBe(0);
  });
  
  it("returns valid when drift is +20% (within 25% cap)", () => {
    const source = "Ein zwei drei vier fünf sechs sieben acht neun zehn";  // 10
    const target = "One two three four five six seven eight nine ten eleven twelve";  // 12
    const result = validateWordDriftCap(source, target, 25);
    expect(result.valid).toBe(true);
    expect(result.driftPct).toBe(20);
  });
  
  it("returns invalid when drift exceeds cap (+50%)", () => {
    const source = "Eins zwei drei vier fünf sechs sieben acht neun zehn";  // 10
    const target = "One two three four five six seven eight nine ten eleven twelve thirteen fourteen fifteen";  // 15
    const result = validateWordDriftCap(source, target, 25);
    expect(result.valid).toBe(false);
    expect(result.driftPct).toBe(50);
    expect(result.message).toMatch(/exceeded.*\+50%.*cap 25%/);
  });
  
  it("allows arbitrarily short target (no lower bound)", () => {
    const source = "Ein langer deutscher Satz mit vielen vielen Wörtern hier drin total";  // 11
    const target = "Short.";  // 1
    const result = validateWordDriftCap(source, target, 25);
    expect(result.valid).toBe(true);
    expect(result.driftPct).toBeLessThan(0);
  });
  
  it("handles empty source gracefully (no divide-by-zero)", () => {
    const result = validateWordDriftCap("", "Some target text", 25);
    expect(result.valid).toBe(true);
    expect(result.driftPct).toBe(0);
    expect(result.message).toMatch(/no words.*skipped/);
  });
  
  it("respects custom capPct", () => {
    const source = "Eins zwei drei vier fünf";  // 5
    const target = "One two three four five six seven";  // 7
    
    expect(validateWordDriftCap(source, target, 25).valid).toBe(false);  // 40% > 25%
    expect(validateWordDriftCap(source, target, 50).valid).toBe(true);   // 40% ≤ 50%
  });
});

## 7. Risiken

| Risk | Mitigation |
|---|---|
| 25% cap zu aggressive für tatsächlich verbose source → false-positive bei jedem 2. article | Discovery zeigt avg drift +52% — 25% ist realistic cure-target. Wenn false-positives auftreten, cap kann später per project-setting (eigene Spec) |
| Cumulative retry-prompt blowed token-count → cost-impact | Max 1 retry per article. Plus: stronger guidance ist ~200 tokens, negligible vs source content tokens |
| Word-count heuristic falsch bei markdown edge-cases (z.B. nested tables, HTML embeds) | Tests cover common patterns; fallback returns 0 → "no validation possible" (acceptable) |
| Refactor `#runWithFaqRetry` → `#runWithValidationRetry` breaks 64.4 tests | Backwards-compat: existing FAQ tests pass single-validator array, behavior identical |
| LLM ignores word-count constraint trotz stronger guidance | After retry: step doesn't fail. Marcel reviews EN siblings before publish. Plus: cost-log shows drift visible. |
| countBodyWords zählt unterschiedlich für DE compounds vs EN words | Compound "Vertragsverlängerung" = 1 DE word, "contract renewal" = 2 EN words → built-in +100% bias bei compounds. 25% cap berücksichtigt das implicit (avg drift bleibt unter cap wenn LLM concise ist) |
| Same body-step.ts as 64.4 → merge conflict | Sequential merge: 64.4 first, then 64.5. Both Specs reference same file; second Spec extends helper structure |

## 9. Implemented

  - `WORD_COUNT_CONSTRAINT` constant with `{sourceWords}` + `{sourceWordsCap}` placeholders.
  - `STRONGER_DRIFT_GUIDANCE` constant with `{sourceWords}` + `{previousTargetWords}` + `{previousDriftPct}` + `{sourceWordsCap}` placeholders, substituted via `.replaceAll()` (multi-occurrence-safe per the 64.4 footgun).
  - `#runWithFaqRetry` → `#runWithValidationRetry`: runs **both** FAQ + word-drift validators after each attempt, builds a cumulative retry suffix from whichever validators failed. ## 10. Discovered & Deviations

| # | Discovery | Decision |
|---|---|---|
| 1 | `WORD_COUNT_CONSTRAINT` needs the actual source word count substituted at call time, but `countBodyWords` would have to run twice (once in path runner, once in retry helper) if both compute independently. | Both paths compute `sourceWords` + `sourceWordsCap` at the top of their runner. Retry helper recomputes internally for substituting `STRONGER_DRIFT_GUIDANCE` placeholders — duplicate `countBodyWords()` call is cheap (~ms regex pass). Trade ~µs for cleaner module boundaries. |
| 2 | `validateWordDriftCap` counts words on the LLM's RAW output, which still contains the `<TITLE>…</TITLE>`, `<META_DESCRIPTION>…</META_DESCRIPTION>`, `<TAGS>…</TAGS>` tagged blocks (parsed out only after validation). The TITLE+META+TAGS overhead is ~22 words. | Production: negligible relative to typical 500-3000-word bodies. Tests: had to bump fixture source bodies to ~350+ words so the +25% cap (≥ ~438 words) comfortably exceeds the tagged-block overhead. Did NOT change validator to strip tags first — keeping it source-shape-agnostic. |
| 3 | The spec's example test asserted `countBodyWords("**Bold** and *italic* text")` returns 3. Actual: 4. After stripping `*` markers the string becomes `Bold and italic text` = 4 words. | Spec example was off by one; fixed in test. The implementation is correct — `*` removal doesn't merge tokens. |
| 4 | The 64.4 helper signature took `buildUserMessage: (faqRetrySuffix: string) => string`. After refactor the suffix is cumulative for whichever validators failed (FAQ-only, drift-only, or both). | Renamed lambda param to `retrySuffix` (locale-neutral) across both path runners. Behaviourally identical for callers that pass FAQ-only content. |
| 5 | The 64.4 `lastValidation` was a single object. The refactor needs two separately-keyed validation results. | Helper now returns `{ raw, faqValidation, wordDriftValidation }`. Both call sites destructure and pass both into the `OutputSchema`. Old single-validator return shape is gone — no consumer outside `#runLiteralPath`/`#runAdaptivePath`. |
| 6 | Outline call in the adaptive path was NOT wrapped in 64.4's retry helper (it only emits headings, no FAQ items). Spec 64.5 §3.3 left this implicit. | Same decision: outline call stays unwrapped. Word-drift is a body-length concern and outline doesn't drive body length materially. If a future audit shows outline length correlates with body inflation, revisit. |
| 7 | The pre-existing typecheck failures in `test/article/hero-image-batch.test.ts` belong to an untracked WIP for Spec 64.7. | Not in 64.5 scope. Left untouched. Documented here so /review-task doesn't flag them as introduced by 64.5. |
| 8 | The validator runs even when 64.4 FAQ tests pass — they exercise short fixture bodies (~100 words) where the small target (~70-90 words) registers as -28% drift = valid. No 64.4 test regressed. | Backward-compat confirmed via running `body-step-faq-retry.test.ts` after the refactor: 3/3 pass with the new helper. |
