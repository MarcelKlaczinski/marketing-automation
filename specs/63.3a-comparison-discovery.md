# Mini-Task 63.3a — ComparisonDiscovery Manual Test-Run

**Modus: ONE-OFF EXECUTION. Kein Code, kein Spec. Daten-getriebene Vorbereitung für 63.3b-Entscheidung.**

**Aufwand: 5-15 Min.**

## Kontext

Theme-63-Discovery hat ergeben:
- ComparisonDiscovery existiert als implementierter + getesteter Algorithmus in `packages/planner/src/comparison-discovery.ts`
- Aber: **0 comparison_discovery briefs jemals erzeugt** für Toolwiki
- Grund: kein Cron, kein Worker, einziger Trigger ist manueller HTTP-Endpoint
- Endpoint: `POST /api/projects/:slug/comparison-discovery/run`

**Bevor wir den Cron in 63.3b spec'en, müssen wir wissen ob der Algorithmus überhaupt brauchbare Pairs findet.** Wenn 0 oder nur generic Pairs ("Tool A vs Tool B"), brauchen wir andere Strategie. Wenn 10+ sinnvolle Pairs, ist 63.3b ein no-brainer.

## Aufgabe

### Schritt 1 — Endpoint triggern

```bash
# Pfad bestätigen
grep -A 10 "comparison-discovery.*run\|comparisonDiscoveryRun" apps/api/src/routes/

# Trigger manuell
curl -X POST http://localhost:3050/api/projects/toolwiki/comparison-discovery/run
```

**Achten auf:**
- Response-Status: 200/202 (success), 4xx/5xx (Fehler)
- Response-Body: vermutlich `{ created: N, pairs: [...] }` oder ähnlich
- Wenn Endpoint async (BullMQ-Job): erst Job-Completion abwarten, dann DB checken

**Bei Fehler:** stop, in Report dokumentieren, NICHT versuchen zu fixen.

### Schritt 2 — Ergebnisse aus DB lesen

Nach Endpoint-Run:

```sql
-- Wieviele Briefs wurden erzeugt?
SELECT COUNT(*) FROM topic_briefs
WHERE source = 'comparison_discovery'
  AND project_id = (SELECT id FROM projects WHERE slug = 'toolwiki')
  AND created_at > NOW() - INTERVAL '15 minutes';
```

```sql
-- Konkret welche Briefs?
SELECT
  topic_title,
  suggested_title,
  intent_type,
  cluster_action,
  metadata->>'comparisonToolSlugs' AS tool_pair,
  metadata->>'commonUseCases' AS use_cases,
  created_at
FROM topic_briefs
WHERE source = 'comparison_discovery'
  AND project_id = (SELECT id FROM projects WHERE slug = 'toolwiki')
ORDER BY created_at DESC
  LIMIT 30;
```

```sql
-- Distribution: wie viele Tool-Pairs? Welche Use-Cases?
SELECT
  metadata->>'comparisonToolSlugs' AS pair,
  COUNT(*) AS briefs_for_pair
FROM topic_briefs
WHERE source = 'comparison_discovery'
  AND project_id = (SELECT id FROM projects WHERE slug = 'toolwiki')
GROUP BY pair
ORDER BY briefs_for_pair DESC
  LIMIT 20;
```

### Schritt 3 — Quality-Check der Top-Pairs

Stichprobe:
- Sind die Tool-Pairs sinnvoll? (z.B. "Claude vs ChatGPT" gut, "Loomly vs Asana" off-topic für Toolwiki)
- Haben die Pairs gemeinsame Use-Cases identifiziert?
- Sehen die `suggested_title` Texte nach gutem Comparison-Content aus?

- **Wenn 1-4 sinnvolle Pairs:** 63.3b mit niedrigerer Frequenz oder weiter manuell

## Anti-Patterns

- Code-Changes "while we're at it" am ComparisonDiscovery-Algorithmus
- Briefs automatisch approven
- /suggest auf die neuen Briefs triggern (eigene Diskussion)
- Trend-Brief Routing-Fix (A.3) berühren — separate Mini-Spec falls nötig
- ComparisonDiscovery-Algorithmus untersuchen wenn er Pairs liefert — nur wenn 0
