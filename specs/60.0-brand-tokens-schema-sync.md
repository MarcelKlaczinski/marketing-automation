# Spec 60.0 — brand_tokens Schema Sync + DS Token Extension

**Theme:** 60 (Design System Visual Refresh)
**Status:** Draft
**Estimated effort:** 1 day (~6-8 focused hours across 3 sessions)
**Prerequisite:** 59.3.5 layout-shift patterns shipped
**Successor:** 60.0b — Shared DS Components Library

---

## Goal

Resolve the existing divergence between the database `BrandTokens` TypeScript type and the runtime `brandTokensSchema` Zod schema, and extend the unified schema with the Design System tokens needed for Spec 60.1+ (Visual Refresh).

After 60.0 lands:
- One **source-of-truth** for brand_tokens: the Zod schema in `packages/social/`
- The DB type is **generated** from the Zod schema via `drizzle-zod`, eliminating manual drift
- The schema includes `brandHue` + `accentHue` numeric fields for deriving all DS color stops at render time
- Optional explicit overrides for `surfaceRaised` + `border` (the two DS tokens where derivation isn't reliable)
- Existing project brand_tokens data is migrated to the new shape via a data-transform script
- No render behavior changes — Spec 60.0 is purely a schema correctness fix + extension; consumption happens in 60.0b and 60.1+

## What this is NOT

- Not a visual change — no compositions modified
- Not a Settings UI expansion — UI work happens in 60.1 (adds `brandHue` slider when needed)
- Not a DS component library — that's 60.0b
- Not a migration to multi-theme storage — themes are still chosen at render-time via the `theme: "dark" | "light"` parameter; brand_tokens hold the brand-specific values used by both themes
- Not a removal of unused fields — deprecation notes are added, removal deferred to a future cleanup spec

## Background: the divergence (per Audit Section 1)

The audit surfaced that `BrandTokens` (DB type in `packages/db/src/schema/projects.ts`) and `brandTokensSchema` (Zod schema in `packages/social/src/compositions/list-carousel/types.ts`) have diverged:

**Only in DB type** (typography, mostly older / unused at render time):
- `typography.fontFamilyOptions`, `eyebrowWeight`, `captionWeight`
- `typography.headingLetterSpacing`, `bodyLetterSpacing`
- `typography.headingSize`, `subheadSize`, `bodySize`, `eyebrowSize`
- `typography.headingLineHeight`, `bodyLineHeight`

**Only in Zod schema** (color + render-time additions):
- `colors.surfaceSecondary`, `eyebrowColor`
- `colors.pricingFree`, `pricingFreemium`, `pricingPaid`
- `colors.prosColor`, `consColor` (added in 59.3)
- `typography.rankBadgeSize/Weight/LetterSpacing`
- `typography.footerWebsiteSize/HandleSize/LabelSize/Gap`

The Zod schema is the contract used at render-time (compositions consume it via `BrandTokens` import from `list-carousel/types.ts`). The DB type is what gets stored. When the two disagree, stored data may have fields the renderer ignores, and rendered fields may have no DB column to be stored in.

## Section A — Schema Unification

### A.1 Source-of-truth: Zod schema in `packages/social/`

`brandTokensSchema` (Zod) is the single source of truth. The DB `BrandTokens` type is derived from it via `drizzle-zod`.

**Why Zod, not DB type:**
- The render path is the load-bearing consumer (every Remotion render reads brand_tokens via `BrandTokens` from Zod)
- Render-time validation already happens against the Zod schema
- Adding a new color/typography field means modifying the renderer first; the DB schema follows
- `drizzle-zod` is already a dependency (or trivial to add) for syncing the two

### A.2 New file structure

The Zod schema moves out of `list-carousel/types.ts` (where it currently lives for historical reasons) into a top-level location:

```
packages/social/src/brand-tokens/
  schema.ts          ← brandTokensSchema (Zod, source-of-truth)
  types.ts           ← exported type BrandTokens = z.infer<typeof brandTokensSchema>
  derive.ts          ← deriveDsTokens(brandTokens, theme) — used in 60.0b
  defaults.ts        ← DEFAULT_BRAND_TOKENS object (replaces inline .default() chains where useful)
  index.ts           ← barrel export
```

`list-carousel/types.ts` re-exports from `brand-tokens/` for back-compat, with a JSDoc note marking the re-export as deprecated for new code.

### A.3 The unified schema (post-60.0)

```typescript
// packages/social/src/brand-tokens/schema.ts

export const brandTokensSchema = z.object({
  colors: z.object({

    accentHue: z.number().min(0).max(360).default(168),

    // Surface — light + dark base values (used by getThemeTokens at render time)
    surface: z.string().default("#ffffff"),
    surfaceDark: z.string().default("oklch(16% 0.02 250)"),

    // Optional surface stops (DS adds these; if absent, derived from surface/surfaceDark)
    surfaceRaised: z.string().optional(),
    surfaceRaisedDark: z.string().optional(),
    surfaceSunken: z.string().optional(),
    surfaceSunkenDark: z.string().optional(),

    // Borders — optional override
    border: z.string().optional(),
    borderDark: z.string().optional(),

    // Ink (text foreground)
    ink: z.string().default("oklch(20% 0.025 250)"),
    inkMuted: z.string().default("oklch(45% 0.025 250)"),

    // Semantic colors
    pricingFree: z.string().default("#22c55e"),
    pricingFreemium: z.string().default("#3b82f6"),
    pricingPaid: z.string().default("#f59e0b"),

    consColor: z.string().optional(),

    // DEPRECATED — kept for back-compat, will be removed in a future spec

    surfaceSecondary: z.string().optional(),
    /** @deprecated Use accent + theme handling instead */
    eyebrowColor: z.string().optional(),
    /** @deprecated Use brandHue (no longer stored as separate field) */
    primaryHue: z.number().optional(),
    /** @deprecated toolwiki-specific legacy color, not in DS reference */
    wikiCream: z.string().optional(),
  }),

  typography: z.object({
    fontFamily: z.string().default("Inter Variable, Inter, sans-serif"),
    fontFamilyMono: z.string().default("ui-monospace, 'SF Mono', 'JetBrains Mono', Menlo, monospace"),

    headingWeight: z.number().int().min(100).max(900).default(800),
    bodyWeight: z.number().int().min(100).max(900).default(400),
    eyebrowLetterSpacing: z.string().default("0.08em"),

    // Rank badge — list-carousel specific
    rankBadgeSize: z.number().default(72),
    rankBadgeWeight: z.number().int().min(100).max(900).default(900),
    rankBadgeLetterSpacing: z.string().default("-0.03em"),

    // Footer — used across templates
    footerWebsiteSize: z.number().default(20),
    footerHandleSize: z.number().default(16),
    footerLabelSize: z.number().default(18),
    footerGap: z.number().default(2),
  }),

  voice: z.object({
    locale: z.string().default("de-DE"),
    addressForm: z.enum(["du", "Sie"]).default("du"),
    forbiddenWords: z.array(z.string()).default([]),
    signaturePhrases: z.array(z.string()).default([]),
  }),

  social: z.object({
    instagramHandle: z.string().default("@toolwiki.ai"),
    websiteUrl: z.string().default("toolwiki.ai"),
    logoAssetKey: z.string().default("main"),
  }),
}).strip();

export type BrandTokens = z.infer<typeof brandTokensSchema>;
```

## Section B — DS Token Additions

### B.1 `brandHue` + `accentHue` as the primary multi-color knob

The DS uses a single hue per scale and derives 7 lightness/chroma stops from it (per Audit Section 2A). Storing the hue (a number) instead of every stop (7 strings) is more compact and matches the DS design model.

```typescript
brandHue: 248    // toolwiki blue
accentHue: 168   // toolwiki mint/cyan
```

Spec 60.0b implements `deriveDsTokens(brandTokens, theme)` which returns the full token set including all 7 brand stops + 2 accent stops, derived from the hue at render time.

### B.2 Why `primary` and `accent` strings are kept

Backward compatibility. The current compositions read `brandTokens.colors.primary` and `brandTokens.colors.accent` as direct strings. Removing them would require touching every composition immediately, which is out of scope for 60.0.

Going forward (60.0b + 60.1+):
- New code uses `deriveDsTokens(brandTokens, theme)` → returns `{ brand: { 50, 100, 300, 500, 700, 900, 950 }, accent: { 500, 600 }, ... }`
- Legacy code reading `brandTokens.colors.primary` continues to work — the renderer keeps the string in sync with `oklch(64% 0.16 ${brandHue})` (Section B.4)

### B.3 `surfaceRaised` + `border` as optional overrides

For most projects, surface-raised and border can be derived from the base surface color (lighten by ~3-5% for raised, darken by ~8% for border in light mode; inverse in dark). But the DS specifies precise values that don't always follow a simple formula (it uses chroma + hue shifts at certain stops).

Two-pronged approach:
- `surfaceRaised` is optional. If set, used directly. If not set, derived from `surface` via a lightness shift.
- Same for `border`.

This keeps Settings UI simple (most projects never touch these) but allows explicit overrides when brand demands it.

### B.4 Keeping `primary`/`accent` synced with hue (data integrity)

When a project sets `brandHue: 248` but `primary: "oklch(64% 0.16 100)"` (stale value from old hue), the renderer would render inconsistently.

**Convention**: When `brandHue` is set (i.e. not `undefined`), the renderer ignores `primary` and computes it as `oklch(64% 0.16 ${brandHue})`. This is implemented in `deriveDsTokens()` in 60.0b — Spec 60.0 just adds the field.

A unit test verifies the convention; the Settings UI for `brandHue` (added later) should also update `primary` on save to keep stored data consistent.

## Section D — Data Migration Script

### D.1 Goal

Transform all existing `projects.brand_tokens` JSONB values to match the new schema shape. After migration:
- Every project's `brand_tokens` parses cleanly against the new `brandTokensSchema`
- No data loss (deprecated fields preserved unless they're being removed; renames carry values across)
- Idempotent (running twice produces the same result)

### D.2 Script location + execution

```
packages/db/migrations/scripts/0042-brand-tokens-schema-sync.ts
```

Runs as a one-off script via `bun run --cwd packages/db migrate:custom 0042-brand-tokens-schema-sync` after the corresponding Drizzle migration adds any new JSONB shape expectations.

Actually a JSONB column doesn't need a Drizzle migration for shape changes (the column type is just `jsonb`). The migration is a pure data-transform script:

```typescript
// packages/db/migrations/scripts/0042-brand-tokens-schema-sync.ts

import { db } from "../../src/client";
import { projects } from "../../src/schema/projects";
import { eq } from "drizzle-orm";

const DEPRECATED_TYPOGRAPHY_FIELDS = [
  "fontFamilyOptions",
  "eyebrowWeight",
  "captionWeight",
  "headingLetterSpacing",
  "bodyLetterSpacing",
  "headingSize",
  "subheadSize",
  "bodySize",
  "eyebrowSize",
  "headingLineHeight",
  "bodyLineHeight",
] as const;

export async function run() {
  const allProjects = await db.select().from(projects);

  for (const project of allProjects) {
    const original = (project.brandTokens ?? {}) as Record<string, any>;
    const transformed = transformBrandTokens(original);
    const changed = JSON.stringify(transformed) !== JSON.stringify(original);

    if (changed) {
      await db
        .update(projects)
        .set({ brandTokens: transformed })
        .where(eq(projects.id, project.id));
      console.log(`Migrated project ${project.id}: ${project.name}`);
    }
  }
}

function transformBrandTokens(input: Record<string, any>): Record<string, any> {
  const colors = { ...(input.colors ?? {}) };
  const typography = { ...(input.typography ?? {}) };
  const voice = { ...(input.voice ?? {}) };
  const social = { ...(input.social ?? {}) };

  // Rename primaryHue → brandHue (keep old field with deprecated marker via comment in code)
  if (colors.primaryHue !== undefined && colors.brandHue === undefined) {
    colors.brandHue = colors.primaryHue;
  }

  // accentHue default if not present (derived from accent oklch hue)
  if (colors.accentHue === undefined) {
    colors.accentHue = extractHueFromOklch(colors.accent) ?? 168;
  }

  // brandHue default if not present
  if (colors.brandHue === undefined) {
    colors.brandHue = extractHueFromOklch(colors.primary) ?? 248;
  }

  // Drop DB-only typography fields that were never consumed
  for (const field of DEPRECATED_TYPOGRAPHY_FIELDS) {
    delete typography[field];
  }

  return { colors, typography, voice, social };
}

function extractHueFromOklch(value: string | undefined): number | null {
  if (!value || typeof value !== "string") return null;
  // Match oklch(L% C H) — capture the H number
  const match = value.match(/oklch\(\s*[\d.]+%\s+[\d.]+\s+([\d.]+)/i);
  if (!match) return null;
  const hue = parseFloat(match[1]!);
  return Number.isFinite(hue) ? hue : null;
}

// Run if invoked directly
if (import.meta.main) {
  await run();
  console.log("Done.");
  process.exit(0);
}
```

### D.3 Pre-migration backup

The migration script begins with a one-line backup:

```typescript
console.log("Backing up brand_tokens to projects_brand_tokens_backup_0042 ...");
await db.execute(sql`
  CREATE TABLE IF NOT EXISTS projects_brand_tokens_backup_0042 AS
  SELECT id, brand_tokens, NOW() AS backed_up_at FROM projects;
`);
```

If anything goes wrong, restore via:
```sql
UPDATE projects p
SET brand_tokens = b.brand_tokens
FROM projects_brand_tokens_backup_0042 b
WHERE p.id = b.id;
```

The backup table is dropped manually after 30 days via cleanup script (or kept indefinitely — it's a few KB per project).

### D.4 Idempotency

Running the migration twice produces the same result because:
- Field renames check the destination first: `if (colors.brandHue === undefined) colors.brandHue = colors.primaryHue`
- Default-injection only happens when the field is absent
- Field-drops are no-ops the second time (already absent)

### D.5 Validation post-migration

After the script runs, every project's `brand_tokens` must parse against the new Zod schema:

```typescript
// At the end of the migration script:
for (const project of await db.select().from(projects)) {
  const result = brandTokensSchema.safeParse(project.brandTokens);
  if (!result.success) {
    console.error(`Project ${project.id} FAILS schema validation:`, result.error.format());
    throw new Error(`Migration left invalid data for project ${project.id}`);
  }
}
console.log(`All ${allProjects.length} projects pass schema validation.`);
```

## Section E — drizzle-zod Integration

### E.1 Goal

Make `BrandTokens` in `packages/db` automatically reflect changes to `brandTokensSchema` in `packages/social`. No more manual sync.

### E.2 Dependency direction

`packages/db` currently has no dependency on `packages/social` (intentional — db is upstream of most other packages).

To avoid creating a circular or upward dependency, the Zod schema lives in **`packages/shared`** (already a dependency of both `packages/db` and `packages/social`), not in `packages/social`.

**Revised file location:**

```
packages/shared/src/brand-tokens/
  schema.ts          ← brandTokensSchema (Zod, source-of-truth)
  types.ts           ← BrandTokens = z.infer<typeof brandTokensSchema>
  defaults.ts        ← DEFAULT_BRAND_TOKENS
  index.ts           ← barrel export
```

`packages/social/src/brand-tokens/` becomes a re-export and adds the `derive.ts` (which lives in social because it's render-time concern, not storage concern):

```
packages/social/src/brand-tokens/
  derive.ts          ← deriveDsTokens(brandTokens, theme) — implemented in 60.0b
  index.ts           ← re-exports from @marketing-auto/shared/brand-tokens
                       + adds derive.ts
```

### E.3 DB type generation

In `packages/db/src/schema/projects.ts`:

```typescript
import { brandTokensSchema, type BrandTokens } from "@marketing-auto/shared/brand-tokens";
import type { z } from "zod";

export const projects = pgTable("projects", {
  // ... other columns
  brandTokens: jsonb("brand_tokens").$type<BrandTokens>().notNull().default({} as BrandTokens),
});

// Re-export for downstream consumers that imported from packages/db before
export type { BrandTokens };
```

No more `BrandTokens` interface defined in `packages/db`. Single import line, no duplicated type.

### E.4 Runtime validation at write time

When the API writes brand_tokens (e.g. settings save endpoint), it parses through the Zod schema:

```typescript
// apps/api/src/routes/projects.ts or wherever brand_tokens is updated
import { brandTokensSchema } from "@marketing-auto/shared/brand-tokens";

const parsed = brandTokensSchema.parse(body.brandTokens);  // throws on invalid
await db.update(projects).set({ brandTokens: parsed }).where(eq(projects.id, projectId));
```

This is the missing validation that currently allows malformed data into the DB. Adding it as part of 60.0 catches drift early going forward.

## Section F — Tests + Verification

### F.1 Unit tests

```typescript
// packages/shared/test/brand-tokens-schema.test.ts

import { describe, it, expect } from "vitest";
import { brandTokensSchema, DEFAULT_BRAND_TOKENS } from "../src/brand-tokens";

describe("brandTokensSchema", () => {
  it("parses an empty object to defaults", () => {
    const result = brandTokensSchema.parse({});
    expect(result.colors.brandHue).toBe(248);
    expect(result.colors.accentHue).toBe(168);
    expect(result.typography.fontFamily).toContain("Inter");
  });

  it("preserves explicit brandHue", () => {
    const result = brandTokensSchema.parse({ colors: { brandHue: 12 } });
    expect(result.colors.brandHue).toBe(12);
  });

  it("strips unknown fields", () => {
    const result = brandTokensSchema.parse({
      colors: { brandHue: 100, totallyMadeUpField: "x" },
    }) as any;
    expect(result.colors.totallyMadeUpField).toBeUndefined();
  });

  it("rejects out-of-range hue", () => {
    expect(() => brandTokensSchema.parse({ colors: { brandHue: 400 } })).toThrow();
  });

  it("accepts optional surfaceRaised without requiring it", () => {
    const a = brandTokensSchema.parse({});
    expect(a.colors.surfaceRaised).toBeUndefined();
    const b = brandTokensSchema.parse({ colors: { surfaceRaised: "oklch(99% 0.005 250)" } });
    expect(b.colors.surfaceRaised).toBe("oklch(99% 0.005 250)");
  });
});
```

### F.2 Migration script tests

```typescript
// packages/db/test/migrations/0042-brand-tokens-schema-sync.test.ts

import { describe, it, expect } from "vitest";
import { transformBrandTokens } from "../../migrations/scripts/0042-brand-tokens-schema-sync";

describe("transformBrandTokens (migration 0042)", () => {
  it("renames primaryHue → brandHue", () => {

    expect(out.colors.brandHue).toBe(248);

  });

  it("falls back to default brandHue if primary is unparseable", () => {
    const input = { colors: { primary: "#ff0000" } };

  });

  it("drops deprecated typography fields", () => {
    const input = {
      typography: {

        fontFamilyOptions: ["Roboto"],
        eyebrowWeight: 500,

    const out = transformBrandTokens(input);
    expect(out.typography.fontFamily).toBe("Inter");
    expect(out.typography.fontFamilyOptions).toBeUndefined();

  it("produces output that parses cleanly against the schema", () => {
```

3. **Should the verification script run on every CI build, or only on the migration PR?**

  - PR-only: faster CI, but drift goes undetected
  - Default: every build (cheap; pure read).

4. **Should `primary`/`accent` strings be auto-synced when `brandHue`/`accentHue` changes?**
  - At API write time (recommended): when the request body includes a new `brandHue`, recompute `primary` = `oklch(64% 0.16 ${brandHue})` and overwrite the stored `primary`. Keeps DB consistent.
  - At render time only: `deriveDsTokens` always computes from hue; stored `primary` is ignored. Drift in DB is invisible.
  - Default: auto-sync at write time.
