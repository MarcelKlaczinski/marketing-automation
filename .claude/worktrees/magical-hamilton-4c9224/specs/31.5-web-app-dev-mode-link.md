# Spec 31.5: Dev-Mode Magic Link Console Output

**Phase:** 4 (Web App Foundation Wave 1) — small enhancement spec
**Estimated Effort:** 1-2 hours (single session)
**Dependencies:** Spec 11.5 (email adapter), Spec 31 (auth UI — must be implemented or in progress)
**Status:** Ready for implementation
**Recommended Model:** Sonnet 4.6 (small, focused change)

---

## Goal

Improve the dev-mode console output of the email adapter so the **magic link URL is prominently displayed and easy to copy**. Currently the `sendEmail()` dev-fallback logs only the first 200 characters of the HTML body, which can hide the verify URL inside an `<a href>` tag.

After this spec:
- When SMTP is unconfigured, sending a magic link produces a clearly formatted, easy-to-spot console block
- The verify URL is on its own line, NOT embedded in HTML
- The format is consistent across all magic-link-style emails (auth, future password reset if added)
- The login flow is fully usable WITHOUT any email setup — Marcel copies the URL from the API server console and pastes it into his browser

This is **the canonical onboarding path** for new users (Marcel today, future Bellemann/Balkonkraftwerk admins): no SMTP setup needed for first-time login. SMTP can be configured later via the installer.

## Why this matters now

Marcel does not have an email account he wants to dedicate to SMTP yet. Setting up Gmail App Password requires:
1. A Gmail account
2. 2FA enabled on it
3. App Password generation
4. Storing the credential securely

For day-1 access to the system, all of that is friction. The magic-link mechanism via console log is **already the dev fallback**, but the current implementation doesn't surface the URL well. This spec fixes that.

## Non-Goals

- **No new auth methods** — Magic-link remains the only login path
- **No password authentication** — Out of scope; if Marcel ever wants this, it's a future spec
- **No automatic browser opening** of the verify URL — Marcel copies/pastes manually (avoids OS-specific code, more transparent)
- **No structured log output (JSON) for parsing** — purely human-readable terminal formatting
- **No removal of HTML email body** — when SMTP IS configured, full HTML is still sent. This spec only changes the dev-fallback path.

## Detailed Implementation

### Change 1: Add a `devLog` parameter to the email adapter

The current adapter logs HTML truncated. We need a way for `sendMagicLinkEmail()` to provide a **structured dev-log payload** that the adapter prints prominently when in fallback mode.

`packages/adapters/email/src/types.ts` — extend `SendEmailInput`:

```typescript
export type SendEmailInput = {
  // ... existing fields ...

  /**
   * Structured payload for dev-mode console output.
   * When SMTP is NOT configured, this object is pretty-printed to stdout
   * instead of (or alongside) the truncated HTML body.
   *
   * Use this for emails where a specific URL or token is the primary content.
   * Example for magic-link: { primaryAction: "Click to sign in", url: "https://..." }
   */
  devLog?: {
    primaryAction: string;
    url?: string;
    token?: string;
    expiresInMinutes?: number;
    additionalLines?: string[];
  };
};
```

### Change 2: Update the dev-fallback console output

`packages/adapters/email/src/client.ts` — replace the existing dev-fallback block:

```typescript
if (!transporter) {
  log.warn(
    { to: input.to, subject: input.subject, operation: input.operation },
    "SMTP not configured — email logged to console (dev fallback)",
  );

  if (input.devLog) {
    // Pretty-print the structured payload for easy human reading
    printDevLogBlock({
      subject: input.subject,
      to: input.to,
      operation: input.operation,
      ...input.devLog,
    });
  } else {
    // Generic fallback for emails without structured devLog
    console.log(
      `\n📧 Email (would-be-sent) — ${input.subject}\n` +
      `   To: ${input.to}\n` +
      `   ${input.html.slice(0, 200)}${input.html.length > 200 ? "…" : ""}\n`,
    );
  }

  return { messageId: "dev-fallback", delivered: false };
}
```

Add the helper function below the main client export:

```typescript
function printDevLogBlock(payload: {
  subject: string;
  to: string;
  operation: string;
  primaryAction: string;
  url?: string;
  token?: string;
  expiresInMinutes?: number;
  additionalLines?: string[];
}): void {
  const divider = "═".repeat(72);
  const lines: string[] = [
    "",
    divider,
    `📧  EMAIL (DEV FALLBACK — SMTP not configured)`,
    divider,
    `Subject:    ${payload.subject}`,
    `To:         ${payload.to}`,
    `Operation:  ${payload.operation}`,
    "",
    `${payload.primaryAction}:`,
  ];

  if (payload.url) {
    lines.push("");
    lines.push(`   ${payload.url}`);
    lines.push("");
  }

  if (payload.token && !payload.url) {
    lines.push("");
    lines.push(`   Token: ${payload.token}`);
    lines.push("");
  }

  if (typeof payload.expiresInMinutes === "number") {
    lines.push(`Expires in: ${payload.expiresInMinutes} minutes`);
  }

  if (payload.additionalLines) {
    lines.push("");
    lines.push(...payload.additionalLines);
  }

  lines.push(divider);
  lines.push("");

  // Use console.log for direct stdout — pino logger would format as JSON
  console.log(lines.join("\n"));
}
```

### Change 3: Update `sendMagicLinkEmail()` to populate `devLog`

`packages/adapters/email/src/client.ts` — modify the existing `sendMagicLinkEmail`:

```typescript
export async function sendMagicLinkEmail(input: SendMagicLinkInput): Promise<SendEmailResult> {
  const html = `
    <div style="font-family:-apple-system,sans-serif;max-width:480px;margin:24px auto;color:#1a1a1a;">
      <h1 style="font-size:18px;margin:0 0 16px;">Sign in to Marketing Automation</h1>
      <p style="font-size:14px;line-height:1.5;margin:0 0 24px;">
        Click the button below to sign in. This link expires in ${input.expiresInMinutes} minutes
        and can only be used once.
      </p>
      <a href="${input.verifyUrl}"
         style="display:inline-block;background:#0066ff;color:#fff;padding:12px 24px;
                border-radius:6px;text-decoration:none;font-weight:500;">
        Sign in
      </a>
      <p style="font-size:12px;color:#666;margin:24px 0 0;line-height:1.5;">
        If you didn't request this, you can safely ignore this email.<br>
        Or copy this link: <span style="word-break:break-all;">${input.verifyUrl}</span>
      </p>
    </div>
  `.trim();

  const text = [
    "Sign in to Marketing Automation",
    "",
    input.verifyUrl,
    "",
    `This link expires in ${input.expiresInMinutes} minutes.`,
  ].join("\n");

  return sendEmail({
    projectId: input.projectId ?? null,
    operation: "magic-link",
    to: input.to,
    subject: "Sign in to Marketing Automation",
    html,
    text,
    devLog: {
      primaryAction: "🔐  Magic link (copy this URL into your browser)",
      url: input.verifyUrl,
      expiresInMinutes: input.expiresInMinutes,
      additionalLines: [
        `Recipient: ${input.to}`,
        `Note:      Configure SMTP via the installer to send real emails.`,
      ],
    },
  });
}
```

Add a section to the README (or create one if absent at `apps/api/README.md`):

```markdown
## First-time login (no SMTP setup needed)

The system uses magic-link authentication. SMTP is optional — for development, magic-link URLs are printed to the API server console.

To log in for the first time:

1. Make sure the API server is running: `bun --filter @marketing-auto/api dev`
   ```

════════════════════════════════════════════════════════════════════════

## Acceptance Criteria

- [ ] `SendEmailInput` type has new optional `devLog` field with the documented shape
- [ ] When `devLog` is present and SMTP is unconfigured, the adapter prints a clearly formatted block with the URL on its own line
- [ ] The block is bordered by `═` characters and uses 📧 / 🔐 emoji for visibility
- [ ] When `devLog` is absent (legacy callers), the adapter falls back to the existing 200-char HTML truncation behavior
- [ ] `sendMagicLinkEmail()` always provides a `devLog` payload so magic links never use the truncation fallback
- [ ] Verify URL is fully visible (not truncated) regardless of length
- [ ] When SMTP IS configured: dev-log output is suppressed, normal email is sent (existing behavior unchanged)
- [ ] Frontend i18n strings (`auth.login.checkServerLogHint`) reference the new console block format
- [ ] Manual test: stop SMTP env vars, restart API, attempt login from web app → URL appears in API console, copy-paste works, login succeeds
- [ ] README section explaining dev-mode login is added or updated

## Open Questions / Decisions Made

**Decision 1: `devLog` is optional, falls back to old HTML truncation.**
Backward compat. Other emails (cost alerts, briefings) that haven't been updated still work, just with the truncated fallback.

**Decision 2: `console.log` directly, not via the pino logger.**
The pino logger formats as JSON for production observability. For dev-fallback console output, we want human-readable text, so we go around pino. The structured log via `log.warn(...)` still happens for parseable history.

**Decision 3: Emoji for visual scanning.**
A line of `═` plus 📧 and 🔐 makes the block easy to spot in a terminal full of debug logs. Marcel knows what to look for.

**Decision 4: Token alone (without URL) is also supported.**
Future use case: if we ever add a different auth mechanism (e.g., one-time codes), the same `devLog` shape supports it via the `token` field. For magic links specifically, the URL is what matters.

**Decision 5: No production-mode toggle.**
The dev-fallback only triggers when SMTP credentials are absent. There's no separate "dev mode" flag — credentials presence IS the signal. Avoids configuration creep.

**Decision 6: README addition is essential.**
A future user (or Marcel after a long pause) needs to understand the dev-mode login flow at a glance. The README is the discovery surface.

## Discovered During Implementation

**`printDevLogBlock` placed after callers — valid due to function hoisting.**
The helper is defined at the bottom of `client.ts` (after `sendMagicLinkEmail`), but called from
`sendEmail` which is defined earlier. TypeScript/ESM hoist regular `function` declarations within
the module scope, so this is safe. Arrow-function `const` would require forward declaration.

**Legacy `else` branch also needs the `console.log` justification comment.**
The spec only mentioned the comment for `printDevLogBlock`, but the pre-existing `else` branch
(backward compat truncation) uses the same `console.log` pattern and was missing it. Added for
consistency so any reader understands both intentional usages.
