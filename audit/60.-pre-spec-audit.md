### Task 5 — 9:16 → 4:5 adaptation analysis

The HTML files are 1080×1920 (9:16, Instagram Reels/Stories aspect).
The compositions render 1080×1350 (4:5, Instagram feed aspect).

For each of the 10 HTML files:
1. Identify the visual elements
2. Determine which are vertically positioned in a way that won't fit 4:5 as-is
3. Recommend an adaptation strategy per template

Three adaptation strategies are likely:

- **Compress**: reduce vertical spacing proportionally (570px tighter overall); risk: text feels cramped
- **Crop**: remove the "tall middle" or a non-essential top/bottom section; risk: losing visual hierarchy
- **Reflow**: change layout from vertical-stack to grid; risk: more invasive, but most layout-preserving

Output per template: which strategy fits, where the 570px disappear, what visual element absorbs the reduction.

### Task 6 — Multi-theme schema recommendation

Based on Task 4 Gap C, recommend ONE schema structure for multi-theme `brand_tokens`. Three candidates to evaluate:

**Candidate 1 — Nested themes**:
```ts
brand_tokens: {
  light: { background, foreground, accent, ... },
  dark:  { background, foreground, accent, ... },
  shared: { logoUrl, fontFamily, ... }
}
```

**Candidate 2 — Flat with theme suffix**:
```ts
brand_tokens: {
  backgroundLight, foregroundLight, accentLight,
  backgroundDark,  foregroundDark,  accentDark,
  logoUrl, fontFamily, ...
}
```

**Candidate 3 — Theme overlay**:
```ts
brand_tokens: {
  /* defaults are light */
  background, foreground, accent, logoUrl, fontFamily,
  /* dark overrides only the fields that differ */
  darkOverrides: { background?, foreground?, accent? }
}
```

Recommend ONE with rationale. Consider:
- Settings UI complexity (how many input fields user sees)
- Migration path from current single-theme schema
- Render-time switch ergonomics (what does the composition receive?)
- Future-proofing (3rd theme? "high-contrast" variant?)

### Task 9 — LLM Constraint Injection: current state + recommendation

**Background**: Spec 59.3.5 Section A.2 establishes a `*Bounds` object as the single source of truth for content lengths. Section F handles post-LLM validation (Zod parse + reprompt). But the *prompt-side* mechanic — how the LLM learns about the bounds in the first place — is intentionally left open in 59.3.5. This audit task surfaces the empirical state and recommends a mechanic.

**What to investigate** for each of the 5 templates:

1. **Current state**: Find the LLM prompt-construction code for each template's `generateContent()`. How are length constraints currently communicated to the LLM?
  - Hardcoded in prompt string? (e.g. `"maximal 80 Zeichen"`)
  - Read from the `*Bounds` object dynamically?
  - Not communicated at all? (relying on the LLM to "guess right")
  - Mixed (some fields bounded in prompt, others not)?

2. **Drift detection**: For each template, compare:
  - Bounds in `*Bounds` object (post 59.3.5)
  - Bounds mentioned in the LLM prompt string
  - Are they consistent? Or has one drifted from the other?

   Output table:

   | Template | Field | Bounds-object max | Prompt-string max | Drift? |
      |----------|-------|-------------------|-------------------|--------|
   | ...      | ...   | 80                | 100               | ⚠️     |

3. **Reprompt observation** (if data available): query `pipeline_runs` for the last 50 renders per template. Count how many required a reprompt (Section F.2 mechanic). High reprompt rate = LLM not getting clear-enough constraint signal in the initial prompt.

   If no reprompt-tracking column exists yet (not implemented by 59.3.5 Session 1 or 2), flag as missing telemetry in Section 9.

4. **Bilingual implications**: The 5 templates run in both DE and EN. Inspect each template's prompt for:
  - Is there a single prompt with locale-conditional sections?
  - Or two separate prompts (DE + EN)?
  - For each, how are bounds communicated per locale?

   **Note**: Marcel has decided that bound communication should be locale-specific (du-form imperative in DE, plain imperative in EN). The audit should report whether the current implementation supports this or needs refactoring.

5. **Mechanic recommendation**: Three candidates to evaluate. Marcel's preference is Candidate B; the audit confirms or pushes back based on empirical findings.

   **Candidate A — Inline strings (status quo)**:
   ```ts
   const prompt = `... Schreibe einen verdict_snippet, maximal 80 Zeichen. ...`;
   ```
   Pros: simple, every template-author tips it themselves.
   Cons: drift risk between bounds-object and prompt-string. No mechanical guarantee of consistency.

   **Candidate B — Auto-injection from bounds object (Marcel's preference)**:
   ```ts
   import { buildConstraintBlock } from "@marketing-auto/social/llm";

   const prompt = `${promptBody}\n\n${buildConstraintBlock(proConVerdictBounds, locale)}`;
   ```
   Helper formats the bounds-object into a structured "Format Requirements" block at the end of the prompt. Locale-specific formatting (DE du-form imperative, EN imperative).
   Pros: single source of truth, no drift, mechanical consistency.
   Cons: new helper to write + test. Initial setup cost.

   **Candidate C — Hybrid (template-level opt-in)**:
   Per-template flag `useAutoConstraintInjection: true/false`. Easier rollout but creates two patterns to maintain.

6. **`buildConstraintBlock` design sketch** (if Candidate B is recommended):
  - Input: `Bounds` object + locale
  - Output: formatted string block, ~5-15 lines
  - Locale-specific:
    - DE: `"Format-Vorgaben:\n- verdict_snippet: 30–80 Zeichen\n- when_to_use: 40–120 Zeichen\n..."` with `du`-imperative for any imperatives
    - EN: `"Format requirements:\n- verdict_snippet: 30–80 characters\n- when_to_use: 40–120 characters\n..."` plain imperative
  - List counts + per-item lengths formatted compactly: `"- hashtags: exactly 7, each ≤24 characters"`
  - Trailing reminder: `"Output ONLY valid JSON matching this contract."` (locale-specific phrasing)

   Sketch the helper signature + 1 example output per locale. Don't implement — that belongs in Spec 59.3.6 or Spec 60.1 depending on Marcel's later decision.

7. **Where does the spec for this live?** Three options for Marcel to decide post-audit:
  - **Option X**: Mini-spec 59.3.6 between 59.3.5 and 60.1 (clean separation, pure LLM-prompt concern)
  - **Option Y**: Folded into Spec 60.1 as a section (one spec covers Design + Prompt)
  - **Option Z**: Retroactive Section H added to 59.3.5 if still in early implementation

   Recommend ONE based on:
  - Timing (is 59.3.5 already deep into implementation?)
  - Coupling (does Constraint Injection genuinely need to land before Spec 60.1, or can 60.1 proceed independently?)
  - Spec hygiene (does it bloat 60.1 or stand cleanly on its own?)
